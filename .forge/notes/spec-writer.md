# Spec-writer addendum (this repo)

- **A guard states its attacker.** When the job adds or changes a guard (verify integrity, merge gating, scope or budget enforcement, daemon permissions, the dashboard's Host/Origin/token checks), add a `Threat model` paragraph to Approach. Name the attacker (usually the builder agent itself, a hostile checkout, or tracker/PR text), and list the bypasses the guard must handle, each backed by an AC whose test attempts it. Recurring ones here: git config, attributes or sparse checkout that reshape output; symlinks and type changes; option injection through values passed to git or `gh`; GitHub behaviour that acts sooner than the docs suggest (`gh pr merge --auto` merges at once when GitHub considers the PR mergeable). Evidence: 1-verify-reports-test-integrity-deleted, 15-auto-merge-must-not-bypass, daemon-supervisor-config-migration-and-roz1. (added 2026-10-13)
- **A live Claude Code session is never an AC's proof.** The builder can't count on a working `claude` login or a nested session, so the approver escalates such ACs as unproven. Give the AC a proof the builder can run: for a hook, pipe its JSON input to the hook script and assert the exit code and output; for the daemon or a headless run, put a stub `claude` on PATH in the test that records its argv and env; for plugin loading, `claude plugin validate . --strict`. Put the real-session check (`claude --plugin-dir .` firing the hook, one real `claude -p` run) under Infra & rollout as a human step after the PR opens, with the exact command. Evidence: engine-ts-toolchain-and-foundation-lkmo (AC11), engine-ts-surface-modules-and-vnos (AC17), daemon-per-job-with-detailed-alva (AC24). (added 2026-10-13)
