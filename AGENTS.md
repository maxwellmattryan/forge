# Working on Forge itself

This repo is **Forge**: a Claude Code plugin that is also its own marketplace. This guide is for changing Forge. To *use* it in another repo, run `/forge` there. Read `README.md` first; for depth see `docs/ARCHITECTURE.md` (layers, versioning, concurrency, security) and `docs/CONFIG.md` (every config key).

## Layout
- `bin/forge`: CLI entry (also on PATH while the plugin is enabled); it turns on the start-up cache, then imports `lib/cli.ts`
- `lib/`: the engine. `cli.ts` (routing only) + `commands/` (one module per command group, each with its `HELP` table; `help.ts` renders help and errors), `jobs.ts` (state + events), `step.ts` (`forge job step`: the pure decider of the next pipeline action) + `brief.ts` (the agent briefs it renders), `schema.ts` (versions, normalisers, migrations), `config.ts`, `config-fields.ts` (the settings allowlist and its validation) + `config-set.ts` (the one write path `forge config set` and `/api/config` share), `doctor.ts`, `worktree.ts`, `pr.ts`, `trackers/`, `stats.ts`, `evals.ts`, `retro.ts`, `usage.ts` + `pricing.json`, `server.ts`, `daemon.ts` (one supervised headless session) + `daemon-pool.ts` (the inbox and per-job sessions `forge dash` runs), `commands/daemon.ts` (`forge daemon status|log`), `detect.ts`, `yaml.ts`, `types.ts` (shared shapes)
- `dashboard/`: a Svelte 5 app in strict TypeScript. It has `index.html`, `style.css`, `svelte.config.mjs`, and `src/` with `main.ts`, `App.svelte`, `views/` (one per page), `components/`, `messages/` (the i18n catalogs; `en.json` is the source, read through `lib/i18n.ts` and the `$t` store in `lib/locale.ts`), and `lib/`. `lib/` holds plain-TS helpers and API types that `npm test` imports (`types.ts` mirrors `/api/*`), plus `*.svelte.ts` rune state. Vite builds it into the committed `dashboard/dist/` (`npm run build:dashboard`), and `forge dash` serves that. `dashboard/fonts/` holds the vendored OFL woff2 typefaces (`README.md` records their source).
- `hooks/`: plugin hooks (`hooks.json`, the no-AI-attribution PreToolUse hook, and the SessionStart `plugin-path.ts` hook that puts the plugin's `bin/` first on PATH)
- `skills/forge/`: the orchestrator (`SKILL.md`) and on-demand procedures (`reference/`)
- `agents/`: one prompt per role · `reviewers/`: lens checklists · `templates/`: files `init` seeds into `.forge/`
- `docs/`: user docs · `test/`: `node:test` suites
- `scripts/`: dev-only TypeScript run through npm, type-checked with the engine (`docs-commands.ts` is `npm run docs:commands`, `dev.ts` is `npm run dev`, `dev-claude.ts` is `npm run dev:claude`)
- `.github/workflows/ci.yml`: CI, the verify list below on every PR and push to `main`

## Where a change goes

| You're changing… | Touch | Also update |
|---|---|---|
| a CLI command or its JSON output | `lib/commands/<group>.ts` (+ the domain module); `lib/cli.ts` only for a new top-level command | the group's `HELP` table in `lib/commands/<group>.ts` (`CORE` in `lib/commands/help.ts` for what `lib/cli.ts` routes), then `npm run docs:commands` for README's CLI table; `docs/CLI.md` for a new exit, error code or env var; `skills/forge/SKILL.md` / `reference/*.md` if the orchestrator calls it; tests |
| `job.json`, an event or a config shape | `lib/schema.ts` (bump version, add a migration), `lib/config.ts` `defaults()`, and the shape in `lib/types.ts`; an `/api` shape also in `dashboard/src/lib/types.ts`, which `test/types-parity.ts` keeps equal | `docs/CONFIG.md`; `API_VERSION` if `/api/state` changes; a test that reads the old shape; for a new config key, a `lib/config-fields.ts` entry if the dashboard should show it (editable only under the rule in its header, otherwise locked with a reason; `test/config-set.test.ts` checks every entry against `defaults()` and docs/CONFIG.md) |
| a pipeline rule or an agent brief | `lib/step.ts` (add the rule ID to `RULES`) / `lib/brief.ts` | a row per rule in `test/step.test.ts`; SKILL.md states no rule `step` owns |
| orchestrator behaviour (the loop itself) | `skills/forge/SKILL.md` (keep it lean) or a `reference/*.md` loaded on demand | README "How it works" if user-visible |
| a role's behaviour | `agents/<role>.md` | its prompt hash changes (shown in the roster); CHANGELOG; measure with evals where possible |
| a review lens | `reviewers/<lens>.md` | `lib/detect.ts` suggestions + `reference/init.md` presets if it should be offered |
| tracker behaviour | `lib/trackers/{local,github}.ts`, contract in `lib/types.ts` (loader in `index.ts`), status mapping in `status.ts` (`status.mjs` re-exports it for older adapters) | `docs/TRACKERS.md` |
| the dashboard | `dashboard/src/**` (`views/`, `components/`, `lib/`), `dashboard/index.html`, `dashboard/style.css`, and endpoints in `lib/server.ts` | rebuild and commit `dashboard/dist/` (`npm run build:dashboard`); `API_VERSION` on shape changes; `dashboard/src/lib/types.ts` on any `/api/*` or SSE shape change; `npm run check:dashboard`. The server's allowlist is `dist/manifest.json`, so new modules need no server change |
| prices or model ids | `lib/pricing.json` (bump `asOf`) | take prices from Anthropic's current pricing, never from memory |
| CI | `.github/workflows/ci.yml` | the verify list in this file, in the same order; `test/ci-workflow.test.ts` |

Each dashboard page is one component in `dashboard/src/views/`. Put shared pieces in `components/` and logic you want tested in plain `src/lib/*.ts`, not in a growing view. Only one in-flight change may bump a version constant in `lib/schema.ts`: two branches that both migrate from the same version merge into a broken migration table.

## Rules
- **Zero runtime dependencies.** Node ≥ 22.18 built-ins only. The engine (`lib/`, `hooks/`, `bin/`) is strict TypeScript that Node runs by type stripping, type-checked by `npm run typecheck` with the exact-pinned `typescript` and `@types/node`. The only engine JavaScript is `bin/forge`, an extensionless entry that turns on the start-up cache and imports `lib/cli.ts`, and the `lib/trackers/status.mjs` re-export kept for custom tracker adapters. The dashboard's `src/` is strict TypeScript and Svelte 5 components (runes only), limited to erasable syntax, type-checked by svelte-check with the exact-pinned `typescript` devDependency, and never loaded at runtime. Build tools are exact-pinned devDependencies, the dashboard loads no external assets, and there is never a `prepare` or install script, so installing the plugin never builds or installs anything. No Python tooling: Node, or Rust if a native binary is ever justified.
- **`dashboard/style.css` is the source of truth for the dashboard's look** (the Smithy design system: its tokens and `@utility` classes; the icons live in `dashboard/src/lib/icons.ts`). New classes are `@utility`s there, colours come from the token variables, and fonts are vendored in `dashboard/fonts/`, never linked.
- **Commit the built dashboard.** Never hand-edit `dashboard/dist/`. Rebuild it in the same commit as its sources; `test/dashboard-dist.test.ts` fails otherwise.
- **The CLI is the only writer of state.** New state means a new CLI command, never "the agent edits job.json".
- **Version every shape change.** Bump the constant in `lib/schema.ts`, add a migration keyed by the old version, keep normalisers tolerant, and bump `API_VERSION` if `/api/state` changes. Never break reading older jobs.
- **Keep the orchestrator's context small.** New commands return compact JSON. Large outputs go to files in the job dir, and the CLI returns their paths.
- **Prompts are product.** Agent prompts and checklists are short, imperative, and end with a one-line reply contract. Prefer measuring a prompt or policy change (evals, `forge stats`) over arguing about it.
- **Never add AI attribution** to commits, PRs, issues or comments in this repo either. The hook in `hooks/` enforces it while the plugin is enabled.
- **Preserve the security posture** (ARCHITECTURE.md "Untrusted input" and "Dashboard security"): never adopt fork PRs; the server answers loopback Hosts only; POSTs need the token, a matching Origin and JSON; tracker and PR text is fenced as data, and agents are told so. Anything new that ingests outside text follows the same pattern.
- Comments explain why, not what.
- Keep `README.md`, `docs/*.md` and `skills/forge/**` in sync with CLI behaviour.

## Verify before claiming it works
```bash
npm ci                                  # once: the dashboard's build toolchain (devDependencies only)
npm run typecheck                       # tsc --noEmit: the engine (tsconfig.json) and its tests (test/tsconfig.json)
npm run check:dashboard                 # svelte-check: strict TS over dashboard/src (.ts and .svelte), warnings fail
npm run build:dashboard && git status --porcelain -- dashboard/dist   # must print nothing
node --test "test/*.test.ts"            # not `node --test test/`: Node 22 treats a directory arg as a module
for f in bin/forge lib/trackers/status.mjs dashboard/*.mjs; do node --check "$f"; done   # the JS files tsc does not check
claude plugin validate . --strict
```
- **CI runs this list.** `.github/workflows/ci.yml` runs these commands as named steps, in this order, on every PR and every push to `main`. It runs them on Node 22.18.0 (`.nvmrc`) and the latest Node 24, on Ubuntu and macOS, each cell split in two by a `shard` axis: the test step there is `node --test --test-shard="$TEST_SHARD" "test/*.test.ts"`, with `TEST_SHARD` set from the matrix (`1/2`, `2/2`), so each half-suite runs on its own runner. That is the one command that differs from the list above. For the last step it installs `@anthropic-ai/claude-code@2.1.299` from npm. That pin is the CLI version maintainers run locally, so CI validates by the same rules as a local run, even when the release is only days old (the action pins wait two weeks). Bump it in the workflow and here together. `claude plugin validate` needs no login, so CI runs it rather than skipping it. A separate `audit` job runs `npm audit --omit=dev`, which blocks, and a report-only `npm audit`. Change this list and the workflow together: `test/ci-workflow.test.ts` fails when they differ. The same test holds the workflow to allowlists of triggers, keys, `env`, actions and `${{ }}` expressions, and pins the job names, the matrix, the action inputs, every `run` (the stale-dist script and the audit steps included) and the single CLI install exactly, so changing any of those means editing the test in the same diff.
- **Forge needs Node ≥ 22.18, for the plugin and the tests:** type stripping is on by default there and prints no warning. Check changes on 22.18 itself (`~/.nvm/versions/node/v22.18.0`; `nvm use` reads `.nvmrc`), not only on a newer 22.x.
- **Never point the CLI at a real repo's `.forge/` while developing.** Use a scratch git repo in a temp dir, or set `FORGE_ROOT=<scratch>` (as `test/helpers.ts` does). Delete scratch repos *and* their `<repo>.worktrees` siblings afterwards.
- **Dashboard:** in a scratch repo, seed a job or two (`forge job new`, `forge job set`), then run `FORGE_ROOT=<scratch> npm run dev` from this checkout: it serves your sources and rebuilds on save (reload to see an edit; one Ctrl-C stops it). Open it in a browser. Check the forge, ash and temper themes, a phone-width viewport, the job drawer, and that markdown containing `<script>` / `<img onerror>` renders escaped. Finally run `npm run build:dashboard` and commit `dist/` with the sources (`forge dash` serves `dashboard/dist/`, not the sources).
- **The plugin inside Claude Code:** `claude --plugin-dir <this checkout>` loads it without installing. `claude plugin details forge` shows the component inventory and projected token cost, which is useful when trimming prompts.
- **GitHub code paths** (`pr.ts`, `trackers/github.ts`): read-only checks against real repos are fine. Anything that writes (PRs, labels, Project fields, comments, issues) goes only to a throwaway repo the maintainer approves.

## Gotchas already paid for
- **Tailwind v4**: `@apply` accepts only built-in utilities or classes declared with `@utility`; plain `.class {}` rules can't be `@apply`'d. Tailwind only sees the `@source` files in `dashboard/style.css`: build class names from whole literals, never `bg-${tone}`; no `class:` directives, and no `<style>` blocks in components. Upgrading means bumping the exact devDependency versions and rebuilding.
- **All TS (engine and dashboard) runs through Node's type stripping, which ignores tsconfig:** write relative imports with their real extension (`.ts`; `.mjs` only for the dashboard's build scripts and the `status.mjs` re-export), bring types in with `import type`, and use no `enum`, `namespace` or parameter properties (`erasableSyntaxOnly` enforces it).
- **Fast tests:** `test/helpers.ts` runs configured commands without a login profile (`$SHELL` is `test/fixtures/bin/no-login-shell`) and keeps a compile cache in `node_modules/.cache/forge/compile-cache`. It also puts `test/fixtures/strip-cache.mjs` in `NODE_OPTIONS`, which keeps type-stripped modules in `node_modules/.cache/forge/strip-cache`: Node 22 never caches stripped TypeScript, and without the hook every CLI start costs about 150 ms there instead of 40 ms. The suite is CPU-bound, so raising `--test-concurrency` above the default doesn't help; cutting what each test spawns does. For CLI-heavy tests use `forgeAsync` and put independent tests in `describe(…, { concurrency: 4 })` (at most 4: node already runs about 9 files at once), never beside a test that changes `process.env` or `process.cwd()`; poll with `waitFor` instead of sleeping; and copy a `repoTemplate` instead of re-initialising a repo per test. A long file that sorts late in `test/` sets the suite's wall time, so split one rather than letting it grow.
- **Start-up cache:** `bin/forge` keeps V8's code cache, and on Node 22 the stripped `lib/` modules, in `.cache/` at the plugin root, beside the code it caches (ARCHITECTURE.md "Start-up cache"; it writes its own `.gitignore`). Never move it to a shared or temp dir: a sandboxed agent could plant a module there that an unsandboxed start then runs. Entries are keyed by content, so an edit is never served stale. Its load hook stays plain JS in `bin/forge`: anything in `lib/` would load the stripper it exists to skip. `NODE_DISABLE_COMPILE_CACHE=1` rules it out when a start behaves oddly, and `test/startup-cache.test.ts` holds the directory's ownership and permission checks.
- **Typecheck caches:** `npm run typecheck` keeps tsc build info in `node_modules/.cache/forge/` and `npm run check:dashboard` keeps svelte-check's incremental cache in `dashboard/.svelte-check/` (gitignored; thrown away when older than `package-lock.json` or `dashboard/svelte.config.mjs`). Delete both if a check behaves oddly.
- **Engine TS:** class fields are `declare`d (a plain field becomes a runtime field and changes `Object.keys`); unions with a runtime list derive from its `as const` (`(typeof STAGES)[number]`); shared shapes live in `lib/types.ts`; tests are checked loosely (`test/tsconfig.json`) and change only their extension and references to renamed modules; never install Forge under `node_modules`, where Node refuses to strip types.
- **Dashboard text comes from `dashboard/src/messages/en.json`.** Components write `$t('literal.key')` (import `t` from `lib/locale.ts`); `test/dashboard-i18n.test.ts` fails on hard-coded prose in markup or text attributes, on a non-literal or unknown key, and on an unused message. Don't name a loop variable `t`: it shadows the store.
- **Text never sits on the grain.** Put dashboard text, controls and components on a `plate` (not `plate open`, which is a see-through container), `plain`, `solid` or `chrome` surface; the Grain pref (`data-grain`) only hides the texture, never a surface; `test/dashboard-shell.test.ts` › "text never sits on the bare ground" enforces it.
- **Escape everything the dashboard renders.** Svelte's `{…}` escapes, so never call `esc()` in a component. `{@html}` is allowed only on `md()`, `budgetChip`/`budgetCell`/`budgetPanel` and `screenshotsPanel`, whose output is escape-first, and `test/dashboard-svelte.test.ts` enforces it. Session log lines are untrusted: supervisor, stderr, tool input and result lines render as text; assistant/thinking prose and subagent prompts and reports render only through `md()`. Don't add a markdown library or any `innerHTML`. Job HTML (mockups) renders only in the sandboxed iframe (`/raw`).
- **Tests can't import `.svelte` or `.svelte.ts`** (runes need the compiler). Keep logic you want tested in plain `src/lib/*.ts`.
- **Claude Code transcripts** (`~/.claude/projects/*/<session>/subagents/agent-<id>.jsonl`) log each content block as its own line sharing one `message.id`. Their `usage.output_tokens` is the stream's opening snapshot, not the final count, which is why `usage.ts` dedupes by message id, counts tools by block id, and estimates output from content.
- **Plugin runtime**: `${CLAUDE_PLUGIN_ROOT}` and `${CLAUDE_SESSION_ID}` are substituted in skill/agent *markdown*, not exported to the shell. Claude Code appends `bin/` to the end of PATH; the SessionStart hook puts it first for every Bash command. Plugin agents are invoked as `forge:<role>`.
- **CLI output**: string results print raw (e.g. `forge worktree path`), everything else prints compact JSON.
- **`--field` values** are not comma-split, because JSON arrays contain commas. Other list flags are.
- **Local tracker refs** are title slugs, and the job id for a non-numeric ref is the ref itself. Numeric (GitHub) refs become `<n>-<slug>`.
- **Worktrees live outside the repo** on purpose: a nested worktree inside a Cargo workspace breaks Cargo, and bundlers and watchers pick up the copies. Don't "simplify" this to an in-repo `.worktrees/`.

## Publishing
This repo is public. Use the GitHub no-reply commit email, and never commit hostnames, home paths, tokens or real job state (`.forge/` is tracked here, like in any repo that uses Forge, and its own `.gitignore` excludes `jobs/`, `locks/` and `runtime/`). Bump `version` in `package.json` and `.claude-plugin/plugin.json` together (they must match), and add a `CHANGELOG.md` entry. Forge jobs on this repo leave `CHANGELOG.md` and the version alone; the release commit at the end of a wave adds them.
