# Working on Forge itself

This repo is **Forge**: a Claude Code plugin that is also its own marketplace. This guide is for changing Forge. To *use* it in another repo, run `/forge` there. Read `README.md` first; for depth see `docs/ARCHITECTURE.md` (layers, versioning, concurrency, security), `docs/CONFIG.md` (every config key) and [`docs/GLOSSARY.md`](docs/GLOSSARY.md) (the words docs, prompts and dashboard copy use).

## Essentials
Obey these on every change; each links the section with the detail.
- **Zero runtime dependencies**: Node ≥ 22.18 built-ins only; build tools are exact-pinned devDependencies ([Rules](#rules)).
- **The CLI is the only writer of state**: new state means a new CLI command, never an agent editing `job.json` ([Rules](#rules)).
- **Version every shape change**: bump the constant in `lib/schema.ts` with a migration keyed by the old version, and `API_VERSION` when `/api/state` changes; only one in-flight change may bump each constant ([Rules](#rules), [Where a change goes](#where-a-change-goes)).
- **Never add AI attribution** to commits, PRs, issues or comments ([Rules](#rules)).
- **Preserve the security posture**: never adopt fork PRs; the server answers loopback Hosts only; POSTs need the token, a matching Origin and JSON; tracker and PR text is fenced as data ([Rules](#rules)).
- **Work on `develop`**: branch from it and open PRs into it; `main` takes only the main update and hotfixes ([Publishing](#publishing)).
- **Never commit `dashboard/dist/`** or hand-edit it: it is a gitignored build; run `npm run build:dashboard` to check it. CI builds it for the main update into `main` ([Rules](#rules)).
- **Escape everything the dashboard renders**: `{@html}` only on the escape-first helpers ([dashboard/AGENTS.md](dashboard/AGENTS.md)).
- **Touching `dashboard/`?** Read [dashboard/AGENTS.md](dashboard/AGENTS.md) first: its look, i18n, Tailwind and escaping rules.
- **Never point the CLI at a real repo's `.forge/`** while developing: use a scratch repo or `FORGE_ROOT` ([Verify](#verify-before-claiming-it-works)).
- **Jobs leave `CHANGELOG.md` and versions alone**: the release commit adds them ([Publishing](#publishing)).
- **Use the glossary's words** in docs, prompts and dashboard copy ([`docs/GLOSSARY.md`](docs/GLOSSARY.md)).
- **Keep docs in sync with CLI behaviour**: `README.md`, `docs/*.md` and `skills/forge/**` ([Rules](#rules)).
- **Run the verify list before claiming it works** ([Verify](#verify-before-claiming-it-works)).

The rest of this file is reference: read a section when your change touches it.

## Layout
- `bin/forge`: CLI entry (also on PATH while the plugin is enabled); it turns on the start-up cache, then imports `lib/cli.ts`
- `lib/`: the engine. `cli.ts` (routing only) + `commands/` (one module per command group, each with its `HELP` table; `help.ts` renders help and errors), `jobs.ts` (state + events, and the job lease: claim, renew, expire, the epoch fence), `step.ts` (re-exports `step/`) + `step/` (`forge job step`: the pure decider of the next pipeline action; `order.ts` walks the tables (`step()`, `TABLES`), `rules.ts` the rule IDs and row types, `input.ts` the only reader of disk and clock (`loadStepInput`), `facts.ts` state helpers and the facts read by event position, `panel.ts` review panels, `actions.ts` the actions and `shellLine`, `generic.ts` the shared per-role rows, `gates.ts` the gate tables and gate tells, `global.ts` the global and kind tables, `stages/` one table per stage) + `brief.ts` (the agent briefs it renders), `schema.ts` (versions, normalisers, migrations), `config.ts`, `config-fields.ts` (the settings allowlist and its validation) + `config-set.ts` (the one write path `forge config set` and `/api/config` share), `doctor.ts`, `worktree.ts` + `job-command.ts` (the environment, placeholders and shell of a configured command Forge runs for a job), `pr.ts`, `trackers/`, `stats.ts`, `evals.ts`, `retro.ts`, `usage.ts` + `pricing.ts` + `pricing.json`, `server.ts`, `daemon.ts` (one supervised headless session) + `daemon-files.ts` (the session records and logs, opened without following links) + `session-agents.ts` (which agents keep a job session) + `daemon-pool.ts` (the inbox and per-job sessions `forge dash` runs) + `daemon-owner.ts` (what a daemon session may not do, and the session ids each dash record names) + `reconcile.ts` (the reconciler: which running jobs nothing drives, one resume each, then escalation; `progressMark`), `commands/daemon.ts` (`forge daemon status|log`), `verifiers.ts` (repo-local yes/no checks between verify and the panel) + `commands/verifiers.ts` (`forge verifiers list|run|record`), `backing.ts` (backing services through the Docker CLI) + `backing-config.ts` (their validation) + `commands/backing.ts` (`forge backing up|down|status`), `ports.ts` (per-component job ports) + `endpoints.ts` (the placeholders and env they become) + `endpoints-config.ts` (their validation, kept apart for the same import cycle as `backing-config.ts`), `detect.ts`, `yaml.ts`, `types.ts` (shared shapes)
- `dashboard/`: a Svelte 5 app in strict TypeScript. It has `index.html`, `style.css`, `svelte.config.mjs`, and `src/` with `main.ts`, `App.svelte`, `views/` (one per page), `components/`, `messages/` (the i18n catalogs; `en.json` is the source, read through `lib/i18n.ts` and the `$t` store in `lib/locale.ts`), and `lib/`. `lib/` holds plain-TS helpers and API types that `npm test` imports (`types.ts` mirrors `/api/*`), plus `*.svelte.ts` rune state. Vite builds it into `dashboard/dist/` (`npm run build:dashboard`), and `forge dash` serves that. `dist/` is gitignored: CI builds it for the main update that `npm run release` pushes to `main` (hotfixes on `main` carry their own), so plugin installs, which follow `main`, never build. `dashboard/fonts/` holds the vendored OFL woff2 typefaces (`README.md` records their source).
- `hooks/`: plugin hooks (`hooks.json`, the no-AI-attribution PreToolUse hook, and the SessionStart `plugin-path.ts` hook that puts the plugin's `bin/` first on PATH)
- `skills/forge/`: the orchestrator (`SKILL.md`) and on-demand procedures (`reference/`)
- `agents/`: one prompt per role · `reviewers/`: lens checklists · `templates/`: files `init` seeds into `.forge/` (`templates/release-gate/`: the seeded CI check, plain JS for consumer repos that the tests run, outside the engine's TypeScript)
- `docs/`: user docs · `test/`: `node:test` suites; unit files in `test/`, `test/integration/<cli|server|pool>/`, `test/e2e/<flow>/`, and shared helpers in `test/support/`, imported through `test/helpers.ts` ([docs/TESTING.md › Layout](docs/TESTING.md#layout))
- `scripts/`: dev-only TypeScript run through npm, type-checked with the engine (`docs-commands.ts` is `npm run docs:commands`, `dev.ts` is `npm run dev`, `dev-claude.ts` is `npm run dev:claude`, `release.ts` is `npm run release`, `release-check.ts` is `npm run release:check`, `release-plan.ts` is what `release.yml` runs to detect a release and write its notes, `coverage.ts` is `npm run coverage` (docs/TESTING.md › Coverage), `test-times.ts` is the reporter behind `npm run test:times` (each test file's time, slowest first), and `main-update.ts` builds and checks the main-update commit `release.ts` pushes)
- `.github/workflows/ci.yml`: CI, the verify list below on every PR, every push to `develop` and `main`, and on dispatch
- `.github/workflows/main-update.yml`: on a push to `develop`, builds the dashboard with a read-only token and uploads it as the artifact `npm run release` puts on `main` (docs/RELEASES.md)
- `.github/workflows/release.yml`: on a push to `main` that changes the version, runs all of `ci.yml`, then tags `v<version>` and publishes the GitHub Release (docs/RELEASES.md)

## Where a change goes

| You're changing… | Touch | Also update |
|---|---|---|
| a CLI command or its JSON output | `lib/commands/<group>.ts` (+ the domain module); `lib/cli.ts` only for a new top-level command | the group's `HELP` table in `lib/commands/<group>.ts` (`CORE` in `lib/commands/help.ts` for what `lib/cli.ts` routes), then `npm run docs:commands` for README's CLI table; `docs/CLI.md` for a new exit, error code or env var; `skills/forge/SKILL.md` / `reference/*.md` if the orchestrator calls it; tests |
| `job.json`, an event or a config shape | `lib/schema.ts` (bump version, add a migration), `lib/config.ts` `defaults()`, and the shape in `lib/types.ts`; an `/api` shape also in `dashboard/src/lib/types.ts`, which `test/types-parity.ts` keeps equal | `docs/CONFIG.md`; `API_VERSION` if `/api/state` changes; a row in the migration table in `test/schema.test.ts`; for a new config key, a `lib/config-fields.ts` entry if the dashboard should show it (editable only under the rule in its header, otherwise locked with a reason; `test/config-set.test.ts` checks every entry against `defaults()` and docs/CONFIG.md) |
| a pipeline rule or an agent brief | `lib/step/stages/<stage>.ts` or `lib/step/gates.ts` (add a table row, and its ID to `RULES` in `lib/step/rules.ts`) / `lib/brief.ts` | a row per transition in `test/step-rows.ts` (run by `test/step.test.ts`); update the pinned order in `test/step-tables.test.ts`; SKILL.md states no rule `step` owns |
| orchestrator behaviour (the loop itself) | `skills/forge/SKILL.md` (keep it lean) or a `reference/*.md` loaded on demand | README "How it works" if user-visible |
| a role's behaviour | `agents/<role>.md` | its prompt hash changes (shown in the roster); CHANGELOG; measure with evals where possible |
| a review lens | `reviewers/<lens>.md` | `lib/detect.ts` suggestions + `reference/init.md` presets if it should be offered |
| tracker behaviour | `lib/trackers/{local,github}.ts`, contract in `lib/types.ts` (loader in `index.ts`), status mapping in `status.ts` (`status.mjs` re-exports it for older adapters) | `docs/TRACKERS.md` |
| the dashboard | `dashboard/src/**` (`views/`, `components/`, `lib/`), `dashboard/index.html`, `dashboard/style.css`, and endpoints in `lib/server.ts` | rebuild `dashboard/dist/` (`npm run build:dashboard`) but never commit it; `API_VERSION` on shape changes; `dashboard/src/lib/types.ts` on any `/api/*` or SSE shape change; `npm run check:dashboard`. The server's allowlist is `dist/manifest.json`, so new modules need no server change |
| prices or model ids | `lib/pricing.json` (bump `asOf`) | take prices from Anthropic's current pricing, never from memory |
| CI | `.github/workflows/ci.yml` | the verify list in this file, in the same order; [docs/CI.md](docs/CI.md); `test/ci-workflow.test.ts` |
| the release pipeline | `.github/workflows/release.yml`, `.github/workflows/main-update.yml`, `scripts/release*.ts`, `scripts/main-update.ts` | `test/release.test.ts`, `test/release-workflow.test.ts`, `test/main-update.test.ts`, `test/main-update-workflow.test.ts`, docs/RELEASES.md |

Only one in-flight change may bump a version constant in `lib/schema.ts`: two branches that both migrate from the same version merge into a broken migration table.

## Rules
- **Zero runtime dependencies.** Node ≥ 22.18 built-ins only. The engine (`lib/`, `hooks/`, `bin/`) is strict TypeScript that Node runs by type stripping, type-checked by `npm run typecheck` with the exact-pinned `typescript` and `@types/node`. The only engine JavaScript is `bin/forge`, an extensionless entry that turns on the start-up cache and imports `lib/cli.ts`, and the `lib/trackers/status.mjs` re-export kept for custom tracker adapters. The dashboard's `src/` is strict TypeScript and Svelte 5 components (runes only), limited to erasable syntax, type-checked by svelte-check with the exact-pinned `typescript` devDependency, and never loaded at runtime. Build tools are exact-pinned devDependencies, the dashboard loads no external assets, and there is never a `prepare` or install script, so installing the plugin never builds or installs anything. No Python tooling: Node, or Rust if a native binary is ever justified.
- **`dashboard/style.css` is the source of truth for the dashboard's look** ([dashboard/AGENTS.md](dashboard/AGENTS.md)).
- **Never commit the built dashboard.** `dashboard/dist/` is gitignored and never hand-edited. Build it with `npm run build:dashboard` before the tests: the ones that read it skip without it (`test/dist.ts`), and CI sets `FORGE_REQUIRE_DIST=1` so there they run. CI builds it for the main update (`.github/workflows/main-update.yml`), which `npm run release` pushes to `main`; only a hotfix branch from `main` rebuilds and commits it by hand ([docs/RELEASES.md](docs/RELEASES.md#releasing)).
- **The CLI is the only writer of state.** New state means a new CLI command, never "the agent edits job.json".
- **Version every shape change.** Bump the constant in `lib/schema.ts`, add a migration keyed by the old version, keep normalisers tolerant, and bump `API_VERSION` if `/api/state` changes. Never break reading older jobs.
- **No import cycles in `lib/`, and only `lib/commands/` and `lib/cli.ts` import `lib/commands/`** (`test/lib-imports.test.ts`). When a low-level module needs something above it, move the shared piece to a leaf, or take it as a parameter or a hook (`onTransition` in `jobs.ts`).
- **Keep the orchestrator's context small.** New commands return compact JSON. Large outputs go to files in the job dir, and the CLI returns their paths.
- **Prompts are product.** Agent prompts and checklists are short, imperative, and end with a one-line reply contract. Prefer measuring a prompt or policy change (evals, `forge stats`) over arguing about it.
- **Never add AI attribution** to commits, PRs, issues or comments in this repo either. The hook in `hooks/` enforces it while the plugin is enabled.
- **Preserve the security posture** (ARCHITECTURE.md "Untrusted input" and "Dashboard security"): never adopt fork PRs; the server answers loopback Hosts only; POSTs need the token, a matching Origin and JSON; tracker and PR text is fenced as data, and agents are told so. Anything new that ingests outside text follows the same pattern.
- Comments explain why, not what.
- **Use the glossary's words.** New docs, prompts and dashboard copy use the terms in `docs/GLOSSARY.md`; a new term goes there first.
- Keep `README.md`, `docs/*.md` and `skills/forge/**` in sync with CLI behaviour.

## Verify before claiming it works
```bash
npm ci                                  # once: the dashboard's build toolchain (devDependencies only)
npm run typecheck                       # tsc --noEmit: the engine (tsconfig.json) and its tests (test/tsconfig.json)
npm run check:dashboard                 # svelte-check: strict TS over dashboard/src (.ts and .svelte), warnings fail
npm run build:dashboard                 # the build's own tests skip without it; it is gitignored, never commit it
node --test "test/**/*.test.ts"         # not `node --test test/`: Node 22 treats a directory arg as a module
for f in bin/forge lib/trackers/status.mjs dashboard/*.mjs; do node --check "$f"; done   # the JS files tsc does not check
claude plugin validate . --strict
```
- **CI runs this list.** `.github/workflows/ci.yml` runs these commands as named steps, in this order, on every PR and push to `main`, with the tests sharded and the CLI pinned at `@anthropic-ai/claude-code@2.1.299`; [docs/CI.md](docs/CI.md) covers the matrix (Ubuntu only), the `audit` and `release check` jobs, and what `test/ci-workflow.test.ts` pins. Change this list and the workflow together.
- **Forge needs Node ≥ 22.18, for the plugin and the tests:** type stripping is on by default there and prints no warning. Check changes on 22.18 itself (`~/.nvm/versions/node/v22.18.0`; `nvm use` reads `.nvmrc`), not only on a newer 22.x.
- **Never point the CLI at a real repo's `.forge/` while developing.** Use a scratch git repo in a temp dir, or set `FORGE_ROOT=<scratch>` (as `test/helpers.ts` does). Delete scratch repos *and* their `<repo>.worktrees` siblings afterwards.
- **Dashboard:** seed a scratch repo and run `FORGE_ROOT=<scratch> npm run dev`; the full check is in [dashboard/AGENTS.md](dashboard/AGENTS.md) › Verify.
- **The plugin inside Claude Code:** `claude --plugin-dir <this checkout>` loads it without installing. `claude plugin details forge` shows the component inventory and projected token cost, which is useful when trimming prompts.
- **GitHub code paths** (`pr.ts`, `trackers/github.ts`): read-only checks against real repos are fine. Anything that writes (PRs, labels, GitHub Project fields, comments, issues) goes only to a throwaway repo the maintainer approves.

## Gotchas already paid for
- **All TS (engine and dashboard) runs through Node's type stripping, which ignores tsconfig:** write relative imports with their real extension (`.ts`; `.mjs` only for the dashboard's build scripts and the `status.mjs` re-export), bring types in with `import type`, and use no `enum`, `namespace` or parameter properties (`erasableSyntaxOnly` enforces it).
- **Fast tests:** `test/helpers.ts` runs configured commands without a login profile (`$SHELL` is `test/fixtures/bin/no-login-shell`) and keeps a compile cache in `node_modules/.cache/forge/compile-cache`. It also puts `test/fixtures/strip-cache.mjs` in `NODE_OPTIONS`, which keeps type-stripped modules in `node_modules/.cache/forge/strip-cache`: Node 22 never caches stripped TypeScript, and without the hook every CLI start costs about 150 ms there instead of 40 ms. The suite is CPU-bound, so raising `--test-concurrency` above the default doesn't help; cutting what each test spawns does. Check each case of a validation or refusal table in-process (the domain function or `forgeInProcess`) and keep one spawned-CLI test per command. For CLI-heavy tests use `forgeAsync` and put independent tests in `describe(…, { concurrency: 4 })` (at most 4: node already runs about 9 files at once), never beside a test that changes `process.env` or `process.cwd()`; poll with `waitFor` instead of sleeping; and copy a `repoTemplate` instead of re-initialising a repo per test. A long file that sorts late in `test/` sets the suite's wall time, so split one rather than letting it grow.
- **Tests per behaviour:** a job adds a test only for behaviour no test covers, extending the nearest test or table first; tests check public functions or the CLI's JSON, never one job's output, prompt or doc wording, markup or class names. Source-text tests are allowed only for the invariants in [docs/TESTING.md](docs/TESTING.md).
- **Start-up cache:** `bin/forge` keeps V8's code cache, and on Node 22 the stripped `lib/` modules, in `.cache/` at the plugin root, beside the code it caches (ARCHITECTURE.md "Start-up cache"; it writes its own `.gitignore`). Never move it to a shared or temp dir: a sandboxed agent could plant a module there that an unsandboxed start then runs. Entries are keyed by content, so an edit is never served stale. Its load hook stays plain JS in `bin/forge`: anything in `lib/` would load the stripper it exists to skip. `NODE_DISABLE_COMPILE_CACHE=1` rules it out when a start behaves oddly, and `test/startup-cache.test.ts` holds the directory's ownership and permission checks.
- **Typecheck caches:** `npm run typecheck` keeps tsc build info in `node_modules/.cache/forge/` and `npm run check:dashboard` keeps svelte-check's incremental cache in `dashboard/.svelte-check/` (gitignored; thrown away when older than `package-lock.json` or `dashboard/svelte.config.mjs`). Delete both if a check behaves oddly.
- **Engine TS:** class fields are `declare`d (a plain field becomes a runtime field and changes `Object.keys`); unions with a runtime list derive from its `as const` (`(typeof STAGES)[number]`); shared shapes live in `lib/types.ts`; tests are checked loosely (`test/tsconfig.json`) and change only their extension and references to renamed modules; never install Forge under `node_modules`, where Node refuses to strip types.
- **Claude Code transcripts** (`~/.claude/projects/*/<session>/subagents/agent-<id>.jsonl`) log each content block as its own line sharing one `message.id`. Their `usage.output_tokens` is the stream's opening snapshot, not the final count, which is why `usage.ts` dedupes by message id, counts tools by block id, and estimates output from content.
- **Plugin runtime**: `${CLAUDE_PLUGIN_ROOT}` and `${CLAUDE_SESSION_ID}` are substituted in skill/agent *markdown*, not exported to the shell. Claude Code appends `bin/` to the end of PATH; the SessionStart hook puts it first for every Bash command. Plugin agents are invoked as `forge:<role>`.
- **CLI output**: string results print raw (e.g. `forge worktree path`), everything else prints compact JSON.
- **`--field` values** are not comma-split, because JSON arrays contain commas. Other list flags are.
- **Issue refs** live in `job.issues` (`lib/issue-ref.ts`): GitHub refs are stored qualified (`owner/repo#12`), local refs are title slugs, custom refs are the adapter's own. Only `nativeRef` output reaches a tracker call. Job ids: this repo's GitHub issue gives `<n>-<slug>`, a foreign `owner/repo#n` gives `repo-<n>-<slug>`, any other ref is the ref itself slugified.
- **Worktrees live outside the repo** on purpose: a nested worktree inside a Cargo workspace breaks Cargo, and bundlers and watchers pick up the copies. Don't "simplify" this to an in-repo `.worktrees/`.

## Publishing
**Branches.** `develop` is the working branch: every job, feature and fix branches from it and merges into it, and Forge's `git.base` here is `develop`. `main` is what plugin installs follow, so it takes only the main update (`npm run release` pushes it: develop's tree plus the CI-built `dashboard/dist/`) and hotfixes (a branch from `main` with a rebuilt `dist/`, then ported to `develop` in a PR without `dist/`; never merge `main` into `develop`). Never target `main` with a job ([docs/RELEASES.md](docs/RELEASES.md#releasing)).

This repo is public. Use the GitHub no-reply commit email, and never commit hostnames, home paths, tokens or real job state (`.forge/` is tracked here, like in any repo that uses Forge, and its own `.gitignore` excludes `jobs/`, `locks/` and `runtime/`). Bump `version` in `package.json` and `.claude-plugin/plugin.json` together (they must match), and add a `CHANGELOG.md` entry. Forge jobs on this repo leave `CHANGELOG.md` and the version alone; the release commit at the end of a wave adds them. `npm run release -- patch|minor|X.Y.Z` makes that commit on `develop` (you edit the drafted notes; it runs `npm run release:check -- --dist absent`), waits for CI, pushes the main update, and `release.yml` then tags `v<version>` and publishes the GitHub Release ([docs/RELEASES.md](docs/RELEASES.md)).
