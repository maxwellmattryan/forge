## 0.18.0

- **Behaviour change: protected paths enforced by the CLI.** The new `policy.protectedPaths` key is a list of rules, each with `paths` globs, an `action` (`refuse` or `escalate`) and a `reason`. A repo without a `policy` key gets seven defaults: CI configuration, `Dockerfile*` and `*.tf`, `**/migrations/**`, the npm, yarn, pnpm and Cargo lockfiles, and `**/.env*` escalate; `**/*.pem` and Forge's own policy files (`.forge/config.yml`, `.forge/secrets-allow.txt`, `.forge/trackers/**`) are refused. An explicit `policy: { protectedPaths: [] }` turns it off, and an invalid policy fails closed with `config_invalid`. `forge git add|commit` checks a preview index before writing anything and exits 1 with the new error code `protected_path` on a refused path; `forge verify` runs a new `protected` step after `secrets`, and `forge pr open` re-checks the branch, refuses unapproved escalate paths even with `--force`, and pushes the exact sha it checked. An escalate hit parks the job on a human (new step rule `PP1`, with `PP2` sending a refused path back to build), and the approval is tied to the content it saw; every decision is a `protected-path` event. Under a non-empty policy, `forge pr merge` never queues GitHub's auto-merge, so a PR with pending CI waits for `forge sync` or `forge pr merge`, and a PR whose head is not the sha `forge pr open` pushed (an adopted PR, or one updated with GitHub's Update branch) needs `forge pr open` again or `--now`. The board card and drawer show a `Protected` chip, and the Needs-you card lists each path with its reason and a View diff button.
- **Verifiers.** A verifier is a repo-local yes/no question in `.forge/verifiers/<name>.md`, scoped to file globs. After a passing `forge verify` and before the review panel (step rules `VF1`–`VF3`), a `forge:verifier` agent (`runtime.models.verifier`, default `haiku`) answers each selected question against only the diff hunks of the files it matches. A `mode: block` failure whose severity is in `review.blockOn` counts as a failed verify attempt and sends the builder back without spawning the panel; `mode: warn` only annotates, so a new check can prove itself first. New `forge verifiers list|run|record`, a Verifiers column in the drawer's verdict matrix, and `verifiers.<name>` runs, fails, blocks and hit rate in `forge stats`. Verifiers load from the main checkout only, and once one exists, editing `.forge/verifiers/` stops a running daemon until a human restarts it, like `.forge/trackers/`. Nothing changes until a repo adds a verifier file; see `docs/VERIFIERS.md`.
- **Deterministic review panel.** A `review.panel` entry can carry `paths` globs. Once per round, after verify and before any reviewer starts (new step rule `RV9`), the new `forge job panel <id>` recomputes the lens set from the committed branch diff and logs a `panel` event with a reason for every lens, so a build that strays into server, tracker or CI files gets the security lens even when the spec never named them. `when` stays as a prose hint for the spec writer, `forge init detect` suggests `paths` for the design, security, infra and docs lenses, and this repo's config now uses them. `forge job set --field kind=retro|eval` is refused, because it could pin the panel at `code`/`docs` mid-build.
- **Readiness triage.** `forge next` no longer takes an unclear issue as it is. `/forge next` (and the inbox session's `next`) first runs triage: `forge tracker triage [--limit N] [--all]` writes a fenced batch of ready items, a haiku `forge:triage` agent judges each for a clear outcome, acceptance criteria or a reproduction, a bounded scope, and no duplicate of an active job or open PR, and `forge tracker triage --apply <batch>` validates the verdicts. An item that fails is marked needs-info (a `[?]` mark and one `Needs info:` line in the local backlog, the `forge:needs-info` label on GitHub) and gets one templated comment naming the missing pieces, and `forge next` skips it until it changes. A content-hash cache means an unchanged item is never judged, commented on or marked twice, and a triage failure never blocks `next`. `/forge triage [n]` runs it on its own, the Backlog gains a Readiness column, and custom tracker adapters get an optional `setNeedsInfo` hook. Triage posts public comments from your GitHub account and has no config switch.
- **Notifications.** A new `notify` block posts a fixed-shape message to `notify.webhooks` (generic `json` or Slack `slack` format, each with an optional `events` list) and/or runs `notify.command` when a job hits a human gate, a PR opens or merges, a job fails, the daemon stops on its own, a budget is exceeded or a secret is found. Delivery runs in a detached process with a 5 s timeout and one retry and never blocks the pipeline. Messages carry only fixed reason text and the sanitised job title; the command gets its values only through `FORGE_NOTIFY_*` environment variables and is killed after 30 s. Webhook URLs must be `https:` (plain `http:` only for loopback) without credentials. Both keys are read-only in Settings and refused by `forge config set`, `/api/config` masks them, `forge doctor` checks them, and `forge notify test [--event <name>]` sends a sample. With nothing configured, Forge starts no process and makes no request.
- **Repo-level cost governance.** A new top-level `budget:` block caps what the whole repo spends per UTC day and month: `budget.usdPerDay`, `budget.usdPerMonth` and `budget.tokensPerMonth` (all null, unlimited, by default) and `budget.onExceeded: hold | warn` (default `hold`), each editable in Settings and with `forge config set`. Spend is the estimated cost of every finished agent across live and archived jobs, re-priced with today's pricing table and cached in `.forge/runtime/spend.json`. Under `hold`, the CLI checks the cap wherever a job starts: `forge job new` parks the new job waiting on `budget`, `forge job claim` parks a job that isn't running an agent and exits 4, `forge next` starts nothing and returns `{held: true}`, `forge job from-ref` exits 4, and the daemon pool holds a job session's resume, rework, answer, revise-spec and approve requests (cancel, gate and inbox requests still run). Retro jobs are exempt, and `forge job new --force` starts a job anyway and exempts it for the month. `forge budget` prints the status, and only a human can lift a hold: `forge budget ack --period <YYYY-MM|YYYY-MM-DD>` grants one more cap's worth for that period and records it in `.forge/runtime/audit.jsonl`. `forge budget ack` and `job new --force` are refused in daemon sessions. When the repo is no longer held, held jobs go back to `queued`, after their own per-job budgets are re-checked. Under `warn` nothing is held, and commands report the overrun instead. `forge stats --csv [--since] [--by job|role|model|day]` exports spend for finance as formula-safe CSV. The dashboard adds a period meter at the top of Analytics, a month spend chip in the status bar, and a Repo budget section at the head of Needs you that lists the held jobs with an Acknowledge button (`POST /api/budget/ack`, current period only). `DENY_TOOLS` gains `Edit(.forge/runtime/spend.json)` and `Edit(.forge/runtime/audit.jsonl)`. Per-job budgets (`pipeline.budget`) are unchanged.

- **Audit trail.** Every human action now records a best-effort, unauthenticated actor `{ login, source }`, resolved from the daemon session, `FORGE_ACTOR`, `gh api user` (cached 24 h), the git email or the OS user, in that order. That covers gate actions, links, budget sets and acks, forced claims and dependency overrides, `forge pr merge --now`, `forge config set` and `POST /api/config` (into a repo-level `.forge/runtime/audit.jsonl`), and dashboard permission answers. New `forge job audit <id> [--json|--csv]` and `forge audit --since <date> [--until <date>] [--csv]`. The dashboard Timeline shows "by <login>" and gate cards show who last acted, a human-approved escalation names its approver in the PR body's `## Decision` section, and `forge sync` posts a one-time tracker comment on merge. Only `gh` and `FORGE_ACTOR` logins are ever published; other sources show only the source. A foreman decision never counts as a person's.
- **Job retention.** `forge job archive <id>` and `forge job archive --done --older-than D` move finished jobs into compact records in `.forge/archive/<id>.json` (gitignored) and delete their job folders; a job that is active, an eval, owned by a live session, still has a worktree or an open PR, or is needed by an unfinished job is refused with a reason. `forge job prune --older-than D [--dry-run]` does the same in bulk and also deletes stale daemon session logs. New keys `retention.jobsDays`, `retention.logsDays` and `retention.logMaxBytes` (all null by default, so nothing is deleted until you set one) let `forge sync` and `forge dash` apply the policy, and rotate a session log to `<scope>.log.1` at the size limit. Stats, audit, retro, dependencies, `forge status` and Analytics read archived jobs, so their numbers don't change after a prune. Every deletion is logged in `.forge/runtime/retention.log`, both commands are refused in daemon sessions, and `forge doctor` gains a `storage` check.
- **Redacted support bundle.** `forge doctor --bundle [<job>] [--out <dir>]` writes a zip with doctor output, versions, the redacted effective config, each active job's events, step decision, latest verify round and logs, and daemon log tails, and prints the manifest first. Paths, home directories, emails, logins, the host name and anything the secret scanner finds are replaced, every config value that is not plainly safe is hidden, and agent prose is left out unless you pass `--include-text`. The file is written `0600` and never overwrites. Settings › Diagnostics can download the same bundle, which never includes agent text. Redaction is pattern-based and best effort, so skim a bundle before you attach it.
- **Releases and provenance.** Each release is now a `v<x.y.z>` tag and a GitHub Release with its CHANGELOG section and a source archive plus its `.sha256`, published by a new `release.yml` workflow when `main`'s version changes; 0.18.0 is the first. `forge version --json` prints `{version, commit, installedAs, node}`, Settings › About shows the commit and how Forge is installed, and `forge doctor` warns when the install is behind the latest Release and when a deprecated config key is set. `npm run release:check` (also a CI job) checks the versions, the CHANGELOG section, a clean tree and the dashboard build. New `docs/RELEASES.md` covers versioning, support, deprecation, pinning and rollback.
- **Support matrix.** New `docs/SUPPORT.md` defines three tiers: macOS and Linux supported, WSL2 supported with notes, native Windows unsupported. `forge doctor` (and `GET /api/doctor`) reports the tier as its first check, flags a repo under `/mnt/` on WSL2, and now checks `git >= 2.38` and, when gh is needed, `gh >= 2.40`; older versions make it report `ok: false`, though it still exits 0. On native Windows the daemon and `forge update` are refused up front with a clear message, and command templates run through Git Bash's `sh`. CI gains a `windows (node 22.18.0)` job that runs typecheck and the tests that pass on Windows, with a fail-closed `WINDOWS_SKIP` list naming each skipped file and why.
- **Eval A/B.** `forge eval` run records carry a `pluginHash` over the agent prompts, checklists, skill and pipeline rules, so two dev builds with the same version can be told apart. `forge eval start --set key=value` applies a per-run config overlay (an allowlist of model, effort, pipeline, panel and verify keys) without editing `.forge/config.yml`, `--repeat N` (1–10) runs each task several times, and graded results add minutes per stage, agent and orchestrator minutes, reviewer runs and per-task n, mean, min and max. `eval compare` reports sample counts and a stage delta.
- **Review-finding counts.** Builders answer review findings as one parseable line each (`- <lens> <severity> <path:line> → fixed | disagree: <reason>`). The new `forge job findings <id>` counts raised, fixed, disputed and recurring findings per round and per lens, `forge stats` adds a per-lens dispute rate and a recurring-findings count, and `forge retro prepare` lists findings that bounce between rounds as oscillation signals.
- **Learnings expire on evidence.** A learning can carry `experiment: <id>` (an id in `.forge/notes/experiments.md`) and `review-by: <date>`. `forge retro prepare` lists the learnings past their review-by with their experiment's baseline, current value and verdict, and the retro prompt retires the ones whose metric didn't move. `forge roster` reports the learning count and the oldest review-by.
- Dashboard: one notification bell replaces the Inbox and Needs-you indicators in the status bar. Its badge counts decisions waiting plus pending permission prompts across the pool, and its popover lists the prompts first, then the decisions, in a compact panel whose rows wrap instead of scrolling sideways. The inbox session's log moves to the Daemon popover, under **Inbox session log**.
- Docs: new `docs/GLOSSARY.md` settles one vocabulary for the project model, multi-repo jobs, releases, environments and profiles ahead of multi-repo work. Each term gets one sentence and the config key it maps to today (or the milestone that will add one), and a "Collisions we avoid" section keeps existing words such as `resources`, `services:` and GitHub Project from being overloaded.
- Versions: `API_VERSION` 19 → 23, job schema 9 → 10, config schema 5 → 9, event schema 1 → 2; archive records (`.forge/archive/<id>.json`) start at version 1, and eval run records are `schemaVersion: 2`. Older jobs, configs, events and eval records migrate on read.

## 0.17.0

These notes cover everything since 0.16.0, including what 0.16.1 shipped without notes.

- **Behaviour change: integrate before decide, merge by default.** The stage order is now `… review, integrate, decide, pr, done`, so the approver judges a branch that is up to date with its base and an approved job opens its PR at once. `forge integrate` now uses `pr.updateStrategy` (default `merge`) whether or not a PR exists, so branches without a PR get merge commits instead of being rebased; set `pr.updateStrategy: rebase` to keep rebasing. `--strategy` accepts only `merge` or `rebase`. A gate is skipped on re-entry only when a human approved at that same gate, and `forge verify`'s secret scan also reads merge commits with `--remerge-diff`, so a key added in a conflict resolution is caught.
- **Behaviour change: no integration review for docs-only conflicts.** The new `pr.integrationReview` key defaults to `code-only`: when every conflicted path, and every path the resolution changed beyond git's own merge, is docs (`*.md`, `docs/**`) or generated (`worktrees.generated` or rebuilt by `forge integrate`), the one-lens `code` review is skipped with a note on the job. Set `pr.integrationReview: always` for the old behaviour. Computing the resolution diff needs git 2.38 or later; on older git the review is kept.
- **Behaviour change: a fresh builder per rework round.** Rework rounds no longer resume the previous builder and its whole context. Each round spawns a new builder with a findings-first brief (`Rework:`, `Rework scope:`, `Reference:`) naming the previous round's non-PASS reviews, the failing verify report and PR or human feedback. Only an answered NEEDS-INPUT still resumes the agent that asked. Watch `forge stats` for rework duration and cost.
- **Dashboard restyle: Smithy replaces Drafting.** Gunmetal and brushed-steel plates, one silver-blue `gleam` for agents at work and one warm `ember` for work waiting on you. The themes are now `forge` (dark, the default) and `ash` (light), plus System; saved `cyanotype`, `dark` and `nightprint` load as Forge, and `vellum` and `light` as Ash. One **Grain** preference replaces Grid and Paper and inherits the old Paper value. Barlow Semi Condensed, Barlow and DM Mono replace Space Grotesk and IBM Plex, still self-hosted. The sidebar gets a brand plaque and a full-width command input, the status bar a facts strip, and `REV` reads `YOU`. `dashboard/style.css` is now the only source of the design system; the separate `smithy/` design folder is removed.
- **Dashboard layout: split job pane and a Needs-you popover.** The job view is a resizable pane beside the board on wide screens (drag or use the arrow keys on its separator; double-click resets, and the width is remembered per browser), and fills the main column on narrow ones. The Inbox page is gone: a bell in the status bar shows the urgent count and opens the same content as a popover, and old `#/inbox` links open it. Settings opens with Cmd+, (Ctrl+, elsewhere) instead of the bare `,` key, whose checkbox is removed. Toasts no longer cover controls, Thread and Log messages are tinted by sender, the Daemon popover is reworked for per-job sessions, and chrome text is no longer selectable while code, prose and log entries still are.
- Foreman (opt-in, `foreman.enabled: false` by default): with the daemon on, `forge dash` runs an office session (scope `_office`) that decides parked gates. When a job parks on a gate class listed in `foreman.decides`, the CLI queues a `gate` request; the office hands it to a `forge:assistant` sub-agent that reads the job's files, then records the verdict with `forge job human … --actor foreman`. The CLI enforces the limits: gates matching `foreman.reserved` (by default, topics such as credentials, secrets, auth, permissions, security, CI/CD and payments) or any non-PASS security review stay with a human, and the office can't merge PRs. New `forge job assist`, `runtime.models.assistant` (default `sonnet`) and `runtime.efforts.assistant`. The status bar shows the office session, gate cards say "Foreman deciding" or "Human-owned", and `forge stats` counts foreman decisions apart from human reworks.
- Effort per role: `runtime.efforts.<role>` sets a level per agent role, a `review.panel` entry can set its own `effort`, and `runtime.effortByComplexity` maps the spec's new `Complexity: low | medium | high` header to a level. From round 2 a builder gets one level more, unless `job.effort` set it. A job's own effort still wins. Settings › Agents edits every new key, and the Agents page shows each role's and lens's level and its source. `forge job set --field complexity=<low|medium|high|null>` sets complexity by hand.
- Faster review rounds: `forge job step` returns the whole remaining review panel in one `spawn` action (an additive `spawns` list), so the orchestrator launches every reviewer at once instead of one per step.
- Design lens on the running app: a `review.panel` entry's new `needsApp` says whether its lens gets the dev server and a `Dev server:` line in its brief. It defaults to true for `ui`, `ux`, `accessibility` and `design`. The plugin ships a repo-neutral `design` checklist, and setup detection now suggests `design` for UI repos instead of the three separate lenses.
- Live agent activity: job cards, the job pane and the Agents page show what each running agent is doing, from its Claude Code transcript. The job pane gets an Agents tab, and a running or finished agent's transcript (or an interactive owner session's) opens read-only in the session log viewer. New `forge job agent <id> attach`, which the orchestrator calls when it spawns a background agent, and `GET /api/jobs/:id/transcript` plus `/transcript/events`. Both routes are loopback-only, check Origin and need the token; the live stream takes it as a `token` query parameter because EventSource can't send headers. Usage lookup honours `$CLAUDE_CONFIG_DIR`.
- Daemon: a job session that stalls because Claude Code never surfaced a finished background agent's notification is nudged with a single `resume` after 60 s (logged as `missed-agent-end`), and the orchestrator now records `agent end` at the first of the agent's report or its notification.
- Faster CLI start: `bin/forge` turns on V8's code cache on every Node and, below Node 24, caches type-stripped `lib/` modules, cutting a start on Node 22.18 from about 145 ms to about 40 ms. The cache lives in `.cache/` at the plugin root (or `$FORGE_CACHE_DIR`) and is used only when it is a private directory you own; otherwise the CLI runs uncached and silent. `NODE_DISABLE_COMPILE_CACHE=1` turns it off.
- Repository: the test suite caches type-stripped modules (about 3x faster on Node 22.18), and CI splits each verify cell into two test shards.
- Versions: `API_VERSION` 16 → 19, job schema 8 → 9, config schema 3 → 5. Older jobs and configs migrate on read.

## 0.16.0

- **Breaking CLI contract:** exit codes are now classes: 0 ok, 1 failed, 2 usage, 3 owned, 4 blocked, 5 external. Usage errors exit 2 instead of 1, and git, gh and claude failures exit 5 instead of 1. Every error carries a code from a closed set, and under `--json` errors print as one JSON line on stdout and string results are JSON-encoded. `forge help <command>` is generated from each command's help table, and the new `docs/CLI.md` documents the exit classes, error codes, environment variables and stable JSON field names. Scripts that check for exit 1 need updating.
- Secret scanning: a zero-dependency scanner refuses to publish a likely credential. It runs as a built-in `secrets` step at the start of `forge verify`, in `forge git commit`, in `forge pr open` (title, body and pushed range) and on tracker writes, and it notes likely secrets in what agents write to the job dir. Findings are always masked. A blocked job parks on a new human gate (an Inbox "Human check" card) that clears only when the value is removed or its fingerprint is allowlisted in `.forge/secrets-allow.txt` in the main checkout. New `forge secrets scan <id> | --paths <globs>`, config `verifySecrets: block | warn` (default `block`), error code `secret_found`. Job schema 8.
- Effort per job: a repo default `runtime.effort` (null by default, editable in Settings) and a per-job override (`forge job new --effort`, `forge job effort <id> <level>|--inherit`) resolve to one level. Daemon sessions start with `--effort`, every agent gets it, and the dashboard shows and sets it per job. Job schema 7.
- One human visit before build: a free-text job on a repo with a tracker no longer stops at Intake for an issue link. `/forge approve <id> <ref>|new|none` approves the spec and links the issue in the same gate, and a job still unlinked after the spec gate parks before build, so one job is still one PR and one issue.
- Faster rounds: a `verify` entry can be a group (`[lint, typecheck, test]`) whose steps run concurrently, and the next entry waits for all of them (config schema 3). `forge run <job> <command> -- <args…>` lets the builder run only the tests it touched, for commands that opt in with `{args}`. Typecheck and svelte-check are incremental, and Forge's own suite runs in under a minute.
- Lost or missing reviewers are retried in parallel instead of one per step, so a review round recovers from a session eviction in minutes, not tens of minutes.
- The daemon pool never evicts a session whose job has running agents, and idle time counts from the last agent's end. A session that dies anyway marks its agents `lost`, so the next session respawns them instead of waiting on phantoms.
- `forge sync` moves a PR that conflicts (under `pr.conflicts: fix`) or has only fallen behind (under any policy) straight to `integrate`, and queues a resume when the daemon is on. It never acts on a job another session holds or on a head Forge did not push; `ask` still asks, and `defer` parks with a note.
- A human rework on a job past `maxRounds` now runs its whole round (build, verify, review, decide) instead of re-parking before verify. A later round without a new rework still parks.
- `forge eval grade` restores the candidate's copies of the files a hidden test patch touches before applying it, so a builder writing its own test file no longer fails the task.

## 0.11.0
