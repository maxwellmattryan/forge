# Working on the dashboard

Read this before you change anything under `dashboard/`. The root [AGENTS.md](../AGENTS.md) still applies; this file adds the dashboard's own rules.

## Rules
- **`dashboard/style.css` is the source of truth for the dashboard's look** (the Smithy design system: its tokens and `@utility` classes; the icons live in `dashboard/src/lib/ui/icons.ts`). New classes are `@utility`s there, colours come from the token variables, and fonts are vendored in `dashboard/fonts/`, never linked.
- **The dashboard imports the API types and never redefines them.** `src/lib/core/types.ts` re-exports the engine's `#api/types.ts` and holds only the runtime constants the bundle needs, each pinned with `satisfies` to `#api/constants.ts`. Anything from the engine's `lib/` comes in with `import type` or `export type` only: a value import would bundle engine code.
- **Motion uses the tokens and one door.** Durations are `--motion-*` (anything that gates a control) or `--heat-*` (ambient activity), never literals; every Svelte transition comes from `src/lib/ui/motion.ts`, never `svelte/transition`; and heat and entry effects wait for `settled()`, so a page load, a reconnect or a stream (re)open never animates.
- **A project page selects its project; a global page keeps it.** `#/overview` and `#/machine` are global pages that leave the selection (`S.selected`) as it was; `#/p/<project>/<view>` selects `<project>` (`src/lib/shell/routes.ts` checks the raw segment against `PROJECT_NAME`, and `route()` in `src/lib/core/app.svelte.ts` switches). The selection is the machine pref `lastProject`: a page opened on a global route selects it, and `checkSelection()` drops it once the first `/api/projects` shows it is no longer registered and openable. `main.ts` turns an old `?project=` link into its route before the app mounts. Everything a project owns remounts on a switch (App's `{#key}`), and an async result for another project is dropped. Prefs are per project (`forge.p/<project>/<key>`, falling back to the old `forge.<key>`) except `MACHINE_PREFS` in `src/lib/settings/prefs.ts`: add a new pref there when it belongs to the browser, not a project.
- **Every per-project request goes through `projectApi`.** One machine server serves every project under `/api/p/<project>/…`, and the selected project comes from the route. `src/lib/core/project.ts` builds those paths: wrap a literal `/api/…` path in `projectApi(...)` (the shared fetch helpers already do) and don't write `/api/p/` by hand. The one exception is the Drawer's sandboxed mockup iframe, whose literal `src` the dashboard invariants pin. `/api/about`, `/api/projects*` and `/api/session` (the login exchange in `src/lib/core/login.ts`) are the machine's own and stay bare.
- **No dashboard code reads or sends a token.** `main.ts` trades a login link's `#k=` fragment for the server's HttpOnly login cookie before the app mounts (`watchLoginFragment` does the same, ahead of the router, for a link pasted into an open tab), and every same-origin `fetch` and `EventSource` carries that cookie on its own: never add an `x-forge-token` header or a `?token=` query. A 401 is the signed-out banner (`connectionBanner` in `src/lib/core/login.ts`), not a lost connection.
- Each page is one component in `src/views/`. Put shared pieces in `components/` and logic you want tested in a plain `.ts` in the `src/lib/<module>/` folder for its concern, not in a growing view.
- **`src/lib/` is module folders, like the root `lib/`.** Read [`src/lib/AGENTS.md`](src/lib/AGENTS.md) before you add a lib file: it goes in the folder for its concern, never at the `src/lib/` root. Folders hold 3–12 entries, with no `index.ts` and no name that repeats its folder (`test/invariants/dashboard-layout.test.ts`). Each file opens with its header comment, and `npm run docs:map` writes the folder maps from those.
- **Never commit the built dashboard.** `dist/` is gitignored and never hand-edited. Rebuild it with `npm run build:dashboard` before the tests: the ones that read the build (token contrast, remote assets, the index) skip without it, and CI runs them. CI builds `dist/` for the main update that the release PR carries into `main` ([docs/DEVELOPING.md](../docs/DEVELOPING.md#publishing) › Publishing).

## Gotchas already paid for
- **Tailwind v4**: `@apply` accepts only built-in utilities or classes declared with `@utility`; plain `.class {}` rules can't be `@apply`'d. Tailwind only sees the `@source` files in `dashboard/style.css`: build class names from whole literals, never `bg-${tone}`; no `class:` directives, and no `<style>` blocks in components. Upgrading means bumping the exact devDependency versions and rebuilding.
- **Dashboard text comes from `dashboard/src/messages/en/<area>.json`.** Add keys to the file whose components use them. Start a new area file only for a new view or a component area with no file, and never define a top-level key in two files (the invariant test fails and the dashboard throws at load). Components write `$t('literal.key')` (import `t` from `src/lib/text/locale.ts`); `test/invariants/dashboard-invariants.test.ts` fails on hard-coded prose in markup or text attributes, on a non-literal or unknown key, and on an unused message. Don't name a loop variable `t`: it shadows the store.
- **Text never sits on the grain.** Put dashboard text, controls and components on a `plate` (not `plate open`, which is a see-through container), `plain`, `solid` or `chrome` surface; the Grain pref (`data-grain`) only hides the texture, never a surface.
- **Escape everything the dashboard renders.** Svelte's `{…}` escapes, so never call `esc()` in a component. `{@html}` is allowed only on `md()` from `src/lib/text/markdown.ts`, whose output is escape-first; anything else that needs markup is a component over a plain-TS model, and `test/invariants/dashboard-invariants.test.ts` enforces it. Session log lines are untrusted: supervisor, stderr, tool input and result lines render as text; assistant/thinking prose and subagent prompts and reports render only through `md()`. Don't add a markdown library or any `innerHTML`. Job HTML (mockups) renders only in the sandboxed iframe (`/raw`), with scripts off.
- **Tests can't import `.svelte` or `.svelte.ts`** (runes need the compiler). Keep logic you want tested in a plain `.ts` in the `src/lib/<module>/` folder for its concern.

## Verify
Run `npm run dev -- --scenario <name>` from the checkout: it seeds a scratch repo with a dashboard scenario (`npm run scenario -- --list` names them: `busy` has a job in every stage and one with a long file list, `gates` one per human gate, `issues` a local backlog with an issue a job holds, one needing info and one with earlier jobs, for the issue panel, `failures`, `costs` and `empty` what they say), serves your sources and rebuilds on save (reload to see an edit; one Ctrl-C stops it and removes the scratch repo). A state no scenario has gets a new file in `test/fixtures/scenarios/` ([docs/TESTING.md](../docs/TESTING.md#dashboard-scenarios-and-the-render-check)). Open it in a browser. Check the forge, ash, temper, crucible, patina and obsidian themes, a phone-width viewport, the job drawer, and that markdown containing `<script>` / `<img onerror>` renders escaped. Finally run `npm run build:dashboard`, then `npm run test:render` (every view of every scenario beside a second project and a removed one, plus the Overview, the Machine page and a project switch, in headless Chrome, failing on console errors or missing text; it needs Google Chrome or `FORGE_RENDER_CHROME`, and CI's `render` job runs it too), and the tests, and commit the sources only, never `dist/` (`forge dash` serves `dashboard/dist/`, which CI builds for `main`).
