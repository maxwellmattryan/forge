# Working on the dashboard

Read this before you change anything under `dashboard/`. The root [AGENTS.md](../AGENTS.md) still applies; this file adds the dashboard's own rules.

## Rules
- **`dashboard/style.css` is the source of truth for the dashboard's look** (the Smithy design system: its tokens and `@utility` classes; the icons live in `dashboard/src/lib/icons.ts`). New classes are `@utility`s there, colours come from the token variables, and fonts are vendored in `dashboard/fonts/`, never linked.
- **Restraint: ornament on the frame, two type registers, one primary.** Only the frame takes the `hammered` texture: the sidebar brand plaque, the page header, the status bar and the drawer header; every other plate is plain panel. Controls (nav items, tabs, `btn` and so `seg`) are Barlow sentence case; labels and data (`label`, `stamp-line`, table headers, chips, ids) are mono uppercase. Buttons are primary (a flat gleam fill, at most one per view or dialog; in the drawer's action dock, the gate's accepting action), secondary (the plain `btn`) or `tertiary` (text only: close, cancel, show more); `ghost` is only for the status bar's indicators.
- Each page is one component in `src/views/`. Put shared pieces in `components/` and logic you want tested in plain `src/lib/*.ts`, not in a growing view.
- **Never commit the built dashboard.** `dist/` is gitignored and never hand-edited. Rebuild it with `npm run build:dashboard` before the tests: the ones that read the build (token contrast, remote assets, the index) skip without it, and CI runs them. CI builds `dist/` for the main update into `main` (the root [AGENTS.md](../AGENTS.md) › Publishing).

## Gotchas already paid for
- **Tailwind v4**: `@apply` accepts only built-in utilities or classes declared with `@utility`; plain `.class {}` rules can't be `@apply`'d. Tailwind only sees the `@source` files in `dashboard/style.css`: build class names from whole literals, never `bg-${tone}`; no `class:` directives, and no `<style>` blocks in components. Upgrading means bumping the exact devDependency versions and rebuilding.
- **Dashboard text comes from `dashboard/src/messages/en.json`.** Components write `$t('literal.key')` (import `t` from `lib/locale.ts`); `test/dashboard-invariants.test.ts` fails on hard-coded prose in markup or text attributes, on a non-literal or unknown key, and on an unused message. Don't name a loop variable `t`: it shadows the store.
- **Text never sits on the grain.** Put dashboard text, controls and components on a `plate` (not `plate open`, which is a see-through container), `plain`, `solid` or `chrome` surface; the Grain pref (`data-grain`) only hides the texture, never a surface.
- **Escape everything the dashboard renders.** Svelte's `{…}` escapes, so never call `esc()` in a component. `{@html}` is allowed only on `md()`, `budgetChip`/`budgetCell`/`budgetPanel` and `screenshotsPanel`, whose output is escape-first, and `test/dashboard-invariants.test.ts` enforces it. Session log lines are untrusted: supervisor, stderr, tool input and result lines render as text; assistant/thinking prose and subagent prompts and reports render only through `md()`. Don't add a markdown library or any `innerHTML`. Job HTML (mockups) renders only in the sandboxed iframe (`/raw`).
- **Tests can't import `.svelte` or `.svelte.ts`** (runes need the compiler). Keep logic you want tested in plain `src/lib/*.ts`.

## Verify
In a scratch repo, seed a job or two (`forge job new`, `forge job set`), then run `FORGE_ROOT=<scratch> npm run dev` from the checkout: it serves your sources and rebuilds on save (reload to see an edit; one Ctrl-C stops it). Open it in a browser. Check the forge, ash, temper, crucible, patina and obsidian themes, a phone-width viewport, the job drawer, and that markdown containing `<script>` / `<img onerror>` renders escaped. Finally run `npm run build:dashboard` and the tests, and commit the sources only, never `dist/` (`forge dash` serves `dashboard/dist/`, which CI builds for `main`).
