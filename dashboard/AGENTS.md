# Working on the dashboard

Read this before you change anything under `dashboard/`. The root [AGENTS.md](../AGENTS.md) still applies; this file adds the dashboard's own rules.

## Rules
- **`dashboard/style.css` is the source of truth for the dashboard's look** (the Smithy design system: its tokens and `@utility` classes; the icons live in `dashboard/src/lib/icons.ts`). New classes are `@utility`s there, colours come from the token variables, and fonts are vendored in `dashboard/fonts/`, never linked.
- **The dashboard imports the API types and never redefines them.** `src/lib/types.ts` re-exports the engine's `#api/types.ts` and holds only the runtime constants the bundle needs, each pinned with `satisfies` to `#api/constants.ts`. Anything from the engine's `lib/` comes in with `import type` or `export type` only: a value import would bundle engine code.
- **Motion uses the tokens and one door.** Durations are `--motion-*` (anything that gates a control) or `--heat-*` (ambient activity), never literals; every Svelte transition comes from `src/lib/motion.ts`, never `svelte/transition`; and heat and entry effects wait for `settled()`, so a page load, a reconnect or a stream (re)open never animates.
- Each page is one component in `src/views/`. Put shared pieces in `components/` and logic you want tested in plain `src/lib/*.ts`, not in a growing view.
- **Never commit the built dashboard.** `dist/` is gitignored and never hand-edited. Rebuild it with `npm run build:dashboard` before the tests: the ones that read the build (token contrast, remote assets, the index) skip without it, and CI runs them. CI builds `dist/` for the main update that the release PR carries into `main` ([docs/DEVELOPING.md](../docs/DEVELOPING.md#publishing) › Publishing).

## Gotchas already paid for
- **Tailwind v4**: `@apply` accepts only built-in utilities or classes declared with `@utility`; plain `.class {}` rules can't be `@apply`'d. Tailwind only sees the `@source` files in `dashboard/style.css`: build class names from whole literals, never `bg-${tone}`; no `class:` directives, and no `<style>` blocks in components. Upgrading means bumping the exact devDependency versions and rebuilding.
- **Dashboard text comes from `dashboard/src/messages/en/<area>.json`.** Add keys to the file whose components use them. Start a new area file only for a new view or a component area with no file, and never define a top-level key in two files (the invariant test fails and the dashboard throws at load). Components write `$t('literal.key')` (import `t` from `src/lib/locale.ts`); `test/invariants/dashboard-invariants.test.ts` fails on hard-coded prose in markup or text attributes, on a non-literal or unknown key, and on an unused message. Don't name a loop variable `t`: it shadows the store.
- **Text never sits on the grain.** Put dashboard text, controls and components on a `plate` (not `plate open`, which is a see-through container), `plain`, `solid` or `chrome` surface; the Grain pref (`data-grain`) only hides the texture, never a surface.
- **Escape everything the dashboard renders.** Svelte's `{…}` escapes, so never call `esc()` in a component. `{@html}` is allowed only on `md()` from `src/lib/markdown.ts`, whose output is escape-first; anything else that needs markup is a component over a plain-TS model, and `test/invariants/dashboard-invariants.test.ts` enforces it. Session log lines are untrusted: supervisor, stderr, tool input and result lines render as text; assistant/thinking prose and subagent prompts and reports render only through `md()`. Don't add a markdown library or any `innerHTML`. Job HTML (mockups) renders only in the sandboxed iframe (`/raw`), with scripts off.
- **Tests can't import `.svelte` or `.svelte.ts`** (runes need the compiler). Keep logic you want tested in plain `src/lib/*.ts`.

## Verify
Run `npm run dev -- --scenario <name>` from the checkout: it seeds a scratch repo with a dashboard scenario (`npm run scenario -- --list` names them: `busy` has a job in every stage, `gates` one per human gate, `failures`, `costs` and `empty` what they say), serves your sources and rebuilds on save (reload to see an edit; one Ctrl-C stops it and removes the scratch repo). A state no scenario has gets a new file in `test/fixtures/scenarios/` ([docs/TESTING.md](../docs/TESTING.md#dashboard-scenarios-and-the-render-check)). Open it in a browser. Check the forge, ash, temper, crucible, patina and obsidian themes, a phone-width viewport, the job drawer, and that markdown containing `<script>` / `<img onerror>` renders escaped. Finally run `npm run build:dashboard`, then `npm run test:render` (every view of every scenario in headless Chrome, failing on console errors or missing text; it needs Google Chrome or `FORGE_RENDER_CHROME`, and CI's `render` job runs it too), and the tests, and commit the sources only, never `dist/` (`forge dash` serves `dashboard/dist/`, which CI builds for `main`).
