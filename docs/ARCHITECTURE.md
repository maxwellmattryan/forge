# Architecture

## Layers

| Layer | Where | Changes when |
|---|---|---|
| **Engine**: CLI, dashboard, data schemas | `bin/`, `lib/`, `dashboard/` | the plugin is updated |
| **Roster**: orchestrator skill, agent prompts, reviewer catalog | `skills/`, `agents/`, `reviewers/` | the plugin is updated |
| **Repo layer**: config, learnings, role addenda, repo checklists, evals, custom trackers | `<repo>/.forge/` (committed) | `/forge init`, humans, retros |
| **Runtime state**: jobs, locks, dashboard inbox, caches | `<repo>/.forge/{jobs,locks,runtime}/` (gitignored) | every Forge action |

Repos never copy the engine or the roster, so there is nothing to drift. Everything repo-specific is data in `.forge/`, and that's also the only layer the retro loop edits.

**Which `forge` runs.** Claude Code appends a plugin's `bin/` to the end of PATH, so a `forge` earlier on PATH (a `~/.local/bin` shim, an `npm link` of another checkout) would run a different install's CLI against the loaded plugin's skills. The SessionStart hook `hooks/plugin-path.ts` appends `export PATH='<plugin root>/bin':"$PATH"` to `$CLAUDE_ENV_FILE`, which Claude Code sources before every Bash command of the session, subagents included, so `forge` is always the loaded plugin's. The line is built only from the hook's own location and single-quoted; the hook prints nothing on stdout and always exits 0. It does nothing when `CLAUDE_ENV_FILE` is unset or empty, on Windows, or when the file already holds the line (resume, clear and compact run it again). Daemon sessions get the same order from `sessionEnv()`.

## Why a CLI does the bookkeeping

LLMs are good at judgement and unreliable at bookkeeping. Everything with a single right answer is code: valid state transitions, which transition comes next, unique job ids, atomic writes, locks, port allocation, worktree setup, command logging, verdict policy, PR and tracker calls, usage maths. Agents and the orchestrator call `forge …` and get compact JSON back. Four things follow:

1. **Data shapes can't drift.** No model hand-writes `job.json`, so a skill update can't produce state that a dashboard update can't read.
2. **Context stays small.** `forge verify` returns pass/fail plus a log tail, not 3,000 lines of compiler output. `forge job verdicts --compact` returns one word per lens. `forge job scope` returns at most 20 out-of-spec files; the full list goes to `scope.md`.
3. **The protocol is portable.** Any agent runtime that can run shell commands can drive Forge (see PROTOCOL.md).
4. **The pipeline is tested code.** `forge job step <id>` (`lib/step.ts`) is the one decider of transitions: a pure function from recorded state (`job.json`, the config, which job files exist, the events it needs) to the next action: `spawn` an agent with the brief `lib/brief.ts` rendered, `run` one forge command, `wait` on agents or a human gate, follow a reference `procedure`, or `done`. It never writes, so the same state always gives the same answer (the CLI's `--session <owner>` only refreshes that owner's heartbeat before deciding), and each rule is a row in `test/step.test.ts`. `forge job advance <id> --session <owner>` (`lib/commands/advance.ts`) is step's executor: it runs the `run` actions step returns in-process, through the same dispatcher `bin/forge` uses, and returns the first `spawn`, `wait`, `procedure` or `done` with a one-line summary of each command it ran, so step stays pure and a deterministic stretch of the pipeline costs the orchestrator one call. A review round's RV4 returns the whole remaining panel at once, the first unstarted lens plus the others as `spawns`, and each lens is still recorded by its own `agent start`, so a re-step never lists a started lens. The facts the orchestrator used to carry in conversation are recorded instead: suggested lenses in the `spec.md` header, the agent to resume after an answered question in `agents.<role>.agentId`, reviewers in flight in agent `status`, split mode in `job.splitMode`, human decisions in `human` events, and missing outputs in `outputMissing`, which `forge job agent … end` sets for single-output roles. Commands it emits are built only from ids, numbers, config names and fixed templates, never from file contents or agent replies, and briefs carry paths, never contents, so text an agent wrote after reading tracker or PR input never becomes a shell argument or another agent's prompt.

The CLI is TypeScript that Node ≥ 22.18 runs directly through its built-in type stripping, with zero dependencies. That means no build step, no install step inside the plugin, and Node is already present wherever Claude Code is. The only JavaScript left in the engine is `bin/forge`, an extensionless entry that sets up the start-up cache below and then imports `lib/cli.ts`, and `lib/trackers/status.mjs`, a one-line re-export kept for custom tracker adapters. Node does not strip types under `node_modules`, which is why Forge has no npm-package install. The dashboard is built with Vite at development time and its output (`dashboard/dist/`) is committed, so installing still needs no build or install step. The dashboard is a Svelte 5 app in strict TypeScript (`dashboard/src/`), type-checked with svelte-check and compiled by Vite at development time; nothing at runtime loads Svelte's compiler or TypeScript. A native (e.g. Rust) port would only pay off for a long-running worker daemon. The CLI's commands and JSON outputs are the contract, so a port could replace it without touching the skill or agents.

### Start-up cache

Agents and the orchestrator call `forge` hundreds of times a job, so start-up time is paid on every call. Before it imports `lib/cli.ts`, `bin/forge` turns on two caches in one directory:

- **V8's code cache** (`module.enableCompileCache`), on every Node. From Node 24 it covers type-stripped modules too.
- **Stripped modules**, on Node 22 and 23 only. Their code cache skips type-stripped modules, so every start loads the stripper and strips all of `lib/` again. A `module.registerHooks` load hook keeps each stripped `.ts` file of the plugin as `strip/<node version>/<sha256 of the source>.js`. Content keys mean an edited file or an updated plugin is never served stale, and identical files of different installs share an entry. A miss strips with `module.stripTypeScriptTypes` and silences its one-time ExperimentalWarning, which agents would read as a fault. The entry is written aside and renamed, so concurrent starts never read half a module. A file the stripper rejects goes to Node's own loader, which reports the error as usual.

`forge job list`, median of 30 warm starts on an M-series Mac:

| Node | Before | After |
|---|---|---|
| 22.18 | 144 ms | 37 ms |
| 22.23 | 98 ms | 39 ms |
| 26.3 | 148 ms | 70 ms |

A miss costs about 15 ms over an uncached start, once per changed file. On Node 22 the modules `forge job list` loads take about 1.3 MB of cache (0.9 MB stripped, 0.4 MB V8), per Node version.

The cache holds code the CLI runs, so it must be no easier to write than the code it caches. It is `.cache/` in the plugin root (or `$FORGE_CACHE_DIR`), so whoever can write it could already rewrite `lib/`. It is not in a temp or other shared dir, because Claude Code's sandbox lets Bash write the temp dir: a sandboxed agent could plant a module there that a later unsandboxed `forge` would run. `bin/forge` creates the dir as `0700` with a `.gitignore` of `*`, so a checkout's `git status` never shows it. It uses the dir only when it is a real directory (not a symlink), owned by the current user, not group- or world-writable, in a parent owned by that user or root that is either not group- or world-writable or sticky. Otherwise, and whenever a read or write fails, the CLI runs uncached and prints nothing. A read-only install, or a sandbox that can't write the plugin, still reads entries an earlier unsandboxed start wrote and skips writing misses. Each plugin version starts with an empty cache and is removed along with it. `NODE_DISABLE_COMPILE_CACHE=1` turns both caches off. A `NODE_COMPILE_CACHE` already set wins for the V8 cache. Deleting the directory is always safe.

## Data and versioning

Every persisted shape carries a version: `config.yml` → `schemaVersion`, `job.json` → `schemaVersion`, each event line → `v`, `/api/state` → `apiVersion`. `apiVersion` (`API_VERSION`) also covers the other `/api/*` shapes the dashboard reads, such as `/api/config`, `/api/doctor` and `/api/about`.

- **Readers upgrade, writers write current.** `normalizeJob` and `migrateConfig` (in `lib/schema.ts`) upgrade old shapes in memory and fill defaults, so new code reads old jobs. `forge migrate` rewrites them on disk.
- **Newer-than-me is refused, not guessed.** A plugin that meets a job from a newer schema stops with "update the plugin".
- **Unknown fields are preserved.** Normalisation spreads the raw object first, so fields from a newer minor version survive a read-modify-write by an older one.
- **The dashboard is served by the same plugin version as the CLI**, so they can't disagree. The page checks `apiVersion` anyway, for a dashboard left open across an update.
- **Events are append-only**, so history is never rewritten by a migration.

When a shape must change: bump the version constant, add a migration keyed by the old version, and keep normalisers tolerant.

Job schema v6 (API version 10) records what `forge job step` decides from: `splitMode` (`never` for jobs from `forge job from-ref` and after a `revise-split`, else null; a v5 job reads as null, because v5 never recorded how a job started), each agent record's `output`, `retry` and `outputMissing`, and each verify run's `failure` (the failing step's name). Events gained `pr-find` (`forge pr find` adopted nothing) and `scope` (`forge job scope` ran, with its round and HEAD). API version 12 (from 11) adds `ownerStatus` (`none | live | stale | dead`, with the session, its claim and heartbeat times, `agentRunning` and a `dead` reason) and `jobSession` to each `/api/state` job and to the job detail; job.json and events are unchanged.

The `panel` event (`forge job panel` ran, with `{round, head, mergeBase, lenses, reasons, added}`) records each round's review lenses and why each is on the panel; step reads it to know the panel is current for the round. It is a new event type and job.json is unchanged, so it needed no schema bump, and a review panel entry's optional `paths` passes through older config normalisers untouched.

Job schema v7 (API version 15) adds `effort`: the human's reasoning effort for the job (`low | medium | high | xhigh | max`), or null to inherit `runtime.effort`. A v6 job reads as null, and so does any value outside the five levels, whoever wrote it. Events gained `effort` (`{effort, previous, from: "cli" | "dashboard"}`), and a `created` event names the level when `forge job new --effort` set one. `/api/state` adds `config.effort` (`runtime.effort` when valid, else null) and each daemon session's `effort`.

Job schema v8 (API version 16) adds `waitingOn: human`: a CLI check stopped the job and only a human can clear it, and the reason names the check (today the secret scanner: `secret scan blocked verify round <n>` or `secret scan blocked pr open`). No v7 job waits on it, so the migration changes nothing; the bump makes an older Forge refuse a job parked on a gate it can't explain. Events gained `secret-found` (`{gate: verify | commit | pr | agent-end, blocked, count, allowed, findings, more, round?, role?}`, at most 10 masked findings, each `{kind, path, line, excerpt, fingerprint}`, logged only when something was found), and verify's JSON gained `secrets`. The config gained `verifySecrets` with a default, which needs no config bump.

Job schema v9 (API version 17) adds `complexity` (`low | medium | high`, or null): the spec's `Complexity:` header, recorded by SP3 through `forge job set --field complexity=…`, which accepts only those three values or null. A v8 job, and any other stored value, reads as null. `/api/roster` adds `effort` and `effortSource` to each `agents[]` and `reviewers[]` item. Config schema v4 adds `runtime.efforts.<role>`, `runtime.effortByComplexity.<low|medium|high>` and a panel entry's `effort`, all unset by default, so a v3 config migrates unchanged.

API version 18 adds each `/api/state` job's `activity` (what its running agents did last) and the transcript endpoints behind the drawer's Agents tab; job.json and events are unchanged.

Config schema v5 and API version 19 add the foreman: `foreman.*` (off by default), `runtime.models.assistant` and `runtime.efforts.assistant`, a `gate` request type routed to the `_office` scope, `/api/state` `daemons.office` and `daemons.foreman`, and a per-job `gateOwner`. A v4 config migrates unchanged. Job schema stays at v9: `human` events gain an optional `actor` (`human | foreman`), and an older event without it reads as `human`.

API version 20 adds `/api/about` `commit` and `installedAs` and an optional `warn` on `/api/doctor` checks; job.json, config and events are unchanged.

## Updating

`forge update` (`lib/update.ts`) updates the install that is running, its own `PLUGIN_ROOT` after realpath, never whichever `forge` comes first on `PATH`. It works outside a git repo and without `.forge/`, like `forge version`.

- **Detection, plugin first.** A root under `plugins/cache/<marketplace>/<plugin>/<version>` (with `plugins/installed_plugins.json` beside it) or `plugins/marketplaces/<marketplace>` (with `plugins/known_marketplaces.json`) is a Claude Code plugin install. The plugins dir comes from the root's own path rather than `CLAUDE_CONFIG_DIR`, so it always describes this install. This check runs before the git check because Claude Code's cache dirs can contain a `.git`, and pulling there would fork the install from what Claude Code tracks. Otherwise a root that is its own git toplevel is a clone (`npm link`, `claude --plugin-dir`). Anything else is unknown, and the command prints the manual route instead of guessing.
- **Commands.** For a plugin it runs `claude plugin marketplace update <marketplace>`, then `claude plugin update <plugin>@<marketplace>`. Names from the path must match `^[A-Za-z0-9][A-Za-z0-9._-]*$` and are passed as separate argv entries with no shell, so a directory named like an option never reaches `claude`. For a clone it runs `git pull --ff-only`. The explicit flag overrides `pull.rebase` and `pull.ff`.
- **Refusals.** A clone with uncommitted changes, a detached HEAD or no upstream is left untouched. Forge never stashes, resets, rebases or merges, and a diverged history fails with git's own message. A daemon session (`FORGE_DAEMON=1`) is refused before detection or any subprocess, because an unattended agent must not swap the code it and the dashboard run on. An interactive session runs under the human's own permissions and can only move the install to its marketplace's or upstream's head, which is accepted.
- **Versions.** The new version is read from disk after the update: for a plugin, from the `installPath` that `installed_plugins.json` now records (user scope first). The cached `forgeVersion()` belongs to the old code.
- **Dashboard.** If the repo at cwd has a running dashboard and the version changed, Forge restarts it by running the new install's `bin/forge dash --stop` and `dash --background`. `forge dash` spawns the server from its own `PLUGIN_ROOT`, so running the old bin would bring the old code back up. `--keep-dash`, or a restart that fails, leaves it running and reports it as stale. Dashboards in other repos get a hint, because Forge keeps no global registry of them.
- **Provenance.** `forge version --json` (`lib/version.ts`) reports the running commit: a stamped `COMMIT` file (release archives), else the plugin install record's `gitCommitSha`, else `git rev-parse HEAD` when the root is its own toplevel, else null. The same detection decides `installedAs`. See [RELEASES.md](RELEASES.md#provenance-and-pinning).
- **Nothing is built.** `dashboard/dist/` is committed and there are no runtime dependencies, so an update never runs `npm install` or a build.
- **Shadowing.** A `forge` earlier on `PATH` that resolves under `node_modules` (an old global npm copy) cannot run, because Node does not strip types there. Forge warns and names the uninstall command. It deletes nothing.

## Job model

`stage` is where the job is in the pipeline:
`backlog → plan → spec → design → build → verify → review → integrate → decide → pr → done`

Integrate runs before decide, so the approver judges the branch as it will merge, and an approved job opens its PR at once. After any gate wait (an escalation, an infra runbook, a budget stop), step runs `forge integrate` again before the PR, and does more work (verify, the integrator, the integration review) only when it reports `behind > 0`. Older jobs found in `decide` with no integration since their review integrate before `pr`. Eval jobs never integrate: review sends them straight to `decide`.

`state` is what is happening there:
`queued | running | waiting | blocked | failed | cancelled | done`

`waitingOn` says why a job is waiting:
`spec-approval | split-approval | issue-link | input | escalation | infra | conflicts | rounds-exhausted | pr-review | external | budget | human` (`human`: a CLI check, such as the secret scan, stopped the job; approve means "I cleared it, check again", never "ship it anyway")

Trackers see a coarser view: `queued`, `in-progress`, `review`, `blocked`, `done`, `cancelled`. Adapters map those to labels, GitHub Project options, or anything else.

**Ownership**: a session claims a job (`owner.session` plus a heartbeat). Only the owner's own activity refreshes the heartbeat: `forge job claim`, `forge job step <id> --session <owner>`, `forge job advance <id> --session <owner>` (the orchestrator's loop; it refuses a job its session does not hold, at entry and after every command it runs) and the worktree commands its agents run (`forge run`, `forge verify`). No other write does, so sync, dependency parking, other sessions' commands and the dashboard can't keep a dead session's claim alive. Another session can take over only with `--force`, or after 30 minutes without that activity and with no agent still marked running (a running agent keeps the claim alive for up to two hours after it started, so a long builder is not mistaken for a dead session). Idle jobs give their claim up: parking a job on dependencies releases its owner in the same locked write (a `released` event), split children start unowned (`forge job new --parent` never claims, even with `--session`), and the split procedure releases the parked umbrella. `forge next --claim --session S` first resumes a queued job nobody drives (not eval, not an umbrella, dependencies done, no `resume` request pending or in progress, owner absent, stale or provably gone), oldest first, and returns it with `resumed: true`; only then does it start a new tracker item. `forge sync` moves a PR job to `integrate` only when its owner is not live by that same test, judged inside the job lock, and never claims the job itself. The dashboard drawer's **Resume** (and the command bar's `continue`) queues a `resume` for a queued, failed or stalled job; the server refuses one with 409 while another session's owner is live, but not when the live owner is the job's own daemon session, which takes the resume itself (see "Dashboard security"). `/api/state` reports each job's `ownerStatus` by the time rule alone, so polling never runs `ps`; the job detail adds the session-record proofs below, so it can say `dead`. Jobs record each session that drove them in `runs[]`. A `forge dash` session (lib/daemon-owner.ts) also yields its claim without `--force` when its session record proves it let go: the record has replaced that session id since (`moved-on`; a record runs one child at a time and keeps the last 20 ids in `pastSessionIds`), the record still names it but its child isn't provably running (`not-running`, the same `pidAlive` + `isOurChild` proof reaping uses), or it is the inbox's and the claimer is the job's own daemon session (`inbox-handoff`). The takeover is logged as a `note` (`took over from session <old>: <reason>`). An owner whose id is in no record, such as a human's session, keeps the time-based rule, and a live daemon session other than the inbox keeps its claim.

**Evidence**: every `forge verify` run records the worktree HEAD it checked, its attempt number within the round, and its result; earlier attempts are archived, never overwritten, so "verify first-pass" means the first attempt. `forge pr open` refuses to push a HEAD that the latest verify did not pass on. `forge job verdicts` records the sha the reviewers saw. When the integrator resolves conflicts after the panel passed, a one-lens `code` review of the resolution (`review/integration/code.md`, `forge job verdicts --round integration`) must pass before the PR opens (under `pr.integrationReview: code-only`, the default, a resolution whose conflicts and changed files were all docs or generated files skips it with a note); it is logged as an `integration-review` event, not in `job.verdicts`, so stats keep counting numbered rounds only. `forge pr open` records the sha it pushed (`pr.pushedSha`), and the first `forge pr sync` that sees the PR merged measures the human delta, the commits, lines and files humans added after that push (`pr.humanDelta`). Each verify also writes a test-integrity report (deleted or renamed tests, added skip/focus markers, the test-count delta, test and CI config edits since the merge-base), which reviewers and the approver read and `verifyIntegrity: block` turns into a failure. Evidence for an older commit is not evidence.

**Generated files**: committed paths a command regenerates (`worktrees.generated`, e.g. `dashboard/dist/**`) are never hand-merged. When `forge integrate` stops on conflicts, Forge splits them: a path counts as generated only when it matches a glob and passes the same checks as `forge git add` (no leading `-`, nothing absolute, no `..`, no `.git` segment, no symlinked parent leading out of the worktree, and the name must resolve to itself); everything else is a real conflict. When generated paths are all a stop has, Forge takes the base side of each (`--theirs` in a merge, `--ours` in a rebase; a path the base deleted is deleted), runs `worktrees.generatedBy` through the same logging as `forge run` (`logs/integrate-regenerate-*.log`), stages every glob-matching path the build wrote, added or deleted, and commits the merge or continues the rebase, repeating for each later pick that stops the same way. Names reach git only as literal pathspecs, over stdin. The build runs only in the job's own worktree on the job's branch (never the main checkout, a subdirectory or another branch; mid-rebase the branch is read from `rebase-merge/head-name`), and every `rebase --continue` Forge runs first checks that the todo holds only picks. A mixed stop goes to the integrator with the real conflicts only: the generated paths are listed as `regenerated` and, under `--keep-conflicts`, staged from the base side but not built, since the sources may still hold conflict markers; `forge integrate --continue` rebuilds them once nothing is unmerged. When Forge can't rebuild (no `generatedBy` command, an invalid glob, the worktree guard, or a failing build), it falls back to the old behaviour: every unmerged path is listed, `regenerateError` says why (with the build's last 20 lines), and an aborted merge leaves the worktree clean. A generated-only integration logs `integrated` with `regenerated`, so step re-verifies it and moves to `pr`: no integrator runs and no integration review is needed. Results and events carry `regenerated` and `regenerateError` only when they are non-empty.

**Budgets**: `pipeline.budget` limits tokens, estimated cost, agent minutes (summed agent run time), committed changed lines vs the base, and failed verify runs per round. Limits are read from config at every check, and a job's own `budget.limits` override them. Three checkpoints enforce them: `forge job agent end`, `forge job round` (before incrementing) and `forge verify`. An exceeded key parks the job at `waiting` on `budget` with its stage kept, logs a `budget` event, and adds a `budget` block to the command's JSON. `forge job budget <id> --set k=v` raises a limit; `--ack` grants one more full budget past the current use (a `verifyRetries` ack lasts only for its round). Neither changes state; the orchestrator resumes the job. Every checkpoint writes `budget.lastCheck` with what was used, so the dashboard can show it without running git. The dashboard derives effective limits and use client-side from `config.pipeline.budget`, the job's usage and `lastCheck`, and offers approve (ack, or raise via the note) on `waiting:budget`.

**Dependencies**: `dependsOn` lists job ids, set with `forge job set <id> --field 'dependsOn=[…]'`, which rejects unknown ids, the job itself and cycles. A dependency counts only when its job is `done`; `cancelled` or missing ones block until a human removes them. A queued job with unmet dependencies is parked at `waiting` on `external` with a `dependencies not done: …` reason (other waits are never overwritten), `forge next` skips it, and `forge job claim` refuses it with exit code 4 unless `--force`. Parking releases the job's owner, since nobody drives a parked job; rewriting the reason of a parked job or unparking it keeps the owner, so a `--force` claim on a parked job survives sync. `forge sync` unparks a job to `queued` once its dependencies are done, and `forge next --claim` then resumes it. A new branch for a job with exactly one unmerged dependency starts from that dependency's branch, and `job.base` becomes that branch, so the PR, `forge integrate` and reviewers' diffs are against it (a `stacked` event). Once the dependency merges, `forge sync` moves the base back to the dependency's own base (retargeting an open PR with `gh pr edit --base`) and logs `retargeted`. More than one unmerged dependency is refused.

**Inbox**: dashboard requests are claimed by a session before they are handled, under a lock, so two orchestrators draining the same inbox cannot both act on one request. A claim with no ack for 30 minutes can be taken over. The drainer is either your own session (`/forge requests`) or, with `daemon.enabled`, the headless sessions `forge dash` supervises (see "Daemon"); both go through the same claims, so they can run side by side. Each request has a **scope**: a job request (`approve`, `revise-spec`, `rework`, `answer`, `cancel`, `resume`) whose job exists belongs to that job, and everything else, including a job request whose job is malformed or unknown, belongs to the inbox (`_inbox`). A daemon session sees and may claim or ack only the requests of its own scope; a human's session sees them all. The inbox session does intake only: for `run`/`next` it creates or claims the job and hands it off with `forge requests add resume --job <id> --intake run|next --session <its session>`, which releases the claim when that session (or any inbox session id) holds it, so every pipeline runs in its job's own session. Under the inbox scope, `forge worktree create` and `forge job agent … start` refuse, so the inbox never drives a pipeline. A job created from the dashboard (`POST /api/jobs`) skips the inbox: the server creates it and queues its `resume` (`args.intake: new`) straight to the job's own session.

## Concurrency

- **Many jobs, one session**: the orchestrator runs agents in the background and advances each job as notifications arrive, up to `runtime.maxParallelJobs`.
- **Many sessions, one repo**: all state is in the main checkout's `.forge/`. Writes take a per-job `mkdir` lock and are atomic (write and rename). Backlog edits and tracker claims take their own locks. Job ids are created with an exclusive `mkdir`.
- **Worktrees** live outside the repo (`../<repo>.worktrees/<job>` by default), so watchers, bundlers and Cargo workspaces don't see nested copies. Untracked files agents need, such as a gitignored `CLAUDE.md` or `.env`, are copied in, and setup commands run once.
- **Rust**: with `worktrees.cargo.sharedTarget`, one `.cargo/config.toml` above all worktrees points every job at a single target dir. Dependencies compile once, and disk use doesn't multiply. Cargo serialises concurrent builds on that directory's lock, which is usually still far faster than cold builds per worktree.
- **Ports**: each active job gets a unique port from `ports.base`. Commands see it as `{port}`, `$PORT` and `$FORGE_PORT`.
- **One headless session per job**: with `daemon.enabled`, `forge dash` supervises an inbox session plus up to `daemon.maxConcurrent` (default 3) job sessions, each driving one job. A job's claim and owner lock still keep a human's session and its daemon session from driving the same job; claims pass between daemon sessions (inbox to job session, one incarnation to the next) without `--force` when the session records prove the owner let go (see "Ownership"). `runtime.maxParallelJobs` limits a human's interactive session, not the pool. A second `forge dash` on the same repo sees the first one's live pid in a `daemons/*.json` record and refuses to start its own.
- **Background commands** are idempotent per job and command: `forge run <id> dev --background` returns the recorded process while it is alive (`reused: true`) instead of starting another on the same port, and reports `listening` once the port answers. A per-job lock covers the check and spawn, so parallel UI reviewers share one dev server; the orchestrator starts it before them and runs `forge stop` after.

## Daemon

`forge dash` supervises a **pool** of `claude -p --input-format stream-json --output-format stream-json` children (`lib/daemon-pool.ts`): one inbox session for requests without a job, with `foreman.enabled` one **office** session (scope `_office`) for `gate` requests (see [Foreman](#foreman)), and one session per job with work, up to `daemon.maxConcurrent` (1 to 16, default 3; neither the inbox nor the office is counted). Each session is supervised on its own by `lib/daemon.ts`, with its own state, failure count, budget hold, idle stop, resume id and log, so one job's crash loop never stalls the others. The supervisors never run agents or write job state: they only decide when a session gets its one turn. Every child is built the same way (`daemon.command`, `DENY_TOOLS`, git pins, the trust snapshot) and differs only in its session uuid and `FORGE_DAEMON_SCOPE=<scope>` in its environment; the scope never reaches stdin or argv.

**States** (per session: `/api/state.daemons.inbox|jobs[id].status`, SSE `state` events): `off` (no child), `idle` (child alive, no turn in flight), `busy` (a turn was written and no `result` has been read), `stopping` (SIGTERM sent). Two things set `busy`: a turn write, and a `system`/`init` read while the session is `idle` after its child's first `result`. The second is a turn claude started by itself (a background agent finished and its notification woke the orchestrator): the supervisor logs `wake` once per such turn and writes the session no turn until it ends. `turns` and `lastTurnAt` count only the turns the supervisor wrote. A stdout line that parses as JSON with `type: "result"` is the only thing that sets `idle`. A fresh child is `idle`, because a stream-json `claude -p` does nothing until it reads a line. A session also reports `waiting` (it has work but no free slot), `held` (`budget`) and `kept` (`agents`: below).

**Missed agent ends.** Claude Code delivers a finished background agent as two queued messages: the agent's report, then a task notification with its usage. It can dequeue the second into an empty `result` (`num_turns: 0`) that no model call made (seen on 2.1.299). An orchestrator that ended the report's turn waiting for the notification then never runs again, and its job sat with the agent `running` until someone queued a `resume`. So the supervisor tracks the task count in claude's latest `system`/`background_tasks_changed` line. When a job session is `idle` after a `result` (or such a line arrives while it is), claude lists no background task, and its job still has an agent that keeps it, nothing is left to wake the session. If that still holds `missedEndMs` (60 s) later with no turn in between, the session queues its job a `resume` (`from: "daemon:supervisor"`, fixed text that says to record each finished agent's end), logs `missed-agent-end` with `roles` and the request id, and pokes the pool, which turns it like any request. It does this once per set of stuck agent runs (role and `startedAt`), so a turn that again leaves them unrecorded is not nudged in a loop. A claude that never sends `background_tasks_changed` gets no nudges.

**Trigger** (edge-triggered per request id). Every `pollMs` (2 s), after every `POST /api/requests` and after every `result`, the pool checks the trust digest, reads the pending requests once and routes each to its scope (`requestScope` in `lib/requests.ts`). Per session, it sets aside the budget-held requests (below) and takes the ids not yet in that session's `committed` set. If any are left and the session is not `busy`/`stopping`, it spawns a child if there is none (subject to the cap), writes the turn and records the eligible ids as in flight. A working `result` adds them to `committed`, which each tick prunes to ids still pending; a failed one (`is_error`) commits nothing and sets a retry time instead ("Failures" below). So one request causes at most one turn (a request the session leaves pending can't loop), a request that arrives mid-turn causes exactly one more turn, a child that dies mid-turn drops its in-flight ids so they retrigger, a turn that failed before claiming anything is sent again, and claimed (`in-progress`) requests never count. A pool start brings the inbox up even without work; the office and job sessions spawn only on demand, and the office only while `foreman.enabled` (with it off, pending `gate` requests get no spawn and no turn).

**Cap and slots.** When `maxConcurrent` job sessions are running, a job with fresh work is marked `waiting` (logged once as `waiting`). Slots go to waiting jobs in the order of their oldest pending request. When a job waits and some job session is `idle` and not kept, the pool stops the idle session with the oldest `lastResultAt` (`idle-stop`, `reason: "slot"`) and gives the slot away; that session resumes its conversation the next time it has work. A session is **kept** while a running agent keeps it, or for a grace of 30 s after the later of its last `result` and its last agent end (the gap between a review turn's end and its reviewers being recorded). Its agents are the `job.agents` of its job, counted only while `job.owner.session` is the session's own id, so another owner's agents (a human's terminal session) never keep it. A running agent keeps it only for 2 h after its `startedAt`, the ceiling `ownerStatus` uses, so a phantom can't hold a slot forever. A kept session still counts toward the cap: when every running job session is kept, the waiting job stays `waiting` and gets the next slot that frees, which the 2 s tick finds within one poll of the grace passing or the last agent ending. Each tick refreshes `kept` for running job sessions; it reports `agents` only, never the grace. After a job session's `result`, if its job is `done`, `cancelled` or `failed` (or gone) and no pending request routes to it, the pool logs `finished` and stops it (`stop`, `reason: "job-finished"`). Sessions that are off and clean, with no request routed to them, are pruned at the next tick; their files stay.

**Budget hold.** Limits are per job, so a hold is per session: `resume`, `rework`, `answer` and `revise-spec` requests whose job is at `waiting: budget` and still over a limit (`exceededKeys` in `lib/budget.ts`) are never sent or committed, and that session reports `held: "budget"`. `approve` (the acknowledgement), `cancel` and job-less requests are never held. Once a human raises or acknowledges the budget, the next tick sends the turn. A `held` log line is written when the session's hold changes. Spend scales with the number of live sessions.

**Files** (`.forge/runtime/daemons/`, gitignored, unversioned): `<scope>.json` holds `{sessionId, resumable, pid, serverPid, argv0, startedAt, spawnSessionId, lastTurnAt, logBase}`. `<scope>.log` gets every child stdout line verbatim, except that a JSON line with neither claude's `timestamp` (only its `assistant` and `user` lines carry one) nor an `at` gets the receipt time as `at`, so every line has a time; non-JSON stdout as `forge-raw`, stderr as `forge-stderr` (4 KiB per line), and the supervisor's own events as `forge-daemon` (`spawn`, `turn` (with `requests` and the session's turn number), `result`, `exit`, `stop`, `idle-stop`, `waiting`, `finished`, `resume-failed`, `session-changed`, `held`, `retry` (with `at`, `reason`, `attempt`, `requests`), `reaped`, `error`, `line-truncated`, `wake` (a turn claude started by itself), `agents-lost` (with `roles`), `missed-agent-end` (with `roles` and `request`); `stop` and `idle-stop` carry a `reason`). A stdout line over 8 MiB is dropped and replaced by a `line-truncated` marker. Each session rotates its own log to `<scope>.log.1` at spawn once it passes 20 MiB, and pauses its child's stdout while the log stream is full. Pool-wide events (a trust stop, a config refusal) are written to every live session's log. The old one-session `daemon.json` is reaped by the same proof and then ignored; `daemon.log` is never read.

**Offsets.** Every log line has an offset: `logBase` plus the line's byte position in `<scope>.log`. A rotation adds the rotated file's size to `logBase`, so offsets only grow. Offsets are the SSE ids and the history keys, so the dashboard merges live lines and older pages without duplicates. The last 200 lines of each session stay in memory for SSE replay.

**Session and resume.** Each scope keeps its own session id. The first spawn gets a fresh `--session-id <uuid>`; once a child of that session has written a line, `resumable` is set and later spawns (a restarted `forge dash`, new work after an idle or slot stop) use `--resume <uuid>`, passing `--plugin-dir` again because resume does not restore it. A `system`/`init` with another `session_id` replaces the stored one (`session-changed`). A `--resume` child that exits non-zero without ever emitting `system`/`init` lost its transcript: the supervisor logs `resume-failed`, undoes whatever that child's error `result` committed, starts one fresh session and re-ticks, without counting a failure.

**Failures** are per session. A spawn `error` with no pid (ENOENT, EACCES) stops wanting that session (`cannot start daemon: …`), with no retry. Unexpected exits with no `result` since spawn are counted; at 3 the session stops wanting itself (`daemon stopped after 3 failed starts: …`); any `result` resets the count. `idleStopMinutes` ends stdin and stops an idle child, keeping the session wanted. The window counts from the later of the last spawn or `result` and the last agent end, and never runs out while a running agent keeps the session. **Lost agents:** whenever a job session's child exits, for any reason (pool or session stop, `forge dash` shutdown, a trust change or other pool-wide stop, a permission-mode narrowing, failed-turn strike-out, a job-finished or idle stop, a crash), every agent of its owned job still marked `running` is ended with status `lost` and summary `lost: its daemon session ended`, through the same `recordAgent` path as `forge job agent <id> end --status lost` (an `agent-end` job event), and the session logs one `agents-lost` with `roles`. It happens before the stop resolves. Agents that already ended, and another owner's agents, are never touched, so the next session's `step` respawns the role (L1) or retries the reviewer (M1) instead of waiting on phantoms (G5). A failed `job.json` read or write here is logged as an `error` and the exit still completes. The synchronous last-resort SIGTERM from an `exit` handler marks nothing; the next orchestrator handles those agents as before. A `result` with `is_error` (claude reports an expired login or an exhausted quota that way, often with subtype `success`) means no request made progress: the child stays up, nothing is committed, and the session's `lastError` reads `last turn failed: …; retry at <time>` until a turn works or the session is stopped on purpose, so the dashboard shows it failing rather than idle. The session writes no turn before that time, which a `retry` log line records with its `reason` and `attempt`: when the child printed a `rate_limit_event` with `status: "rejected"` during the turn, the retry is at that window's `resetsAt`; otherwise it is a backoff that doubles from 1 minute (5 minutes for a limit without a reset time, such as an API key's spend cap) to 1 hour. A failure is a `limit` when that event was seen or the message says so (usage or rate limit, 429, 529, overloaded): limits are retried for as long as it takes. Any other failure is a strike, and at 3 in a row the session stops wanting itself (`daemon stopped after 3 failed turns: …`) and stops its child so the slot frees. A working turn clears the strikes and the backoff, as does a human's Start. In every case the other sessions keep running and the pool stays wanted; a session that isn't wanted spawns nothing until a human starts it (or the whole pool) again. What is repo-wide stops the whole pool and every child, with the error on the pool and in every session log: a trust-digest change, `daemon.enabled: false` at spawn, a `daemon.*` config problem, and symlinks under `.forge/trackers/`.

**Start and stop.** A pool start (dashboard Start, or `forge dash` booting with `enabled: true`) refuses while another live `forge dash` owns any record; otherwise it wants the pool, resets every session's wanted flag, failures and error, takes a new trust snapshot only when no child runs anywhere, and ticks. Stop stops every child. One session can be started (only inside a wanted pool, and never with a new snapshot) or stopped from its drawer's Log tab; a stopped job session stays listed and spawns nothing for new work until started again.

**Effort.** At every spawn, a session resolves its effort with `resolveEffort` (`lib/config.ts`), the one place levels combine. A session runs the orchestrator, so it resolves with no role: its job's `job.effort`, else `runtime.effort`, from the config bytes that spawn just hashed and the `job.json` read then. The inbox uses `runtime.effort` alone, and so does a session whose job is missing or unreadable. A level adds `--effort <level>` to argv after Forge's `--permission-mode` and before `--disallowedTools`, replacing every `--effort x` and `--effort=x` in `daemon.command`; with none, Forge passes nothing and the template's own `--effort`, if any, applies. The log records `{"event":"effort","level":<level> | "inherit","source":"job" | "config" | "none"}` right after `spawn` (a session never gets the `panel`, `role` or `complexity` sources that `resolveEffort` gives agents), and the session's `effort` in `/api/state` is the level its running child got (null while none runs, or when Forge passed none). A changed effort never stops, signals or messages a running child: it applies at that session's next spawn (an idle stop, a slot handover, a human's stop and start). Agents inherit their session's effort, since no `forge:*` agent's frontmatter sets one, and also get the level explicitly: every `spawn` from `forge job step` carries `effort` and every brief an `Effort:` line, which the orchestrator passes as the Agent tool's `effort`. An agent's level is resolved for its role: `job.effort`, the lens's panel `effort`, `runtime.efforts.<role>`, `runtime.effortByComplexity[job.complexity]`, then `runtime.effort`, and a builder on round 2 or later gets one level more unless the job's own effort set it. So agents started after a change already run at the new level while the session itself switches at its next spawn.

**HTTP surface** (consumed by the dashboard). `/api/state` has `config.daemon: {enabled}`, `config.effort` and `daemons: {enabled, wanted, maxConcurrent, live, lastError, inbox, office, foreman, jobs, clients}` (`foreman` is `foreman.enabled` from the latest config read), and each job row has `gateOwner` (`foreman`, `human`, or `null` when it waits on nothing or the foreman is off), where `inbox`, `office` and each `jobs[id]` are `{scope, wanted, running, status, sessionId, pid, lastTurnAt, lastResultAt, turns, failures, held, waiting, lastError, permissions, permissionMode, kept, effort}` (`kept` is `"agents"` while a child runs, the session isn't `stopping` and a running agent keeps it, else `null`; `effort` is the `--effort` Forge passed the running child, else `null`); `jobs` lists a session while it runs or stops, waits, is held, has an error, or was stopped by a human. `GET /api/events?session=<scope>` streams that session's `event: state` on connect (an off state for an unknown session) and on every change, its buffered lines after `Last-Event-ID`, then `event: line` with `id: <offset>` per new line (lines over 64 KiB become a `forge-truncated` marker), and `: ping` every 15 s; lines of other sessions are never sent. `GET /api/daemons/log?session=<scope>&before=<offset>` returns a page of complete lines read backwards from `before` (at most 256 KiB or 1000 lines, lines over 64 KiB as markers at their real offset, at most 16 MiB scanned) as `{scope, lines: [{offset, line}], start, end, more}`; only the current `<scope>.log` is served. `POST /api/daemon {"action":"start"|"stop", "scope"?}` answers 200 with the pool state; without a scope it starts or stops the pool (409 `{error}` for `start` while `daemon.enabled` is false or the `daemon.*` config has a problem), with one it starts or stops that session (400 for an invalid scope, 404 for an unknown job, 409 `start the daemon first` for a scoped start while the pool isn't wanted). `POST /api/requests` answers with the request plus `daemon: <pool wanted>`, and 400 for a `gate` request (only the CLI writes those), for a `run` without a valid `args.ref`, an `args.link` outside `approve` or not `new`, `none` or a ref, or an `args.n` outside `next` or 1..16. `POST /api/jobs {text, title?}` creates a job (title derived from the text unless given; 400 for missing, blank or over-20,000-character text or an empty title, 409 before `/forge init`), queues its `resume`, and answers `{id, title, branch, request, daemon}`. `POST /api/jobs/<id>/effort {"effort": "low" | "medium" | "high" | "xhigh" | "max" | null}` sets or (null) clears the job's effort through the same `setJobEffort` as `forge job effort`, and answers `{id, effort, previous, changed}`; it works while the pool is wanted, because `job.json` is outside the trust digest, and is 400 for any other body and 404 for an unknown id or `_inbox`. `GET /api/jobs/<id>` includes the job's `requests` (every status, oldest first, the last 50) and `request`, its `request.md` without the title line (at most 2,000 characters), which opens the drawer's Thread, and `requestFromTracker`, true only when the job's `created` event carries a ref (a job started from an issue), so a job linked later still shows `request` as the user's words.

**Terminal.** `forge daemon status` prints the dashboard and every session record from the runtime files (no server call). Each session has `{scope, job, pid, alive, sessionId, startedAt, lastTurnAt, logBytes, kept, agents}`: `agents` lists the sorted roles of the running agents of the job that session owns (read from the record's `sessionId` and the job's `job.json`), and `kept` is `"agents"` when one of them keeps it; both are `null` and `[]` when the session is not alive, is the inbox or the office, or owns no agents. The office sorts right after the inbox. `forge daemon log <job>|--inbox|--office [--lines N] [--follow]` prints a session log's tail as raw JSONL with every C0/C1 control character escaped, and `--follow` keeps printing new lines across rotations.

**Stopping and orphans.** Children are spawned `detached` with no shell, so each leads its own process group. A stop SIGTERMs the group and SIGKILLs it after 5 s. `forge dash` stops every session on SIGTERM/SIGINT before exiting, and an `exit` handler sends a synchronous SIGTERM to each as a last resort. `forge dash --stop` waits up to 12 s for the server, then reaps (`daemonReaped: true` when anything was). A pool being created also reaps. Each record (the legacy `daemon.json` and every `daemons/<scope>.json`, regular files with a valid scope name only) is proven on its own: if it names a live pid whose server is gone, the pid is signalled only after it is proven to be the recorded child: it is > 1 and not us or our group, it leads its own process group, `ps` reports a start time within 30 s of `startedAt`, its command line contains the recorded `claude` executable and `--session-id`/`--resume` followed by the recorded uuid. A live `serverPid` other than ours in any record means another dashboard owns the daemon, and a pool start refuses. None of this runs on Windows, so on native Windows a pool start is refused outright (`lastError` says why and links [SUPPORT.md](SUPPORT.md)), nothing is spawned, and the dashboard serves without the daemon; `forge dash` prints the refusal (`daemonRefused` under `--background`) and skips the `daemon.auth` question.

**Recorded framing** (claude 2.1.296, headless run in a scratch repo with the default `command` and `--plugin-dir` pointing at this checkout). The only line the daemon writes, `TURN_LINE`:
```json
{"type":"user","message":{"role":"user","content":[{"type":"text","text":"/forge requests"}]}}
```
followed by `\n`. Observed on stdout, one JSON object per line:
- `system`: `hook_started`, `hook_progress`, `hook_response`, `commands_changed`, `init` (at the start of every turn, carrying `session_id`, `agents` with the `forge:*` roles, `slash_commands` with `forge:forge`, `plugins` with this checkout as `forge@inline`, and `permissionMode`, the mode `daemon.command` passes), `task_started` / `task_updated` / `task_notification` around a subagent, `thinking_tokens`.
- `assistant`: content blocks `thinking`, `text`, `tool_use` (an `Agent` call with `subagent_type: "forge:builder"` ran the plugin's builder and returned a `tool_result`).
- `user`: `tool_result` blocks; a subagent's own messages carry `parent_tool_use_id`.
- `rate_limit_event`.
- `result`: one per turn (`subtype: "success"`, `is_error: false`, `num_turns`, `result`, `session_id`), the same `session_id` across turns of one process.

`/forge requests` is expanded headless as the plugin's skill: the session ran the skill's opening `forge doctor`, `forge sync`, `forge requests`. A second stdin turn in the same process produced a second `result` with the same `session_id`; closing stdin made the process exit 0; a new process with `--resume <id> --plugin-dir <checkout>` accepted a turn and remembered the first process's conversation. `--resume` of an unknown id prints one `{"type":"result","subtype":"error_during_execution","is_error":true,"num_turns":0,…}` line, `No conversation found with session ID: <id>` on stderr, and exits 1.

## Foreman

Unattended runs stop at every human gate. With `foreman.enabled` (off by default; docs/CONFIG.md "Foreman"), the office session decides the gates it is allowed to, through `forge:assistant` sub-agents, so a human is needed only where policy says so.

**Routing.** `forge job set` that parks a job on `spec-approval`, `split-approval`, `escalation`, `rounds-exhausted` or `conflicts` (a new park, or a different gate) whose class is in `foreman.decides` enqueues one `gate` request `{job, args: {gate, reserved}, from: "forge"}`, unless one for that job and gate is pending or in progress. `forge pr sync` (never `forge pr merge`) does the same for a job waiting on `pr-review` with failing checks, or with changes requested or unresolved threads from someone with write access (`OWNER`, `MEMBER` or `COLLABORATOR`; a stranger's comment alone never starts an unattended rework): `args.gate: "pr-feedback"` and `args.key: <head sha>`, once per head in any status, so a push re-arms it. `requestScope` sends every `gate` to `_office`; the dashboard (`POST /api/requests`) and `forge requests add` cannot create one. The pool spawns the office within the tick, writes it the fixed `/forge requests` turn, and treats it like the inbox for trust, `DENY_TOOLS`, budget holds and failures, never counting it against the cap.

**The turn** (`skills/forge/reference/foreman.md`). Claim, then `forge job assist <job> --gate <gate>`, which returns `{gate, stale, reserved, model, effort, subagent: "forge:assistant", brief}` and writes nothing. The office spawns one assistant with that brief, reads its single line `ASSIST: approve|revise|rework|escalate · <reason>` (anything else is `escalate`), records the verdict with `forge job human <job> <action> --actor foreman --note "<reason>"` and a `job set`, queues a `resume` for the job's own session, and acks. On `escalate` or a reserved gate it leaves a `job note` and acks `rejected`, and the job keeps waiting for a human.

**Context rule.** The office session never reads a job file: the brief `forge job assist` returns carries absolute paths, the gate class and the reserved list, never file content, and the procedure names only `forge` calls. The assistant reads the files and writes `feedback.md` itself on `revise` or `rework`, so the office's log holds CLI JSON and one-line verdicts.

**Authority, enforced by the CLI.** `forge job human … --actor foreman` runs every check before any write, and a refusal (exit 1) leaves `job.json` and `events.jsonl` untouched. It is refused outside the `_office` scope; inside it, `job human` without `--actor foreman` is refused too. It needs a `--note`, takes no `--link` or `--reason`, and needs the job to be waiting on a class in `foreman.decides` (`pr-review` counts as `pr-feedback`) with an action of that class: `approve-spec`/`revise-spec`, `approve-split`/`revise-split`, `approve`/`revise-spec`/`rework` for escalation and rounds-exhausted, `approve` for conflicts, `rework` for pr-feedback. It is refused when a `foreman.reserved` pattern matches the reason, the note, or (for escalation and rounds-exhausted) the `## Why` and `## For the human` sections of `decision.md`; a `decision.md` that isn't a small regular file counts as a match, and so does a security review whose latest recorded verdict is anything but `PASS` (`CHANGES`, `MALFORMED`), at any gate. A `rework` on pr-feedback also needs a pending or in-progress `gate` request keyed by the PR's current head sha, so the foreman acts only on feedback sync armed for that push. Patterns match case-insensitively as whole phrases (no letter or digit on either side) and are escaped literals, so matching is linear; a `reserved` that isn't a list of non-empty strings makes every gate reserved. In the office, `forge job set` only carries out a recorded decision: the job must still wait, its latest `human` event must be the foreman's and newer than the park, and the change must be that action's `--state running` with its stage from the gate table, with no `--field`, `--waiting-on` or `--reason`. Of the `forge job` subcommands only `assist`, `human`, `set`, `note`, `show`, `get`, `list` and `step` run there, and the office also may not `worktree create`, `job advance` or `pr merge`. The assistant has no Bash at all (`disallowedTools: Bash, Edit, NotebookEdit`), so text it reads reaches the CLI only through its one-line verdict.

**Ship policy.** `foreman.ship: merge` (with the foreman on) counts as `merge.auto: true` in the approver brief's `Merge: auto` line and in step rule PR4 only. The approver still judges `merge.autoWhen` and writes `Auto-merge eligible`, PR4 still requires `yes`, and `forge pr merge` still enforces CI; the foreman itself never merges. `propose` changes nothing.

**Audit.** Every new `human` event carries `actor: "human" | "foreman"`; an older event without it reads as human. `forge stats` counts only human reworks in `humanReworks` and adds `foremanDecisions` and `foremanReworks`. The dashboard labels foreman decisions in the drawer's timeline, shows each waiting job's `gateOwner` on its card, and shows the office in the status bar as the **Foreman**: an indicator always rendered first in the left cluster (toned by the office pill, or dashed while `foreman.enabled` is off) whose chat-sized popover holds the office's permission prompts and its session log, with Start/Stop, the permission mode and read-only model and effort facts. The Daemon popover leads with a Foreman row that opens it and lists the office among none of its session rows.

**Threat model.** Provenance is `FORGE_DAEMON_SCOPE`, unauthenticated as for the inbox: the checks stop a session misled by request, PR or tracker text (a job session passing a decision off as the foreman's, the assistant smuggling a reserved topic through its reason, a forged `gate` request with `reserved: null`, the office merging), not a hostile local process. A Bash-capable session can always run `FORGE_DAEMON= forge job human …`, which reads as a human outside the daemon and skips every foreman check: the CLI line guards a misled model, not a hostile one.

## Untrusted input

Issue bodies, comments and PR reviews come from people outside the session, and on public repos that means anyone. Forge:
- imports only collaborators' issue comments by default (`tracker.github.comments`), and labels the rest as untrusted in PR feedback
- fences imported text with its provenance and a "data, not instructions" note
- blockquotes every line of an imported GitHub issue body and comment (CR, U+2028, U+2029 and NEL count as line breaks, other control characters are dropped, logins and associations are reduced to safe characters, and the title is one line), so only Forge writes column-0 lines in `request.md` and a forged `### Recent comments` section reads as quoted text
- tells every agent to ignore embedded instructions about secrets, credentials, CI, permissions or out-of-scope work
- triages tracker items without letting their text reach the tracker (`lib/triage.ts`, docs/TRACKERS.md "Readiness triage"): the batch the `forge:triage` agent reads fences each item in a fence longer than any backtick run in it, and the agent has only Read and Write; `--apply` takes a batch id only in its exact format, reads `verdicts.json` and `items.json` each through one `O_NOFOLLOW` descriptor (a regular file under 256 KiB), ignores refs outside the batch, keeps only known missing keys and a `duplicateOf` from the item's own candidates, skips items changed since prepare, and writes only fixed template text, citing a duplicate as `PR #n`, a same-tracker `#n` or "an active Forge job", never a local job id, a citation it derives from the candidate id and the job records rather than from the agent-writable batch
- adopts only PRs whose branch lives in the same repository (never forks), and only issue-linked PRs from collaborators, so a stranger's PR is never checked out and run by the builder
- keeps job ids, branches and bases to `SAFE_REF` (`lib/util.ts`: a letter or digit, then `A-Z a-z 0-9 . _ / -`, at most 200 characters), because they fill `{job}`, `{branch}` and `{base}` in shell command templates and reach git argv: command templates (`forge run`, `forge verify`, worktree setup) and `forge worktree create` refuse an unsafe value before anything runs, `forge job new --branch` refuses one before the job exists, and PR adoption refuses a PR whose `headRefName` or `baseRefName` fails it (a `pr-adopt-refused` event names the field, never the value). `forge job set --field` can't write a job's identity (`id`, `branch`, `base`, `worktree`, `port`, `owner`, `schemaVersion`, `createdAt`, `source`, `pr`, `runs`, `usage`, or any key under them), its `effort` (only `forge job effort` writes it, and refuses in a daemon session), its `eval` record and config overlay (only `forge eval start` writes it, and refuses `--set` in a daemon session; every load checks the overlay again and fails closed), a `kind` of `retro` or `eval` (only `forge job new --kind retro` and `forge eval start` create those, because step gives a retro job a fixed review panel and an eval job no PR or escalation gate) or any `__proto__`, `constructor` or `prototype` segment, so a misled session can't point a job at `main` before `forge pr open`; the commands that own those keys still set them. The extra arguments of `forge run <job> <name> -- <args…>` reach the shell too: each is wrapped in single quotes and never filled again as a placeholder, and an argument containing a quote, backslash or control character (which would end the quoting in sh, bash, zsh or fish), a word before `--`, or any argument with `--background` is refused before anything runs. Arguments are opt-in: a template without `{args}` refuses them, so a configured command that reaches outside systems can't be steered with flags a session picks. Arguments are also refused where the template would not keep them as plain words: an `{args}` that isn't a whole unquoted word (inside `'…'` or `"…"`, where `$(…)` expands or a `'` ends the quoting, or after a backslash), or any template with a heredoc, `$'` or `\'`, where `\'` does not close the quote. `forge verify`, worktree setup, background servers, the regenerate build and eval grading have no argument path at all, so arguments can never narrow the gate
- refuses to publish a likely credential, in its own code rather than a prompt (`lib/secrets.ts`, docs/CONFIG.md "Secret scanning"): verify scans every commit of the branch, its messages and the staged changes before any configured step, and `forge git commit`, `forge pr open` and every tracker adapter's writes refuse a likely secret (`secret_found`) before git, `gh` or the adapter is called. Findings are masked and fingerprinted, never printed. The allowlist (`.forge/secrets-allow.txt`) is read from the main checkout only, and the mode from the main checkout's config, so a branch can neither allowlist its own leak nor turn the gate off; diffs run with the same pinned git config and `--text --no-ext-diff --no-textconv` as the integrity report, so attributes and drivers can't hide added lines. A refusal parks the job on `waitingOn: human`, and no agent retry gets past it
- limits what an agent fooled by that text can do when nobody is watching: the daemon's default `allowedTools` names only the git/gh subcommands the agents use (no `git -c`, `git rebase --exec`, `git config`, `git log --output` or `gh api`), validation refuses blanket git/gh entries and permission-widening `daemon.command` flags, and the session runs git with hooks and fsmonitor pinned off ("Daemon security" below)

**Request provenance is not authenticated.** A request's `from` (`dashboard`, `cli`, `daemon:<scope>`) and the daemon-session checks in `forge requests` come from the caller's environment (`FORGE_DAEMON`, `FORGE_DAEMON_SCOPE`), which a session's own commands could drop. They are guardrails that keep a session following the skill from acting on another job's requests or queuing anything but a `resume` hand-off, not a boundary against a misled session: such a session can already run `forge job human …` or `forge job budget --ack` directly through `Bash(forge:*)`. The defences against that are the ones above: what reaches agents is fenced as data, and the unattended session's tools are narrow.

## Authorship policy

`lib/attribution.ts` defines what counts as AI attribution: signature lines and trailers, not mentions. It is shared by the Bash `PreToolUse` hook (`hooks/no-ai-attribution.ts`, which blocks before anything is written), by `forge pr open` (which scrubs branch commit messages with a non-interactive `rebase --exec`, then pushes with `--force-with-lease` if anything changed), and by the GitHub tracker (which strips issue and comment bodies). On Node older than 22.18 the hook cannot load and exits 1, which Claude Code does not treat as a block, so the policy is not enforced there. The policy is on by default (`aiAttribution: forbid`).

## Review policy

Reviewers tag findings `[blocker] [major] [minor] [nit]`. The CLI decides the verdict from the tags and the repo's `review.blockOn`, not from the reviewer's own first line. This keeps the threshold consistent across lenses and models: "CHANGES over a nit" or "PASS over a blocker" can't slip through. A review without a verdict line is `CHANGES` when its tags already force a round, otherwise `MALFORMED` and re-run once; a second malformed review is counted as `CHANGES` (`--malformed changes`) so a reviewer that cannot follow the format cannot stall the job. A lens with no file is `PENDING` while its reviewer (`reviewer:<lens>` in `job.agents`) has not ended for that review, and `MISSING`, with the expected path, once it has: an agent can claim a review it never wrote, so the orchestrator re-spawns it rather than waiting. `forge job round` and `forge job paths` create the review directory before any reviewer is briefed.

**Model diversity.** A gate that runs on the same model as the builder tends to share its blind spots: it finds the code plausible for the same reasons the builder wrote it. `forge roster` therefore always reports which gatekeepers (the approver, then each panel lens) share the builder's model family. The family is `opus`, `sonnet`, `haiku` or `fable` when the model string names one, else the whole string, with `inherit` resolved through the orchestrator's model. With `runtime.diversity: true`, `forge roster` and `forge init write` turn each overlap into a warning. It never blocks a job: picking models is the human's call. The Balanced init preset already puts the approver on a different family.

## Usage accounting

The orchestrator records every agent start and end. With Claude Code, `--import` reads the subagent transcript (`<session>/subagents/agent-<id>.jsonl` under `$CLAUDE_CONFIG_DIR/projects`, else `~/.claude/projects`). It looks first under the job's own sessions (the owner's, then the last five in `runs[]`) in this repo's project dirs, and falls back to scanning every project dir for an agent whose parent session isn't recorded. The orchestrator records a background agent's id as soon as it is spawned (`forge job agent <id> attach`), so the dashboard can follow that transcript while the agent runs. Input and cache tokens come out exact, along with tool calls (by unique block id) and duration. Output tokens are estimated from the logged content, because transcripts store the stream's opening usage snapshot. A resumed agent (SendMessage, as the builder is for rework) appends to the same transcript, so each agent record keeps `importedThrough`, the last transcript timestamp imported per agent id, and the next import of that agent counts and times only the lines after it. Without a transcript, the runtime-reported total is used with a blend assumption, and the dashboard shows coverage (how many agent runs reported usage, and how many exactly). Prices live in `lib/pricing.json` (dated, overridable via `usage.pricing`). For subscription plans they're API-equivalent figures, not a bill.

## Dashboard security

The server binds 127.0.0.1 only and answers only requests whose Host is a loopback name, which defeats DNS rebinding. GETs are read-only. POSTs (enqueue a request, create a job from free text, start or stop the daemon, answer a session's permission prompt, switch a session's permission mode, change a setting, set a job's effort: `/api/requests`, `/api/jobs`, `/api/daemon`, `/api/daemon/permission`, `/api/daemon/mode`, `/api/config`, `/api/jobs/:id/effort`) need a random per-process token embedded in the served page, a matching Origin and a JSON content type, so other sites in your browser can't trigger work. A `resume` for a job whose owner is live (by the time rule, after the session-record proofs, judged as the job's own daemon session would judge them) is refused with 409 naming the session, whatever its `args`, and nothing is queued, unless that owner is the job's own running daemon session, which the resume reaches and which reclaims as itself (`ownerStatus.jobSession`). The check runs after the token, Origin and JSON guards and only for a syntactically valid id with a `job.json`; it is advisory, because the job session's own claim inside the job lock still decides. `GET /api/doctor` runs `git` and `gh`, so it also needs the token, and any Origin it sends must be ours. `GET /api/github/preview?url=` (the hover card on GitHub links) runs `gh api graphql` on the user's login and rate limit, so it takes the same token and Origin check; it answers only an `https://github.com/` repository, pull request, issue or commit URL, parsed into an owner, a name and a number or hex sha before `gh` is called with no shell, caches answers per page, and returns GitHub text that the card renders as text. `GET /api/config` (the settings schema and effective values) and `GET /api/about` (versions) only read: its commit, which can take `git` to find, is computed once when the server starts, never per request. `GET /api/jobs/:id` proves the owner against the session records, which can run `ps`, so it rejects a foreign Origin or a cross-site `Sec-Fetch-Site`, as the log routes do. `POST /api/config` goes through the same `setConfigValue` as `forge config set`: only the keys `lib/config-fields.ts` marks editable can be written, and none of them can name a command, file, module, tool or repository Forge runs or writes to, or loosen a security or attribution policy, so a forged or mistaken POST can't turn into code execution. It is refused with 409 while the daemon is wanted, because any change to `config.yml` would stop the daemon through its trust check, and the server never re-blesses that snapshot: only a human's Start does. The `/api/events` stream follows the same loopback Host rule and also rejects a mismatched Origin. Everything the page renders goes through Svelte's escaping interpolation; raw HTML is limited to the escape-first markdown renderer and budget/screenshot builders (a test enforces the allowlist), so agent- and issue-authored markdown is escaped first, and inline markdown is tokenised into code, link, bare-URL and text segments that are each rendered once, so no autolink, emphasis or chip pass ever runs over generated HTML, and session log lines (headless session output) are parsed: tool input, tool results, supervisor and other lines render as plain text, while assistant and thinking prose, subagent prompts and reports, and the Thread's request text and replies render only through the escape-first `md()` (each surface has a Raw view of the exact text, and items over 20,000 characters stay text), and a session's stream is opened only while its job panel's Log tab (or the Inbox log in the status bar's Inbox popover, or the office log in the Foreman popover) is shown and the tab is visible. `GET /api/jobs/:id/transcript` (a page of a job agent's, or an interactive owner's, Claude Code transcript, read backwards) and `GET /api/jobs/:id/transcript/events` (its live tail) are GET only and loopback only, refuse a foreign Origin or a cross-site `Sec-Fetch-Site`, and need the token: as the `x-forge-token` header for the page, and as a `token` query parameter (compared in constant time) for the stream, because EventSource can't send headers; the token reaches that URL only on our own same-origin page, which already embeds it. No query value is ever a path or a path segment: `agent` must be an own key of the job's `agents`, and every path is derived from job state, a session id that must be a UUID and an agent id that must match `^[A-Za-z0-9_-]{1,100}$`. Only this repo's project dirs are tried (the slugs of the root, its realpath and the job's worktree under `$CLAUDE_CONFIG_DIR/projects`, else `~/.claude/projects`), never another repo's: the worktree counts only when it is the job's own (`<worktrees.root>/<id>`) or sits under the worktrees dir, as written and resolved, since job.json is agent-writable. A project dir must resolve to exactly `<projects>/<slug>` and the transcript's realpath must stay inside that slug dir (checked at lookup and again when the file is opened, not merely anywhere under the projects dir), and the file is then checked to be a regular file and read through one non-blocking `O_NOFOLLOW` descriptor (held open for the stream's life, so a symlink swapped in later can't redirect it), so a planted symlink or FIFO is a 404. The owner route answers only for an owner in no daemon session record. The stream counts toward the event-stream cap, is recycled like the others, never receives the pool's frames and stops polling the file when it closes. `/api/state` carries each running agent's last tool call or line of text from the last 64 KiB of its transcript, cached by size and mtime. Transcript text is returned as data inside JSON and SSE frames and rendered as text, or through `md()` for prose, like the session log. Job HTML (mockups) is shown in a sandboxed iframe and served with `Content-Security-Policy: sandbox allow-scripts; default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data:; font-src data:`, so a mockup must be self-contained: it blocks every subresource load (external scripts, styles, images, fonts, media, frames, workers) and every connection (`fetch`, XHR, WebSocket, EventSource), so secrets a misled agent wrote into a mockup aren't sent off the machine when a human opens it. CSP has no working directive for the rest, which stays residual risk: the frame navigating itself (`location = …`), a user clicking a link, WebRTC and DNS prefetch. File reads are confined to the job directory. Screenshot images are served only from a job's `screenshots/` dir, only as PNG/JPEG/WebP (never SVG or other active types), with `nosniff`, a `default-src 'none'` CSP, `Cross-Origin-Resource-Policy: same-origin` (so another site can't embed them, even though its `<img>` would carry a loopback Host), a 10 MiB cap, and a realpath check that keeps symlinks from escaping the job dir; the file is then checked and read through one descriptor. The page loads no external scripts, styles or fonts: Tailwind is compiled into the committed `dashboard/dist/`, the three typefaces are vendored woff2 files (`dashboard/fonts/`, OFL) served from the same origin, and the film grain is an inline SVG `data:` URI. The server serves only the page (`no-store`, token injected) and the hashed `assets/*.js|css|woff2` files that `dist/manifest.json` lists (never SVG or HTML), matched by exact path and cached immutably. Nothing is served by directory, so the sources, the manifest and the rest of the plugin root never are.

`forge dash --dev` (what `npm run dev` runs) changes only where the page and assets come from: the fixed `node_modules/.cache/forge/dashboard-dev/` inside the plugin root, which is exactly as trusted as `dashboard/dist/` (anyone who can write either can already rewrite `lib/server.ts`). It takes no path, so it can't serve a job worktree's files. The loopback Host, token, Origin and JSON-POST guards and the manifest allowlist are the same in dev mode. The flag is CLI-only: no config key and no `/api` route sets it. A dev dashboard never starts the daemon by itself (only Start does), so a fresh clone of a repo that commits `daemon.enabled: true` doesn't boot a paid session, and it refuses to start beside a live dashboard for the same repo instead of taking it over.

## Daemon security

The daemon runs an unattended agent under `daemon.allowedTools`, asking a human in the dashboard about anything else (or, with `--permission-mode dontAsk`, refusing it, or, in a session a human switched to `auto`, letting Claude Code's classifier decide), so its inputs are narrow on purpose:
- **One fixed stdin turn.** Every session gets only `TURN_LINE` (`/forge requests`) as a message. The only other stdin lines answer claude's own `can_use_tool` permission requests ("Permission prompts" below), carrying nothing from HTTP but the decision, or ask claude to switch permission mode ("Permission mode" below), carrying one value from a fixed list. Request text, request and job ids, config values and HTTP bodies never reach stdin; the session reads requests through `forge requests`, where the skill treats them as the human's words about one job, never as rules. Free text from the dashboard's command bar (`POST /api/jobs`) is written only to the new job's `request.md` (and, through the derived title, `job.json` and `events.jsonl`); the `resume` queued for it carries no text.
- **The scope travels in the environment only, validated.** A session learns its scope from `FORGE_DAEMON_SCOPE`, set by the supervisor from a routed request whose job id matched `^[A-Za-z0-9][A-Za-z0-9._-]*$` (at most 200 characters) and has a `job.json`; anything else routes to `_inbox`, which can't be a job id. Under `FORGE_DAEMON=1`, `forge requests list|claim|ack|scope|add` refuse a missing or invalid scope, list only that scope's requests, refuse to claim or ack a request that doesn't exist or belongs to another scope, and queue only `resume` hand-offs. These keep a session that follows the skill in its lane; they are not authentication (see "Untrusted input"). Request ids are checked against their `<time>-<id>` format before any path is built from them. Runtime file paths are built only from validated scopes.
- **argv comes from the repo's config, with no shell.** `daemon.command` is split into words and run directly, and placeholders expand to single arguments. Nothing from HTTP or requests reaches argv. A session id read back from a session record or a child's `system`/`init` must be a uuid before it can follow `--resume`, so a planted value can't become a flag.
- **Trust boundary: `.forge/config.yml` is code.** Whoever can change it can run code through the daemon, exactly as through `commands.*` (which verify runs through a shell): validation refuses the claude flags that widen permissions (`--dangerously-skip-permissions`, `--permission-mode bypassPermissions`, `--settings`, `--mcp-config`, `--add-dir`, `--agents`, a second `--plugin-dir`, a literal `--allowedTools`; docs/CONFIG.md "Daemon" has the full list), but the session still runs `commands.*` through `forge run`/`forge verify`, and `daemon.enabled: true` in committed config starts an unattended, paid session on every machine that runs `forge dash`. The config is read from the main checkout only, never from a job worktree or a PR branch, but a merged change applies everywhere. Give `daemon.command`, `daemon.allowedTools` and `daemon.enabled` code-owner review, like CI config. The session itself can't use this route (next bullet). The validator's rule that the first word is a bare `claude` or an absolute path to `claude` outside the repo catches mistakes (a migrated shell template, a relative path that would run a repo file); it is not a security boundary. Configured commands run without the `FORGE_DAEMON*` markers: the trust check guards the session's own `forge` calls, and a command's nested `forge` call against a scratch repo (a test suite) must not be judged by it. A command can run any code anyway, so that check never bound it. The git pins below still apply to commands.
- **The session can't change what Forge executes.** Its cwd is the main checkout and it has `Edit`/`Write`, so an agent misled by tracker or PR text could otherwise rewrite `commands.*` (which `forge run`/`forge verify` run through a shell) or `daemon.*` (picked up at the next spawn or resume). Three layers, innermost first:
  - *The CLI checks at the sink.* When a human starts the daemon (dashboard Start, or `forge dash` with `enabled: true`), the supervisor takes `trustDigest`: a sha256 of the checkout's realpath, `.forge/config.yml`, `.forge/secrets-allow.txt` (or its absence: a session that could edit it could allow its own leak) and every file under `.forge/trackers/` (custom tracker modules `forge` imports). It hands the digest to the session as `FORGE_DAEMON_TRUST`. Under `FORGE_DAEMON=1`, every `forge` command recomputes it before reading config and refuses on a mismatch, or when the variable is missing. The check catches every route, including Bash (`git mv -f`, a redirect) and a fake checkout reached through `cd`. `forge init write`, `forge migrate` and `forge config set` refuse outright, because they write config.yml through `forge` itself. config.yml is read once, and the bytes that were hashed are the bytes parsed. A custom tracker module is checked again just before it is imported. Any symlink under `.forge/trackers/` is refused (its target could change without the link changing), and the walk never follows one. What the digest can't see: files a tracker module imports from outside `.forge/trackers/`, so keep tracker modules self-contained.
  - *The supervisor stops the session.* Every poll, and before any spawn, it compares the digest with the one taken at start. On a change it stops the child and stays stopped with an error in the dashboard; respawns after an idle stop or a failed resume reuse the old snapshot, so a change made during a turn is never blessed by a restart. A spawn hashes config.yml once and builds argv from those same bytes, so a file swapped and restored between two reads can't slip in. Only a human's Start takes a new snapshot, and only when no child is running. A human editing config while the daemon runs gets the same stop, which is the price of not being able to tell the two apart.
  - *Claude Code refuses the write.* `--disallowedTools Edit(.forge/config.yml),Edit(.forge/trackers/**),Edit(.forge/secrets-allow.txt)` follows every `daemon.command`, whatever the template says. Edit rules cover every file-writing tool and Bash redirections. Relative paths anchor at the session's cwd (the main checkout, so job worktrees, where a self-improvement job legitimately edits Forge config, are unaffected), deny beats allow in every mode, and subagents inherit the rules. This layer does not cover programs that write files themselves (`forge`, `git`), which is why the first layer exists. `.claude/` and `.mcp.json` are already Claude Code protected paths, which are never allowed without a human: `dontAsk` refuses them, and `default` asks.

  The anchor is the session's environment, which it can't change: Bash allow rules don't match a command with a leading `VAR=…` assignment (except a few known-safe variables), and `env`/`export` aren't allowed. This keeps the *repo's* trusted commands in force; it does not stop those commands from running code the job wrote, which every verify does by design (that code is reviewed after verify, not before).
- **Start and stop** need the dashboard token, a matching Origin and JSON, and a pool `start` additionally needs `daemon.enabled: true` and no `daemon.*` validation problem. A scoped start only re-enables one session inside a pool a human already started, so it never takes a trust snapshot. The config migration never sets `enabled`. Concurrent start/stop POSTs never leave more than one child per session: a start while a child exists or is stopping spawns nothing new.
- **SSE is loopback-only and per session**, rejects a foreign Origin and any request whose `Sec-Fetch-Site` is not `same-origin`/`none` (the same `readGuard` the history route uses), syntax-checks `session` (400 otherwise), sends a stream only its own session's lines, sends no CORS headers, allows 8 streams at once across all sessions (`503` beyond), ends any client more than 1 MiB behind, and recycles every stream after 5 minutes (EventSource reconnects with `Last-Event-ID`). The dashboard opens only the stream of the session on screen. Another site can never read a stream. In a browser that sends neither Origin nor Fetch Metadata on a no-cors GET, a cross-site page can still occupy slots until they are recycled; that costs the live log's availability, never the daemon.
- **History reads are confined.** `GET /api/daemons/log` validates the scope before building a path, requires the daemons dir to be the real `.forge/runtime/daemons` (not a symlink to elsewhere), resolves `<scope>.log` with realpath and serves it only from inside that dir, and reads it through one descriptor opened `O_NONBLOCK` and `fstat`-checked as a regular file. Session records (`<scope>.json`) are read through one `O_NOFOLLOW|O_NONBLOCK` descriptor and must be regular files under 64 KiB, or they count as absent. Logs are opened for appending with `O_NOFOLLOW|O_NONBLOCK` and must be regular files (a session whose log can't be opened keeps running without one), and `forge daemon log` opens them the same way for reading. So a symlink or FIFO planted in the runtime dir is never followed and can't hang the server, on read (the history route, `/api/events`) or on write (session logs, reap notes).
- **Permission prompts are answered from the dashboard only.** Every daemon command ends with `--permission-prompt-tool stdio`, so claude sends each call it would ask a person about to the supervisor as a `control_request`. The supervisor holds it in memory (never in a file the session could edit), shows it in `/api/state`, and answers when a human posts `POST /api/daemon/permission` with the token, a matching Origin and JSON. The body names a scope, the supervisor's uuid for the prompt and a decision (`allow`, `session` or `deny`); the reply is built from claude's own request: an allow echoes its input unchanged, a deny carries fixed text, and "allow for this session" grants only the allow rules and absolute directories claude suggested, rewritten to the `session` destination, so suggestions to save rules to a settings file or change the permission mode are dropped. There is no CLI command to answer a prompt, because the session itself runs `forge`. Prompts end with their child, at most 20 wait per session, and any other control request subtype gets an error so claude never hangs. What a prompt shows (the input, the agent's description, the blocked path) is session output and renders as text. A prompt is exactly as safe as the human reading it: the tool, its full input and any blocked path are shown, and the agent's description is labelled as its own words.
- **Permission mode is a human's choice, held in memory.** `POST /api/daemon/mode` (token, matching Origin, JSON) names a scope (validated, and a job must have a `job.json`) and one of `default`, `auto` or `dontAsk` (lib/daemon.ts `PERMISSION_MODES`); anything else is a 400. The pool keeps the choice in memory only: session records live in `.forge/runtime/`, which the session can write, so a mode read back from disk would be one the session could choose for itself. A running child gets a `set_permission_mode` control request; a later spawn gets `--permission-mode <mode>` in place of the template's. Until claude reports its mode (at its first turn's init) the supervisor takes the one the child was launched with. A switch claude refuses or doesn't confirm fails closed: a narrowing one stops the child, so the next spawn starts in the chosen mode, and a widening one leaves the choice at what the child still reports. `auto` stays refused in `daemon.command`, so a repo's config can't put every session on every machine that runs `forge dash` into it: only a human at the dashboard can, for one session, until that `forge dash` stops. In `auto`, Claude Code's classifier approves calls outside `allowedTools` without a human, so a misled agent's call may run unread; the deny rules, the trust check and the git pins below still hold. `bypassPermissions` is never offered, and claude refuses it on a session not launched with `--dangerously-skip-permissions`, which validation forbids. There is no CLI command to switch modes, for the same reason there is none to answer a prompt. **Auto on one session reaches the whole daemon.** The dashboard serves its token to any local client and a non-browser client can send any Origin, so a session whose calls run without a human (Auto, or one a human allowed `curl` to) can read the token and post to `/api/daemon/mode` or `/api/daemon/permission`: switch other sessions to Auto, or answer their prompts and its own. Nothing on loopback tells the page apart from a session's process, so treat putting any session in Auto as trusting every session's input.
- **Effort is a human's per-job setting, read back from `job.json`.** The level reaches argv only as one word from the fixed list (`EFFORTS` in `lib/schema.ts`), and never stdin. `normalizeJob` reads anything else in `job.json` as null and `buildArgv` ignores a value outside the list, so a hand- or session-written `"--dangerously-skip-permissions"` or `"high --add-dir /"` never becomes an option. An invalid `runtime.effort` is a `daemonProblems` refusal, so no session starts. `withEffort` drops every `--effort` and `--effort=` in `daemon.command`, so a duplicate can't win over Forge's. `forge job set --field effort=…` is refused, and `forge job effort` and `forge job new --effort` refuse under `FORGE_DAEMON=1`, so a misled session can't raise its own or another job's level through the CLI. `POST /api/jobs/:id/effort` takes the token, a matching Origin and JSON, an existing job id and a value from the list or null. Residual risk: a session can still write a valid level into its own `job.json` with `Write`, as it can `budget.limits`. That costs tokens and time, bounded by `pipeline.budget` and visible in the session log's `effort` event and the card chip, and it never widens what the session may do. `complexity` is session-writable through `forge job set --field`, but only as `low`, `medium`, `high` or null, and it only selects among levels a human configured in `runtime.effortByComplexity`, which never reaches a session's argv. That is why, unlike the permission mode, effort is read back from disk: it is a human's setting that must survive a `forge dash` restart.
- **Narrow permissions, still not a sandbox.** Anything `allowedTools` doesn't list is asked about (or refused under `dontAsk`), and subagents inherit the list. The default allows Bash only for `forge` and specific git/gh subcommands (rev-parse, merge/rebase `--abort`; `gh pr view|list|checks`, `gh run view`). The session's cwd is the main checkout and `cd` and `git -C` aren't allowed, so a bare `git add`/`git commit` would act on the base branch: agents stage and commit through `forge git add|commit <job>`, which runs git with the job's worktree as cwd (refusing the main checkout, a branch other than the job's, and a merge or rebase in progress for `commit`), takes only `--message`/`--message-file` (a file inside the job dir) and paths, so no `-c`, `-C`, `--git-dir`, `--amend`, `--no-verify` or `--author`, refuses paths outside the worktree or in a `.git`, checks the message for AI attribution, clears `GIT_DIR`-style variables, and under `FORGE_DAEMON=1` runs git with the session pins below (outside the daemon, a human's hooks run). Claude Code matches each part of a compound command against the rules and won't match past `git -c` or an env assignment, so `git -c core.sshCommand=…`, `git -c alias.x='!…'` and `FOO=… git …` are refused. `git diff|log|show|range-diff` are left out because `--output=<file>` writes wherever git can, and Claude Code's protected-path check covers its own file tools, not git: `git log --format=… --output=.git/config` would plant a textconv or filter driver that the next diff or add runs. Agents read history through `forge git`, which refuses `--output` (git accepts no abbreviation of it), `--ext-diff`, `--textconv` and `--open-files-in-pager`, and forces `--no-ext-diff --no-textconv`. `git rebase` is left out because `--exec` runs shell: the integrator starts merges and rebases with `forge integrate --keep-conflicts` and finishes them with `forge integrate --continue`, which refuses a rebase todo holding anything but picks. `git mv` is left out too: given a `x/../.git/config` destination it reports an invalid path, then renames the file anyway and exits 0. `gh api` and other GitHub writes are left out; Forge's own writes (push, PR, labels, comments) go through `forge`. Validation refuses `allowedTools` entries that undo this (unscoped `Bash`, bare `git`/`gh`, `git -…`, `git config|grep|submodule|bisect|…`, `git diff|log|show|range-diff|…`, `git mv`, `git rebase`, `gh api|extension|alias|auth|…`); the list catches known forms and is not exhaustive.
- **Git hooks are off in the session.** `Edit`/`Write` are unscoped, and a repo can point `core.hooksPath` at a tracked directory (`.githooks/`, unlike `.git/` and `.husky/`, isn't one of Claude Code's protected paths), so a hook written there would run on the next `git commit`, or on a `forge pr open` push. The daemon therefore spawns the session with `core.hooksPath=/dev/null` and `core.fsmonitor=false` in `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n`, which outrank every config file and are inherited by subagents, `forge` and verify commands. The cost: no hooks at all in daemon mode, including Git LFS's pre-push upload. Not pinned: filter, diff and merge drivers and `gpg.program`, which only `.git/config` or `~/.gitconfig` can define. The session has no allowed way to write `.git/` (Claude Code's file tools treat it as protected, so only a human's answer to a prompt could allow it, and the git forms it may run take no output path), but anything the human or another tool puts there still applies. What remains broad is `Edit`/`Write` itself, which can still change repo files that build and test tooling executes (`.forge/config.yml` and `.forge/trackers/` are pinned; see above). Enable the daemon only on repos whose tracker input you trust (or with intake restricted, e.g. `tracker.github.comments: collaborators` and ready labels only maintainers set).
- **Keeping a slot and marking agents lost read `job.json`, which the session writes.** A session that records agents it never ends can pin its own slot, never another job's, for at most 2 h per agent start (the `RUNNING_AGENT_MAX_MS` ceiling; a `startedAt` or `endedAt` more than 60 s in the future is ignored, so a forged time can't stretch the ceiling, the grace or the idle window, and the idle timer never re-arms for longer than its window), and a human's session or pool Stop ends it sooner, the same bound as a turn that never returns a `result`. Lost-marking writes on behalf of a session that no longer exists, so it touches only agents of a job whose `owner.session` is that session's id, never another driver's. The job id it reads is the validated scope, so no path is built from session output, and nothing new reaches the child's stdin, argv or environment.
- **Orphan reaping** proves each record (`daemon.json` and every `daemons/<scope>.json`) separately before signalling its pid (see "Daemon"), so a stale or planted record can't make Forge kill an unrelated process.
- **The logs** (`daemons/<scope>.log`) live in gitignored `.forge/runtime/`; they hold whatever the sessions printed, so treat them like transcripts. The dashboard renders every log string as text, and `forge daemon log` escapes control characters so session output can't drive the terminal.

## Release security

`.github/workflows/release.yml` holds the only write token Forge's automation uses: it tags commits and publishes Releases. [RELEASES.md](RELEASES.md#releasing) describes the flow. `test/release-workflow.test.ts` pins the file with allowlists that fail closed on any trigger, key, permission, action or expression it does not list, so weakening it means editing that test in the same reviewed diff.

- **Who it defends against.** A PR author (a fork included) who wants the token or the Release, a retagged or compromised action, repo text (the `package.json` version, CHANGELOG) that would reach a shell, `GITHUB_OUTPUT` or argv, and a later edit, by a person or an agent, that quietly weakens the workflow.
- **Never on PR events.** It runs on pushes to `main` only: no `pull_request`, `pull_request_target`, `workflow_run` or `workflow_dispatch`.
- **Write scope in one job, after verify.** The workflow's token is `contents: read`. Only the `release` job asks for `contents: write`, and it needs `detect` and `verify` (all of `ci.yml`, called with no inputs, no secrets and the read-only token).
- **The token reaches two steps.** `github.token` appears only as `GH_TOKEN` on the tag and publish steps, which call `gh`. Checkout keeps no credentials, so the scripts and `git archive` never hold a token.
- **Repo text is validated or passed as a file.** `scripts/release-plan.ts detect` exits before writing anything unless the version is `X.Y.Z`, so a version with a newline can't add outputs. The version reaches `run` only through `env`, never `${{ }}`. The CHANGELOG section reaches `gh` only as `--notes-file`. The tag message and Release title are fixed text.
- **Pinned actions.** Only `actions/checkout` and `actions/setup-node`, each pinned to the same full SHA as `ci.yml`.
- **Residual risk: code runs beside the write token.** The `release` job still runs `actions/setup-node` and `node scripts/release-plan.ts notes` while it holds `contents: write`. On a hosted runner, any step can read the runner's memory and lift the job token (the 2025 tj-actions compromise did this). Both are pinned or come from merged `main`, so this is accepted rather than closed: a change to `scripts/release-plan.ts` or the pinned actions is a change to what runs with the token, and gets reviewed as one.
- **The archive proves its commit.** The release job refuses an archive whose stamped `COMMIT` is not the pushed sha, and publishes its `.sha256` beside it. `forge version --json` is self-reported; the annotated tag and the checksum are the audit anchors.

`forge doctor`'s release row (`latestReleaseCheck` in `lib/version.ts`) runs `gh release view` with a repo taken from `known_marketplaces.json` or the install's `plugin.json`, both writable by anything that can write `~/.claude` or the checkout. The repo must match `^[A-Za-z0-9][A-Za-z0-9-]*/[A-Za-z0-9._][A-Za-z0-9._-]*$` (no leading `-`) before it becomes argv, with no shell. The call has a 5 s timeout, the returned tag must be `v?X.Y.Z` before it is shown, and any failure leaves the row out.
