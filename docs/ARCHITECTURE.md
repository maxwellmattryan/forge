# Architecture

Terms for projects with several repos are defined in [GLOSSARY.md](GLOSSARY.md).

## How it works

- **The orchestrator** (the `forge` skill) runs a short loop: `forge job advance <id> --session <its session>` (which keeps its claim alive) runs the bookkeeping commands step builds itself and returns the next action that needs judgement, the orchestrator does it (spawn the named agent with the brief step rendered, or wait), records the agent with `forge job agent … end`, and advances again. `forge job step` is the read-only view of the same decision. The CLI decides each step from recorded state, the same way it is the only writer of that state, so the pipeline's rules are tested code rather than prose. The orchestrator reads JSON and one-line agent replies, never code or full reviews, so it can drive many jobs without filling its context.
- **Agents** (`agents/*.md`) each own one step and one output file: planner → `plan.md`, spec-writer → `spec.md`, designer → `design.md`/`mockup.html`, builder → commits + `tasks.md` + `build.md`, reviewer → `review/round-N/<lens>.md` (and `review/integration/code.md` after a resolved conflict, judged by `forge job verdicts --round integration`), approver → `decision.md` + `pr.md`, integrator → merge resolution, verifier → `verify/round-N-verifier-answers.md` (yes/no answers to the repo's verifiers), retro → improvement proposals, digest → `friction-<n>.md` (friction patterns from the worst agent runs' transcripts, for the retro), judge → eval scores, triage → readiness verdicts for tracker items, assistant → the foreman's gate decisions, drafter → a goal mandate's milestone draft, surveyor → a few lines summarising one mandate's board for the Foreman. They get their context from files, so any session can resume any job.
- **The CLI** (`forge`) owns the deterministic parts: state transitions, worktrees, ports, running and logging commands, the verify gate (with a test-integrity report), scope checks (files changed vs the spec's Approach), the review panel (lenses from the diff: `forge job panel` matches each lens's `paths` against the branch and records why), AC coverage (`forge job acs`: spec ACs vs the builder's proof table), finding counts (`forge job findings`: raised, fixed, disputed and recurring review findings), verdict policy, PRs, trackers, usage accounting, stats, evals and the dashboard server.
- **Committed build output merges itself.** With `worktrees.generated` set, `forge integrate` rebuilds conflicted generated files (the base side, then `worktrees.generatedBy`) instead of calling the integrator, which sees only real conflicts.
- **The PR opens first, and the merge waits on a person.** An approver's escalation, a before-merge runbook, unapproved protected paths and a missing recall eval park the job after `forge pr open`, on the open PR, which `forge pr gate` labels (`pr.needsHumanLabel`) and tells why. Only a push that is itself the risk is held before it leaves the machine: a CI config change, a security review that isn't `PASS`, or secrets the scan only reported (`push_held`; docs/CONFIG.md "The held push").
- **Merging waits for CI, and for a human where it matters.** `forge pr merge` syncs first, then merges only when `merge.auto` is on, the approver's recorded `APPROVE` (marked auto-merge eligible) covers the exact PR head (or that head plus clean merges of the base) and no rework, later round or change request on GitHub has replaced that decision, protected paths recomputed at that head are all approved, and the PR changes nothing on the **escalate floor** (`.forge/`, Claude Code's control files such as `.claude/` and `CLAUDE.md`, instruction files, test, build and CI config), each compared against the base branch as the push remote holds it. Then it merges directly only when checks pass, or the repo has no CI on any known system, at a head pushed at least 5 minutes ago, and every **required check** has passed from its own source: the names in `merge.requiredChecks`, else the base branch's protection (a missing one waits; one that fails, is skipped or neutral, or comes from two sources refuses; a commit status counts only when bound to who posted it; `forge doctor` and `forge pr open` warn when the base has neither); it refuses when checks fail, and while they are pending queues GitHub auto-merge only if branch protection will hold the PR, no protected-paths policy applies and the required checks do not come from `merge.requiredChecks` (GitHub's protection does not know those); otherwise it defers and the next `forge sync` continues the merge itself. Refused and failed merges exit 1. A multi-repo job's PRs link each other and merge in the components' `dependsOn` order, never a PR before its dependencies, and the job is done only when every PR merged. `--now` is a human-only operation: a person confirms it at a terminal by typing the job id (or uses **Merge now** in the dashboard); it skips these checks (never the merge order) and is logged as `pr-merge-bypass`. A daemon session, an agent or a configured command can't pass it, and a daemon session merges only its own job (docs/CONFIG.md "Merge").
- **Every job reaches build with an issue.** A job opens one PR and carries one or more issues, from this repo or others (`owner/repo#12`), and one issue may sit on several jobs. With a tracker in use, a job that didn't start from an issue gets one at spec approval: the same answer that approves the spec links one of the candidates Forge found, approves a new issue, or records that it needs none. A spec approved without one, or a job with no spec gate (`specApproval: never`), waits for that choice before build (see [Linking jobs to issues](TRACKERS.md#linking-jobs-to-issues)).
- **Agents propose repos; a person adds them.** In a multi-repo project the planner and spec-writer see the project graph, and when the work needs a change in a member repo the job lacks (say, a library's API the app uses) they propose it with a reason (`forge job repo propose`). The job waits until a human approves or rejects it in the dashboard or their own terminal (`forge job human <id> approve-repos|reject-repos`), or the foreman does when `repo-proposal` is in `foreman.decides`; approving gives the repo its own worktree, branch and PR, and rejecting re-runs the agent within the job's repos.
- **State** lives in `.forge/jobs/<id>/` (gitignored) in the main checkout, shared by every worktree and session: `job.json`, an append-only `events.jsonl`, and the agents' markdown files.
- **Every human action says who.** Approvals, budget acks, links, forced claims, `--now` merges, config changes and dashboard permission answers record a best-effort, unauthenticated `actor` (`FORGE_ACTOR`, else `gh`, `git` or the OS user; `dashboard` for a dashboard route, `daemon` for a daemon session); `forge job audit <id>` and `forge audit --since <date>` export the trail as JSON or CSV (see [Audit trail](architecture/audit-trail.md)).

## Topics

- [Layers](architecture/layers.md): the engine, roster, repo layer, runtime state and the machine index, where each lives and when it changes, and which `forge` runs. Read it to decide where something outside `lib/` belongs.
- [Why a CLI does the bookkeeping](architecture/cli-bookkeeping.md): why every decision with one right answer is CLI code and agents only judge. Read it before moving work between an agent and the CLI.
- [Start-up cache](architecture/startup-cache.md): `bin/forge`'s code and stripped-module caches, their timings, and why they sit beside the code, plus the worktree seeds that share their directory and trust argument. Read it before touching `bin/forge`, start-up time or `lib/engine/workspace/seed.ts`.
- [Data and versioning](architecture/versioning.md): how every persisted shape is versioned and migrated, and the history of job, event, config and API versions. Read it before any shape change.
- [Updating](architecture/updating.md): `forge update`: detection, commands, refusals, versions and provenance. Read it when changing how Forge updates itself.
- [Job model](architecture/job-model.md): stages, states and `waitingOn`, moves, answered gates, the lease, evidence, budgets, dependencies and the inbox. Read it before changing how a job moves or who drives it.
- [Job repos](architecture/job-repos.md): member repos in one job, linked PRs and merge order, repo proposals, downstream verification, local links, and their threat models. Read it for any multi-repo change.
- [Interim strategies](architecture/interim-strategies.md): what a consumer's PR points at while its dependency is unmerged: deferral, pins, release gates and the threat model. Read it before changing interim releases.
- [Concurrency](architecture/concurrency.md): sessions per job and per repo, locks that prove death, one `forge dash` per repo, worktrees, ports and background commands. Read it before adding shared state or a lock.
- [Daemon](architecture/daemon.md): the session pool `forge dash` supervises: periodic sync, the reconciler, turn timeouts, states, triggers, the cap and budget holds. Read it before changing when sessions run.
- [Daemon runtime](architecture/daemon-runtime.md): session files and offsets, resume, failures, start and stop, effort, the HTTP surface, the terminal, orphans and the recorded stream-json framing. Read it before changing how a session is spawned, logged or stopped.
- [Foreman](architecture/foreman.md): how the Foreman decides gates: routing, its turn, the context rule, the authority the CLI enforces, the release gate class, ship policy, audit and threat model. Read it before changing what the Foreman may decide.
- [Audit trail](architecture/audit-trail.md): the actor every human action records, how it is resolved, why it is not authenticated, and export. Read it before adding a human action.
- [Retention](architecture/retention.md): archiving and pruning finished jobs: archive format, eligibility, write order, readers, logs and threat model. Read it before changing what Forge keeps or removes.
- [Deleting a job](architecture/deleting-a-job.md): `forge job delete`: what it refuses, its order of work and the dashboard card. Read it before changing job deletion.
- [Untrusted input](architecture/untrusted-input.md): how tracker, PR and request text reaches agents only as fenced data, why fork PRs are never adopted, and one wrapper per tool. Read it before anything that ingests outside text.
- [Policies](architecture/policies.md): authorship (AI attribution), review verdicts and model diversity, the repo budget, and usage accounting. Read it when changing a verdict, attribution or spend rule.
- [Dashboard security](architecture/dashboard-security.md): loopback Hosts only, the token, Origin and JSON every POST needs, read guards and the page CSP, plus the support bundle and `--dev`. Read it before adding or changing a route.
- [Daemon security](architecture/daemon-security.md): what an unattended session may run and change: one fixed stdin turn, argv from config, the trust digest, permission prompts and mode, git hooks off, orphan reaping and logs. Read it before changing a session's argv, env or permissions.
- [Release security](architecture/release-security.md): the release workflow's write token, who it defends against, pinned actions and residual risk. Read it before changing `release.yml` or `main-update.yml`.
