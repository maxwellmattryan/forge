# Architecture

Terms for projects with several repos are defined in [GLOSSARY.md](GLOSSARY.md).

## Layers

| Layer | Where | Changes when |
|---|---|---|
| **Engine**: CLI, dashboard, data schemas | `bin/`, `lib/`, `dashboard/` | the plugin is updated |
| **Roster**: orchestrator skill, agent prompts, reviewer catalog | `skills/`, `agents/`, `reviewers/` | the plugin is updated |
| **Repo layer**: config, learnings, role addenda, repo checklists, verifiers, evals, custom trackers | `<repo>/.forge/` (committed) | `/forge init`, humans, retros |
| **Runtime state**: jobs, locks, dashboard inbox, caches | `<repo>/.forge/{jobs,locks,runtime}/` (gitignored) | every Forge action |

Repos never copy the engine or the roster, so there is nothing to drift. Everything repo-specific is data in `.forge/`, and that's also the only layer the retro loop edits.

**Which `forge` runs.** Claude Code appends a plugin's `bin/` to the end of PATH, so a `forge` earlier on PATH (a `~/.local/bin` shim, an `npm link` of another checkout) would run a different install's CLI against the loaded plugin's skills. The SessionStart hook `hooks/plugin-path.ts` appends `export PATH='<plugin root>/bin':"$PATH"` to `$CLAUDE_ENV_FILE`, which Claude Code sources before every Bash command of the session, subagents included, so `forge` is always the loaded plugin's. The line is built only from the hook's own location and single-quoted; the hook prints nothing on stdout and always exits 0. It does nothing when `CLAUDE_ENV_FILE` is unset or empty, on Windows, or when the file already holds the line (resume, clear and compact run it again). Daemon sessions get the same order from `sessionEnv()`.

## Why a CLI does the bookkeeping

LLMs are good at judgement and unreliable at bookkeeping. Everything with a single right answer is code: valid state transitions, which transition comes next, unique job ids, atomic writes, locks, port allocation, worktree setup, command logging, verdict policy, PR and tracker calls, usage maths. Agents and the orchestrator call `forge …` and get compact JSON back. Four things follow:

1. **Data shapes can't drift.** No model hand-writes `job.json`, so a skill update can't produce state that a dashboard update can't read.
2. **Context stays small.** `forge verify` returns pass/fail plus a log tail, not 3,000 lines of compiler output. `forge job verdicts --compact` returns one word per lens. `forge job scope` returns at most 20 out-of-spec files; the full list goes to `scope.md`.
3. **The protocol is portable.** Any agent runtime that can run shell commands can drive Forge (see PROTOCOL.md).
4. **The pipeline is tested code.** `forge job step <id>` (`lib/engine/pipeline/step/`) is the one decider of transitions: a pure function from recorded state (`job.json`, the config, which job files exist, the events it needs) to the next action: `spawn` an agent with the brief `lib/engine/pipeline/brief.ts` rendered, `run` one forge command, `wait` on agents or a human gate, follow a reference `procedure`, or `done`. It never writes, and it reads no file and no clock: `loadStepInput` (`lib/engine/pipeline/step/input.ts`) reads everything once, the time included (`StepInput.now`), so the same state always gives the same answer (the CLI's `--session <driver>` only renews that driver's lease before deciding). Each stage is an ordered table of `{ id, when, then }` rows (`lib/engine/pipeline/step/stages/`, the gates in `lib/engine/pipeline/step/gates.ts`), and precedence is the tables' order in `lib/engine/pipeline/step/order.ts` and the rows' order within each, pinned by `test/step-tables.test.ts`. Every transition has its own rule ID and at least one row in `test/step-rows.ts` (run by `test/step.test.ts`). Facts about the event log (when the job entered its stage, left review, was approved at a gate) are read by log position, so two events in one millisecond, or a clock that stepped back, keep their order. `forge job advance <id> --session <owner>` (`lib/cli/commands/advance.ts`) is step's executor: it runs the `run` actions step returns in-process, through the same dispatcher `bin/forge` uses, and returns the first `spawn`, `wait`, `procedure` or `done` with a one-line summary of each command it ran, so step stays pure and a deterministic stretch of the pipeline costs the orchestrator one call. A review round's RV4 (RV10 on a narrowed rework round, with only the rework panel) returns the whole remaining panel at once, the first unstarted lens plus the others as `spawns`, and each lens is still recorded by its own `agent start`, so a re-step never lists a started lens. The facts the orchestrator used to carry in conversation are recorded instead: suggested lenses in the `spec.md` header, the agent to resume after an answered question in `agents.<role>.agentId`, reviewers in flight in agent `status`, split mode in `job.splitMode`, human decisions in `human` events, and missing outputs in `outputMissing`, which `forge job agent … end` sets for single-output roles. Commands it emits are built only from ids, numbers, config names and fixed templates, never from file contents or agent replies, and briefs carry paths, never contents, so text an agent wrote after reading tracker or PR input never becomes a shell argument or another agent's prompt.

The CLI is TypeScript that Node ≥ 22.18 runs directly through its built-in type stripping, with zero dependencies. That means no build step, no install step inside the plugin, and Node is already present wherever Claude Code is. The only JavaScript left in the engine is `bin/forge`, an extensionless entry that sets up the start-up cache below and then imports `lib/cli/main.ts`, and `lib/trackers/status.mjs`, a one-line re-export kept for custom tracker adapters. Node does not strip types under `node_modules`, which is why Forge has no npm-package install. The dashboard is built with Vite at development time and its output (`dashboard/dist/`) is committed, so installing still needs no build or install step. The dashboard is a Svelte 5 app in strict TypeScript (`dashboard/src/`), type-checked with svelte-check and compiled by Vite at development time; nothing at runtime loads Svelte's compiler or TypeScript. A native (e.g. Rust) port would only pay off for a long-running worker daemon. The CLI's commands and JSON outputs are the contract, so a port could replace it without touching the skill or agents.

### Start-up cache

Agents and the orchestrator call `forge` hundreds of times a job, so start-up time is paid on every call. Before it imports `lib/cli/main.ts`, `bin/forge` turns on two caches in one directory:

- **V8's code cache** (`module.enableCompileCache`), on every Node. From Node 24 it covers type-stripped modules too.
- **Stripped modules**, on Node 22 and 23 only. Their code cache skips type-stripped modules, so every start loads the stripper and strips all of `lib/` again. A `module.registerHooks` load hook keeps each stripped `.ts` file of the plugin as `strip/<node version>/<sha256 of the source>.js`. Content keys mean an edited file or an updated plugin is never served stale, and identical files of different installs share an entry. A miss strips with `module.stripTypeScriptTypes` and silences its one-time ExperimentalWarning, which agents would read as a fault. The entry is written aside and renamed, so concurrent starts never read half a module. A file the stripper rejects goes to Node's own loader, which reports the error as usual. Beside it, a resolve hook resolves each layer alias (`#core/…`) a `lib/` file imports once per process, because Node 22 walks up to `package.json` on every one.

`forge job list`, median of 30 warm starts on an M-series Mac:

| Node | Before | After |
|---|---|---|
| 22.18 | 144 ms | 37 ms |
| 22.23 | 98 ms | 39 ms |
| 26.3 | 148 ms | 70 ms |

A miss costs about 15 ms over an uncached start, once per changed file. On Node 22 the modules `forge job list` loads take about 1.3 MB of cache (0.9 MB stripped, 0.4 MB V8), per Node version.

The cache holds code the CLI runs, so it must be no easier to write than the code it caches. It is `.cache/` in the plugin root (or `$FORGE_CACHE_DIR`), so whoever can write it could already rewrite `lib/`. It is not in a temp or other shared dir, because Claude Code's sandbox lets Bash write the temp dir: a sandboxed agent could plant a module there that a later unsandboxed `forge` would run. `bin/forge` creates the dir as `0700` with a `.gitignore` of `*`, so a checkout's `git status` never shows it. It uses the dir only when it is a real directory (not a symlink), owned by the current user, not group- or world-writable, in a parent owned by that user or root that is either not group- or world-writable or sticky. Otherwise, and whenever a read or write fails, the CLI runs uncached and prints nothing. A read-only install, or a sandbox that can't write the plugin, still reads entries an earlier unsandboxed start wrote and skips writing misses. Each plugin version starts with an empty cache and is removed along with it. `NODE_DISABLE_COMPILE_CACHE=1` turns both caches off. A `NODE_COMPILE_CACHE` already set wins for the V8 cache. Deleting the directory is always safe.

## Data and versioning

Every persisted shape carries a version: `config.yml` → `schemaVersion`, `job.json` → `schemaVersion`, each event line → `v`, `/api/state` → `apiVersion`. `apiVersion` (`API_VERSION`) also covers the other `/api/*` shapes the dashboard reads, such as `/api/config`, `/api/doctor` and `/api/about`.

- **Readers upgrade, writers write current.** `normalizeJob`, `migrateConfig` and `normalizeEvent` (in `lib/core/job/schema.ts`) upgrade old shapes in memory and fill defaults, so new code reads old jobs. `forge migrate` rewrites jobs and configs on disk; event files are never rewritten.
- **Newer-than-me is refused, not guessed.** A plugin that meets a job from a newer schema stops with "update the plugin".
- **Unknown fields are preserved.** Normalisation spreads the raw object first, so fields from a newer minor version survive a read-modify-write by an older one.
- **The dashboard is served by the same plugin version as the CLI**, so they can't disagree. The page checks `apiVersion` anyway, for a dashboard left open across an update.
- **Events are append-only**, so history is never rewritten by a migration.

When a shape must change: bump the version constant, add a migration keyed by the old version, and keep normalisers tolerant.

Job schema v6 (API version 10) records what `forge job step` decides from: `splitMode` (`never` for jobs from `forge job from-ref` and after a `revise-split`, else null; a v5 job reads as null, because v5 never recorded how a job started), each agent record's `output`, `retry` and `outputMissing`, and each verify run's `failure` (the failing step's name). Events gained `pr-find` (`forge pr find` adopted nothing) and `scope` (`forge job scope` ran, with its round and HEAD). API version 12 (from 11) adds `ownerStatus` (`none | live | stale | dead`, with the session, its claim and last-activity times, `agentRunning` and a `dead` reason) and `jobSession` to each `/api/state` job and to the job detail; job.json and events are unchanged.

The `panel` event (`forge job panel` ran, with `{round, head, mergeBase, lenses, reasons, added}`) records each round's review lenses and why each is on the panel; step reads it to know the panel is current for the round. It is a new event type and job.json is unchanged, so it needed no schema bump, and a review panel entry's optional `paths` passes through older config normalisers untouched. On a narrowed rework round (`review.onRework: narrow`, docs/CONFIG.md "Rework panel") the event also carries `rerun` and `rerunReasons`, the lenses that re-run and why; step spawns only those (RV10) and only when the event postdates the round's last verify and every name is on the round's panel. The fields are optional additions, so `EVENT_SCHEMA_VERSION` stays 2: an older reader ignores them and reviews with the full panel, the safe direction. The comparison point is the sha on round N−1's `verdicts` event, used only when it is 40 to 64 lowercase hex characters and an ancestor of HEAD, so a rewritten history or an injected revision falls back to the full panel before any git command sees it. In a job with a reviewed member, the `scope`, `panel`, `verdicts` and `integration-review` events gain an optional `heads` map of member HEADs, and `job.reviewers` and `job.verdicts` keys may hold qualified `<repo>:<name>` lenses (["Job repos"](#job-repos)): additive, with no schema bump.

Job schema v7 (API version 15) adds `effort`: the human's reasoning effort for the job (`low | medium | high | xhigh | max`), or null to inherit `runtime.effort`. A v6 job reads as null, and so does any value outside the five levels, whoever wrote it. Events gained `effort` (`{effort, previous, from: "cli" | "dashboard"}`), and a `created` event names the level when `forge job new --effort` set one. `/api/state` adds `config.effort` (`runtime.effort` when valid, else null) and each daemon session's `effort`.

Job schema v8 (API version 16) adds `waitingOn: human`: a CLI check stopped the job and only a human can clear it, and the reason names the check (today the secret scanner: `secret scan blocked verify round <n>` or `secret scan blocked pr open`). No v7 job waits on it, so the migration changes nothing; the bump makes an older Forge refuse a job parked on a gate it can't explain. Events gained `secret-found` (`{gate: verify | commit | pr | agent-end, blocked, count, allowed, findings, more, round?, role?}`, at most 10 masked findings, each `{kind, path, line, excerpt, fingerprint}`, logged only when something was found), and verify's JSON gained `secrets`. A scan that could not finish also logs `secret-found`, with `count: 0`, no findings and the scan's `error` line, so a blocked `pr open` scan error parks the job like a finding. The config gained `verifySecrets` with a default, which needs no config bump.

Job schema v9 (API version 17) adds `complexity` (`low | medium | high`, or null): the spec's `Complexity:` header, recorded by SP3 through `forge job set --field complexity=…`, which accepts only those three values or null. A v8 job, and any other stored value, reads as null. `/api/roster` adds `effort` and `effortSource` to each `agents[]` and `reviewers[]` item. Config schema v4 adds `runtime.efforts.<role>`, `runtime.effortByComplexity.<low|medium|high>` and a panel entry's `effort`, all unset by default, so a v3 config migrates unchanged.

API version 18 adds each `/api/state` job's `activity` (what its running agents did last) and the transcript endpoints behind the drawer's Agents tab; job.json and events are unchanged.

Config schema v5 and API version 19 add the foreman: `foreman.*` (off by default), `runtime.models.assistant` and `runtime.efforts.assistant`, a `gate` request type routed to the `_office` scope, `/api/state` `daemons.office` and `daemons.foreman`, and a per-job `gateOwner`. A v4 config migrates unchanged. Job schema stays at v9: `human` events gain an optional `actor` (`human | foreman`, an object since event schema v2), and an older event without it reads as `human`.

API version 20 adds `/api/about` `commit` and `installedAs` and an optional `warn` on `/api/doctor` checks; job.json, config and events are unchanged.

Event schema v2 (API version 22) makes `actor` an object, `{ login: string | null, source: env | gh | git | os | dashboard | foreman | unknown }`, on every human-action event ("Audit trail" below). `readEvents` passes each line through `normalizeEvent`: a v1 (or unversioned) `human` event's `"foreman"` becomes `{ login: null, source: "foreman" }`, and `"human"` or no actor becomes `{ login: null, source: "unknown" }`; other v1 events get no actor; any malformed actor reads as source `unknown` with its login sanitised, except that an object with source `foreman` always reads as `{ login: null, source: "foreman" }`; a line from a newer Forge (`v > 2`) is kept as written except that its actor is sanitised. The legacy string `"foreman"` stays the foreman's on any version, so no shape change lets a foreman decision pass as a person's. `/api/state` jobs gain `lastHuman`; job.json and config are unchanged.

Job schema v11 (API version 25) replaces the single `source` with `issues`, a list of `{tracker, ref, url}` (docs/TRACKERS.md "Linking jobs to issues"), so a job can carry issues from several repos and one issue can sit on several jobs. Migration 10 turns a v10 `source` into a one-entry list: a GitHub number whose url names its repo becomes `owner/repo#N`, one without stays a bare number (which still reads as this repo), and a ref the new grammar refuses (`forge job new --ref` stored refs unchecked before) is kept in the nearest form it accepts, so a linked job stays linked. The normaliser drops malformed entries, duplicates and any url that isn't one `http(s)://` token, and folds a stray `source` in. Events gained `linked` and `unlinked`, and `created` carries `issues`. `/api/state` jobs and the job detail serve `issues` instead of `source`; config is unchanged.

Job schema v12 (API version 27) adds `repos`, the job's repos (["Job repos"](#job-repos) below). Migration 11 gives a v11 job a one-entry list, the root mirror `{ repo: null, worktree, branch, base, pr, verifyOnly: false }` built from its top-level fields, and older Forges refuse a v12 job. Verify runs gained `repos` (one `{ repo, sha, ok, failure }` per member, only with members), and events gained `job-repo-added`, `job-repo-removed`, `repo-worktree`, `repo-worktree-removed`, `repo-pr-opened`, `repo-pr-updated` and `repo-pr-sync-failed`. `/api/state` jobs carry `repos`; config is unchanged.

Job schema v13 (API version 28) adds `interim`, the job's interim strategy override, on the job and on each `repos[]` entry (["Interim strategies"](#interim-strategies) below). Migration 12 gives a v12 job `interim: null` (inherit config), `repos[0].interim` mirrors the job's, a value outside `canary | git-ref | local | sequential` reads as null, and older Forges refuse a v13 job. Events gained `pr-deferred`, `canary-published`, `job-repo-interim` and `pr-state-corrected`. `/api/state` jobs carry `interim` and each `repos[]` entry its `interim`; config schema v13 adds `release.interim` and a link's `manifest`.

Job schema v14 (API version 29) adds `ports`, one port per port-bearing component (["Ports and endpoints"](CONFIG.md#ports-and-endpoints) in docs/CONFIG.md): migration 13 gives a v13 job `ports: {}`, and its `port` stays its first entry's until the next `forge worktree create` allocates the map, and older Forges refuse a v14 job. The `worktree` event carries `ports` beside `port`. `/api/state` endpoints gain `kind` (`component` or `backing`), a nullable `url` and a nullable `live`; config is unchanged.

Job schema v15 (API version 30) adds `outcome`, the merged root PR's post-merge outcome that `forge sync` measures (docs/CLI.md "Outcomes"): migration 14 gives a v14 job `outcome: null`, a malformed stored outcome reads as null (and is measured again), and older Forges refuse a v15 job. Events gained `outcome`. `/api/state` jobs carry `outcome`, and `/api/stats` `quality` gains `autonomyRate`, `autonomyRateStrict`, `revertRate`, `followUpRate`, `churnRate` and `outcomeCoverage`; config schema v24 adds `outcomes.windowDays` (identity migration from v23).

Job schema v16 (API version 31) adds `score`, a sampled merged job's post-merge judge score (docs/CLI.md "Scoring"): migration 15 gives a v15 job `score: null`, a malformed stored score reads as null, and older Forges refuse a v16 job. Events gained `score`. A done job keeps its judge marked running while its score is `queued`, so the score run's wait (JS1) holds. `/api/state` jobs carry `score`, `/api/stats` `quality` gains `medianScore`, `scoreCoverage` and `scoreByBuilderModel`, and `/api/evals/compare` gains `realJobs`; config schema v25 adds `scoring.sample` and `scoring.model` (identity migration from v24).

Job schema v17 (API version 33) replaces the time-ruled `owner` with a fenced `lease` (`{ driver, epoch, since, renewedAt, expiresAt }`, ["Job model"](#job-model) › Ownership): migration 16 turns a v16 `owner` into a lease driven by its session at epoch 1, renewed at its last recorded activity and expiring 30 minutes after it (an unparseable time keeps the driver but reads as expired), a v16 job with no owner gets `{ driver: null, epoch: 0 }`, and the job is written back with no `owner`. Older Forges refuse a v17 job. Events gained `lease-expired` (`{ session, reason }`) and `reconcile` (`{ action: resume | escalate, stage }`), and `claimed` records its `epoch`; old `stranded` and `missed-agent-end` events stay readable as generic events. `/api/state` jobs and the job detail carry `lease`, and `ownerStatus` becomes `{ status: none | live | expired, session, since, renewedAt, expiresAt, epoch, jobSession }`; a daemon session's `kept` is `agents` or null; a request may carry `requeues`. Config schema v28 adds `daemon.turnTimeoutMinutes` (identity migration from v27).

API version 34 adds `foremanHandoff` per job (derived from `foreman-handoff` events; job schema stays v17): `{ gate, class: reserved | escalated | refused, reason, at }` while the job still waits at the park the Foreman left for a person, else null.

API version 26 adds `GET /api/project`, the dashboard's Project view: `{ components, backing, edges, problems }`, where each component is only `{ name, repo, kind, path }` and each edge `{ from, to, target, type }`, derived from `components` by `projectGraph` in `lib/engine/project/graph.ts`. It never carries a component's commands, owners or notes. job.json, config and events are unchanged.
## Updating

`forge update` (`lib/engine/ops/update.ts`) updates the install that is running, its own `PLUGIN_ROOT` after realpath, never whichever `forge` comes first on `PATH`. It works outside a git repo and without `.forge/`, like `forge version`.

- **Detection, plugin first.** A root under `plugins/cache/<marketplace>/<plugin>/<version>` (with `plugins/installed_plugins.json` beside it) or `plugins/marketplaces/<marketplace>` (with `plugins/known_marketplaces.json`) is a Claude Code plugin install. The plugins dir comes from the root's own path rather than `CLAUDE_CONFIG_DIR`, so it always describes this install. This check runs before the git check because Claude Code's cache dirs can contain a `.git`, and pulling there would fork the install from what Claude Code tracks. Otherwise a root that is its own git toplevel is a clone (`npm link`, `claude --plugin-dir`). Anything else is unknown, and the command prints the manual route instead of guessing.
- **Commands.** For a plugin it runs `claude plugin marketplace update <marketplace>`, then `claude plugin update <plugin>@<marketplace>`. Names from the path must match `^[A-Za-z0-9][A-Za-z0-9._-]*$` and are passed as separate argv entries with no shell, so a directory named like an option never reaches `claude`. For a clone it runs `git pull --ff-only`. The explicit flag overrides `pull.rebase` and `pull.ff`.
- **Refusals.** A clone with uncommitted changes, a detached HEAD or no upstream is left untouched. Forge never stashes, resets, rebases or merges, and a diverged history fails with git's own message. A daemon session (`FORGE_DAEMON=1`) is refused before detection or any subprocess, because an unattended agent must not swap the code it and the dashboard run on. An interactive session runs under the human's own permissions and can only move the install to its marketplace's or upstream's head, which is accepted.
- **Versions.** The new version is read from disk after the update: for a plugin, from the `installPath` that `installed_plugins.json` now records (user scope first). The cached `forgeVersion()` belongs to the old code.
- **Dashboard.** If the repo at cwd has a running dashboard and the version changed, Forge restarts it by running the new install's `bin/forge dash --stop` and `dash --background`. `forge dash` spawns the server from its own `PLUGIN_ROOT`, so running the old bin would bring the old code back up. `--keep-dash`, or a restart that fails, leaves it running and reports it as stale. Dashboards in other repos get a hint, because Forge keeps no global registry of them.
- **Provenance.** `forge version --json` (`lib/engine/ops/version.ts`) reports the running commit: a stamped `COMMIT` file (release archives), else the plugin install record's `gitCommitSha`, else `git rev-parse HEAD` when the root is its own toplevel, else null. The same detection decides `installedAs`. See [RELEASES.md](RELEASES.md#provenance-and-pinning).
- **Nothing is built.** Every commit on `main` carries `dashboard/dist/`, which CI builds for the main update (RELEASES.md "Releasing"), and there are no runtime dependencies, so an update never runs `npm install` or a build. A clone of `develop`, where `dist/` is gitignored, needs `npm ci` and `npm run build:dashboard` after an update; `forge dash` and `forge doctor` (`dashboard built`) say so until it has one.
- **Shadowing.** A `forge` earlier on `PATH` that resolves under `node_modules` (an old global npm copy) cannot run, because Node does not strip types there. Forge warns and names the uninstall command. It deletes nothing.

## Job model

`stage` is where the job is in the pipeline:
`backlog → plan → spec → design → build → verify → review → integrate → decide → pr → done`

Integrate runs before decide, so the approver judges the branch as it will merge, and an approved job opens its PR at once. After any gate wait (an escalation, an infra runbook, a budget stop), step runs `forge integrate` again before the PR, and does more work (verify, the integrator, the integration review) only when it reports `behind > 0`. Older jobs found in `decide` with no integration since their review integrate before `pr`. Eval jobs never integrate: review sends them straight to `decide`.

`state` is what is happening there:
`queued | running | waiting | blocked | failed | cancelled | done`

`waitingOn` says why a job is waiting:
`spec-approval | split-approval | issue-link | input | escalation | infra | conflicts | rounds-exhausted | pr-review | external | budget | human` (`human`: a CLI check, such as the secret scan, stopped the job; approve means "I cleared it, check again", never "ship it anyway")

Trackers see a coarser view: `queued`, `in-progress`, `review`, `blocked`, `done`, `cancelled`. Adapters map those to labels, GitHub Project options, or anything else.

**Moves** (`lib/engine/pipeline/moves/`). A change to a job's stage, state or `waitingOn` that needs follow-up goes through `moveJob`: one locked `setJob` write, then three effects in this order, each once, against the job as the write's lock read it and the job after it. The **environment** effect tears down a job's environment when an active job finishes; the **gate** effect queues the Foreman's `gate` request on a new park on a class it decides (Foreman › Routing); the **mirror** effect mirrors the job to its tracker, logging a failure as `tracker-error` and never throwing. An effect with nothing to do is a no-op, and the call resolves once the mirror has finished. Three named inputs change it, and nothing disables the gate: `environment: 'stop'` only stops the environment (the inbox and office sessions, chosen from the process's own daemon scope, never from job data), `mirror: false` skips the mirror (a cancel after a failed tracker claim, where Forge doesn't hold the issue), and `afterWrite` runs between the write and the effects (`forge job set`'s dependency refresh). `forge job set`, `forge job advance`'s repeated-failure park, the reconciler's escalation, the syncs in `forge pr sync`, `forge sync` and `forge pr merge`, the tracker claim-failure cancels and `forge sync`'s umbrella done all move through it. `mirrorJob` runs the mirror alone, for `forge sync`'s dependency release and `forge job delete`. Notifications follow every transition from every writer instead, through `setJob`'s transition hook list (`lib/core/job/transitions.ts`), on which `main()` in `lib/cli/main.ts` registers notify at start; importing `lib/office/notify.ts` registers nothing.

**Answered gates** (`lib/engine/pipeline/step/answered.ts`, rules GA1–GA11). A decision recorded with `forge job human` (a person's or the foreman's) moves the job at its next `forge job step`, which returns the gate's follow-up `forge job set` as a `run` action ahead of the park's wait (G4/G4b) and the PR claim release (G3), so `forge job human` plus `forge requests add resume --job <id>` is the whole recipe from any session. A decision answers the park only when it is a `human` event logged after the job's last `transition`, that transition entered exactly the job's current stage, `waiting` state and `waitingOn`, and the latest such event's action is one the gate takes; positions in the log, not timestamps, decide. So an approve at an earlier park, or at a `budget` park, never moves a later escalation, and `note`, `budget-ack`, `release-approval` and `foreman-handoff` events never answer. The follow-ups: `approve-spec` → `--state running`; `approve` at `escalation` or `rounds-exhausted` → `integrate` (`decide` from `integrate`), at `infra` → `integrate`, at `issue-link` or a `human` check → `--state running`; `approve` or `rework` at `conflicts` → `integrate`; `rework` at `escalation`, `rounds-exhausted`, `infra`, `pr-review` or `human` → `build`; `revise-spec` → `spec`; `approve-split`/`revise-split` → `plan`; `approve-repos`/`reject-repos` at a repo proposal park → `--state running` (RP1 parks again while proposals remain); `answer` at `input` → `--state running`. A `budget` park is answered by an approve only while nothing is still over its limit after acks (`budgetExceeded`, which `loadStepInput` computes only at a budget park), and never when it is the repo cap (`repo budget:`). An `approve` or `rework` at an escalation before build (`backlog`, `plan`, `spec`, `design`) is not answered: revise instead. Anything unanswered waits as before. A job whose log holds no matching transition (hand-written or very old) waits too. Once the follow-up has run the job is no longer waiting, so no GA rule fires twice.

**Ownership**: one fenced **lease** per job (`job.lease`: `{ driver, epoch, since, renewedAt, expiresAt }`, lib/core/job/store.ts) says which session drives it. The lease is `live` while it has a driver and `expiresAt` is ahead, `expired` once that time has passed, and `none` without a driver.
- **Claim** (`forge job claim`, `forge job new|from-ref --session`, `forge next --claim`, dependency claims) takes a lease that is none, expired or already the caller's; another driver's live lease refuses with exit 3 (`owned`) unless `--force`. Every change of driver (null to a session included) increments `epoch` and sets `since`; a re-claim by the same driver keeps both. Every claim sets `renewedAt` and extends `expiresAt` to at least 30 minutes ahead (`LEASE_MS`). The `claimed` event records the epoch, and a takeover logs a `note`: `took over from session <old> (lease expired|forced)`. The claim's output returns `lease` and `epoch`.
- **Renewal** comes only from the driver's own activity: `forge job step|advance <id> --session S` (only while S is the driver, even past expiry, provided nobody took over), the worktree commands its agents run (`forge run`, `forge verify` and the others in `lib/engine/workspace/` and `lib/engine/verify/`) and `forge job agent start|end`. `agent start` extends the lease to two hours (`AGENT_LEASE_MS`), so a long builder with no CLI writes keeps its driver; that is the ceiling, so a crashed session can't hold a job forever. A renewal without a session (the worktree and agent commands) renews only a live lease, so an orphaned agent can't revive a dead driver's. Nothing else renews: sync, dependency parking, other sessions, the dashboard and the reconciler never do.
- **Expiry by the supervisor**: when a `forge dash` session's child exits for any reason, the supervisor expires the lease of every job whose driver is any of that session's ids (current, spawn or past: `recordIds` in lib/office/driver.ts), not only its own scope's, each in one locked write: `expiresAt` becomes now, driver and epoch are kept, and a `lease-expired { session, reason }` event is logged. So an inbox that dies holding a job it claimed for intake frees it at once. At pool start, holding the daemon lock and after reaping orphans, the pool runs the same release for every id in every session record (`daemonSessionIds`, reason `dash-start`), since no earlier dash's child can still run, and marks those jobs' running agents lost too. A lease held by an interactive session (in no record) runs out only by time, and its agents and claims are left alone.
- **Release** (`forge job release`, parking on dependencies) drops the driver and `expiresAt` and keeps the epoch, so it only ever grows. Idle jobs give their lease up: parking a job on dependencies releases it in the same locked write (a `released` event), split children start with no driver (`forge job new --parent` never claims, even with `--session`), and the split procedure releases the parked umbrella.
- **Fencing**: `forge job step|advance|set|claim` and `forge job agent start|end` accept `--epoch N`, the epoch the caller's claim returned. With it, the command is refused before any write, inside the job lock and in the same write it guards, when `lease.epoch` is not N, or (with `--session S`) the driver is not S: exit 3, code `stale_epoch`, `job <id> was taken over (lease epoch <cur>, you hold <N>); stop driving it`. `advance` checks at entry and before every command it runs. Without `--epoch`, `advance` keeps the driver check (it refuses a job its session does not drive). Writes not made on a driver's behalf (sync, the dashboard, humans, the reconciler) are never fenced. The orchestrator skill passes `--epoch` on every step and advance, so a session that slept or was suspended through a takeover can't write after it.
- **Requests follow the lease** (`requeueOrphans` in lib/core/job/requests.ts): an `in-progress` request goes back to `pending` when (a) it routes to a job whose lease its session holds and that lease has expired, (b) its session is one the caller saw exit (the supervisor on a child's exit, the pool at boot), or (c) neither lease rule covers it and its claim is older than 30 minutes (inbox, office and job-less requests). Rule (c) never requeues a claim of a `forge dash` session that is `busy` or `stopping`, since a turn may run up to `daemon.turnTimeoutMinutes`, and only callers that can see those sessions apply it: the dash's reconciler, `forge sync` and `forge requests` (list) when no dash runs, and the pool at boot. A supervisor seeing its own child exit applies only (a) and (b). Requeueing clears its session, increments `requeues` and notes it on the job; a request orphaned a second time is `rejected` with `its session ended twice while handling it`, so one that kills its session can't loop.

`forge next --claim --session S` first resumes a queued job nobody drives (not eval, not an umbrella, dependencies done, no `resume` request pending or in progress, no live lease), oldest first, and returns it with `resumed: true`; only then does it start a new tracker item. `forge sync` moves a PR job to `integrate` only when its lease is not live, judged inside the job lock, and never claims the job itself. The dashboard drawer's **Resume** (and the command bar's `continue`) queues a `resume` for a queued, failed or expired job; the server refuses one with 409 while another driver's lease is live, but not when the driver is any id the job's own pool session has had (current, spawn or past, so a `session-changed` doesn't make it a stranger) and that session's child runs (`idle`, `busy` or `stopping`), since it takes the resume itself (see "Dashboard security"). The server asks only the pool session whose scope is that job (`whoDrives` in lib/office/driver.ts, never `ps`), so the same id driving another job is a stranger there. `/api/state` and the job detail report each job's `ownerStatus` from the lease; only the detail sets `jobSession`, from the same answer. Jobs record each session that drove them in `runs[]`.

**Evidence**: every `forge verify` run records the worktree HEAD it checked, its attempt number within the round, and its result; earlier attempts are archived, never overwritten, so "verify first-pass" means the first attempt. `forge pr open` refuses to push a HEAD that this round's last verify run did not pass on (and every member HEAD with it). `forge job verdicts` records the sha the reviewers saw. When the integrator resolves conflicts after the panel passed, a one-lens `code` review of the resolution (`review/integration/code.md`, `forge job verdicts --round integration`) must pass before the PR opens (under `pr.integrationReview: code-only`, the default, a resolution whose conflicts and changed files were all docs or generated files skips it with a note); it is logged as an `integration-review` event, not in `job.verdicts`, so stats keep counting numbered rounds only. `forge pr open` records the sha it pushed (`pr.pushedSha`), and the first `forge pr sync` that sees the PR merged measures the human delta, the commits, lines and files humans added after that push (`pr.humanDelta`). After the merge, `forge sync` keeps measuring the job's outcome (`job.outcome`: a revert, follow-up bug issues and churn inside `outcomes.windowDays`) until the window closes, and `lib/engine/evals/autonomy.ts` judges a job with a final outcome for the autonomy rate. Each verify also writes a test-integrity report (deleted or renamed tests, added skip/focus markers, the test-count delta, test and CI config edits since the merge-base), which reviewers and the approver read and `verifyIntegrity: block` turns into a failure. Evidence for an older commit is not evidence.

**Generated files**: committed paths a command regenerates (`worktrees.generated`, e.g. `dashboard/dist/**`) are never hand-merged. When `forge integrate` stops on conflicts, Forge splits them: a path counts as generated only when it matches a glob and passes the same checks as `forge git add` (no leading `-`, nothing absolute, no `..`, no `.git` segment, no symlinked parent leading out of the worktree, and the name must resolve to itself); everything else is a real conflict. When generated paths are all a stop has, Forge takes the base side of each (`--theirs` in a merge, `--ours` in a rebase; a path the base deleted is deleted), runs `worktrees.generatedBy` through the same logging as `forge run` (`logs/integrate-regenerate-*.log`), stages every glob-matching path the build wrote, added or deleted, and commits the merge or continues the rebase, repeating for each later pick that stops the same way. Names reach git only as literal pathspecs, over stdin. The build runs only in the job's own worktree on the job's branch (never the main checkout, a subdirectory or another branch; mid-rebase the branch is read from `rebase-merge/head-name`), and every `rebase --continue` Forge runs first checks that the todo holds only picks. A mixed stop goes to the integrator with the real conflicts only: the generated paths are listed as `regenerated` and, under `--keep-conflicts`, staged from the base side but not built, since the sources may still hold conflict markers; `forge integrate --continue` rebuilds them once nothing is unmerged. When Forge can't rebuild (no `generatedBy` command, an invalid glob, the worktree guard, or a failing build), it falls back to the old behaviour: every unmerged path is listed, `regenerateError` says why (with the build's last 20 lines), and an aborted merge leaves the worktree clean. A generated-only integration logs `integrated` with `regenerated`, so step re-verifies it and moves to `pr`: no integrator runs and no integration review is needed. Results and events carry `regenerated` and `regenerateError` only when they are non-empty.

**Budgets**: `pipeline.budget` limits tokens, estimated cost, agent minutes (summed agent run time), committed changed lines vs the base, and failed verify runs per round. Limits are read from config at every check, and a job's own `budget.limits` override them. Three checkpoints enforce them: `forge job agent end`, `forge job round` (before incrementing) and `forge verify`. An exceeded key parks the job at `waiting` on `budget` with its stage kept, logs a `budget` event, and adds a `budget` block to the command's JSON. `forge job budget <id> --set k=v` raises a limit; `--ack` grants one more full budget past the current use (a `verifyRetries` ack lasts only for its round). Neither changes state; the orchestrator resumes the job. Every checkpoint writes `budget.lastCheck` with what was used, so the dashboard can show it without running git. The dashboard derives effective limits and use client-side from `config.pipeline.budget`, the job's usage and `lastCheck`, and offers approve (ack, or raise via the note) on `waiting:budget`.

**Dependencies**: `dependsOn` lists job ids, set with `forge job set <id> --field 'dependsOn=[…]'`, which rejects unknown ids, the job itself and cycles. A dependency counts only when its job is `done`; `cancelled` or missing ones block until a human removes them. A queued job with unmet dependencies is parked at `waiting` on `external` with a `dependencies not done: …` reason (other waits are never overwritten), `forge next` skips it, and `forge job claim` refuses it with exit code 4 unless `--force`. Parking releases the job's lease, since nobody drives a parked job; rewriting the reason of a parked job or unparking it keeps the driver, so a `--force` claim on a parked job survives sync. `forge sync` unparks a job to `queued` once its dependencies are done, and `forge next --claim` then resumes it. A new branch for a job with exactly one unmerged dependency starts from that dependency's branch, and `job.base` becomes that branch, so the PR, `forge integrate` and reviewers' diffs are against it (a `stacked` event). Once the dependency merges, `forge sync` moves the base back to the dependency's own base (retargeting an open PR with `gh pr edit --base`) and logs `retargeted`. More than one unmerged dependency is refused.

**Inbox**: dashboard requests are claimed by a session before they are handled, under a lock, so two orchestrators draining the same inbox cannot both act on one request. A claim with no ack for 30 minutes can be taken over. The drainer is either your own session (`/forge requests`) or, with `daemon.enabled`, the headless sessions `forge dash` supervises (see "Daemon"); both go through the same claims, so they can run side by side. Each request has a **scope**: a job request (`approve`, `revise-spec`, `rework`, `answer`, `cancel`, `resume`) whose job exists belongs to that job, and everything else, including a job request whose job is malformed or unknown, belongs to the inbox (`_inbox`). A daemon session sees and may claim or ack only the requests of its own scope; a human's session sees them all. The inbox session does intake only: for `run`/`next` it creates or claims the job and hands it off with `forge requests add resume --job <id> --intake run|next --session <its session>`, which releases the claim when that session (or any inbox session id) holds it, so every pipeline runs in its job's own session. Under the inbox scope, `forge worktree create` and `forge job agent … start` refuse, so the inbox never drives a pipeline. A job created from the dashboard (`POST /api/jobs`) skips the inbox: the server creates it and queues its `resume` (`args.intake: new`) straight to the job's own session.

## Job repos

A job can change [member repos](GLOSSARY.md#multi-repo-jobs) together with the root repo. `job.repos` lists every [job repo](GLOSSARY.md#multi-repo-jobs) as `{ repo, worktree, branch, base, pr, verifyOnly, interim }` (`interim`: the job's [interim strategy](#interim-strategies) override for that repo as a dependency):

- `repos[0]` is the root repo (`repo: null`). It is a mirror: the top-level `branch`, `base`, `worktree` and `pr` stay the root's own fields, every reader keeps using them, and `normalizeJob` and `serializeJob` rebuild `repos[0]` from them, so it can't drift. Nothing writes `repos[0]` directly.
- Entries 1..n are members, named by a `repos` entry in config. A member's `branch` is always the job's branch (null for a verify-only member), derived on every load and never read back from disk. Its `base` is the member's `defaultBranch` when it was added.
- A single-repo job has exactly one entry, and its briefs, verify report and records, worktree result, PR body and PR results are what they were before job repos existed.

Members are added four ways, never by an agent editing `job.json` (`repos` is locked in `forge job set`): a human with `forge job repo add|remove` (which also removes), a planner or spec-writer proposal that a human (or the foreman, when allowed) approves ("Repo proposals" below; approving a proposal for a verify-only member promotes it to an edited one), CLI intake from a member repo's issue (`forge next --claim`, `forge job from-ref owner/name#N`; "Member repo trackers" in docs/TRACKERS.md), and `forge job repo downstream`, which the job's own session runs to add the consumers of the repos it changes, verify-only ("Downstream verification" below). Then each member gets a worktree at `<member worktrees root>/<id>` (`worktrees.root` with `{repo}` set to the clone's basename, resolved from the clone; by default `../<clone>.worktrees/<id>`), on the job's branch, or detached at its base for a verify-only member. Members get no `worktrees.copy`, setup commands or shared Cargo target; a member component of kind `service` or `app` holds a job port like a root one (its `--repo` commands get it as `{port}` and `$PORT`), and a member `library` sees `{port}` empty. `forge run … --repo <name>` runs a member component's command there, `forge git add|commit … --repo <name>` stages and commits there, and `forge verify` checks every member after the root (`worktree-clean`, `secrets`, the `verify` steps as the member's component commands, and `integrity`), recording one `repos` entry per member in the run. A HEAD counts as verified only when this round's last run passed and the root and every member HEAD are the ones it checked. `forge pr open` checks every repo before anything is pushed, then opens or updates one PR per non-verify-only member, then the root PR; `forge pr sync` records each member PR's state. `forge integrate`, the integration review, verifiers, e2e and PR feedback import stay root-only; review covers every repo (below).

A job with at least one non-verify-only member is a linked job, and its PRs are one unit (lib/engine/project/repo-order.ts):

- **Merge order.** Repo A depends on repo B when a component in A depends (`build` or `runtime`) on a component in B; a component without `repo` is the root's. Dependencies through a repo outside the job count. The order puts dependencies first and keeps `job.repos` order otherwise. When the edges cycle, the order uses `build` edges alone; when those cycle too, the order is `job.repos` and the job has a `cycle`.
- **Sibling links.** Every PR body has a Forge-owned section between `<!-- forge:siblings -->` and `<!-- /forge:siblings -->`. Once two PRs have numbers, `forge pr open` and `forge pr sync` write `Part of job <id>: o/lib#7 then o/app#11` there in every OPEN PR, rewriting only the text between the markers in the live body, and only when the line changed since the last write (`pr-links-updated`). A body whose markers a human removed is left alone (`pr-links-skipped`), and a failed write (`pr-links-failed`) never fails the command.
- **Done.** The job is done only when the root PR and every member PR merged (`all PRs merged`), each read by this sync: a member whose sync failed counts as not merged. A merged root with an unmerged member waits on `pr-review`, naming the member. A member PR closed without merging logs `repo-pr-closed` once and adds a note; it never cancels the job.
- **Merging.** `forge pr merge` merges the PRs in order, each only when every PR it depends on is MERGED by this call's own sync, with each PR's own checks, head pin and auto-merge rules; `--repo NAME` or `--root` merges one PR under the same rule (docs/CLI.md "Merging"). A member's merge events carry `repo`, a targeted call's carry `target: true`, and `forge sync`'s `mergeDeferred` continues the walk once a queued dependency merged.

These add events `repo-pr-closed`, `pr-links-updated`, `pr-links-skipped` and `pr-links-failed`, and optional `repo` and `target` fields on the merge events, with no schema change.

**Repo proposals** (lib/engine/project/repo-proposals.ts). The planner and spec-writer briefs carry a `Project repos (JSON)` line when config `repos` is non-empty: each member repo, whether the job has it (`onJob`), its components and the components in other repos that depend on them (`repoGraph` in lib/engine/project/graph.ts, config only). An agent that finds the work needs a change in a repo the job lacks runs `forge job repo propose <job> <repo> --reason R`: a `repo-proposed` event `{repo, reason}`, and `repo-proposals.md` (fenced reasons and notes under an untrusted-data line) and `repo-proposals.json` rewritten in the job dir. Only a config `repos` name is accepted, never for an eval job, a job at stage `pr` or `done` (or done, cancelled or failed), or a repo already rejected on the job; a pending or member repo returns `already`. Under the daemon it runs only in the job's own session. Once no agent is running, step rule RP1 parks the job on `human` with reason `repo proposal: <names>` at any stage before `pr`, ahead of the spec and split gates. A human decides in the dashboard (the Needs-you card or the drawer, `POST /api/jobs/:id/repos`) or with `forge job human <id> approve-repos|reject-repos --repo a,b --note N` in their own terminal; the foreman decides the same way with `--actor foreman` only when `repo-proposal` is in `foreman.decides`, naming the `repos` that `forge job assist` returned. Those are the names, with their reasons, in the assistant brief's `Pending repos (JSON)` line, read from events and not from the session-editable `repo-proposals.md`; the assistant escalates when that file shows a different pending set, so a repo hidden from the file is never decided unseen. A decision always names its repos: each must be pending, and the dashboard's and the foreman's must be the whole pending set, so nothing proposed after the decider looked is decided with it; a person on the CLI may name a subset. It runs under a per-job lock in `.forge/locks/`. Approve adds each repo through the `forge job repo add` path (every clone check runs before the first write); both log one `human` event carrying `repos` and the actor, which `forge job audit` shows. RP2 then creates the new member's worktree, and a rejection re-runs the planner (P1) or spec-writer (SP2) that proposed. Events gain the additive `repo-proposed` type and `repos` on `human` events under event schema v2; nothing else changes shape.

**Downstream verification** (lib/engine/project/downstream.ts, CONFIG.md "Downstream verification"). The changed repos are the root and every non-verify-only member. A `repos` entry whose component has a `dependsOn` edge to a component in a changed repo is a direct consumer, and, when it has a `link` to a changed repo, a verify step command and room under `downstream.max`, and is not in `downstream.skip` or removed from the job by a human, `downstreamRepos` (pure: config, job and events) lists it to add. In `build` and `verify`, step rule DS1 runs `forge job repo downstream <id>` when a candidate is one the last `downstream-checked` event does not name; the command recomputes the list, runs doctor's clone check on each, adds each passing one as a verify-only member whose `job-repo-added` event carries `downstream: true` (a *downstream repo*), and logs one `downstream-checked {added, skipped}` event. RP2 creates their detached worktrees. Verify runs a downstream repo like any verify-only member, except that one with no active link from a changed repo fails a `links` step instead of running its steps; the report heads it `# Downstream consumer <repo>`, names each failing one after `VERIFY: FAIL`, `forge verify` returns `downstream: [{repo, ok, failure}]`, and V3's reason names the first failing one. The builder's rework brief then carries `Downstream failures (JSON)`: it fixes the library, or proposes the consumer. Proposing a verify-only member is allowed, and approving it promotes the member: its detached worktree (at the computed path) must hold no uncommitted or untracked change and no commit beyond its base, then it is removed, `verifyOnly` becomes false, a `job-repo-promoted` event is logged, and RP2 checks the repo out on the job's branch. The stored `VerifyRun` shape is unchanged; events gain `downstream-checked`, `job-repo-promoted` and `downstream` on `job-repo-added`, with no schema bump.

**Combined review.** A *reviewed member* is a non-verify-only member; a job without one reviews exactly as a single-repo job. With one:

- `forge job scope` diffs the root, then each reviewed member from its checked worktree against its own base (`resolveBase`), and lists member files under a `<repo>/` prefix, so a spec's Approach names them as `<repo>/<path>`. `scope.md` adds a `Repo <name>: base … @ … · HEAD …` line per member, and `scope.diff` in the job dir holds one unified diff with a `# repo <name|root> base … @ … · HEAD …` section per repo, member hunks prefixed `a/<repo>/` and `b/<repo>/`. Prefixes, context, colour, renames, external drivers and textconv are pinned on the command line, and replace objects and grafts are ignored. Protected paths in `scope.md` stay root-only (members are checked by `forge git`, verify and `pr open`).
- `forge job panel` adds each member's own lenses, read from the member's **clone** (`.forge/config.yml` `review.panel`, checklists in `.forge/reviewers/`), never from its job worktree. A member entry becomes the qualified lens `<repo>:<name>`, unless the root panel has `<name>` and the member gives it no checklist of its own: then it is subsumed, adding its `approach` and `paths` reasons to the root lens. Qualified lenses follow the root's, by member and panel order; they use `runtime.models.reviewer`, the reviewer effort layers and no app. A carried qualified lens stays only while its repo is a reviewed member.
- A qualified lens writes `review/round-<n>/<repo>.<name>.md` (`:` is not a valid Windows file name character; plain lens names never contain `.`). `roundLenses`, rework inputs and `forge job verdicts` drop a qualified name whose repo is not a reviewed member, wherever it was written.
- Every reviewer's brief gains `Diff: <jobDir>/scope.diff` (and `scopeDiff` in its job paths); a qualified lens's brief also names its `Lens repo:` worktree and base.
- The `scope`, `panel`, `verdicts` and `integration-review` events, and the scope, panel and verdicts output, gain `heads: { <repo>: <sha> }`, each reviewed member's HEAD (`null` in verdicts when the stored worktree is not Forge's). `sha`/`head` stay the root's, so single-repo records are unchanged. `heads` is evidence only: a later member commit does not invalidate a recorded verdict.

**Threat model.** The attacker is the builder, or a session misled by tracker or PR text: it can run `forge` commands and `Write` `job.json` and `events.jsonl` in its job dir. A hostile member clone config is covered by the same pinned git options as the root.

1. Widening the repos through the CLI: `repos` is locked in `forge job set`, and `forge job repo add|remove` refuse under `FORGE_DAEMON=1`, so pushing to another repo stays a human decision. The one exception is intake (`forge next --claim`, `forge job from-ref owner/name#N`, docs/TRACKERS.md "Member repo trackers"), which may add a member repo, in a daemon session too, because the repo comes from human-owned config rather than agent text: it must be a config `repos` entry with a GitHub tracker a human did not set to `kind: none`, its clone must pass doctor's member check, and the issue must exist and be claimable in that member's own tracker. The bypasses it handles:
   - (a) Widening an existing job: intake on an issue an active job already carries returns that job unchanged, so a repo is added only to the job intake just created, and `forge job repo add|remove` still refuse under `FORGE_DAEMON=1`.
   - (b) Naming an arbitrary repo: only an `owner/name` equal (case-insensitively) to a configured member tracker's slug matches; anything else stays foreign and `from-ref` refuses it.
   - (c) Option injection into `gh`: the ref must pass the `QUALIFIED` grammar (no leading `-`, no `..`, a 1–10 digit number without a leading zero), only the digits reach `gh` as the issue argument, and `-R` is the slug from validated config or a remote url.
   - (d) A missing or wrong clone: doctor's member check runs before anything is created or claimed.
   - (e) The root's GitHub Project leaking onto member issues: a member tracker's derived config has no project and syncs labels only.

   Residual risk: an agent that can create issues in a member repo through some other channel could get a job started from text it wrote, the same exposure as the root's issues have; readiness triage and the spec gate still apply.
2. A hand-edited member entry: a name that fails the repo name grammar (an option-like or traversal name) is dropped when the job loads; a member not in config `repos` is refused at every sink, because the clone is recomputed from config plus `.forge/local.yml` (and doctor's member check) every time, never read from job.json; the base is checked as a safe ref before it reaches git or a template; the stored worktree is used only when it equals the computed path; the branch is always derived.
3. Committing in the member's main clone instead of its worktree: `forge git commit --repo` refuses when the directory's top level is the clone.
4. Untrusted `gh` output for member PRs: only a safe integer number and an https url are stored, and a PR from a fork found by branch is refused.
5. Secrets leaving through a member PR body or member commits: both are scanned before the first push of any repo.
6. Protected paths in a member repo (a CI workflow there runs with that repo's secrets on the first push): `policy.protectedPaths` applies to every non-verify-only member exactly as to the root. `forge git add|commit --repo` previews the member's index against its own base and refuses a `refuse` path; verify's `protected` step and `forge pr open` check each member's branch from its merge-base at the HEAD they check; `pr open` first refreshes each member's base from its push remote, as it does the root's, so a remote-tracking base moved from the worktree can't hide a path. Member hits are named `<repo>:<path>` on the one `job.protectedPaths` flag and tagged with their `repo` (and in `protected.diff` under a `# repo <name>` header), so an escalate path in any repo parks the job at PP1 and `pr open` pushes nothing, in any repo, until a human approves at that park.
7. A consumer landing before its dependency: `forge pr merge` decides only on this call's `gh` answers, so a hand-edited member state in job.json counts for nothing and a member whose sync failed counts as unmerged. A member PR counts only when gh reports its head on the job's branch and its base on the member's base, so a hand-edited number that names a PR merged elsewhere, or an unrelated open PR, is a sync failure: it is not recorded, satisfies no order check, and is never merged or edited. The root PR's recorded number is not checked this way (residual risk, as before linked merges). `--now` never bypasses the order, `--auto` is never queued on a PR whose dependencies are unmerged (GitHub may merge it at once), a cycle refuses every merge, and `--repo` must name a non-verify-only member that passes the repo name grammar. Sibling links splice only Forge's own line, built from checked slugs, safe numbers and the job id, between Forge's markers, and re-upload the rest of the body unchanged, after reading the body again just before the write and skipping (`pr-links-skipped`, reason `changed`, retried on the next sync) when it changed since the first read; the body is never rendered or run.
8. Choosing its own review: the builder can commit a weaker `.forge/config.yml` or rewritten checklists in a member worktree, or write a qualified lens for a repo the job doesn't have into `job.reviewers`. Member panels and checklists are read only from the human-owned clone, and a qualified lens counts at panel, step and verdicts only while its repo is a reviewed member. The combined diff can't be reshaped through the member worktree's git config (`diff.noprefix`, `diff.mnemonicPrefix`, `diff.external`, textconv, replace objects or grafts), and repo, base and lens names pass their grammars before they reach argv or a shell line.
9. A hostile or broken member clone config: `forge job panel` opens it non-blocking, accepts only a regular file of at most 256 KiB that parses with a `review.panel` list, and otherwise fails with `repo <name>: …` and records no panel, so a round never reviews with a lens silently missing. An entry with a bad name or `paths`, no checklist, or an explicit checklist that resolves (after symlinks) outside the clone is dropped and reported in `problems`.

8. Widening the repos through a proposal: a job session can only propose. `decideRepoProposals` runs only in a human's terminal (it refuses every daemon session but the office), the dashboard server, or the office with `--actor foreman` under `foreman.decides`, and it decides only the repos the decider named, checked against the pending set computed from events and config, never from `repo-proposals.json` (the dashboard and the foreman must name that whole set, so a repo hidden from an edited file is refused, not approved unseen). `foreman.reserved` patterns are matched against the pending proposals' reasons too. A name in an event that fails the repo name grammar is ignored everywhere, so it never reaches argv, RP1's reason or the dashboard. The proposal files sit in the job dir, which a session could edit, the same residual risk as `issue-candidates.json`; they are rendered as text and only ever describe the decision.
9. Widening the repos through downstream verification: `forge job repo downstream` is the one path by which a daemon session adds a repo, and only the job's own session (or a human outside the daemon) may run it; another job's session, the inbox, the office and an invalid `FORGE_DAEMON_SCOPE` are refused before anything is read. It takes no repo name: candidates are computed from config, the job and events, so it can add only a `repos` entry with a linked edge to a changed repo, and only as verify-only, which never branches, pushes or gets a PR. Only `decideRepoProposals`, with its existing authority checks, turns a downstream repo into an edited one; a job.json hand-edited to clear `verifyOnly` on a downstream repo gives it no push, since `forge pr open` refuses a member whose latest `job-repo-added` says `downstream: true` with no `job-repo-promoted` after it. An unlinked consumer, which would pass against the released library, is skipped at discovery and fails verify's `links` step, so it never reads as green. Promotion refuses a verify-only worktree with uncommitted, untracked or unpushed work rather than discard it. Suppressing downstream verification by forging events or dropping a member from job.json stays possible, as for any member today.

Residual risk: a `Write` to job.json can flip a member's `verifyOnly` or drop a member entry; the flip is still bounded by the commits-ahead check and the verified-HEAD rule. The same `Write` can also add a member entry by hand, skipping the human-only `forge job repo add`; `pr open` then pushes to that repo and opens a PR there. It is bounded: only a repo a human listed in config `repos` whose clone passes doctor's check qualifies, its branch gets every check above (secrets, protected paths, verified HEAD), and every member it pushes is listed in `pr open`'s `repos` result. Forge now merges member PRs, so such a member would be merged too, bounded by the same checks plus CI and the head pin at merge time. The merge order comes from the main checkout's `.forge/config.yml`, which a session with `Write` there could change. Requiring a `job-repo-added` event would not close it, since `events.jsonl` is just as writable; binding members to a tamper-evident record is the same follow-up as for approvals ("Untrusted input").

### Local links

A `link` on a `dependsOn` edge (CONFIG.md "Local links") makes a consumer job repo build against a dependency job repo's worktree while the job is in progress. The rule is that a link never reaches a commit: `lib/engine/project/links.ts` recomputes the links from config and the job's repos before every `forge run` and verify step, renders them only into `<jobDir>/links/`, and puts shims for cargo, cmake and npm first on that command's PATH; tracked lockfiles the patched build rewrites are written back afterwards. Verify's integrity report (`lib/engine/guard/integrity.ts`) then flags any override that was committed anyway.

**Threat model.** The attackers are the builder (or a session misled by tracker or PR text) and a hostile checkout.

1. Committing a link override so the PR builds only on this machine: integrity rules R1 (an absolute path of the root's or a member's worktrees root, or of `.forge/jobs`), R2 (`FETCHCONTENT_SOURCE_DIR_`), R3 (a `[patch` table in a `.cargo/config(.toml)`) and R4 (a `file:`/`link:` dependency in `package.json` that is absolute or leaves the repo), blocking under `verifyIntegrity: block`. The diff is read with `--text`, so `-diff`/`binary` attributes hide nothing; renames are read on their new side; a symlinked `.cargo/config.toml` is reported as a link-mode change.
2. Editing job.json so a link points a build at a directory of its choosing: worktrees are recomputed (`isOwnWorktreePath`, `trustedMemberWorktree`), never taken from the stored value alone, and a link dir that resolves outside its worktree is inactive.
3. Config text reaching TOML and sh: names and sources are pattern-checked at validation, every value is single-quoted in the shims, and paths are JSON-escaped into TOML.
4. Planted shims in the job dir: Forge rewrites every rendered file before each command, deletes what it did not render, and replaces a planted symlink there instead of following it. The session can run commands as the same user anyway, so this is not a privilege boundary.

Residual risk: a command that calls a tool by absolute path builds without links (a missing link, not a leak), and R1 knows only this machine's paths. Two `forge run`s at once in one consumer worktree can race the lockfile snapshot; verify's `worktree-clean` then reports what is left.

### Interim strategies

What a consumer's PR points at while its dependency is unmerged is the dependency's **interim strategy** (CONFIG.md "Interim strategies"): `local` (the default: the consumer PR is a draft and never auto-merged), `sequential` (the consumer PR opens after the dependency's merges), `git-ref` (verify pins the dependency's commit in the consumer's manifest) or `canary` (verify pins a `-canary.<sha12>` npm version a human publishes). The job override is `job.interim` for the root and `repos[i].interim` for a member (`repos[0].interim` mirrors `job.interim`; job schemaVersion 13), set only by the human-only `forge job repo interim` (`interim` is locked in `forge job set`); null inherits config. `lib/engine/release/interim.ts` resolves strategies and edge states without I/O (step imports it); `lib/engine/release/interim-apply.ts` writes and checks pins and publishes.

- **Deferral.** `forge pr open` holds back a repo whose sequential dependency is not MERGED according to `gh` now, or whose canary is unpublished, plus every repo that depends on a held one through a sequential, git-ref or canary edge. A held repo is checked like any other but never pushed and never given a PR, and the result's `deferred` list and a `pr-deferred` event (logged after that call's PR events) record why. Deferral is recomputed on every `pr open`; nothing is stored in job.json. Step treats the latest of `pr-opened`, `pr-updated` and `pr-deferred` as the last open attempt (PR3), then parks a canary deferral on `human` (PR6), runs `pr open` again once every deferral can open (PR7), or waits on `pr-review` (PR8); `forge pr sync` resumes a parked job whose sequential dependencies merged in its own answers (`reopen: true`, plus a `resume` request when the daemon is on), before the merged-root wait and even when the root has no PR. With interim edges, a PR already MERGED is never pushed again. A record of MERGED that `gh` denies is corrected to the live state (`pr-state-corrected`), so step does not run PR7 again on the same input; one `gh` can't confirm stops `pr open` (external).
- **Pins.** Verify commits pins before it reads any HEAD, dependencies first, after scrubbing a dependency's branch the way `pr open` will, so the sha pinned is the sha pushed; `pr open` recomputes every pin against the checked commits and refuses a stale one (`interim_stale`), and pushes the root's branch first when a member pins it. A manifest is written through a temp file with a random name in its real parent directory, opened `O_EXCL | O_NOFOLLOW` with mode `0600` and renamed over it, so a link planted at either path is never written through, and the temp file is removed when the write, chmod or rename fails.
- **Release gates.** Every edge has a gate (`releaseGates` in `lib/engine/release/interim.ts`, shown by `forge job interim`): `ci` for git-ref and canary, which the check `forge init write` seeds (`.forge/ci/release-gate.mjs` and its workflow; CONFIG.md "Release gate") fails while a pin remains, so Forge itself does not block them; `held` for local and sequential until an `interim-released` event records the dependency's release; then `bump-due` while a consumer with links and an unmerged PR does not name the release yet (no `interim-bumped` for that version after the record; verify's release bump writes it), and `released`. A held consumer's PR is created as a draft (local always, sequential while held), `forge pr ready` refuses it before any `gh` call (`release_gate`), `forge pr merge` refuses it after the merge-order check (`pr-merge-refused`, `reason: release`; `--now` included), and step's PR4 never runs while a local edge's gate is not released, a gate is held or bump-due or, in a job with any interim edge, a recorded PR is a draft (a job without edges auto-merges as before, draft or not). Only the human-only `forge job interim release` and a `--job` `forge release run` write `interim-released`, after the dependency's recorded PR is MERGED; only verify writes `interim-bumped`; `forge pr ready` logs `pr-ready` per PR and records `isDraft: false`. Readers check every `interim-released` record: a repo key that fails `isRepoKey` or a version that is not semver or names a canary is ignored.

**Threat model.** The attacker is the builder or orchestrator, possibly steered by tracker or PR text, which can write job.json, events.jsonl and the worktrees. The assets are a package published under the human's npm credentials and pins that point CI at code nobody verified.

1. Publishing or declaring a release from a daemon session or an agent: `forge job interim publish`, `forge job interim release` and `forge job repo interim` refuse under `FORGE_DAEMON=1` (`release` before it reads the job or config), and `publish --confirm` also refuses when stdin is not a terminal (an agent's Bash tool has none). The TTY check is a speed bump against a misled session, not a sandbox.
2. An automatic path publishing: only `forge job interim publish --confirm` runs `npm`; verify, `pr open`, `pr sync` and step never do. A hand-edited `interim: canary` only defers PRs.
3. Publishing someone else's package: the exported `package.json` `name` must equal the link's `name` from config.
4. Publishing unverified or uncommitted content: the dependency's HEAD must be the sha this round's last verify run recorded, and that run must have passed, and git must show that commit on the job's branch (job.json alone is writable). The package is written from that commit's git objects (`ls-tree` plus `cat-file`, no checkout, so no git filter, hook or attribute runs and nothing untracked or ignored ships) into a fresh `mkdtemp` directory under the system temp dir, outside the repo and the job dir, which is removed afterwards.
5. npm running the package's own code or config: `npm publish --ignore-scripts --workspaces=false` runs no lifecycle script (`prepublishOnly`, `prepack`, `publish` …) and looks for no workspace root; a package that tracks npm, yarn or pnpm config anywhere is refused (it could redirect the registry and the token): any path component whose name, NFKC-normalized, case-folded and stripped of default-ignorable code points, NTFS stream suffixes, trailing dots and spaces and leading dots, starts with `npmrc`, `yarnrc` or `pnpmrc`, so `.NPMRC` on APFS or NTFS is caught; a tracked symlink (or any non-regular blob) is refused, and the export writes with `O_EXCL | O_NOFOLLOW`, so two paths that fold to one name fail rather than overwrite; and in case a name still slips through, npm runs from an empty `--prefix` (its cwd too) with `npm_config_globalconfig` pointed at an empty file, so it reads no project or global config at all, only the human's user config that holds the token; `publishConfig` is deleted from the rewritten `package.json` (it could change the registry or make the canary `latest`).
6. Secrets in what ships: the secret scan runs over the dependency's branch commits and then over every exported file (base content ships too), and blocks under `verifySecrets: block`.
7. Option and manifest injection: `npm` gets fixed argv with no shell; a sha must be a full hex id; a remote passes the same check as `repos[].remote` and goes into TOML or JSON via `JSON.stringify`, into CMake as a whole-token replace. A remote's credentials are dropped under every scheme (through the last `@` of the authority; a bare ssh user stays), and a local path in the home directory is never pinned (the edge is `blocked`), so a pushed manifest names no home path.
8. A forged pin (a rev edited to an unverified sha): `pr open` recomputes it from the checked commits and refuses.

Accepted: a forged `canary-published` event only lets a consumer PR open against a version that doesn't exist, so its CI fails; nothing is published. A forged, well-formed `interim-released` event opens a held consumer's gate: `forge pr ready` and `forge pr merge` then treat the dependency as released. Nothing is published, a human still reviews the PR, and `forge job interim release` itself refuses in a daemon session. A forged `job.interim` in job.json can switch a strategy (it is not tamper-evident, like other job.json fields); every effect stays bounded by the checks above.

## Concurrency

- **Many jobs, one session**: the orchestrator runs agents in the background and advances each job as notifications arrive, up to `runtime.maxParallelJobs`.
- **Many sessions, one repo**: all state is in the main checkout's `.forge/`. Writes take a per-job `mkdir` lock and are atomic (write and rename). Backlog edits and tracker claims take their own locks. Job ids are created with an exclusive `mkdir`.
- **Locks prove death** (`withLock`, `withLockAsync` and `tryLock` in lib/core/os/lock.ts). Acquiring is `mkdir <lockDir>`; the holder then writes `<lockDir>/holder.json` = `{ v: 1, pid, startedAt, host, token }` (its process's start time and a token unique to the acquisition). A lock's age never counts: a waiter breaks a parseable holder's lock only when the holder is on this host and provably gone, its pid dead or, from `ps -o lstart=` (at most once a second per token), started more than 30 s from `startedAt`, so the pid was reused. Another host, a live pid with a matching start, or a `ps` that fails all count as alive, and a long section keeps its lock with no refresh. A dir with no parseable `holder.json` (an older Forge's lock, one caught between its mkdir and its write, or a planted file) falls under the one age rule: it may be broken once its mtime is over 60 s old. Breaking is one breaker at a time: `mkdir <lockDir>/breaking` (anyone else waits), re-read `holder.json` and back off unless its token is still the one judged dead, then rename the dir to a `<lockDir>.dead-<random>` grave and remove that. A breaker that dies mid-break leaves the marker, which wedges the lock (waiters time out with `timed out waiting for lock <dir> (held by pid <pid>)`) but never admits a second holder. Release removes the dir only while `holder.json` still carries the holder's own token. `tryLock` makes one attempt, with the death-proof break applied once.
- **One `forge dash` per repo**: the pool takes `tryLock(<locks>/daemon)` at start and holds it until it stops, closes or the process exits; a second dash started at the same moment loses the mkdir and reports `another forge dash (pid N) owns the daemon`. A dash that dies leaves a lock naming a dead pid, which the next start breaks. The older record check (`otherOwner`) still runs after the lock, so a dash from an older Forge, which takes no lock, is still seen.
- **Worktrees** live outside the repo (`../<repo>.worktrees/<job>` by default), so watchers, bundlers and Cargo workspaces don't see nested copies. Untracked files agents need, such as a gitignored `CLAUDE.md` or `.env`, are copied in, and setup commands run once.
- **Rust**: with `worktrees.cargo.sharedTarget`, one `.cargo/config.toml` above all worktrees points every job at a single target dir. Dependencies compile once, and disk use doesn't multiply. Cargo serialises concurrent builds on that directory's lock, which is usually still far faster than cold builds per worktree.
- **Ports**: each active job gets one unique port per service or app component (`job.ports`, `dev` when there are none) from `ports.base`, under the same lock as backing ports; `job.port` is the first one. Commands see them as `{endpoint.<component>}`, `FORGE_PORT_<C>` and `FORGE_ENDPOINT_<C>`, the component's own as `{port}`, `$PORT` and `$FORGE_PORT`, and backing ports as `{backing.<name>.port}` (lib/engine/environment/ports.ts, lib/engine/environment/endpoints.ts; docs/CONFIG.md "Ports and endpoints").
- **One headless session per job**: with `daemon.enabled`, `forge dash` supervises an inbox session plus up to `daemon.maxConcurrent` (default 3) job sessions, each driving one job. A job's lease still keeps a human's session and its daemon session from driving the same job; it passes between daemon sessions without `--force` because the inbox releases it when it hands a job off, and the supervisor expires a session's lease when its child exits (see "Ownership"). `runtime.maxParallelJobs` limits a human's interactive session, not the pool.
- **Background commands** are idempotent per job and command: `forge run <id> dev --background` returns the recorded process while it is alive (`reused: true`) instead of starting another on the same port, and reports `listening` once the port answers. A per-job lock covers the check and spawn, so parallel UI reviewers share one dev server; the orchestrator starts it before them and runs `forge stop` after.

## Daemon

`forge dash` supervises a **pool** of `claude -p --input-format stream-json --output-format stream-json` children (`lib/office/pool.ts`): one inbox session for requests without a job, with `foreman.enabled` one **office** session (scope `_office`) for `gate` requests (see [Foreman](#foreman)), and one session per job with work, up to `daemon.maxConcurrent` (1 to 16, default 3; neither the inbox nor the office is counted). Each session is supervised on its own by `lib/office/session/lifecycle.ts`, with its own state, failure count, budget hold, idle stop, resume id and log, so one job's crash loop never stalls the others. The supervisor never reads claude's output: `lib/integrations/claude/child.ts` spawns the child and kills its process group, and `lib/integrations/claude/stream.ts` turns its stream-json lines into domain events (a turn started or ended, a session id, a permission prompt) that the supervisor reacts to. The supervisors never run agents or write job state: they only decide when a session gets its one turn. Every child is built the same way (`daemon.command`, `DENY_TOOLS`, git pins, the trust snapshot) and differs only in its session uuid and `FORGE_DAEMON_SCOPE=<scope>` in its environment; the scope never reaches stdin or argv.

**Periodic sync.** While the pool is wanted and `daemon.enabled` holds, it also runs `forge sync` every 2 minutes as a plain CLI child (`runSyncChild`: no daemon scope, so it acts as the human who started `forge dash`, the same as typing it), never in the server process, whose synchronous `gh` calls would stall every session's pipe. One runs at a time, a run over 10 minutes is killed, it is skipped while the trust snapshot is stale, and each distinct failure is logged once to the inbox log. This is what turns failing checks, PR feedback and conflicts into `gate` requests, unparks dependents and finishes merged jobs without a session having to sync first; the pool ticks as soon as each run ends.

**Reconciler** (lib/office/reconcile.ts). A job whose `state` is `running` has no gate holding it, so anything that leaves it with nothing to drive it (a crashed session, a turn that ended with nothing queued, an agent end claude never delivered) would strand it. One level-triggered pass answers "is this job driven?" from what is, not from which event happened. It runs in `forge dash` every 30 s (`RECONCILE_MS`) while the pool is wanted, for one job when its session's turn ends and when its child exits, and once per `forge sync` unless a live process holds `<locks>/daemon`, which sync reads without taking (then it reports `reconcile: "skipped (forge dash owns it)"`). Each pass first requeues orphaned requests ("Ownership"), then judges every `running` job; jobs in any other state are parked, queued, blocked, waiting on a person or finished, so it never acts on them and drops their record. A running job is **driven** when a request routed to it is pending or in progress, when (in dash) its own session is `busy` or `stopping`, or when its lease is live, except that a live lease whose driver is the job's own session does not count while that session is `off`, or has sat `idle` for 60 s (`IDLE_UNDRIVEN_MS`) with no background task in claude's latest `system`/`background_tasks_changed` (Claude Code can dequeue a finished agent's task notification into an empty result the model never sees, which left a job with an agent marked running and nothing to wake it; a claude that has not reported its tasks counts as busy with them only while `job.json` marks an agent running). An **undriven** job whose record is missing, or whose progress mark moved since its record, gets one fixed-text `resume` (`from: "reconciler"`; nothing from job.json reaches it), a record `{ mark, stage, resumedAt, request }` and a `reconcile { action: "resume" }` event. Undriven again at the same mark, with nothing routed to it, it is parked on `escalation` (`undriven at <stage>: resumed once with no progress since`), re-decided under the job lock, with a `reconcile { action: "escalate" }` event and the gate queued, so the Foreman or a person takes it. The records live in `<runtime>/reconcile.json`, written under `<locks>/reconcile`, so a restarted dashboard keeps its count. The mark is the time of the newest progress event (`PROGRESS_EVENTS`: transitions, rounds, verify runs, agent starts and ends, human decisions, integrations, PR opens and updates; never renewals, syncs, notes or failures). Separately, `forge job advance` logs every failed command as `advance-failed {rule, command, error, mark}`; when the same rule and command fail again with the same mark, it parks the job on `escalation` with the error as the reason, queues the gate, and returns `parked: true`.

**Turn timeout.** A job, inbox or office session's turn still `busy` `daemon.turnTimeoutMinutes` (default 60; `null` means no limit) after it was written, or after claude woke it itself, is stopped: the supervisor logs `turn-timeout { minutes }` and kills the child (`stop`, `reason: "turn-timeout"`). The exit path then marks its agents lost, expires its lease and requeues its claims, and the session stays wanted, so the pool respawns it for the requeued work and the reconciler watches the job. The timer is a `setTimeout`, which is monotonic, so a wall-clock jump never fires it.

**Exits let go.** Whenever a session's child is gone, because it exited for any reason or a kill saw no close and gave up on it, the session runs one release (`releaseSession` in lib/office/driver.ts) over every id it has had: for every job one of those ids drives (any job, not only its own scope), it marks the running agents `lost` (re-checked per role, stopping once another driver has the job) and expires the live lease, then requeues the requests those ids claimed. The inbox and office go through the same release. The log keeps `exit` first, then `agents-lost { job, roles }` and `lease-expired { job, session, reason }` per job, `requeued` and any `error`; then the pool reconciles the job and ticks. A pool boot runs the same release over every recorded id ("Ownership").

**States** (per session: `/api/state.daemons.inbox|jobs[id].status`, SSE `state` events): `off` (no child), `idle` (child alive, no turn in flight), `busy` (a turn was written and no `result` has been read), `stopping` (SIGTERM sent). Two things set `busy`: a turn write, and a `system`/`init` read while the session is `idle` after its child's first `result`. The second is a turn claude started by itself (a background agent finished and its notification woke the orchestrator): the supervisor logs `wake` once per such turn and writes the session no turn until it ends. `turns` and `lastTurnAt` count only the turns the supervisor wrote. A stdout line that parses as JSON with `type: "result"` is the only thing that sets `idle`. A fresh child is `idle`, because a stream-json `claude -p` does nothing until it reads a line. A session also reports `waiting` (it has work but no free slot), `held` (`budget` or `repo-budget`) and `kept` (`agents`: below).

**Trigger** (edge-triggered per request id). Every `pollMs` (2 s), after every `POST /api/requests` and after every `result`, the pool checks the trust digest, reads the pending requests once and routes each to its scope (`requestScope` in `lib/core/job/requests.ts`). Per session, it sets aside the budget-held requests (below) and takes the ids not yet in that session's `committed` set. If any are left and the session is not `busy`/`stopping`, it spawns a child if there is none (subject to the cap), writes the turn and records the eligible ids as in flight. A working `result` adds them to `committed`, which each tick prunes to ids still pending; a failed one (`is_error`) commits nothing and sets a retry time instead ("Failures" below). So one request causes at most one turn (a request the session leaves pending can't loop), a request that arrives mid-turn causes exactly one more turn, a child that dies mid-turn drops its in-flight ids so they retrigger, a turn that failed before claiming anything is sent again, and claimed (`in-progress`) requests never count. A pool start brings the inbox up even without work; the office and job sessions spawn only on demand, and the office only while `foreman.enabled` (with it off, pending `gate` requests get no spawn and no turn).

**Cap and slots.** When `maxConcurrent` job sessions are running, a job with fresh work is marked `waiting` (logged once as `waiting`). Slots go to waiting jobs in the order of their oldest pending request. When a job waits and some job session is `idle` and not kept, the pool stops the idle session with the oldest `lastResultAt` (`idle-stop`, `reason: "slot"`) and gives the slot away; that session resumes its conversation the next time it has work. A session is **kept** only while a running agent of its job keeps it; there is no grace after a result. Its agents are the `job.agents` of its job, counted only while `job.lease.driver` is one of the session's ids (current, spawn or past), so another driver's agents (a human's terminal session) never keep it. A running agent keeps it only for 2 h after its `startedAt`, the lease `agent start` gives, so a phantom can't hold a slot forever. A kept session still counts toward the cap: when every running job session is kept, the waiting job stays `waiting` and gets the next slot that frees, which the 2 s tick finds within one poll of the last agent ending. Each tick refreshes `kept` (`agents` or null) for running job sessions. After a job session's `result`, if its job is `done`, `cancelled` or `failed` (or gone) and no pending request routes to it, the pool logs `finished` and stops it (`stop`, `reason: "job-finished"`). Sessions that are off and clean, with no request routed to them, are pruned at the next tick; their files stay.

**Budget hold.** Limits are per job, so a hold is per session: `resume`, `rework`, `answer` and `revise-spec` requests whose job is at `waiting: budget` and still over a limit (`exceededKeys` in `lib/engine/metrics/budget.ts`) are never sent or committed, and that session reports `held: "budget"`. `approve` (the acknowledgement), `cancel` and job-less requests are never held. Once a human raises or acknowledges the budget, the next tick sends the turn. A `held` log line is written when the session's hold changes. Spend scales with the number of live sessions.

**Repo budget hold.** `budget:` caps what the whole repo spends per UTC day and month (see "Repo budget" below). While a cap is reached under `onExceeded: hold`, every job session's pending `resume`, `rework`, `answer`, `revise-spec` and `approve` waits unless its job is exempt (a retro, or one a human forced past the cap this month), and the session reports `held: "repo-budget"`, which wins over `budget` when both apply. `approve` waits too, because approving is no acknowledgement of the repo cap. `cancel`, gate requests (the office) and job-less requests (the inbox) are never held, and a busy session finishes its turn. The pool computes the status without writing anything (`write: false`) and reuses it for up to 10 s, recomputing at once when the audit log grows (an ack) or the `budget:` block changes.

**Files** (`.forge/runtime/daemons/`, gitignored, unversioned): `<scope>.json` holds `{sessionId, resumable, pid, serverPid, argv0, startedAt, spawnSessionId, lastTurnAt, logBase}`. `<scope>.log` gets every child stdout line verbatim, except that a JSON line with neither claude's `timestamp` (only its `assistant` and `user` lines carry one) nor an `at` gets the receipt time as `at`, so every line has a time; non-JSON stdout as `forge-raw`, stderr as `forge-stderr` (4 KiB per line), and the supervisor's own events as `forge-daemon` (`spawn`, `turn` (with `requests` and the session's turn number), `result`, `exit`, `stop`, `idle-stop`, `waiting`, `finished`, `resume-failed`, `session-changed`, `held`, `retry` (with `at`, `reason`, `attempt`, `requests`), `reaped`, `error`, `line-truncated`, `wake` (a turn claude started by itself), `agents-lost` (with `job` and `roles`), `lease-expired` (with `job`, `session` and `reason`), `requeued` (with `requests` and `rejected`), `reconcile` (with `action`), `turn-timeout` (with `minutes`); `stop` and `idle-stop` carry a `reason`). A stdout line over 8 MiB is dropped and replaced by a `line-truncated` marker. Each session rotates its own log to `<scope>.log.1` at spawn once it passes 20 MiB or, with `retention.logMaxBytes` set, as soon as it reaches that size mid-session (one older generation is kept, logBase grows by the rotated size, and writes still pending on the old descriptor land in `.log.1`, which is why the rotated size counts them); `GET /api/daemons/log` pages from `.log` back into `.log.1` under the same confinement. It pauses its child's stdout while the log stream is full. Pool-wide events (a trust stop, a config refusal) are written to every live session's log.

**Offsets.** Every log line has an offset: `logBase` plus the line's byte position in `<scope>.log`. A rotation adds the rotated file's size to `logBase`, so offsets only grow. Offsets are the SSE ids and the history keys, so the dashboard merges live lines and older pages without duplicates. The last 200 lines of each session stay in memory for SSE replay.

**Session and resume.** Each scope keeps its own session id. The first spawn gets a fresh `--session-id <uuid>`; once a child of that session has written a line, `resumable` is set and later spawns (a restarted `forge dash`, new work after an idle or slot stop) use `--resume <uuid>`, passing `--plugin-dir` again because resume does not restore it. A `system`/`init` with another `session_id` replaces the stored one (`session-changed`). A `--resume` child that exits non-zero without ever emitting `system`/`init` lost its transcript: the supervisor logs `resume-failed`, undoes whatever that child's error `result` committed, starts one fresh session and re-ticks, without counting a failure.

**Failures** are per session. A spawn `error` with no pid (ENOENT, EACCES) stops wanting that session (`cannot start daemon: …`), with no retry. Unexpected exits with no `result` since spawn are counted; at 3 the session stops wanting itself (`daemon stopped after 3 failed starts: …`); any `result` resets the count. `idleStopMinutes` ends stdin and stops an idle child, keeping the session wanted. The window counts from the later of the last spawn or `result` and the last agent end, and never runs out while a running agent keeps the session. **Lost agents:** whenever a job session's child exits, for any reason (pool or session stop, `forge dash` shutdown, a trust change or other pool-wide stop, a permission-mode narrowing, failed-turn strike-out, a job-finished or idle stop, a crash), every agent still marked `running` on a job one of its ids drives is ended with status `lost` and summary `lost: its daemon session ended`, through the same `recordAgent` path as `forge job agent <id> end --status lost` (an `agent-end` job event), and the session logs one `agents-lost` with `job` and `roles` per job. It happens before the stop resolves. Agents that already ended, and another owner's agents, are never touched, so the next session's `step` respawns the role (L1) or retries the reviewer (M1) instead of waiting on phantoms (G5). A job that finishes (`done` or `cancelled`) with an agent still marked `running` ends it the same way in the write that finishes it, with summary `lost: the job was <state> while it ran` and an `agent-end` event, and a job an older Forge finished that way reads as `lost` (no event), so nothing waits on an agent a finished job can never end. A failed `job.json` read or write here is logged as an `error` and the exit still completes. The synchronous last-resort SIGTERM from an `exit` handler marks nothing; the next orchestrator handles those agents as before. A `result` with `is_error` (claude reports an expired login or an exhausted quota that way, often with subtype `success`) means no request made progress: the child stays up, nothing is committed, and the session's `lastError` reads `last turn failed: …; retry at <time>` until a turn works or the session is stopped on purpose, so the dashboard shows it failing rather than idle. The session writes no turn before that time, which a `retry` log line records with its `reason` and `attempt`: when the child printed a `rate_limit_event` with `status: "rejected"` during the turn, the retry is at that window's `resetsAt`; otherwise it is a backoff that doubles from 1 minute (5 minutes for a limit without a reset time, such as an API key's spend cap) to 1 hour. A failure is a `limit` when that event was seen or the message says so (usage or rate limit, 429, 529, overloaded): limits are retried for as long as it takes. Any other failure is a strike, and at 3 in a row the session stops wanting itself (`daemon stopped after 3 failed turns: …`) and stops its child so the slot frees. A working turn clears the strikes and the backoff, as does a human's Start. In every case the other sessions keep running and the pool stays wanted; a session that isn't wanted spawns nothing until a human starts it (or the whole pool) again. What is repo-wide stops the whole pool and every child, with the error on the pool and in every session log: a trust-digest change, `daemon.enabled: false` at spawn, a `daemon.*` config problem, and symlinks under `.forge/trackers/`.

**Start and stop.** A pool start (dashboard Start, or `forge dash` booting with `enabled: true`) refuses while another live `forge dash` owns any record; otherwise it wants the pool, resets every session's wanted flag, failures and error, takes a new trust snapshot only when no child runs anywhere, and ticks. Stop stops every child. One session can be started (only inside a wanted pool, and never with a new snapshot) or stopped from its job panel's header (the Inbox and office sessions from their logs); a stopped job session stays listed and spawns nothing for new work until started again.

**Effort.** At every spawn, a session resolves its effort with `resolveEffort` (`lib/core/config/models.ts`), the one place levels combine. A session runs the orchestrator, so it resolves with no role: its job's `job.effort`, else `runtime.effort`, from the config bytes that spawn just hashed and the `job.json` read then. The inbox uses `runtime.effort` alone, and so does a session whose job is missing or unreadable. A level adds `--effort <level>` to argv after Forge's `--permission-mode` and before `--disallowedTools`, replacing every `--effort x` and `--effort=x` in `daemon.command`; with none, Forge passes nothing and the template's own `--effort`, if any, applies. The log records `{"event":"effort","level":<level> | "inherit","source":"job" | "config" | "none"}` right after `spawn` (a session never gets the `panel`, `role` or `complexity` sources that `resolveEffort` gives agents), and the session's `effort` in `/api/state` is the level its running child got (null while none runs, or when Forge passed none). A changed effort never stops, signals or messages a running child: it applies at that session's next spawn (an idle stop, a slot handover, a human's stop and start). Agents inherit their session's effort, since no `forge:*` agent's frontmatter sets one, and also get the level explicitly: every `spawn` from `forge job step` carries `effort` and every brief an `Effort:` line, which the orchestrator passes as the Agent tool's `effort`. An agent's level is resolved for its role: `job.effort`, the lens's panel `effort`, `runtime.efforts.<role>`, `runtime.effortByComplexity[job.complexity]`, then `runtime.effort`, and a builder on round 2 or later gets one level more unless the job's own effort set it. So agents started after a change already run at the new level while the session itself switches at its next spawn.

**HTTP surface** (consumed by the dashboard). `/api/state` has `config.daemon: {enabled}`, `config.effort` and `daemons: {enabled, wanted, maxConcurrent, live, lastError, inbox, office, foreman, jobs, clients}` (`foreman` is `foreman.enabled` from the latest config read), and each job row has `gateOwner` (`foreman`, `human`, or `null` when it waits on nothing or the foreman is off), where `inbox`, `office` and each `jobs[id]` are `{scope, wanted, running, status, sessionId, pid, lastTurnAt, lastResultAt, turns, failures, held, waiting, lastError, permissions, permissionMode, kept, effort}` (`kept` is `"agents"` while a child runs, the session isn't `stopping` and a running agent keeps it, else `null`; `effort` is the `--effort` Forge passed the running child, else `null`); `jobs` lists a session while it runs or stops, waits, is held, has an error, or was stopped by a human. `GET /api/events?session=<scope>` streams that session's `event: state` on connect (an off state for an unknown session) and on every change, its buffered lines after `Last-Event-ID`, then `event: line` with `id: <offset>` per new line (lines over 64 KiB become a `forge-truncated` marker), and `: ping` every 15 s; lines of other sessions are never sent. `GET /api/daemons/log?session=<scope>&before=<offset>` returns a page of complete lines read backwards from `before` (at most 256 KiB or 1000 lines, lines over 64 KiB as markers at their real offset, at most 16 MiB scanned) as `{scope, lines: [{offset, line}], start, end, more}`; only the current `<scope>.log` is served. `POST /api/daemon {"action":"start"|"stop", "scope"?}` answers 200 with the pool state; without a scope it starts or stops the pool (409 `{error}` for `start` while `daemon.enabled` is false or the `daemon.*` config has a problem), with one it starts or stops that session (400 for an invalid scope, 404 for an unknown job, 409 `start the daemon first` for a scoped start while the pool isn't wanted). `POST /api/requests` answers with the request plus `daemon: <pool wanted>`, and 400 for a `gate` request (only the CLI writes those), for a `run` without a valid `args.ref`, an `args.link` outside `approve` or not `new`, `none` or a ref, or an `args.n` outside `next` or 1..16. `POST /api/jobs {text, title?}` creates a job (title derived from the text unless given; 400 for missing, blank or over-20,000-character text or an empty title, 409 before `/forge init`), queues its `resume`, and answers `{id, title, branch, request, daemon}`. `POST /api/jobs/<id>/effort {"effort": "low" | "medium" | "high" | "xhigh" | "max" | null}` sets or (null) clears the job's effort through the same `setJobEffort` as `forge job effort`, and answers `{id, effort, previous, changed}`; it works while the pool is wanted, because `job.json` is outside the trust digest, and is 400 for any other body and 404 for an unknown id or `_inbox`. `POST /api/jobs/<id>/repos {"decision": "approve" | "reject", "repos": [names], "note"?: string | null}` decides a job's pending repo proposals through `decideRepoProposals` with the dashboard as actor, and answers `{id, decision, repos, added, pending, resumed}`; when nothing is left pending and the job sits on the RP1 park it sets the job running and queues a `resume` unless a live session holds it (`resumed`). It is 404 for an unknown id, 400 for any other body (a `repos` that isn't a non-empty list of repo names, or a note over 2,000 characters), and 409 when nothing is pending, when `repos` is not exactly the pending set, or when a clone check fails. `GET /api/jobs/<id>` includes the job's `requests` (every status, oldest first, the last 50) and `request`, its `request.md` without the title line (at most 2,000 characters), which opens the drawer's Thread, with `requestTruncated` true when it was cut (the Thread's **Show the whole request** then reads `request.md` through `GET /api/jobs/<id>/file`), and `requestFromTracker`, true only when the job's `created` event carries an issue with a ref (its `issues`, or a pre-v11 `source`; a job started from an issue), so a job linked later still shows `request` as the user's words.

**Terminal.** `forge daemon status` prints the dashboard and every session record from the runtime files (no server call). Each session has `{scope, job, pid, alive, sessionId, startedAt, lastTurnAt, logBytes, kept, agents}`: `agents` lists the sorted roles of the running agents of the job that session owns (read from the record's `sessionId` and the job's `job.json`), and `kept` is `"agents"` when one of them keeps it; both are `null` and `[]` when the session is not alive, is the inbox or the office, or owns no agents. The office sorts right after the inbox. `forge daemon log <job>|--inbox|--office [--lines N] [--follow]` prints a session log's tail as raw JSONL with every C0/C1 control character escaped, and `--follow` keeps printing new lines across rotations.

**Stopping and orphans.** Children are spawned `detached` with no shell, so each leads its own process group. A stop SIGTERMs the group and SIGKILLs it after 5 s. `forge dash` stops every session on SIGTERM/SIGINT before exiting, and an `exit` handler sends a synchronous SIGTERM to each as a last resort. `forge dash --stop` waits up to 12 s for the server, then reaps (`daemonReaped: true` when anything was). A pool being created also reaps. Each record (every `daemons/<scope>.json`, regular files with a valid scope name only) is proven on its own: if it names a live pid whose server is gone, the pid is signalled only after it is proven to be the recorded child: it is > 1 and not us or our group, it leads its own process group, `ps` reports a start time within 30 s of `startedAt`, its command line contains the recorded `claude` executable and `--session-id`/`--resume` followed by the recorded uuid. A live `serverPid` other than ours in any record means another dashboard owns the daemon, and a pool start refuses. None of this runs on Windows, so on native Windows a pool start is refused outright (`lastError` says why and links [SUPPORT.md](SUPPORT.md)), nothing is spawned, and the dashboard serves without the daemon; `forge dash` prints the refusal (`daemonRefused` under `--background`) and skips the `daemon.auth` question.

**Recorded framing** (claude 2.1.296, headless run in a scratch repo with the default `command` and `--plugin-dir` pointing at this checkout). The only line the daemon writes, `TURN_LINE`:
```json
{"type":"user","message":{"role":"user","content":[{"type":"text","text":"/forge requests"}]}}
```
followed by `\n`. Observed on stdout, one JSON object per line:
- `system`: `hook_started`, `hook_progress`, `hook_response`, `commands_changed`, `init` (at the start of every turn, carrying `session_id`, `agents` with the `forge:*` roles, `slash_commands` with `forge:forge`, `plugins` with this checkout as `forge@inline`, and `permissionMode`, the mode `daemon.command` passes), `task_started` / `task_updated` / `task_notification` around a subagent, `thinking_tokens`.
- `assistant`: content blocks `thinking`, `text`, `tool_use` (an `Agent` call with `subagent_type: "forge:builder"` ran the plugin's builder and returned a `tool_result`).
- `user`: `tool_result` blocks; a subagent's own messages carry `parent_tool_use_id`.
- `rate_limit_event`.
- `result`: one per turn (`subtype: "success"`, `is_error: false`, `num_turns`, `result`, `session_id`), the same `session_id` across turns of one process.

`/forge requests` is expanded headless as the plugin's skill: the session ran the skill's opening `forge doctor`, `forge sync`, `forge requests`. A second stdin turn in the same process produced a second `result` with the same `session_id`; closing stdin made the process exit 0; a new process with `--resume <id> --plugin-dir <checkout>` accepted a turn and remembered the first process's conversation. `--resume` of an unknown id prints one `{"type":"result","subtype":"error_during_execution","is_error":true,"num_turns":0,…}` line, `No conversation found with session ID: <id>` on stderr, and exits 1.

## Foreman

Unattended runs stop at every human gate. With `foreman.enabled` (off by default; docs/CONFIG.md "Foreman"), the office session decides the gates it is allowed to, through `forge:assistant` sub-agents, so a human is needed only where policy says so.

**Routing.** A move (Job model › Moves) that parks a job on `spec-approval`, `split-approval`, `escalation`, `rounds-exhausted`, `conflicts` or RP1's repo proposal park (a `human` wait whose reason starts `repo proposal:` while a proposal is pending, the derived class `repo-proposal`) (a new park, or a different gate) whose class is in `foreman.decides` enqueues one `gate` request `{job, args: {gate, reserved}, from: "forge"}`, unless one for that job and gate is pending or in progress. It does so whoever writes the park: `forge job set`, `forge job advance`'s repeated-failure park, the reconciler, and the syncs in `forge pr sync`, `forge sync` and `forge pr merge`. The policy lives in `lib/engine/pipeline/moves/foreman-gates.ts`; `lib/office/foreman.ts` keeps the session side. `forge pr sync` (never `forge pr merge`) does the same for a job waiting on `pr-review` with changes requested or unresolved threads from someone with write access (`OWNER`, `MEMBER` or `COLLABORATOR`; a stranger's comment alone never starts an unattended rework): `args.gate: "pr-feedback"` and `args.key: <head sha>`, once per head in any status, so a push re-arms it. Failing checks on such a job skip the office: sync records a foreman `rework` itself (`ciHead` on the event dedupes it per head), writes a fixed `feedback.md` with no check text in it, moves the job to `build` and queues a `resume`; a reserved match falls back to the gate. The **CI rework cap** (`pr.maxCiReworks`, 3) bounds it: counted from the event log (foreman `rework` events with a `ciHead` since a person's latest `human` event), never from `job.json`, so a session can't reset it; at the cap a red head starts nothing, the reason names at most 5 allowlisted check names, a `ci-rework-capped` event is logged once per head, and no `pr-feedback` gate is queued, so the foreman is refused there too. Any head counts, because only someone with write access can push a same-repo branch and fork PRs are never adopted; `forge job round` pulls that head into the worktree before the builder starts. `requestScope` sends every `gate` to `_office`; the dashboard (`POST /api/requests`) and `forge requests add` cannot create one. The pool spawns the office within the tick, writes it the fixed `/forge requests` turn, and treats it like the inbox for trust, `DENY_TOOLS`, budget holds and failures, never counting it against the cap.

**The turn** (`skills/forge/reference/foreman.md`). Claim, then `forge job assist <job> --gate <gate>`, which returns `{gate, stale, reserved, model, effort, subagent: "forge:assistant", brief}` and writes nothing. The office spawns one assistant with that brief, reads its single line `ASSIST: approve|revise|rework|escalate · <reason>` (anything else is `escalate`), records the verdict with `forge job human <job> <action> --actor foreman --note "<reason>"`, queues a `resume` for the job's own session, and acks; that session's next `forge job step` turns the decision into the gate's follow-up (["Job model"](#job-model) › Answered gates). On `escalate`, a reserved gate, or a decision the CLI refuses (not a stale one), it records a **Foreman hand-off** with `forge job handoff <job> --class escalated|reserved|refused --reason "<reason>"` (an office-only command whose gate is read from the job) and acks `rejected`, and the job keeps waiting for a human. `forge status`, `forge job show`, `/api/state` and the dashboard's Needs you card show the hand-off (`foremanHandoff`, derived from events) until a decision answers that park or the job parks again.

**Context rule.** The office session never reads a job file: the brief `forge job assist` returns carries absolute paths, the gate class and the reserved list, never file content, and the procedure names only `forge` calls. The assistant reads the files and writes `feedback.md` itself on `revise` or `rework`, so the office's log holds CLI JSON and one-line verdicts.

**Authority, enforced by the CLI.** `forge job human … --actor foreman` runs every check before any write, and a refusal (exit 1) leaves `job.json` and `events.jsonl` untouched. It is refused outside the `_office` scope; inside it, `job human` without `--actor foreman` is refused too. It needs a `--note`, takes no `--link` or `--reason`, and needs the job to be waiting on a class in `foreman.decides` (`pr-review` counts as `pr-feedback`) with an action of that class: `approve-spec`/`revise-spec`, `approve-split`/`revise-split`, `approve`/`revise-spec`/`rework` for escalation and rounds-exhausted, `approve` for conflicts, `rework` for pr-feedback, `approve-repos`/`reject-repos` for repo-proposal, with `--repo` naming the whole pending set (then `--state running` with no stage). It is refused when a `foreman.reserved` pattern matches the reason, the note, or (for escalation and rounds-exhausted) the `## Why` and `## For the human` sections of `decision.md`, or (for repo-proposal) a pending proposal's reason; a `decision.md` that isn't a small regular file counts as a match, and a security review whose latest recorded verdict is anything but `PASS` (`CHANGES`, `MALFORMED`) refuses every action that accepts the job, at any gate, while `rework` and the revise actions stay the foreman's (`SECURITY_MITIGATIONS`): security always has to pass, so the foreman may fix it but never approve past it. Step keeps reworking such a job past `maxRounds`, up to twice it, before B2 parks it on `rounds-exhausted`. Past the **total-round ceiling** (`pipeline.maxTotalRounds`, by default twice `maxRounds`), which counts every round whoever opened it, B7 parks the job there unless a person (a `human` event whose actor isn't the foreman) reworked or revised since the previous round started, and every foreman action at that park is refused, whatever the security verdict: no gate request is queued for it. A `rework` on pr-feedback also needs a pending or in-progress `gate` request keyed by the PR's current head sha, so the foreman acts only on feedback sync armed for that push. Patterns match case-insensitively as whole phrases (no letter or digit on either side) and are escaped literals, so matching is linear; a `reserved` that isn't a list of non-empty strings makes every gate reserved. In the office, `forge job set` only carries out a recorded decision: the job must still wait, its latest `human` event must be the foreman's and newer than the park, and the change must be that action's `--state running` with its stage from the gate table, with no `--field`, `--waiting-on` or `--reason`. Of the `forge job` subcommands only `assist`, `human`, `set`, `note`, `handoff`, `show`, `get`, `list` and `step` run there, and the office also may not `worktree create`, `job advance` or `pr merge`. The assistant has no Bash at all (`disallowedTools: Bash, Edit, NotebookEdit`), so text it reads reaches the CLI only through its one-line verdict.

**The release gate class** (lib/engine/release/approval.ts). No job waits on a release, so `release` is routed from the plan, not a park: `forge release plan --job <id>` logs `release-planned {planHash}` (the full sha256, unless the job's latest one already has it) and, when the foreman decides `release`, enqueues one `gate` request `{job, args: {gate: "release", key: <planHash>, reserved}}`, unless one for that job and key exists in any status, so a gate left for a human is never re-armed for the same plan. "Decides" means `foreman.enabled`, `release` in `foreman.decides`, and no `gate:release` in `foreman.reserved`, which the defaults keep: `decides()` drops every class reserved with `gate:<class>`, so reserved wins for every gate and caller, and a `gate:` entry naming no class makes `reservedMatch` fail closed. `forge job assist <job> --gate release` is `stale` unless release.json selects the job, its latest `release-planned` is release.json's hash and that hash has no approval; its brief names release.md, config.yml (`release`, `repos[].release`) and the job's request, spec and decision paths, plus `Release plan: <path> (plan <hash12>)`. `forge job human <job> approve-release --actor foreman --note "<reason>"` checks, before any write: the office scope; a note and no `--link`, `--reason` or `--repo`; the policy (each refusal names enabled, decides or `gate:release`); a readable release.json selecting this job; `freshPlan` recomputed from config and the clones matching it; the job's latest `release-planned` being that hash; a pending or in-progress `release` gate request keyed by it; no approval for it yet; and `reservedFor` over the job's reason and the note, which also refuses a latest security review that isn't PASS. It then logs one `release-approval {planHash, note, actor}` event and nothing else: no `human` event, no state change, and no `SET_AFTER` entry, so the office's `forge job set` stays refused. Without `--actor foreman` it is refused everywhere: a person approves at `forge release run`'s prompt. `forge release run` without a terminal passes a publish step only when the job has a foreman `release-approval` whose `planHash` is the plan it just recomputed, the foreman still decides `release`, and `reservedFor` over the job and the approval's note is null; the result carries `approvedBy: "foreman"`. A terminal always asks, a manual step still needs one, and the run itself stays refused in every daemon session, so a human or CI starts it.

**Release gate threat model.** The attackers are the office foreman or its assistant misled by text in release.md, the config or a tracker; a job or inbox session posing as the foreman; and a Bash-capable agent writing `events.jsonl`, `release.json` or the request inbox directly. The scope check and the reserved note and security checks stop the first two; a forged or reused request fails the key match against the recomputed plan; an edited or stale release.json fails `freshPlan`; an approval for another plan or by another actor is ignored at run time, and so is one left over after the owner takes the class back, because the policy is re-read every time. Residual risk: in a repo that delegated `release`, a process that can append to the job's `events.jsonl` can stand in for the foreman's approval of the current plan. It still can't change what runs (commands come from config and the recomputed plan), and no daemon session can start the run; in a repo that did not delegate, a forged approval does nothing.

**Ship policy.** `foreman.ship: merge` (with the foreman on) counts as `merge.auto: true` in the approver brief's `Merge: auto` line and in step rule PR4 only. The approver still judges `merge.autoWhen` and writes `Auto-merge eligible`, PR4 still requires `yes`, and `forge pr merge` still enforces CI; the foreman itself never merges. `propose` changes nothing.

**Audit.** Every new `human` event carries `actor: { login, source }` ("Audit trail" below); a foreman decision is `{ login: null, source: "foreman" }`, and an older event's `"foreman"` reads as that, its `"human"` or missing actor as `{ login: null, source: "unknown" }`. `isForemanActor` (lib/core/job/store.ts) is the one check protected paths, stats, retro and the office's `forge job set` use, and it accepts the legacy string too. `forge stats` counts only human reworks in `humanReworks` and adds `foremanDecisions` and `foremanReworks`. The dashboard labels foreman decisions in the drawer's timeline, shows each waiting job's `gateOwner` on its card, and shows the office in the status bar as the **Foreman**: an indicator always rendered first in the left cluster (toned by the office pill, or dashed while `foreman.enabled` is off) whose chat-sized popover holds the office's permission prompts and its session log, with Start/Stop, the permission mode and read-only model and effort facts. The Daemon popover leads with a Foreman row that opens it and lists the office among none of its session rows.

**Threat model.** Provenance is `FORGE_DAEMON_SCOPE`, unauthenticated as for the inbox: the checks stop a session misled by request, PR or tracker text (a job session passing a decision off as the foreman's, the assistant smuggling a reserved topic through its reason, a forged `gate` request with `reserved: null`, the office merging), not a hostile local process. A Bash-capable session can always run `FORGE_DAEMON= forge job human …`, which reads as a human outside the daemon and skips every foreman check: the CLI line guards a misled model, not a hostile one.

## Audit trail

Every human action records a best-effort `actor: { login, source }` on its event, so `events.jsonl` says who, not only which session. These events carry it, and only these: `human` (every `forge job human` action); `linked`, `unlinked` and `issue-link` (`forge job link`, and `--link` on `forge job human`); `budget-set` and `budget-ack`; `release-approval` (`{ planHash, note }`, always the foreman's, from `forge job human … approve-release --actor foreman`); `claimed` and `dependencies-overridden` of a `forge job claim --force`; `pr-merge-bypass` and the `pr-merged`, `pr-auto-merge` or `pr-merge-failed` of the same `forge pr merge --now`; `daemon-permission` and `daemon-mode` when the dashboard answers a job session's permission prompt or switches its mode (the daemon log lines `permission` and `permission-mode-set` carry the actor too, for every scope); `archived` (`{ trigger }`, the last event of an archived job's record; see "Retention"); and `config-set` (`{ key, previous, value, changed: true }`) in the repo-level `.forge/runtime/audit.jsonl` when `forge config set` or `POST /api/config` changes a value. Agent-driven events, a plain claim, a merge without `--now` (the approver's auto-merge) and the daemon's automatic permission deny carry none.

**Resolution** (`lib/integrations/github/actor.ts`) runs at most once per process, lazily, only on a path that writes one of those events, so a CLI call that writes none never spawns `gh` or `git`:

1. inside a daemon session (`FORGE_DAEMON=1`): the OS user running `forge dash`, source `dashboard`, because the session acts on requests a person queued from the dashboard; `FORGE_ACTOR` is ignored there
2. `FORGE_ACTOR`: source `env`
3. `gh api user --jq .login` (5 s timeout): source `gh`, cached in `.forge/runtime/actor.json` for 24 h per gh host (`GH_HOST`, else `github.com`); a failure is not cached
4. `git config user.email`: source `git`
5. the OS user name: source `os`
6. else `{ login: null, source: "unknown" }`

The dashboard's own routes (`/api/config`, `/api/daemon/permission`, `/api/daemon/mode`) record the OS user running `forge dash`, source `dashboard`. Every login is sanitised when it is resolved and again whenever it is read back, from the cache or an event: only `[A-Za-z0-9 ._@+-]`, single spaces, at most 100 characters; one that ends up empty falls through to the next source. Only a `gh` or `env` login is published: the PR body and the tracker comment name it inside a code span, so it can never mention anyone or carry markdown. A `dashboard`, `os` or `git` login is a local account name or a raw email address, so those surfaces print only the source (`Approved by a person (dashboard) on <date>`), as they do for `unknown`; the login stays in `events.jsonl` and the audit export. The escalation reason goes in a code span too, because the agent that wrote it read untrusted text.

**The actor is not authenticated.** Like request provenance below, it is whatever the environment says. Source `dashboard` means the action ran inside a dashboard session (or a dashboard route), not that a person clicked: an agent in a daemon job session that runs `forge job human` is stamped the same way. Beyond that, anyone who can set `FORGE_ACTOR`, log `gh` in as someone else or write `events.jsonl` can name anyone. It is a record for auditors, never a grant of authority: no check in Forge passes or fails on a login. The one distinction Forge enforces is foreman versus person, and that rests on the office's daemon scope, not on the actor.

**Export.** `forge job audit <id> [--json|--csv]` prints a job's rows in time order: every event with an actor, every gate transition (`gate:<waitingOn>` into a wait, `gate-cleared:<waitingOn>` out of one), `pr-opened` and `pr-merged` / `pr-auto-merge`, with the job's PR number and merge method. `forge audit --since <date> [--until <date>] [--csv]` merges every job's rows with the repo-level log for a period (docs/CLI.md "Audit trail"). The CSV guards against spreadsheet formula injection. A human-approved escalation is also named in the PR body (a `## Decision` section) and, once, in a tracker comment when `forge sync` first sees the merge.

## Retention

Retention (`lib/engine/ops/retention.ts` writes, `lib/core/job/archive.ts` reads) keeps `.forge/jobs/` and `.forge/runtime/` from only growing, with the CLI as the only writer. It is off until a human sets a `retention` key (docs/CONFIG.md "Retention"); `forge job archive` and `forge job prune` run it by hand.

**Archive format.** `.forge/archive/<id>.json` (versioned by `ARCHIVE_SCHEMA_VERSION`, 1) holds `{ archiveVersion, id, archivedAt, trigger: cli|prune|policy, job, events, summary }`: `job` is job.json as stored, `events` every event ending with the `archived` one (`{ trigger, actor }`), and `summary` is `{ title, kind, state, createdAt, finishedAt, rounds, pr, verdicts, usage, findings, bytesFreed }`, with `findings` read by `jobFindings` before the review files and build.md are deleted. The directory is created 0700 with a `.gitignore` of `*`.

**Eligibility**, checked inside the job's lock, each with a fixed reason: the state is `done` or `cancelled` (else `active (<stage>/<state>)`); not an eval job; no live lease (`leaseStatus`; `agent start` keeps a lease live for 2 h); no live `pid` or `serverPid` in the job's daemon session record; no open PR; no worktree on disk; not named in an unfinished job's `dependsOn` or `children`; and a readable job dir (a real directory, a job.json this Forge can read). A refusal writes nothing.

**Order of writes.** Inside the lock: re-check, measure the dir, read the findings, log the `archived` event, write the record (a fresh exclusive temp file renamed over the target), delete the job dir, then append a `retention.log` line. The record lands before the delete, so a crash leaves both copies; every reader prefers the live job and ignores the record.

**Readers.** `listJobs` never sees archived jobs, so the board, `forge status`, `forge job list` and `/api/state` don't either. `computeStats` merges live jobs and records (events and findings from the record), so stats are unchanged by archiving except `counts.archived`; `forge audit` and `forge job audit` read records' events; `forge retro due` counts archived jobs; and `unmetDependencies` reads an archived dependency's state. `validateDependsOn` still rejects an archived id for a new dependency.

**Logs.** Prune and `retention.logsDays` delete only regular files named exactly `<scope>.log` or `<scope>.log.1` for a valid scope, whose newest mtime is old enough, whose record names no live process, and whose scope is not an active live job; a job scope with no job dir left also loses its `<scope>.json`. Every archived job and deleted log appends `{ ts, type: "pruned", kind, … , trigger, bytes }` to `.forge/runtime/retention.log`, opened without following links or blocking on a FIFO. `forge doctor`'s `storage` check sizes `.forge/jobs`, `.forge/archive` and `.forge/runtime` with lstat and warns past 500 MiB.

**Threat model.** The attackers are a hostile checkout or another process planting symlinks or FIFOs in `.forge/jobs`, `.forge/archive` or `.forge/runtime/daemons`; a job id on the command line; and a misled daemon session (the inbox and job sessions read tracker text) running `forge job prune --older-than 0` to wipe evidence. Ids go through the job-id regex and scopes through `validScope` before any path is built; a symlinked job dir or archive dir is refused, and a link planted at the record's path is replaced by the rename, never followed; log deletion checks each file with lstat; ownership and session liveness are checked inside the lock; both commands exit 1 in any daemon session (the office refuses them through its allowlist), while the human's policy still runs from `forge sync` there; `.log.1` reads use the server's confinement; and `retention.jobsDays`/`logsDays` are locked in the dashboard, so its token alone can't delete files. What an auditor needs survives a prune: the `archived` event and the audit rows in the record, and `retention.log`.

## Deleting a job

`forge job delete <id> [--force]` (`lib/engine/ops/delete.ts`) and the drawer's **Delete job** card (`POST /api/jobs/:id/delete`) remove a job started by mistake, for good. Unlike archiving, nothing is kept: no archive record, so `forge stats`, audit and retro never count it; one `{ type: "deleted", kind: "job", id, title, trigger: cli|dashboard, actor }` line in `.forge/runtime/retention.log` records who deleted what.

**Refused**, with nothing changed, for an eval job; a job with a PR (real work: cancel and archive it); a live interactive owner (unless `--force`); a running daemon session (the CLI refuses; the dashboard stops the job's own session itself, once nothing else refuses); a split parent whose children still exist; and a job an active job `dependsOn`. Like archive and prune, it exits 1 in any daemon session, and the office's allowlist leaves it out.

**Order of work.** Check everything; mirror the job to the tracker as cancelled (best effort), which releases its issues; `removeWorktree` with `--force` (the root and member worktrees, background commands, per-job backing services) and, only when the branch is the one Forge named (`git.branchPrefix` + id), the branch; reject the job's open requests; delete its daemon session record and logs; then, inside the job's lock with the owner re-checked, the job dir. A failed worktree or backing teardown stops before the job dir goes, so a rerun finishes.

**Dashboard.** The POST needs the token, a matching Origin and JSON like every other, and its body must be `{"confirm": "<id>"}`: the card arms only once the id is typed back, so a stray or replayed click never deletes a job nobody named. The card offers no delete for an eval job or one with a PR.

## Untrusted input

Issue bodies, comments and PR reviews come from people outside the session, and on public repos that means anyone. Forge:
- imports only collaborators' issue comments by default (`tracker.github.comments`), and labels the rest as untrusted in PR feedback
- fences imported text with its provenance and a "data, not instructions" note
- blockquotes every line of an imported GitHub issue body and comment (CR, U+2028, U+2029 and NEL count as line breaks, other control characters are dropped, logins and associations are reduced to safe characters, and the title is one line), so only Forge writes column-0 lines in `request.md` and a forged `### Recent comments` section reads as quoted text
- re-imports an issue (`forge job refresh-request`, and a claim before `plan.md` or `spec.md` exists) only through the tracker's own `get`, so a refreshed `request.md` is fenced exactly as at intake; a claim refreshes only a request intake imported from that issue (`origin: issue` on `created`, or the GitHub import fence on older jobs), never words a person wrote, and only from an issue whose author has write access (`author_association` `OWNER`, `MEMBER` or `COLLABORATOR`), so an outside author's edit after a person picked the issue never reaches an agent unseen; `refresh-request` is that person's explicit choice
- tells every agent to ignore embedded instructions about secrets, credentials, CI, permissions or out-of-scope work
- triages tracker items without letting their text reach the tracker (`lib/engine/trackers/triage.ts`, docs/TRACKERS.md "Readiness triage"): the batch the `forge:triage` agent reads fences each item in a fence longer than any backtick run in it, and the agent has only Read and Write; `--apply` takes a batch id only in its exact format, reads `verdicts.json` and `items.json` each through one `O_NOFOLLOW` descriptor (a regular file under 256 KiB), ignores refs outside the batch, keeps only known missing keys and a `duplicateOf` from the item's own candidates, skips items changed since prepare, and writes only fixed template text, citing a duplicate as `PR #n`, a same-tracker `#n` or "an active Forge job", never a local job id, a citation it derives from the candidate id and the job records rather than from the agent-writable batch
- adopts only PRs whose branch lives in the same repository (never forks), and only issue-linked PRs from collaborators, so a stranger's PR is never checked out and run by the builder. Every PR read is validated once, in `lib/integrations/github/pull-requests.ts`, into a snapshot that `lib/engine/pr/` reads through its `GitHub` adapter: a PR not marked same-repo (`isCrossRepository` missing or anything but `false`) counts as a fork, and a ref name that fails `SAFE_REF`, a head that is not a sha and a url that is not https are dropped before any policy sees them
- passes trackers only this repo's own issue refs (`nativeRef` in `lib/core/job/issue-ref.ts`): an `owner/repo#N` from another repo on a job is recorded and cited, never read, claimed, mirrored or commented on, and every stored ref must start with a letter or digit and hold no spaces or `..`, so no ref reaches `gh` as an option; job.json's `issues`, `source` and `noIssue` are locked against `forge job set --field`
- keeps job ids, branches and bases to `SAFE_REF` (`lib/core/text.ts`: a letter or digit, then `A-Z a-z 0-9 . _ / -`, at most 200 characters), because they fill `{job}`, `{branch}` and `{base}` in shell command templates and reach git argv: command templates (`forge run`, `forge verify`, worktree setup) and `forge worktree create` refuse an unsafe value before anything runs, `forge job new --branch` refuses one before the job exists, and PR adoption refuses a PR whose `headRefName` or `baseRefName` fails it (a `pr-adopt-refused` event names the field, never the value). `forge job set --field` can't write a job's identity (`id`, `branch`, `base`, `worktree`, `port`, `owner`, `schemaVersion`, `createdAt`, `source`, `pr`, `runs`, `usage`, or any key under them), its `effort` (only `forge job effort` writes it, and refuses in a daemon session), its `eval` record and config overlay (only `forge eval start` writes it, and refuses `--set` in a daemon session; every load checks the overlay again and fails closed), a `kind` of `retro` or `eval` (only `forge job new --kind retro` and `forge eval start` create those, because step gives a retro job a fixed review panel and an eval job no PR or escalation gate) or any `__proto__`, `constructor` or `prototype` segment, so a misled session can't point a job at `main` before `forge pr open`. `setJob` enforces these rules through `lib/core/job/fields.ts` for every caller, not only the CLI, and the commands that own those keys write them through its `owned` change instead. The extra arguments of `forge run <job> <name> -- <args…>` reach the shell too: each is wrapped in single quotes and never filled again as a placeholder, and an argument containing a quote, backslash or control character (which would end the quoting in sh, bash, zsh or fish), a word before `--`, or any argument with `--background` is refused before anything runs. Arguments are opt-in: a template without `{args}` refuses them, so a configured command that reaches outside systems can't be steered with flags a session picks. Arguments are also refused where the template would not keep them as plain words: an `{args}` that isn't a whole unquoted word (inside `'…'` or `"…"`, where `$(…)` expands or a `'` ends the quoting, or after a backslash), or any template with a heredoc, `$'` or `\'`, where `\'` does not close the quote. `forge verify`, worktree setup, background servers, the regenerate build and eval grading have no argument path at all, so arguments can never narrow the gate
- confines config sinks (`lib/engine/environment/config-sinks-apply.ts`, docs/CONFIG.md "Config sinks") to the job's own worktree: a forged `job.worktree` is refused, every output path must be git-ignored and untracked so job values never reach a commit, a symlink at an output path is replaced rather than followed (the write goes through a randomly named temp file opened exclusively, so a planted entry at a guessed name fails instead of redirecting it), a parent directory or a `from` file that resolves outside the worktree is refused, as is a `from` that is a symlink or a hard link and a hard-linked output path that a merge with no `from` would read as its base, and no rendered value reaches a result, an event, an error or a log header. Residual risk: the confinement checks and the write or read are separate syscalls (Node has no directory handle with `openat`/`O_NOFOLLOW`), so a same-user process that swaps a parent directory or `from` for a symlink in between wins the race; the worktree and the job's own session are already that user
- refuses to publish a likely credential, in its own code rather than a prompt (`lib/engine/guard/secrets.ts`, docs/CONFIG.md "Secret scanning"): verify scans every commit of the branch, its messages and the staged changes before any configured step, and `forge git commit`, `forge pr open` and every tracker adapter's writes refuse a likely secret (`secret_found`) before git, `gh` or the adapter is called. Findings are masked and fingerprinted, never printed. The allowlist (`.forge/secrets-allow.txt`) is read from the main checkout only, and the mode from the main checkout's config, so a branch can neither allowlist its own leak nor turn the gate off; diffs run with the same pinned git config and `--text --no-ext-diff --no-textconv` as the integrity report, so attributes and drivers can't hide added lines. A refusal parks the job on `waitingOn: human`, and no agent retry gets past it
- resolves secret references (`lib/engine/guard/secret-refs.ts`, `lib/engine/guard/known-secrets.ts`, docs/CONFIG.md "Secret references") only when a config sink renders `{secret.NAME}`, from declarations in the main checkout's `.forge/config.yml` alone, which protected paths keep human-only. The attackers are the builder (it writes the worktree, template `from` files, `.gitignore`, the job dir and agent outputs, and runs `forge`), a hostile checkout, and tracker or PR text. Keychain fields and op references are validated (no leading `-`, a fixed charset) and go in argv with no shell; a `file` source must be a regular, git-ignored, untracked file inside the repo, never a symlink or hard link; a value under 8 characters is refused because it can't be redacted reliably. Every resolved value is recorded in the job's 0600 `known-secrets.json` before any write or command sink, and Forge replaces known values (raw and JSON-escaped) with `[redacted]` in every log, tail, event, session log line, dashboard response and support bundle it writes or serves; `known-secrets.json` and `backing-db.json` are never served or bundled. The secret scanner's `known-secret` kind blocks a known value on the branch or in PR text in either `verifySecrets` mode, and the allowlist can't allow it, so a `.gitignore` edited around a rendered file and a `git add -f` still can't publish it. A job's commands receive the values by design: Forge guarantees a value never lands verbatim in what it persists, serves, briefs or publishes, not that code the builder writes can't encode or split one, so users declare only development credentials. Residual risk: an agent can delete or rewrite `known-secrets.json`, which weakens serve-time redaction of files a child process wrote itself (background logs, transcripts); every render rewrites the record, and write-time redaction uses the values the rendering process holds in memory, so logs, tails and verify reports Forge writes stay clean
- treats the job's own diff as hostile when a small model reads it ([docs/VERIFIERS.md](VERIFIERS.md)): verifiers are read from the main checkout only (`.forge/verifiers/`, like `config.yml`), so a branch can't add or weaken one; `forge verifiers run` reads the verified commit's diff with the integrity report's pinned git config, `--no-renames` and replace objects ignored, and writes it into fences longer than any backtick run inside, after CR, U+2028, U+2029 and NEL became line feeds, with paths only JSON-encoded; the verifier agent's brief carries paths and a count, never diff or verifier text; and `forge verifiers record` parses answers fail-closed (a missing, symlinked, oversized, fenced or unparseable answer counts as no answer, which fails a block verifier), re-derives selection, mode and severity from the main checkout rather than the job dir, and forces every reason onto one line so it can't forge a finding
- enforces `policy.protectedPaths` (`lib/engine/guard/protected.ts`, docs/CONFIG.md "Protected paths") in code, against a builder or integrator fooled by that text: `forge git add|commit` preview the index the call would produce and refuse a `refuse` path before anything is written, and verify and `forge pr open` re-check the whole branch from the merge-base, so a plain `git commit` gets no further. Renames are checked on both sides, symlinks and submodules by their target and by the directory they stand in for, and paths case-insensitively; every diff pins external diff, textconv, relative paths and renames off and ignores replace objects and grafts. The policy is read from the main checkout only and `.forge/config.yml` is itself a refuse default, so a branch can't loosen it. Escalate paths park the job on a human (PP1, even after `APPROVE`, never auto-merged), and only a human approve given at that park after the paths' current content was recorded counts: not the foreman, not an approve at another gate. `pr open` recomputes the set rather than trusting `job.protectedPaths`, which `forge job set` can't write, and the PP1 reason prints only shell-safe paths. `pr open` pushes the exact commit it checked (`<sha>:refs/heads/<branch>`, or that commit with its messages scrubbed), never whatever HEAD has become by then, and records it as `pr.pushedSha`. `forge pr merge` refuses a PR head other than that one, unless a human passes `--now`, and while the policy has rules it never queues GitHub auto-merge: whether GitHub still holds `--match-head-commit` when a queued merge lands is not documented, so it defers while checks are pending and `forge sync` surfaces the retry. Residual risk: the gate binds an agent that changes the job through Forge's commands, not one that writes Forge's own files. `pr open` recomputes the paths, but the approval rests on `at` in `job.json` and on `events.jsonl`, and neither is integrity-protected, so a hand-edited flag (new blobs, an old `at`) carries an old approval over to new content, and an appended `human` approve counts. Any session other than the office can also park the job itself (`forge job set --state waiting --waiting-on human --reason 'protected paths: …'`) and then record `forge job human <id> approve`. Binding approvals to a tamper-evident audit trail is left to a follow-up
- sends notifications without that text (`lib/office/notify.ts`, docs/CONFIG.md "Notifications"): the webhook and command set is trusted config (`.forge/config.yml`, read-only in Settings and `forge config set`, a protected path, and in the daemon's trust digest), and the payload has a fixed key set whose `reason` is a fixed English string chosen by code. The only free text is the job title, control-stripped and capped at 200 characters; in Slack it sits only in `plain_text` (no mentions or links) and is escaped in the fallback, and the command receives every value through `FORGE_NOTIFY_*` environment variables its `{placeholders}` reference, never interpolated into the shell source. Webhooks refuse redirects, and only a webhook's host is recorded, shown in doctor or sent to the dashboard (`/api/config` masks the path). An agent that runs `forge notify send` or `forge notify test` itself reaches only the targets a human configured, with the same fixed payload
- limits what an agent fooled by that text can do when nobody is watching: the daemon's default `allowedTools` names only the git/gh subcommands the agents use (no `git -c`, `git rebase --exec`, `git config`, `git log --output` or `gh api`), validation refuses blanket git/gh entries and permission-widening `daemon.command` flags, and the session runs git with hooks and fsmonitor pinned off ("Daemon security" below)
- runs backing services without letting a session steer Docker (`lib/engine/environment/backing.ts`, docs/CONFIG.md "Backing services"): config is read from the main checkout only, and validation keeps every image, name and volume path to a fixed charset with no leading `-`, so nothing reaches `docker` as an option; every call is argv only; env values go through a 0600 `--env-file` in a fresh temp directory that is removed afterwards, and errors carry only the subcommand and a stderr tail, so a value never reaches argv, `ps`, events or results; ports bind to `127.0.0.1` only; and teardown derives container and volume names from the job id and config, never from the agent-writable `backing.json`, and removes only what is labelled with this checkout's root hash and job, so a forged record or a same-named container of another checkout is never touched. A forged record can at most reserve ports in range (wasting them) or name ports that are ignored and allocated again
- gives each job its own database on a shared Postgres without letting a session reach another job's data (`lib/engine/environment/backing-db.ts`, docs/CONFIG.md "Job databases"): every database and role name is derived from the job id or the template hash, checked against `^[a-z_][a-z0-9_]{0,62}$` and double-quoted, and every SQL statement goes to `psql` on stdin, never in argv; Postgres receives only a SCRAM-SHA-256 verifier, so a password never reaches argv, `ps`, the server log or `pg_authid`; the job's password lives only in the 0600 `backing-db.json` and the env of the job's configured commands, and the setup and template-build tails Forge stores are redacted; that record is agent-writable, so it is read without following a symlink, a field that fails its regex is ignored, and teardown drops only the names derived from the job id; each job role has its own login, `CONNECT` on its database is revoked from everyone else, no job role is a member of the `forge_tpl` role that owns a template while it builds (a clone's objects are reassigned to the job's role instead), `CONNECT` on a template is revoked from everyone else from its creation, and a built template belongs to the superuser and takes no connections, so a job cannot reach another job's database or alter the template, mid-build or after; and template build commands run only in the worktree path Forge computes for the job, never `job.worktree`. The residual risk: migrate and seed run code from the building job's worktree, and a file they read outside `inputs` can shape a template later jobs with the same hash reuse
- treats `forge release`'s runtime files as data (`lib/engine/release/run.ts`, docs/RELEASES.md "Releasing a project"): `release.json` and `state.json` in `.forge/runtime/release/` are writable by any session, so `forge release run` recomputes the plan from the main checkout's config and the clones and refuses when either file's hash differs, takes every command and check from that recomputation, runs each step's check before the step so an edited state can't publish twice, asks before every publish step without a terminal override (`release.publish: allow` is a hand edit of config; the question stops accidental publishes from agent sessions, not a determined one that fakes a terminal), refuses a symlinked release dir or file, and is refused in a daemon session. Without a terminal, the one stand-in for the question is a foreman `release-approval` for the recomputed plan's hash in a repo that delegated the `release` gate class ("Foreman" above); a process that can append to the job's `events.jsonl` can forge one there, though not change what runs, and in a repo that did not delegate a forged approval does nothing
- treats `forge release`'s runtime files as data (`lib/engine/release/run.ts`, docs/RELEASES.md "Releasing a project"): `release.json` and `state.json` in `.forge/runtime/release/` are writable by any session, so `forge release run` recomputes the plan from the main checkout's config and the clones and refuses when either file's hash differs, takes every command and check from that recomputation, runs each step's check before the step so an edited state can't publish twice, asks before every publish step without a terminal override (`release.publish: allow` is a hand edit of config; the question stops accidental publishes from agent sessions, not a determined one that fakes a terminal), refuses a symlinked release dir or file, and is refused in a daemon session
- treats the release records in `events.jsonl` as data (`lib/engine/release/interim.ts`, `lib/engine/release/interim-apply.ts`, docs/CONFIG.md "Interim strategies"): only the human-only `forge job interim release` and a `--job` `forge release run` write `interim-released` (both refuse in a daemon session), and the run takes the version only from checks it ran itself, never from `state.json`. Every reader validates `interim-released` and `interim-bumped` (repo keys, a semver version of at most 120 characters that names no canary), so `-Zunstable` or `1.2.0 && x` is ignored; the release bump refuses a record whose dependency's recorded PR is not MERGED, writes manifests through `writeManifest` and never through a symlinked manifest or lockfile, runs the lockfile refresh with a fixed argv and no shell (`lockfileArgv` refuses a name or version that starts with `-`; npm always gets `--ignore-scripts`), puts every file back when the refresh fails or touches another path, and commits with `--no-verify --only -m`, so no hook, template or trailer config adds attribution. A forged `interim-bumped` only flips the pure gate: `forge pr open` (`interim_stale`) and `forge pr ready` (`release_gate`) read the consumer's manifests from git and refuse one that doesn't name the release. Accepted residuals: a forged, well-formed `interim-released` for a merged dependency bumps the consumer to a version that exists (the posture a local or sequential record already has); a planted tag satisfies the cmake tag check; and cargo and npm read builder-writable project config during the refresh, as verify's own commands do. No publish or release command ever runs from the bump.

**One wrapper per tool.** Every git, gh and docker process in `lib/` starts in one module, so no call site can forget a pin, a clean environment or a timeout. `lib/integrations/git/runner.ts` prepends `-c core.fsmonitor=false -c core.quotepath=off -c diff.interHunkContext=0 -c diff.suppressBlankEmpty=false -c diff.relative=false` to every call: the worktree's config can't run an fsmonitor program or reshape output a parser reads, and the diff pins are git's defaults, so they only override a user's or a worktree's config. Without a caller's own `env`, each call drops the inherited `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY` and `GIT_NAMESPACE` (Forge run from a git hook would otherwise act on another repo), and a read runs with `GIT_OPTIONAL_LOCKS=0`, so it never locks the index of a worktree whose builder is running git at the same moment. Call-specific options stay at their call sites (`core.hooksPath` on member git, `--no-ext-diff`, `--no-textconv`). `lib/integrations/github/gh.ts` gives every gh call a 60 s timeout unless the call sets a shorter one (the actor lookup and the release check 5 s, the link preview 15 s), so a hung gh can't block `pr sync` or a tracker call, and parses JSON output in one place. `lib/integrations/docker/runner.ts` holds the sync runner `lib/engine/environment/backing.ts` uses, an async runner and the streaming spawn behind the dashboard's container logs; Docker's state travels as `docker` in `forge backing status <job>` and as the error codes `docker_missing` and `docker_stopped`, never as message text. The release scripts share the git pins through `scripts/git.ts`.

**Request provenance is not authenticated.** A request's `from` (`dashboard`, `cli`, `daemon:<scope>`) and the daemon-session checks in `forge requests` come from the caller's environment (`FORGE_DAEMON`, `FORGE_DAEMON_SCOPE`), which a session's own commands could drop. They are guardrails that keep a session following the skill from acting on another job's requests or queuing anything but a `resume` hand-off, not a boundary against a misled session: such a session can already run `forge job human …` or `forge job budget --ack` directly through `Bash(forge:*)`. The defences against that are the ones above: what reaches agents is fenced as data, and the unattended session's tools are narrow.

## Authorship policy

`lib/engine/guard/attribution.ts` defines what counts as AI attribution: signature lines and trailers, not mentions. It is shared by the Bash `PreToolUse` hook (`hooks/no-ai-attribution.ts`, which blocks before anything is written), by `forge pr open` (which rewrites the messages of the commits it checked from their raw objects, keeping every tree, author and committer, moves the branch only if it still points at the checked commit, then pushes that exact commit with `--force-with-lease` if anything changed), and by the GitHub tracker (which strips issue and comment bodies). On Node older than 22.18 the hook cannot load and exits 1, which Claude Code does not treat as a block, so the policy is not enforced there. The policy is on by default (`aiAttribution: forbid`).

## Review policy

Reviewers tag findings `[blocker] [major] [minor] [nit]`. The CLI decides the verdict from the tags and the repo's `review.blockOn`, not from the reviewer's own first line. This keeps the threshold consistent across lenses and models: "CHANGES over a nit" or "PASS over a blocker" can't slip through. A review without a verdict line is `CHANGES` when its tags already force a round, otherwise `MALFORMED` and re-run once; a second malformed review is counted as `CHANGES` (`--malformed changes`) so a reviewer that cannot follow the format cannot stall the job. A lens with no file is `PENDING` while its reviewer (`reviewer:<lens>` in `job.agents`) has not ended for that review, and `MISSING`, with the expected path, once it has: an agent can claim a review it never wrote, so the orchestrator re-spawns it rather than waiting. `forge job round` and `forge job paths` create the review directory before any reviewer is briefed.

**Model diversity.** A gate that runs on the same model as the builder tends to share its blind spots: it finds the code plausible for the same reasons the builder wrote it. `forge roster` therefore always reports which gatekeepers (the approver, then each panel lens) share the builder's model family. The family is `opus`, `sonnet`, `haiku` or `fable` when the model string names one, else the whole string, with `inherit` resolved through the orchestrator's model. With `runtime.diversity: true`, `forge roster` and `forge init write` turn each overlap into a warning. It never blocks a job: picking models is the human's call. The Balanced init preset already puts the approver on a different family.

## Repo budget

Per-job budgets stop one job; `budget:` (docs/CONFIG.md "Repo budget") caps the repo's spend per UTC day and month. `lib/engine/metrics/spend.ts` sums every `agent-end` usage across live jobs and `.forge/archive/` records, re-priced with today's table, into buckets by UTC day, role and model. `.forge/runtime/spend.json` caches each job's buckets keyed by its events file's size and mtime (an archive record's by `lstat`), plus the cache version and a hash of the price table. It is read through one `O_NOFOLLOW | O_NONBLOCK` descriptor and rebuilt on any mismatch, so a planted symlink or a stale or understated cache is never trusted; `/api/state` and the daemon pool compute the status with `write: false`, so neither writes it. `lib/engine/metrics/repo-budget.ts` turns the ledger into `RepoBudgetStatus` and enforces it in the CLI only, at every place a job starts: `forge job new` (parks the new job), `forge job claim` (parks it and exits 4, unless an agent is running, another live session owns it, or it already waits), `forge next` (starts nothing) and `forge job from-ref` (exits 4). Repo holds reuse `waiting: budget` with a `repo budget:` reason, so the budget notifications fire unchanged. Release (back to `queued`, plus a `resume` when the daemon is on) re-checks the job's own per-job budget, so a session that rewrites its per-job stop's reason to `repo budget:` stays held. A human acknowledges a period with `forge budget ack` or `POST /api/budget/ack`; the ack is a `repo-budget-ack` line in `.forge/runtime/audit.jsonl`, and the effective cap is `cap × (1 + acks)`. Both that command and `forge job new --force` refuse under `FORGE_DAEMON=1`, and `DENY_TOOLS` covers the cache and the audit log.

Residual risk: a session with shell write access could still append a fake `repo-budget-ack` line or forge a fingerprint-matching cache, the same trust level as `forge job budget --ack` ("Request provenance is not authenticated"). A job claimed before the cap trips runs until its next claim, bounded by its per-job budget.

## Usage accounting

The orchestrator records every agent start and end. With Claude Code, `--import` reads the subagent transcript (`<session>/subagents/agent-<id>.jsonl` under `$CLAUDE_CONFIG_DIR/projects`, else `~/.claude/projects`). It looks first under the job's own sessions (the owner's, then the last five in `runs[]`) in this repo's project dirs, and falls back to scanning every project dir for an agent whose parent session isn't recorded. The orchestrator records a background agent's id as soon as it is spawned (`forge job agent <id> attach`), so the dashboard can follow that transcript while the agent runs. Input and cache tokens come out exact, along with tool calls (by unique block id) and duration. Output tokens are estimated from the logged content, because transcripts store the stream's opening usage snapshot. A resumed agent (SendMessage, as the builder is for rework) appends to the same transcript, so each agent record keeps `importedThrough`, the last transcript timestamp imported per agent id, and the next import of that agent counts and times only the lines after it. Without a transcript, the runtime-reported total is used with a blend assumption, and the dashboard shows coverage (how many agent runs reported usage, and how many exactly). Prices live in `lib/integrations/claude/pricing.json` (dated, overridable via `usage.pricing`). For subscription plans they're API-equivalent figures, not a bill.

## Dashboard security

The server binds 127.0.0.1 only and answers only requests whose Host is a loopback name, which defeats DNS rebinding. GETs are read-only. POSTs (enqueue a request, create a job from free text, start or stop the daemon, answer a session's permission prompt, switch a session's permission mode, change a setting, set a job's effort, decide a job's repo proposals, acknowledge the repo budget, set or clear focus, start a job's dev server, start, stop or restart a job's dev server or backing services, open a job's worktree in an editor: `/api/requests`, `/api/jobs`, `/api/daemon`, `/api/daemon/permission`, `/api/daemon/mode`, `/api/config`, `/api/jobs/:id/effort`, `/api/jobs/:id/repos`, `/api/budget/ack`, `/api/focus`, `/api/jobs/:id/run`, `/api/jobs/:id/environment`, `/api/jobs/:id/editor`) need a random per-process token embedded in the served page, a matching Origin and a JSON content type, so other sites in your browser can't trigger work. The guards live in `lib/server/http.ts`, and the route table in `lib/server/start.ts` names each route's guards: dispatch runs the POST guard on every POST route, before its own guards and its handler. A `resume` for a job whose lease another driver holds live is refused with 409 naming the session, whatever its `args`, and nothing is queued, unless the driver is any id the job's own pool session has had and that session's child runs (asked of the pool session whose scope is that job, never `ps`), which the resume reaches and which reclaims as itself (`ownerStatus.jobSession`). A session that writes another pool session's id as its job's driver gains nothing: only the facts of the job's own session count, and that session's claim decides inside the job lock. The check runs after the token, Origin and JSON guards and only for a syntactically valid id with a `job.json`; it is advisory, because the job session's own claim inside the job lock still decides. Focus is a pointer in `.forge/runtime/focus.json`, read through one non-blocking `O_NOFOLLOW` descriptor with a 64 KiB cap and honoured only for a valid job id with a `job.json`, so a planted symlink, FIFO or forged record reads as no focus; setting it starts, stops and signals no background process, and only starts the focused job's own backing services (ensure up, docs/CONFIG.md "Backing services"), whose names come from the validated id and config. Moving it may run the configured `checkout` steps (docs/CONFIG.md "Checkout steps"), which run configured commands and write symlinks at the configured fixed paths, linking only to a source whose realpath stays inside the job's own `<worktrees.root>/<id>` and running a command (or its undo) only when that job has its own contained worktree, as Run does; containment is checked when focus moves, not continuously, so a link's source swapped for a symlink out of the worktree afterwards is followed until the next switch; their record, `.forge/runtime/checkout.json`, is read the same no-follow way and only steers undo for targets and command pairs the current config names, so a POST to `/api/focus` (behind the same token, Origin and JSON guard) runs nothing the main checkout's config does not. `POST /api/jobs/:id/run` accepts only `{"command": "dev"}` and runs the configured `commands.dev` through `startBackground`, which reuses a live server rather than starting a second. `POST /api/jobs/:id/editor` runs `FORGE_EDITOR` (the human's own environment, trusted like `$EDITOR`; default `code`) split into argv with no shell, plus one argument: the job's worktree, and only when the stored value is itself `<worktrees.root>/<id>` (as configured or resolved, so `<own worktree>/x/..` is refused) and its realpath is a directory equal to the realpath of `<worktrees.root>` joined with the job id, so another job's worktree, an arbitrary directory, a symlink out or a value starting with `-` is a 409 and nothing is spawned; Run takes the same containment check, since job.json's `worktree` is agent-writable. The Environment card's routes treat the job dir (which the job's agents can write: `runtime.json`, `job.json`'s `worktree`, `logs/`) as hostile. `POST /api/jobs/:id/environment` takes only `{"target": "dev"|"backing", "action": "start"|"stop"|"restart"}` (400 otherwise); every action needs the job's own contained worktree as Run does, and start and restart an active job, else 409 with nothing spawned or signalled. Stop signals the dev server only after `ownDevProcess` proves the pid in `runtime.json` is the one Forge started for this job: an integer above 1 that is not the server's own, leading its own process group (and not the server's) with no controlling terminal (a shell the human opened in the worktree, and what it runs, keeps one), started within 30 s of the recorded `startedAt` (`ps -o pgid= -o tty= -o lstart=`), with its working directory inside the job's worktree (`/proc/<pid>/cwd` on Linux, `lsof -a -p <pid> -d cwd -Fn` on macOS; argv only). Anything unproven, and every pid on Windows, is a 409 that points at `forge stop`. A proven stop sends SIGTERM to the group, SIGKILL after 5 s, under the runtime lock, removes only the `dev` key and logs `background-stop` with `actor.source: dashboard`. Backing actions run `forge environment up <id>` (start) and `forge backing stop <id>` (stop, after which the server marks the job `stopped` in the environment record) as an async CLI child (`lib/engine/environment/status.ts` `forgeJson`, output capped, killed on timeout), because `lib/engine/environment/backing.ts` runs Docker synchronously and would freeze every request; `backing stop` stops only per-job containers whose labels name this checkout and job, keeping volumes, records and shared containers. `GET /api/jobs/:id/environment` and `GET /api/environments` need the token header, refuse a foreign Origin or a cross-site `Sec-Fetch-Site`, and are memoized (2 s per job, 5 s with one shared computation) because each read may spawn the CLI, `docker stats` and `ps`; container names reach `docker stats` only from the label-filtered listing and after a name regex. `GET /api/jobs/:id/environment/logs?source=dev|backing:<name>` takes the token as a constant-time-compared query parameter, as the transcript stream does, and counts toward the event-stream cap. The dev log is always `<jobDir>/logs/dev.log` (never `runtime.json`'s `log` field), confined to the real job dir and read through one non-blocking `O_NOFOLLOW` descriptor, so a symlink or FIFO is a 404; a container name is derived from config and the job id (the `<name>` must be a managed entry), checked against Docker's name charset, required to read `running` or `stopped` with this job's labels in `backing status` (else 409), and passed after `--` to `docker logs --follow --tail 200`, whose child is killed when the client leaves; a client that leaves while that status check runs gets no slot and no child, and a recycled container stream ends with `event: end` rather than reconnecting and replaying its last lines. `forge dash --dev` (what `npm run dev` runs) changes only where the page and assets come from: the fixed `node_modules/.cache/forge/dashboard-dev/` inside the plugin root, which is exactly as trusted as `dashboard/dist/` (anyone who can write either can already rewrite `lib/server/`). It takes no path, so it can't serve a job worktree's files. The loopback Host, token, Origin and JSON-POST guards and the manifest allowlist are the same in dev mode. The flag is CLI-only: no config key and no `/api` route sets it. A dev dashboard never starts the daemon by itself (only Start does), so a fresh clone of a repo that commits `daemon.enabled: true` doesn't boot a paid session, and it refuses to start beside a live dashboard for the same repo instead of taking it over.

## Daemon security

The daemon runs an unattended agent under `daemon.allowedTools`, asking a human in the dashboard about anything else (or, with `--permission-mode dontAsk`, refusing it, or, in a session a human switched to `auto`, letting Claude Code's classifier decide), so its inputs are narrow on purpose:
- **One fixed stdin turn.** Every session gets only `TURN_LINE` (`/forge requests`) as a message. The only other stdin lines answer claude's own `can_use_tool` permission requests ("Permission prompts" below), carrying nothing from HTTP but the decision, or ask claude to switch permission mode ("Permission mode" below), carrying one value from a fixed list. A fourth, an error reply to a control request forge does not handle, repeats only the first 40 characters of claude's own subtype back to claude. All of them are built in `lib/integrations/claude/stream.ts`, which exposes no write that takes free text: the supervisor can only ask for the turn, pick a decision for a request claude itself sent, or name a mode. Request text, request and job ids, config values and HTTP bodies never reach stdin; the session reads requests through `forge requests`, where the skill treats them as the human's words about one job, never as rules. Free text from the dashboard's command bar (`POST /api/jobs`) is written only to the new job's `request.md` (and, through the derived title, `job.json` and `events.jsonl`); the `resume` queued for it carries no text.
- **The scope travels in the environment only, validated.** A session learns its scope from `FORGE_DAEMON_SCOPE`, set by the supervisor from a routed request whose job id matched `^[A-Za-z0-9][A-Za-z0-9._-]*$` (at most 200 characters) and has a `job.json`; anything else routes to `_inbox`, which can't be a job id. Under `FORGE_DAEMON=1`, `forge requests list|claim|ack|scope|add` refuse a missing or invalid scope, list only that scope's requests, refuse to claim or ack a request that doesn't exist or belongs to another scope, and queue only `resume` hand-offs. These keep a session that follows the skill in its lane; they are not authentication (see "Untrusted input"). Request ids are checked against their `<time>-<id>` format before any path is built from them. Runtime file paths are built only from validated scopes.
- **argv comes from the repo's config, with no shell.** `daemon.command` is split into words and run directly, and placeholders expand to single arguments. Nothing from HTTP or requests reaches argv. A session id read back from a session record or a child's `system`/`init` must be a uuid before it can follow `--resume`, so a planted value can't become a flag.
- **Trust boundary: `.forge/config.yml` is code.** Whoever can change it can run code through the daemon, exactly as through `commands.*` (which verify runs through a shell): validation refuses the claude flags that widen permissions (`--dangerously-skip-permissions`, `--permission-mode bypassPermissions`, `--settings`, `--mcp-config`, `--add-dir`, `--agents`, a second `--plugin-dir`, a literal `--allowedTools`; docs/CONFIG.md "Daemon" has the full list), but the session still runs `commands.*` through `forge run`/`forge verify`, and `daemon.enabled: true` in committed config starts an unattended, paid session on every machine that runs `forge dash`. The config is read from the main checkout only, never from a job worktree or a PR branch, but a merged change applies everywhere. Give `daemon.command`, `daemon.allowedTools` and `daemon.enabled` code-owner review, like CI config. The session itself can't use this route (next bullet). The validator's rule that the first word is a bare `claude` or an absolute path to `claude` outside the repo catches mistakes (a migrated shell template, a relative path that would run a repo file); it is not a security boundary. Configured commands run without the `FORGE_DAEMON*` markers: the trust check guards the session's own `forge` calls, and a command's nested `forge` call against a scratch repo (a test suite) must not be judged by it. A command can run any code anyway, so that check never bound it. The git pins below still apply to commands.
- **The session can't change what Forge executes.** Its cwd is the main checkout and it has `Edit`/`Write`, so an agent misled by tracker or PR text could otherwise rewrite `commands.*` (which `forge run`/`forge verify` run through a shell) or `daemon.*` (picked up at the next spawn or resume). Three layers, innermost first:
  - *The CLI checks at the sink.* When a human starts the daemon (dashboard Start, or `forge dash` with `enabled: true`), the supervisor takes `trustDigest`: a sha256 of the checkout's realpath, `.forge/config.yml`, `.forge/secrets-allow.txt` (or its absence: a session that could edit it could allow its own leak), every file under `.forge/trackers/` (custom tracker modules `forge` imports) and every file under `.forge/verifiers/` (a session that could weaken a block verifier could pass its own work; symlinks hash as links). It hands the digest to the session as `FORGE_DAEMON_TRUST`. Under `FORGE_DAEMON=1`, every `forge` command recomputes it before reading config and refuses on a mismatch, or when the variable is missing. The check catches every route, including Bash (`git mv -f`, a redirect) and a fake checkout reached through `cd`. `forge init write`, `forge migrate` and `forge config set` refuse outright, because they write config.yml through `forge` itself. config.yml is read once, and the bytes that were hashed are the bytes parsed. A custom tracker module is checked again just before it is imported. Any symlink under `.forge/trackers/` is refused (its target could change without the link changing), and the walk never follows one. What the digest can't see: files a tracker module imports from outside `.forge/trackers/`, so keep tracker modules self-contained.
  - *The supervisor stops the session.* Every poll, and before any spawn, it compares the digest with the one taken at start. On a change it stops the child and stays stopped with an error in the dashboard; respawns after an idle stop or a failed resume reuse the old snapshot, so a change made during a turn is never blessed by a restart. A spawn hashes config.yml once and builds argv from those same bytes, so a file swapped and restored between two reads can't slip in. Only a human's Start takes a new snapshot, and only when no child is running. A human editing config while the daemon runs gets the same stop, which is the price of not being able to tell the two apart.
  - *Claude Code refuses the write.* `--disallowedTools Edit(.forge/config.yml),Edit(.forge/trackers/**),Edit(.forge/secrets-allow.txt),Edit(.forge/verifiers/**),Edit(.forge/runtime/spend.json),Edit(.forge/runtime/audit.jsonl)` follows every `daemon.command`, whatever the template says. Edit rules cover every file-writing tool and Bash redirections. Relative paths anchor at the session's cwd (the main checkout, so job worktrees, where a self-improvement job legitimately edits Forge config, are unaffected), deny beats allow in every mode, and subagents inherit the rules. This layer does not cover programs that write files themselves (`forge`, `git`), which is why the first layer exists. `.claude/` and `.mcp.json` are already Claude Code protected paths, which are never allowed without a human: `dontAsk` refuses them, and `default` asks.

  The anchor is the session's environment, which it can't change: Bash allow rules don't match a command with a leading `VAR=…` assignment (except a few known-safe variables), and `env`/`export` aren't allowed. This keeps the *repo's* trusted commands in force; it does not stop those commands from running code the job wrote, which every verify does by design (that code is reviewed after verify, not before).
- **Start and stop** need the dashboard token, a matching Origin and JSON, and a pool `start` additionally needs `daemon.enabled: true` and no `daemon.*` validation problem. A scoped start only re-enables one session inside a pool a human already started, so it never takes a trust snapshot. The config migration never sets `enabled`. Concurrent start/stop POSTs never leave more than one child per session: a start while a child exists or is stopping spawns nothing new.
- **SSE is loopback-only and per session**, rejects a foreign Origin and any request whose `Sec-Fetch-Site` is not `same-origin`/`none` (the same `readGuard` the history route uses), syntax-checks `session` (400 otherwise), sends a stream only its own session's lines, sends no CORS headers, allows 8 streams at once across all sessions (`503` beyond), ends any client more than 1 MiB behind, and recycles every stream after 5 minutes (EventSource reconnects with `Last-Event-ID`). The dashboard opens only the stream of the session on screen. Another site can never read a stream. In a browser that sends neither Origin nor Fetch Metadata on a no-cors GET, a cross-site page can still occupy slots until they are recycled; that costs the live log's availability, never the daemon.
- **History reads are confined.** `GET /api/daemons/log` validates the scope before building a path, requires the daemons dir to be the real `.forge/runtime/daemons` (not a symlink to elsewhere), resolves `<scope>.log` with realpath and serves it only from inside that dir, and reads it through one descriptor opened `O_NONBLOCK` and `fstat`-checked as a regular file. Session records (`<scope>.json`) are read through one `O_NOFOLLOW|O_NONBLOCK` descriptor and must be regular files under 64 KiB, or they count as absent. Logs are opened for appending with `O_NOFOLLOW|O_NONBLOCK` and must be regular files (a session whose log can't be opened keeps running without one), and `forge daemon log` opens them the same way for reading. So a symlink or FIFO planted in the runtime dir is never followed and can't hang the server, on read (the history route, `/api/events`) or on write (session logs, reap notes).
- **Permission prompts are answered from the dashboard only.** Every daemon command ends with `--permission-prompt-tool stdio`, so claude sends each call it would ask a person about to the supervisor as a `control_request`. The supervisor holds it in memory (never in a file the session could edit), shows it in `/api/state`, and answers when a human posts `POST /api/daemon/permission` with the token, a matching Origin and JSON. The body names a scope, the supervisor's uuid for the prompt and a decision (`allow`, `session` or `deny`); the reply is built from claude's own request: an allow echoes its input unchanged, a deny carries fixed text, and "allow for this session" grants only the allow rules and absolute directories claude suggested, rewritten to the `session` destination, so suggestions to save rules to a settings file or change the permission mode are dropped. There is no CLI command to answer a prompt, because the session itself runs `forge`. Prompts end with their child, at most 20 wait per session, a request whose `request_id` is already waiting is ignored (a repeated id must not swap the input an allow runs), and any other control request subtype gets an error so claude never hangs. What a prompt shows (the input, the agent's description, the blocked path) is session output and renders as text. A prompt is exactly as safe as the human reading it: the tool, its full input and any blocked path are shown, and the agent's description is labelled as its own words.
- **Permission mode is a human's choice, held in memory.** `POST /api/daemon/mode` (token, matching Origin, JSON) names a scope (validated, and a job must have a `job.json`) and one of `default`, `auto` or `dontAsk` (lib/integrations/claude/argv.ts `PERMISSION_MODES`); anything else is a 400. The pool keeps the choice in memory only: session records live in `.forge/runtime/`, which the session can write, so a mode read back from disk would be one the session could choose for itself. A running child gets a `set_permission_mode` control request; a later spawn gets `--permission-mode <mode>` in place of the template's. Until claude reports its mode (at its first turn's init) the supervisor takes the one the child was launched with. A switch claude refuses or doesn't confirm fails closed: a narrowing one stops the child, so the next spawn starts in the chosen mode, and a widening one leaves the choice at what the child still reports. `auto` stays refused in `daemon.command`, so a repo's config can't put every session on every machine that runs `forge dash` into it: only a human at the dashboard can, for one session, until that `forge dash` stops. In `auto`, Claude Code's classifier approves calls outside `allowedTools` without a human, so a misled agent's call may run unread; the deny rules, the trust check and the git pins below still hold. `bypassPermissions` is never offered, and claude refuses it on a session not launched with `--dangerously-skip-permissions`, which validation forbids. The same POST with scope `_jobs` sets the default for every job session without its own choice, also in memory only; the inbox and office never take it. `forge dash --permission-mode` sets that default at start-up: the human's own command line, refused when `FORGE_DAEMON=1`, so a session can't start a second dashboard with it. There is no CLI command to switch a running dashboard's modes, for the same reason there is none to answer a prompt. **Auto on one session reaches the whole daemon.** The dashboard serves its token to any local client and a non-browser client can send any Origin, so a session whose calls run without a human (Auto, or one a human allowed `curl` to) can read the token and post to `/api/daemon/mode` or `/api/daemon/permission`: switch other sessions to Auto, make Auto the job sessions' default (`_jobs`, which also reaches jobs created later), or answer their prompts and its own. A session that only runs what `allowedTools` lists can't: no `forge` command posts to these routes, and `forge dash --permission-mode` refuses a daemon session. Nothing on loopback tells the page apart from a session's process, so treat putting any session in Auto as trusting every session's input.
- **Effort is a human's per-job setting, read back from `job.json`.** The level reaches argv only as one word from the fixed list (`EFFORTS` in `lib/core/job/schema.ts`), and never stdin. `normalizeJob` reads anything else in `job.json` as null and `buildArgv` ignores a value outside the list, so a hand- or session-written `"--dangerously-skip-permissions"` or `"high --add-dir /"` never becomes an option. An invalid `runtime.effort` is a `daemonProblems` refusal, so no session starts. `withEffort` drops every `--effort` and `--effort=` in `daemon.command`, so a duplicate can't win over Forge's. `forge job set --field effort=…` is refused, and `forge job effort` and `forge job new --effort` refuse under `FORGE_DAEMON=1`, so a misled session can't raise its own or another job's level through the CLI. `POST /api/jobs/:id/effort` takes the token, a matching Origin and JSON, an existing job id and a value from the list or null. Residual risk: a session can still write a valid level into its own `job.json` with `Write`, as it can `budget.limits`. That costs tokens and time, bounded by `pipeline.budget` and visible in the session log's `effort` event and the card chip, and it never widens what the session may do. `complexity` is session-writable through `forge job set --field`, but only as `low`, `medium`, `high` or null, and it only selects among levels a human configured in `runtime.effortByComplexity`, which never reaches a session's argv. That is why, unlike the permission mode, effort is read back from disk: it is a human's setting that must survive a `forge dash` restart.
- **Narrow permissions, still not a sandbox.** Anything `allowedTools` doesn't list is asked about (or refused under `dontAsk`), and subagents inherit the list. The default allows Bash only for `forge` and specific git/gh subcommands (rev-parse, merge/rebase `--abort`; `gh pr view|list|checks`, `gh run view`). The session's cwd is the main checkout and `cd` and `git -C` aren't allowed, so a bare `git add`/`git commit` would act on the base branch: agents stage and commit through `forge git add|commit <job>`, which runs git with the job's worktree as cwd (refusing the main checkout, a branch other than the job's, and a merge or rebase in progress for `commit`), takes only `--message`/`--message-file` (a file inside the job dir) and paths, so no `-c`, `-C`, `--git-dir`, `--amend`, `--no-verify` or `--author`, refuses paths outside the worktree or in a `.git`, checks the message for AI attribution, clears `GIT_DIR`-style variables, and under `FORGE_DAEMON=1` runs git with the session pins below (outside the daemon, a human's hooks run). Claude Code matches each part of a compound command against the rules and won't match past `git -c` or an env assignment, so `git -c core.sshCommand=…`, `git -c alias.x='!…'` and `FOO=… git …` are refused. `git diff|log|show|range-diff` are left out because `--output=<file>` writes wherever git can, and Claude Code's protected-path check covers its own file tools, not git: `git log --format=… --output=.git/config` would plant a textconv or filter driver that the next diff or add runs. Agents read history through `forge git`, which refuses `--output` (git accepts no abbreviation of it), `--ext-diff`, `--textconv` and `--open-files-in-pager`, and forces `--no-ext-diff --no-textconv`. `git rebase` is left out because `--exec` runs shell: the integrator starts merges and rebases with `forge integrate --keep-conflicts` and finishes them with `forge integrate --continue`, which refuses a rebase todo holding anything but picks. `git mv` is left out too: given a `x/../.git/config` destination it reports an invalid path, then renames the file anyway and exits 0. `gh api` and other GitHub writes are left out; Forge's own writes (push, PR, labels, comments) go through `forge`. Validation refuses `allowedTools` entries that undo this (unscoped `Bash`, bare `git`/`gh`, `git -…`, `git config|grep|submodule|bisect|…`, `git diff|log|show|range-diff|…`, `git mv`, `git rebase`, `gh api|extension|alias|auth|…`); the list catches known forms and is not exhaustive.
- **Git hooks are off in the session.** `Edit`/`Write` are unscoped, and a repo can point `core.hooksPath` at a tracked directory (`.githooks/`, unlike `.git/` and `.husky/`, isn't one of Claude Code's protected paths), so a hook written there would run on the next `git commit`, or on a `forge pr open` push. The daemon therefore spawns the session with `core.hooksPath=/dev/null` and `core.fsmonitor=false` in `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n`, which outrank every config file and are inherited by subagents, `forge` and verify commands. The cost: no hooks at all in daemon mode, including Git LFS's pre-push upload. Not pinned: filter, diff and merge drivers and `gpg.program`, which only `.git/config` or `~/.gitconfig` can define. The session has no allowed way to write `.git/` (Claude Code's file tools treat it as protected, so only a human's answer to a prompt could allow it, and the git forms it may run take no output path), but anything the human or another tool puts there still applies. What remains broad is `Edit`/`Write` itself, which can still change repo files that build and test tooling executes (`.forge/config.yml`, `.forge/trackers/` and `.forge/verifiers/` are pinned; see above). Enable the daemon only on repos whose tracker input you trust (or with intake restricted, e.g. `tracker.github.comments: collaborators` and ready labels only maintainers set).
- **Keeping a slot and marking agents lost read `job.json`, which the session writes.** A session that records agents it never ends can pin its own slot, never another job's, for at most 2 h per agent start (the `AGENT_LEASE_MS` ceiling; a `startedAt` or `endedAt` more than 60 s in the future is ignored, so a forged time can't stretch the ceiling or the idle window, and the idle timer never re-arms for longer than its window), and a human's session or pool Stop ends it sooner, the same bound as a turn that never returns a `result`. Lost-marking writes on behalf of a session that no longer exists, so it touches only agents of a job whose `lease.driver` is that session's id, never another driver's. The job id it reads is the validated scope, so no path is built from session output, and nothing new reaches the child's stdin, argv or environment.
- **Orphan reaping** proves each record (every `daemons/<scope>.json`) separately before signalling its pid (see "Daemon"), so a stale or planted record can't make Forge kill an unrelated process.
- **The logs** (`daemons/<scope>.log`) live in gitignored `.forge/runtime/`; they hold whatever the sessions printed, so treat them like transcripts. The dashboard renders every log string as text, and `forge daemon log` escapes control characters so session output can't drive the terminal.

## Release security

`.github/workflows/release.yml` holds the only write token Forge's automation uses: it tags commits and publishes Releases. [RELEASES.md](RELEASES.md#releasing) describes the flow. `test/invariants/release-workflow.test.ts` pins the file with allowlists that fail closed on any trigger, key, permission, action or expression it does not list, so weakening it means editing that test in the same reviewed diff.

- **Who it defends against.** A PR author (a fork included) who wants the token or the Release, a retagged or compromised action, repo text (the `package.json` version, CHANGELOG) that would reach a shell, `GITHUB_OUTPUT` or argv, and a later edit, by a person or an agent, that quietly weakens the workflow.
- **Never on PR events.** It runs on pushes to `main` only: no `pull_request`, `pull_request_target`, `workflow_run` or `workflow_dispatch`.
- **Write scope in one job, after verify.** The workflow's token is `contents: read`. Only the `release` job asks for `contents: write`, and it needs `detect` and `verify` (all of `ci.yml`, called with no inputs, no secrets and the read-only token).
- **The token reaches two steps.** `github.token` appears only as `GH_TOKEN` on the tag and publish steps, which call `gh`. Checkout keeps no credentials, so the scripts and `git archive` never hold a token.
- **Repo text is validated or passed as a file.** `scripts/release-plan.ts detect` exits before writing anything unless the version is `X.Y.Z`, so a version with a newline can't add outputs. The version reaches `run` only through `env`, never `${{ }}`. The CHANGELOG section reaches `gh` only as `--notes-file`. The tag message and Release title are fixed text.
- **Pinned actions.** Only `actions/checkout` and `actions/setup-node`, each pinned to the same full SHA as `ci.yml`.
- **Residual risk: code runs beside the write token.** The `release` job still runs `actions/setup-node` and `node scripts/release-plan.ts notes` while it holds `contents: write`. On a hosted runner, any step can read the runner's memory and lift the job token (the 2025 tj-actions compromise did this). Both are pinned or come from merged `main`, so this is accepted rather than closed: a change to `scripts/release-plan.ts` or the pinned actions is a change to what runs with the token, and gets reviewed as one.
- **The archive proves its commit.** The release job refuses an archive whose stamped `COMMIT` is not the pushed sha, and publishes its `.sha256` beside it. `forge version --json` is self-reported; the annotated tag and the checksum are the audit anchors.

`forge doctor`'s release row (`latestReleaseCheck` in `lib/engine/ops/version.ts`) runs `gh release view` with a repo taken from `known_marketplaces.json` or the install's `plugin.json`, both writable by anything that can write `~/.claude` or the checkout. The repo must match `^[A-Za-z0-9][A-Za-z0-9-]*/[A-Za-z0-9._][A-Za-z0-9._-]*$` (no leading `-`) before it becomes argv, with no shell. The call has a 5 s timeout, the returned tag must be `v?X.Y.Z` before it is shown, and any failure leaves the row out.
