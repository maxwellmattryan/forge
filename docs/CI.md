# Forge's own CI

`.github/workflows/ci.yml` runs the [verify list](../AGENTS.md#verify-before-claiming-it-works) as named steps, in its order, on every PR, every push to `develop` and `main`, every call from another workflow (`workflow_call`) and every manual or dispatched run (`workflow_dispatch`, no inputs). Read this page when you change the workflow or the list; `test/invariants/ci-workflow.test.ts` fails when they differ.

## The verify job
- It runs on Node 22.18.0 (`.nvmrc`) and the latest Node 24, on Ubuntu only, each cell split in two by a `shard` axis: the test step there is `node --test --test-shard="$TEST_SHARD" "test/**/*.test.ts" "lib/**/*.test.ts" "dashboard/src/**/*.test.ts"`, with `TEST_SHARD` set from the matrix (`1/2`, `2/2`), so each half-suite runs on its own runner. That is one of the two commands that differ from the list; the other is the validate step (below). The step also sets `FORGE_REQUIRE_DIST: '1'`: the tests that read the real dashboard build (`test/dist.ts` › `noDist()`) skip when `dashboard/dist/manifest.json` is missing, as on a fresh clone of `develop`, and with it set they run, and fail if the build step left nothing. Beside it, `FORGE_REQUIRE_BROWSER: '1'` makes the render check's own test fail instead of skipping when Chrome can't launch (the runner ships Google Chrome).
- Directly after `npm ci`, the "Check touchpoints" step runs `npm run check:touchpoints` (`scripts/check-touchpoints.ts`), which reads the diff and names each companion change it is missing, with the fix: an `API_CHANGES` step for an `/api` shape change, a config step and a `CONFIG_DISCLOSURE` class for a new config key, this page for a `ci.yml` change, docs/RELEASES.md and the release tests for the release pipeline, `asOf` for a price change and docs/TRACKERS.md for a tracker contract change. The step sets `FORGE_TOUCHPOINTS_BASE: HEAD^1`, so the diff is what this run adds: on a PR, HEAD is GitHub's merge commit and `HEAD^1` the base branch's tip; on a push, the previous commit; on the main update (parents `main` and `develop`), the previous `main`. That is why the checkout sets `fetch-depth: 2`: HEAD and its parents, and nothing older. Any error (a ref that doesn't resolve, no merge base, a failing git call) exits 2 and fails the run; it never skips. There is no per-PR skip: a rule that fires on a complete diff gets a narrower trigger in the script's table. Locally it compares against `origin/develop` and includes uncommitted and untracked files.
- For the last step it installs `@anthropic-ai/claude-code@2.1.299` from npm with `--ignore-scripts`, so no lifecycle script from the package runs on the runner. That pin is the CLI version maintainers run locally, so CI validates by the same rules as a local run, even when the release is only days old (the action pins wait two weeks). Bump it in the workflow, here and docs/DEVELOPING.md together, and check that the new version still ships `cli-wrapper.cjs`. The package's `postinstall` only copies the native binary over the `bin/claude.exe` stub, so without it `claude` on PATH is that stub; the "Validate plugin" step instead runs the package's own `cli-wrapper.cjs` (`node "$(npm root -g)/@anthropic-ai/claude-code/cli-wrapper.cjs" plugin validate . --strict`), which runs the binary from the pinned platform package (`@anthropic-ai/claude-code-linux-x64`, which has no scripts). Validation needs no login, so CI runs it rather than skipping it. It is the second command that differs from the list, and the test maps it back to `claude plugin validate . --strict`. There is no lockfile for this install: an exact npm version is immutable and npm checks the tarball's integrity against the registry.

## The other jobs
- **`audit`** runs `npm audit --omit=dev`, which blocks, and a report-only `npm audit`.
- **`render`** (`render check`) runs `npm ci`, `npm run build:dashboard` and `npm run test:render` on Node from `.nvmrc`: every view of every dashboard scenario in the runner's Google Chrome, failing on a console error, a page error, a 5xx or missing text ([TESTING.md](TESTING.md#dashboard-scenarios-and-the-render-check)). It stays outside the verify list, which every change runs without Chrome. Because `release.yml` calls `ci.yml` whole, a release waits for it too.
- **`release check`** runs `npm run release:check` after `verify` passes, choosing `--dist` from `REF` (the PR's base branch, or the pushed or dispatched branch, set in the step's `env`): `--dist absent` on `develop`, where `dashboard/dist/` must not be tracked; `--dist present` on `main`, where it must be tracked and match its build stamp; and no flag elsewhere, which checks the stamp only when dist is tracked.

`ci.yml` is also a reusable workflow (`workflow_call`, no inputs or secrets) that `release.yml` calls whole before it tags a release ([RELEASES.md](RELEASES.md)). `npm run release` waits for its push run on the release commit before it pushes `main`. Its bare `workflow_dispatch` re-runs it by hand; the token here stays read-only, so a dispatch can run nothing a PR couldn't.

## The main-update workflow
`.github/workflows/main-update.yml` runs on every push to `develop` and on `workflow_dispatch`, and its one job, `build`, also checks `github.ref == 'refs/heads/develop'`. It runs `npm ci` and `npm run build:dashboard` with the read-only token and uploads `dashboard/dist/` as the `dashboard-dist` artifact, kept 7 days. It writes nothing: `npm run release` checks that artifact and pushes `main` with the maintainer's own credentials ([RELEASES.md](RELEASES.md#releasing)). Its concurrency group is per commit, so a later push never cancels a release commit's pending build. `test/invariants/main-update-workflow.test.ts` checks it stays read-only and uses no token or secret.

## What the tests check
The three workflow tests share `test/invariants/workflow-lint.ts` and check security properties, not exact job, step or key lists: every remote `uses:` is pinned to a 40-hex SHA (local `./` workflows and `docker://…@sha256:` images pass), `permissions` are set and grant no write beyond each test's allowed map, checkouts don't persist credentials, and a credential (`${{ secrets.* }}` or `${{ github.token }}`) reaches only the `env` or `with` of the step that uses it, never job- or workflow-level `env` or `run:` text. In all three, no `run:` interpolates any `${{ … }}` expression (values reach a script through the step's `env`), no workflow runs on `pull_request_target` or `workflow_run`, and nothing restores a dependency cache (`actions/cache`, or setup-node without `package-manager-cache: false`). `test/invariants/ci-workflow.test.ts` also checks that CI runs the verify list in order, that it has no gate bypass (`|| true`, `continue-on-error` beyond the report-only audit), that the runtime `npm audit --omit=dev` exists and blocks, that the CLI install is pinned and runs once, right before validation, and that the touchpoints step keeps `FORGE_TOUCHPOINTS_BASE: HEAD^1` and the checkout `fetch-depth: 2` (a base of `HEAD` would compare HEAD with itself and always pass). `test/invariants/release-workflow.test.ts` holds that only a push to `main` runs the release and that the release job needs `verify` and runs only when detect says so. `test/invariants/main-update-workflow.test.ts` holds that only a push to `develop` or a manual run with no inputs builds the artifact, and that the job checks it is on `develop`.
