# Forge's own CI

`.github/workflows/ci.yml` runs the [verify list](../AGENTS.md#verify-before-claiming-it-works) as named steps, in its order, on every PR, every push to `develop` and `main`, every call from another workflow (`workflow_call`) and every manual or dispatched run (`workflow_dispatch`, no inputs). Read this page when you change the workflow or the list; `test/ci-workflow.test.ts` fails when they differ.

## The verify job
- It runs on Node 22.18.0 (`.nvmrc`) and the latest Node 24, on Ubuntu and macOS, each cell split in two by a `shard` axis: the test step there is `node --test --test-shard="$TEST_SHARD" "test/*.test.ts"`, with `TEST_SHARD` set from the matrix (`1/2`, `2/2`), so each half-suite runs on its own runner. That is the one command that differs from the list. The step also sets `FORGE_REQUIRE_DIST: '1'`: the tests that read the real dashboard build (`test/dist.ts` › `noDist()`) skip when `dashboard/dist/manifest.json` is missing, as on a fresh clone of `develop` or the Windows leg, and with it set they run, and fail if the build step left nothing.
- For the last step it installs `@anthropic-ai/claude-code@2.1.299` from npm. That pin is the CLI version maintainers run locally, so CI validates by the same rules as a local run, even when the release is only days old (the action pins wait two weeks). Bump it in the workflow, here and AGENTS.md together. `claude plugin validate` needs no login, so CI runs it rather than skipping it.

## The other jobs
- **`audit`** runs `npm audit --omit=dev`, which blocks, and a report-only `npm audit`.
- **`windows (node 22.18.0)`** runs on `windows-latest` outside the list: `npm ci`, `npm run typecheck`, then `node scripts/windows-tests.ts`, which runs every `test/*.test.ts` except those named in the step's `WINDOWS_SKIP` block. Native Windows is unsupported (`docs/SUPPORT.md`), so the job only guards the cheap Windows fixes against regressions. Each skip is one line, `test/<file>.test.ts: <reason>`; the script exits 1 before running anything on a line with no reason, a path that isn't one existing test file, a repeat, or a list that leaves nothing to run, and `test/ci-workflow.test.ts` › "every Windows skip names an existing test file and its reason" holds the workflow to the same rule. Drop a skip once its file passes there.
- **`release check`** runs `npm run release:check` after `verify` passes, choosing `--dist` from `REF` (the PR's base branch, or the pushed or dispatched branch, set in the step's `env`): `--dist absent` on `develop`, where `dashboard/dist/` must not be tracked; `--dist present` on `main` and `ci/main-update`, where it must be tracked and match its build stamp; and no flag elsewhere, which checks the stamp only when dist is tracked.

`ci.yml` is also a reusable workflow (`workflow_call`, no inputs or secrets) that `release.yml` calls whole before it tags a release, and `main-update.yml` before it builds the main-update PR ([RELEASES.md](RELEASES.md)). Its bare `workflow_dispatch` exists for `main-update.yml`: a push or PR made with `GITHUB_TOKEN` starts no PR checks, so the publish job runs `gh workflow run ci.yml --ref ci/main-update`, and the checks land on the PR head under the names branch protection requires. The token here stays read-only, so a dispatch can run nothing a PR couldn't.

## The main-update workflow
`.github/workflows/main-update.yml` runs on every push to `develop` and on `workflow_dispatch`, and each job also checks `github.ref == 'refs/heads/develop'`. `verify` calls `ci.yml`; `build` builds the dashboard with the read-only token and uploads it; `publish` holds the only write token (`contents`, `pull-requests` and `actions`), runs no `npm`, checks the artifact with `scripts/main-update.ts`, force-pushes `ci/main-update` with the token in a `-c http.https://github.com/.extraheader=` argument (never in git config or a URL), and opens or edits the one PR into `main` with `--body-file`. A push GitHub refuses, as it can when the commit changes `.github/workflows/` relative to `main`, fails the step with `Push refused`; [RELEASES.md](RELEASES.md#releasing) › Workflow changes has the manual push. `test/main-update-workflow.test.ts` pins its triggers, permissions, actions, expressions and every `publish` script; [RELEASES.md](RELEASES.md#releasing) explains the PR.

## What the test pins
`test/ci-workflow.test.ts` holds the workflow to allowlists of triggers, keys, `env`, actions and `${{ }}` expressions, and pins the job names, the matrix, the action inputs, every `run` (the release check's `--dist` choice and the audit steps included) and the single CLI install exactly, so changing any of those means editing the test in the same diff.
