# `.forge/config.yml`

`/forge init` writes this file. Every key is optional; anything omitted takes the default shown. The file uses a strict YAML subset (block maps and lists, quoted or plain scalars, `[a, b]` / `{a: 1}` flow collections, `|` blocks, comments; no anchors or tags). `forge config validate` checks it, `forge config show` prints the effective config, `forge config get <key>` prints one effective value, and `forge config set <key> <value>` changes one editable key (see [Changing settings](#changing-settings)). The reference block below is generated from `lib/core/config/keys/` by `npm run docs` (to change a key's comment, edit its doc string in `lib/core/config/keys/docs.ts`); the sections after it are hand-written.

Command templates are POSIX `sh`: each runs as `/bin/sh -c <cmd>` with an allowlisted environment and no login profile, in and out of the daemon ([Command environment](#command-environment) covers what they inherit, `commandEnv.inherit` and `commandEnv.loginShell`), and on native Windows under Git for Windows' `sh` (Git Bash; the first `sh.exe` on PATH, else `%ProgramFiles%\Git\bin\sh.exe`), or is refused with an error when there is none (see [SUPPORT.md](SUPPORT.md)). Command templates may use `{port}`, `{job}`, `{worktree}`, `{root}`, `{branch}`, `{base}`, `{args}`, `{endpoint.<component>}`, `{backing.<name>.port}` and `{backing.<name>.url}` (the last three under [Ports and endpoints](#ports-and-endpoints) and [Backing services](#backing-services)). `{args}` holds the extra arguments of `forge run <job> <name> -- <args…>`, each already in single quotes, and arguments go only where a template has it: `forge run` refuses arguments for a template without `{args}`, so a command takes none unless you opt in. Write `{args}` unquoted, as a whole word: after the start, a space, a tab, a newline or `(`, and before the end, a space, a tab, a newline, `;`, `&`, `|` or `)`. Arguments for a template where it sits inside `'…'` or `"…"` or touches another word (`x{args}`, `\{args}`) are refused, and so are arguments for any template containing a heredoc (`<<`), `$'` or `\'`, where the quoting would not hold. The arguments become words of whatever command surrounds `{args}`, so `exec {args}`, `env {args}` or `time {args}` runs the first one as a program. An argument containing a quote, backslash or control character is refused too. Every refusal comes before anything runs. Only `forge run` has arguments: `forge verify`, worktree setup, `forge run --background`, `forge integrate`'s rebuild and `forge eval grade` fill `{args}` with nothing. The other placeholders are filled in unquoted, so `{job}`, `{branch}` and `{base}` are checked first: each must start with a letter or digit and use only `A-Z a-z 0-9 . _ / -` (at most 200 characters), and an unsafe value stops the command before it runs, with an error naming the field. `{worktree}` is filled only with the path Forge computes for the job, `<worktrees.root>/<job id>`: a command whose template uses it stops before it runs when the job's stored `worktree` is anything else, for the same reason. Commands that don't use `{worktree}` are not affected. Commands also get `PORT`, `FORGE_PORT`, `FORGE_JOB`, `FORGE_WORKTREE`, `FORGE_PORT_<C>` and `FORGE_ENDPOINT_<C>` (one pair per port-bearing component) in their environment, on top of the [command environment](#command-environment). That never holds the daemon session's `FORGE_DAEMON*` variables, so a command that calls `forge` behaves the same under the daemon as for a human, nor the source variable of a declared `env` secret: its value reaches a command only through a config sink ([Secret references](#secret-references)).

## Instruction files

`project.instructions` names the files each agent reads first, relative to the repo root; a brief lists only those that exist in the main checkout. It takes one of two forms:

- **A list**: every role reads the same files.
- **A map**: `default` (the list for every role the map doesn't name) plus any of `planner`, `spec-writer`, `designer`, `builder`, `reviewer` (every lens), `approver`, `integrator`, `verifier` and `judge`. A role's list **replaces** `default`; it doesn't add to it, so repeat a file the role still needs. A role mapped to `[]` gets no instruction files. A map without `default` keeps the default list, `[AGENTS.md, CLAUDE.md]`.

```yaml
project:
  instructions:
    default: [AGENTS.md]
    builder: [AGENTS.md, docs/DEVELOPING.md]
    spec-writer: [AGENTS.md, docs/DEVELOPING.md]
```

`forge config validate` reports a key that is not a role, a value that is not a list, an entry that is not a non-empty string, an absolute path and a `..` segment; the briefs skip any such entry. `forge job paths <id>` prints the `default` list. A config at schemaVersion 30 or older still loads: its list reads as `{ default: <list> }`, and `forge migrate` writes it that way.

**The main checkout's copies, never the branch's.** `paths.instructions` points at the main checkout's files, read as they are on disk, so a branch can't rewrite the conventions its own reviewers and approver follow. The worktree's copies are the branch's edits and part of its diff: data to review, never instructions. When the branch's committed diff changes an instruction file (`**/AGENTS.md`, `**/CLAUDE.md`, `**/CLAUDE.local.md`, `.claude`, `**/.claude/**`, `.mcp.json`, or any role's `project.instructions` entry, matched case-insensitively), every brief but the scoring judge's carries an `Instructions changed by this branch (JSON): [...]` line naming them, or a `not checked` line when the diff can't be read. Verify records the same list in `verify/round-<n>.md`'s `## instructions` section, and the default policy escalates them ("Protected paths"). An eval job reads the main checkout's copies too, and those may postdate the task's base commit.

**Keep the auto-loaded file short.** Claude Code loads the root `AGENTS.md` (or `CLAUDE.md`) into every session as project instructions, the orchestrator and every agent included, and the brief tells an agent to skip a file already in its context. So naming fewer files per role saves little while that root file stays long. Keep it to what every session needs and move the reference into a file only the roles that need it are given, such as `docs/DEVELOPING.md` above.

## Worktree seed

`worktrees.setup` (an `npm ci`, say) runs in every new job worktree and starts it cold: dependencies rebuilt, test and type-check caches empty. A **worktree seed** lets a new worktree start warm instead. Forge keeps a private copy of a fresh base worktree's untracked paths (`worktrees.seed.paths`, such as `node_modules` with its `.cache`), and a new worktree clones it copy-on-write whenever its key files (`worktrees.seed.key`, such as `package-lock.json`) hash the same. It is off while `paths` is empty, and applies only to the root repo's worktree in `forge worktree create`: never to member repos or eval clones, whose results have no `seed`.

**On create**, after `worktrees.copy`, ports and backing services:

- **Key.** A sha256 of the new worktree's key files, `worktrees.setup`, `seed.paths`, and the platform, arch and Node ABI. A missing key file (or one that is not a regular file) gives `reason: "no-key"`.
- **Where.** `<cache>/seeds/<repoId>/<key>/`, where `<cache>` is the start-up cache's directory (`.cache/` in the plugin root, or `$FORGE_CACHE_DIR`, honoured only inside the plugin root) and `<repoId>` is the first 16 hex characters of a hash of the main checkout's real path. Every level must be a real directory you own that nobody else can write, else `reason: "cache-unusable"` (see [Start-up cache › Worktree seeds](architecture/startup-cache.md#worktree-seeds)).
- **Hit.** Each path is cloned (`cp -c` on macOS, `cp --reflink=auto` on Linux, else a plain copy; `method` is `"copy"` when any path fell back), then `seed.setup` runs instead of `worktrees.setup`, with the same placeholders, environment, tail and redaction. A seed path already in the worktree (`reason: "exists"`), a path that won't copy (`"clone-failed"`) or a failing `seed.setup` (`"check-failed"`: the clone is removed and that seed deleted) falls back to `worktrees.setup` as if there were no seed.
- **Miss and refresh.** On a clean miss (`"no-seed"`) setup runs as usual. If it succeeds and this create made the job's branch new at the tip of `git.base` (not an existing branch, not stacked, not `--from`, and the job's base still `git.base`), Forge takes the seed lock, runs `seed.warm` in the worktree (a failed warm command is reported and the rest still run), re-checks that HEAD has not moved, no tracked file changed (both `not-base`) and the key is unchanged, and stores the paths as the seed for that key. Anything else skips the refresh and says why in `refreshSkipped`; so does a seed path that was already in the worktree before setup (`exists`, from `worktrees.copy` say), since only what setup built may become a seed. A symlink in the paths that is absolute, leaves the tree or has a `..` after another segment (`symlink-out`) refuses it too. A miss after `exists`, `clone-failed` or `check-failed` never refreshes: the next clean miss does.

A seed problem never fails the create. A failing `worktrees.setup` behaves as it always has (`ok: false`, step rule I4).

**Result.** `forge worktree create` adds `seed: { used, key (first 16 hex, or null), method?, reason?, checks?, warm?, refreshed?, refreshSkipped?, durationMs }`, where `reason` is `no-key | cache-unusable | no-seed | exists | clone-failed | check-failed`, `refreshSkipped` is `not-base | no-key | cache-unusable | busy | key-changed | missing-path | symlink-out | exists | failed`, `checks` and `warm` are `{ cmd, ok, tail }` lists, and `durationMs` covers everything from the key to the end of the refresh, setup included. On a hit `setup` is `[]`. Each create logs one `worktree-seed` event with the same fields minus the command tails.

**Disk.** One copy of the paths per key, the newest two kept per repo. Each plugin version starts with an empty `.cache/`, like the start-up cache, and deleting `<cache>/seeds/` by hand is always safe.

**Turning it on** for an npm repo:

```yaml
worktrees:
  setup:
    - npm ci
  seed:
    paths: [node_modules]       # node_modules/.cache travels with it
    key: [package-lock.json]
    setup: ["npm ls"]           # a quick check that the cloned tree fits
    warm: ["npm run typecheck"] # fills the caches the seed carries
```

## Changing settings

`forge config get <dotted.key>` prints the effective value (defaults merged with the file): strings raw, everything else as JSON, and `null` for a path that doesn't exist. `forge config set <dotted.key> <value>` changes exactly that key in the main checkout's `.forge/config.yml` and prints `{"ok":true,"key":…,"value":…,"previous":…,"changed":true}`. Only that value's line changes (or, for a missing key, one line is inserted as the last child of its section), so comments, blank lines and key order survive. Setting a key to its current value writes nothing and replies `"changed":false`. The dashboard's Settings modal saves through the same code (`POST /api/config`).

**Values** follow the key's type: `true`/`false`; a decimal number; `null` for keys that allow it; text as written; and lists as `[a, b]` or a JSON array (`'["a","b"]'`, `[]`). Values are checked against the key's range or options, text may not contain control or invisible formatting characters (bidi overrides, zero-width characters) or exceed 200 characters, `review.blockOn` must keep both `blocker` and `major` (adding `minor` or `nit` is allowed), `daemon.idleStopMinutes` and `daemon.turnTimeoutMinutes` must be greater than 0 (or `null`), and `tracker.github.labels.prefix` must be at least 2 characters ending in `:`, `/` or `-`, because Forge removes every issue label that starts with it. The result must also pass `forge config validate`, though problems the file already had never block an unrelated change.

**Editable keys**: `pipeline.plan`, `split`, `specApproval`, `design`, `maxRounds`, `maxTotalRounds` and every `pipeline.budget.*`; `review.blockOn`, `review.onPrFeedback` and `review.onRework`; `pr.integrationReview` and `pr.maxCiReworks`; `runtime.models.<role>`, `runtime.modelByComplexity.*`, `runtime.reworkModel`, `runtime.maxParallelJobs`, `runtime.diversity`, `runtime.effort`, `runtime.efforts.<role>` and `runtime.effortByComplexity.*`; `foreman.model`, `foreman.effort`, `foreman.assistants.model|effort` and `foreman.surveyors.model|effort`; `tracker.github.ready.*`, `tracker.github.claim.assign`, `tracker.github.statusSync` and `tracker.github.labels.prefix`; `dashboard.port` (used by the next `forge dash`); `daemon.idleStopMinutes`, `daemon.turnTimeoutMinutes` and `daemon.auth`; `retention.logMaxBytes`; `environments.maxRunning`; `outcomes.windowDays`; `scoring.sample` and `scoring.model`; and `budget.usdPerDay`, `budget.usdPerMonth`, `budget.tokensPerMonth` and `budget.onExceeded`. The rule: a key is editable only when it can't name a command, file, module, tool or repository Forge runs, loads or writes to, and can't loosen a security or attribution policy. Everything else (`commands.*`, `worktrees.*`, `verify*`, `git.*`, `merge.*`, `approver.*`, `aiAttribution`, `infra.*`, `review.panel`, `tracker.kind`, `tracker.github.repo`/`comments`/`project.*`, `daemon.enabled`/`command`/`allowedTools`/`maxConcurrent`/`jobBudget`/`dailyUsd` (caps unattended spend), `foreman.*` except the model and effort keys above, `retention.jobsDays`/`logsDays` (they delete files), `notify.webhooks` (names a URL Forge posts to), `notify.command` (runs a program), …) is refused with `<key> is not editable with forge config set (<why>); edit .forge/config.yml by hand`, and the dashboard shows it read-only. `lib/core/config/fields.ts` is the allowlist.

**Errors** exit 1 and leave the file byte-identical: an unknown key, a read-only key, an invalid value, or a layout the edit can't change without dropping a comment (a block map or `|` block, a list of maps, a list with comments between or on its items, a key inside a flow map). A repo without `.forge/config.yml` exits 2; `/forge init` creates it.

**The daemon.** A daemon session may not run `forge config set` (like `forge init write` and `forge migrate`). All three take the same `.forge/locks/config` lock, so they never interleave. If you run it while the dashboard's daemon is running, the change stops the daemon, exactly as a hand edit does (see [Daemon](#daemon)); the dashboard refuses to save settings until you stop the daemon, and only you may start it again.

## Split gate

`pipeline.split` decides what happens when the planner proposes several jobs for one request. `ask` (the default) parks the job on `split-approval` and creates nothing until you `/forge approve` it (create the jobs) or `/forge revise` it (keep it as one job). `auto` creates the tracker sub-issues and child jobs right away, and `never` makes the planner always plan one job, noting any split it would recommend under `## External`. A job started with `/forge issue <ref>` (or a dashboard Start) always plans as `never`: you chose that boundary. `forge job from-ref` records that as the job's `splitMode: "never"`, and so does `/forge revise` on a split proposal; every other job follows `pipeline.split`.

## How step reads the pipeline keys

`forge job step` decides each move from these keys and the job's recorded state:

- **`pipeline.plan: auto`** runs the planner when the request body (`request.md` without its title) is longer than 600 characters, or has 3 or more lines that start with a list marker (`-`, `*`, `1.`) or a `#` heading. `always` always plans and `never` never does.
- **`review.panel`** is picked twice. Once the spec is written (SP3), the panel is every `always: true` lens, plus the spec's `Suggested reviewers:` that are in the panel, plus each lens whose `when` names a path (a token with a `/` or a file extension, such as `lib/server/start.ts` or `dashboard/src/**`) or whose `paths` cover one of the spec's Approach paths. A `when` written only in prose is left to the spec-writer's suggestion. Then, after each build round's verify and before any reviewer starts, step runs `forge job panel <id>` (RV9), which recomputes the round's lenses from the branch's committed diff since the merge-base, in panel order: (1) `always` lenses, reason `always`; (2) the spec's suggestions in the panel, `suggested`; (3) lenses whose `when` paths or `paths` cover an Approach path, `approach <path>`; (4) lenses whose `paths` match a changed file, one reason per matching glob, `paths <glob>: <first file>` plus ` (+N more)`; (5) every lens already on the job, `carried`, keeping its panel position or appended when it isn't in the panel. Carrying only adds, so a lens never drops within a job's build loop: the spec-time panel, a lens a human added with `forge job set --field reviewers=…` and a lens an earlier round's diff matched all stay, and emptying `job.reviewers` can't remove what rules 1–4 select. A retro job always gets `code` and `docs`. `job.reviewers` is rewritten only when the set changed, and every run logs a `panel` event with the lenses and their reasons. `paths` globs use the matcher of `forge job scope` and `verifyE2e.paths`: an exact path, a `dir` or `dir/` prefix, and `*`, `**` and `?`, where a glob without a `/` also matches the file name at any depth (`*.svelte` matches `a/b/c.svelte`). No negation (`!`) or braces. `forge config validate` and `forge doctor` refuse a `paths` that isn't a list, or an entry that is empty, absolute, starts with `-`, `!` or `:`, or has a `..` segment. Uncommitted changes don't count. Names that aren't plain lowercase lens names are dropped. In a job with member repos, each reviewed member adds the lenses its own clone's panel defines, as `<repo>:<name>` after the root's ("Member review panels" under Repos). An entry with **`pathsOnly: true`** skips rules 2 and 3: it is chosen only by `always`, a `paths` hit or carry, so a spec can't pull it in by suggestion or Approach. `forge config validate` reports a `pathsOnly` that isn't `true` or `false`, and a `pathsOnly: true` entry with no non-empty `paths` (it could never run).
- **`review.panel[].needsApp`** says whether a lens reviews the running app. When a lens in the round needs it and `commands.dev` is set, Forge starts the dev server before the reviewers spawn and puts `Endpoints: <component> http://localhost:<port>; …` (one per port-bearing component) in that lens's brief. Absent, it defaults to `true` for `ui`, `ux`, `accessibility` and `design` and `false` for every other name; an explicit value wins for any name (`needsApp: false` keeps a `ui` lens off the app, `needsApp: true` puts a custom lens such as `visual-qa` on it). Anything but `true` or `false` is a config problem. A lens recorded on a job but no longer in the panel gets the name default.
- **`review.onPrFeedback`** picks the lenses for a rework round on an open PR: `full` re-runs the job's whole recorded panel, `none` skips review and goes straight to `forge pr open`, and `changed` (the default) re-runs the `always: true` lenses. `changed` can't look at which files the round touched, because step decides from recorded state, not the diff. Under `full`, RV9 re-runs `forge job panel` for the rework round, so the recorded panel gains any lens the diff now matches; `changed` stays always-only and `none` skips review, and both leave the panel alone. A re-review round on an open PR (a commit after review sent the job back, rules DC11 and PR12) follows this key too, so under `changed` a commit after review on an open PR is re-reviewed by the `always: true` lenses only.
- **`review.onRework`** picks the lenses for rounds 2 and later of a job without an open PR. `narrow` (the default) re-runs only the **rework panel**; `full` re-runs every lens, as before v21. Round 1 is the same under both. See "Rework panel".
- **`pipeline.maxRounds`** parks a build round past it on `rounds-exhausted` (B2), unless a rework (anyone's) opened that round; past it while the latest security review isn't `PASS`, the limit is twice `maxRounds`.

## Total-round ceiling

**`pipeline.maxTotalRounds`** (null, the default, means twice the job's `maxRounds`; otherwise an integer ≥ 1) counts every round (`job.round`), whoever opened it: the builder, a human, the foreman, or the CI rework `forge sync` records as the foreman's. In build, a round past the ceiling parks on `rounds-exhausted` (rule B7, checked before B2) unless a **person** (a `human` event whose actor is not the foreman) did `rework` or `revise-spec` after the previous round started. A person's rework past the ceiling opens one more round, and the round after it parks again unless a person reworks again. The foreman can't clear this park: every foreman action there is refused, the gate shows as a human's, and no foreman gate request is queued. An eval job past the ceiling goes to decide to be graded (B6), as it does past `maxRounds`. Editable in Settings.

## Rework panel

Under `review.onRework: narrow`, `forge job panel` on round N ≥ 2 still records the full panel on `job.reviewers` (a lens never drops), and also computes the lenses that re-run this round. In panel order, a lens re-runs when it is `always: true` (reason `always`) or always-on-rework (`always on rework`), its round N−1 verdict is missing (`new this round`) or not `PASS` (`changes requested in round <N−1>`), or one of its `paths` globs matches a file changed between the commit the round N−1 review saw (the sha on that round's `verdicts` event) and HEAD (`paths <glob>: <file>`). Every other lens is skipped and keeps its last `PASS`; the approver's brief lists those carried passes with the round each passed in. A panel entry's **`alwaysOnRework`** makes a lens re-run on every rework round; absent, it defaults to `true` for `security` and `false` for every other name, so a security lens re-reviews each fix even with no `paths` (`alwaysOnRework: false` lets it narrow like the rest). `forge config validate` reports a value that isn't `true` or `false`. Any other lens with only a prose `when` and no `paths` re-runs only when it asked for changes, so give a lens `paths` or `alwaysOnRework: true` if a fix in its area must always bring it back.

There is no narrowing (every lens re-runs) when `onRework` is `full` or any other value, round N−1 has no verdicts or all of them are `PASS` (a human rework), the round N−1 `verdicts` event has no sha, the sha isn't 40 to 64 hex characters or isn't an ancestor of HEAD (history was rewritten), the job has an open PR (`review.onPrFeedback` decides), a reviewed member repo or is a retro job, or the rework panel would be empty or every lens. When it narrows, `forge job panel` returns `rerun` and `skipped`, the `panel` event records `rerun` and `rerunReasons`, and `forge job step` spawns only `rerun` (rule RV10) and records verdicts for those lenses only.

## Open PRs

`forge sync` (and `forge pr sync <id>`) re-reads every open PR. A job parked on `pr-review` or `conflicts` whose PR has moved under it is handled by these keys:

- **`pr.conflicts`** decides a PR that conflicts with its base. `ask` (the default) waits on `conflicts` until you `/forge approve` it. `fix` has `forge sync` move the job to `integrate` itself, where the integrator resolves the conflicts, re-verifies and runs the integration review. `defer` leaves the job on `pr-review` with a note.
- **`pr.updateStrategy`** is how `forge integrate` brings a branch up to date with its base, before a PR and after one is open (`merge` by default, so nothing is force-pushed). A PR that is only behind its base needs no conflict decision, so `forge sync` moves it to `integrate` under every `pr.conflicts` policy, including the default `ask`, and `forge integrate` updates it with this strategy. `merge` resolves conflicts once per integration, never rewrites pushed commits and never force-pushes. `rebase` gives a linear history, but it replays each job commit, can raise conflicts at each one, and rewrites the branch. A rebase that moves a reviewed branch, even without conflicts, is not a clean base merge, so the job goes back to review and costs one review round ([Reviewed head](architecture/job-model.md)). `--strategy` on `forge integrate` overrides it for one run.
- **`pr.integrationReview`** decides whether a conflict resolution gets the one-lens `code` integration review. `code-only` (the default) skips it, with a note on the job, when every conflicted path in the episode, and every path the resolution changed beyond git's own merge of the two sides (commits after it included, up to the verified sha), is docs (`*.md`, `docs/**`) or generated (rebuilt by `forge integrate`, or matching `worktrees.generated`); any other path, an unsafe or malformed name, or a resolution diff Forge can't compute, or a review that already ran in the episode keeps it. `always` reviews every resolution, and so does any other value. The resolution is verified either way.
- **`pr.maxCiReworks`** (an integer ≥ 0, default 3; editable in Settings, 0 to 20) is the **CI rework cap**. With the daemon and the foreman on and `pr-feedback` in `foreman.decides`, `forge sync` turns failing checks on a parked PR into a foreman rework, once per head; a job in a mandate gets it only when that mandate delegates `pr-feedback`, and otherwise the `pr-feedback` gate is queued instead. It counts consecutive CI reworks (foreman `rework` events with a `ciHead`) since the latest event by a person, of any action. At the cap, a further red head starts no rework: the job stays on `pr-review` with the reason `CI rework cap: <n> CI reworks in a row, checks still failing on PR #<n>: <names>. A human decides`, a `ci-rework-capped` event is logged once per head, and no `pr-feedback` foreman gate is queued for that head, so the foreman is refused there too. `<names>` lists at most 5 failing check names that match `^[A-Za-z0-9 ._/-]{1,60}$`; the rest are counted as `and <k> more`, because the PR's own workflows choose them. Any person's action on the job resets the count, and `0` sends every red head to a person.

Both routes have the same guards. The job is not claimed by a live session (the test `forge next` uses, judged inside the job lock), the PR head is the commit Forge pushed (a human push is left alone), and each head is routed once, so a failed integration doesn't loop. Sync never claims the job: with `daemon.enabled` it queues a `resume` for the job's session, and otherwise `forge sync` lists the job under `integrating` for `/forge continue <id>`. `forge pr merge` syncs without routing.

## Merge

`merge.auto: true` (or `foreman.ship: merge` or `release` with the foreman on) lets Forge merge a PR without a person, and `forge pr merge` itself decides whether it may, whoever runs it: the orchestrator through step rule PR4, `forge sync` continuing a deferred merge, or a person without `--now`. Before any CI decision, each PR must pass, in order:

1. **`merge.auto` is on.** Otherwise `reason: auto-off`.
2. **The decision still stands.** Nothing has replaced the approver's last decision: the job is at stage `pr` (a rework that moved it to `build`, a `revise-spec` back to `spec` or any other move out of `pr` replaces it), it is not `cancelled` or `failed` (a cancel keeps the stage) and was not set to either after the last `decision` event, even when a session set it back since, no `round` event comes after the last `decision` event (a round on an open PR with `merge.auto` off skips the approver, step rule DC10, so the only decision on record is the previous round's), no `human` `rework` or `revise-spec` comes after it, a person's or the foreman's (a sync CI rework, a PR-feedback rework), and no `rework`, `revise-spec` or `cancel` request for the job is still in the request inbox, `pending` or `in-progress` (the dashboard's Rework and Cancel queue a request first, and a session records the `human` event only when it handles it, which a busy pool slot or a repo budget hold can delay; a forged request can only block a merge). GitHub feedback that asks for changes replaces it too: no `gate` request for the job is `pending` or `in-progress` (the Foreman has not decided that gate yet; `forge sync` queues a `pr-feedback` one for a PR with feedback in the same pass that continues deferred merges), and no review on GitHub requests changes on any open PR of the job, the root PR or a linked job's member PR, which merge under the one decision (each PR's `changesRequested`, which this call's own sync counts at the live head from the reviews GitHub lists as `CHANGES_REQUESTED`, is 0; a PR GitHub merged or closed counts none; a reviewer's later approval leaves the earlier review as it was, and dismissing it on GitHub clears it). Positions in `events.jsonl` decide, never timestamps. An `approve` or `answer` after the decision replaces nothing, so a protected-paths approval still merges, and a newer decision from the approver run that follows the rework or the round stands again. Otherwise `reason: superseded`, with the rule that matched in `error`.
3. **An eligible recorded decision.** The last `decision` event is an `APPROVE` the approver marked `Auto-merge eligible: yes`, with the head it covers. `forge job decision` records it once per approver run, with the job worktree's `HEAD` (`head`) and each PR member's (`heads`); a later call in the same run, a `decision.md` edited after it, or a second `forge job agent end` changes nothing (an agent's end time moves only when a run that is still running ends, and `forge job set` cannot write `agents`). An `ESCALATE` never auto-merges, even after a human cleared it, and neither does a decision recorded before Forge bound decisions to a head. Otherwise `reason: decision`.
4. **The approved head.** The PR still targets the job's base branch on GitHub (read by this call: GitHub merges into the PR's own base, so a PR retargeted with `gh pr edit --base` would be checked on a diff that does not land). Its live head on GitHub (read by this call, never `job.json`) is the decided head, or that head with only clean merges of the base on top: each such commit's second parent is already on the base and its tree is exactly git's own merge without conflicts. "On the base" means the base branch as the push remote holds it when the merge runs: Forge fetches it into a private ref, never trusting `<remote>/<base>` in the clone, which a job's worktree can move (steps 4 to 6 use the same fetched commit). A base that can't be fetched refuses. A rework commit, a human push, a conflict resolution, a rebase (`pr.updateStrategy: rebase`) or a merge that carries extra changes all wait on a human. Otherwise `reason: decision`.
5. **Protected paths at that head.** Recomputed from git at the live head: a `refuse` hit, or an `escalate` hit whose path and content the job flag does not hold under a human approval, exits 1 with `protected_path`.
6. **The escalate floor.** Whatever `policy.protectedPaths` says, a PR whose diff from its merge-base touches any of these merges only by a person: anything under `.forge/` (in any case), Claude Code's own control files in any repo of the job (a `.claude` directory, `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md` and `.mcp.json`, at any depth, whatever `project.instructions` says), a file `project.instructions` names (for any role), and test, build or CI config as verify's integrity report counts it (CI files of every system below, `Makefile`s, runner configs such as `jest.config.*`, a `package.json` whose `scripts` or test-runner keys changed, a `Cargo.toml`'s dev-dependencies, `.gitattributes`, and every script a `commands.*` entry runs). Every name is folded the way macOS and Windows file systems open it, so `Jest.config.js`, `MAKEFILE` and `agentſ.md` (a long s, which those systems read as `AGENTS.md`) count, and a `package.json` or `Cargo.toml` spelled in another case is a hit whatever it holds. A docs-only change is not on the floor and keeps auto-merging. Otherwise `reason: floor`.

Then CI. A direct merge needs passing checks, or a base with no CI, at a **settled** head: at least 5 minutes after Forge's last `pr-opened`/`pr-updated` event, because a rollup read sooner may not list every check yet. A head that is not the decided one but carries base merges on it must also be 5 minutes past its own commit time, so a merge made on the PR since Forge's push (GitHub's "Update branch") cannot ride an old push. A PR with no Forge push event never settles. Passing checks while GitHub reports the PR `UNSTABLE` count as pending. A base has CI when it holds `.github/workflows/*.yml` (or `.yaml`), anything under `.circleci/` or `.buildkite/`, or a root `.gitlab-ci.yml`, `Jenkinsfile` or `azure-pipelines.yml`. While checks are pending or the head is settling, the merge is queued with GitHub auto-merge when GitHub enforces requirements (`BLOCKED`, `BEHIND`), no protected-paths policy applies and the required checks (below) do not come from `merge.requiredChecks`, and deferred otherwise; `forge sync` then continues it, only while the job is at `pr`, the decision still stands (check 2) and the deferral came after it. Failing checks refuse. A check Forge can't compute (a git error, a missing commit or base) refuses under its own reason, never passes.

**Required checks.** The rollup alone can't tell a fast job that finished first from a slower required one that has not registered yet, and a status or check run with a required name can come from anyone with push access. So the CI decision also needs the PR's **required checks**, each bound to its source. For the root PR they are `merge.requiredChecks` when it is set (protection is then not read); otherwise, and for every member PR of a linked job (the root's key names root checks only), they come from the base branch's protection: its rulesets' required status checks, then the branch's own protection summary, then the admin-only `/protection` read, through `gh api`, at most once per base per `forge pr merge` and never stored in `job.json`.

```yaml
merge:
  requiredChecks:
    - test                                              # any check run named test
    - { name: slow, workflow: .github/workflows/ci.yml } # a check run from that workflow file
    - { name: lint, app: github-actions }               # a check run from that GitHub App
    - { name: deploy/preview, creator: vercel[bot] }    # a commit status posted by that login
```

Forge reads the head's check runs (each with its app and workflow file) and commit statuses (each with who posted it) in one GraphQL read, keeps the latest observation per name and source, and decides each required check from the observations with exactly its name: any failing one (from any source) fails it; any unfinished one keeps it pending; matching observations from more than one source fail it (`ambiguous`: a PR that adds a workflow with the same job name); none from its source keeps it pending (`missing` when nothing has that name, `foreign` when only other sources report it, `status` when only commit statuses do: **a commit status never satisfies a name without `creator`**, since anyone with push access can post one); and the one matching source must conclude `SUCCESS`. **`SKIPPED` and `NEUTRAL` never satisfy a required check**: both are final, so the merge refuses rather than waits (they still pass in the rollup). A protection rule with an app id binds to that app; without one, any check run counts. A read GitHub cut short counts as pending (`incomplete`). Prefer a `workflow:` binding: an unbound name or an `app:` binding is also met by a check run that any Actions workflow of the repo creates through the Checks API on the PR's head (a `workflow_dispatch` workflow on another branch with `checks: write`, say), which only matters while the real check never registers (a `paths` filter, a disabled workflow). A `merge.requiredChecks` that fails validation (`forge config validate`: an unknown key, a `workflow` outside `.github/workflows/`, an `app` that is not a slug, a repeated name) is never partly read: the root PR's merge refuses with `required.state: failing` and `required.note` naming the first problem, so a typo cannot loosen the gate.

A required check that is pending defers (or, when it comes from protection, queues `--auto` where GitHub enforces requirements, as above; checks from `merge.requiredChecks` always defer, since GitHub's own protection does not know them and would land a queued merge without them), even when the rollup reads passing, and a failing one refuses with `required checks are not passing: <name> (<why>), …`. With required checks, an empty rollup passes only when they all pass. With none (`required.source: none`), or with protection Forge could not read (`unavailable`: a token without access, say), the rollup alone decides as before, and the result's `required.note` says so. Every merge result and `pr-merge-deferred` / CI `pr-merge-refused` event without `--now` carries `required: { source, state, blocking, note? }` (docs/CLI.md "Merging"). `forge doctor` and `forge pr open` warn when the base has neither `merge.requiredChecks` nor protection with a required check and a required review, with the `gh api` command that turns protection on, and `/forge init` offers the `pull_request` workflow jobs it finds as `merge.requiredChecks`. The key is locked in the settings: emptying it loosens the merge gate. A support bundle counts its entries and never prints them: a `creator` login can be a person's.

`--now` is a human-only operation: a person confirming at a terminal by typing the job id (or **Merge now** in the dashboard). It skips all of this, check 2 included, never the merge order or a release gate, and is logged as `pr-merge-bypass` with who confirmed it. Every `pr-merged` event says who ran the merge, with or without `--now`: `actor`, plus `scope` (the `FORGE_DAEMON_SCOPE`) when a daemon session ran it and `via: sync` when `forge sync` continued it. A daemon session, an agent, a script or a configured command can't pass `--now` (code `human_only`; docs/architecture/daemon-security.md "Human-only operations"); a daemon session can't merge another job, and is refused when its scope is missing or invalid.

**The backstop no session can change** is GitHub's own branch protection: required reviews and required status checks on your base branches. Forge never turns it on for you; with it on, a misled session or a forged job file still can't land a PR GitHub holds.

## Model profiles

`/forge init` offers three presets for `runtime.models`. The defaults above are not a preset; they predate them.

| Profile | Models |
|---|---|
| Balanced (recommended) | planner, spec-writer, builder, retro, judge `opus`; approver `sonnet`; designer, reviewer, integrator `sonnet`; security lens `opus` |
| Economy | builder and approver `sonnet`; everything else `haiku`, except the security lens `sonnet` |
| Max quality | everything `opus`; spec-writer and builder `fable` if available |

Any profile can add `runtime.diversity: true`. Expect warnings by design where a profile shares families: the Balanced security lens is `opus` like the builder, and Economy and Max quality put the builder and approver on one family. `forge roster` always reports `diversity.overlap`: the approver and every panel lens whose model shares the builder's family (`opus`, `sonnet`, `haiku` or `fable` when the model names one, else the whole model string; `inherit` resolves through `runtime.models.orchestrator`). With `diversity: true`, `forge roster` and `forge init write` also return one warning per overlap. Diversity warns; it never blocks a job.

## Builder model

The builder is most of a job's spend, so it can run a cheaper model where that is safe. For the builder only, the model is the first valid value of:

| # | Layer | When |
|---|---|---|
| 1 | `runtime.reworkModel` | a rework round (2 or later) whose only input is review findings: no failed verify or verifiers, PR feedback, `feedback.md` or answer |
| 2 | `runtime.modelByComplexity[<job's complexity>]` | the spec's `Complexity:` header was recorded |
| 3 | `runtime.models.builder` | always |
| 4 | `inherit` | nothing else is set |

A value counts only when it is a string of letters, digits and `. _ : - [ ]` (as `runtime.models.<role>` takes); anything else is unset and resolution falls through. With both keys null (the default), every builder spawn's model is `runtime.models.builder` as before. The spawn action's `model`, its `start --model` and the roster all come from one resolver. `forge config validate` and `forge doctor` report a `runtime.modelByComplexity` that isn't a map, an unknown key in it, and an invalid value in either key. `forge roster` gives the builder entry `modelBy: { low, medium, high, rework }`, and the Agents page shows each set one under the builder's model. Diversity warnings keep comparing against `runtime.models.builder`.

**Migration** (config `schemaVersion` 20 → 21): nothing changes. v21 adds `runtime.modelByComplexity`, `runtime.reworkModel`, `review.onRework` and a panel entry's `pathsOnly` and `alwaysOnRework`; defaults fill them. `onRework` defaults to `narrow`, so an upgraded repo's rework rounds re-run only the rework panel, while round 1 is unchanged and a `security` lens still re-runs every round (the `alwaysOnRework` name default); set `review.onRework: full` to keep the old behaviour. The bump lets older Forges refuse a config whose builder models and rework panel they would ignore. `forge migrate` writes the new version.

## Effort

Reasoning effort is how much the model thinks before it answers: `low`, `medium`, `high`, `xhigh` or `max`. Higher levels cost more tokens and time. Forge sets it per job, per role and per spec complexity:

- **Precedence.** For an agent of role R in job J, the level is the first valid value of:

  | # | Layer | Source |
  |---|---|---|
  | 1 | J's own effort (`forge job new … --effort <level>`, `forge job effort <id> <level>`, or the drawer's **Effort** button) | `job` |
  | 2 | reviewers only: the lens's `review.panel` entry `effort` | `panel` |
  | 3 | `runtime.efforts.<role>` (`reviewer` for every lens) | `role` |
  | 4 | `runtime.effortByComplexity[<J's complexity>]` | `complexity` |
  | 5 | `runtime.effort` | `config` |
  | 6 | nothing: Forge passes no effort | `none` |

  With nothing set, `daemon.command`'s own `--effort` applies if it has one, and otherwise Claude Code's own setting does. `forge job effort <id> --inherit` clears a job's level. A value outside the five levels counts as unset at every layer and resolution falls through to the next, and `forge config validate`, `forge doctor` and every daemon start refuse an invalid `runtime.effort`. `forge config validate` and `forge doctor` also report a `runtime.efforts` or `runtime.effortByComplexity` that isn't a map, an unknown key in either, a level outside the five, and an invalid panel `effort`; those never stop a daemon start, because they never reach a session's command line.
- **Rework bump.** A builder on a rework round (`round` 2 or later) runs one level above what it resolved to (`low` → `medium` → `high` → `xhigh` → `max`; `max` stays `max`), unless the level is the job's own effort or nothing. Round 1, including a verify-fail retry inside it, is never bumped, and no other role is.
- **Complexity.** The spec writer adds a `Complexity: low | medium | high` header under `Size:`, judged as difficulty, not volume. When the spec is recorded, a valid value (any case) becomes the job's `complexity`; a spec without a valid one clears a complexity an earlier spec set. `forge job set <id> --field complexity=<low|medium|high|null>` sets it by hand and refuses anything else. It only picks among levels a human configured in `runtime.effortByComplexity`.
- **Daemon sessions** start with `--effort <level>` on their `claude -p` command line, replacing any `--effort` in `daemon.command`. A session runs the orchestrator, not a role, so only layers 1, 5 and 6 apply: per-role, panel and complexity levels never reach a session. The inbox session uses `runtime.effort`. Each session's log records the level it started with and where it came from (`job`, `config` or `none`).
- **Agents.** `forge job step` puts each spawn's own level (resolved for its role) on every `spawn` action, and every brief has an `Effort:` line, so the orchestrator, yours or a daemon's, passes it to each agent it starts. The `forge:*` agents set no effort of their own, so without one they inherit their session's.
- **Changing it.** A job's new effort applies to the agents started after the change at once, and to a running daemon session the next time it starts (after an idle stop, a restart, or a slot handover). Forge never stops a session to apply it. Changing `runtime.effort` while the daemon runs is a config change, so the trust check stops the daemon, as for any edit of this file; a job's effort lives in its `job.json` and stops nothing.
- **In the dashboard**, a job's panel header has an **Effort** button beside Permissions, on every tab, which opens a small popover of levels (Inherit shows what it resolves to), a job whose own level differs from `runtime.effort` shows a chip such as "Extra high effort" on its card, in its drawer and on the Agents page, Settings → Agents edits `runtime.effort`, each `runtime.efforts.<role>` and each `runtime.effortByComplexity.*`, and the Agents page's roster and review panel tables show each role's and lens's level with where it comes from (panel entry, role setting or default), before any job's own effort or complexity. While a job's session runs at another level than the one now set, a note in that popover (and the button's tooltip) says it applies to new agents now and to the session when it restarts.
- **A daemon session may not change effort**: `forge job effort` and `forge job new --effort` refuse under `FORGE_DAEMON=1`, and `forge job set --field effort=…` is always refused. Set it from the dashboard or your own session.
- Needs a Claude Code with `--effort` (checked on 2.1.299).
- **Migration** (config `schemaVersion` 3 → 4): nothing changes. v4 adds `runtime.efforts`, `runtime.effortByComplexity` and a panel entry's `effort`, all unset by default; the bump lets older Forges refuse a config whose effort levels they would ignore. Job `schemaVersion` 9 adds `complexity` (null for older jobs).

## Verify groups

An entry in `verify` is a step name or a list of step names; the built-in `secrets` step always runs before the first entry ("Secret scanning"). A list is a group: its steps start together and run at the same time, and the next entry starts only after all of them have finished. Group steps that don't depend on each other's output, typically the checks that follow a build, in one list:

```yaml
verify:
  - build
  - [lint, typecheck, test]
```

A failing step never stops its siblings: each runs to completion and keeps its own log and `command` event, and then no later entry runs. `failure` (and `verifyRuns[].failure`) is the first failing step in config order, not the first to finish, and `verify/round-N.md` and the JSON `steps` keep one entry per step in config order. A step with no command is reported `skipped (no command configured)` in its place, and `e2e` listed anywhere, inside a group too, is not run a second time by `verifyE2e`. Steps in a group share the worktree, the job's `{port}` and the environment, so don't group steps that write the same files (a formatter or `--fix` beside a test) or bind `{port}`. A `verify` of plain step names runs one step after another, as the default `[build, lint, test]` does. `forge verify` refuses to start (exit 1, nothing recorded) when `verify` is not a list, when an entry is neither a step name nor a non-empty list of names (a nested list included), or when a step is listed twice; `forge config validate` and `forge doctor` report the same problems.

**Migration** (config `schemaVersion` 2 → 3): nothing changes, because every v2 `verify` is a valid v3 one, and `forge migrate` only rewrites the version. The bump lets Forge refuse a config it can't read: `forge verify` exits 1 on a `schemaVersion` newer than its own. A Forge older than this change can't tell, so it reads a group as one unknown step (`lint,typecheck,test`), reports it skipped and passes verify without it: update Forge everywhere verify runs before you commit a group.

## Verify integrity

Every `forge verify` on a clean worktree also reports what the committed diff since the merge-base with the base branch did to the tests, in an `## integrity` section of `verify/round-N.md` and a compact `integrity` key in its JSON. Test files are paths matching `evals.testPattern`; when that is null, the built-in default (`DEFAULT_TEST_PATTERN` in `lib/engine/guard/integrity.ts`) matches files under `test/`, `tests/`, `__tests__/`, `spec/` or `specs/`, `*.test.*`/`*.spec.*` (also `-test`, `_spec`, …), `*_test.go|py|rs` and `test_*.py`. The base is `refs/remotes/<git.remote>/<base>`, else `refs/heads/<base>`; a full commit sha or a `refs/…` name in the job's base is used as given, and other revisions (tags, `HEAD~3`) are not accepted. Replace objects and grafts are ignored, and every diff setting the parser depends on is pinned, so repo config written from the worktree cannot change what is read.
- **Deleted test files**: test files that were deleted, renamed out of the pattern, moved where a runner glob may no longer find them (another directory, a different test suffix or extension, or a dropped `test_` prefix: `test/a.test.mjs` → `test/old/a.test.mjs`, `a.test.mjs.off`, `a.test.ts`), or replaced by a symlink or submodule.
- **Renamed test files**: same directory and suffix, new name; informational.
- **Skip/focus markers added**, matched line by line, so the list is what is covered and nothing more:
  - in any file: Rust `#[ignore]`; `pytest.mark.skip`/`skipif`/`xfail` (decorator or `pytestmark = …`), `pytest.skip(`; `@unittest.skip`/`skipIf`/`skipUnless`/`expectedFailure`, `unittest.SkipTest`.
  - in test files only: `describe`/`it`/`test`/`context`/`suite`/`t` with `.skip`/`.only`/`.todo` (also `['skip']`, and a chained `.skip(` starting a line), `.skipIf(`/`.runIf(`, `xit`/`xdescribe`/`xtest`/`xcontext`/`fit`/`fdescribe`, node:test options (`{ skip: true }`, `{ todo: 'why' }`, the `{ skip }` shorthand in a test call, alone on a line, or assigned as `= { skip }`/`= { only }`), mocha `this.skip()`, `self.skipTest(`, Go `t.Skip`/`SkipNow`/`Skipf` and `//go:build ignore` (or `// +build … ignore`) in `_test.go`, JUnit `@Disabled`/`@Ignore`.

  Binary-looking files are scanned for markers too, but not counted. A removed marker line cancels an added one only when their text matches apart from whitespace, so moving or reindenting a skip is not a finding but retitling one is.
- **Test-count delta**: declared tests in the changed test files, before and after.
- **Test, build or CI config edits**: `package.json` `scripts`/`jest`/`mocha`/`ava`, Make and just files, CI config, `Cargo.toml` dev-dependencies, test-runner config, `.gitattributes`, `.forge/config.yml`, and script files the configured `commands` run.
- **Local link overrides committed** (rules R1–R4, see [Local links](#local-links)): an added line holding an absolute path of the root's or a member's worktrees root or of `.forge/jobs` (R1), `FETCHCONTENT_SOURCE_DIR_` (R2), a `[patch` table in a `.cargo/config` or `.cargo/config.toml` at any depth, or such a file committed as a symlink (R3), and a `package.json` dependency, override or resolution added or changed to `file:`/`link:` with an absolute path or one leaving the repo (R4). In-repo forms (`path = "crates/x"`, `file:./packages/x`) are fine. The JSON lists them as `linkOverrides` (`<path>:<line> (<rule>)`).

Under `warn` the report never changes the result; reviewers and the approver read it. Under `block`, a deleted test file, an added skip/focus marker or a committed local link override fails verify (`failure.name: integrity`), and so does a report that cannot be computed (base not found, invalid pattern, or a base that already contains commits the job branch's reflog records as made on it). A deletion is sanctioned, listed as *named in spec* and never blocks, when a line of the spec's `## Approach` makes its exact path the object of delete, remove or drop (``- Delete `test/old.test.mjs` ``, ``- Remove the test files `a` and `b` ``); a move the runner may miss is sanctioned the same way by ``- Move `test/a.test.js` to `test/a.test.ts` `` (or rename … to/into …; a `to` ending in `/` keeps the file name). The path must end the clause: ``Remove `x` from the lint glob``, ``Drop `x` coverage of …`` or ``Remove the `x` case`` sanction nothing. A mere mention, any line with a negation (not, n't, never, keep, avoid, without, leave, cannot), a rename out of the pattern or a type change is never sanctioned. For any other legitimate skip or deletion, the human escape is `verifyIntegrity: warn`. The mode is always read from the main checkout's config, so a job that edits `.forge/config.yml` cannot switch it off.

Verify's clean check also fails, in either mode, when the files on disk can differ from HEAD without `git status` showing it: assume-unchanged flags, a skip-worktree file that is still on disk, or one missing from disk that no sparse checkout leaves out (paths outside a cone-mode sparse checkout are fine; with non-cone or malformed patterns only files that are not tests or test config may be missing), or a clean/smudge filter that changes a test or test-config file on checkout (the standard git-lfs filter is trusted; Forge's eval checkouts sparse-exclude only `.forge/evals/`). If that check itself cannot run, the report becomes an integrity error (fails `block`, printed under `warn`). In the verify JSON, `integrity` is `null` when the worktree is unclean (no report is computed) and `{ "mode", "ok", "error" }` when the report cannot be computed.

## Eval overlays

`forge eval start --set <key>=<value>` (repeatable) runs one eval run under a variant of this file without writing it, so an A/B comparison needs no config edit and never trips the daemon's trust check. The keys allowed are `runtime.models.<role>` (every role but `orchestrator`, whose model no job session reads), `runtime.effort`, `runtime.efforts.<role>`, `runtime.effortByComplexity.<level>`, `runtime.modelByComplexity.<level>`, `runtime.reworkModel`, `review.onRework`, the `pipeline.*` settings (`plan`, `split`, `specApproval`, `design`, `maxRounds`, `budget.*`), `review.panel` (built-in or repo lens names; no `checklist` path) and `verify` (at least one step, each a key in `commands`). Every other key, `commands.*` included, is refused. Values are checked as `forge config set` checks them, and the overlaid config may add no `forge config validate` problem. The overlay is recorded on the run and on each eval job (`eval.overlay`, which `forge job set --field` can't write), checked again whenever a command loads that job, and applied only to that job's `job step`, `job advance`, `verify` and budgets. The run's `configHash` covers it; an empty overlay hashes as before. A daemon session may not pass `--set`.

## Secret scanning

Forge refuses to publish a likely credential, and the check lives in its own code (`lib/engine/guard/secrets.ts`), not in a prompt. The scanner has no dependencies and runs wherever Forge sends something off the machine:

| Gate | What it scans | On a finding |
|---|---|---|
| `forge verify` | a `secrets` step before the first configured group, clean worktree or not: every non-merge commit in `merge-base..HEAD` on its own (a key added and deleted later is still found), each merge commit's own changes (`git show --remerge-diff`: a conflict resolution, which no ordinary commit holds), the net diff (what a merge brought in), every commit message, and the staged changes | `block`: the step fails, no configured group runs, the integrity report is still computed. `warn`: the step passes with a reason |
| `forge git commit` | the message, before anything is staged; then the staged diff against HEAD | the message: always refused. Staged content: refused under `block` (the index stays staged), committed under `warn` with `secrets: <n>` in the result |
| `forge pr open` | the PR title and body exactly as Forge would send them, before any `gh` call or push, even when the PR exists; then the commit range (commits, messages, net diff) of the HEAD it pushes, verified or not (`--force` skips verify, and a HEAD verified by a Forge without the scanner was never scanned), after fetching the base from the remote's push URL into its remote-tracking ref, but only when a fetch of that URL would reach it too (git applies one `url.*.insteadOf` rewrite per resolution, so a chained rewrite would send the fetch elsewhere) | the text: always refused. The range: refused under `block`, and so is a base fetch that fails or a push URL that `insteadOf` rewrites again; under `warn` either skips the fetch and scans against the ref as it is |
| tracker writes | `comment` bodies and `create` titles and bodies, in every adapter (`forge tracker comment\|create`, `forge job link --create`, `job human … --link new`, the split procedure); a custom adapter's `update`/`claim` also have the job's title and reason scanned | always refused |
| `forge job agent end` | the role's output, its extras (builder: `build.md`, `tasks.md`; integrator: `build.md`; approver: `pr.md`, `runbook.md`; designer: `mockup.html`; retro: `spec.md`) and `questions.md`, when written since the agent started and a regular file inside the job dir | never blocks: a `secret-found` event, and `secrets: <n>` in the result |

A refusal exits 1 with error code `secret_found` and a one-line message such as `possible secret in the PR body: aws-access-key at (pr body) line 3 (AKIA…XY, sha256:<64 hex>)`, plus how many more, and never calls the adapter, `gh` or `git commit`. `forge secrets scan <id>` shows what a job would publish, and `forge secrets scan --paths <globs>` scans the main checkout's tracked files (untracked files and symlinks are left out, files over 2 MiB are counted as skipped); both exit 1 on a finding.

**What counts.** Provider patterns, each a kind: `private-key` (a PEM `PRIVATE KEY` block with at least 64 base64 characters, split over lines or written with literal `\n`, reported once at its first line), `aws-access-key`, `github-token`, `github-pat`, `gitlab-token`, `slack-token`, `stripe-live-key` (test keys are not), `anthropic-key`, `openai-key` (its body has a digit), `google-api-key`, `bearer-token` (an `Authorization: Bearer` header with a token of 20+ characters) and `url-credential` (`password=`/`token=`-style query values and `scheme://user:pass@host`). An `sk-ant-` key is only ever `anthropic-key`. Then `high-entropy`: a value of 33 to 256 characters of `[A-Za-z0-9+/_=-]` inside quotes or backticks, or after `name =`. A hex value (all lower- or all upper-case) needs at least 3.0 bits of entropy per character and a secret word on its line (`secret`, `token`, `passw`, `pwd`, `api_key`, `private_key`, `credential`, `auth_token`, `access_key`, `signing_key`, …); any other value needs at least 4.3 bits and an upper-case letter, a lower-case letter and a digit. SRI hashes (`sha512-…`), UUIDs, slugs, paths, values over 256 characters and anything of 32 characters or fewer are never flagged by the entropy check. Last, `known-secret`: an exact occurrence of one of the job's [known values](#secret-references), in the branch scan (verify, `forge pr open`, `forge job interim publish`), the staged scan of `forge git commit`, the PR text and every gate that names a job. A declared secret is never a false positive: the allowlist never allows a `known-secret`, and it blocks under `warn` too, so a `.gitignore` edited around a rendered file and a `git add -f` still can't publish it. A known value can be short, so its finding shows `<known>` instead of a masked excerpt and `known:<12 hex>` (keyed by a random per-process key, only to dedupe) instead of its sha256, which could be brute-forced.

**Where only provider patterns run.** Lockfiles (`package-lock.json`, `yarn.lock`, `Cargo.lock`, `go.sum`, …), `*.min.js`, `*.min.css`, `*.map`, `*.svg`, paths matching `worktrees.generated`, files whose added content holds a NUL byte, and the text Forge sends (commit messages, PR title and body, tracker text), where prose often quotes hashes and the gates refuse outright.

**Placeholders are not findings:** an env reference (`${X}`, `$X`), a `<…>` or `{{…}}` value, a value with fewer than 5 distinct characters, one containing `example`, `placeholder`, `dummy`, `redacted`, `changeme`, `xxxx`, `****`, `your_` or `your-`, and one that is exactly a stock word such as `password` or `token`.

**Masking and fingerprints.** A finding shows the first 4 and last 2 characters of a value of 16 or more (`AKIA…XY`), the first 2 of one of 8 to 15 (`hu…`), and nothing of a shorter one (`…`); a backtick, `|`, whitespace or control character in what is shown becomes `?`. The full value is never printed, logged, written to a file or put in an event. Each finding carries `fingerprint`: `sha256:` and the hex sha256 of the full value (of a PEM key, its body without whitespace). The fingerprint is not secret material and appears in output, errors, verify files and events.

**Allowlist.** `.forge/secrets-allow.txt`, read from the main checkout only: a copy in the job's worktree, or committed on its branch, is ignored, and a daemon session can't edit it (it is in the trust digest and denied to `Edit`; see docs/architecture/daemon-security.md). A branch that edits it shows up as a config edit in the integrity report. One entry per line:

```text
# Comments and blank lines are ignored; a comment takes its own line.
# A path glob (forge job scope matching) allows repository content only:
test/fixtures/**
# A fingerprint allows that value anywhere:
sha256:<64 lower-case hex>
```

A path glob never allows text: commit messages, the PR title and body, tracker text and job-dir files need the fingerprint. A malformed `sha256:` line or a `!` line is listed as a problem and ignored; a symlinked allowlist allows nothing. An allowed finding is listed with the line that allowed it (`allowedBy: .forge/secrets-allow.txt:<line>`).

**Modes.** `verifySecrets` covers content: verify's branch scan, the staged scan in `forge git commit` and the range scan in `forge pr open`. Text Forge composes and sends is refused in either mode. The mode always comes from the main checkout's config, and any value other than `warn` counts as `block`. A scan that cannot finish (base not found, a git failure, more than 1,000 commits) fails under `block` and passes with `error` under `warn`; it never reads as clean.

**The human gate.** When verify fails on `secrets` (in the verify, integrate or pr stage) and no builder or integrator has run since, or `forge pr open` was refused, `forge job step` parks the job on `waitingOn: human` with the reason `secret scan blocked verify round <n>` or `secret scan blocked pr open` (an eval job fails instead). No agent retry gets past it. A human removes the value (and rewrites the branch if it was committed; Forge never amends, rebases or force-pushes for it) or allowlists it, then `/forge approve <id>`: step runs the scan again and parks the job again if the value is still there. `/forge rework <id> <note>` sends it back to build.

**Residual risks.** A secret split across strings or lines, or encoded (base64 of a token, compressed or binary formats), is found only if the entropy check happens to catch it. An evil merge whose content a later commit deletes is not seen. The sha256 of a short `password=` value can be guessed offline from its fingerprint. A key in a UTF-16 file (NUL-interleaved text) gets only the provider patterns, which can't match it. A file the branch routes through `filter=lfs` is scanned as its pointer, while a push outside Forge uploads the real content. Verify compares against the base's remote-tracking ref as the checkout has it, which the job's worktree can move with `git update-ref`. `forge pr open` first fetches the base into that ref from the remote's push URL, when git would fetch that URL from the same place (it resolves the URL once more through `url.*.insteadOf`, as a fetch would, and compares). Under `block` a chained rewrite or a failed fetch refuses to open the PR; under `warn` the fetch is skipped or fails and the scan uses the ref as it is. So under `block` the range it pushes is scanned against the base the push target reports at that moment; a push target that lies about its own base branch is out of reach. Regex false positives happen; the allowlist handles them. Forge does not revoke or rotate a leaked credential.

## Protected paths

Paths are code, judgement calls are prose. `approver.alwaysEscalate` is prose a model reads after the build; `policy.protectedPaths` is the part that can be said as paths, and the CLI enforces it when a change is staged or committed, re-checks it over the whole branch before anything is pushed, and records each decision as a `protected-path` event. `approver.alwaysEscalate` stays as the backstop for what paths can't express.

**Rules.** Each rule is `{ paths: [glob, …], action: escalate | refuse, reason: "<text>" }`, numbered from 1 in list order. Messages name a rule as `rule <n> (<glob that matched>): <reason>`. When a path matches both actions, `refuse` wins; within one action, the first matching rule is named. The defaults are the list above. `policy.protectedPaths: []` turns the policy off. The policy is read from the main checkout's `.forge/config.yml` only, never from the job's worktree, and `.forge/config.yml` itself is a refuse default. It is read-only in the dashboard and `forge config set` (`names what Forge refuses to write`).

**Instruction files.** The default list ends with rule 8, an escalate rule for `**/AGENTS.md`, `**/CLAUDE.md`, `**/CLAUDE.local.md`, `.claude`, `**/.claude/**` and `.mcp.json`: the files Claude Code loads into every session whatever a brief says ("Instruction files"), the settings and skills of a nested `.claude/` directory included, so a branch that changes one needs a human. It is appended last, so rules 1–7 keep their numbers. A config without a `policy` key, and a new `forge init`, get it. A config with its own `policy.protectedPaths` list keeps that list exactly as written: no migration or re-init adds the rule. `forge doctor` warns (`protected instruction files`) when a non-empty list leaves `AGENTS.md`, `lib/AGENTS.md`, `CLAUDE.md`, `CLAUDE.local.md`, `.claude/settings.json`, `lib/.claude/skills/x/SKILL.md` or `.mcp.json` unmatched; add the rule by hand:

```yaml
policy:
  protectedPaths:
    # … your rules …
    - paths: ['**/AGENTS.md', '**/CLAUDE.md', '**/CLAUDE.local.md', .claude, '**/.claude/**', .mcp.json]
      action: escalate
      reason: "agent instructions and Claude Code settings: every session reads them"
```

**Matching** is `forge job scope`'s: an exact path, a directory prefix, `**` crossing directories, `*` and `?` within one segment, and a slash-free glob or bare name matched against the basename too (`package-lock.json` matches `web/package-lock.json`). Paths and globs are lowercased first, so `.GitHub/Workflows/ci.yml` matches `.github/workflows/**`. A path counts when its content, mode or existence differs between the comparison point (the merge-base of the base with HEAD, or with `MERGE_HEAD` while a merge is in progress, so the base's own changes never count) and the result being checked. A rename counts as a delete of the old path and an add of the new one, and both are matched. A symlink or submodule also matches when its target does, or when its path is a leading directory of a rule's glob (a symlink named `.github`). A symlink whose target can't be read, or is longer than 4 KiB, is refused (`link target could not be checked`).

**Where it is enforced.**

| Gate | refuse | escalate |
|---|---|---|
| `forge git add\|commit` | previews the index the call would produce (a temp copy, removed after) and exits 1 with `protected_path`, writing nothing, when a path the call changes differs from the comparison point. Putting a path back to its comparison-point content is allowed, so a refusal verify reports stays fixable | goes ahead, records the job's flag and prints `protected: <n>` |
| `forge verify` | a `protected` step right after `secrets` fails (`failure: protected`), and no configured command runs | the step passes with `<n> protected paths need a human` and records the flag |
| `forge pr open` | exits 1 with `protected_path` before any `gh` call or push, `--force` included | recomputes the set (it never trusts the stored flag) and exits 1 with `protected_path` until a human approved it |
| `forge pr merge` | recomputes the set at the PR's live head and exits 1 with `protected_path`, unless a person confirming at a terminal (or the dashboard) merges with `--now` | recomputes the set at the live head and exits 1 with `protected_path` unless the flag holds every path at that content under a human approval; `--now` only from a person confirming at a terminal (or the dashboard) |

**Member repos.** A job's [member repos](architecture/job-repos.md) get the same rules at the same gates, each over its own branch from its own base: `forge git add|commit --repo <name>` previews the member's index, and verify's `protected` step and `forge pr open` check every non-verify-only member's branch. A member's paths are named `<repo>:<path>` in messages, events and the one job flag, and its patch sits under a `# repo <name>` line in `protected.diff`, so one human approval at PP1 covers every repo, and a refusal or a missing approval in any repo stops `pr open` before anything is pushed.

**Approval.** The flag (`job.protectedPaths`, written by the CLI only; `forge job set` refuses it) holds the escalate paths with their blob ids (up to 200, the rest counted, with a digest over all of them) and `at`, which moves only when a path or its content is new; past 200 paths, any change to the set moves it. `forge job step` parks the job on `waitingOn: human` with the reason `protected paths: <paths>` (rule PP1) in `decide`, even after an `APPROVE`, and in `pr`, and never auto-merges it (PR4). `forge pr merge` recomputes the set at the PR's live head (see [Merge](#merge)), so neither a stale flag nor `protectedPaths: null` waives a hit, and while the policy has rules it defers instead of queueing GitHub auto-merge. Only a human `approve` given at that park after `at` counts: a foreman decision, an approve at another gate, or one older than the last content change doesn't. The approver's brief names the paths, and `protected.diff` in the job dir holds the patch of every one of them (capped at 1 MiB). A refusal at verify (PP2) or pr open (PP2b) sends the job back to build.

**An invalid policy fails closed:** `forge git add|commit` and `forge pr open` exit 2 with `config_invalid`, and verify's `protected` step fails. Valid means `policy` is a map, `protectedPaths` a list, each entry a map whose `paths` is a non-empty list of relative globs (no `..` segment, not starting with `-`, `!` or `:`), `action` is `escalate` or `refuse`, and `reason` is 1 to 200 characters with no newline. `forge config validate` lists each problem.

**Migration** (config `schemaVersion` 5 → 6, job `schemaVersion` 9 → 10): nothing changes on disk. A config without `policy` gets the defaults, so after upgrading, a branch that changes a lockfile parks on a human and one that changes `.forge/config.yml` is refused; write an explicit `policy:` block on the base branch to change that.

## Command environment

`forge verify` runs code the branch wrote before any reviewer reads it, so every configured command gets an allowlist of the environment Forge runs with, never the whole of it. The rules are the same in and out of the daemon, and cover `forge run`, verify steps and verify's e2e, worktree setup and the seed's setup and warm commands, `forge run --background`, config-sink commands, job database builds, checkout steps, `forge integrate`'s rebuild, `forge eval grade`'s check and `notify.command`.

**What passes.**
- Exact names: `PATH` (sanitised, below), `HOME`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `LANGUAGE`, `TZ`, `TMPDIR`, `TEMP`, `TMP`, `TERM`, `COLORTERM`, `NO_COLOR`, `FORCE_COLOR`, `CI`, `GIT_CONFIG_COUNT`, `GIT_EDITOR`, `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `XDG_CONFIG_DIRS` and `XDG_DATA_DIRS`. On Windows also `SYSTEMROOT`, `SYSTEMDRIVE`, `WINDIR`, `COMSPEC`, `PATHEXT`, `USERPROFILE`, `USERNAME`, `USERDOMAIN`, `HOMEDRIVE`, `HOMEPATH`, `APPDATA`, `LOCALAPPDATA`, `PROGRAMDATA`, `PROGRAMFILES`, `PROGRAMFILES(X86)`, `PROGRAMW6432`, `COMMONPROGRAMFILES`, `COMMONPROGRAMFILES(X86)`, `COMMONPROGRAMW6432`, `NUMBER_OF_PROCESSORS`, `PROCESSOR_ARCHITECTURE`, `OS` and `MSYSTEM`.
- Families: `LC_*`; `GIT_CONFIG_KEY_<n>` and `GIT_CONFIG_VALUE_<n>` (the git pins of a [daemon](#daemon) session); `NODE_*` except `NODE_OPTIONS`, which can load any file into node; `FORGE_*` except the internal variables below.
- The names `commandEnv.inherit` lists.
- **Never, whatever matches:** the daemon markers (`FORGE_DAEMON`, `FORGE_DAEMON_*`), an outer job's `FORGE_PORT_*`, `FORGE_ENDPOINT_*` and `FORGE_BACKING_*`, `FORGE_COMMAND_PATH` and `FORGE_COMMAND_PATH_SOURCE`, and the source variable of every declared `env` secret, even when an `inherit` entry names it. A declared secret reaches a command only through its sink ([Secret references](#secret-references)).

Everything else is dropped: `GH_TOKEN`, every `AWS_*` (`AWS_REGION` and `AWS_PROFILE` too), `SSH_AUTH_SOCK`, `DATABASE_URL`, proxies, `JAVA_HOME`, `BASH_ENV`, `ENV`, `ZDOTDIR`, `XDG_RUNTIME_DIR`, `GIT_DIR`, `GIT_SSH_COMMAND`, `npm_config_*` and any name nobody listed. Forge then adds the job's own variables, unfiltered: `FORGE_JOB`, `FORGE_WORKTREE`, `PORT`, `FORGE_PORT`, the job's backing and endpoint variables, config-sink `env`, link `env` and `notify.command`'s `FORGE_NOTIFY_*`. So a sink `env: { DB_PASSWORD: … }` still reaches its command. On native Windows names compare in any letter case (`Path`, `SystemRoot`, `java_*`), keeping their own spelling; elsewhere they compare exactly.

**Credential-like names.** A family or a glob never passes a name that, in any letter case, ends `_TOKEN`, `_KEY`, `_PAT`, `_PASS` or `_PWD`, contains `PASSWORD`, `PASSWD`, `ACCESS_KEY`, `APIKEY` or `AUTHTOKEN`, has `SECRET` at its start or after `_`, or has `AUTH`, `JWT`, `COOKIE`, `SESSION`, `CREDENTIAL` or `CREDENTIALS` as a `_`-separated word (1Password's `OP_SESSION_<account>` too). `DOCKER_AUTH_CONFIG`, `NETRC`, `KUBECONFIG` and `GH_CONFIG_DIR`, which point at credential files, count as credential-like too. So `NODE_AUTH_TOKEN` never passes through `NODE_*`, `inherit: [APP_*]` does not pass `APP_SECRET_KEY` or `APP_SESSION`, `DOCKER_*` passes `DOCKER_HOST` but not `DOCKER_AUTH_CONFIG`, and `npm_config_*` does not pass npm's `npm_config_//<registry>/:_authToken`. An exact `inherit` name, with no `*`, always passes.

**`commandEnv.inherit`** is a list of names that commands get as well. `*` matches any run of characters, and an entry matches the whole name: `JAVA_*` passes `JAVA_HOME` but not `MY_JAVA_HOME`. An entry uses only letters, digits, `_`, `(`, `)` and `*`, with at least one character that is not `*`: a bare `*` would pass the whole environment, so it is refused. Credentials belong under `secrets` with a config sink, never here.

```yaml
commandEnv:
  inherit: [JAVA_HOME, "ANDROID_*", DATABASE_URL]
  loginShell: false
```

**Shell.** Commands run as `/bin/sh -c <cmd>`, and on native Windows as Git for Windows' `sh -c <cmd>`, so no login profile, `.zshenv`, `BASH_ENV` or `ENV` file is sourced, whatever `$SHELL` is. **`commandEnv.loginShell: true`** runs them as `$SHELL -lc <cmd>` instead (`/bin/sh` when `$SHELL` is unset), in and out of the daemon: your profile then runs in every command and can export what the allowlist dropped. The daemon honours it because `.forge/config.yml` is reviewed by a human and a command template could source a profile anyway. `notify.command` always runs `-c`. Both keys are read-only in Settings and in `forge config set`.

**PATH.** Commands get `FORGE_COMMAND_PATH` when Forge has one, else Forge's own `PATH`, with empty and relative entries (`.`, `./node_modules/.bin`, `bin`) and later repeats removed: a relative entry resolves in the worktree, where the job's own code could plant a binary. With neither, a command gets no PATH. `forge dash` (the foreground server, its `--background` child and `--dev`) captures the login shell's PATH once at start: it runs `$SHELL -lc` in your home directory with stdin closed and a 5 s timeout, reads the PATH it prints between two marker lines (profile output around them is ignored), puts this plugin's `bin/` first and keeps the result in `FORGE_COMMAND_PATH` for its own process and its sessions. So a dashboard started from a GUI terminal or launchd still finds the `node` that nvm adds in your profile. When the capture times out, exits non-zero or prints no PATH, Forge uses its own PATH, sanitised the same way; on native Windows nothing is spawned. Outside `forge dash` (your terminal, an interactive orchestrator session) nothing is captured and commands get the `forge` process's own PATH, which in a Claude Code session is what its Bash tool built from your profile.

**What doctor and init report.** `forge doctor` adds `command PATH`, naming where the PATH came from (`login-shell (<shell>)`, `inherited: <reason>` or this process's PATH) and warning on a failed capture or a dropped relative or empty entry, and `command environment`, warning with the names (never the values) your environment exports that commands do not get and that look like build settings: `JAVA_HOME` and other `*_HOME` and `*_ROOT` names, proxies, `NODE_OPTIONS`, `CC`, `CFLAGS` and the like. `SSH_AUTH_SOCK`, `DATABASE_URL` and `REDIS_URL` get a clause of their own, because they carry credentials: inherit one only if a command needs it, or declare a secret with a config sink. A [support bundle](CLI.md#support-bundle)'s `doctor.json` names only the fixed names and counts the other `*_HOME` and `*_ROOT` names, which can say what a machine has. `forge init` suggests `commandEnv.inherit` from the names a root `.env.example`, `.env.sample` or `.env.template` assigns (without credential-like names, `PORT` and what passes anyway), plus `JAVA_HOME` for a Gradle or Maven repo and `ANDROID_HOME` and `ANDROID_SDK_ROOT` for an Android build.

**What it does not cover.**
- `forge release run` keeps its caller's whole environment and `$SHELL -lc`: its publish steps need your registry credentials, it is refused under the daemon, and each publish step asks first.
- `HOME` passes, so code a command runs can still read dotfile credentials (`~/.aws/credentials`, `~/.config/gh/hosts.yml`, `~/.npmrc`) or start a login shell of its own. Only an OS sandbox would stop that; keep production credentials out of the account Forge runs as.
- A name you put in `inherit` exactly passes, whatever it holds, and `loginShell: true` re-sources your profile in every command.
- One machine dashboard serves every registered project, so every project's daemon sessions and commands start from the environment of the shell that started it, not from the project's own shell: a direnv export or a project's `DATABASE_URL` set only in that project's shell never reaches them, and one set in the dashboard's shell reaches every project (through `inherit` for commands, and for sessions everything but the API and provider keys). `forge dash` run in a second repo reuses the running server and adds nothing to its environment. Start the dashboard from a shell that holds nothing one project would not want another's sessions to see.

**Migration** (config `schemaVersion` 31 → 32): nothing changes on disk, and `commandEnv` comes from the defaults, so after upgrading every repo's commands get the allowlist: a command that read `AWS_REGION`, a proxy or `JAVA_HOME` from your environment needs it in `commandEnv.inherit`, which `forge doctor` suggests.

## Daemon

With `daemon.enabled: true`, `forge dash` supervises headless orchestrator sessions, so requests queued from the dashboard get handled without a Claude Code window open: one **inbox** session for requests without a job (`next`, `run`, `sync`, `retro`, `eval-run`), which only does intake and hands each new job off, and one session **per job**, started when that job has work. With `foreman.enabled: true` the pool also holds the office session and the Foreman's assistant foremen, which decide parked gates (see [Foreman](#foreman)). Whenever a session's pending requests change and it is idle, it gets one fixed turn, `/forge requests`, on stdin; the session claims and handles them exactly as yours would, seeing only its own scope's requests. Each session fails, idles and logs on its own. They spend tokens unattended, under the permissions `allowedTools` grants, so the daemon is off by default.

While the daemon runs, `forge dash` also runs `forge sync` itself every 2 minutes (one at a time, as you), so CI results, PR feedback and conflicts reach the job sessions and the [Foreman](#foreman) without anyone syncing (docs/architecture/daemon.md "Periodic sync"). With `foreman.enabled` it also runs the Office pass (`forge office pass`, one at a time, as you) at start, when a mandate changes or a mandate job settles, and every `foreman.cadence` minutes, which enforces each mandate's contract and wakes the office session when there is work to start ([Mandates](#mandates) › Enforcement; docs/architecture/daemon.md "Periodic Office pass").

- **`command`** is split into argv like a shell would split words (whitespace; `'…'` literal; `"…"` with `\"` and `\\`), then run directly, with no shell: no pipes, globbing, `$VARS` or `~`. Its first word must be a bare `claude` (found on PATH) or an absolute path to `claude` outside the repo; relative paths are refused because the session runs with the repo as its working directory. This catches mistakes; it isn't a security boundary: whoever can edit this file can run code through the daemon (docs/architecture/daemon-security.md), so give the `daemon` keys code-owner review. The session's PATH starts with this plugin's `bin/`, so its `forge` is the same version as `forge dash`'s. Placeholders expand after splitting, so each stays one argument even with spaces in it:
  - `{pluginRoot}`: this plugin's directory. Pass it with `--plugin-dir` so the session has the `/forge` skill and the `forge:*` agents; `--resume` doesn't restore it, so it is passed on every spawn.
  - `{session}` (required, as its own word): `--session-id <uuid>` for a new session, or `--resume <uuid>` to continue the stored one after a restart or an idle stop.
  - `{allowedTools}`: the `allowedTools` list joined with commas, as one argument.
  - Anything else in braces is left as is.
  - `--effort` in `command` is allowed, but Forge replaces it whenever a job or `runtime.effort` sets a level (see [Effort](#effort)).
- **`allowedTools`** must include `Agent` (every role runs as a subagent), and entries can't contain commas. Subagents inherit the list. List bare `Edit` and `Write`: at spawn Forge drops every file tool (`Edit`, `Write`, `MultiEdit`, `NotebookEdit`) and, when the list had one, scopes writes to the job folders (`.forge/jobs/`) and every worktrees root, so a write anywhere else (the rest of the checkout, `~/.ssh/config`) becomes a permission prompt, and the write guard hook refuses it. Validation refuses an entry that scopes a file tool itself (`Edit(//**)`, `Write(~/**)`, `Edit(src/**)`) or names an MCP tool (`mcp__…`); MCP tools are allowed per call from the dashboard. A `worktrees.root` that is the checkout or contains it (`..`), or lies inside `.forge/` or around a protected file, stops the daemon from starting. A tool call it doesn't cover is sent to you: see **Permission prompts** below. The default allows Bash only for `forge` and the git/gh forms the skill and agents name: `rev-parse`, aborting a merge or rebase, and reading PRs and CI runs. Everything else goes through `forge`: staging and committing (`forge git add <job> -- <paths>` and `forge git commit <job> --message …`, which run git in the job's worktree, because the session's cwd is the main checkout, where a bare `git add`/`git commit` would land on the base branch; they take no git options and refuse paths outside the worktree), checks (`forge run`, `forge verify`, so build tools need no entry), pushes, PRs and tracker writes, history reads (`forge git diff|log|show|range-diff`, which refuses `--output`, `--ext-diff`, `--textconv` and `--open-files-in-pager` and forces external diff and textconv off, because `git log --output=.git/config` could rewrite git config), and starting and finishing a merge or rebase (`forge integrate --keep-conflicts` / `--continue`; `--continue` refuses a rebase todo with anything but picks). Validation refuses entries that reach arbitrary execution, file writes or GitHub writes on their own: unscoped `Bash`/`Bash(*)`, `git` or `gh` with no subcommand, `git -…` (`-c`), `git config|grep|submodule|bisect|difftool|mergetool|filter-branch`, `git diff|log|show|range-diff|whatchanged|format-patch` (`--output`), `git mv` (a `x/../.git/…` destination is renamed even though git reports it invalid), `git rebase` other than `--continue|--abort|--skip` (`--exec`), and `gh api|extension|alias|auth|secret|codespace`. That list catches the known forms; it is not exhaustive, so add any other `Bash(<cmd> <sub>:*)` entry deliberately. The list replaces the default as a whole, so write every entry you want. Older defaults also listed `Bash(git status|add|rm|commit:*)`; they still validate, but in a daemon session they act on the main checkout, so drop them.
- **Flags `daemon.command` may not pass**, because they widen the session past `allowedTools`: `--dangerously-skip-permissions`, `--allow-dangerously-skip-permissions`, `--permission-mode` other than `default` (or `manual`, the name current Claude Code lists for it), `dontAsk` or `plan` (so no `bypassPermissions`, `acceptEdits` or `auto`; a human can still put one session in `auto` from the dashboard, see **Permission mode per session** below), `--settings`, `--mcp-config`, `--add-dir`, `--permission-prompt-tool` (Forge passes its own), `--max-budget-usd` (Forge passes its own from the job's dollar budget; see **Dollar cap per spawn** below), `--agents`, a `--plugin-dir` other than `{pluginRoot}`, and `--allowedTools`/`--allowed-tools` with anything but `{allowedTools}`. Both `--flag value` and `--flag=value` are checked. claude reads `--allowedTools` and `--plugin-dir` values variadically, so a bare word right after their value (other than `{session}`) is refused too: it would become one more tool or plugin dir.
- **Permission prompts.** Forge appends `--permission-prompt-tool stdio` to every daemon command, so a tool call outside `allowedTools` (a `cp` in a worktree, a folder outside the checkout, a compound command) reaches the supervisor instead of failing. Under the default `--permission-mode default`, the session waits while the dashboard shows the call in the status bar's Needs-you popover and in the job drawer's dock: the tool, its exact input, the agent's own description of it (untrusted text), and any path outside the session's folders. **Allow once** runs it. **Allow for this session** also adds the rules and folders Claude Code suggested, for that session only: they are never written to a settings file, and they end when the session restarts. A suggestion that would allow a tool's every call (a bare `Bash`, or a wildcard-only pattern) is dropped, so a session grant is only ever a pattern you read, such as `Bash(cp:*)`. The input shown is exactly what an allow runs, never cut short: a call whose input is over 4,000 characters is denied unasked. **Deny** returns a fixed message telling the agent not to retry or work around it. Nothing you type reaches the session; only your choice does. A prompt nobody answers waits as long as the session runs, and goes away when it stops. With `--permission-mode dontAsk`, nothing is ever asked: anything `allowedTools` doesn't list is refused, as the old default did. A session holds at most 20 prompts; more are denied unasked. Allowing a call is a real grant: read the command, and expect protected paths (`.git/`, `.claude/`) and commands prefixed with variables to show up here too, because `dontAsk` refused them outright.
- **Permission mode per session.** Each session (a job's panel header, on every tab, or the Inbox session log in the status bar's Inbox popover) has a **Permissions** button, which opens a small popover with one choice per mode: **Ask** (`default`: prompts as above), **Auto** (Claude Code's `auto` mode: its classifier approves routine calls on its own and still sends risky ones to you as prompts) and **Refuse** (`dontAsk`). While a session is in Auto, a warning icon sits beside its Permissions button, and hovering, focusing or tapping it shows the reminder to switch back to Ask when you stop watching. It starts at `daemon.command`'s mode. A change applies at once to a running session, through Claude Code's `set_permission_mode` control request, and the log records claude's confirmation; a session that isn't running starts in it. The choice is held by `forge dash` in memory only, never in a file (a session can write files in the repo, so it could otherwise pick its own mode), so it lasts until `forge dash` stops, and the Workers popover names the mode on the rows of the job sessions you switched. If claude refuses a switch or doesn't confirm it within 15 seconds, the log says why. A switch to a wider mode (`auto` isn't available on every account or model) falls back: the button shows the mode the session still runs in. A switch to a narrower mode stops the session instead, and it starts in the mode you chose with its next request, so a session never keeps more reach than you picked. `bypassPermissions` and `acceptEdits` are never offered. `daemon.allowedTools`, the `.forge/config.yml` deny rules and the trust check apply in every mode.
- **Default for job sessions.** The Workers popover's **Job sessions' permissions** picks a mode for every job session without its own choice: the running ones switch at once, as if each were switched one by one, and the rest, including jobs created later, start in it. A job's own choice in its panel header overrides it, and stays when the default changes again; choosing the default's mode in a job's panel header drops that job's own choice, so it follows the default again. The inbox, office and assistant foreman sessions keep `daemon.command`'s mode. `forge dash --permission-mode default|auto|dontAsk` sets the default at start-up, so an overnight run can start in Auto with nothing to click; a daemon session can't pass it. Like every choice of mode it is held in memory, never in `.forge/config.yml` (which would put every machine's sessions in it, and which a branch can edit), and lasts until `forge dash` stops. Even Auto still waits for you on the calls Claude Code's classifier sends as prompts, so an unattended run can still pause; `dontAsk` never waits, and refuses whatever `allowedTools` doesn't list. Auto approves most calls with nobody reading them, so use it on a session you are watching, and switch back to Ask when you leave. It isn't contained to that session either: a call that runs unread can reach the dashboard's own API and switch or answer for the others (docs/architecture/daemon-security.md).
- **Git inside the session** runs with `core.hooksPath=/dev/null` and `core.fsmonitor=false` pinned through `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` (appended after any you already export), plus `GIT_EDITOR=true`. That covers subagents, `forge` and your verify commands too: **no git hooks run in daemon mode**, including your pre-commit and pre-push hooks and Git LFS's pre-push upload, so repos that depend on hooks should keep those checks in `commands.*`/`verify`, and LFS repos should not push from the daemon.
- **What configured commands inherit.** The same as outside the daemon: the [command environment](#command-environment), an allowlist of the environment `forge dash` started with (the git pins above included), under `/bin/sh -c` unless `commandEnv.loginShell` is true, and the PATH `forge dash` captured from your login shell. A session can edit a test and run `forge verify` before anyone reads the change, so no token, unlisted credential or login profile reaches that code. `forge release run` is refused under the daemon.
- **What the session may not change.** Forge always appends `--disallowedTools Edit(.forge/config.yml),Edit(.forge/trackers/**),Edit(.forge/secrets-allow.txt),Edit(.forge/verifiers/**),Edit(.forge/runtime/spend.json),Edit(.forge/runtime/audit.jsonl)` to `command`. Every `forge` call in the session also checks that those files are the ones a human started the daemon with, and refuses if they changed (`forge init write`, `forge migrate` and `forge config set` always refuse there). If they change while the daemon runs, by the session or by you, the supervisor stops it with an error in the dashboard and never restarts it on its own: review `git diff .forge/`, then press Start, which takes a fresh snapshot. docs/architecture/daemon-security.md explains the layers.
- **`enabled`** means the daemon may run and starts with `forge dash`, except `forge dash --dev` (what `npm run dev` runs), which leaves it off until you press Start. `POST /api/p/<project>/daemon {"action":"stop"}` stops it until the next `start` or the next `forge dash`; to keep it off across restarts, set `enabled: false`. The machine dashboard boots a project's daemon when it starts, and when you register or restore the project, only while the files Forge trusts are the ones you last approved there: by pressing Start, or by running `forge dash` in that repo when it starts the dashboard or registers the repo (opening the running dashboard for a repo already registered approves nothing). After you or a session change one (a pull, a trust stop), or for a project you only registered with `forge project add`, the daemon stays off, marked `needs approval` in the dashboard, until you review the files and press Start (docs/architecture/daemon-security.md).
- **`maxConcurrent`** (an integer from 1 to 16, default 3) caps how many job sessions run at once; the inbox session is not counted. A job with work beyond the cap waits for a slot, and an idle job session gives its slot up to a waiting job (it resumes its conversation the next time it has work). A session whose job has agents running (reviewers it started in the background, say) is kept: it is never stopped for a slot, though it still counts toward the cap, so the waiting job gets the next slot that frees. So is a session for 30 s after its last turn or agent ended. Each job session drives one job, so `runtime.maxParallelJobs` (how many jobs your own interactive session runs at once) does not apply to the pool. Spend scales with the number of live sessions: set `maxConcurrent: 1` for one job session at a time. The dashboard shows this key read-only. On top of it, the **machine cap** bounds job sessions across every project the machine dashboard serves: `forge project settings --max-concurrent <1-64>` sets it in the machine index, and `auto` (the default) uses the highest loaded project's `maxConcurrent`, so a single project behaves as this key alone says. A free slot goes to the waiting job with the oldest pending request on the machine, and an idle job session in another project may be stopped to make room.
- **`auth`** (`subscription`, the default, or `api-key`): which credential the sessions run on. claude prefers an `ANTHROPIC_API_KEY` (or `ANTHROPIC_AUTH_TOKEN`) in its environment over the Claude login, and a headless session never asks, so a key exported in the shell that ran `forge dash` (often for some other tool) would quietly bill that API account, and its spend cap then fails every turn with `last turn failed: API Error: 400 … usage limits`. The provider switches `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX` and `CLAUDE_CODE_USE_FOUNDRY`, and `ANTHROPIC_BASE_URL`, do the same quietly: each sends the session to another account or through another endpoint. With `subscription`, all six variables are dropped from the sessions' environment and they run on the login, like your own sessions; with `api-key`, all six pass. The first time `forge dash` starts a daemon-enabled repo from a terminal with a key set and no `auth` in this file, it asks once and writes the answer; started anywhere else (from `/forge dash`, a script), it assumes `subscription` and says so in its output. A session's log records an `auth` event listing whichever of the six were set, with whether they were passed on. `forge doctor`'s `daemon billing` check lists them too, as a warning when a provider switch or `ANTHROPIC_BASE_URL` is set, and the Workers popover shows a line above Start/Stop while any is set where `forge dash` started, in warning tone by the same rule as doctor (an API key alone is listed muted).
- **`idleStopMinutes`**: a session with no turn in flight for this long is stopped. The time counts from its last turn or the last agent of its job ending, whichever is later, and a session is never idle-stopped while its job's agents run. It stays wanted, and its next request resumes the same conversation. `null` never stops it. A job session also stops once its job is done, cancelled or failed and nothing is left for it.
- **`turnTimeoutMinutes`** (default 60): a job, inbox, office or assistant foreman session's turn still running this long after it started is stopped (`turn-timeout` in its log): the child is killed, its agents are marked lost, its job's lease expires and the requests it claimed go back to pending, and the session stays wanted, so the pool starts it again for that work and the reconciler watches the job (docs/architecture/daemon.md). `null` means no limit; any other value must be a number greater than 0. Editable with `forge config set` and in the dashboard.
- **`jobBudget`** (default `{ tokens: 600000000, usd: 150 }`, or `null` to turn it off): with `enabled: true`, it fills each spend key (`tokens`, `usd`, `minutes`) on its own: a key that is null in `pipeline.budget` and absent from the job's own overrides gets this map's value for it, when that value is non-null, so an unattended job never loops without a spend ceiling. Setting one key (say `pipeline.budget.usd`) keeps the backstop for the others. A person's explicit per-job `null` override for a key (`forge job budget <id> --set usd=null` at a confirmed terminal, or the dashboard's Approve on the budget gate with `usd=null`) still means unlimited for that key only; a session can't set one, because `budget` is not settable through `forge job set --field`. It goes through the one limits rule every check uses: budget stops, the budget hold below, the repo budget, scoring, `forge job budget` and the dashboard all see the same limits. It keys on `daemon.enabled`, not on whether a session drives the job, so a job you drive yourself in a daemon-enabled repo gets the same backstop. The default is roughly twice the costliest jobs Forge itself has run. Raise it for one job with `forge job budget <id> --set usd=…`, for every job with `pipeline.budget.*` or here, or turn it off with `jobBudget: null`. A map you write is merged over the default, so write `tokens: null` to drop the token limit. Each key is `null` or a number ≥ 0, `tokens` an integer; any other key is a config problem. The dashboard shows it read-only.
- **Budget hold.** `pipeline.budget` limits are per job, so a budget stop is pending per request: a `resume`, `rework`, `answer` or `revise-spec` request whose job is at `waiting: budget` and still over a limit (on its metered spend, below) sends no turn. Once you raise or acknowledge the budget, the next tick sends it. In the dashboard, **Approve & continue** on the budget gate does that first: it POSTs `/api/jobs/<id>/budget` with the note's `key=value` limits (`usd=20 tokens=2000000`), or an acknowledgement when the note names none, and queues the `approve` only when nothing is still over; otherwise it shows the error and keeps the note. At a terminal, run `forge job budget <id> --set … | --ack` yourself (it asks you to type the job id). `approve` is never held, nor are `cancel` and requests without a job; a session that handles an `approve` only resumes the job once a person has raised or acknowledged the budget. The repo budget (`budget:`, "Repo budget" below) holds more: while it is exceeded under `hold`, every pending `resume`, `rework`, `answer`, `revise-spec` and `approve` of a job that isn't exempt waits, and the session reports `held: "repo-budget"`.
- **Dollar cap per spawn.** Every job session's child gets `--max-budget-usd <cap>`, recomputed at every spawn (resumes included, since the flag caps one process): the job's effective `usd` limit, plus the acknowledged base, minus its `usage.estCostUsd`, at least `0.01` and floored to cents. No flag is passed when the job's `usd` limit is null, for the inbox, office and assistant foreman sessions, or when the job can't be read. The session log's `spawn` event records it as `capUsd`. When claude reaches it (a `result` with `subtype: error_max_budget_usd`), the session stops at once instead of retrying, with an error in the dashboard naming the cap; raise or acknowledge the job's budget, then start the session again. The spend it subtracts is the job's metered spend (**Metered spend** below). On a resume it adds back the conversation's last metered cumulative (`baseline`): claude restores its running total on `--resume`, so the cap is `limit + acknowledged base − spent + baseline`, and a fresh spawn's baseline is 0.
- **Metered spend.** At the end of every turn the supervisor records claude's own cost report from the `result` line (`total_cost_usd` and `modelUsage`, cumulative per conversation, carried over a `--resume`, background subagents included) in `.forge/runtime/meter/<scope>.jsonl`, as the delta against a baseline it holds per spawn. Only the supervisor in `forge dash` writes it; no CLI command does. A job's enforced spend is the reported total when it has no meter, else `max(reported, metered + max(0, reported − covered))`, where `covered` is the reported usage of the agents that ended inside the job's own session (their `agent-end` carries `metered: true`). Every budget check reads that one figure: budget stops, the budget hold, the repo budget's release check, `forge job budget`, the step's budget gate, scoring and the dollar cap. After each metered turn of a job session the supervisor runs the `session-meter` budget checkpoint; when it parks the job on `budget`, it stops the session (it stays wanted, so its held requests start it again once you raise or acknowledge the budget and approve the gate), and the dashboard shows why. The drawer's budget rows show the larger of the reported total and the last check's figure.
- **`dailyUsd`** (default `{ inbox: 25, office: 60, chat: 25 }`, dollars per UTC day; `null` turns all three off, a `null` key turns one off): what the inbox session, the office session with its assistant foremen, and every chat of the project together may spend in a UTC day, metered. `office` caps the office and every assistant foreman together: their meter files are summed, so running more assistants never multiplies it. `chat` caps every chat of the project together (every `_chat-<id>` meter in `.forge/runtime/meter/` summed), so opening more chats never multiplies it. At the cap the session stops wanting itself, its child is stopped (a chat's after the result that reached it), a `daemon-stopped` notification goes out with reason `daily-cap`, and the session controls show `daemon stopped: the office session and its assistant foremen spent $61.20 of the $60.00 daily cap (daemon.dailyUsd.office) on 2026-10-24 (UTC); …` (for a chat, `the chat sessions spent … (daemon.dailyUsd.chat) …`). Starting it again the same UTC day is refused with the same text (for the chats, starting any chat); a cap of 0 refuses every start. When a meter file the cap sums can't be read (over 64 MiB, a link, or a runtime or meter directory that is not a real one), the cap can't be checked, so every session it caps stops and its start is refused, with a `meter: …` error naming the path; fix or move the file aside, then start it again. The defaults sit above the heaviest day observed on Forge itself (office $38.66, inbox about $15). A goal mandate's drafting run is spent by the office session, so it counts against `daemon.dailyUsd.office`. Job sessions have no daily cap: their own budget applies. Each key is `null` or a number ≥ 0; any other key is a config problem. The dashboard shows it read-only.
- **`keepAwake`** (`auto`, the default, or `never`): while this project's pool is started and it has an active mandate (`status: active`, not waiting on its `after`) or a `running` job at an agent stage (`plan` through `decide`), the machine dashboard holds one sleep assertion for the whole machine (`caffeinate -i` on macOS, `systemd-inhibit --what=idle:sleep` on Linux), and releases it once no project needs it, checked every 15 s. `never` leaves this project out; `FORGE_KEEP_AWAKE=never` in `forge dash`'s environment turns it off for every project. A dev dashboard never holds one. Any other value is a config problem. Editable in Settings. `forge service install` keeps the dashboard itself running across logins and crashes (docs/CLI.md "Login service").
- **Migration from `dashboard.launcher`** (config `schemaVersion` 1 → 2): a non-empty launcher moves to `daemon.command` (an existing `daemon.command` wins) and `dashboard.launcher` is removed; `enabled` is never set, so upgrading never turns the daemon on. A launcher was a shell template with `{prompt}`, run once per request; `forge config validate` and `forge doctor` reject a `{prompt}` command until you rewrite it in the form above (usually: take the default `command` and add your flags), because the daemon sends its turn on stdin and never through a shell. A launcher that ran some other agent CLI cannot be migrated: the daemon supervises only Claude Code's stream-json mode. The migration happens in memory on every read; `forge migrate` writes it to disk.

Files (gitignored, under `.forge/runtime/daemons/`): `<scope>.json` (session id, the last 20 ids it replaced in `pastSessionIds`, pids, the log's base offset; `forge job claim` reads these to let a daemon owner that provably let go yield without `--force`) and `<scope>.log` (every stdout event plus `forge-daemon`/`forge-stderr` lines; rotated to `<scope>.log.1` past 20 MiB at spawn, or at `retention.logMaxBytes` as soon as it is reached; one older generation is kept, and the dashboard pages back into it), where the scope is `_inbox` or a job id. The session learns its scope only from `FORGE_DAEMON_SCOPE` in its environment. A `daemon.json` / `daemon.log` left by a Forge older than the pool is not read; delete it. `forge daemon status` lists the sessions and `forge daemon log <job>|--inbox [--lines N] [--follow]` prints one's log. docs/architecture/daemon.md and daemon-runtime.md cover the lifecycle and docs/architecture/daemon-security.md the threat model.

## Retention

`.forge/jobs/` and `.forge/runtime/` only grow until something removes them. Retention is off by default: every key is `null`, which keeps everything forever. docs/architecture/retention.md covers the archive format and the threat model.

- **`retention.jobsDays`** (null, or an integer from 1 to 3650): `forge sync` and `forge dash` startup archive every eligible finished job whose `finishedAt` (else `updatedAt`) is at least this many days old. Archiving writes `.forge/archive/<id>.json` (the job.json as stored, every event, ending with an `archived` event that names the actor, and a summary) and deletes the job's folder: its agents' markdown, reviews, verify reports, logs and screenshots. A job is skipped while it is active, an eval job, owned by a live session, has a running daemon session, has an open PR, still has a worktree (`forge worktree remove <id>` first), or is named in an unfinished job's `dependsOn` or `children`. Read-only in Settings (`deletes job files`).
- **`retention.logsDays`** (null, or an integer from 1 to 3650): the same runs delete `<scope>.log` and `<scope>.log.1` under `.forge/runtime/daemons/` when the newer of the two is at least this old, the session record names no live process, and the scope is not an active job; a job scope with no job folder left loses its `<scope>.json` too. Read-only in Settings (`deletes session logs`).
- **`retention.logMaxBytes`** (null, or an integer from 1048576 (1 MiB) to 1073741824 (1 GiB)): the supervisor rotates a session log to `<scope>.log.1` as soon as it reaches this size, mid-session, replacing the older `.log.1`. Null keeps today's rule: rotate only at spawn, past 20 MiB. Editable in Settings; it takes effect at the session's next spawn. `startBackground` (the dashboard's Run, `forge run <job> <cmd> --background`) rotates a job's background log `logs/<name>.log` to `.log.1` before starting the command once it has reached this size, or past 20 MiB when null.

Archived jobs leave the board, the Done filter, `forge status`, `forge job list --all` and `/api/p/<project>/state`, but `forge stats`, `/api/p/<project>/stats` (which counts them in `counts.archived`), `forge audit`, `forge job audit <id>`, `forge retro due` and the dependency check still read them. Every archived job and deleted log adds one JSON line to `.forge/runtime/retention.log`, and so does every job `forge job delete` removes (docs/architecture/deleting-a-job.md). `forge job archive <id>|--done --older-than D` and `forge job prune --older-than D [--dry-run]` do the same by hand (and are refused in daemon sessions); `forge doctor` warns when `.forge/jobs`, `.forge/archive` or `.forge/runtime` passes 500 MiB.

**Migration** (config `schemaVersion` 6 → 7): nothing changes. v7 adds `retention`, whose defaults keep everything; the bump lets older Forges refuse a config whose retention policy they would ignore. A repo upgraded from an older Forge gets `.forge/archive/.gitignore` (`*`) on its first archive, so records are never committed.

## Outcomes

- **`outcomes.windowDays`** (an integer from 1 to 365, default 14): after a job's root PR merges, `forge sync` watches this many days for a revert of its merge, `bug` issues that reference its PR or issues (GitHub tracker only), and churn (later non-Forge commits on the files it changed). The job's **outcome** stays `open` until the window closes, then turns `final` and counts in `forge stats`' autonomy rate. An open outcome follows the current value; a final one keeps the window it was measured with. Editable in Settings. docs/CLI.md "Outcomes" covers the measurement and the stats fields.

**Migration** (config `schemaVersion` 23 → 24): nothing changes. v24 adds `outcomes.windowDays`, 14 by default; the bump lets older Forges refuse a config whose outcome window they would ignore. `forge migrate` writes the new version.

## Environments

A job's **environment** (its per-job backing containers and volumes, its job databases and its background processes) starts on demand, stops while the job is parked and is torn down when the job finishes ([Backing services](#backing-services) › Start on demand, stop when parked, and › Teardown). `environments.maxRunning` caps how many run at once.

- **`environments.maxRunning`** (null, or an integer from 1 to 64; default null, no cap). Ensure up for job J does its record step under `.forge/locks/environments`: it drops entries whose job is missing or finished, marks J `running` with `usedAt` now, and while more than `maxRunning` entries are `running`, marks the one with the oldest `usedAt` `stopped`. The job being started and the focused job (read inside the same lock) are never chosen. When only those two are left, the cap is exceeded and the start goes ahead. Each victim is then stopped outside the lock (`docker stop`, background processes signalled; volumes and job databases kept), logging `environment-stop` with `trigger: evict` and `by: <J>`, and J's `environment-up` lists them in `evicted`. A victim whose stop fails stays `stopped` in the record, and its next resume (step rule E1) or ensure up starts it again. Eviction only ever stops, never removes, so a wrong choice costs one restart. Editable in Settings.
- **Sizing.** Set it to at least `daemon.maxConcurrent` + 1 (or `runtime.maxParallelJobs` + 1 for the orchestrator), so the jobs being worked on plus the focused one fit; a smaller cap makes active jobs evict each other on every verify.
- **Reading the record.** `.forge/runtime/environments.json` is read without following a symlink or FIFO and with a size cap; an unreadable file reads as empty, an entry whose id fails the job-id check or whose `state` is not `running` or `stopped` is dropped, a `usedAt` later than now reads as now and an unparseable one as the epoch. A hand-written entry can therefore only cause a stop, never protect a job from eviction or reach a Docker argv. `forge environment list` prints `{ maxRunning, focused, jobs: [{ id, state, usedAt }] }`, most recently used first.

**Migration** (config `schemaVersion` 24 → 25): nothing changes. v25 adds `environments.maxRunning`, null by default; the bump lets older Forges refuse a config whose cap they would ignore. `forge migrate` writes the new version.

## Scoring

Off by default. With both keys at their defaults, sync queues nothing and no job gets a **score**.
- **`scoring.sample`** (a number from 0 to 1, default 0): the share of merged jobs that get one post-merge judge run. A job is in the sample when the first 4 bytes of `sha256(<job id>)`, read as an unsigned integer over 2^32, are below this value, so the same job is always in or out and a later sync never re-rolls it. `1` scores every merged job. `forge sync` considers live (not archived, not eval) jobs whose root PR merged in the last 7 days, at most 5 per run, oldest merge first. A job over its per-job budget, or one seen while the repo budget holds, is recorded as `held` and never scored. Otherwise sync writes the merged PR's diff to `<job dir>/score.diff` (cut at 1 MiB), marks the score `queued` and adds a `resume` request. The job's session then runs the judge against the spec's acceptance criteria and records its `SCORE: <n>/5` with `forge job score record`. The run's usage counts toward the job's and the repo's spend.
- **`scoring.model`** (a model alias or id, or null): the scoring judge's model. Null uses `runtime.models.judge`. The eval judge always uses `runtime.models.judge`.

Both keys are editable in Settings. docs/CLI.md "Scoring" covers the command, the sync result and the `forge stats` fields.

**Migration** (config `schemaVersion` 25 → 26): nothing changes. v26 adds `scoring`, off by default; the bump lets older Forges refuse a config whose score sampling they would ignore. `forge migrate` writes the new version.

## Repo budget

`pipeline.budget` stops one job. `budget:` caps what the whole repo spends per calendar UTC day (`YYYY-MM-DD`) and month (`YYYY-MM`), so the daemon and `/forge next 3` can't start jobs without limit. Every key defaults to `null` (unlimited), and per-job budgets work exactly as before.

**Spend** is one ledger from two sources, each counted on the UTC day and month of its `ts`. The reported source is the estimated cost of every `agent-end` event with usage, across live jobs and the records in `.forge/archive/` (every kind: evals and retros included), re-priced with today's `lib/integrations/claude/pricing.json`. The supervisor source is every daemon session's metered spend (`.forge/runtime/meter/`, **Metered spend** under "Daemon"): a job's orchestrator, the inbox, the office and each assistant foreman (role `assistant`, its `forge:assistant` sub-agents included), priced by claude itself and never re-priced. A job's metered cell, per day and model, is the remainder past the agent ends its own session's meter already holds, so no run counts twice. Meter files are never deleted, so a deleted job's metered spend still counts. `.forge/runtime/spend.json` caches the totals per entry and is rebuilt whenever it is missing, unreadable, a symlink, or written for another cache version or pricing table.

**Exceeded.** The effective cap is `cap × (1 + acknowledgements for the period)`. A key is exceeded when spend reaches its cap (`>=`, so `0` holds everything). The reason reads `repo budget: $103.20 of $100.00 this month` (also `<n> of <cap> tokens this month` and `$… of $… today`).

**Hold** (`onExceeded: hold`, the default) is enforced by the CLI wherever a job starts:
- `forge job new` still creates the job but parks it `waiting` on `budget`, unclaimed. `--kind retro` is never parked. `--force` creates and claims it anyway and logs a `budget-override` event (refused in a daemon session).
- `forge next` starts nothing and prints `{held: true, repoBudget}`; `forge job from-ref` exits 4.
- `forge job claim` parks a job that isn't running an agent and exits 4. A job with a running agent, a live foreign owner or an existing wait is claimed (or refused) exactly as before.
- The daemon pool holds a job session's `resume`, `rework`, `answer`, `revise-spec` and `approve` requests (`held: "repo-budget"`); `cancel`, gate requests and inbox requests still run.

Retro jobs, and a job forced past the cap this month, are exempt. Under `warn` nothing is parked or refused: commands add a `repoBudget` block to their output and log a `repo-budget-warn` event.

**Release.** `forge budget ack --period <YYYY-MM|YYYY-MM-DD>` (a human-only operation: a person confirming at a terminal by typing the period, or the dashboard) grants one more period's cap for the current, exceeded month or day and logs a `repo-budget-ack` line in `.forge/runtime/audit.jsonl`. The dashboard's Acknowledge button in Needs you does the same. Whenever a check finds the repo no longer held (`forge budget`, `forge next`, `forge job new|claim|from-ref`, `forge sync`, an ack, or simply a new month), every job parked by the repo budget whose own per-job budget is fine goes back to `queued` (with a `resume` request when the daemon is on). `forge job budget <id> --ack` never lifts the repo cap.

`forge budget` prints spend, caps, remaining, the projected month-end and the held jobs. `forge stats --csv [--since DATE] [--by job|role|model|day]` exports the same spend for finance, with a `source` column (`reported` or `supervisor`) after the key columns.

## Notifications

Forge pushes a small, fixed-shape message to your webhooks and command when a job needs a human, a PR opens or merges, a job fails, the daemon stops on its own, a budget is exceeded or a secret is found. With `webhooks: []` and `command: null` (the defaults) it does nothing: no child process, no network, no events.

```yaml
notify:
  webhooks:
    - url: https://hooks.slack.com/services/T000/B000/XXXX
      events: [gate, pr-opened, job-failed]   # omitted = every event
      format: slack                           # json (default) | slack
  command: null                               # e.g. ./scripts/page.sh {event} {job} {title} {url}
```

- **`webhooks`**: a list of maps with `url` (required), `events` (a non-empty list; omitted subscribes to every event) and `format` (`json` or `slack`). `url` must be `https:`, without a username or password; plain `http:` is accepted only for `127.0.0.1`, `localhost` and `[::1]`, for local testing. An invalid entry is skipped by delivery and reported by `forge config validate` and `forge doctor`, named by its index and host, never its path or query. Teams, pagers and other services take the `json` format through their own webhook adapters.
- **`command`**: null, or a shell command run once per notification (with the first event) through the POSIX shell (`sh -c`) in the repo root, stdio ignored, killed after 30 s. Its `{placeholders}` (`{event}`, `{job}`, `{title}`, `{url}`, `{stage}`, `{reason}`, `{dashboardUrl}`; any other is a validation problem) are replaced by quoted references to environment variables, never by the values: `{title}` becomes `"$FORGE_NOTIFY_TITLE"`, likewise `FORGE_NOTIFY_EVENT`, `FORGE_NOTIFY_JOB`, `FORGE_NOTIFY_URL`, `FORGE_NOTIFY_STAGE`, `FORGE_NOTIFY_REASON` and `FORGE_NOTIFY_DASHBOARD_URL` (empty for null). So a title like `$(touch pwned)` reaches the script as text. Write placeholders unquoted; Forge adds the double quotes.
- Both keys are read-only in Settings and refused by `forge config set`, and `.forge/config.yml` is a protected path, so an agent cannot add a target.

**Events** (each fires once per state change; eval jobs never notify):

| Event | Fires when | Reason |
|---|---|---|
| `gate` | a job enters `waiting` on `spec-approval`, `split-approval`, `issue-link`, `input`, `escalation`, `infra`, `conflicts`, `rounds-exhausted`, `budget` or `human`, from another state or another `waitingOn` (`pr-review` and `external` are not gates); or `forge mandate draft record` stores a goal mandate's milestone draft (no job, no title); or the Office pass plans an `until: released` mandate's release, which waits for approval (no job; the title is `Mandate <id>: <title>`) | the `waitingOn` value, `milestone-approval`, or `mandate-release` |
| `budget-exceeded` | the same transition with `waitingOn: budget` | `budget` |
| `job-failed` | a job enters `failed` | `failed` |
| `pr-opened` | `forge pr open` creates a new PR (not an update or adoption) | `pr-opened` |
| `pr-merged` | a job with a PR number enters `done` | `pr-merged` |
| `secret-found` | the secret scan logs a finding on a job, or a blocked scan could not finish | `secret-found` |
| `daemon-stopped` | the supervisor stops on its own: a trust change (`trust`, no job), or a session's failed turns or starts (`failed-turns`, `failed-starts`), or the inbox, or the office with its assistant foremen, or a chat (the chats share one cap) reaching its `daemon.dailyUsd` cap (`daily-cap`) | that code |
| `mandate-stalled` | the Office pass paused a mandate with no progress (no job; the title is `Mandate <id>: <title>`), or stalled one of its jobs back at its gate `stall.bounces` times (the job's title) | `mandate-stalled` |
| `mandate-budget` | the Office pass paused a mandate at its `budget.usd` or `budget.jobs` (no job) | `mandate-budget` |
| `mandate-closed` | the Office pass closed a mandate whose work is done (no job) | `mandate-closed` |
| `service-restarted` | the login service's dashboard (`forge dash --service`) started and this project's boot pass found running jobs or open Office requests; no job, and the title names only this project and its counts (`web resumed: 2 running jobs, 1 Office request, 1 active mandate`). A start by hand sends none | `service-restarted` |

A budget transition carries `[budget-exceeded, gate]`: each webhook gets at most one message, the first of those it subscribes to, and the command runs once with `budget-exceeded`.

**Payload** (`format: json`), exactly these keys:

```json
{ "event": "gate", "job": "42-add-login", "title": "Add login", "stage": "spec", "reason": "Spec is waiting for approval", "url": null, "dashboardUrl": "http://127.0.0.1:7400/?project=web#/pipeline", "at": "2026-10-16T09:00:00.000Z" }
```

`reason` is a fixed English string chosen by the reason code, never the job's reason, notes, request, reviews, PR text or agent output. `title` is the job title with control characters replaced by spaces and bidi controls (U+202A–U+202E, U+2066–U+2069) removed, trimmed and cut to 200 characters (ending in `…`); it is the only free text. `url` is the job's PR URL when it has the shape of a pull or merge request, `https://<host>/<owner>/<repo>/pull/<n>` or `https://<host>/<group>/…/<project>/-/merge_requests/<n>` with no credentials, query or fragment, else null (job.json is agent-writable, so no other link reaches the channel). `job`, `title` and `stage` are null for a daemon stop with no job. `dashboardUrl` is the origin in the machine dashboard's record (`<FORGE_HOME>/dashboard.json`) when it is an http loopback origin with a port, else `http://127.0.0.1:<dashboard.port>`, plus `/?project=<name>#/pipeline` when the repo is registered in the machine index, else `/#/pipeline`. Only the url's shape is checked, not that a dashboard serves it (nothing is signalled).

**Payload** (`format: slack`): Block Kit with every variable string in `plain_text`, so a title cannot mention `@channel` or add links: a `header` (`<label>: <title>`, cut to 150 characters), a `section` with the reason, a `context` with `<job> · <stage> · <dashboardUrl>`, and an "Open PR" button when `url` is set. The fallback `text` is `Forge <label>: <title>` with `&`, `<` and `>` escaped. Labels: Needs you, PR opened, PR merged, Job failed, Daemon stopped, Budget exceeded, Secret found, Forge restarted, Mandate stalled, Mandate budget, Mandate closed.

**Delivery** never runs in the command that changed state: it spawns a detached `forge notify send`, so a slow endpoint never stalls `forge job set`, `forge pr open` or the daemon, and a delivery failure never changes job state. A webhook gets a `POST` (`content-type: application/json`, redirects refused, 5 s timeout); a network error, timeout, 429 or 5xx is retried once after 1 s. A command's exit 0 is success and it is not retried. Each target's outcome is one event on the job (`.forge/runtime/notify.jsonl` for a daemon stop with no job): `notified { event, target, host, format, status, attempts }` or `notify-failed { event, target, host, error, status, code, attempts }`, with `error` one of `timeout`, `network`, `http`, `redirect`, `invalid`, `exit`, `spawn`. Only the webhook's host is ever recorded; no event, log line or doctor detail contains its path, query or the command text, and `/api/config` shows webhook URLs as `<scheme>//<host>/…` and a set command as `<set>`. `.forge/runtime/notify.jsonl` is appended through a descriptor that refuses a symlink or other non-regular file.

`forge notify test [--event <name>]` sends a sample (job null, title "Forge test notification") to every valid webhook regardless of its `events`, runs the command if set, prints each target's result and exits 1 when one fails or nothing is configured. `forge doctor` adds a `notify webhook <n> (<host>)` check per webhook (a best-effort `HEAD`; unreachable and plain-http entries are warnings) and a `notify command` check that never runs the command.

**Migration** (config `schemaVersion` 7 → 8): nothing changes. v8 adds `notify`, empty by default; the bump lets older Forges refuse a config whose notifications they would ignore.

## Foreman

With `foreman.enabled: true` and `daemon.enabled: true`, `forge dash` runs the Foreman's **assistant foremen** beside the inbox: `assistants.sessions` supervised sessions (scopes `_assistant-1` … `_assistant-<n>`) while `assistants.enabled` holds. They never count against `daemon.maxConcurrent` or the machine cap, and they share the pool's trust check, deny rules, budget holds and failure handling. The **office** session (scope `_office`) turns `draft` requests into a goal mandate's milestone draft and `direct` requests into the next starts of active mandates (see [Mandates](#mandates)); it spawns on `foreman.model` and `foreman.effort`, and `forge dash` runs the Office pass that queues its `direct` requests every `foreman.cadence` minutes. When `forge job set` parks a job on a gate whose class is in `decides`, the CLI queues a `gate` request; `forge pr sync` does the same for a job waiting on `pr-review` with changes requested or unresolved threads from someone with write access to the repo (`pr-feedback`, once per PR head; feedback only from others stays with a human). Failing checks need no judgement, so they skip the assistant foremen: while the foreman decides `pr-feedback` (for a job in a mandate, only while that mandate delegates `pr-feedback`; otherwise the gate is queued), `forge pr sync` itself records a foreman `rework` (once per PR head, any head, a GitHub "Update branch" included), writes a fixed `feedback.md` pointing the builder at `gh pr checks`, moves the job to `build` and queues a `resume` for its session. A reserved match (a security review that isn't `PASS`, or a `reserved` pattern in the job's reason) still goes through the `pr-feedback` gate. After `pr.maxCiReworks` CI reworks in a row the next red head waits for a person instead, with no gate queued (see [Open PRs](#open-prs)), and a `rounds-exhausted` park past the [total-round ceiling](#total-round-ceiling) is a person's alone. Every rework round on an open PR starts from the PR's head: `forge job round` fetches the job's branch and fast-forwards or merges it into the worktree (a conflicting merge is aborted, logged as `pr-head-pulled`, and left for the next push to surface). When `forge pr open` finds the PR branch moved, it merges it in and step re-verifies the merged HEAD (PR2b), unless the merge is not a clean base merge on the reviewed head: then the job first goes back to review (PR12); a conflicting one is aborted, and step parks the job on `human` (PR11) until a person merges it in the worktree and runs `forge verify <id>`. An assistant foreman claims each gate request (the first claim wins) and hands it to a `forge:assistant` sub-agent (model `foreman.assistants.model`, effort `foreman.assistants.effort`) that reads the job's files, then records the verdict with `forge job human … --actor foreman` and queues a `resume` for the job's session. It never reads a job file itself.

- **`enabled`** (default `false`): nothing changes while it is off. No `gate` request is written and no assistant foreman runs. The status bar's Foreman indicator still shows, dashed, as **Foreman off**, and its popover says how to turn it on here (the key is locked in Settings and `forge config set`).
- **`decides`**: the classes it may decide, from `spec-approval`, `split-approval`, `escalation`, `rounds-exhausted`, `conflicts`, `pr-feedback`, `repo-proposal`, `release` and `milestone-approval`. The default lists every class but `repo-proposal`, `release` and `milestone-approval`: approving an agent's repo proposal widens the repos a job pushes to (docs/architecture/job-repos.md), a release publishes what can't be unpublished (RELEASES.md "Releasing a project"), and approving a goal mandate's milestone draft files issues to the tracker ([Mandates](#mandates)), so an owner adds them deliberately; a mandate's own `decides` must list `milestone-approval` too. `release` is a job's `forge release plan --job`, or an `until: released` mandate's release plan, awaiting approval: the Foreman's approval stands in for `forge release run`'s publish prompt when there is no terminal, for that exact plan only. `input`, `issue-link`, `infra`, `budget`, `human` and `external` are never foreman gates. An unknown entry is reported by `forge config validate` / `forge doctor` and ignored at run time.
- **`reserved`**: patterns matched as whole phrases, case-insensitively, against the job's reason, the `## Why` and `## For the human` sections of `decision.md` (escalation and rounds-exhausted) and the foreman's own note. A match leaves the gate with a human, and the CLI refuses the foreman's decision even if the request said otherwise. Security always has to pass: while the latest recorded security verdict is anything but `PASS` (`CHANGES`, or `MALFORMED`), the CLI refuses every foreman action that accepts the job (`approve`, `approve-spec`, `approve-split`, `approve-repos`, `approve-release`), whatever the texts say, and allows the ones that fix it (`rework`, `revise-spec`, `revise-split`, `reject-repos`). The gate still reaches the assistant, whose brief carries a `Security review:` line, so it chooses how to fix the findings. A gate with no fixing action (`conflicts`, `release`) stays with a human. A value that isn't a list of non-empty strings fails closed: every gate stays with a human until it is fixed. An entry `gate:<class>` (lowercase `gate:`, then a class from `decides`' list, whitespace trimmed) is never matched as text: it reserves that whole class. The form is exact: any other entry that starts like one (`Gate:release`, `gate: release`, `gate:Release`) is reported by `forge config validate` and fails closed like an invalid `reserved`, never read as text. The default list ends with `gate:release`.
- **Reserved wins.** The Foreman decides a class only when `enabled` is true, the class is in `decides`, and `reserved` has no `gate:<class>` entry. Listing `release` in `decides` while keeping the default `reserved` still leaves releases with a human; to hand the class over, *move* it: add `release` to `decides` and remove `gate:release` from `reserved`. `gate:` works for every class (`gate:repo-proposal` keeps repo proposals with a human whatever `decides` says). A `gate:` entry naming no class (`gate:relase`) is reported by `forge config validate` / `forge doctor`, and at run time fails closed like any invalid `reserved`. A plain `release` text pattern would not do the same job: it would keep every gate whose reason mentions "release" with a human, and still not reserve the class.
- **`ship`** (`propose`, `merge` or `release`, in that order, each including the one before): `merge` (with `enabled`) counts as `merge.auto: true` in the approver's brief and in step rule PR4, so a PR the approver marks `Auto-merge eligible: yes` under `merge.autoWhen` is merged, and `forge pr merge` still enforces every check in [Merge](#merge). `release` does the same, and also lets a mandate run `until: released` ([Mandates](#mandates)). No level makes the Foreman decide a release: that stays `decides`, `reserved` and the mandate's `decides`. The office and the assistant foremen can never run `forge pr merge`.

- **`model`**, **`effort`** and **`cadence`** (defaults `inherit`, `null`, `10`): the office session's model and effort when it directs work under mandates (`--model` and `--effort` on its spawn; `inherit` keeps `daemon.command`'s model, and a null effort falls through to the default effort), and the minutes (1–1440; anything else reads as 10) between the Office's passes over its mandates. A mandate stalls after `stall.cadences` passes of this many minutes with no progress.
- **`assistants`** (`{ enabled: true, sessions: 1, model: sonnet, effort: null }`): `model` and `effort` are the `forge:assistant` sub-agent's, which `forge job assist` returns and `forge roster` shows (its effort: the job's own, then `assistants.effort`, then `runtime.effortByComplexity`, then `runtime.effort`). With `enabled` (and `foreman.enabled`), the pool keeps `sessions` (1–16) assistant foremen, each in its own session, that claim the Foreman's gate requests; with `enabled: false` no assistant runs, and every gate request waits for a human, shown as a human's gate.
- **`surveyors`** (`{ enabled: false, model: haiku, effort: null }`): with `enabled`, the office session summarises each mandate's board through `forge:surveyor` sub-agents (`forge office board`, on `model` and `effort`, which `forge roster` shows) before it chooses what to start; with it off, `forge office board` is refused.
- **`mandate`**: the contract terms `forge mandate new` fills a term it isn't given with (see [Mandates](#mandates)).

The model and effort keys (`foreman.model`, `foreman.effort`, `foreman.assistants.model|effort`, `foreman.surveyors.model|effort`) are editable in the settings and with `forge config set`: they pick a model and how much it thinks, never what it may do. Every other key here is read-only there: edit it by hand.

- **Migration** (config `schemaVersion` 38 → 39): nothing changes. v39 adds `foreman.ship: release` and `foreman.mandate.until: released`; the bump lets older Forges refuse a config whose `ship` or `until` they would reject.
- **Migration** (config `schemaVersion` 36 → 37): nothing changes. v37 adds the `mandate-stalled`, `mandate-budget` and `mandate-closed` notification events; the bump lets older Forges refuse a webhook subscribed to an event they lack.
- **Migration** (config `schemaVersion` 34 → 35): `runtime.models.assistant` moves to `foreman.assistants.model` and `runtime.efforts.assistant` to `foreman.assistants.effort`, as written; a value already under `foreman.assistants` wins, and the old keys are deleted. A config with neither key, or whose `foreman` isn't a map, is unchanged; the other new keys come from the defaults. A hand-written `runtime.efforts.assistant` in a current config is reported as `runtime.efforts.assistant is not a role`.
- **Migration** (config `schemaVersion` 17 → 18): a `foreman.reserved` list without `gate:release` gains it at the end; nothing else changes. `deepMerge` replaces lists, so a config that wrote out its own `reserved` would otherwise miss the new default. A v17 `decides` can't name `release` (it was invalid there), so no delegation is taken away, and the bump lets older Forges refuse a config whose `decides` names a class they would ignore.
- **Migration** (config `schemaVersion` 4 → 5): nothing changes. v5 adds `foreman.*` (off by default), `runtime.models.assistant` and `runtime.efforts.assistant`; the bump lets older Forges refuse a config whose foreman policy they would ignore. docs/architecture/foreman.md covers routing and the authority checks.

### Mandates

A **mandate** is the owner's standing instruction to the Office: one file, `.forge/runtime/mandates/<id>.md`, with the mandate contract as YAML frontmatter and the owner's guidance as free text after it. `runtime/` is gitignored and outside every daemon session's write roots, so a mandate is this machine's alone and no branch or PR can change one. Only the owner writes it: `forge mandate` (docs/CLI.md), or the dashboard's Foreman page, which writes through the same checks and refusals (docs/DASHBOARD.md):

- `forge mandate new <id> --title T [terms] [--goal G]` creates it, `active`. Each term it isn't given comes from `foreman.mandate`, and the default `decides` is cut to the classes the Foreman may decide (`foreman.decides` minus `gate:<class>` reservations), so a default never causes a refusal. `edit` replaces only the terms given (`none` empties a list, `--after none` clears `after`); `pause`, `resume` and `close` move its status (each idempotent; a closed mandate is never edited, paused or resumed); `list` and `show` read.
- The id matches `^[a-z0-9][a-z0-9-]{0,39}$` and is not `none`.
- **The contract.** `scope` (`milestones`, in order; `labels`; `issues`, at least one non-empty, or all empty for a goal mandate), `until` (`merge-ready`, `merged` or `released`: a job under `merged` or `released` reaches it when it merges, and a `released` mandate then waits for its release, below), `maxJobs` (1–16), `order` (`graph`, `priority` or `listed`: `listed` works exactly `scope.issues` in order, and issues need it), `decides` (gate classes), `budget` (`usd` over 0 and at most 100000, `jobs` 1–1000), `stall` (`cadences` and `bounces`, 1–100), `onUnfinishable` (`park` or `cancel`) and `after` (another mandate's id). Milestones are 1–200 characters (a filed draft's title becomes one) and labels 1–100; both never start with `-` and have no control or hidden characters (zero-width, bidi overrides), at most 10 each; at most 100 issues, each a ref the tracker accepts. A write that breaks any rule is refused with every problem named, and nothing is written.
- **As it applies now.** `forge mandate show` prints the contract as written (`contract`) and as it applies (`effective`), with one `capped` line per term the config changed: `decides` keeps only the classes in `foreman.decides` that `foreman.reserved` doesn't hold as a class (none while `foreman.enabled` is false or `foreman.reserved` can't be read), `until: merged` applies only under `foreman.ship: merge` or `release` (else `until: merged needs foreman.ship: merge; merge-ready applies`), and `until: released` only under `release` (else `until: released needs foreman.ship: release; merged applies` under `merge`, or `…; merge-ready applies` under `propose`). Defaults are filled at write time, so a file states its own contract; caps apply at read time.
- **Chains.** `after` links mandates into linear chains: a mandate is `waiting` until the one it follows is closed (or while that one is missing or unreadable), and closing a link makes the next one `active` without writing to it. `list` and `show` give each mandate's `chain` and its `activeLink`, the first link not closed.
- **Jobs and narrowing.** `forge job new --mandate <id>` puts a job in a mandate (refused for an unknown, closed or unreadable one), and a split child keeps its parent's; `mandate` is locked, so `forge job set` can't move a job out. For a job in a mandate, the Foreman decides only the classes the effective `foreman.decides` and that mandate's `decides` both name, while the mandate is active or paused (a paused mandate's in-flight jobs finish), and none once it is closed (`mandate <id> is closed: left for a human`). A gate the job has come back to `stall.bounces` times since a person last decided (a new entry into the same wait; `pr-review` and `external` never count) is a person's too: the **bounce hold** (`mandate <id>: back at <wait> <n> times (stall.bounces <k>): left for a human`). `checkForemanDecision` refuses the rest (and `forge job human … approve-release`, for the `release` class), `gateOwner` shows them as a human's, and `forge job assist` returns them as `reserved` so the assistant foreman hands them off. The CI rework in `forge pr sync` and `forge sync` (see above) follows the same rule: a job in a mandate gets it only when its mandate delegates `pr-feedback`, and otherwise the `pr-feedback` gate is queued. For the `release` class only, the status counts too: a paused or closed mandate delegates no release (`approve-release --actor foreman` is refused with `mandate <id> is paused: release left for a human`, or closed), and a foreman release approval already recorded counts for `forge release run` and `forge release status` only while the mandate still delegates `release`, so it stops counting once the mandate is narrowed, paused, closed, deleted or unreadable. An `until: released` mandate's own release plan is held the same way: the Foreman decides it only while `foreman.decides` lists `release` without `gate:release`, the mandate is active and its `decides` lists `release`, `until: released` applies (`foreman.ship: release`), and no `reserved` pattern matches the mandate's title, a title of one of its jobs or the approval's note. A recorded approval stops counting as soon as any of these changes, or the plan's hash does. A mandate file that is missing or can't be read (a link, not a regular file, over 64 KiB, bad frontmatter, a term that breaks the rules, a `schemaVersion` from a newer Forge, an id unlike its file name) delegates nothing.
- **Enforcement.** With `foreman.enabled` and the pool running, `forge dash` runs the **Office pass** (`forge office pass`, code with no model) at start, when a mandate file changes, when a mandate job settles, and every `foreman.cadence` minutes. For each mandate that is not closed (goal mandates still drafting aside) it: applies `onUnfinishable` to every failed job (`cancel` cancels it, `park` leaves it failed for a person to retry); stalls a job back at its gate `stall.bounces` times (the bounce hold, above), notifying `mandate-stalled`; **closes** an active or paused mandate once nothing is left to start and none of its jobs is in flight or failed and unhandled, with the reason `done: <n> jobs reached <until>, <p> parked, $<usd>`, notifying `mandate-closed` and writing its closing summary (`.forge/runtime/mandates/<id>/summary.json`: each job's outcome, spend, human interventions, stalls, parked, skipped, needs-info and elsewhere issues, which `forge mandate show` returns as `summary`), and starts the next link of its chain in the same pass; for an effective `until: released` mandate, first **waits for release approval** instead of closing (see **Until released**, below); pauses an active mandate whose jobs' spend reaches `budget.usd`, or that started `budget.jobs` jobs with issues left (split children don't count), notifying `mandate-budget`; and pauses an active mandate with no progress (no job created or moved, no agent running) for `stall.cadences × foreman.cadence` minutes, notifying `mandate-stalled`. An owner's edit, pause or close made meanwhile wins. When a mandate has issues to start or queued jobs to resume, the pass wakes the office session with one `direct` request, and the office picks which in-scope issues start (`forge office survey`, then `forge office start <id> <ref> --reason R`, which re-checks every limit: the mandate active, `maxJobs`, both budgets, the repo budget, and the issue among its next ones in its `order`). A mandate's scope comes from the tracker (`scope` in docs/TRACKERS.md: one call per milestone, worked one milestone at a time, or one for labels; `order: listed` needs no call), and a tracker that can't list it keeps the mandate from starting or closing. Every choice and enforcement is a **directive** in the repo audit log, which `forge audit` lists and `forge mandate show` returns with `progress`. The office session's own spend is not a mandate's: it counts against `daemon.dailyUsd.office`.
- **Until released.** Once an effective `until: released` mandate's jobs have all merged (nothing left to start, nothing in flight or failed and unhandled), the Office pass plans its release instead of closing it: a `--since <tag>` plan from the root repo's latest tag reachable from HEAD, bound to the mandate (release.md reads `since <tag> for mandate <id>`). It logs `mandate-release-planned` to the repo audit log and a `release` directive, notifies `gate` with the reason `mandate-release`, and, when the Foreman decides `release` and the mandate delegates it, queues one job-less `release` gate request for an assistant foreman (one per mandate and plan, whatever became of it). It never runs the release: a person runs `forge release run` in a terminal, or a human or CI runs it without one after the foreman approved that plan ([RELEASES.md](RELEASES.md#releasing-a-project)). The pass closes the mandate once the run finished every step (`done: <n> jobs reached released, …`). Until then the mandate stays open, its `blocked` says why (`release: <detail>`), and no budget pause, cadence stall or `direct` request applies, since waiting on a person isn't a stall. The pass plans only a mandate with no plan yet, or one whose plan went stale before any step ran (a new plan, a new request); it reports and waits on no tag in the root repo, nothing to release since it, an unfinished run of another plan, a failed step, a plan that went stale after a step ran, and a `release.json` that now holds another plan. A paused mandate is never planned, but it does close once its release finished. A person re-plans an active mandate's release after the pass planned it once with `forge release plan --mandate <id>`. New scope items send the mandate back to directing work. `forge mandate show` and each `forge office pass` line carry its `release` state (`unplanned`, `done`, `replaced`, `failed`, `stale`, `started`, `approved` or `pending`, with the plan, tag, step counts, owner and a one-line detail).
- **Guidance is data.** The body (at most 8000 characters) reaches the assistant's brief and `forge mandate show` only fenced, as for tracker text: a provenance line, then `>` lines, with hidden characters and HTML comments removed. It never widens what the Foreman may decide.
- **Goal mandates.** `forge mandate new <id> --title T --goal "<text>"` (or `--goal-file F`, `-` for stdin) states what to achieve instead of what to run. The goal is set once (`edit --goal` is a usage error): CRLF and lone CR become LF, it is trimmed, and it must then hold at least one character that is not whitespace, at most 4000 characters, and no control character but line feed and tab (nor U+2028 or U+2029). A goal mandate's scope stays empty until its draft is filed; any other mandate, and a filed goal mandate, needs at least one scope entry. The goal is data like the guidance: `show` returns it fenced as `goal` (`''` without one), and every summary carries `intake: true` for a goal mandate. `new --goal` queues a drafting run (`draft.request` in its result): the office session turns the goal into a milestone draft, `.forge/runtime/mandates/<id>/draft.json`, which `forge mandate draft show <id>` reads with its status and spend (docs/architecture/foreman.md "Intake"). `forge mandate draft start <id>` queues another for an active goal mandate. A drafting run's spend is the office session's, so it counts against `daemon.dailyUsd.office`; a run a person drives from their own terminal is recorded only on the mandate's ledger.
- **Milestone approval and filing.** A ready draft waits at the `milestone-approval` gate, in `forge mandate draft show` and the dashboard's Needs you card. `forge mandate draft approve <id>` files it to the tracker: the milestone, then each issue in wave order with a `wave-<n>` label, and then the mandate becomes an ordinary scoped mandate over that milestone (`filedAt` set; `edit` may change its scope, never to empty), whose issues go through readiness triage. `draft revise <id> --note N` sends it back to the drafter with the note; `draft reject <id>` closes the mandate. `--request` and `--digest` pin the draft you read. An assistant foreman decides it (approve or revise, never reject) only when `foreman.decides` and the mandate's `decides` both list `milestone-approval` and `foreman.reserved` neither holds the class nor matches the draft or the goal; otherwise it is the owner's. The tracker needs `createMilestone` (the local backlog and GitHub have it; `none` doesn't). docs/architecture/foreman.md "Milestone approval and filing".
- **Daemon sessions** (job, inbox, office or assistant foreman) may run `list`, `show` and `draft show` but no write: `new`, `edit`, `pause`, `resume`, `close` and `draft start` are refused before anything is read. `draft prepare` and `draft record`, and `forge office survey|board|start|resume|note`, run only in the office session (or a person's own terminal); `forge office pass` runs in no daemon session. `draft approve`, `revise` and `reject` are refused in every daemon session unless an assistant foreman passes `--actor foreman`, and `draft assist` runs only in an assistant foreman session (or a person's terminal). `release assist` runs only in an assistant foreman session (or a person's terminal); `release approve` is only an assistant foreman's, with `--actor foreman`, and `forge release plan --mandate` runs in no daemon session. Each write that changes something appends a `mandate-<action>` event to the repo audit log, which `forge audit` lists with the mandate's id as its detail, as it does `mandate-release-planned`, `mandate-release-approved` and `mandate-release-finished`.
- **Migration** (mandate `schemaVersion` 3 → 4): nothing changes. v4 lets `until` be `released`; the bump lets an older Forge refuse a file whose `until` it would reject.

## Components

`components` lists the parts of a repo: libraries, services and apps, with their own commands and what they depend on. It is edited by hand (Settings shows it read-only), and `/forge init` proposes it from `forge init detect`'s `suggestions.components`. Each entry:

```yaml
components:
  - name: core                  # required, unique; letters, digits and . _ / -, starting with a letter or digit
    repo: null                  # optional; a repos name, or null / absent for this repo
    path: crates/core           # required, relative, inside the repo; "." is the repo root
    kind: library               # required: library | service | app
    commands: { test: "cargo test" }   # optional, like the top-level commands
    dependsOn:                  # optional, default []
      - { component: proto, type: build }
      - { backing: postgres, type: runtime }
      - { component: engine-core, type: build, link: { ecosystem: cargo, name: engine-core } }   # see Local links
    owners: ["@team-core"]      # optional list of strings
    notes: null                 # optional string
    config:                     # optional: config sinks rendered before each of this component's commands (see Config sinks)
      - env: { PORT_HTTP: "{port}" }
```

- **Selection.** A job's `services` field names the components it touches (the spec's `Services:` header fills it; step records only names that are configured components). When it names exactly one component of this repo, `forge run` and `forge verify` use that component's command, falling back to the top-level one, and run it from `<worktree>/<path>`. With none, several, an unknown name or a component whose `repo` is set, the top-level commands run from the worktree root. The verify integrity scan counts a component's script files under its path, and skips components whose `repo` is set.
- **Dependencies.** Each `dependsOn` entry names exactly one of `component` (another entry's name) or `backing` (a backing service such as a database; only its shape is checked for now), and a `type`: `build` (needed to build or test this one) or `runtime` (needed only while it runs). The dashboard's **Project** view draws them as the project graph (build edges solid, runtime edges dashed) and highlights a job's components and their downstream consumers; [downstream verification](#downstream-verification) adds those consumers to a job verify-only.
- **Validation** (`forge config validate`, `forge doctor`, `forge init write`, Settings): `components` must be a list of maps; a `name` that is missing, unsafe or repeated, a `path` that is missing, empty, absolute (`/…`, `\…`, a drive letter) or has a `..` segment, and a `kind` outside the three are problems, as are a non-string `repo` or `notes`, a `repo` that names no `repos` entry (`components "<c>".repo names unknown repo "<x>"`), `owners` that isn't a list of strings, and `commands` that isn't a map of strings or nulls. A `dependsOn` entry with neither or both targets, an empty target, a `type` other than `build | runtime`, or a `component` that names no component is a problem. A cycle of `build` edges is reported once with its path, e.g. `components: build dependency cycle a -> b -> c -> a` (a component naming itself as a build dependency is the cycle `a -> a`). Cycles that include a `runtime` edge are allowed.
- **`repo`** names a member repo from [`repos`](#repos); null or absent is the root repo. Today it only keeps the component out of command selection and the integrity scan.

### Ports and endpoints

A job holds one port per **port-bearing component**: every `service` or `app` entry of `components`, in config order, with the job's own component (the one its `services` names, when it names exactly one) first; a `library` listens on nothing and gets none. A repo with no service or app component has the single entry `dev`, which is what every job had before. `forge worktree create` chooses them from `ports.base`/`ports.span` under the same locks as backing ports, skipping every other active job's `port` and `ports`, every backing port and every port another registered project holds, and stores them in `job.json` as `ports: { "<name>": <port> }` with `port` set to the first entry's; `forge job show` and the `worktree` event carry both. An entry keeps its port across creates while it is free and in range, a job from before `ports` keeps its `port` as its first entry's, and a key naming no current entry is dropped. When the range runs short the create fails (`no free port in <base>-<end> for <job> (<n> needed): raise ports.span in .forge/config.yml or finish jobs holding ports`) and records nothing.

Every configured command Forge runs for the job (`worktrees.setup`, `forge run` for the root, a component or a member repo, `forge run --background`, `forge verify` steps, `forge integrate`'s rebuild and `forge eval grade`) gets:

- `{endpoint.<component>}` → `http://localhost:<port>`, no trailing slash, so `{endpoint.api}/health` composes.
- `{backing.<name>.port}` → the host port of that entry's first container port, as `FORGE_BACKING_<NAME>_PORT` holds it.
- `{backing.<name>.url}` → the text `"$FORGE_BACKING_<NAME>_URL"`, a quoted reference to the environment variable, never the url itself: a url can hold credentials and shell metacharacters, and command text is logged.
- `{port}`, `$PORT` and `$FORGE_PORT` → for a root command the port of the job's component when it has one, else `port`; for a member-repo command the port of the component the command runs in (none for a library).
- `FORGE_PORT_<C>` and `FORGE_ENDPOINT_<C>` per port-bearing component, with `C` the name upper-cased and every character outside `A-Z 0-9` as `_`.

A placeholder naming an unknown component or backing entry, or one whose port is not allocated yet, stays as written. `forge config validate`, `forge doctor`, `forge init write` and Settings check every template in `commands`, `components[].commands` and `worktrees.setup` for an `{endpoint.X}` that names no service or app component (`commands.dev uses {endpoint.docs}, which is not a service or app component`), a `{backing.X.url}` or `{backing.X.port}` that names no `backing` entry, and a `{backing.X.port}` on an `external` entry or one with no `ports`; two port-bearing components whose env names collide are reported once (`components "api-v1" and "api_v1" share the environment name FORGE_PORT_API_V1`). Problems never show a url. Builder and reviewer briefs that get the running app carry one `Endpoints:` line listing every component endpoint, and the dashboard's Environment card lists them with the managed backing ports.

### Local links

While a job changes a dependency in one repo and its consumer in another, the consumer must build against the dependency's job worktree, not its released version, and that override must never reach a commit. A `dependsOn` edge that names a `component` in another repo declares it once with `link`:

```yaml
components:
  - name: app                   # the consumer (this repo)
    path: .
    kind: app
    dependsOn:
      - component: engine-core
        type: build
        link:
          ecosystem: cargo      # cargo | cmake | npm
          name: engine-core     # the crate, FetchContent or package name
          source: crates-io     # cargo only, default crates-io: the [patch.<source>] table (a registry name or a git url)
          path: crates/core     # optional: the directory in the dependency's repo; default the dependency component's path
          manifest: Cargo.toml  # optional: the consumer's manifest an interim pin goes in, relative to its repo (see Interim strategies)
  - { name: engine-core, repo: engine, path: crates/core, kind: library }
```

- **Active rule.** A link is active for a job only when the consumer's repo and the dependency's repo are both [job repos](architecture/job-repos.md) with a worktree Forge trusts (the root's is `<worktrees.root>/<id>`, a member's the path Forge computes for it, never a value read from job.json alone) and `<dependency worktree>/<path>` is a directory there. Otherwise it is inactive, with a reason. `forge job links <id>` lists every declared link and its state (docs/CLI.md "Local links"). Links are recomputed before every command and never stored, so removing a job repo removes its links.
- **What a command gets.** Before `forge run` (with or without `--repo`), each verify step and verify's e2e, Forge renders the links of the repo the command runs in into `<jobDir>/links/<repo or _root>/`, never into a worktree, rewriting a file only when it changed and deleting what is no longer needed. Then it runs `PATH=<that dir>/bin:"$PATH"` at the start of the command, after the login profile when `commandEnv.loginShell` sources one, so a profile that puts `~/.cargo/bin` first cannot shadow the shims, and calls through PATH from make, scripts or `cargo xtask` go through them too:
  - **cargo** (an active cargo link): `cargo-links.toml` holds a `[patch."<source>"]` table per source with `"<name>" = { path = "<dir>" }`, and the `cargo` shim runs the real cargo with `--config <that file>` (a leading `+toolchain` stays first). `FORGE_CARGO_CONFIG` holds its path.
  - **cmake** (any declared cmake link): a configure (no `--build`, `--install`, `--open`, `-E`, `-P`, `--workflow`, `--find-package`, `--help`, `-h`, `--version` or `--system-information`) gets `-DFETCHCONTENT_SOURCE_DIR_<NAME>=<dir>` per active link and `-UFETCHCONTENT_SOURCE_DIR_<NAME>` per inactive one, `NAME` upper-cased; the `-U` clears what an earlier configure cached once a link goes away, so declaring a link hands that cache variable to Forge. `FORGE_CMAKE_ARGS` holds the same arguments as quoted shell words.
  - **npm** (an active npm link): after an `install`, `i`, `in`, `add`, `ci`, `clean-install`, `ic`, `install-clean`, `update`, `up` or `upgrade` that passes, the shim runs `npm install --no-save --no-audit --no-fund --install-links=false <dirs>` in the same directory, so `node_modules/<name>` is a symlink into the dependency's worktree and neither `package.json` nor the lockfile is written.
- **Lockfiles.** A cargo `[patch]` makes cargo rewrite `Cargo.lock`, so with active cargo (or npm) links Forge snapshots every tracked `Cargo.lock` (or `package-lock.json` and `npm-shrinkwrap.json`) in the consumer's worktree first and writes back any that changed or went missing after the command, pass or fail; verify does it once per repo around its groups. The result's `restored` lists them and a `link-lockfiles-restored` event is logged. Your own uncommitted lockfile edit, made before the run, is what the snapshot holds, so it survives.
- **Not linked.** A command that calls a tool by absolute path bypasses the shims (use the env vars), and background commands (`forge run --background`, the dashboard's Run) and `worktrees.setup` get no links. On native Windows Forge writes no shims; the env vars and `forge job links` still work.
- **Validation.** `link` must be a map with `ecosystem` `cargo | cmake | npm`; it is a problem on a `backing` edge, between two components of the same repo, with a `name` that fails its ecosystem's pattern (a crate name, a FetchContent name, an npm package name), with a `source` on a non-cargo link or one that is not `crates-io`, a registry name or an `https://`, `ssh://` or `git://` url without whitespace, quotes, backslashes or control characters, with a `path` that is absolute or has a `..` segment, with a `manifest` that is absolute, has a `..` segment or is not the ecosystem's file (`Cargo.toml` for cargo, `CMakeLists.txt` or a `*.cmake` file for cmake, `package.json` for npm), and when two links give one consumer repo the same ecosystem and name (and cargo source) with different dependency directories.
- **Downstream verification.** A consumer repo with a link to a repo the job changes is what [Downstream verification](#downstream-verification) adds to a job; without a link it would test the released library, so it is skipped.
- **Never committed.** Verify's integrity report flags added lines that carry a local override (an absolute path of a worktrees root or of `.forge/jobs`, `FETCHCONTENT_SOURCE_DIR_`, a `[patch` table in a `.cargo/config(.toml)`, or a `file:`/`link:` dependency in `package.json` that is absolute or leaves the repo) as blocking under `verifyIntegrity: block` (see [Verify integrity](#verify-integrity)).

### Config sinks

Projects take their configuration in different ways: environment variables, `.env` files, `config.json`, generated files. A component's `config` lists its **config sinks**, and Forge renders every one of them with the job's values right before it runs that component's command, so the component always reads the job's port and id wherever it expects them. Each sink is a map with exactly one kind key:

```yaml
components:
  - name: api
    path: services/api
    kind: service
    commands: { test: "npm test", dev: "npm run dev" }
    config:
      - env:                                   # injected into the command's environment; nothing on disk
          PORT_HTTP: "{port}"
          API_BASE: "http://localhost:{port}"
      - env-file: .env.local                   # written as NAME=value lines
        values: { JOB_ID: "{job}" }
      - file: { path: config.json, format: json, mode: merge, from: config.example.json }
        values: { server: { port: "{port}", name: "{job}" } }
      - file: { path: app.toml, format: toml, mode: template, from: app.toml.template }
      - command: "node scripts/write-config.mjs" # a project script; gets values as env and JSON on stdin
        values: { PORT_HTTP: "{port}" }
```

- **`env`**: a map from variable name to a string expression, merged into the command's environment over the inherited one. Nothing is written to disk.
- **`env-file`**: a path, plus `values`, a flat map of names to string expressions, written one `NAME=value` line per entry in `values` order. A value matching `^[A-Za-z0-9_./:@%+,-]*$` is written bare; any other is double-quoted with `\\`, `\"` and `\n` escaped. Quoting is for dotenv loaders, which read the value literally: `$`, backticks and `!` are not escaped, so a shell that `source`s the file expands them.
- **`file`**: `{ path, format: json | yaml | toml, mode: template | merge, from? }`, plus `values` for merge mode.
  - `template`: `from` is required and `values` is not allowed. The text of `from` is filled with expressions and written to `path`. A `json` result must parse, or the render fails naming `from`; yaml and toml output is not parsed.
  - `merge`: `values` is required: a nested map whose leaves are strings (expressions), numbers, booleans or null. The base is `from` when given, otherwise the current file at `path` when it exists, otherwise `{}`. `values` are deep-merged over the base: maps merge key by key, and arrays and scalars from `values` replace. The result is written in `format`: 2-space JSON with a trailing newline, or YAML through Forge's own writer (the base must stay in the YAML subset config.yml itself uses: no anchors, tags or multi-document streams). Merge is for `json` and `yaml` only: Forge has no TOML parser, so `toml` with `mode: merge` is a validation problem; use `mode: template`.
- **`command`**: a shell command (with the same `{job}`, `{port}`, `{worktree}`, `{branch}` and `{base}` placeholders as other commands), plus optional `values`, a flat map like env-file's. It runs in the component's directory before the configured command, with the command's environment plus the values as variables and `JSON.stringify(values)` on stdin. Its output goes only to `<jobDir>/logs/config-<component>-<timestamp>-<i>.log`. A non-zero exit stops everything: `config sink command <i> of component "<c>" exited <n>; see <log path>`.

Every path (`env-file`, `file.path`, `file.from`) is relative to the component's directory (`<worktree>/<path>`), the same cwd its commands run in.

**Expressions.** An expression is `{name}` inside a string value. The roots are `{job}` (the job id), `{port}` (the job's port, a number, or null when the job has none), `{worktree}` (the absolute path of the job's checkout), `{branch}`, `{base}`, `{component.name}`, `{component.path}` and `{component.dir}` (the absolute `<worktree>/<path>`). `{secret.NAME}` is the value of the declared secret `NAME`, always a string, read from its source only when the render reaches it ([Secret references](#secret-references)). `{endpoint.…}` and `{backing.…}` are reserved for [endpoints](GLOSSARY.md) and backing services: using one passes validation but fails the render with the issue to watch (`{endpoint.api} needs endpoints (#195), which this Forge does not support yet`).
- **Typing.** A string that is exactly one expression takes the expression's type: `"{port}"` becomes the number `4123`, or `null` without a port. Any other string is interpolated into a string, and null interpolates as the empty string. In `env`, `env-file` and `command` values everything is stringified, with null as `''`. Quote the expression in YAML (`"{port}"`): unquoted, a YAML parser reads `{port}` as a map, and validation says so.
- **In config values**, any `{x}` whose `x` looks like an identifier path (`^[A-Za-z_][A-Za-z0-9_.-]*$`) must be a known or reserved root or a `{secret.NAME}` naming a declared secret, or validation reports it. Braces around anything else (`{"a":1}`) are literal.
- **In template files**, only known and reserved roots and `{secret.NAME}` are recognised, and any other `{…}` is left untouched, so JSON objects, TOML inline tables and literal braces survive. A substituted string is escaped as the content of a double-quoted JSON string, valid inside double quotes in JSON, YAML and TOML basic strings; a number or null is written bare.

**When sinks apply.** Every time Forge prepares a command for a job whose selected component (the one root-repo component its `services` names) has `config`, it renders all of that component's sinks in list order before the command starts: `forge run <job> <name>`, each `forge verify` step (and checkout `run` steps, which go through it) and `forge run <job> <name> --background` (a reused live process renders nothing). `worktrees.setup` and member-repo commands never render sinks, and a job with no component or several runs the top-level commands with none. Sinks are re-rendered on every command, so a file always matches the current config and job values; a file whose bytes and mode are already correct is not rewritten, and writes go through a randomly named temp file opened exclusively (an entry planted at that name fails the write instead of being followed) plus rename, so a reader sees either the old file or the new one. When sinks were applied, `forge run`'s result (and the verify step) gains `config: { component, env, files, commands, secrets }`: the env names, the worktree-relative paths of the rendered files, how many command sinks ran and the names of the secrets the render resolved (sorted, never their values), and one `config-sinks` event with the same fields is logged per prepared command. No rendered value appears in output, errors, events, logs or `runtime.json`, and a secret value a command prints is redacted from what Forge keeps of its output ([Secret references](#secret-references)).

**Git-ignored rule.** An output path (`env-file` or `file.path`) must be git-ignored and untracked in the job's checkout (`git check-ignore` says so, asked about the file's real location, so a parent symlink inside the worktree can't land an ignored path on a tracked file), or the run is refused: `config sink path services/api/config.json must be git-ignored and untracked; add it to .gitignore` (with the real location in parentheses when a parent symlink made it differ). This keeps rendered job values out of commits and out of verify's worktree-clean gate; Forge writes nothing to `.git/info/exclude`. Rendered files are written with mode `0600`. The checkout is treated as hostile: a symlink at the output path is replaced by a regular file, never followed; a parent directory that resolves outside the worktree is refused (missing ones are created); a `from` that is a symlink or a hard link, is not a regular file, resolves outside the worktree or is missing is refused, naming the path, and so is an output path that is a hard link when a merge with no `from` would read it as its base (`config sink path services/api/config.json must not be a hard link`); a merge base that doesn't parse is refused naming the file, with the parser's message for a `from` file but only a fix hint for the previous render at `path` (that file holds job values, and a parser quotes the text around the error); and a job whose stored `worktree` is not the path Forge computes for it is refused (`config sinks need the job's own worktree`). Each refusal stops before the configured command runs.

**Validation** (`forge config validate`, `forge doctor`, Settings; `forge run` and `forge verify` load config without validating it, so they run the same checks on the selected component's sinks before rendering and refuse with `config_invalid`: `config sinks are invalid: <problems>`) names each malformed sink as `components "<c>".config[<i>]`: a sink with no kind key or two, a non-list `config`, an absolute, empty or `..` path, an unknown `format` or `mode`, `toml` with `merge`, `template` without `from` or with `values`, `merge` without `values`, a variable name outside `^[A-Za-z_][A-Za-z0-9_]*$` or starting with `FORGE_` or equal to `PORT` (Forge sets those itself), a non-string `env`, env-file or command value, a merge `values` leaf that is an array (or a `__proto__`, `constructor` or `prototype` key), an unknown expression root, a `{secret.NAME}` naming no declared secret (`components "api".config[0].env.DB names undeclared secret {secret.NOPE}; declare it under secrets`), an empty `command`, and `config` on a component whose `repo` is set (a member repo has no checkout in the job's worktree).

**Migration** (config `schemaVersion` 19 → 20): nothing changes. v20 adds `components[].config`, absent by default; the bump lets older Forges refuse a config whose sinks they would ignore. `forge migrate` writes the new version.

### Release strategy

Each repo writes down how it releases, so the Foreman and humans read one place instead of guessing: its **versioning**, the **mechanism** (tool) that cuts a release, the **registry** it publishes to, and its **cadence**. The keys sit beside `interim` (below) in the top-level `release` for the root repo and in `repos[].release` for each member, with the same names and values. A single-repo project declares its strategy by editing only `release:`. `forge release plan` reads `mechanism`, `command`, `registry`, `cadence` and `publish` to build a release plan, and `forge release run` runs it ([RELEASES.md "Releasing a project"](RELEASES.md#releasing-a-project)); validation and `forge doctor` read every key. `versioning` is documentation: each mechanism's own tool decides the version.

```yaml
release:
  interim: local
  versioning: semver
  mechanism: tag
  command: npm run release     # required with mechanism: tag, refused otherwise
  registry: none
  cadence: on-merge
repos:
  - name: engine
    remote: git@github.com:acme/engine.git
    defaultBranch: main
    release: { interim: git-ref, versioning: semver, mechanism: cargo-release, registry: crates.io, cadence: manual, publish: confirm }
```

| Key | Values | Default | Meaning |
|---|---|---|---|
| `versioning` | `semver`, `calver` | `null` | How version numbers are chosen. |
| `mechanism` | `release-please`, `cargo-release`, `changesets`, `tag` | `null` | The tool that cuts a release; `tag` means a git tag made by the repo's own `command`. |
| `command` | a one-line string, at most 1000 characters | `null` | The command a human runs to release; read only with `mechanism: tag`. `forge release run` runs it, after asking unless `publish: allow`; doctor never does. Support bundles redact it. |
| `registry` | `crates.io`, `npm`, `none` | `null` | Where released packages are published (`none`: a tag or GitHub Release only). |
| `cadence` | `on-merge`, `scheduled`, `manual` | `null` | When a release happens: every merge to the default branch, on a timer (usually CI), or when a human decides. |
| `publish` | `confirm`, `allow` | `null` | Whether `forge release run` asks on a terminal before each of this repo's publish steps (`confirm`, and `null`) or runs them without asking (`allow`). With `allow`, an agent session that runs `forge release run` publishes too: set it only where that is acceptable. Only a hand edit of `.forge/config.yml` sets it: Settings does not edit it. |

Every key is optional, and `null` or absent means undeclared ("unknown"): nothing defaults to a value, and doctor runs no check for a repo with no `mechanism`. A member's `release` may be absent, `null`, or a partial map; one without `interim` still has its other keys checked. Unknown keys inside `release` are ignored, and combinations (such as `cargo-release` with `registry: npm`) are not cross-checked.

**Validation** (`forge config validate`, `forge doctor`'s `config valid`, `forge init write`, Settings diagnostics), one message per problem, where `<at>` is `release` or `repos "<name>".release` (`repos[<i>].release` for an unnamed entry) and `<v>` is the value as JSON, cut at 120 characters (`nothing` when absent):

- `<at>.versioning must be one of semver | calver (got <v>)`
- `<at>.mechanism must be one of release-please | cargo-release | changesets | tag (got <v>)`
- `<at>.registry must be one of crates.io | npm | none (got <v>)`
- `<at>.cadence must be one of on-merge | scheduled | manual (got <v>)`
- `<at>.publish must be one of confirm | allow (got <v>)`
- with `mechanism: tag`, a `command` that is absent, not a string, empty after trimming, over 1000 characters, or contains a control character (a newline included): `<at>.command must be a one-line command of at most 1000 characters when mechanism is tag (got <v>)`
- with any other mechanism, or none, a `command` that is set: `<at>.command is only read when mechanism is tag; remove it or set mechanism: tag`

**Doctor.** `forge doctor` (and Settings › Diagnostics) adds a `release mechanism` check for the root when `release.mechanism` is set and the top-level `release` validates, then a `release mechanism <name>` check per `repos` entry with a mechanism, in config order, when `repos` validates; they follow the `repo <name>` checks. A member is checked in its `.forge/local.yml` clone, `<dir>` below (the root repo for the root check). Doctor only looks: it never runs `command`, the tool, or the tool with `--version`, and finds tools by `stat` and access checks alone. PATH entries that are empty or relative are skipped, so the current directory never supplies a tool; on Windows each `PATHEXT` extension is tried.

| Mechanism | Looks for |
|---|---|
| `release-please` | `release-please` in `<dir>/node_modules/.bin`, then on PATH |
| `changesets` | `changeset` in `<dir>/node_modules/.bin`, then on PATH |
| `cargo-release` | `cargo-release` on PATH |
| `tag` | `git` on PATH, and the program `command` runs (below) |

| Situation | Result | Detail |
|---|---|---|
| every tool found | passes | `<mechanism>: <tool> at <path>` (tag: `tag: git at <path>, <program> at <path>`) |
| a tool missing, `cadence` unset or `manual` | fails | `<mechanism>: <tool> not found in <dir>/node_modules/.bin or on PATH; install it: <hint>` (`not found on PATH` for a PATH-only tool, `not found at <path>` for a program given as a path) |
| a tool missing, `cadence` `on-merge` or `scheduled` | warns | the same, plus `; cadence <c> usually releases from CI, so this matters only to release from this machine` |
| a `tag` command whose program can't be told | warns | `tag: cannot tell which program release.command runs (<reason>); checked git only` (a missing git still fails, or warns by cadence) |
| a member with no `local.yml` entry, or whose path is not a directory | warns | `<mechanism>: <name>'s clone is not resolved (see the repo <name> check); not checked` |

The hints: `npm install --save-dev release-please`, `npm install --save-dev @changesets/cli`, `cargo install cargo-release`, `install git`, and for a tag command's program `install <program> or fix release.command`. The program is `command`'s first word after any leading `NAME=value` assignments, with quotes removed (`'my tool' x` runs `my tool`). Doctor can't tell when the command has an unterminated quote, has no word after the assignments, contains any of `` $ ` ( ) ; | & < > `` anywhere, has any of `* ? [ ] { } ~` in the program, the program is a shell builtin or keyword (`cd . source exec eval export set unset if for while until case command builtin time !`), or, on Windows, the program is a network (UNC) path starting with `\\` or `//`. A program containing `/` (or `\` on Windows) is resolved against `<dir>` and must be a regular file (executable outside Windows); any other is looked up on PATH.

**Forge's own release** ([RELEASES.md](RELEASES.md)) maps onto these keys as `versioning: semver`, `mechanism: tag` (`release.yml` tags `v<version>` on a merge to `main` that changes the version; the `command` would be what a human runs by hand, such as `git tag v<version> && git push origin v<version>`, quoted as one string), `registry: none` (a GitHub Release, no package registry) and `cadence: on-merge`. Forge's own `.forge/config.yml` does not declare them.

**Migration** (config `schemaVersion` 15 → 16): nothing changes. v16 adds `release.versioning`, `release.mechanism`, `release.command`, `release.registry` and `release.cadence` (and the same keys on `repos[].release`), all unset by default; the bump lets older Forges refuse a config whose release strategy they would ignore. `forge migrate` writes the new version.

**Migration** (config `schemaVersion` 16 → 17): nothing changes. v17 adds `release.publish` (and `repos[].release.publish`), unset by default, which `forge release run` reads as "ask first"; the bump lets older Forges refuse a config whose publish policy they would ignore. `forge migrate` writes the new version.

### Interim strategies

A multi-repo job's consumer PR has to point at *something* while its dependency's change is unmerged or unreleased, and projects release differently, so each dependency repo has an **interim strategy**. An **edge** is a consumer job repo and a dependency job repo, from `components[].dependsOn` (the merge order [Job repos](architecture/job-repos.md) uses, transitive through repos outside the job); its **links** are the `link`s joining the two repos. A verify-only member is unchanged, so it is never a dependency. The strategy is per dependency and every edge into it shares it, resolved as: the job's override (`forge job repo interim <id> <name>|--root <strategy>`, human-only), then config (`repos[].release.interim` for a member, the top-level `release.interim` for the root repo), then `local`.

```yaml
release:
  interim: local               # the root repo as a dependency
repos:
  - name: engine
    remote: git@github.com:acme/engine.git
    defaultBranch: main
    release: { interim: git-ref }   # optional; absent or null is local
```

| Strategy | What the consumer's PR points at | What Forge does |
|---|---|---|
| `local` (default) | nothing CI can resolve: local links only | Publishes and pins nothing. `forge pr open` creates the consumer's PR as a draft, whatever `pr.draft` or `--draft` says (an existing PR is left as it is), and step never auto-merges the job (PR4 falls through to PR5). The draft stays one until a human records the dependency's release (`forge job interim release`, below) and, when the edge has links, verify has bumped the consumer to it: until then `forge pr ready` and `forge pr merge` refuse the consumer. |
| `sequential` | the dependency after it merges | `forge pr open` opens the dependency's PR and defers the consumer's (not pushed, no PR) until GitHub reports the dependency's PR `MERGED`; then `forge pr sync` resumes the job (`reopen: true`) and the next `forge pr open` opens it, as a draft until a human records the dependency's release (`forge job interim release`); after that a new consumer PR follows `pr.draft` and `--draft` again. Merge opens the consumer's PR; the recorded release lets it leave draft (`forge pr ready`) and merge. |
| `git-ref` | the dependency's commit | `forge verify` writes the pin into the consumer's manifest and commits it in the consumer's worktree: cargo, a `[patch."<source>"]` entry `"<name>" = { git = "<remote>", rev = "<sha>" }` in one block between `# forge:interim begin` and `# forge:interim end`; cmake, the one `GIT_TAG` of the one `FetchContent_Declare(<name> …)`; npm, `git+<url>#<sha>` in every dependency section that has the package. |
| `canary` (npm only) | a published pre-release, `<major>.<minor>.<patch>-canary.<sha12>` | `forge verify` pins that exact version (not the moving `canary` dist-tag, so the consumer's CI is reproducible); `forge pr open` opens the dependency's PR and defers the consumer's until a human publishes the canary with `forge job interim publish <id> <name>|--root --confirm`; it and `forge release run` are the only commands in Forge that publish anything. |

- **The manifest** is the link's `manifest`, or the ecosystem's file (`Cargo.toml`, `CMakeLists.txt`, `package.json`) in the consumer component's `path`. The remote is the member's `remote`, or the root's `git.remote` URL; an absolute path becomes `file://<path>` (one in your home directory leaves the edge `blocked`, since a pushed manifest must not name it), `user@host:path` becomes `ssh://user@host/path`, and a URL loses its password under every scheme, and its whole `user:password@` under http(s).
- **Verify** refreshes the pins first, dependencies first, before it reads any HEAD: when `aiAttribution` is `forbid` it scrubs the dependency's branch as `pr open` will (so the pinned sha is the one pushed), then commits the changed manifests as `forge: interim pins for job <id>`. Nothing is committed when nothing changed, or when a worktree involved is dirty (`worktree-clean` then fails the run). A pin that can't be written (no link, a `[patch."<source>"]` table outside the Forge block, zero or several matching `FetchContent_Declare` or `GIT_TAG`, an npm package below its repo's root, a dependsOn cycle) fails the `interim` step, which runs after `protected` and, like it, stops every configured step. With only `local` and `sequential` edges verify has no `interim` step.
- **`forge pr open`** refuses before pushing anything when an edge is blocked, and with `interim_stale` (hint `forge verify <id>`) when a pin in the checked commits is not the dependency's checked HEAD. It opens member PRs dependencies first, pushes the root's branch before any member's when the root is a git-ref or canary dependency, and lists what it held back as `deferred: [{ repo, why, waitingOn, version? }]` (a `pr-deferred` event). A repo that depends on a deferred one through a sequential, git-ref or canary edge is deferred too.
- **Publishing a canary** (`forge job interim publish`) is refused in a daemon session, with `--confirm` when stdin is not a terminal, for a repo that is not the dependency of a canary edge whose links are all npm, unless the repo's HEAD is the one this round's last verify run passed on and git shows it on the job's branch, and for a package that tracks a symlink or npm, yarn or pnpm config anywhere (`.npmrc`, `.yarnrc*`, `.pnpmrc`, matched in any case and Unicode form); the secret scan runs over its commits (`verifySecrets: block` refuses a finding or an incomplete scan). Without `--confirm` it only lists what it would publish. With it, each npm link's package is exported from the verified commit's git objects into a fresh temporary directory outside the repo (nothing untracked or ignored, no checkout filter; removed afterwards), every exported file is scanned for secrets (base content ships too), its `package.json` `name` must equal the link's, its `version` is set to the canary version and its `publishConfig` is dropped, and `npm publish <dir> --ignore-scripts --workspaces=false --tag canary --prefix <empty dir>` runs from that empty dir with no shell and the global config pointed at an empty file, so none of the package's lifecycle scripts runs and npm reads only your user config (`~/.npmrc` or `npm_config_userconfig`), never project or global config. Each publish logs `canary-published`; a version already published is skipped, and a job parked for it resumes.
- **Limits.** crates.io refuses to publish a crate with git dependencies, so `git-ref` suits consumers that are not published themselves. Lockfiles (`Cargo.lock`, `package-lock.json`) are not rewritten for a pin, so `cargo --locked` or `npm ci` in the consumer's CI needs a lockfile update by hand. npm installs a git dependency only from its repo's root, so an npm `git-ref` needs the package there. `canary` is npm-only, and is refused for a dependency a cargo or cmake link depends on. Submodule bumps are not a `git-ref` form. The seeded [release gate](#release-gate) check fails while a pin remains; recording the dependency's release (below) is what replaces the pin. The release bump's lockfile refresh needs `cargo` (for a tracked `Cargo.lock`) or `npm` (for a tracked `package-lock.json`) on PATH where verify runs, and registry access, since it resolves the released version; on native Windows an `npm` that resolves to a `.cmd` can't run without a shell, so the step fails and you refresh that lockfile by hand. The bump refuses what it can't rewrite safely: a renamed cargo dependency (`foo = { package = "lib" }`), a multi-line inline table, a dotted `<name>.version` key and an entry with no version. A changed lockfile is a default [protected path](#protected-paths), so `forge pr open` asks a human to approve the bump commit's lockfile.
- **Inspect.** `forge job interim <id>` lists every edge with its strategy, `source` (`job` or `config`), links, `state` and a one-line `detail`, with no network call: `held` (local), `waiting` (an unmerged sequential dependency, an unpublished canary), `ready`, `blocked` (can't be pinned or bumped), `stale` (verify has not pinned the dependency's HEAD yet, or, after a recorded release, the consumer's manifests at HEAD don't name it: `<files> in <consumer> does not name the released version <V> of <dependency>; run: forge verify <id>`) or `released` (a recorded release the manifests at HEAD name; a release edge also carries `release: <V>`). Its `gates` list each edge's release gate: `ci` (git-ref, canary, no release recorded: the seeded check guards it), `held` (local, sequential, no release recorded), `bump-due` with the `version` (a release is recorded, the edge has links, the consumer's PR is not merged, and no `interim-bumped` for that version came after the record) or `released` with the `version`.
- **Recording a release.** `forge job interim release <id> <name>|--root <version>` is how a human says the dependency of an edge of any strategy shipped. It is refused in a daemon session (before anything is read), for a done or cancelled job, an unknown repo, a repo that no edge depends on, a version that is not semver (`1.2.0`, `v1.2.0`, `1.2.0-rc.1`, at most 120 characters) or names a canary, and a dependency whose recorded PR is not `MERGED` (run `forge pr sync <id>` first). It logs `interim-released` `{ repo, version }` (`repo` null for the root) and returns `{ id, repo, version, recorded, clear, bump, resumed? }`: `clear` lists the consumers whose gates are all `released`, `bump` the ones with a `bump-due` gate, and `resumed: true` says a job waiting on `pr-review` at stage `pr` was set running (with a `resume` request when the daemon is on and none is pending; no other wait is touched). The same version again records nothing (`recorded: false`), and a later different version wins and makes the gate `bump-due` again. A `--job` `forge release run` records it too (docs/RELEASES.md "Consumers after a release").
- **The release bump.** Once a release is recorded, an edge with links whose consumer PR is not `MERGED` is a *release edge*: `forge verify`'s interim pre-step writes the released form instead of a pin, alongside any pins in one consumer pass and one commit. cargo: the crate leaves the Forge `[patch]` block (the block goes when it is left empty), and every entry for it in `[dependencies]`, `[dev-dependencies]`, `[build-dependencies]`, `[workspace.dependencies]` and `[target.*.dependencies]` (a string, a one-line inline table's `version`, a `[dependencies.<name>]` table) gets the requirement, its `=`, `^` or `~` kept, a leading `v` and `+build` dropped, `workspace = true` left alone. cmake: the `GIT_TAG` becomes the version exactly as recorded (`v1.2.0` stays `v1.2.0`), and the tag must exist in the dependency's worktree or clone (`tag <version> is not in <dependency>; fetch its tags, or record the version as the tag names it`). npm: `^`/`~` kept before a numeric range, the bare version for an exact one, `^<version>` for anything else (a git, canary, file or tag spec). When a manifest changed and a tracked `Cargo.lock` or `package-lock.json` sits in its directory or an ancestor, Forge refreshes it with a fixed argv and no shell: `cargo update -p <name> --precise <version>` in the manifest's directory, or `npm install --package-lock-only --ignore-scripts --no-audit --no-fund` in the lockfile's (10-minute timeout). A missing tool, a non-zero exit, a timeout, a lockfile that isn't a regular file, or a refresh that changes any other path puts the consumer's manifests and lockfiles back at their HEAD text, commits nothing, and fails the `interim` step with `<consumer> on <dependency> (release <V>): <tool> <why>: <output tail>`. Otherwise the manifests and lockfile are committed as `forge: release bump for job <id>`, one `<dep>: release <version>` line per edge (pins in the same commit keep their lines), the step's `reason` says `release bump committed in <repo> (<sha12>)`, and verify logs `interim-bumped` `{ repo, dependency, version, sha }` once per consumer, dependency and version, which turns the gate `released`. A recorded release whose dependency's recorded PR is not `MERGED` fails the step and writes nothing. A consumer whose PR already merged is left alone, and a dependency with no links goes straight to `released`. Verify's configured steps still build through local links; the lockfile refresh and the consumer's CI on the pushed commit prove the released version. Then step pushes the bumped commit (`forge pr open`, PR3, after PR9 ran verify) and, for a draft consumer whose gates are all `released`, runs `forge pr ready <id> --repo <name>|--root` (PR10).
- **What the gates block.** `forge pr ready` refuses a `held` or `bump-due` consumer, and one whose manifests at HEAD don't name a recorded release (git, no network), with code `release_gate` before any `gh` call (bump-due: `<consumer>'s manifests don't name <dependency>'s released version <V> yet; run: forge verify <id>, then forge pr open <id>`). `forge pr merge` refuses them after the merge-order check (`action: refused`, `reason: release`; `--now` never bypasses it). `forge pr open`'s `interim_stale` covers release edges too. Step never auto-merges a job while a gate is `held` or `bump-due`, a `local` edge's gate is not `released`, or one of its PRs is a draft. events.jsonl is writable outside the CLI, so only records whose `repo`, `dependency` and `version` pass these checks count; a well-formed `interim-released` written by hand still opens a gate, and a forged `interim-bumped` is caught by the git check in `pr open` and `pr ready` (docs/architecture/untrusted-input.md).

#### Release gate

`canary` and `git-ref` leave a pin in the consumer's manifest, and nothing in Forge stops a human from merging the consumer with that pin still in it. So when `forge init write` writes a config where `release.interim`, or any `repos[].release.interim`, is `git-ref` or `canary`, it seeds a check into the repo (each file only when it doesn't exist yet) and warns you to commit both and make the check required:

- `.forge/ci/release-gate.mjs`: plain Node (18 or later), no dependencies. It reads the tracked files (`git ls-files`, so nothing untracked or ignored) and fails on an interim reference. The `RULES` table at its top holds one rule per ecosystem (edit it to match your project): `cargo`, a `# forge:interim begin` line, or a `rev = "<full commit id>"` in any `[patch…]` section, in a `Cargo.toml`; `cmake`, a `GIT_TAG` set to a full commit id in a `CMakeLists.txt` or `*.cmake`; `npm`, a `git+…#<sha>` spec or a `-canary.` version in any dependency section of a `package.json`. `IGNORE` lists path regexes it skips (`node_modules/` by default). It exits 0 with `release gate: no interim references in <n> manifests`, 1 with one `<path>:<line>: <ecosystem>: <why>: <text>` line per finding, and 2 (`release gate: cannot check: <reason>` on stderr) when it can't check, such as a `package.json` that isn't a JSON object or a tracked manifest that is a symlink (it never follows one): it fails closed.
- `.github/workflows/forge-release-gate.yml`: the `release gate` job, on `pull_request` and `merge_group`, with read-only `contents` permission, a pinned `actions/checkout` without persisted credentials, and `node .forge/ci/release-gate.mjs`; no setup or install.

Forge never changes repository settings: mark the `release gate` check required in branch protection yourself. Only the root repo is seeded; copy both files into a member repo that consumes a git-ref or canary dependency, at the same paths. `.forge/ci/**` is a refuse default of [`policy.protectedPaths`](#protected-paths), so no job can edit the script, and the workflow is already covered by `.github/workflows/**`. A config written before the gate existed keeps its own `protectedPaths` list, so when `init write` seeds the gate and no refuse rule already matches `.forge/ci/release-gate.mjs`, it appends `{ paths: [.forge/ci/**], action: refuse }` to that list. The root's rules apply to every member a job commits to, so a hand-copied script at `.forge/ci/release-gate.mjs` in a member is refused too; if you copy it anywhere else, or edit the root's list by hand, keep a refuse rule that matches the script's path. A job's own override (`forge job repo interim`) never seeds anything.

**Migration** (config `schemaVersion` 12 → 13): nothing changes. v13 adds `release.interim` (default `local`) and a link's `manifest`, absent by default; the bump lets older Forges refuse a config whose interim strategy they would ignore. `forge migrate` writes the new version.

**Migration** (config `schemaVersion` 11 → 12): nothing changes. v12 adds `link` on `dependsOn` edges, absent by default; the bump lets older Forges refuse a config whose links they would ignore. `forge migrate` writes the new version.

**Migration** (config `schemaVersion` 9 → 10): `services` becomes `components`. Each service keeps its `name`, `path` (`.` when it had none), `commands`, `owners`, `notes` and any other keys, and gains `kind: service` and `dependsOn: []`, so every job runs the same commands from the same path as before. The migration happens in memory on every read; `forge migrate` writes it to disk. A config with no `schemaVersion` that still has `services` and no `components` is folded the same way. A v10 config that sets both is refused: `services was renamed to components in config schemaVersion 10; move its entries under components and delete services`.

## Repos

A project can span several repos: the **root repo**, which holds `.forge/`, and **member repos** such as the libraries an app builds on. `repos` lists the members; the root repo is implicit and never listed. It is edited by hand (it is not a `forge config set` key and Settings doesn't show it), and support bundles hide it like `resources`, since remotes can name private hosts. Each entry:

```yaml
repos:
  - name: ui-kit                               # required, unique; A-Z a-z 0-9 . _ -, starting with a letter or digit, at most 100
    remote: git@github.com:acme/ui-kit.git     # required: the clone url
    defaultBranch: main                        # required
    tracker: { kind: github, repo: acme/ui-kit }   # optional: kind github | none; repo is owner/name
    release: { interim: local, versioning: semver, mechanism: changesets, registry: npm, cadence: manual }   # optional; interim: canary | git-ref | local | sequential (see Interim strategies); the rest: see Release strategy
```

`tracker` defaults to the GitHub repo `remote` names: with no `tracker`, or `kind: github` without `repo`, the member's tracker is the `owner/name` of its `remote` on github.com (or `GH_HOST`), and a remote that names none (another host, a local path) means no tracker. `kind: none` turns it off. A member with a tracker has its ready issues offered by `forge next` after the root's and can start a job with `forge job from-ref owner/name#N`, which adds the member to that job; its issues get status labels only, never the root's GitHub Project ([Member repo trackers](TRACKERS.md#member-repo-trackers)).

Where each member is cloned differs per machine, so the paths live in **`.forge/local.yml`**, which `/forge init` gitignores and Forge never writes:

```yaml
repos:
  ui-kit: { path: ../ui-kit }
```

A relative path resolves against the root repo, a leading `~/` is the home directory, and an absolute path is used as is. `forge init write` adds a `local.yml` line to `.forge/.gitignore` when it lacks one (and lists the file in `written`); other lines are never touched.

**Validation** (`forge config validate`, `forge doctor`, `forge init write`, Settings diagnostics), one message per problem:

- `repos must be a list (got …)`; `repos[<i>] must be a map`
- a `name` that is missing or unsafe, a name listed twice (`repos "<name>" is listed more than once`), or the root repo's directory name (`repos "<name>" is the root repo; the root repo is implicit`)
- a `remote` that isn't a non-empty string of at most 2000 characters, starts with `-`, or contains whitespace or control characters
- a `defaultBranch` that isn't a safe branch name (`A-Z a-z 0-9 . _ / -`, starting with a letter or digit, at most 200 characters), or contains `..` or `//`, or ends in `/` or `.lock`
- a `tracker` that is set but isn't a map with `kind` `github | none`, or a `github` `repo` that isn't `owner/name`
- a `release` that is set but isn't a map, an `interim` outside `canary | git-ref | local | sequential`, or a `versioning`, `mechanism`, `command`, `registry` or `cadence` that [Release strategy](#release-strategy) refuses (the top-level `release` is checked the same way)
- `components "<c>".repo names unknown repo "<x>"` for a component whose `repo` names no entry

**Doctor.** When `repos` validates, `forge doctor` (and Settings › Diagnostics) adds one `repo <name>` check per member, after `config valid`, and always prints the fix:

| Situation | Result | Detail |
|---|---|---|
| no `local.yml`, or no entry for the name | fails | `no path in .forge/local.yml; clone it: git clone <remote> ../<name>, then add to .forge/local.yml: repos: { <name>: { path: ../<name> } }` |
| the path does not exist | fails | `missing clone at <path>; run: git clone <remote> <path>` |
| the path isn't the top level of a git clone | fails | `<path> is not a git clone; point .forge/local.yml at the clone's top-level directory` |
| the clone's `git.remote` remote is missing or points elsewhere | fails | `remote "<git.remote>" is <actual or missing>, expected <remote>; run: git -C <path> remote set-url <git.remote> <remote>` (`remote add` when missing; `<git.remote>` is `origin` by default, and `<actual>` is shown without any `user:password@`) |
| no local `defaultBranch` | warns | `no local branch <defaultBranch>; run: git -C <path> fetch <git.remote> <defaultBranch>:<defaultBranch>` |
| checked out on `defaultBranch` with uncommitted changes | warns | `<defaultBranch> has uncommitted changes (<n> paths) at <path>` |
| otherwise | passes | `<path> on <branch or detached>` |

Remotes match when they are equal after dropping any `user:password@`, a trailing `/` and `.git`, or name the same GitHub `owner/name` (`git@github.com:acme/x.git` and `https://github.com/acme/x` match). Paths are single-quoted when they contain anything outside `A-Za-z0-9._/~-`. A `local.yml` check appears only when that file has a problem: unparsable YAML, a `repos` that isn't a map, or an entry without a non-empty string `path` fails it (and every member then reads as having no entry), and names that aren't in `repos` give a warning. With no `repos` and no `local.yml` there are no new checks. Doctor only reads: it never clones, fetches or checks out, runs git with `core.fsmonitor=false` and `GIT_OPTIONAL_LOCKS=0` so `status` never rewrites a member's index, and never passes `remote` to git. After these checks come the `release mechanism <name>` checks for members that declare a mechanism ([Release strategy](#release-strategy)).

**Using a member in a job.** A human adds a member to one job with `forge job repo add <id> <name> [--verify-only]` (refused unless the member passes the doctor check above, and refused in a daemon session), or a job started from the member's own issue gets it at creation; the job then changes that repo too ([Job repos](architecture/job-repos.md)). `forge worktree create` makes the member's worktree at `worktrees.root` with `{repo}` set to the clone's directory name, resolved from the clone (by default `../<clone>.worktrees/<id>`), on the job's branch, or detached at `defaultBranch` for a verify-only member. A member's commands are its components' `commands` (`forge run <id> <cmd> --repo <name>`; `forge verify` runs each `verify` step as the member component's command, and skips a step none defines). `forge pr open` opens the member's PR in `tracker.repo` when `tracker.kind` is `github`, else in the `owner/name` its `remote` names on github.com (or `GH_HOST`). Members get no `worktrees.copy`, `worktrees.setup` or shared Cargo target; a member component of kind `service` or `app` is port-bearing like a root one ([Ports and endpoints](#ports-and-endpoints)), so its `--repo` commands get its port as `{port}` and `$PORT`, and a member `library` sees `{port}` empty. `policy.protectedPaths` applies to every member the job commits to exactly as to the root ("Protected paths" above).

**Member review panels.** A member that a job reviews (one not added `--verify-only`) brings its own lenses: `forge job panel` reads `review.panel` from the member clone's `.forge/config.yml`, with checklists from the clone's `.forge/reviewers/<name>.md`, never from the job's worktree of it. Each entry becomes the lens `<repo>:<name>` (review file `review/round-<n>/<repo>.<name>.md`), selected by its `always`, a `Suggested reviewers:` entry naming `<repo>:<name>`, its `when`/`paths` covering an Approach path under `<repo>/`, or its `paths` matching the member's changed files (repo-relative; reasons cite `<repo>/<file>`). **Subsumption:** an entry named like a root panel lens, with no `checklist:` and no `.forge/reviewers/<name>.md` in the clone, is not a lens of its own; its matches add reasons to the root lens, which reviews the combined diff. So a member that lists `code` with `paths: [src/**]` brings the root `code` lens in for its changes, and one with its own `realtime.md` gets `<repo>:realtime`. A member entry's `model`, `effort` and `needsApp` are ignored (`runtime.models.reviewer`, the reviewer effort layers, no app). A member config that is not a regular file, is over 256 KiB, isn't valid YAML or has a `review.panel` that isn't a list fails `forge job panel` with `repo <name>: …`; an entry with a bad name or `paths`, no checklist, or a `checklist` outside the clone is dropped and listed in the result's `problems`. A member without `.forge/config.yml` or `review.panel` adds no lenses.

**Downstream consumers.** A member that consumes, through a link, a repo the job changes joins the job verify-only on its own: see [Downstream verification](#downstream-verification).

**Migration** (config `schemaVersion` 10 → 11): v11 adds `repos`, empty by default; an older config gains `repos: []` (an existing `repos` value is kept for validation to judge), and a leftover `services` is still folded into `components`. The bump lets older Forges refuse a config whose member repos they would ignore. The migration happens in memory on every read; `forge migrate` writes it to disk.

## Downstream verification

When a job changes a library, every repo that consumes it can break, including repos the job never edits. `downstream` adds those consumers to the job as **downstream repos**: verify-only members ([Job repos](architecture/job-repos.md)) whose tests verify runs against the job's changes through [local links](#local-links). It is edited by hand; Settings shows the three keys locked, since turning the check off or capping it at 0 loosens a verification gate and `skip` names repositories.

```yaml
downstream:
  enabled: true     # default true
  max: 5            # default 5; 0 to 50 downstream repos per job
  skip: []          # repos names never added
```

- **Candidates.** The changed repos are the root and every member on the job that is not verify-only. A repo C is a candidate when a component in C has a `dependsOn` edge to a component in a changed repo. Only direct consumers count (a consumer of a consumer, or of a verify-only member, does not), only `repos` entries (the root is always on the job), in `repos` order, and a repo already on the job is neither added nor listed. Each candidate is added or skipped with one reason, the first that applies:

  | Rule | Reason |
  |---|---|
  | `enabled: false` | nothing is added or listed |
  | the name is in `skip` | `listed in downstream.skip` |
  | a human removed it from this job (`forge job repo remove` after its latest add) | `removed from the job by a human` |
  | no `link` joins C to a changed repo | `no link on its dependsOn edge to <repo>, so it would test the released library` |
  | no component of C defines a command for a `verify` step | `defines no verify step command` |
  | the job already has `max` downstream repos | `over downstream.max (<n>)` |
  | its clone fails doctor's member check | `repo <name>: <detail>` |

- **Adding.** In `build` and `verify`, step rule DS1 runs `forge job repo downstream <id>` (docs/CLI.md "Downstream verification") whenever a candidate is one the last check did not name; RP2 then creates the new members' detached worktrees. A clone that failed its check is not retried automatically: fix it and run the command again.
- **Verify.** Each `verify` step runs as the downstream repo's component command with its links applied, like any verify-only member. A downstream repo with no active link from a changed repo fails a `links` step and none of its configured steps runs. The report heads its section `# Downstream consumer <repo> · <sha>` and names each failing one after `VERIFY: FAIL`; `forge verify`'s result gains `downstream`, and the round goes back to the builder with `verify failed: downstream consumer <repo> failed <step>`.
- **Changing the consumer.** The builder fixes the library within the job, or proposes the consumer (`forge job repo propose <id> <repo> --reason "…"`). Approving that proposal promotes the downstream repo to an edited one: its detached worktree is removed (refused while it holds uncommitted or untracked changes or commits beyond its base) and recreated on the job's branch. Rejecting it leaves it verify-only.
- **Validation:** `downstream must be a map (got …)`, `downstream.enabled must be true or false (got …)`, `downstream.max must be an integer from 0 to 50 (got …)`, `downstream.skip must be a list of repos names (got …)` and `downstream.skip names unknown repo "<x>"`.
- **Single-repo projects** (no `repos`) have no candidates: nothing changes for them.

**Migration** (config `schemaVersion` 13 → 14): v14 adds `downstream`, on by default, so a v13 config gains `downstream: { enabled: true, max: 5, skip: [] }` (an existing value is kept for validation to judge), and existing multi-repo projects with links get downstream verification on upgrade. The bump lets older Forges refuse a config whose downstream settings they would ignore. `forge migrate` writes the new version.

## Checkout steps

Some tools read one fixed place rather than a job's address: a DAW loads plug-ins from one folder. `checkout` makes that place follow the job you focus (`forge focus <id>` or the dashboard's **Focus**). It is edited by hand (Settings shows it read-only). With no steps, focus is only a pointer, as before.

```yaml
checkout:                                   # default []
  - link: build/MyPlugin.vst3               # path in the job's worktree
    to: ~/Library/Audio/Plug-Ins/VST3/MyPlugin.vst3   # fixed path: absolute or ~/…
  - run: install-plugin                     # names a commands.* entry
    undo: uninstall-plugin                  # optional, names a commands.* entry
```

- **Steps.** Each step has exactly one of `link` or `run`. A `link` step needs `to` and has no `undo`; a `run` step may have `undo` and has no `to`.
- **Focusing a job** first undoes the steps recorded for the previous job (in reverse, best effort: each failure is reported, none blocks the switch), then applies the new job's steps in order:
  - **link**: the source is `<worktree>/<link>` of the job's own worktree (`<worktrees.root>/<id>`; a `worktree` in job.json pointing elsewhere fails the step). It must exist and its realpath must stay inside the worktree. The parent directory of `to` must exist (Forge never creates it). Anything already at `to` is renamed to `<to>.forge-aside`, never deleted, and an existing `<to>.forge-aside` fails the step. Then `to` becomes a symlink to the source.
  - **run**: runs the named command for that job exactly as `forge run <job> <name>` does, only in the job's own worktree (`<worktrees.root>/<id>`; a `worktree` in job.json pointing elsewhere fails the step and nothing runs, on apply and on undo), with a log under the job's `logs/` named `checkout-<name>-…` (`checkout-undo-<name>-…` for an undo) and a `command` event. A non-zero exit fails the step.
- **A failing step** undoes the steps applied so far, re-applies the previous job's steps when that job is still active and has its worktree, and leaves focus where it was. `forge focus` exits 1 and `POST /api/focus` answers 409 with a message such as `checkout[1] run install-plugin failed (exit 2); log: logs/checkout-install-plugin-….log; focus stays on 12-foo`.
- **Re-focusing** the job whose steps are applied does nothing. Focusing it again when its steps are not applied (say `checkout` was added after you focused it) applies them, which is how to re-run them.
- **Clearing focus** (`forge focus --clear`) undoes the recorded steps, also when nothing is focused any more. A job that finishes lets go of focus, but its steps stay applied until the next focus change, `--clear`, or `forge worktree remove` (and `forge sync`'s on-merge cleanup), which undoes them before deleting the worktree.
- **Undo** unlinks `to` only when it is still the symlink Forge made, then renames `<to>.forge-aside` back. A `to` you replaced since is left in place and reported. A run step's `undo` runs in that job's worktree; a step without one does nothing.
- **One switch at a time.** Each switch, `--clear` and worktree removal holds a lock (`.forge/locks/checkout`); another one waits up to 2 seconds and then fails. The lock counts as stale after 10 minutes, so keep run steps shorter than that: a second switch could otherwise start while a long one is still running.
- **The record** of what was applied is `.forge/runtime/checkout.json`, read without following symlinks and capped at 64 KiB. It only steers undo for targets and `run`/`undo` pairs the current config names, so a planted record can't rename, unlink or run anything else. Each step logs a `checkout` event (`phase: apply | undo | rollback`, `step`, `kind`, `ok`) on its job.
- **Validation** (`forge config validate`, `forge doctor`, `forge init write`, Settings) reports each problem as `checkout[<i>]…`: neither or both of `link` and `run`; a `link` that is empty, absolute or has a `..` segment; a `to` that is missing, not absolute or `~/…`, has a `..` segment or a NUL, or is `/`, `~` or `~/`; `undo` on a link step or `to` on a run step; a `run` or `undo` that names no non-null command in `commands` or a component's `commands`; and two link steps whose `to` resolve to the same path (`checkout[3].to repeats checkout[0].to`). A `checkout` that isn't a list is `checkout must be a list (got …)`.

**Migration** (config `schemaVersion` 14 → 15): nothing changes. v15 adds `checkout`, empty by default; the bump lets older Forges refuse a config whose checkout steps they would ignore.

## Backing services

Services under test need databases, caches and queues. `backing` lists them, and Forge gives each job its own container where state matters (`per-job`), one project container where it doesn't (`shared`), or just an address for something run elsewhere (`external`). Forge drives the Docker CLI (`docker` on PATH, its default context) and adds no dependency. The list is edited by hand: Settings has no field for it, and a support bundle hides its values, since images, env values and urls can carry hosts or credentials. With `backing: []`, the default, Forge never calls `docker`.

```yaml
backing:                                    # default []
  - name: postgres                          # ^[a-z][a-z0-9-]{0,31}$, unique
    isolation: per-job                      # required: per-job | shared | external
    image: postgres:16                      # required for per-job and shared
    ports: [5432]                           # container TCP ports; Forge picks the host ports
    env: { POSTGRES_PASSWORD: forge, POSTGRES_DB: app }
    volumes: [/var/lib/postgresql/data]     # container paths; each gets a named volume
    url: postgres://postgres:forge@{host}:{port}/app   # optional template
  - name: redis
    isolation: shared
    image: redis:7
    ports: [6379]
  - name: queue
    isolation: external
    url: amqp://mq.internal:5672            # required for external, used literally
```

- **Validation** reports each problem as `backing[<i>]…`: a `name` that doesn't match `^[a-z][a-z0-9-]{0,31}$` or repeats; an `isolation` that is missing or not one of the three; for `per-job` and `shared`, an `image` that is missing or doesn't match `^[A-Za-z0-9][A-Za-z0-9._/:@-]{0,254}$` (so never a leading `-`), `ports` that aren't at most 8 distinct integers from 1 to 65535, an `env` key that doesn't match `^[A-Za-z_][A-Za-z0-9_]*$` or a value that isn't a string, number or boolean or holds a NUL, CR or LF, `volumes` that aren't at most 8 distinct absolute paths of `A-Z a-z 0-9 . _ / -` with no `..` segment, and a `url` placeholder other than `{host}`, `{port}` (which needs a port) and `{port_<n>}` for an `n` in `ports`; for `external`, a missing `url` (a non-empty string of at most 500 characters with no whitespace or control characters) and any `image`, `ports`, `env` or `volumes`; and unknown keys. Once `backing` is non-empty, a component's `dependsOn: { backing: X }` must name a declared entry. Problems never show an env value, a url, or a `backing` value that isn't a list (any can hold credentials): they name the field and the problem.
- **Names and labels.** The project slug is `project.name` (else the repo directory's name) lowercased, with each run of characters outside `a-z 0-9 _ . -` turned into `-`. A per-job container is `forge-<job>-<rootLabel>-<name>` with volumes `forge-<job>-<rootLabel>-<name>-<i>`; a shared one is `forge-<project>-<rootLabel>-<name>` with volumes `forge-<project>-<rootLabel>-<name>-<i>`, where `<rootLabel>` is the checkout's `forge.root` label below, so two registered projects with one name or job id never share one. A container or volume under the name from before (`forge-<job>-<name>`, `forge-<project>-<name>`) whose labels say it is this checkout's, entry's and job's is still found and used, so an upgrade keeps running containers and shared data; new ones get the qualified name. Every container and volume Forge creates carries `forge.root=<first 12 hex of sha256 of the checkout's real path>`, `forge.backing=<name>` and `forge.isolation=<isolation>`, and per-job ones `forge.job=<job>`. Forge never reuses, starts or removes a container or volume whose labels say it belongs to another checkout, job or entry; bring-up fails with `container <name> exists and is not this job's` (`… this project's` for shared).
- **Ports.** Host ports come from `ports.base`/`ports.span` and bind to `127.0.0.1` only. A job reserves one per container port of each per-job entry, the project one per container port of each shared entry. No port is handed out twice: job ports (`port` and the per-component `ports`, [Ports and endpoints](#ports-and-endpoints)) and backing ports both skip every active job's `port` and `ports`, every port in any job's `.forge/jobs/<job>/backing.json` (active or not, since a cancelled job's container may still run) and every port in `.forge/runtime/backing.json` (the shared record), and every port the other projects registered in the machine index hold the same way, and both are chosen under the machine's lock (`<FORGE_HOME>/locks/ports`) and then the project's (`.forge/locks/ports`), so concurrent `worktree create`s never collide, in one project or across them. Both records are `{ "v": 1, "ports": { "<name>": { "<containerPort>": <hostPort> } } }`, written only by Forge; an entry naming an unknown service or port, or a host port out of range or repeated, is ignored and allocated again.
- **What commands see.** Every configured command Forge runs for a job (`worktrees.setup`, `forge run`, background servers, verify, component and member-repo commands, the regenerate build) gets, per entry, with `NAME` the name upper-cased and `-` as `_`: `FORGE_BACKING_<NAME>_HOST` (`127.0.0.1`; not for external), `FORGE_BACKING_<NAME>_PORT` (the host port of the first container port), `FORGE_BACKING_<NAME>_PORT_<containerPort>` and `FORGE_BACKING_<NAME>_URL` (the external `url`, or the template filled; unset without one). A managed entry whose ports were never allocated adds nothing. In command templates, `{backing.<name>.port}` is the first host port and `{backing.<name>.url}` becomes `"$FORGE_BACKING_<NAME>_URL"`, a quoted reference to the variable rather than the url's text: urls can hold shell metacharacters and credentials, and command text is logged. Builder and reviewer briefs get one `Backing services:` line with each entry's name, isolation and loopback port, never an env value or url.
- **Env values** reach `docker run` only through `--env-file`, a 0600 file in a fresh temp directory that is removed when the call returns. They never appear in argv, events, logs, results or errors. They are still visible to anyone who can reach the Docker daemon (`docker inspect` shows a container's env), so don't put a secret there that such users mustn't see.
- **Lifecycle.** `forge worktree create <job>` brings the job's services up after it allocates the job's port and before `worktrees.setup`, so migrations can run there. Bring-up is idempotent: a missing container is run (its named volumes created first with the same labels; `docker run` pulls the image), a stopped one started, a running one left alone; shared services start at most once, under a lock. The result lists `backing: [{ name, isolation, action: created | started | running | external | none, ok, error? }]`. On a failure, `action` is what Forge attempted (`created` for a missing container, `started` for a stopped one), or `none` when it failed before running or starting one: Docker missing or stopped, no free port, or a same-named container that isn't this job's. A failed service skips setup, makes the result `ok: false` and logs `worktree-setup-failed` with `backing: <name>`, and step rule I4 fails the job, as for a failed setup command. `forge worktree remove <job>` then runs `docker rm -f` on the job's per-job containers and `docker volume rm` on their volumes (only those labelled with this checkout and job; names come from the job id and config, never from `backing.json`) and deletes `backing.json`; its result gains `backing: { removed, volumes, ok, error? }` when the config has per-job entries or the job has a record. When teardown fails (Docker down, say), the worktree is still removed, the command exits 1 and `backing.json` is kept for a retry.
- **Start on demand, stop when parked.** The **environment record**, `.forge/runtime/environments.json` (`{ "v": 1, "jobs": { "<job>": { "state": "running" | "stopped", "usedAt": "<ISO>" } } }`, written only by the CLI under `.forge/locks/environments`), says what Forge last did to each active job's environment; it is not a live Docker probe. **Ensure up** is the idempotent start above (bring-up, then the job database), and marks the job `running` with `usedAt` now. It runs in `forge worktree create`; in `forge verify`, before any configured command and only with at least one per-job or shared entry, as a step named `environment` (a failure records the first failing service's error as its tail, runs no configured command and fails the run); in `forge run <job> <name> --background` before the process starts (exit 5 on a failure, and nothing starts); and after `forge focus <job>` or the dashboard's Focus moves focus (a failure never undoes the focus; `forge focus` adds `environment: { ok, error? }`). **Stop** runs `docker stop` on the job's own labelled per-job containers and stops its background processes, keeping volumes, job databases, `backing.json`, `backing-db.json` and shared containers, and marks the job `stopped` even when Docker fails. Step rules stop the environment whenever a job parks (G3b for `pr-review`, G4 for every other wait and `blocked`, while the record says `running` or `runtime.json` lists a process), and step rule E1 starts it again (`forge environment up <job>`) when a job in `build`, `verify` or `review` runs again with a `stopped` record. Foreground `forge run`, `forge backing up` and `forge stop` leave the record alone. The dashboard's Environment card starts backing services with `forge environment up` (Start, and Restart after its stop), so they count against `environments.maxRunning` and may evict, and its Stop runs `forge backing stop` and then marks the job `stopped` in the record (its dev server keeps running). Starts log `environment-up` (`{ trigger: verify | run | focus | worktree | step | cli, ok, error?, evicted }`) and stops `environment-stop` (`{ trigger: park | evict | cli | done | cancelled, by?, ok, processes, stopped, error? }`). `forge environment up|stop|down <job>` does each by hand, and `forge environment list` shows the record; `up`, `stop` and `down` are refused in the inbox, office and assistant foreman daemon sessions, while Forge's own paths (verify, run, focus, worktree create, job set, pr sync, archive) never are.
- **Teardown.** A job's **environment** is its per-job containers and volumes, its job databases and its background processes. When a job moves to `done` or `cancelled` (`forge job set --state done|cancelled`, `forge pr sync` finding its PR merged or closed, the tracker's "all child jobs finished" and a failed tracker claim), Forge tears it down: `forge stop`, then what `forge backing down <job>` does. The worktree stays. `forge job archive` and retention's archive tear down first too. Teardown runs only when the job has something to tear down (`backing.json` or `backing-db.json` in its job dir, a background process in `runtime.json`, or an entry in the environment record); otherwise there is no Docker call and no event. The state change is written first and never rolled back: when teardown fails (Docker missing or stopped, a failed `docker` or `psql` call, a stopped shared server), the records are kept and any later teardown retries it (archive, `forge environment down <job>`, `forge backing down <job>`, `forge worktree remove <job>`). `forge job set` still exits 0 and its result gains `environment: { ok, processes, removed, volumes, databases?, error? }` whenever teardown ran. Run in the inbox, office or an assistant foreman daemon session, where `forge environment down` is refused, `forge job set` only stops the environment (as Stop below, logging `environment-stop` with `trigger: done | cancelled`) and keeps its volumes, job databases and records, so archive or `forge environment down <job>` tears it down later; its result is then `environment: { ok, processes, stopped, error?, teardown: "deferred" }`. Archive refuses a job whose teardown fails, listing it in `refused` with `environment teardown failed: <error>` and keeping its job dir. Every attempt logs `environment-down` with `{ trigger: done | cancelled | archive | cli, ok, processes, removed, volumes, databases?, error? }`, never a password.
- **On demand.** `forge backing up <job>` brings the services up again, for example after a reboot stopped them (exit 5 when any fails). `forge backing down <job>` removes the job's per-job containers and volumes, for any job, done or cancelled too (free them when you cancel a job), and `forge backing down --shared` removes this checkout's shared containers while keeping their volumes and ports. `forge backing stop <job>` only runs `docker stop` on the job's per-job containers whose labels name this checkout and job, keeping their volumes, records and every shared container (a missing, already stopped or foreign container is listed in `skipped`; `backing up` starts them again); the dashboard's Environment card uses it for Stop. `forge backing status <job>` shows Docker's state as `docker` (`ok`, `missing` or `stopped`, or `null` when no service is managed and Docker was not asked; a managed service reads `unknown` when it is not `ok`) and each service's container, state, `health` (`healthy`, `unhealthy` or `starting` from the image's healthcheck while running, `null` without one), ports and the `FORGE_BACKING_*` names (never values); `forge backing status` lists every container labelled with this checkout, with `orphan: true` for a per-job one whose job is unknown, done or cancelled. `up`, `stop` and `down` (`--shared` too) are refused in the inbox, office and assistant foreman daemon sessions.
- **After a config change** (a new image, env or volume), Forge doesn't recreate a running container: run `forge backing down <job>` and then `forge backing up <job>`. A container that is merely stopped (a reboot, a park) starts again on its own before verify, `forge run --background` and focus; before a foreground `forge run`, run `forge environment up <job>`.
- **Doctor.** With at least one per-job or shared entry, `forge doctor` adds a `docker` check (5 s timeout): `docker not found on PATH: install Docker to run backing services <names>`, `docker is installed but its daemon is not reachable: start Docker (e.g. Docker Desktop, colima start); needed by backing services <names>`, or `Docker <version>; backing: postgres (per-job), redis (shared)`.

**Migration** (config `schemaVersion` 18 → 19): nothing changes. v19 adds `backing`, empty by default; the bump lets older Forges refuse a config whose backing services they would ignore.

### Job databases

A container per job is heavy for a database. A `shared` Postgres entry with `database` gives each job its own **job database** and its own login role on the one shared server instead, cloned in seconds (`CREATE DATABASE … TEMPLATE`) from a **template database** that the project's migrate and seed commands build. Each job gets the same isolation as a per-job container at a fraction of the cost.

```yaml
backing:
  - name: pg
    isolation: shared                        # database is only for a shared entry
    image: postgres:16
    ports: [5432]
    env: { POSTGRES_PASSWORD: forge }        # POSTGRES_USER optional, default postgres
    volumes: [/var/lib/postgresql/data]
    url: …                                   # with {user}, {password} and {database}: see "The url" below
    database:
      engine: postgres                       # required; the only engine for now
      migrate: npm run db:migrate            # optional shell command
      seed: npm run db:seed                  # optional shell command
      inputs: [db/migrations/**, db/seed.sql]  # optional paths/globs, hashed into the template name
```

- **The url** must hold `{user}`, `{password}` and `{database}` besides `{host}` and `{port}`: for Postgres, `postgres://` then `{user}`, `:`, `{password}`, `@` and `{host}:{port}/{database}`, written as one word. Forge fills them per job, so the url carries no static credentials.
- **Names.** A job's database and its role are both `forge_j_<slug>_<first 8 hex of sha256 of the job id>`, where the slug is the job id lowercased, each run of other characters turned into `_`, trimmed of `_` and cut to 40 characters (`job` when nothing is left): at most 57 characters, and two ids that differ only in punctuation still get different names. The template is `forge_tpl_<first 12 hex of the template hash>`, owned by the superuser once built; the `forge_tpl` role owns it while migrate and seed run, with `CONNECT` revoked from everyone else. No job role is a member of `forge_tpl`, so no other job reaches a template mid-build. Instead, once a job's database is cloned, Forge reassigns everything `forge_tpl` owns in it to the job's role (`REASSIGN OWNED`, inside that database), so the job owns the tables its migrations created. A database `forge_tpl` still owns at that point, which under the build lock can only be a build that stopped part way, is dropped first; one that is not a `forge_tpl_<12 hex>` fails the entry with `role forge_tpl owns database "<name>", which Forge did not build: drop it or change its owner, then retry`. The superuser is `env.POSTGRES_USER`, else `postgres`. Every name is derived (never read from a record), checked against `^[a-z_][a-z0-9_]{0,62}$` and double-quoted, and every SQL statement goes to `psql` on stdin through `docker exec -i`, never in argv.
- **The template hash** is sha256 over the engine, `image`, `migrate`, `seed`, `inputs` and, for each file `inputs` matches in the job's worktree (tracked, or untracked and not ignored: `git ls-files --cached --others --exclude-standard`), its path and content (a symlink counts by its target). Changing any of them, including a matched file in a job's worktree, gives a new template name; a file `inputs` doesn't match changes nothing. Inputs are hashed from the job's worktree, so a job that edits its migrations gets a template built from them. **Caveat:** migrate and seed run code from the building job's worktree, and a file they read that `inputs` doesn't cover can still shape a template that later jobs with the same hash reuse. Make `inputs` cover everything those commands read.
- **Lifecycle.** `forge worktree create <job>`, after every backing service is up and before `worktrees.setup`, for each shared entry with `database`: waits until the server accepts TCP connections inside the container (`pg_isready`, at most 60 s); makes sure the template exists, building it under a lock (`.forge/locks/backing-db-<name>`) when it is missing, by running migrate and then seed in the job's worktree with `FORGE_BACKING_<NAME>_URL` pointing at the template as `forge_tpl` with a one-off password; and creates the job's role and its database, cloned from the template, owned by the role, with `CONNECT` revoked from everyone else. A failed migrate or seed drops the half-built template, so the next create builds it afresh. After building a template, Forge drops every other `forge_tpl_<12 hex>` on that server that no job's record names. From then on `FORGE_BACKING_<NAME>_URL`, and `{backing.<name>.url}` through it, is the url with `{user}` and `{database}` the job's names and `{password}` the job's password, for `worktrees.setup` and every later configured command. `forge backing up <job>` runs the same step, building in the worktree path Forge computes for the job (`<worktrees.root>/<job id>`, never the stored `worktree`); without that directory the entry fails with `job <id> has no worktree: run forge worktree create <id>` (exit 5).
- **Reruns** keep the job's database and its data. When the record is missing or invalid but the database exists, the role gets a new password and the record is rewritten. To re-clone from a newer template, run `forge backing down <job>` and then `forge backing up <job>`.
- **Result.** Each `backing` entry with `database` gains `database: { name, template, action: created | kept | none, template_action: built | reused | none }`, and `build: [{ cmd, ok, tail }]` when Forge built the template. The result never holds a password or a filled url, and the setup and build tails Forge stores have every generated password replaced with `[redacted]`. A timeout, a failed migrate or seed, a psql error or a missing worktree makes the entry `ok: false` with `error`, skips setup and logs `worktree-setup-failed` with `backing: <name>`, so step rule I4 fails the job. Job database passwords are [known values](#secret-references), so `forge run` and `forge verify` logs and tails, and everything the dashboard serves, redact them too.
- **The record** is `.forge/jobs/<job>/backing-db.json`, mode 0600, written atomically: `{ "v": 1, "databases": { "<name>": { "template": "forge_tpl_<12 hex>", "password": "<32 characters>" } } }`. The job's password (32 characters of `A-Z a-z 0-9 _ -`) is stored only there; Postgres only ever receives its SCRAM-SHA-256 verifier, and the `forge_tpl` password lives in memory for one build. The record is read without following a symlink; an entry naming no current `database` entry, a template outside `^forge_tpl_[0-9a-f]{12}$` or a malformed password is ignored, and `FORGE_BACKING_<NAME>_URL` is unset until a valid entry exists.
- **Teardown.** `forge worktree remove <job>`, `forge backing down <job>`, `forge environment down <job>`, `forge job delete`, and the teardown when a job finishes or is archived ([Backing services](#backing-services) › Teardown) terminate the job database's connections, drop the database and the role under the same `.forge/locks/backing-db-<name>` lock, and delete the record; the names come from the job id, never from the record. The `backing` result gains `databases: [<dropped names>]`. When Docker is down, the shared container is stopped or a psql call fails, the result is `ok: false`, the record is kept for a retry and the command exits as for any teardown failure (1 for `worktree remove`, 5 for `backing down`). When the shared container no longer exists, nothing is left to reach: the record is deleted and `ok` stays true.
- **Status.** `forge backing status <job>` gives each service with `database` a `database: { name, template }` (`template: null` without a record), shown as a `database` column, and lists `FORGE_BACKING_<NAME>_URL` only once the record exists.
- **Validation** adds, per entry: `backing[<i>].database is only for a shared entry`; `… must be a map with engine`; `… has unknown key "<k>"` (allowed: `engine`, `migrate`, `seed`, `inputs`); `backing[<i>].database.engine must be one of postgres (got …)`; `backing[<i>].database.migrate` (or `seed`) `must be a non-empty string of at most 2000 characters with no NUL, CR or LF` (the value is never shown); `backing[<i>].database.inputs must be a list of at most 64 paths or globs`, each entry checked like `worktrees.generated` (relative, no `..` segment, no leading `-`, `!` or `:`); `backing[<i>].database needs ports`; `backing[<i>].database needs a url with {user}, {password} and {database}`; and `backing[<i>].env.POSTGRES_USER must match ^[a-z_][a-z0-9_]{0,62}$ when database is set`. On an entry without `database`, `{user}`, `{password}` and `{database}` are unknown placeholders like any other.
- **No `database` key**: nothing changes, and Forge makes no `docker exec` call.

**Migration** (config `schemaVersion` 21 → 22): nothing changes. v22 adds a shared entry's `database`, absent by default; the bump lets older Forges refuse a config whose job databases they would ignore. `forge migrate` writes the new version.

## Secret references

Real projects need database and API credentials in their commands. `secrets` names each one and says where its value lives; a [config sink](#config-sinks) hands it to the component's process as `{secret.NAME}`, resolved right before the command runs. Forge never stores a value in config, and nothing is global: the only declarations are in the repo's own `.forge/config.yml`, and Forge reads no per-user or machine-wide secrets file. Declare only development or test credentials: a job's commands receive the values by design, so code the builder writes can read them.

```yaml
secrets:
  DB_PASSWORD: { env: MYAPP_DB_PASSWORD }                              # the Forge process's environment
  STRIPE_KEY:  { keychain: { service: myapp-dev, account: stripe } }   # macOS `security`, Linux `secret-tool`
  API_TOKEN:   { op: "op://Dev/myapp/token" }                          # 1Password CLI `op read`
  LOCAL_KEY:   { file: .secrets/dev.env, key: LOCAL_KEY }              # a git-ignored file in the root repo
components:
  - name: api
    path: services/api
    kind: service
    config:
      - env: { DATABASE_PASSWORD: "{secret.DB_PASSWORD}" }
      - env-file: .env.local
        values: { STRIPE_KEY: "{secret.STRIPE_KEY}" }
```

The expression is `{secret.NAME}`, a dotted root like every other sink expression, rather than the `{secret:NAME}` the issue sketched; the meaning is the same.

**Sources.** A name matches `^[A-Za-z_][A-Za-z0-9_]*$`, is not `__proto__`, `constructor` or `prototype`, and maps to exactly one source:

- **`env`**: a variable name (same pattern) in the environment of the Forge process that renders the sink. That variable is removed from every configured command's environment, in and out of the daemon and whether or not a sink uses it, so the value reaches only the component whose sink names it. A sink may set a variable of the same name (`secrets.DB_PASSWORD: { env: DB_PASSWORD }` with `env: { DB_PASSWORD: "{secret.DB_PASSWORD}" }`): sink env is applied afterwards, so that component's command gets it and no other does. `forge release run` is the exception: it keeps its caller's whole environment, because its publish steps need your registry credentials.
- **`keychain`**: `{ service, account? }`, each 1–128 characters of `A-Z a-z 0-9 . _ @ : / space + -`, never starting with `-`. On macOS Forge runs `security find-generic-password -s <service> [-a <account>] -w`; on Linux `secret-tool lookup service <service> [account <account>]`. Any other platform fails: `secret STRIPE_KEY: the keychain source is not supported on win32`.
- **`op`**: a reference matching `^op://[^\s]+$` (at most 500 characters). Forge runs `op read <ref>`.
- **`file`**: a path relative to the root repo's main checkout, with no `..` segment. It must be a regular file (not a symlink, not a hard link, at most 64 KiB) whose real path stays inside the repo, and `git check-ignore` must say it is ignored and untracked. With `key`, the file is read as dotenv `NAME=value` lines (`#` comments and blank lines skipped, an `export ` prefix and one pair of surrounding quotes stripped) and the value is `key`'s line; without it, the whole file.

Tools run without a shell, each field one argument, with a 30 s timeout. One trailing newline (`\n` or `\r\n`) is stripped from every value. A value shorter than 8 characters fails: `secret X (env) resolved to fewer than 8 characters; Forge can't redact a value that short`.

**Resolution** happens only when a sink render reaches `{secret.NAME}`, so a declared secret no sink uses is never read, and each name is read at most once per Forge process (a `forge verify` with several steps reads each source once). Every failure fails closed and the configured command does not run: an undeclared name, an unset env var, a tool that is missing or exits non-zero, a file that is not ignored, a value that is too short. Errors name the secret and its source kind and quote at most the tool's last stderr line, never the value: `config sink 0: secret API_TOKEN (op) failed: op exited 1: <stderr last line>`, `config sink 0: secret DB_PASSWORD (env): MYAPP_DB_PASSWORD is not set`. The git-ignored rule for `env-file` and `file` outputs still applies, before anything is written. `config.secrets` in `forge run`'s result and the `config-sinks` event lists the names resolved.

**Known values.** When a render resolves a secret, Forge records the value in `<jobDir>/known-secrets.json` (mode 0600, written through a rename, merged by name, rewritten only on a change): `{ "v": 1, "values": { "<NAME>": "<value>" } }`. A job's **known values** are those plus its [job database](#job-databases) passwords. Forge replaces each one, raw and in its JSON-escaped form (so a value with `"` or `\` inside JSONL is caught too), with `[redacted]`. The table's `/api/…` rows are the dashboard's project routes, served under `/api/p/<project>/`:

| Where | When | Values used |
|---|---|---|
| `logs/<name>-<ts>.log` and the `tail` of `forge run` and verify steps (so `verify/round-<n>.md` too) | at write | the job's, plus those the render holds in memory |
| config-sink command logs `logs/config-*.log` | at write | those resolved so far |
| `worktrees.setup` tails | at write | the job's |
| `events.jsonl` (every string in an event's data) | at write | the job's recorded ones |
| daemon session logs, their SSE line frames and replay ring | at write | a job session's own; `_inbox`, `_office` and each `_assistant-<n>` every job's |
| `/api/state` (every string) | at serve | every job's |
| `/api/jobs/<id>`, `/file` (including background logs `logs/<name>.log`, which the child writes itself) and `/raw` (HTML mockups only) | at serve | that job's |
| `/api/daemons/log` pages, `/api/jobs/<id>/transcript` pages and their event frames | at serve | the session's or the job's |
| `/api/events` state frames (permission inputs, errors) | at serve | a job session's own; `_inbox`, `_office` and each `_assistant-<n>` every job's |
| `forge daemon log` | at print | the session's |
| the support bundle | at build, as `<secret:known>` before the pattern passes | every job's |

`known-secrets.json` and `backing-db.json` are **private job files**: `/file` and `/raw` answer 404 for them (in any letter case, for a path whose link resolves to one, and for a hard link, since a job file with more than one link is never served), the job's file list leaves them out, and the support bundle never includes them. `forge worktree remove` deletes `known-secrets.json`. A record that is missing, a symlink, not a regular file, over 1 MiB or malformed counts as empty and is never followed or blocked on; the job database passwords still apply. The secret scanner reports a known value as `known-secret` (see [Secret scanning](#secret-scanning)).

**Briefs.** With `secrets` declared, builder and reviewer briefs carry one line of names and source kinds, never an env var, keychain service, op reference or file path: `Secrets: DB_PASSWORD (env), STRIPE_KEY (keychain), API_TOKEN (op), LOCAL_KEY (file) · values reach commands only through config sinks ({secret.NAME}); never print, log, copy or commit them`.

**Commands.** `forge secrets list` prints `{ secrets: [{ name, source }] }` and resolves nothing. `forge secrets check [<name>...]` resolves each named secret (all by default) and prints `{ secrets: [{ name, source, ok, error? }] }`, never a value or its length; it exits 1 when one fails, and an undeclared name is a usage error. `forge doctor` adds a `secrets` check when any is declared: `N declared`, with a warning for each source it can see is unavailable (an unset env var, `security`, `secret-tool` or `op` not on PATH, the keychain on an unsupported platform, a missing or unignored file). It never runs those tools, which can prompt.

**Validation** (`forge config validate`, `forge doctor`, Settings) reports `secrets must be a map …`, `secrets.<NAME> is not a valid secret name`, `… must have exactly one of env | keychain | op | file`, `… has unknown key …`, `secrets.<NAME>.env must be an environment variable name …`, `secrets.<NAME>.keychain.service is required`, `secrets.<NAME>.keychain.<field> must be 1–128 characters …`, `secrets.<NAME>.op must be a 1Password reference …`, `secrets.<NAME>.file must be a relative path inside the repo …`, `secrets.<NAME>.key …`, and, under the component, a `{secret.NAME}` that names no declared secret. A problem never quotes a field's value. Neither Settings nor `forge config set` edits `secrets`, and support bundles hide it like `commands`.

**What it does not stop.** Forge keeps a value from landing verbatim in what it persists, serves, briefs or publishes, and from being committed or pushed. It does not stop a builder that deliberately encodes or splits a value (code that runs with the value can do anything with it), and an agent that rewrites `known-secrets.json` weakens serve-time redaction of files the child wrote itself; every render rewrites the record, and what Forge writes is redacted with the values it holds in memory. Member-repo commands, `worktrees.setup` and command templates never resolve secrets: values reach a process only through config sinks. Configured commands also get only the allowlisted [command environment](#command-environment) and no login profile, but code they run can still read your files (`~/.aws/credentials`, `~/.npmrc`, `~/.config/gh/hosts.yml`, a shell profile) or start its own login shell, which puts back whatever your profile exports: declare only development or test credentials, and keep production ones out of the account `forge dash` runs as.

**Migration** (config `schemaVersion` 22 → 23): nothing changes. v23 adds `secrets`, `{}` by default; the bump lets older Forges refuse a config whose `{secret.NAME}` references they would reject or leave unredacted. `forge migrate` writes the new version.

## Deprecated keys

A key on its way out is listed in `DEPRECATED_CONFIG_KEYS` in `lib/core/config/validators/deprecations.ts` with the release that deprecated it, the release that removes it (at least one minor later) and what to use instead. While it is set in `.forge/config.yml`, `forge doctor` and Settings › Diagnostics show a warning row, `deprecated config key <key>`, that never fails the report. The policy is in [RELEASES.md](RELEASES.md#deprecation). Each deprecated key is listed below as `` `<key>` ``, and `test/invariants/version.test.ts` checks the list against the registry.
