# Developing Forge

The reference half of the root [AGENTS.md](../AGENTS.md), which keeps only the essentials and the verify list: read a section here when your change touches it.

## Layout
- `bin/forge`: CLI entry (also on PATH while the plugin is enabled); it turns on the start-up cache, then imports `lib/cli/main.ts`
- `lib/`: the engine, in seven lib layers that import downward only (`api` → `core` → `integrations` → `engine` → `office` → `server` → `cli`; [docs/design/lib-layout.md](design/lib-layout.md)). `lib/AGENTS.md` and each layer and module folder's `AGENTS.md` map what is there; read a folder's map before working in it. Entry points:
  - `lib/cli/main.ts`, which only routes;
  - `lib/cli/commands/`, one module per group with its `HELP` table;
  - `lib/engine/pipeline/step/`, which is `forge job step`;
  - `lib/core/job/schema.ts`, the normalisers, and `lib/core/versions/`, the version lists;
  - `lib/core/types.ts`, the type-only barrel for the job, config and `/api` shapes (each module's own shapes are in its `types.ts`);
  - `lib/api/`, the `/api` shapes, one owner module per endpoint area behind the type-only barrel `lib/api/types.ts`, and the tracker contract;
  - `lib/trackers/status.{ts,mjs}`, deprecated re-exports of `lib/api/tracker.ts`.
- `dashboard/`: a Svelte 5 app in strict TypeScript. It has `index.html`, `style.css`, `svelte.config.mjs`, and `src/` with `main.ts`, `App.svelte`, `views/` (one per page), `components/`, `messages/` (the i18n catalogs; the source is the per-area files in `messages/en/`, merged by `mergeCatalogs` in `src/lib/i18n.ts` and loaded by the `$t` store in `src/lib/locale.ts`), and `lib/`. `lib/` holds plain-TS helpers and API types that `npm test` imports (`types.ts` re-exports the API types from the engine's `lib/api/types.ts`), plus `*.svelte.ts` rune state. Vite builds it into `dashboard/dist/` (`npm run build:dashboard`), and `forge dash` serves that. `dist/` is gitignored: CI builds it for the main update that the release PR carries into `main` (hotfixes on `main` carry their own), so plugin installs, which follow a release tag on `main`, never build. `dashboard/fonts/` holds the vendored OFL woff2 typefaces (`README.md` records their source).
- `hooks/`: plugin hooks (`hooks.json`, the no-AI-attribution PreToolUse hook, the `write-guard.ts` PreToolUse hook that confines a daemon session's file writes to its write roots, and the SessionStart `plugin-path.ts` hook that puts the plugin's `bin/` first on PATH); a hook imports nothing from `lib/` when its verdict must survive a broken module
- `skills/forge/`: the orchestrator (`SKILL.md`) and on-demand procedures (`reference/`)
- `agents/`: one prompt per role · `reviewers/`: lens checklists · `templates/`: files `init` seeds into `.forge/` (`templates/release-gate/`: the seeded CI check, plain JS for consumer repos that the tests run, outside the engine's TypeScript)
- `docs/`: user docs (`docs/architecture/`: the architecture topics, one file each, indexed by `docs/ARCHITECTURE.md`; `docs/test-rewrite/`: the per-module behaviour inventories the test rewrite builds from) · tests: `node:test` suites; unit files beside their modules (`lib/**/<module>.test.ts`, `dashboard/src/**/<module>.test.ts`), the kept migration and transition tables in `test/`, `test/integration/<entry>/` (`cli`, `server`, `pool`, `scripts`, `hooks`, `release-gate`), `test/e2e/<flow>/`, `test/invariants/` (the layer, file-size, folder-layout, folder-map and other allowed source-text tripwires), and shared helpers in `test/support/`, imported through `test/helpers.ts` ([docs/TESTING.md › Layout](TESTING.md#layout))
- `scripts/`: dev-only TypeScript run through npm, type-checked with the engine (`docs-commands.ts` is `npm run docs:commands` (docs/CLI.md's Common commands table), `docs-map.ts` is `npm run docs:map` (the `lib/` folder maps), `docs-config.ts` is `npm run docs:config` (docs/CONFIG.md's key reference), `docs-cli.ts` is `npm run docs:cli` (docs/CLI.md's command reference and error codes), and `npm run docs` runs every generator; `dev.ts` is `npm run dev`, `dev-claude.ts` is `npm run dev:claude`, `scenario.ts` is `npm run scenario` (seeds a dashboard scenario from `test/fixtures/scenarios/` into a scratch repo), `render-check.ts` is `npm run test:render` (the render check: every scenario's views in headless Chrome), `release.ts` is `npm run release`, `release-check.ts` is `npm run release:check`, `check-touchpoints.ts` is `npm run check:touchpoints` (the companions a diff is missing; its rule table is the touchpoint rules), `release-plan.ts` is what `release.yml` runs to detect a release and write its notes, `coverage.ts` is `npm run coverage` (docs/TESTING.md › Coverage), `test-times.ts` is the reporter behind `npm run test:times` (each test file's time, slowest first), `main-update.ts` builds and checks the main update `release.ts` pushes to the release PR's branch, and `git.ts` is the scripts' one git runner, with `lib/integrations/git/runner.ts`'s pins)
- `.github/workflows/ci.yml`: CI, the [verify list](../AGENTS.md#verify-before-claiming-it-works) on every PR, every push to `develop` and `main`, and on dispatch
- `.github/workflows/main-update.yml`: on a push to a `release/v*` branch, builds the dashboard with a read-only token and uploads it as the artifact `npm run release` puts in the main update the release PR carries (docs/RELEASES.md)
- `.github/workflows/release.yml`: on a push to `main` that changes the version (the merge of a release PR), runs all of `ci.yml` and a read-only build of the notes and archive, then a job that runs only `gh` tags the merge commit `v<version>` and publishes the GitHub Release (docs/RELEASES.md)

## Where a change goes

`npm run check:touchpoints` names each companion a diff is missing, with the fix (its rule table is in `scripts/check-touchpoints.ts`). The tests and type checks name the rest: stale generated docs and folder maps, missing migration rows, header comments and module `AGENTS.md` files, and the verify list's copies in CI and the PR template. This table keeps the calls they can't make.

| You're changing… | Touch | Also update |
|---|---|---|
| a CLI command or its JSON output | `lib/cli/commands/<group>.ts` (+ the domain module); `lib/cli/main.ts` only for a new top-level command | the group's `HELP` table in `lib/cli/commands/<group>.ts` (`CORE` in `lib/cli/commands/help.ts` for what `lib/cli/main.ts` routes); `ERROR_CODE_DOCS` in `lib/core/errors.ts` for a new error code; docs/CLI.md prose for a new exit or env var; `skills/forge/SKILL.md` / `reference/*.md` if the orchestrator calls it; tests |
| `job.json`, an event or a config shape | append a named step to `lib/core/versions/<config\|job\|event>.ts`, `lib/core/config/keys/defaults.ts` `defaults()` plus a doc string per new key in `lib/core/config/keys/docs.ts`, and the shape in `lib/core/job/types.ts` or `lib/core/config/types.ts`; an `/api` shape in its owner module in `lib/api/` (see `lib/api/AGENTS.md`), which the dashboard imports through `lib/api/types.ts`, so `npm run check:dashboard` shows what it must handle | docs/CONFIG.md prose only for behaviour beyond one key; for a new config key, a `lib/core/config/fields.ts` entry if the dashboard should show it (editable only under the rule in its header, otherwise locked with a reason) |
| a config section's validation | its file in `lib/core/config/validators/`, else `lib/core/config/validate.ts`; `validateConfig` calls it | that file's test table |
| a pipeline rule or an agent brief | `lib/engine/pipeline/step/stages/<stage>.ts` or `lib/engine/pipeline/step/gates.ts` (add a table row, and its ID to `RULES` in `lib/engine/pipeline/step/rules.ts`) / `lib/engine/pipeline/brief.ts` | a row per transition in `test/step-rows.ts` (run by `test/step.test.ts`); update the pinned order in `test/step-tables.test.ts`; SKILL.md states no rule `step` owns |
| orchestrator behaviour (the loop itself) | `skills/forge/SKILL.md` (keep it lean) or a `reference/*.md` loaded on demand | README "How it works" if user-visible |
| a role's behaviour | `agents/<role>.md` | its prompt hash changes (shown in the roster); CHANGELOG; measure with evals where possible |
| a new `lib/` file or folder | `lib/<layer>/<module>/` by docs/design/lib-layout.md › [Layers](design/lib-layout.md#layers) and [Conventions](design/lib-layout.md#conventions) | - |
| a review lens | `reviewers/<lens>.md` | `lib/engine/ops/detect.ts` suggestions + `reference/init.md` presets if it should be offered |
| tracker behaviour | `lib/integrations/{github,backlog}/tracker.ts`, the loader in `lib/engine/trackers/load.ts`, the contract and status mapping in `lib/api/tracker.ts` (`lib/trackers/status.{ts,mjs}` re-export it for older adapters, deprecated) | `docs/TRACKERS.md` |
| the dashboard | `dashboard/src/**` (`views/`, `components/`, `lib/`), `dashboard/index.html`, `dashboard/style.css`, and endpoints in `lib/server/routes/` (a row in the route table in `lib/server/start.ts`) | rebuild `dashboard/dist/` (`npm run build:dashboard`) but never commit it; the owner module in `lib/api/` (see `lib/api/AGENTS.md`) on any `/api/*` or SSE shape change; new text in its area's file under `dashboard/src/messages/en/`; `npm run check:dashboard`; a scenario file in `test/fixtures/scenarios/` when a new state needs one, and `npm run test:render`. The server's allowlist is `dist/manifest.json`, so new modules need no server change |
| prices or model ids | `lib/integrations/claude/pricing.json` | take prices from Anthropic's current pricing, never from memory |
| the release pipeline | `.github/workflows/release.yml`, `.github/workflows/main-update.yml`, `scripts/release*.ts`, `scripts/main-update.ts` | `test/invariants/release-workflow.test.ts` and `test/invariants/main-update-workflow.test.ts` when a workflow's triggers, permissions or jobs change; docs/RELEASES.md when a release script's behaviour changes |

Version bumps: append a named step; on conflict keep both, in merge order (the base branch's entries first). `test/schema.test.ts` and `lib/core/versions/steps.test.ts` prove the merged list.

## Rules
- **Zero runtime dependencies.** Node ≥ 22.18 built-ins only. The engine (`lib/`, `hooks/`, `bin/`) is strict TypeScript that Node runs by type stripping, type-checked by `npm run typecheck` with the exact-pinned `typescript` and `@types/node`. The only engine JavaScript is `bin/forge`, an extensionless entry that turns on the start-up cache and imports `lib/cli/main.ts`, and the deprecated `lib/trackers/status.mjs` re-export kept for custom tracker adapters. The dashboard's `src/` is strict TypeScript and Svelte 5 components (runes only), limited to erasable syntax, type-checked by svelte-check with the exact-pinned `typescript` devDependency, and never loaded at runtime. Build tools are exact-pinned devDependencies, the dashboard loads no external assets, and there is never a `prepare` or install script, so installing the plugin never builds or installs anything. No Python tooling: Node, or Rust if a native binary is ever justified.
- **`dashboard/style.css` is the source of truth for the dashboard's look** ([dashboard/AGENTS.md](../dashboard/AGENTS.md)).
- **Never commit the built dashboard.** `dashboard/dist/` is gitignored and never hand-edited. Build it with `npm run build:dashboard` before the tests: the ones that read it skip without it (`test/dist.ts`), and CI sets `FORGE_REQUIRE_DIST=1` so there they run. CI builds it for the main update (`.github/workflows/main-update.yml`), which `npm run release` pushes to the release PR into `main`; only a hotfix branch from `main` rebuilds and commits it by hand ([docs/RELEASES.md](RELEASES.md#releasing)).
- **The CLI is the only writer of state.** New state means a new CLI command, never "the agent edits job.json".
- **Version every shape change.** Append a named step to its version list in `lib/core/versions/`, and to `API_CHANGES` in `lib/api/versions.ts` when `/api/*` changes; on conflict keep both, in merge order. Keep normalisers tolerant, and never break reading older jobs.
- **`lib/` imports point down the lib layers in [docs/design/lib-layout.md](design/lib-layout.md), with no import cycles, and only `lib/cli/commands/` and `lib/cli/main.ts` import `lib/cli/commands/`** (`test/invariants/layers.test.ts`). When a low-level module needs something above it, move the shared piece to a leaf, or take it as a parameter or a hook (`onTransition` in `lib/core/job/transitions.ts`).
- **Keep the orchestrator's context small.** New commands return compact JSON. Large outputs go to files in the job dir, and the CLI returns their paths.
- **Prompts are product.** Agent prompts and checklists are short, imperative, and end with a one-line reply contract. Prefer measuring a prompt or policy change (evals, `forge stats`) over arguing about it.
- **Never add AI attribution** to commits, PRs, issues or comments in this repo either. The hook in `hooks/` enforces it while the plugin is enabled.
- **Preserve the security posture** (`docs/architecture/untrusted-input.md` and `docs/architecture/dashboard-security.md`): never adopt fork PRs; the server answers loopback Hosts only; POSTs need the token, a matching Origin and JSON; tracker and PR text is fenced as data, and agents are told so. Anything new that ingests outside text follows the same pattern.
- Comments explain why, not what.
- **Use the glossary's words.** New docs, prompts and dashboard copy use the terms in `docs/GLOSSARY.md`; a new term goes there first.
- Keep `README.md`, `docs/*.md` and `skills/forge/**` in sync with CLI behaviour.

## Verify notes
The details behind the [verify list](../AGENTS.md#verify-before-claiming-it-works) in the root AGENTS.md.
- **CI runs this list.** `.github/workflows/ci.yml` runs these commands as named steps, in this order, on every PR and push to `main`, with the tests sharded and the CLI pinned at `@anthropic-ai/claude-code@2.1.299`, installed with `--ignore-scripts` and run through the package's `cli-wrapper.cjs` for the validate step (the second command that differs from the list); [docs/CI.md](CI.md) covers the matrix (Ubuntu only), the `audit` and `release check` jobs, and what `test/invariants/ci-workflow.test.ts` pins. Change this list and the workflow together.
- **Forge needs Node ≥ 22.18, for the plugin and the tests:** type stripping is on by default there and prints no warning. Check changes on 22.18 itself (`~/.nvm/versions/node/v22.18.0`; `nvm use` reads `.nvmrc`), not only on a newer 22.x.
- **Never point the CLI at a real repo's `.forge/` while developing.** Use a scratch git repo in a temp dir, or set `FORGE_ROOT=<scratch>` (as `test/helpers.ts` does), and `FORGE_HOME=<scratch>` for the machine index, so `forge project add` never writes your `~/.forge` (`test/helpers.ts` gives each test process its own). Delete scratch repos *and* their `<repo>.worktrees` siblings afterwards. Never run `forge service install` outside a test's temp `HOME`: it writes and loads a real login item; tests call the engine with temp homes and a fake runner.
- **Dashboard:** run `npm run dev -- --scenario <name>` (it seeds a scratch repo and removes it when dev stops), and `npm run test:render` after `npm run build:dashboard`. The render check needs Google Chrome (or `FORGE_RENDER_CHROME`), so it stays outside the verify list; CI's `render` job runs it. The full check is in [dashboard/AGENTS.md](../dashboard/AGENTS.md) › Verify.
- **The plugin inside Claude Code:** `claude --plugin-dir <this checkout>` loads it without installing. `claude plugin details forge` shows the component inventory and projected token cost, which is useful when trimming prompts.
- **GitHub code paths** (`lib/engine/pr/`, `lib/integrations/github/`): read-only checks against real repos are fine. Anything that writes (PRs, labels, GitHub Project fields, comments, issues) goes only to a throwaway repo the maintainer approves.

## Gotchas already paid for
- **All TS (engine and dashboard) runs through Node's type stripping, which ignores tsconfig:** write relative and aliased imports with their real extension (`.ts`; `.mjs` only for the dashboard's build scripts and the `status.mjs` re-export), bring types in with `import type`, and use no `enum`, `namespace` or parameter properties (`erasableSyntaxOnly` enforces it).
- **Layer aliases live in `package.json` "imports", never tsconfig `paths`:** Node, `tsc` and Vite all read `imports`, so an installed plugin, which never runs `npm install`, resolves `#core/…` too; tsconfig `paths` only fool the type checker. Imports across lib layers use `#api/`, `#core/`, `#integrations/`, `#engine/` or `#office/`; `server` and `cli` have none, and imports inside a layer stay relative (`test/invariants/layers.test.ts`).
- **Fast tests:** configured commands run as `/bin/sh -c`, and `test/helpers.ts` keeps the rest of the suite off the login profile too: `$SHELL` is `test/fixtures/bin/no-login-shell`, which runs `-lc` (`commandEnv.loginShell: true`, `forge dash`'s PATH capture) without `-l`, and it drops an outer `FORGE_COMMAND_PATH`. It keeps a compile cache in `node_modules/.cache/forge/compile-cache`. It also puts `test/fixtures/strip-cache.mjs` in `NODE_OPTIONS`, which keeps type-stripped modules in `node_modules/.cache/forge/strip-cache`: Node 22 never caches stripped TypeScript, and without the hook every CLI start costs about 150 ms there instead of 40 ms. The suite is CPU-bound, so raising `--test-concurrency` above the default doesn't help; cutting what each test spawns does. Check each case of a validation or refusal table in-process (the domain function or `forgeInProcess`) and keep one spawned-CLI test per command. For CLI-heavy tests use `forgeAsync` and put independent tests in `describe(…, { concurrency: 4 })` (at most 4: node already runs about 9 files at once), never beside a test that changes `process.env` or `process.cwd()`; poll with `waitFor` instead of sleeping; and copy a `repoTemplate` instead of re-initialising a repo per test. A long file that sorts late in `test/` sets the suite's wall time, so split one rather than letting it grow.
- **Tests per behaviour:** a job adds a test only for behaviour no test covers, extending the nearest test or table first; tests check public functions or the CLI's JSON, never one job's output, prompt or doc wording, markup or class names. Source-text tests are allowed only for the invariants in [docs/TESTING.md](TESTING.md).
- **Start-up cache:** `bin/forge` keeps V8's code cache, and on Node 22 the stripped `lib/` modules, in `.cache/` at the plugin root, beside the code it caches (`docs/architecture/startup-cache.md`; it writes its own `.gitignore`). Never move it to a shared or temp dir: a sandboxed agent could plant a module there that an unsandboxed start then runs, which is why `FORGE_CACHE_DIR` is honoured only inside the plugin root (tests take theirs from `cacheScratch()` in `test/helpers.ts`). Entries are keyed by content, so an edit is never served stale. Its load hook stays plain JS in `bin/forge`: anything in `lib/` would load the stripper it exists to skip. `NODE_DISABLE_COMPILE_CACHE=1` rules it out when a start behaves oddly, and `test/integration/cli/startup-cache.test.ts` holds the directory's ownership and permission checks.
- **Typecheck caches:** `npm run typecheck` keeps tsc build info in `node_modules/.cache/forge/` and `npm run check:dashboard` keeps svelte-check's incremental cache in `dashboard/.svelte-check/` (gitignored; thrown away when older than `package-lock.json` or `dashboard/svelte.config.mjs`). Delete both if a check behaves oddly.
- **Engine TS:** class fields are `declare`d (a plain field becomes a runtime field and changes `Object.keys`); unions with a runtime list derive from its `as const` (`(typeof STAGES)[number]`); shared shapes live in their module's `types.ts`, re-exported for core and api by `lib/core/types.ts`, and the `/api` and SSE shapes in the owner modules `lib/api/types.ts` re-exports, which import only `lib/api/constants.ts` and each other because the dashboard type-checks them without Node's types; tests are checked loosely (`test/tsconfig.json`) and change only their extension and references to renamed modules; never install Forge under `node_modules`, where Node refuses to strip types.
- **Plugin runtime**: `${CLAUDE_PLUGIN_ROOT}` and `${CLAUDE_SESSION_ID}` are substituted in skill/agent *markdown*, not exported to the shell. Claude Code appends `bin/` to the end of PATH; the SessionStart hook puts it first for every Bash command. Plugin agents are invoked as `forge:<role>`.

## Publishing
**Branches.** `develop` is the working branch and GitHub's default: every job, feature and fix branches from it and merges into it, and Forge's `git.base` here is `develop`. Plugin installs follow the `v<version>` tag that develop's `.claude-plugin/marketplace.json` names. `main` holds the released commits with the CI-built `dashboard/dist/`, and takes only release PRs (`npm run release` opens one from `release/v<version>`: the release commit plus the main update) and hotfix PRs (a `release/v<x.y.z+1>` branch from `main` with a rebuilt `dist/`, then ported to `develop` in a PR without `dist/`; never merge `main` into `develop`). Never target `main` with a job ([docs/RELEASES.md](RELEASES.md#releasing)).

This repo is public. Use the GitHub no-reply commit email, and never commit hostnames, home paths, tokens or real job state (`.forge/` is tracked here, like in any repo that uses Forge, and its own `.gitignore` excludes `jobs/`, `locks/` and `runtime/`). Bump `version` in `package.json` and `.claude-plugin/plugin.json` together (they must match), and add a `CHANGELOG.md` entry. Forge jobs on this repo leave `CHANGELOG.md` and the version alone; the release commit at the end of a wave adds them. There are two paths, with the same checks, and either can finish a release the other started: `forge release plan` (check the version bump, edit the drafted notes in `.forge/runtime/release/notes-root.md`), `forge release run --dry-run`, then `forge release run`, which drives `scripts/release.ts` once `.forge/config.yml` declares it as Forge's script release strategy (docs/CONFIG.md "Release strategy" has the block); or `npm run release` on its own. `npm run release -- patch|minor|X.Y.Z` makes that commit on a new `release/v<version>` branch cut from `develop` (you edit the drafted notes; it runs `npm run release:check -- --dist absent`), pushes it and the main update, and opens the release PR into `main`. You merge the PR with a merge commit; `release.yml` then tags the merge `v<version>` and publishes the GitHub Release, and `npm run release` with no version lands the release commit on `develop` ([docs/RELEASES.md](RELEASES.md)).
