# Releases

How Forge is versioned, which releases get fixes, how a release is cut, and how to pin, verify and roll back an install.

## Versioning

Forge follows [semver](https://semver.org). Below 1.0, a minor release (`0.x` → `0.x+1`) may break any surface below, and a patch release never does. From 1.0, only a major release may. A breaking change is always called out in [CHANGELOG.md](../CHANGELOG.md).

In the general form any repo can declare, [CONFIG.md "Release strategy"](CONFIG.md#release-strategy), this is `versioning: semver`, `mechanism: script` with `script: scripts/release.ts`, `registry: none` and `cadence: manual`.

| Surface | What counts as breaking |
|---|---|
| CLI JSON | Renaming or removing a JSON field, an error code or an exit number ([CLI.md](CLI.md#stability)). New commands, flags and fields are additive. |
| `/api/p/<project>/state` and the other `/api/*` endpoints | Removing or renaming a field. Every shape change, additive or not, bumps `API_VERSION`, and a dashboard refuses data from a newer server. |
| The `job.json`, config and event schemas | Dropping a migration, so an older job or config no longer loads, or changing what a field means. New versions migrate older files on read. |
| Config keys | Removing or renaming a key, or changing what a default does. A key is deprecated first (see Deprecation). |
| The agent/skill contract | `/forge` arguments, `forge:<role>` agent names, agents' reply contracts, job file names and spec headers, review lens names, and the tracker adapter contract in `lib/api/tracker.ts` (`lib/trackers/status.ts` and `status.mjs` re-export it, deprecated, and are removed one minor release after the move ships). |

## Support

Only the latest minor release line gets fixes, security fixes included, as patch releases. Older lines get no backports: upgrade with `forge update`. [SECURITY.md](../SECURITY.md#supported-versions) has the reporting process.

## Deprecation

A config key or CLI flag on its way out is announced in CHANGELOG.md at least one minor release before it is removed. While it still works:

- it is listed in `DEPRECATED_CONFIG_KEYS` in `lib/core/config/validators/deprecations.ts`, with the release that deprecated it, the release that removes it and what to use instead, and in [CONFIG.md](CONFIG.md#deprecated-keys) "Deprecated keys";
- `forge doctor` (and Settings › Diagnostics) shows a warning row, `deprecated config key <key>`, whenever it is set in `.forge/config.yml`. A warning never fails the report.

## Releasing

A release is a reviewed PR into `main`, the **release PR**, from a `release/v<version>` branch. It carries the **release commit**, `Release <version>`: the `version` in `package.json`, `package-lock.json` and `.claude-plugin/plugin.json`, that version's `## <version>` section in CHANGELOG.md, and the forge plugin's `source.ref` in `.claude-plugin/marketplace.json` set to `v<version>`. On top of it sits the **main update**, which adds the CI-built `dashboard/dist/`. A human merges the PR, `release.yml` tags the merge commit and publishes the GitHub Release, and the release commit then lands on `develop`. Forge jobs never make that change: the maintainer makes it at the end of a wave, with `forge release run` or `npm run release`.

**Branches and installs.** `develop` is the working branch and the GitHub default branch: jobs and PRs branch from it and merge into it. Because it is the default, an install added with `claude plugin marketplace add maxwellmattryan/forge` reads `.claude-plugin/marketplace.json` from `develop`, and the forge plugin's `source.ref` there decides which commit it installs. develop's copy is the install switch, and it names the `v<version>` tag of the latest release. `forge update` runs `claude plugin marketplace update` and `claude plugin update`, so it follows that ref; it resolves no tags itself. `main` holds the released commits, each carrying the CI-built `dashboard/dist/`, and takes only release PRs and hotfix PRs. `dashboard/dist/` is gitignored and absent on `develop`, and nobody builds it by hand for a release: CI builds it, because an install never builds. Never merge `main` back into `develop`: it would bring `dist/` with it.

**Two paths, one script.** Once `.forge/config.yml` declares Forge's release as a [script release strategy](CONFIG.md#release-strategy) (the block is in CONFIG.md; a maintainer adds it on `develop`, as a job can't edit that file), `forge release` runs it as it runs any project's release ([Releasing a project](#releasing-a-project)), and `npm run release` stays as the fallback; until then `forge release` skips this repo and `npm run release` is the whole release. Both run `scripts/release.ts` and make every check below; either can finish a release the other started, since every phase finds the release in flight the way a resume does. On a clean `develop` that equals `origin/develop`, with `gh` signed in:

1. `forge release plan` runs `scripts/release.ts --draft-notes` (local git only), shows the version bump it inferred and why (`minor` when a version list moved or any commit is not a fix, else `patch`; never `major`), and writes the draft to `.forge/runtime/release/notes-root.md`. Rewrite the notes there; a re-plan of the same version keeps your edits. `forge release plan --bump patch|minor|major` picks another bump and drafts that version again.
2. `forge release run --dry-run` lists the steps, what each runs and which ask, and runs nothing.
3. `forge release run` runs them: `preflight` (develop is clean and level with `origin/develop`); `start` cuts the release commit from your notes file and pushes `release/v<version>` (**publish**); `build` waits for `main-update.yml`; `pr` pushes the main update and opens the release PR, or checks the open one (**publish**); `merge` is yours, below (**publish**, manual, checked by `--check merged`); `tag` waits for `release.yml`'s tag; `land` lands the release commit on `develop` and pushes it (**publish**). Each publish step asks `Run it?` with its command; the release script asks nothing more, except that hotfixes on `main` the release lacks stop the `pr` step: port them, answer the question with `npm run release` on a terminal, then run `forge release run` again. A release behind `origin/develop` warns and goes on: it is `develop` as it was at `start`.

If a step stops for a reason that isn't a bug, fix it and run `forge release run` again, or finish with `npm run release` and no version.

**Start a release with `npm run release -- patch|minor|major|X.Y.Z [--notes-file <file>] [--yes]`** on a clean `develop` that equals `origin/develop`, with `gh` signed in:

1. It fetches `develop`, `main`, the tags and the `release/*` branches. It refuses when the current version is untagged, when `v<next>` is already tagged, or when a release is in flight: a local or remote `release/vX.Y.Z` branch above develop's version, or `origin/main`'s version above develop's (a merged release not yet landed, or a hotfix not yet ported). The refusal names the version and says to run `npm run release` with no version to finish it, or to port the hotfix.
2. It drafts the `## <version>` section from the first-parent commits on `develop` since the last tag, release commits dropped, plus a `Versions:` line for any version that moved: the lists in `lib/core/versions/` and `lib/api/versions.ts`, and `ARCHIVE_SCHEMA_VERSION`. It opens the draft in `$VISUAL` or `$EDITOR`, or takes the notes from `--notes-file <file>`; lines starting with `<!--` are dropped. Rewrite the draft as notes: behaviour changes first, then fixes, the versions bumped, deprecations and removals.
3. It bumps the three version files, inserts the section into CHANGELOG.md and sets marketplace.json's ref to `v<version>`, checking every file before it writes any. It runs the release check (`--dist absent`) and commits the release commit on a new local branch `release/v<version>` cut from `develop`, then switches back. `develop` and `origin/develop` do not move.
4. It asks, then pushes the release commit to `origin release/v<version>`. That push runs `.github/workflows/main-update.yml`: one `build` job, with a read-only token, runs `npm ci` and `npm run build:dashboard` and uploads `dashboard/dist/` as the `dashboard-dist` artifact. It writes nothing to the repo.
5. It goes on as a resume does.

**Resume: `npm run release` with no version.** It finds the one release in flight and runs whichever steps are not done yet, so nothing runs twice. Before the PR merges, and before it pushes anything or shows the PR, it counts the commits `origin/develop` has that the release commit lacks (`git rev-list --count <release commit>..origin/develop`). When there are any, it prints the count and asks before going on: a release branch cut from an older `develop` commit is still a release commit, and it would ship without them.

- **Before the PR.** It waits for `main-update.yml`'s push run on the release commit, trusting a run only when it is that workflow file's own push or dispatch run in this repo, on the release branch, for that exact commit. It lists the hotfixes on `main` that the release lacks, and asks whether they were ported: the release undoes any that weren't. It downloads the artifact and builds the main update with `scripts/main-update.ts`. That checks the artifact holds only `index.html`, `manifest.json`, `build-stamp.json` and the `assets/*.js|css|woff2` files the manifest names, with no symlinks, and that its build stamp matches both the files and the release commit's dashboard sources. It refuses when the release commit tracks a `dashboard/dist/` path or the version is already tagged. The main update is the release commit's tree plus `dashboard/dist/`, with parents `[origin/main, release commit]`, subject `Release <version>`, authored by you. It asks, pushes it to `release/v<version>` as a fast-forward, opens the release PR (`Release <version>`, into `main`), prints its URL and the instruction, and exits. When the branch already holds a main update (an earlier run pushed it before it stopped), it does not trust it: anyone who can push the branch can push a commit shaped like one, and the PR would carry it into `main`. It downloads the same artifact, builds the main update again and refuses unless the pushed tip has exactly that tree, then goes on.
- **PR open.** It checks the branch tip the same way, then prints the URL and the instruction, and exits. It refuses when the PR's head is not the branch tip.
- **PR closed without merging.** It refuses: reopen the PR, or delete `release/v<version>` (on origin and locally) and start over.
- **PR merged.** It waits for `release.yml`'s push run on the merge commit unless `v<version>` already exists on origin, and refuses unless the tag points at the merge commit. It then checks the head the PR merged again, because the merge published whatever the branch held at that moment and `release.yml` reads no tree: the merge commit must have the head's tree, and the head must be the main update derived from the release commit and `main-update.yml`'s artifact, as in "Before the PR" (that needs the artifact too). When it is not, nothing lands on `develop`, so installs still follow the previous tag, and it says what to delete (see Recovery). Then it lands the release commit on `develop`: a fast-forward when `origin/develop` is still its parent, nothing when `develop` already has it, and otherwise a `Release <version>` merge commit on a `develop` that equals `origin/develop` (on a conflict it aborts and says to merge it by hand). It asks, pushes `develop` and prints the Release URL. If you decline the push, local `develop` keeps the landing, and the next `npm run release` finds the release again (it reads `origin/develop`'s version, not your working tree's) and pushes it as it is, after the same checks. It pushes a local `develop` only when it is exactly the landing: the release commit with `origin/develop` as its parent, or a merge whose parents are `origin/develop` and the release commit. Anything more on it refuses ("develop differs from origin/develop"), since the push would carry it too. If the push is rejected because `origin/develop` moved, put `develop` back on it (`git fetch origin develop`, then `git reset --keep origin/develop`) and run `npm run release` again: it lands the release on the new tip. The repo deletes a PR's head branch on merge, so here it finds the release from `origin/main`'s version and the merged PR.

It refuses a release branch whose tip is neither a release commit nor a main update of one (a hotfix branch: finish it by hand, see Hotfixes below). A release commit has one parent, which is on `origin/develop`'s first-parent chain (a commit `develop` itself was at, not one from a branch merged into it); its subject is exactly `Release <version>`, its `package.json` is at that version and tracks no `dashboard/dist/`, and it changes only the version files, marketplace.json and CHANGELOG.md, each exactly as the bump would: the parent's bytes with only the version lines (and marketplace.json's ref) rewritten, and CHANGELOG.md with one `## <version>` section inserted above its newest heading. Anything else in those files, such as another `resolved` URL in `package-lock.json`, a key added to `plugin.json` or `marketplace.json`, or an older CHANGELOG section edited, is refused. A branch someone else pushed, with anything more in it, is refused the same way. It also refuses an `origin/main` that moved past the main update's first parent (close the PR, delete the branch, port main's commits to `develop` and start again), and nothing in flight (name the next version). `--yes` answers every question; without a terminal it is required, and `--notes-file` replaces the editor. Whoever runs it pushes, and a human merges, not CI: a push or merge `GITHUB_TOKEN` makes starts no workflow run, and `GITHUB_TOKEN` can't push a commit that changes `.github/workflows/`. If GitHub refuses a push over a workflow file, your credential lacks the `workflow` scope: `gh auth refresh -s workflow`, then run it again.

**Merging the release PR.** Its body holds the CHANGELOG section, a compare link from `v<prev>` to the release branch, and the instruction. The PR's own diff is against `main`, so it equals `v<prev>..` only while `main` sits at the tag: after a hotfix it leaves out what the hotfix already changed, and the compare link shows everything since the tag. Wait for its CI, merge it in GitHub with **Create a merge commit** (not squash or rebase: the merge commit is what gets tagged), then run `npm run release`. Merge only while the PR's head is the sha `npm run release` printed as the head it checked (the PR body says it too): a push to the branch after that is not checked until the landing, and what you merge is published first. If the head moved, run `npm run release` again before you merge. The Release notes are the CHANGELOG section in the merged commit, frozen in the release commit and reviewed in the PR diff. The PR body is a copy for reviewers that no workflow reads, so editing it changes nothing and PR text never reaches the Release.

**`release.yml`** runs on the merge's push to `main`:
- **detect** reads the pushed commit. It is a release only when the version differs from the first parent's and no `v<version>` tag exists. Any other push stops here.
- **verify** runs all of `ci.yml` again on that commit, with a read-only token.
- **build**, read-only, writes the notes with `node scripts/release-plan.ts notes` and `forge-<version>.tar.gz` with `git archive`, refusing an archive whose `COMMIT` file does not hold the pushed sha, and uploads both as the `release-files` artifact.
- **release** holds `contents: write` and `actions: read` and runs nothing but `gh`. It downloads this run's `release-files`, finds the PR whose merge commit is the pushed sha (exactly one merged PR into `main` from this repo's `release/v<version>`, or it fails before anything is published) and adds `Release PR: <url>` to the notes. Then it creates the annotated tag `v<version>` (message `Forge <version>`) on the merge commit, and publishes the GitHub Release `Forge <version>` with the notes as its body and the archive as its one asset.

A push to `main` with a bumped version and no release PR publishes nothing.

**When the ref resolves.** develop's marketplace.json, the one installs read, names `v<version>` only once the release commit lands, after the tag exists, so installs never see an unresolved ref. `main`'s copy names `v<version>` from the merge until `release.yml` tags it, about the length of the `verify` run; nothing reads it unless the default branch becomes `main`. A git-clone install that updates with `git pull` (`forge update` in a clone) keeps following its branch, `main` or `develop`, not the tags.

**The release check.** CI's `release check` job runs `npm run release:check -- --dist present` on `main` and on every PR into it, and `--dist absent` on `develop`; `npm run release` runs `--dist absent` before it commits. It fails unless both versions are equal and `X.Y.Z`, CHANGELOG.md has an exact `## <version>` heading with notes and no AI attribution line, `.claude-plugin/marketplace.json` points the forge plugin at `v<version>`, the working tree is clean, and `dashboard/dist/` is tracked and matches its build stamp (`present`) or is not tracked at all (`absent`). With `present` it also fails when `v<version>` is already tagged at another commit, so a hotfix PR without a version bump fails.

**Hotfixes.** Branch `release/v<x.y.z+1>` from `main` and commit the fix, the version bump, its CHANGELOG section, marketplace.json's `ref: v<x.y.z+1>` and a rebuilt `dist/` (`npm ci`, `npm run build:dashboard`, then `git add --force dashboard/dist`). Open a PR into `main`, whose `release check` runs `--dist present`, and merge it with a merge commit: `release.yml` tags and publishes it as it does a release. Then port the fix, bump, section and ref to `develop` in a PR without `dist/`, merged after the tag exists. `npm run release` automates none of this: until the port, it refuses to start a new release, and a resume refuses the hotfix branch.

**Recovery.** If `npm run release` stops (a failed run, a refused push, a closed terminal), fix the cause and run `npm run release` with no version. If the dashboard artifact has expired (after 7 days), use "Re-run all jobs" on the `Main update` run for the release commit in the Actions tab (a re-run builds the same commit), or, while the branch tip is still the release commit, start a `Main update` run on `release/v<version>`; then run `npm run release` again. A resume needs that artifact even once the PR is open, to check the pushed main update, and the landing needs it once more, to check the merged head. That includes a run that only pushes a landing whose push you declined: it checks the merged head again before it pushes. If `release.yml` fails before the tag step (the PR lookup included), use "Re-run failed jobs" on the same run: detect still sees the version change, and the tag does not exist yet. If only the publish step failed, the tag already exists, so a re-run stops at the tag step with "Reference already exists". Publish by hand from that run's `release-files` artifact instead: `gh run download <run id> --repo maxwellmattryan/forge --name release-files --dir release`, append `Release PR: <url>` to `release/notes.md` if it doesn't end with it, then `gh release create v<version> --verify-tag --title "Forge <version>" --notes-file release/notes.md release/forge-<version>.tar.gz`. If the artifact is gone, build both in a clone checked out at the tag: `node scripts/release-plan.ts notes > notes.md` and `git archive --format=tar.gz --prefix=forge-<version>/ -o forge-<version>.tar.gz v<version>`. If the landing is refused because the merged head is not the main update derived from the release commit, or the merge commit does not have the head's tree, nothing reached `develop` and installs still follow the previous tag, but `release.yml` has already published `v<version>` from a merge that was not what was checked and `main` holds it: delete the Release and its tag (`gh release delete v<version> --cleanup-tag`), undo the merge on `main` with a hotfix PR (see Hotfixes), and find out who pushed to `release/v<version>`. If a bad tag or Release was published, delete both by hand (`gh release delete v<version> --cleanup-tag`) and ship the fix as the next patch version. Never move a published tag.

**Repository settings** a maintainer keeps:
- a ruleset on `main` that requires a pull request before merging and blocks force pushes and deletion, bypassed only in an emergency;
- optionally, a ruleset on `release/v*` that restricts creations and updates and blocks force pushes, with only maintainers on its bypass list (deletions stay open, so a merged PR's head branch is still deleted). Without it, anyone who can push can move a release branch after `npm run release` checked its head, and the landing catches that only after `release.yml` has tagged and published the merge. With it, nobody else can create or move one before the merge;
- merge commits allowed on PRs into `main`, and head branches deleted on merge;
- `develop` as the default branch, since installs read its marketplace.json;
- Settings › Actions › General › Workflow permissions at "Read repository contents".

## Releasing a project

`forge release` releases the repos of a project that uses Forge, single- or multi-repo, from each repo's declared [release strategy](CONFIG.md#release-strategy). A human runs it from the CLI; the Foreman never does, though it may approve a job's or an `until: released` mandate's plan when the project hands it the `release` gate class (Confirmation, below). (Forge's own release is [Releasing](#releasing) above.)

1. `forge release plan` picks the repos, orders them dependencies first and writes the plan to `.forge/runtime/release/`: `release.md` for you to read (steps, checks, rollback) and `release.json` for `run`. It runs no release step: no release command, no registry command, no `git fetch`. A repo with `mechanism: script` is the one exception: the plan runs its script's `--draft-notes` (under the command environment; it reads only local git and the working tree), records the version bump on the repo in `release.json` (`bump: {from, to, bump, inferred, reasons, notes}`) and writes the draft to its notes file, `notes-root.md` (`notes-<repo>.md` for a member). The file is kept as it is when its first line is already `## <to>`, so your edits survive a re-plan of the same version. `release.md` shows `<from> → <to>`, the chosen and inferred bump with the reasons, and the notes file. The output lists `bumps: [{repo, from, to, bump, inferred, reasons, notes, notesKept}]`. `--bump patch|minor|major` replaces the inferred bump (any other value is a usage error; on a plan with no script repo it refuses).
2. `forge release run --dry-run` shows what a run would do: `{dryRun: true, plan, hash, selection, done, total, steps, bumps}`, each step with its `command`, `publish`, `manual`, `asks` (a publish step that would ask), `check` and `status` from a `state.json` of this plan. It recomputes the plan and refuses a missing, stale, edited or symlinked one as `run` does, but runs nothing (no step, no check, no script, no `git fetch`), takes no lock and writes nothing, so it is allowed in a daemon session and on native Windows.
3. `forge release run` runs the steps in order, checking each one, and records each step in `state.json` as it goes. It stops at the first failure. Run it again to resume at the first step not done; finished steps never run again.
4. `forge release status` shows each step's status, the tags and versions its checks recorded (what a rollback needs), the next step, `stale: true` when config or the repos have moved since planning, and `approval: {owner, status}`: who decides the publish steps (`human` or `foreman`) and whether the Foreman has approved this plan (`pending` or `approved`, with `actor` and `at`).

**Which repos.** With no flag, the root repo and every `repos` entry. `--job <id>` takes the job's PR repos (not its verify-only members) whose PR merged (`forge pr sync <id>` records it). An unmerged PR repo that is the consumer of an interim edge is listed under "Not released" with `PR not merged: it waits on its dependencies' release`; any other unmerged PR refuses the plan, and so does a job with no merged PR at all. `--since <tag>` takes the repos where the tag resolves and has commits after it, and refuses when no repo has the tag. `--mandate <id>` re-plans an `until: released` mandate's release since the root repo's latest tag (the mandate path, below). A repo with no `release.mechanism`, or (without `--job`) a member whose clone fails doctor's `repo <name>` check, is listed under "Not released" with the reason. A config with problems, or a build cycle between the repos' components, refuses the plan; a cycle that only runtime edges close is ordered by build edges and noted.

**Consumers after a release.** On a `--job` plan, `forge release run` records the release of each dependency repo whose last step reaches done in that run: it logs `interim-released` on the job, as `forge job interim release` would (CONFIG.md "Interim strategies"), which resumes a job waiting on `pr-review` so verify bumps the consumers to it. The version comes only from the checks that run ran, never from `state.json`: a registry check's version, else a tag `<link name>@<version>`, else a tag that is a version itself (`v1.2.0`, `1.2.0`). Several versions at the first level that has any, or none at all, record nothing. The result lists `released: [{ repo, version, recorded, hint? }]`; when `version` is null, `hint` is the `forge job interim release <id> <repo>|--root <version>` command to run by hand. A whole-project or `--since` run records nothing on any job.

**Steps.** Every repo starts with `preflight`: the clone is on its base (`git.base` for the root, `defaultBranch` for a member), has nothing uncommitted, and after `git fetch` equals `<git.remote>/<base>`. Then, by mechanism (**publish** marks an outward-facing step):

| Mechanism | Steps after preflight |
|---|---|
| `tag` | `release`: `release.command`, through the POSIX shell as `forge run` runs commands (**publish**, checked by tag-pushed); then the registry step |
| `cargo-release` | `publish`: `cargo release publish --execute --no-confirm` (**publish**, registry, no check with `registry: none`); `tag`: `cargo release tag --execute --no-confirm` (tagged); `push`: `cargo release push --execute --no-confirm` (**publish**, tag-pushed) |
| `changesets` | `version`: `changeset version`; `stage`: `git add --all`; `commit`: `git commit --message "Version packages"` (clean); `publish`: `changeset publish` (**publish**, tagged); `push`: `git push --follow-tags <remote> HEAD:refs/heads/<base>` (**publish**, tag-pushed) |
| `release-please` | `merge`: you merge the open release PR on GitHub (**publish**, manual, remote-tagged); `sync`: `git merge --ff-only <remote>/<base>` (at-remote); then the registry step |
| `script` | `start`: `node <script> --phase start <v> --notes-file <notes>` (**publish**); `build`: `node <script> --phase wait-build <v>`; `pr`: `node <script> --phase pr <v>` (**publish**); `merge`: you merge the release PR from `release/v<v>` with "Create a merge commit", only while its head is the one the `pr` step printed as checked (**publish**, manual, pr-merged); `tag`: `node <script> --phase wait-tag <v>`; `land`: `node <script> --phase land <v>` (**publish**). No registry step, whatever `registry` says |

For `script`, `<v>` is the plan's `bump.to` and `<notes>` the repo's notes file. A recompute (`run`, `status`, `--dry-run`, the Foreman's approval) takes the bump from `release.json`, never runs the draft again, and refuses a file whose script repo has no valid bump (`to` must be `X.Y.Z`) with "re-run forge release plan"; the notes path is always Forge's own, never the file's. The steps name `<v>`, so the plan hash covers it, but not the notes' content: the release PR's diff is where the notes are reviewed. The CI waits are the script's own polling; Forge adds no loop. Rollback, last step first: `land`, ship the fix as the next patch (to stop installs following `v<v>` sooner, revert the landing in a PR); `merge`, `gh release delete v<v> --cleanup-tag`, then undo the merge on main with a hotfix PR, never moving a published tag; `pr`, close the release PR; `start`, `git push <remote> --delete release/v<v>`, then `git branch -D release/v<v>`.

The registry step, for `tag` and `release-please`: `npm publish` with `registry: npm`, `cargo publish` with `registry: crates.io`, none otherwise. Programs are found on PATH (relative PATH entries are skipped), `changeset` and `release-please` in the clone's `node_modules/.bin` first, and run without a shell in the clone; output goes to your terminal and to `.forge/runtime/release/logs/`. There is no timeout, and stdin is yours, so npm's one-time-password prompt works.

**Checks.** A step with a check is done only when its check passes after the command exits 0: clean (nothing uncommitted), tagged (HEAD carries a tag), tag-pushed (tagged, and the remote has the base at HEAD and every tag at HEAD), remote-tagged (after a fetch, `<remote>/<base>` carries a tag), at-remote (HEAD equals `<remote>/<base>`), registry (`npm view <name>@<version> version`, or `cargo search <name>`, finds the version in the root `package.json` or `Cargo.toml`), pr-merged (the release script's `--check merged <v>`, run with the Node that runs Forge in the clone, exits 0). A workspace root or a private package has no registry check, and `release.md` says to check by hand. On a resume, and before every step, the check runs first: when it already passes, the step is marked done without running, so a step that published but crashed before its checkpoint never publishes twice. CI that already released (cadence `on-merge` or `scheduled`) is skipped the same way.

**Confirmation.** Each publish step asks `Run it? [y/N]` on the terminal, unless that repo sets `release.publish: allow`. Without a terminal on stdin and stderr, the run stops with `needs_confirmation`, so an agent session stops there too; with `allow`, it does not. The release-please and script merges always need a terminal: each prints the instruction and asks `Done? [y/N]`, then checks; a merge whose check already passes is skipped. There is no flag or environment variable that skips the question.

**The Foreman's approval.** A project can hand the decision to the Foreman by moving the `release` gate class: add `release` to `foreman.decides` and remove `gate:release` from `foreman.reserved` (CONFIG.md "Foreman"; the defaults keep it with a human). Then `forge release plan --job <id>` logs a `release-planned` event with the full plan hash and queues one `release` gate request for the assistant foremen, once per job and hash; its output's `approval` says who owns the decision. The Foreman's assistant reads `release.md` and the release strategy, and the assistant foreman records `forge job human <id> approve-release --actor foreman --note "<reason>"`, which re-plans and refuses unless the plan is unchanged, is the job's latest, has a queued request and isn't approved yet, nothing reserved shows in the job or the note, and, for a job in a mandate, the mandate's `decides` names `release` and the mandate is neither paused nor closed (CONFIG.md "Mandates"). Without a terminal, `forge release run` then passes each publish step without asking and reports `approvedBy: "foreman"`, but only while that approval is for the plan it just recomputed, the Foreman still decides `release` with nothing reserved, and the job's mandate, if it has one, still delegates `release`. A re-plan with a different hash, taking the class back, or a mandate that stops delegating `release` or is paused, closed, deleted or unreadable leaves the approval unused: run asks at each publish step again (or stops without a terminal), and `forge release status` reports `approval: {owner: 'human', status: 'pending'}`. On a terminal it still asks at every publish step, the release-please merge still needs a terminal, and the run itself is still started by a human or CI, never a daemon session. A person approves a release by answering the prompt, not with `approve-release`. The question guards against an accidental publish, for example an agent session that runs `forge release run` by mistake; it is not a security boundary, since a process that fakes a terminal can answer it, and such a process could run the publish command itself anyway.

**A mandate's release.** A mandate with `until: released` (it needs `foreman.ship: release`; CONFIG.md "Mandates") plans its own release once every job in its scope has merged: the Office pass plans `--since` the root repo's latest tag reachable from HEAD, bound to the mandate (`release.md` reads `since <tag> for mandate <id> at (root) <sha12>, …`; the hash covers the mandate and each planned repo's HEAD, so a plain `--since` plan of the same tag is another plan, and a commit that lands afterwards, a merge after the approval included, makes the plan stale until the pass plans again). It logs `mandate-release-planned` to the repo audit log and waits for release approval under the same `release` gate class policy as a job's plan. With the default `gate:release` reserved, or a mandate whose `decides` leaves `release` out, no gate request is queued and the decision is a person's: run `forge release run` in a terminal and answer each publish prompt (or set `release.publish: allow`). When the Foreman decides `release`, the pass queues one job-less gate request; the assistant foreman reads its brief with `forge mandate release assist <id> --request <rid>` and records `forge mandate release approve <id> --actor foreman --note "<reason>"`, which logs `mandate-release-approved`. That approval starts nothing: a human or CI runs `forge release run`, which without a terminal passes each publish step of that exact plan (`approvedBy: "foreman"`) only while the Foreman still decides `release`, the mandate is active, still lists `release` in its `decides` and still runs `until: released`, and nothing reserved matches its title, its jobs' titles or the note. A run that finishes the plan logs `mandate-release-finished`, and the next pass closes the mandate, unless a mandate job merged after the plan was planned: then it plans again. The pass never re-plans over another plan (`release: blocked by another plan, plan it with forge release plan --mandate <id>`) or a run in progress: a person plans with `forge release plan --mandate <id>`, which re-plans once the pass planned, and makes the first plan while another plan in `release.json` holds the pass back (one it can't read, or one whose run hasn't finished). It is refused in every daemon session, before the pass's first plan otherwise, for a mandate that isn't active, and for one whose effective `until` isn't `released`. A plan that went stale after a step of its run started waits for `forge release plan --mandate <id> --force`, and `forge release run` names the `--mandate` re-plan when it refuses a stale mandate plan: a plain `forge release plan` would replace it, and the mandate would never close. The mandate uses the root repo's tag only: a member without it is listed under "Not released" (`no tag <tag>`), and a root repo with no tag yet, or nothing to release since it, leaves the mandate waiting with that reason. A repo with `mechanism: script` gets its version bump and notes file as a plain plan does (step 1 above; the pass takes the inferred bump; `forge release plan --mandate <id> --bump patch|minor|major` picks another).

**Safety.** `forge release run` and `forge release plan --force` are refused in a daemon session, and `run` on native Windows (use WSL2, [SUPPORT.md](SUPPORT.md)); `run --dry-run` is not, since it runs nothing. `run` recomputes the plan from config and the clones and refuses when it differs from `release.json` or `state.json`; commands always come from that recomputation, never from the file. One run at a time: `.forge/locks/release/` holds it (exit 3 while another run is alive). `plan` refuses to replace an unfinished run of a different plan unless `--force`, which discards its checkpoints.

**Rollback** is written in `release.md`, last released first, and Forge never runs it. A pushed tag can be deleted (`git push <remote> --delete refs/tags/<tag>`, plus its GitHub Release); a pushed version commit is reverted. Registries limit what can be undone: npm allows `npm unpublish` only within 72 hours and when no other public package depends on the version (otherwise `npm deprecate`), and crates.io never deletes a version, only `cargo yank`s it so new lockfiles skip it.

## Installing and updating

Install the plugin from Claude Code with `/plugin marketplace add maxwellmattryan/forge` and `/plugin install forge@forge`. It needs Node ≥ 22.18, git ≥ 2.38, and the GitHub CLI (`gh` ≥ 2.40) for PR and GitHub-tracker features; [SUPPORT.md](SUPPORT.md) lists the supported platforms. On Node older than 22.18 the CLI fails at import and the attribution hook cannot load: it exits 1, which Claude Code does not treat as a block, so `aiAttribution: forbid` is not enforced.

The CLI also works on its own, for other agent runtimes, scripts or CI: `git clone https://github.com/maxwellmattryan/forge && cd forge && npm link`, then `forge help`. Forge's engine is TypeScript that Node runs directly, and Node does not strip types under `node_modules`, so install from a clone, not as a global npm package.

Run `forge update` in a terminal or `/forge update` in Claude Code. It updates the install that is running. For a plugin install it runs `claude plugin marketplace update <marketplace>` and then `claude plugin update forge@<marketplace>`. For a clone it runs `git pull --ff-only`, and refuses when the checkout has uncommitted changes, a detached HEAD or no upstream. It prints the old and new versions, restarts the current repo's running dashboard on the new code, and lists what still needs a restart: a new Claude Code session for a plugin install, and dashboards in other repos. `forge update --check` only shows what it would run. `--keep-dash` leaves this repo's dashboard alone. A plugin install follows the latest release: the marketplace names its `v<x.y.z>` tag, so `forge update` moves it from one release to the next and never to unreleased work. A plugin install or a clone of `main` builds and installs nothing, because Forge has no runtime dependencies and every commit on `main` carries the built `dashboard/dist/`, which CI builds for each release. A clone keeps following its branch (`git pull`), not the tags. A clone of `develop` has no built dashboard: run `npm ci` and `npm run build:dashboard` after each update (`forge doctor` warns until you do).

Each release is a `v<x.y.z>` tag and a GitHub Release with its CHANGELOG notes and a source archive. `forge version --json` prints the running version and commit. To pin a version, clone its tag (`git clone --branch v<x.y.z>`) or extract its archive and load it with `claude --plugin-dir`; to roll back, check out an older tag. [Versioning](#versioning), [Support](#support) and [Provenance and pinning](#provenance-and-pinning) below have the details.

## Provenance and pinning

Every commit on `main` is the merge of a release PR or a hotfix PR, so its `dashboard/dist/` was built by CI (the `Main update` build of the release branch) and checked against the release commit's sources, or built by the hotfix's author and checked by `release check`. Every `v<version>` tag is an annotated tag that `release.yml` made on such a merge commit, after `verify`.

`forge version --json` prints `{"version","commit","installedAs","node"}`. `commit` comes from the first source that has one: the `COMMIT` file a release archive carries (`git archive` stamps it through `.gitattributes` `export-subst`), Claude Code's own install record for a plugin install, then `git rev-parse HEAD` for a clone. Settings › About shows the same commit and install kind. The output is self-reported, so anything that can edit the install can make it claim any commit. The audit anchors are the annotated tag and comparing the archive with `git archive` of the tag.

**Verify an archive.** Download `forge-<version>.tar.gz` from the Release. Extracted, its `COMMIT` file is the tagged commit, and `forge version --json` run from it reports that commit with `installedAs: "unknown"`. To check it is that commit's tree, compare it with the tag in a clone: `git rev-parse v<version>^{commit}` must print the sha in `COMMIT`, and `gunzip -c forge-<version>.tar.gz | sha256sum` must equal `git archive --format=tar --prefix=forge-<version>/ v<version> | sha256sum` (a different git version can lay out the tar differently: then extract both and `diff -r`). Releases have no `.sha256` asset any more: the same job published it in the same Release as the archive, so it proved nothing HTTPS doesn't, and anyone who could replace one could replace both.

**Pin a version.** Either:

- clone the tag, `git clone --branch v<x.y.z> https://github.com/maxwellmattryan/forge.git`, or
- extract the release archive,

and then load that directory with `claude --plugin-dir <dir>`, or add it as a local marketplace with `claude plugin marketplace add <dir>`. A pinned clone sits on a detached tag, which `forge update` refuses to move.

A marketplace install added from GitHub (`claude plugin marketplace add maxwellmattryan/forge`) follows the latest release: the `v<version>` tag that develop's `.claude-plugin/marketplace.json` names, which `forge update` moves to the next release once it lands. It cannot pin an older version: `claude plugin marketplace add` (Claude Code 2.1.299) takes a URL, a path or a GitHub repo, with no ref. A git clone follows its branch, not the tags, unless it is checked out at a tag.

**Roll back.** In a pinned clone, `git fetch --tags` and `git checkout v<older>`; with an archive, extract the older one. Then start a new Claude Code session (and restart `forge dash`). Jobs and configs written by a newer Forge may not load in an older one; `forge doctor` flags jobs from a newer Forge.

## Release checklist

1. Every job of the wave is merged into `develop`, each after a green CI run on its PR.
2. On a clean `develop`, run `npm run release -- patch` (or `minor`, `major`, `X.Y.Z`). Rewrite the drafted notes: behaviour changes first, the versions bumped (`API_VERSION`, schemas), deprecations and removals.
3. Answer its questions: push the release branch, whether the listed hotfixes were ported, push the main update. It waits for the dashboard build, opens the release PR and prints its URL. `origin/develop` does not move.
4. Check the release PR: `release/vX.Y.Z` into `main`, its body (the notes and the compare link), its diff (the bump, the CHANGELOG section, `ref: vX.Y.Z` and `dashboard/dist/`) and its CI. Merge it with **Create a merge commit**, and only while its head is the sha `npm run release` printed.
5. Run `npm run release` again. It waits for `release.yml` (`detect`, `verify` and `build` read-only, then `release`: download, find the PR, tag, publish), checks the merged head once more, lands the release commit on `develop` after asking, and prints the Release URL.
6. Check the Release page: tag `vX.Y.Z` on the merge commit, the CHANGELOG body ending with the release PR's link, and `forge-X.Y.Z.tar.gz` as its only asset.
7. Run `forge update` on a plugin install and confirm `forge version --json` reports `X.Y.Z` and `forge doctor` shows no "behind the latest release" warning.
