# Releases

How Forge is versioned, which releases get fixes, how a release is cut, and how to pin, verify and roll back an install.

## Versioning

Forge follows [semver](https://semver.org). Below 1.0, a minor release (`0.x` → `0.x+1`) may break any surface below, and a patch release never does. From 1.0, only a major release may. A breaking change is always called out in [CHANGELOG.md](../CHANGELOG.md).

In the general form any repo can declare, [CONFIG.md "Release strategy"](CONFIG.md#release-strategy), this is `versioning: semver`, `mechanism: tag`, `registry: none` and `cadence: on-merge`.

| Surface | What counts as breaking |
|---|---|
| CLI JSON | Renaming or removing a JSON field, an error code or an exit number ([CLI.md](CLI.md#stability)). New commands, flags and fields are additive. |
| `/api/state` and the other `/api/*` endpoints | Removing or renaming a field. Every shape change, additive or not, bumps `API_VERSION`, and a dashboard refuses data from a newer server. |
| The `job.json`, config and event schemas | Dropping a migration, so an older job or config no longer loads, or changing what a field means. New versions migrate older files on read. |
| Config keys | Removing or renaming a key, or changing what a default does. A key is deprecated first (see Deprecation). |
| The agent/skill contract | `/forge` arguments, `forge:<role>` agent names, agents' reply contracts, job file names and spec headers, review lens names, and the tracker adapter contract in `lib/api/tracker.ts` (`lib/trackers/status.ts` and `status.mjs` re-export it, deprecated, and are removed one minor release after the move ships). |

## Support

Only the latest minor release line gets fixes, security fixes included, as patch releases. Older lines get no backports: upgrade with `forge update`. [SECURITY.md](../SECURITY.md#supported-versions) has the reporting process.

## Deprecation

A config key or CLI flag on its way out is announced in CHANGELOG.md at least one minor release before it is removed. While it still works:

- it is listed in `DEPRECATED_CONFIG_KEYS` in `lib/core/config/validators/deprecations.ts`, with the release that deprecated it, the release that removes it and what to use instead, and in [CONFIG.md](CONFIG.md#deprecated-keys) "Deprecated keys";
- `forge doctor` (and Settings › Diagnostics) shows a warning row, `deprecated config key <key>`, whenever it is set in `.forge/config.yml`. A warning never fails the report.

## Releasing

A release is a reviewed PR into `main`, the **release PR**, from a `release/v<version>` branch. It carries the **release commit**, `Release <version>`: the `version` in `package.json`, `package-lock.json` and `.claude-plugin/plugin.json`, that version's `## <version>` section in CHANGELOG.md, and the forge plugin's `source.ref` in `.claude-plugin/marketplace.json` set to `v<version>`. On top of it sits the **main update**, which adds the CI-built `dashboard/dist/`. A human merges the PR, `release.yml` tags the merge commit and publishes the GitHub Release, and the release commit then lands on `develop`. Forge jobs never make that change: the maintainer makes it with `npm run release` at the end of a wave.

**Branches and installs.** `develop` is the working branch and the GitHub default branch: jobs and PRs branch from it and merge into it. Because it is the default, an install added with `claude plugin marketplace add maxwellmattryan/forge` reads `.claude-plugin/marketplace.json` from `develop`, and the forge plugin's `source.ref` there decides which commit it installs. develop's copy is the install switch, and it names the `v<version>` tag of the latest release. `forge update` runs `claude plugin marketplace update` and `claude plugin update`, so it follows that ref; it resolves no tags itself. `main` holds the released commits, each carrying the CI-built `dashboard/dist/`, and takes only release PRs and hotfix PRs. `dashboard/dist/` is gitignored and absent on `develop`, and nobody builds it by hand for a release: CI builds it, because an install never builds. Never merge `main` back into `develop`: it would bring `dist/` with it.

**Start a release: `npm run release -- patch|minor|major|X.Y.Z [--notes-file <file>] [--yes]`** on a clean `develop` that equals `origin/develop`, with `gh` signed in:

1. It fetches `develop`, `main`, the tags and the `release/*` branches. It refuses when the current version is untagged, when `v<next>` is already tagged, or when a release is in flight: a local or remote `release/vX.Y.Z` branch above develop's version, or `origin/main`'s version above develop's (a merged release not yet landed, or a hotfix not yet ported). The refusal names the version and says to run `npm run release` with no version to finish it, or to port the hotfix.
2. It drafts the `## <version>` section from the first-parent commits on `develop` since the last tag, release commits dropped, plus a `Versions:` line for any version that moved: the lists in `lib/core/versions/` and `lib/api/versions.ts`, and `ARCHIVE_SCHEMA_VERSION`. It opens the draft in `$VISUAL` or `$EDITOR`, or takes the notes from `--notes-file <file>`; lines starting with `<!--` are dropped. Rewrite the draft as notes: behaviour changes first, then fixes, the versions bumped, deprecations and removals.
3. It bumps the three version files, inserts the section into CHANGELOG.md and sets marketplace.json's ref to `v<version>`, checking every file before it writes any. It runs the release check (`--dist absent`) and commits the release commit on a new local branch `release/v<version>` cut from `develop`, then switches back. `develop` and `origin/develop` do not move.
4. It asks, then pushes the release commit to `origin release/v<version>`. That push runs `.github/workflows/main-update.yml`: one `build` job, with a read-only token, runs `npm ci` and `npm run build:dashboard` and uploads `dashboard/dist/` as the `dashboard-dist` artifact. It writes nothing to the repo.
5. It goes on as a resume does.

**Resume: `npm run release` with no version.** It finds the one release in flight and runs whichever steps are not done yet, so nothing runs twice.

- **Before the PR.** It waits for `main-update.yml`'s push run on the release commit, trusting a run only when it is that workflow file's own push or dispatch run in this repo, on the release branch, for that exact commit. It lists the hotfixes on `main` that the release lacks, and asks whether they were ported: the release undoes any that weren't. It downloads the artifact and builds the main update with `scripts/main-update.ts`. That checks the artifact holds only `index.html`, `manifest.json`, `build-stamp.json` and the `assets/*.js|css|woff2` files the manifest names, with no symlinks, and that its build stamp matches both the files and the release commit's dashboard sources. It refuses when the release commit tracks a `dashboard/dist/` path or the version is already tagged. The main update is the release commit's tree plus `dashboard/dist/`, with parents `[origin/main, release commit]`, subject `Release <version>`, authored by you. It asks, pushes it to `release/v<version>` as a fast-forward, opens the release PR (`Release <version>`, into `main`), prints its URL and the instruction, and exits.
- **PR open.** It prints the URL and the instruction, and exits. It refuses when the PR's head is not the branch tip.
- **PR closed without merging.** It refuses: reopen the PR, or delete `release/v<version>` (on origin and locally) and start over.
- **PR merged.** It waits for `release.yml`'s push run on the merge commit unless `v<version>` already exists on origin, and refuses unless the tag points at the merge commit. Then it lands the release commit on `develop`: a fast-forward when `origin/develop` is still its parent, nothing when `develop` already has it, and otherwise a `Release <version>` merge commit on a `develop` that equals `origin/develop` (on a conflict it aborts and says to merge it by hand). It asks, pushes `develop` and prints the Release URL. The repo deletes a PR's head branch on merge, so here it finds the release from `origin/main`'s version and the merged PR.

It refuses a release branch whose tip is neither a release commit nor a main update of one (a hotfix branch: finish it by hand, see Hotfixes below), an `origin/main` that moved past the main update's first parent (close the PR, delete the branch, port main's commits to `develop` and start again), and nothing in flight (name the next version). `--yes` answers every question; without a terminal it is required, and `--notes-file` replaces the editor. Whoever runs it pushes, and a human merges, not CI: a push or merge `GITHUB_TOKEN` makes starts no workflow run, and `GITHUB_TOKEN` can't push a commit that changes `.github/workflows/`. If GitHub refuses a push over a workflow file, your credential lacks the `workflow` scope: `gh auth refresh -s workflow`, then run it again.

**Merging the release PR.** Its body holds the CHANGELOG section, a compare link from `v<prev>` to the release branch, and the instruction. The PR's own diff is against `main`, so it equals `v<prev>..` only while `main` sits at the tag: after a hotfix it leaves out what the hotfix already changed, and the compare link shows everything since the tag. Wait for its CI, merge it in GitHub with **Create a merge commit** (not squash or rebase: the merge commit is what gets tagged), then run `npm run release`. The Release notes are the CHANGELOG section in the merged commit, frozen in the release commit and reviewed in the PR diff. The PR body is a copy for reviewers that no workflow reads, so editing it changes nothing and PR text never reaches the Release.

**`release.yml`** runs on the merge's push to `main`:
- **detect** reads the pushed commit. It is a release only when the version differs from the first parent's and no `v<version>` tag exists. Any other push stops here.
- **verify** runs all of `ci.yml` again on that commit, with a read-only token.
- **build**, read-only, writes the notes with `node scripts/release-plan.ts notes` and `forge-<version>.tar.gz` with `git archive`, refusing an archive whose `COMMIT` file does not hold the pushed sha, and uploads both as the `release-files` artifact.
- **release** holds `contents: write` and `actions: read` and runs nothing but `gh`. It downloads this run's `release-files`, finds the PR whose merge commit is the pushed sha (exactly one merged PR into `main` from this repo's `release/v<version>`, or it fails before anything is published) and adds `Release PR: <url>` to the notes. Then it creates the annotated tag `v<version>` (message `Forge <version>`) on the merge commit, and publishes the GitHub Release `Forge <version>` with the notes as its body and the archive as its one asset.

A push to `main` with a bumped version and no release PR publishes nothing.

**When the ref resolves.** develop's marketplace.json, the one installs read, names `v<version>` only once the release commit lands, after the tag exists, so installs never see an unresolved ref. `main`'s copy names `v<version>` from the merge until `release.yml` tags it, about the length of the `verify` run; nothing reads it unless the default branch becomes `main`. A git-clone install that updates with `git pull` (`forge update` in a clone) keeps following its branch, `main` or `develop`, not the tags.

**The release check.** CI's `release check` job runs `npm run release:check -- --dist present` on `main` and on every PR into it, and `--dist absent` on `develop`; `npm run release` runs `--dist absent` before it commits. It fails unless both versions are equal and `X.Y.Z`, CHANGELOG.md has an exact `## <version>` heading with notes and no AI attribution line, `.claude-plugin/marketplace.json` points the forge plugin at `v<version>`, the working tree is clean, and `dashboard/dist/` is tracked and matches its build stamp (`present`) or is not tracked at all (`absent`). With `present` it also fails when `v<version>` is already tagged at another commit, so a hotfix PR without a version bump fails.

**Hotfixes.** Branch `release/v<x.y.z+1>` from `main` and commit the fix, the version bump, its CHANGELOG section, marketplace.json's `ref: v<x.y.z+1>` and a rebuilt `dist/` (`npm ci`, `npm run build:dashboard`, then `git add --force dashboard/dist`). Open a PR into `main`, whose `release check` runs `--dist present`, and merge it with a merge commit: `release.yml` tags and publishes it as it does a release. Then port the fix, bump, section and ref to `develop` in a PR without `dist/`, merged after the tag exists. `npm run release` automates none of this: until the port, it refuses to start a new release, and a resume refuses the hotfix branch.

**Recovery.** If `npm run release` stops (a failed run, a refused push, a closed terminal), fix the cause and run `npm run release` with no version. If the dashboard artifact has expired (after 7 days), re-run the `Main update` workflow on `release/v<version>` from the Actions tab and run `npm run release` again. If `release.yml` fails before the tag step (the PR lookup included), use "Re-run failed jobs" on the same run: detect still sees the version change, and the tag does not exist yet. If only the publish step failed, the tag already exists, so a re-run stops at the tag step with "Reference already exists". Publish by hand from that run's `release-files` artifact instead: `gh run download <run id> --repo maxwellmattryan/forge --name release-files --dir release`, append `Release PR: <url>` to `release/notes.md` if it doesn't end with it, then `gh release create v<version> --verify-tag --title "Forge <version>" --notes-file release/notes.md release/forge-<version>.tar.gz`. If the artifact is gone, build both in a clone checked out at the tag: `node scripts/release-plan.ts notes > notes.md` and `git archive --format=tar.gz --prefix=forge-<version>/ -o forge-<version>.tar.gz v<version>`. If a bad tag or Release was published, delete both by hand (`gh release delete v<version> --cleanup-tag`) and ship the fix as the next patch version. Never move a published tag.

**Repository settings** a maintainer keeps:
- a ruleset on `main` that requires a pull request before merging and blocks force pushes and deletion, bypassed only in an emergency; optionally, one that lets only maintainers create `release/v*` branches;
- merge commits allowed on PRs into `main`, and head branches deleted on merge;
- `develop` as the default branch, since installs read its marketplace.json;
- Settings › Actions › General › Workflow permissions at "Read repository contents".

## Releasing a project

`forge release` releases the repos of a project that uses Forge, single- or multi-repo, from each repo's declared [release strategy](CONFIG.md#release-strategy). A human runs it from the CLI; the Foreman never does, though it may approve a job's plan when the project hands it the `release` gate class (Confirmation, below). (Forge's own release is [Releasing](#releasing) above.)

1. `forge release plan` picks the repos, orders them dependencies first and writes the plan to `.forge/runtime/release/`: `release.md` for you to read (steps, checks, rollback) and `release.json` for `run`. It runs nothing: no release command, no registry command, no `git fetch`.
2. `forge release run` runs the steps in order, checking each one, and records each step in `state.json` as it goes. It stops at the first failure. Run it again to resume at the first step not done; finished steps never run again.
3. `forge release status` shows each step's status, the tags and versions its checks recorded (what a rollback needs), the next step, `stale: true` when config or the repos have moved since planning, and `approval: {owner, status}`: who decides the publish steps (`human` or `foreman`) and whether the Foreman has approved this plan (`pending` or `approved`, with `actor` and `at`).

**Which repos.** With no flag, the root repo and every `repos` entry. `--job <id>` takes the job's PR repos (not its verify-only members) whose PR merged (`forge pr sync <id>` records it). An unmerged PR repo that is the consumer of an interim edge is listed under "Not released" with `PR not merged: it waits on its dependencies' release`; any other unmerged PR refuses the plan, and so does a job with no merged PR at all. `--since <tag>` takes the repos where the tag resolves and has commits after it, and refuses when no repo has the tag. A repo with no `release.mechanism`, or (without `--job`) a member whose clone fails doctor's `repo <name>` check, is listed under "Not released" with the reason. A config with problems, or a build cycle between the repos' components, refuses the plan; a cycle that only runtime edges close is ordered by build edges and noted.

**Consumers after a release.** On a `--job` plan, `forge release run` records the release of each dependency repo whose last step reaches done in that run: it logs `interim-released` on the job, as `forge job interim release` would (CONFIG.md "Interim strategies"), which resumes a job waiting on `pr-review` so verify bumps the consumers to it. The version comes only from the checks that run ran, never from `state.json`: a registry check's version, else a tag `<link name>@<version>`, else a tag that is a version itself (`v1.2.0`, `1.2.0`). Several versions at the first level that has any, or none at all, record nothing. The result lists `released: [{ repo, version, recorded, hint? }]`; when `version` is null, `hint` is the `forge job interim release <id> <repo>|--root <version>` command to run by hand. A whole-project or `--since` run records nothing on any job.

**Steps.** Every repo starts with `preflight`: the clone is on its base (`git.base` for the root, `defaultBranch` for a member), has nothing uncommitted, and after `git fetch` equals `<git.remote>/<base>`. Then, by mechanism (**publish** marks an outward-facing step):

| Mechanism | Steps after preflight |
|---|---|
| `tag` | `release`: `release.command`, through the POSIX shell as `forge run` runs commands (**publish**, checked by tag-pushed); then the registry step |
| `cargo-release` | `publish`: `cargo release publish --execute --no-confirm` (**publish**, registry, no check with `registry: none`); `tag`: `cargo release tag --execute --no-confirm` (tagged); `push`: `cargo release push --execute --no-confirm` (**publish**, tag-pushed) |
| `changesets` | `version`: `changeset version`; `stage`: `git add --all`; `commit`: `git commit --message "Version packages"` (clean); `publish`: `changeset publish` (**publish**, tagged); `push`: `git push --follow-tags <remote> HEAD:refs/heads/<base>` (**publish**, tag-pushed) |
| `release-please` | `merge`: you merge the open release PR on GitHub (**publish**, manual, remote-tagged); `sync`: `git merge --ff-only <remote>/<base>` (at-remote); then the registry step |

The registry step, for `tag` and `release-please`: `npm publish` with `registry: npm`, `cargo publish` with `registry: crates.io`, none otherwise. Programs are found on PATH (relative PATH entries are skipped), `changeset` and `release-please` in the clone's `node_modules/.bin` first, and run without a shell in the clone; output goes to your terminal and to `.forge/runtime/release/logs/`. There is no timeout, and stdin is yours, so npm's one-time-password prompt works.

**Checks.** A step with a check is done only when its check passes after the command exits 0: clean (nothing uncommitted), tagged (HEAD carries a tag), tag-pushed (tagged, and the remote has the base at HEAD and every tag at HEAD), remote-tagged (after a fetch, `<remote>/<base>` carries a tag), at-remote (HEAD equals `<remote>/<base>`), registry (`npm view <name>@<version> version`, or `cargo search <name>`, finds the version in the root `package.json` or `Cargo.toml`). A workspace root or a private package has no registry check, and `release.md` says to check by hand. On a resume, and before every step, the check runs first: when it already passes, the step is marked done without running, so a step that published but crashed before its checkpoint never publishes twice. CI that already released (cadence `on-merge` or `scheduled`) is skipped the same way.

**Confirmation.** Each publish step asks `Run it? [y/N]` on the terminal, unless that repo sets `release.publish: allow`. Without a terminal on stdin and stderr, the run stops with `needs_confirmation`, so an agent session stops there too; with `allow`, it does not. The release-please merge always needs a terminal: it prints the instruction and asks `Done? [y/N]`. There is no flag or environment variable that skips the question.

**The Foreman's approval.** A project can hand the decision to the Foreman by moving the `release` gate class: add `release` to `foreman.decides` and remove `gate:release` from `foreman.reserved` (CONFIG.md "Foreman"; the defaults keep it with a human). Then `forge release plan --job <id>` logs a `release-planned` event with the full plan hash and queues one `release` gate request for the office session, once per job and hash; its output's `approval` says who owns the decision. The Foreman's assistant reads `release.md` and the release strategy, and the office records `forge job human <id> approve-release --actor foreman --note "<reason>"`, which re-plans and refuses unless the plan is unchanged, is the job's latest, has a queued request and isn't approved yet, and nothing reserved shows in the job or the note. Without a terminal, `forge release run` then passes each publish step without asking and reports `approvedBy: "foreman"`, but only while that approval is for the plan it just recomputed and the Foreman still decides `release` with nothing reserved; a re-plan with a different hash, or taking the class back, leaves the approval unused. On a terminal it still asks at every publish step, the release-please merge still needs a terminal, and the run itself is still started by a human or CI, never a daemon session. A person approves a release by answering the prompt, not with `approve-release`. The question guards against an accidental publish, for example an agent session that runs `forge release run` by mistake; it is not a security boundary, since a process that fakes a terminal can answer it, and such a process could run the publish command itself anyway.

**Safety.** `forge release run` and `forge release plan --force` are refused in a daemon session, and `run` on native Windows (use WSL2, [SUPPORT.md](SUPPORT.md)). `run` recomputes the plan from config and the clones and refuses when it differs from `release.json` or `state.json`; commands always come from that recomputation, never from the file. One run at a time: `.forge/locks/release/` holds it (exit 3 while another run is alive). `plan` refuses to replace an unfinished run of a different plan unless `--force`, which discards its checkpoints.

**Rollback** is written in `release.md`, last released first, and Forge never runs it. A pushed tag can be deleted (`git push <remote> --delete refs/tags/<tag>`, plus its GitHub Release); a pushed version commit is reverted. Registries limit what can be undone: npm allows `npm unpublish` only within 72 hours and when no other public package depends on the version (otherwise `npm deprecate`), and crates.io never deletes a version, only `cargo yank`s it so new lockfiles skip it.

## Provenance and pinning

Every commit on `main` is the merge of a release PR or a hotfix PR, so its `dashboard/dist/` was built by CI (the `Main update` build of the release branch) and checked against the release commit's sources, or built by the hotfix's author and checked by `release check`. Every `v<version>` tag is an annotated tag that `release.yml` made on such a merge commit, after `verify`.

`forge version --json` prints `{"version","commit","installedAs","node"}`. `commit` comes from the first source that has one: the `COMMIT` file a release archive carries (`git archive` stamps it through `.gitattributes` `export-subst`), Claude Code's own install record for a plugin install, then `git rev-parse HEAD` for a clone. Settings › About shows the same commit and install kind. The output is self-reported, so anything that can edit the install can make it claim any commit. The audit anchors are the annotated tag and comparing the archive with `git archive` of the tag.

**Verify an archive.** Download `forge-<version>.tar.gz` from the Release. Extracted, its `COMMIT` file is the tagged commit, and `forge version --json` run from it reports that commit with `installedAs: "unknown"`. To check it is that commit's tree, compare it with the tag in a clone: `git rev-parse v<version>^{commit}` must print the sha in `COMMIT`, and `gunzip -c forge-<version>.tar.gz | sha256sum` must equal `git archive --format=tar --prefix=forge-<version>/ v<version> | sha256sum` (a different git version can lay out the tar differently: then extract both and `diff -r`). Releases have no `.sha256` asset any more: the same job published it in the same Release as the archive, so it proved nothing HTTPS doesn't, and anyone who could replace one could replace both.

**Pin a version.** Either:

- clone the tag, `git clone --branch v<x.y.z> https://github.com/maxwellmattryan/forge.git`, or
- extract the release archive,

and then load that directory with `claude --plugin-dir <dir>`, or add it as a local marketplace with `claude plugin marketplace add <dir>`. A pinned clone sits on a detached tag, which `forge update` refuses to move.

A marketplace install added from GitHub (`claude plugin marketplace add maxwellmattryan/forge`) follows the latest release: the `v<version>` tag that develop's `.claude-plugin/marketplace.json` names, which `forge update` moves to the next release once it lands. It cannot pin an older version: `claude plugin marketplace add` (Claude Code 2.1.299) takes a URL, a path or a GitHub repo, with no ref. A git clone follows its branch, not the tags, unless it is checked out at a tag.

**Roll back.** In a pinned clone, `git fetch --tags` and `git checkout v<older>`; with an archive, extract the older one. Then start a new Claude Code session (and restart `forge dash`). Jobs and configs written by a newer Forge may not load in an older one; `forge doctor` flags jobs from a newer Forge.

## Release checklist

1. Every job of the wave is merged into `develop`, each after a green CI run on its PR.
2. On a clean `develop`, run `npm run release -- patch` (or `minor`, `major`, `X.Y.Z`). Rewrite the drafted notes: behaviour changes first, the versions bumped (`API_VERSION`, schemas), deprecations and removals.
3. Answer its questions: push the release branch, whether the listed hotfixes were ported, push the main update. It waits for the dashboard build, opens the release PR and prints its URL. `origin/develop` does not move.
4. Check the release PR: `release/vX.Y.Z` into `main`, its body (the notes and the compare link), its diff (the bump, the CHANGELOG section, `ref: vX.Y.Z` and `dashboard/dist/`) and its CI. Merge it with **Create a merge commit**.
5. Run `npm run release` again. It waits for `release.yml` (`detect`, `verify` and `build` read-only, then `release`: download, find the PR, tag, publish), lands the release commit on `develop` after asking, and prints the Release URL.
6. Check the Release page: tag `vX.Y.Z` on the merge commit, the CHANGELOG body ending with the release PR's link, and `forge-X.Y.Z.tar.gz` as its only asset.
7. Run `forge update` on a plugin install and confirm `forge version --json` reports `X.Y.Z` and `forge doctor` shows no "behind the latest release" warning.
