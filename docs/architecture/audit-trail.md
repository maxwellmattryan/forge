# Audit trail

Every human action records a best-effort `actor: { login, source }` on its event, so `events.jsonl` says who, not only which session. These events carry it, and only these: `human` (every `forge job human` action); `linked`, `unlinked` and `issue-link` (`forge job link`, and `--link` on `forge job human`); `budget-set` and `budget-ack`; `release-approval` (`{ planHash, note }`, always the foreman's, from `forge job human … approve-release --actor foreman`); `claimed` and `dependencies-overridden` of a `forge job claim --force`; every `pr-merged`, with or without `--now` (plus `scope`, the `FORGE_DAEMON_SCOPE`, when a daemon session ran the merge, and `via: sync` when `forge sync` continued it); `pr-merge-bypass` and the `pr-auto-merge` or `pr-merge-failed` of the same `forge pr merge --now`; `daemon-permission` and `daemon-mode` when the dashboard answers a job session's permission prompt or switches its mode (the daemon log lines `permission` and `permission-mode-set` carry the actor too, for every scope); `archived` (`{ trigger }`, the last event of an archived job's record; see ["Retention"](retention.md)); and `config-set` (`{ key, previous, value, changed: true }`) in the repo-level `.forge/runtime/audit.jsonl` when `forge config set` or `POST /api/config` changes a value. Agent-driven events, a plain claim, the queue, failure and refusal of a merge without `--now` (`pr-auto-merge`, `pr-merge-failed`, `pr-merge-refused`) and the daemon's automatic permission deny carry none. A `pr-merged` written before the `merge-provenance` event step has no actor when it ran without `--now`, and reads as unrecorded.

**Resolution** (`lib/integrations/github/actor.ts`) runs at most once per process, lazily, only on a path that writes one of those events, so a CLI call that writes none never spawns `gh` or `git`:

1. inside a daemon session (`FORGE_DAEMON=1`): the OS user running `forge dash`, source `daemon`, because the action is the session's own, run under that user; `FORGE_ACTOR` is ignored there. Events written before source `daemon` existed say `dashboard` and read as before
2. `FORGE_ACTOR`: source `env`
3. `gh api user --jq .login` (5 s timeout): source `gh`, cached in `.forge/runtime/actor.json` for 24 h per gh host (`GH_HOST`, else `github.com`); a failure is not cached
4. `git config user.email`: source `git`
5. the OS user name: source `os`
6. else `{ login: null, source: "unknown" }`

The dashboard's own routes (`/api/config`, `/api/daemon/permission`, `/api/daemon/mode`, `/api/jobs/:id/merge`) record the OS user running `forge dash`, source `dashboard`. A `forge pr merge --now` confirmed at a terminal records the person's resolved actor (sources 2–6 above); the dashboard's Merge now records `dashboard` ([Daemon security](daemon-security.md) › Human-only operations). Every login is sanitised when it is resolved and again whenever it is read back, from the cache or an event: only `[A-Za-z0-9 ._@+-]`, single spaces, at most 100 characters; one that ends up empty falls through to the next source. Only a `gh` or `env` login is published: the PR body and the tracker comment name it inside a code span, so it can never mention anyone or carry markdown. A `dashboard`, `daemon`, `os` or `git` login is a local account name or a raw email address, so those surfaces print only the source (`Approved by a person (dashboard) on <date>`), as they do for `unknown`; the login stays in `events.jsonl` and the audit export. The escalation reason goes in a code span too, because the agent that wrote it read untrusted text.

**The actor is not authenticated.** Like request provenance below, it is whatever the environment says. Source `daemon` means the action ran inside a daemon session, not that a person asked for it: an agent in a daemon job session that runs `forge job human` is stamped so. Source `dashboard` means a dashboard route ran it (older events also stamped daemon sessions `dashboard`). Neither counts as the foreman's. A `pr-merged` a daemon session wrote (the job's own merge at step PR4, or the inbox session's `forge sync` continuing a deferred one) is Forge merging under the approver's recorded decision, not a person's action: its `scope` (the session's `FORGE_DAEMON_SCOPE`, with `via: sync` when `forge sync` continued it) says which session ran it. Beyond that, anyone who can set `FORGE_ACTOR`, log `gh` in as someone else or write `events.jsonl` can name anyone. It is a record for auditors, never a grant of authority: no check in Forge passes or fails on a login. The one distinction Forge enforces is foreman versus person, and that rests on the office's daemon scope, not on the actor.

**Export.** `forge job audit <id> [--json|--csv]` prints a job's rows in time order: every event with an actor, every gate transition (`gate:<waitingOn>` into a wait, `gate-cleared:<waitingOn>` out of one), `pr-opened` and `pr-merged` / `pr-auto-merge`, with the job's PR number and merge method. `forge audit --since <date> [--until <date>] [--csv]` merges every job's rows with the repo-level log for a period (docs/CLI.md "Audit trail"). The CSV guards against spreadsheet formula injection. A human-approved escalation is also named in the PR body (a `## Decision` section) and, once, in a tracker comment when `forge sync` first sees the merge.
