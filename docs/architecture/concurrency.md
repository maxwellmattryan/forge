# Concurrency

- **Many jobs, one session**: the orchestrator runs agents in the background and advances each job as notifications arrive, up to `runtime.maxParallelJobs`.
- **Many sessions, one repo**: all state is in the main checkout's `.forge/`. Writes take a per-job `mkdir` lock and are atomic (write and rename). Backlog edits and tracker claims take their own locks. Job ids are created with an exclusive `mkdir`.
- **Locks prove death** (`withLock`, `withLockAsync` and `tryLock` in lib/core/os/lock.ts). Acquiring is `mkdir <lockDir>`; the holder then writes `<lockDir>/holder.json` = `{ v: 1, pid, startedAt, host, token }` (its process's start time and a token unique to the acquisition). A lock's age never counts: a waiter breaks a parseable holder's lock only when the holder is on this host and provably gone, its pid dead or, from `ps -o lstart=` (at most once a second per token), started more than 30 s from `startedAt`, so the pid was reused. Another host, a live pid with a matching start, or a `ps` that fails all count as alive, and a long section keeps its lock with no refresh. A dir with no parseable `holder.json` (an older Forge's lock, one caught between its mkdir and its write, or a planted file) falls under the one age rule: it may be broken once its mtime is over 60 s old. Breaking is one breaker at a time: `mkdir <lockDir>/breaking` (anyone else waits), re-read `holder.json` and back off unless its token is still the one judged dead, then rename the dir to a `<lockDir>.dead-<random>` grave and remove that. A breaker that dies mid-break leaves the marker, which wedges the lock (waiters time out with `timed out waiting for lock <dir> (held by pid <pid>)`) but never admits a second holder. Release removes the dir only while `holder.json` still carries the holder's own token. `tryLock` makes one attempt, with the death-proof break applied once.
- **One `forge dash` per machine**: the machine dashboard is one server (lib/server/start.ts) with one token, one port and one runtime record (`<FORGE_HOME>/dashboard.json`). It loads a project entry (lib/server/machine.ts) for every project in the machine index whose directory exists, each with its own context, caches and pool, booted when its config would have booted a per-repo dash (not `--dev`, `daemon.enabled: true`, no `daemonProblems`) and a human's approval of its trusted files still matches them (`<FORGE_HOME>/trust/<rootLabel>`, written by Start with the snapshot its pool runs under, and by `forge dash` run in the repo when it starts the dashboard or registers the repo; docs/architecture/daemon-security.md). It re-reads `projects.json` at most every 2 s and only when its size, mtime or inode changed, and also on `GET /api/projects`, after `POST /api/projects` (the dashboard's Add project) and on a request naming an unloaded project: a new registration loads, a removed one (or a name now pointing elsewhere) closes, its pool stopped and its streams ended, and an unreadable index keeps the loaded set and reports the error. `forge dash` in another repo registers it and reports the running server instead of starting a second one.
- **One pool per project**: each project's pool takes `tryLock(<locks>/daemon)` at start and holds it until it stops, closes or the process exits; a second dash started at the same moment loses the mkdir and reports `another forge dash (pid N) owns the daemon`. A dash that dies leaves a lock naming a dead pid, which the next start breaks. The older record check (`otherOwner`) still runs after the lock, so a dash from an older Forge, which takes no lock, is still seen.
- **Worktrees** live outside the repo (`../<repo>.worktrees/<job>` by default), so watchers, bundlers and Cargo workspaces don't see nested copies. Untracked files agents need, such as a gitignored `CLAUDE.md`, are copied in, and setup commands run once. Credentials are not copied: they reach a command through `secrets` and a config sink.
- **Rust**: with `worktrees.cargo.sharedTarget`, one `.cargo/config.toml` above all worktrees points every job at a single target dir. Dependencies compile once, and disk use doesn't multiply. Cargo serialises concurrent builds on that directory's lock, which is usually still far faster than cold builds per worktree.
- **Ports**: each active job gets one unique port per service or app component (`job.ports`, `dev` when there are none) from `ports.base`, under the same locks as backing ports (`withPortsLock`: the machine's `<FORGE_HOME>/locks/ports`, then the project's `.forge/locks/ports`, always in that order); `job.port` is the first one. Job and backing ports skip every port another registered project's active jobs and backing records hold, so two projects with one `ports.base` never collide. Commands see them as `{endpoint.<component>}`, `FORGE_PORT_<C>` and `FORGE_ENDPOINT_<C>`, the component's own as `{port}`, `$PORT` and `$FORGE_PORT`, and backing ports as `{backing.<name>.port}` (lib/engine/environment/ports.ts, lib/engine/environment/endpoints.ts; docs/CONFIG.md "Ports and endpoints").
- **One headless session per job**: with `daemon.enabled`, `forge dash` supervises the intake runner (an inbox session only for a request type it doesn't handle) plus up to `daemon.maxConcurrent` (default 3) job sessions per project, each driving one job, and the machine cap bounds them across projects ([Daemon](daemon.md)). A job's lease still keeps a human's session and its daemon session from driving the same job; it passes between daemon sessions without `--force` because the inbox releases it when it hands a job off, and the supervisor expires a session's lease when its child exits (see "Ownership" in [Job model](job-model.md)). `runtime.maxParallelJobs` limits a human's interactive session, not the pool.
- **Background commands** are idempotent per job and command: `forge run <id> dev --background` returns the recorded process while it is alive (`reused: true`) instead of starting another on the same port, and reports `listening` once the port answers. A per-job lock covers the check and spawn, so parallel UI reviewers share one dev server; the orchestrator starts it before them and runs `forge stop` after.
