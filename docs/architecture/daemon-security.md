# Daemon security

The daemon runs an unattended agent under `daemon.allowedTools`, asking a human in the dashboard about anything else (or, with `--permission-mode dontAsk`, refusing it, or, in a session a human switched to `auto`, letting Claude Code's classifier decide), so its inputs are narrow on purpose:
- **One fixed stdin turn.** Every session gets only `TURN_LINE` (`/forge requests`) as a message. The only other stdin lines answer claude's own `can_use_tool` permission requests ("Permission prompts" below), carrying nothing from HTTP but the decision, or ask claude to switch permission mode ("Permission mode" below), carrying one value from a fixed list. A fourth, an error reply to a control request forge does not handle, repeats only the first 40 characters of claude's own subtype back to claude. All of them are built in `lib/integrations/claude/stream.ts`, which exposes no write that takes free text: the supervisor can only ask for the turn, pick a decision for a request claude itself sent, or name a mode. Request text, request and job ids, config values and HTTP bodies never reach stdin; the session reads requests through `forge requests`, where the skill treats them as the human's words about one job, never as rules. Free text from the dashboard's command bar (`POST /api/jobs`) is written only to the new job's `request.md` (and, through the derived title, `job.json` and `events.jsonl`); the `resume` queued for it carries no text.
- **The scope travels in the environment only, validated.** A session learns its scope from `FORGE_DAEMON_SCOPE`, set by the supervisor from a routed request whose job id matched `^[A-Za-z0-9][A-Za-z0-9._-]*$` (at most 200 characters) and has a `job.json`; anything else routes to `_inbox`, which can't be a job id. Under `FORGE_DAEMON=1`, `forge requests list|claim|ack|scope|add` refuse a missing or invalid scope, list only that scope's requests, refuse to claim or ack a request that doesn't exist or belongs to another scope, and queue only `resume` hand-offs. These keep a session that follows the skill in its lane; they are not authentication (see ["Untrusted input"](untrusted-input.md)). Request ids are checked against their `<time>-<id>` format before any path is built from them. Runtime file paths are built only from validated scopes.
- **argv comes from the repo's config, with no shell.** `daemon.command` is split into words and run directly, and placeholders expand to single arguments. Nothing from HTTP or requests reaches argv. A session id read back from a session record or a child's `system`/`init` must be a uuid before it can follow `--resume`, so a planted value can't become a flag.
- **Trust boundary: `.forge/config.yml` is code.** Whoever can change it can run code through the daemon, exactly as through `commands.*` (which verify runs through a shell): validation refuses the claude flags that widen permissions (`--dangerously-skip-permissions`, `--permission-mode bypassPermissions`, `--settings`, `--mcp-config`, `--add-dir`, `--agents`, a second `--plugin-dir`, a literal `--allowedTools`; docs/CONFIG.md "Daemon" has the full list), but the session still runs `commands.*` through `forge run`/`forge verify`, and `daemon.enabled: true` in committed config starts an unattended, paid session on every machine that runs `forge dash`. The config is read from the main checkout only, never from a job worktree or a PR branch, but a merged change applies everywhere. Give `daemon.command`, `daemon.allowedTools` and `daemon.enabled` code-owner review, like CI config. The session itself can't use this route (next bullet). The validator's rule that the first word is a bare `claude` or an absolute path to `claude` outside the repo catches mistakes (a migrated shell template, a relative path that would run a repo file); it is not a security boundary. Configured commands run without the `FORGE_DAEMON*` markers: the trust check guards the session's own `forge` calls, and a command's nested `forge` call against a scratch repo (a test suite) must not be judged by it. A command can run any code anyway, so that check never bound it. The git pins below still apply to commands.
- **Configured commands get an allowlisted environment and no login shell, in every mode.** The session can't change `commands.*`, but it can `Edit` a test and run `forge verify`, which executes that code before any reviewer reads it, with whatever environment Forge passes. So every spawn site of a configured command (`forge run`, verify steps, worktree setup, `forge run --background`, config-sink commands, job database builds, checkout steps, `forge integrate`'s rebuild, the eval check and `notify.command`) builds its environment with `commandEnv` and its argv with `commandShell` (`lib/engine/guard/command-env.ts`), and neither reads `FORGE_DAEMON`. `commandEnv` passes only an allowlist (fixed names such as `PATH`, `HOME`, `LANG` and the git pins; the `LC_*`, `NODE_*` but `NODE_OPTIONS`, `FORGE_*` and `GIT_CONFIG_KEY_<n>`/`VALUE_<n>` families, never a credential-like name; and what `commandEnv.inherit` names, where a glob never passes a credential-like name either), so a credential under a name nobody listed (`CORP_SESSION_BLOB`) is dropped too. It never passes the daemon markers, an outer job's `FORGE_PORT_*`/`FORGE_ENDPOINT_*`/`FORGE_BACKING_*`, `FORGE_COMMAND_PATH*` or the source variable of a declared `env` secret, whatever `inherit` says; names fold on Windows. `commandShell` runs `/bin/sh -c`, so no login profile, `.zshenv`, `BASH_ENV` or `ENV` puts back what the allowlist dropped, unless `commandEnv.loginShell: true` asks for `$SHELL -lc`. Both keys sit in `.forge/config.yml`, which is a protected path, in the deny tail and in the trust digest, and are read-only in Settings. PATH is the one `forge dash` captured from the login shell at start (`FORGE_COMMAND_PATH`, held only in the dashboard process's environment and its children's, never in a file), else Forge's own, with relative and empty entries removed so the worktree can't plant a binary on it. The job's own variables, sink env and link env are added afterwards and never filtered. A command's child sees no marker, so a nested `forge` behaves as a human's. What this does not stop: code that reads the human's files (`~/.aws/credentials`, `~/.npmrc`, `~/.config/gh/hosts.yml`, a shell profile) or starts its own login shell, and a name a human put in `inherit` exactly. `forge release run` keeps its caller's environment and `$SHELL -lc` (refused under the daemon; its publish steps need registry credentials), and Forge's own tool calls (git, gh, docker, the secret tools) keep the Forge process's.
- **The session can't change what Forge executes, what every agent reads, or anything outside its write roots.** Its cwd is the main checkout, so an agent misled by tracker or PR text could otherwise rewrite `commands.*` (which `forge run`/`forge verify` run through a shell), `daemon.*` (picked up at the next spawn or resume), the files every later agent reads with no review (`.forge/notes/`, `.forge/reviewers/`, `.forge/evals/`, `CLAUDE.md`, the instruction files), the job state the CLI trusts (`job.json`, `events.jsonl`), or files outside the repo, such as `~/.ssh/config`, whose `ProxyCommand` runs on the next push. The **protected set** is `PROTECTED` in `lib/core/config/trust.ts`: `.forge/config.yml`, `.forge/secrets-allow.txt`, `.forge/trackers/`, `.forge/verifiers/`, `.forge/notes/`, `.forge/reviewers/`, `.forge/evals/` (minus `runs/` and `recall/runs/`, which `forge` writes), `.forge/ci/`, the root's `CLAUDE.md`, `CLAUDE.local.md` and `AGENTS.md`, plus every configured `project.instructions` file. A session's **write roots** are the main checkout's `.forge/jobs/` and every worktrees root (the root's and each member repo's that is set up in `.forge/local.yml`). Five layers, each independent of the others:
  - *The CLI checks at the sink (the trust digest).* When a human starts the daemon (dashboard Start, or `forge dash` with `enabled: true`), the supervisor takes `trustDigest`: a sha256 of the checkout's realpath and every file of the protected set (an unreadable or absent one hashes as a marker; symlinks hash as links). It hands the digest to the session as `FORGE_DAEMON_TRUST`. Under `FORGE_DAEMON=1`, every `forge` command recomputes it before reading config and refuses on a mismatch, or when the variable is missing. The check catches every route, including Bash (`git mv -f`, a redirect) and a fake checkout reached through `cd`. `forge init write`, `forge migrate` and `forge config set` refuse outright, because they write config.yml through `forge` itself. config.yml is read once, and the bytes that were hashed are the bytes parsed (the instruction list too). A custom tracker module is checked again just before it is imported. Any symlink under `.forge/trackers/` is refused (its target could change without the link changing), and the walk never follows one. A `git pull` that brings in a merged retro also changes the digest and stops the daemon until a human starts it again; that cost is intended. What the digest can't see: files a tracker module imports from outside `.forge/trackers/`, so keep tracker modules self-contained.
  - *The supervisor stops the session (the poll and the post-turn check).* Every poll, and before any spawn, it compares the trust digest with the one taken at start. The same start also takes a **confine digest** (`confineDigest` in `lib/office/session/confine.ts`): `git status` over the protected set, every `CLAUDE.md` and `CLAUDE.local.md` at any depth, and an in-checkout `core.hooksPath` directory, plus the content of each file that status lists, so a nested `lib/CLAUDE.md` or a file that was already dirty and changes again still counts. After every turn ends, and before every spawn, the session recomputes it. On either change the whole pool stops with an error in the dashboard; respawns after an idle stop or a failed resume reuse the old snapshots, so a change made during a turn (or by a background agent between turns) is never blessed by a restart. A spawn hashes config.yml once and builds argv from those same bytes, so a file swapped and restored between two reads can't slip in. Only a human's Start takes new snapshots, and only when no child is running. A human editing a protected file while the daemon runs gets the same stop, which is the price of not being able to tell the two apart.
  - *Claude Code scopes the file tools.* At spawn, `buildArgv` drops every `Edit`, `Write`, `MultiEdit` and `NotebookEdit` entry of `daemon.allowedTools` (bare or scoped) and, when there was one, appends one `Edit(//<realpath>/**)` rule per write root, so a write anywhere else (`~/.ssh/config`, a shell rc file, the main checkout outside `.forge/jobs/`) becomes a dashboard prompt. One `Edit(…)` rule governs every file-writing tool. Validation refuses a `daemon.allowedTools` entry that scopes a file tool itself (`Edit(//**)`, `Write(~/**)`) or names an MCP tool (`mcp__…`). A write root equal to or containing the checkout (`worktrees.root: ..`), one inside `.forge/` or on (or around) a protected path or instruction file (`worktrees.root: .forge/runtime`, which would let the guard allow the CLI copy), or one a rule can't carry (`, ( ) * ? [ ] { }`, a newline, or a backslash off Windows), refuses the spawn with a pool fatal.
  - *Claude Code refuses the write (the deny tail).* `--disallowedTools` follows every `daemon.command`, whatever the template says: `DENY_TOOLS` in `lib/integrations/claude/argv.ts` (the protected set's `.forge/` entries, `.forge/local.yml`, `.forge/runtime/**`, `.forge/locks/**`, `.forge/archive/**`, and in job folders `job.json`, `events.jsonl`, `.lock/**` and any `CLAUDE.md` or `CLAUDE.local.md`), then `denyRules` from `lib/office/session/confine.ts`: each entry's absolute `//<realpath>/…` twin, the root's `CLAUDE.md`, `CLAUDE.local.md` and `AGENTS.md`, every configured instruction file, `**/CLAUDE.md` and `**/CLAUDE.local.md` unless a worktrees root lies inside the checkout, and a `core.hooksPath` directory inside the checkout. Root-level names appear only in absolute form, so they stay anchored at the root. Relative paths anchor at the session's cwd (the main checkout, so job worktrees, where a self-improvement job legitimately edits Forge config, are unaffected), deny beats allow in every mode, and subagents inherit the rules. `.claude/` and `.mcp.json` are already Claude Code protected paths, which are never allowed without a human: `dontAsk` refuses them, and `default` asks.
  - *The write guard refuses it.* `hooks/write-guard.ts` runs as a `PreToolUse` hook on `Edit|Write|MultiEdit|NotebookEdit`. Without `FORGE_DAEMON=1` it allows everything, so a human's own sessions are unchanged. Under it, it resolves the target's realpath and allows only paths inside a job folder (`.forge/jobs/<id>/…`) or a worktrees root, read from `FORGE_DAEMON_WRITE_ROOTS`, which the spawn sets. Inside a job folder it still refuses `job.json`, `events.jsonl`, `.lock` and anything under it, and any `CLAUDE.md` or `CLAUDE.local.md` at any depth, ignoring case. It refuses a path with a `..` segment, a path that starts with `~` (Claude Code expands it to a home directory, so it would otherwise resolve to a directory called `~` under the cwd), any `.git` segment inside a job folder or a worktree, ignoring case (so a worktree's `.git` file can't be pointed at a gitdir with a filter driver), a dangling symlink and anything it can't resolve, and fails closed on malformed input or env. It imports nothing from `lib/`, so a broken module can't change its verdict, and it doesn't depend on Claude Code's rule syntax, so it holds even if a rule form fails.

  **The CLI owns job state (#448).** `forge job new` writes a job's `job.json` and `events.jsonl` to a **CLI copy** under `.forge/runtime/job-records/<id>/` as well as the job folder, every later store write updates the copy first, and `loadJob`, `listJobs`, `readEvents` and repo spend read the copy (`stateFile` in `lib/core/paths.ts`). So a `pr.pushedSha`, a raised `budget`, a lowered `usage`, a cleared `protectedPaths` or an appended APPROVE line written into the job folder is ignored, and the next CLI write rewrites the folder's `job.json` from the copy. `.forge/runtime/` is out of reach of every file tool (the deny tail and the guard); the session's own `forge` calls write it, which is the CLI writing state. A MAC over event lines was rejected: the session runs `forge`, which must sign its own events, and it can `Read` any key the CLI can.

  The anchor is the session's environment, which it can't change: Bash allow rules don't match a command with a leading `VAR=…` assignment (except a few known-safe variables), and `env`/`export` aren't allowed. This keeps the *repo's* trusted commands in force; it does not stop those commands from running code the job wrote, which every verify does by design (that code is reviewed after verify, not before).

  **Residual risk.** Jobs created before the CLI copy have none and keep reading their job folder until they finish. Programs that write files themselves (`forge`, `git`, a configured command) can still change paths outside the digest's and the post-turn check's pathspecs. `Read`, `Glob` and `Grep` stay unscoped, so a session can read anything the user can.
- **Start and stop** need the dashboard token, a matching Origin and JSON, and a pool `start` additionally needs `daemon.enabled: true` and no `daemon.*` validation problem. A scoped start only re-enables one session inside a pool a human already started, so it never takes a trust snapshot. The config migration never sets `enabled`. Concurrent start/stop POSTs never leave more than one child per session: a start while a child exists or is stopping spawns nothing new.
- **SSE is loopback-only and per session**, rejects a foreign Origin and any request whose `Sec-Fetch-Site` is not `same-origin`/`none` (the same `readGuard` the history route uses), syntax-checks `session` (400 otherwise), sends a stream only its own session's lines, sends no CORS headers, allows 8 streams at once across all sessions (`503` beyond), ends any client more than 1 MiB behind, and recycles every stream after 5 minutes (EventSource reconnects with `Last-Event-ID`). The dashboard opens only the stream of the session on screen. Another site can never read a stream. In a browser that sends neither Origin nor Fetch Metadata on a no-cors GET, a cross-site page can still occupy slots until they are recycled; that costs the live log's availability, never the daemon.
- **History reads are confined.** `GET /api/daemons/log` validates the scope before building a path, requires the daemons dir to be the real `.forge/runtime/daemons` (not a symlink to elsewhere), resolves `<scope>.log` with realpath and serves it only from inside that dir, and reads it through one descriptor opened `O_NONBLOCK` and `fstat`-checked as a regular file. Session records (`<scope>.json`) are read through one `O_NOFOLLOW|O_NONBLOCK` descriptor and must be regular files under 64 KiB, or they count as absent. Logs are opened for appending with `O_NOFOLLOW|O_NONBLOCK` and must be regular files (a session whose log can't be opened keeps running without one), and `forge daemon log` opens them the same way for reading. So a symlink or FIFO planted in the runtime dir is never followed and can't hang the server, on read (the history route, `/api/events`) or on write (session logs, reap notes).
- **Permission prompts are answered from the dashboard only.** Every daemon command ends with `--permission-prompt-tool stdio`, so claude sends each call it would ask a person about to the supervisor as a `control_request`. The supervisor holds it in memory (never in a file the session could edit), shows it in `/api/state`, and answers when a human posts `POST /api/daemon/permission` with the token, a matching Origin and JSON. The body names a scope, the supervisor's uuid for the prompt and a decision (`allow`, `session` or `deny`); the reply is built from claude's own request: an allow echoes its input unchanged, a deny carries fixed text, and "allow for this session" grants only the allow rules and absolute directories claude suggested, rewritten to the `session` destination, so suggestions to save rules to a settings file or change the permission mode are dropped. There is no CLI command to answer a prompt, because the session itself runs `forge`. Prompts end with their child, at most 20 wait per session, a request whose `request_id` is already waiting is ignored (a repeated id must not swap the input an allow runs), and any other control request subtype gets an error so claude never hangs. What a prompt shows (the input, the agent's description, the blocked path) is session output and renders as text. A prompt is exactly as safe as the human reading it: the tool, its full input and any blocked path are shown, and the agent's description is labelled as its own words.
- **Permission mode is a human's choice, held in memory.** `POST /api/daemon/mode` (token, matching Origin, JSON) names a scope (validated, and a job must have a `job.json`) and one of `default`, `auto` or `dontAsk` (lib/integrations/claude/argv.ts `PERMISSION_MODES`); anything else is a 400. The pool keeps the choice in memory only: session records live in `.forge/runtime/`, which the session can write, so a mode read back from disk would be one the session could choose for itself. A running child gets a `set_permission_mode` control request; a later spawn gets `--permission-mode <mode>` in place of the template's. Until claude reports its mode (at its first turn's init) the supervisor takes the one the child was launched with. A switch claude refuses or doesn't confirm fails closed: a narrowing one stops the child, so the next spawn starts in the chosen mode, and a widening one leaves the choice at what the child still reports. `auto` stays refused in `daemon.command`, so a repo's config can't put every session on every machine that runs `forge dash` into it: only a human at the dashboard can, for one session, until that `forge dash` stops. In `auto`, Claude Code's classifier approves calls outside `allowedTools` without a human, so a misled agent's call may run unread; the deny rules, the trust check and the git pins below still hold. `bypassPermissions` is never offered, and claude refuses it on a session not launched with `--dangerously-skip-permissions`, which validation forbids. The same POST with scope `_jobs` sets the default for every job session without its own choice, also in memory only; the inbox and office never take it. `forge dash --permission-mode` sets that default at start-up: the human's own command line, refused when `FORGE_DAEMON=1`, so a session can't start a second dashboard with it. There is no CLI command to switch a running dashboard's modes, for the same reason there is none to answer a prompt. **Auto on one session reaches the whole daemon.** The dashboard serves its token to any local client and a non-browser client can send any Origin, so a session whose calls run without a human (Auto, or one a human allowed `curl` to) can read the token and post to `/api/daemon/mode` or `/api/daemon/permission`: switch other sessions to Auto, make Auto the job sessions' default (`_jobs`, which also reaches jobs created later), or answer their prompts and its own. A session that only runs what `allowedTools` lists can't: no `forge` command posts to these routes, and `forge dash --permission-mode` refuses a daemon session. Nothing on loopback tells the page apart from a session's process, so treat putting any session in Auto as trusting every session's input.
- **Effort is a human's per-job setting, read back from `job.json`.** The level reaches argv only as one word from the fixed list (`EFFORTS` in `lib/core/job/schema.ts`), and never stdin. `normalizeJob` reads anything else in `job.json` as null and `buildArgv` ignores a value outside the list, so a hand- or session-written `"--dangerously-skip-permissions"` or `"high --add-dir /"` never becomes an option. An invalid `runtime.effort` is a `daemonProblems` refusal, so no session starts. `withEffort` drops every `--effort` and `--effort=` in `daemon.command`, so a duplicate can't win over Forge's. `forge job set --field effort=…` is refused, and `forge job effort` and `forge job new --effort` refuse under `FORGE_DAEMON=1`, so a misled session can't raise its own or another job's level through the CLI. `POST /api/jobs/:id/effort` takes the token, a matching Origin and JSON, an existing job id and a value from the list or null. Residual risk: in a job that predates the CLI copy, a session can still write a valid level into its own `job.json`, as it can `budget.limits` (the deny tail and the write guard refuse the file tools; a newer job's folder copy is ignored). That costs tokens and time, bounded by `pipeline.budget` and visible in the session log's `effort` event and the card chip, and it never widens what the session may do. `complexity` is session-writable through `forge job set --field`, but only as `low`, `medium`, `high` or null, and it only selects among levels a human configured in `runtime.effortByComplexity`, which never reaches a session's argv. That is why, unlike the permission mode, effort is read back from disk: it is a human's setting that must survive a `forge dash` restart.
- **Narrow permissions, still not a sandbox.** Anything `allowedTools` doesn't list is asked about (or refused under `dontAsk`), and subagents inherit the list. The default allows Bash only for `forge` and specific git/gh subcommands (rev-parse, merge/rebase `--abort`; `gh pr view|list|checks`, `gh run view`). The session's cwd is the main checkout and `cd` and `git -C` aren't allowed, so a bare `git add`/`git commit` would act on the base branch: agents stage and commit through `forge git add|commit <job>`, which runs git with the job's worktree as cwd (refusing the main checkout, a branch other than the job's, and a merge or rebase in progress for `commit`), takes only `--message`/`--message-file` (a file inside the job dir) and paths, so no `-c`, `-C`, `--git-dir`, `--amend`, `--no-verify` or `--author`, refuses paths outside the worktree or in a `.git`, checks the message for AI attribution, clears `GIT_DIR`-style variables, and under `FORGE_DAEMON=1` runs git with the session pins below (outside the daemon, a human's hooks run). Claude Code matches each part of a compound command against the rules and won't match past `git -c` or an env assignment, so `git -c core.sshCommand=…`, `git -c alias.x='!…'` and `FOO=… git …` are refused. `git diff|log|show|range-diff` are left out because `--output=<file>` writes wherever git can, and Claude Code's protected-path check covers its own file tools, not git: `git log --format=… --output=.git/config` would plant a textconv or filter driver that the next diff or add runs. Agents read history through `forge git`, which refuses `--output` (git accepts no abbreviation of it), `--ext-diff`, `--textconv` and `--open-files-in-pager`, and forces `--no-ext-diff --no-textconv`. `git rebase` is left out because `--exec` runs shell: the integrator starts merges and rebases with `forge integrate --keep-conflicts` and finishes them with `forge integrate --continue`, which refuses a rebase todo holding anything but picks. `git mv` is left out too: given a `x/../.git/config` destination it reports an invalid path, then renames the file anyway and exits 0. `gh api` and other GitHub writes are left out; Forge's own writes (push, PR, labels, comments) go through `forge`. Validation refuses `allowedTools` entries that undo this (unscoped `Bash`, bare `git`/`gh`, `git -…`, `git config|grep|submodule|bisect|…`, `git diff|log|show|range-diff|…`, `git mv`, `git rebase`, `gh api|extension|alias|auth|…`); the list catches known forms and is not exhaustive.
- **Git hooks are off in the session and in the periodic sync.** A repo can point `core.hooksPath` at a tracked directory (`.githooks/`, unlike `.git/` and `.husky/`, isn't one of Claude Code's protected paths), so a hook written there would run on the next `git commit`, on a `forge pr open` push, or on the `reference-transaction` of a fetch. An in-checkout hooks directory is in the deny tail and the confine digest, and a worktree's is reviewed with the job's diff. The daemon also spawns the session with `core.hooksPath=/dev/null` and `core.fsmonitor=false` in `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n`, which outrank every config file and are inherited by subagents, `forge` and verify commands. `forge dash`'s periodic `forge sync` child runs with `SYNC_PINS` (`lib/integrations/git/runner.ts`): the same two, plus `core.pager=cat`, `diff.external=/dev/null` and `gpg.program=gpg` (git's own default, so a user's signed merges keep working), appended after any `GIT_CONFIG_*` the caller exports; `credential.helper` is never pinned. The cost: no hooks at all in daemon mode, including Git LFS's pre-push upload. Not pinned in the session: filter, diff and merge drivers and `gpg.program`, which only `.git/config` or `~/.gitconfig` can define. The session has no allowed way to write `.git/` (Claude Code's file tools treat it as protected, so only a human's answer to a prompt could allow it, the write guard refuses any `.git` segment inside a worktree, including a worktree's `.git` file, and the git forms it may run take no output path), but anything the human or another tool puts there still applies. What remains broad is what the session writes inside its write roots: worktree files that build and test tooling executes, which verify runs and the review panel reads. Enable the daemon only on repos whose tracker input you trust (or with intake restricted, e.g. `tracker.github.comments: collaborators` and ready labels only maintainers set).
- **Keeping a slot and marking agents lost read `job.json`, which the session writes through `forge`** (and, in a job that predates the CLI copy, could write directly). A session that records agents it never ends can pin its own slot, never another job's, for at most 2 h per agent start (the `AGENT_LEASE_MS` ceiling; a `startedAt` or `endedAt` more than 60 s in the future is ignored, so a forged time can't stretch the ceiling or the idle window, and the idle timer never re-arms for longer than its window), and a human's session or pool Stop ends it sooner, the same bound as a turn that never returns a `result`. Lost-marking writes on behalf of a session that no longer exists, so it touches only agents of a job whose `lease.driver` is that session's id, never another driver's. The job id it reads is the validated scope, so no path is built from session output, and nothing new reaches the child's stdin, argv or environment.
- **Orphan reaping** proves each record (every `daemons/<scope>.json`) separately before signalling its pid (see ["Daemon runtime"](daemon-runtime.md)), so a stale or planted record can't make Forge kill an unrelated process.
- **The dashboard record is proven, not trusted.** `.forge/runtime/dashboard.json` is writable by any session that can write the runtime dir, so `provenDashboard` (`lib/engine/ops/dashboard-record.ts`) accepts it only when all of these hold: (1) it is a regular file (never a symlink or FIFO, read without blocking) of at most 4 KiB holding a JSON object; (2) `pid` is an integer > 1, not the reading process, and alive; (3) `ps` reports a start time within 30 s of `startedAt`, so a reused pid fails; (4) the process's command line has `forge` in the script position followed by `dash`: the script position is the first word (basename `forge`, or this install's `bin/forge`), or the word right after a node executable (basename `node`/`node.exe`, or Node's own path). The rule exists because start times are public, so a forged `startedAt` alone could name any process, and a `forge`…`dash` pair anywhere in the line would name an unrelated one such as `claude /forge dash`. A launch with node options before the script, or with whitespace in any other path, fails closed; Forge never launches the dashboard that way; (5) `url` is an `http:` URL on `127.0.0.1`, `localhost` or `[::1]` with an explicit port and no userinfo, path, query or hash, compared on the parsed hostname. What the proof does not bind: the url is not tied to the pid. A writer that copies the live dashboard's `pid` and `startedAt` and changes only the url to another loopback port (one it serves itself) has a proven record, so `forge dash`, `forge daemon status` and `forge update` show that url. So the worst a forged record can do is name the running `forge dash` and point at any loopback port. Binding the url to the process (an HTTP handshake) is out of scope. Anything else is stale: its pid is never signalled and its url never printed. `forge dash` (`--stop`, the running answer, the `--dev` refusal), `forge daemon status` and `forge update` read it only through this check; `forge dash --background` accepts its own child's record when the pid is that child's and the url passes rule 5; notifications use only rule 5, because they build a link and signal nothing. On native Windows no record is proven, since there is no start-time probe. Stopping the write itself is a separate layer: the daemon's deny rules over `.forge/runtime/**` (#382).
- **The logs** (`daemons/<scope>.log`) live in gitignored `.forge/runtime/`; they hold whatever the sessions printed, so treat them like transcripts. The dashboard renders every log string as text, and `forge daemon log` escapes control characters so session output can't drive the terminal.
