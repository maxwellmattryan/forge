# Daemon security

The daemon runs an unattended agent under `daemon.allowedTools`, asking a human in the dashboard about anything else (or, with `--permission-mode dontAsk`, refusing it, or, in a session a human switched to `auto`, letting Claude Code's classifier decide), so its inputs are narrow on purpose:
- **One fixed stdin turn.** Every session gets only `TURN_LINE` (`/forge requests`) as a message. The only other stdin lines answer claude's own `can_use_tool` permission requests ("Permission prompts" below), carrying nothing from HTTP but the decision, or ask claude to switch permission mode ("Permission mode" below), carrying one value from a fixed list. A fourth, an error reply to a control request forge does not handle, repeats only the first 40 characters of claude's own subtype back to claude. All of them are built in `lib/integrations/claude/stream.ts`, which exposes two writes that take free text. The first is a role run's or a gate run's brief (`writeBrief`, built by `briefLine`), sent once as the child's first message: by `runRoleChild` from `forge job step`'s brief (its `Instructions:` line swapped for the fixed `PREFIX_INSTRUCTIONS_LINE` when the run has a trusted prefix), or by the gate runner (lib/office/foreman/attempt.ts) from the assist brief the CLI built, and never by a pool session ("Role runs" below). A gate run's child may also be sent the one fixed verdict retry (`VERDICT_RETRY_LINE`). The second: in a chat session (scope `_chat-<id>`), the owner's own message goes to stdin as one stream-json user line (`writeMessage`, built by `chatMessageLine` with `JSON.stringify`, so newlines and an embedded control line stay inside the one text). Only `Session.writeChat` calls it, only in a chat scope, and only from the pool's `sendChat` (lib/office/chat/send.ts), which `POST /api/p/<project>/chats/<id>/messages` reaches ("Chats" below). For every other scope the supervisor can only ask for the turn, pick a decision for a request claude itself sent, or name a mode. Request text, request and job ids, config values and HTTP bodies never reach stdin; the session reads requests through `forge requests`, where the skill treats them as the human's words about one job, never as rules. Free text from the dashboard's command bar (`POST /api/jobs`) is written only to the new job's `request.md` (and, through the derived title, `job.json` and `events.jsonl`); the `resume` queued for it carries no text.
- **The scope travels in the environment only, validated.** A session learns its scope from `FORGE_DAEMON_SCOPE`, set by the supervisor from a routed request whose job id matched `^[A-Za-z0-9][A-Za-z0-9._-]*$` (at most 200 characters) and has a `job.json`; anything else routes to `_inbox`, which can't be a job id. Under `FORGE_DAEMON=1`, `forge requests list|claim|ack|scope|add` refuse a missing or invalid scope, list only that scope's requests, refuse to claim or ack a request that doesn't exist or belongs to another scope, and queue only `resume` hand-offs. These keep a session that follows the skill in its lane; they are not authentication (see ["Untrusted input"](untrusted-input.md)). Request ids are checked against their `<time>-<id>` format before any path is built from them. Runtime file paths are built only from validated scopes.
- **argv comes from the repo's config, with no shell.** `daemon.command` is split into words and run directly, and placeholders expand to single arguments. Nothing from HTTP or requests reaches argv. A chat session's spawn alone also gets `--append-system-prompt` with the fixed `CHAT_PROMPT` (lib/office/session/launch.ts), before the deny tail. A session id read back from a session record or a child's `system`/`init` must be a uuid before it can follow `--resume`, so a planted value can't become a flag.
- **Trust boundary: `.forge/config.yml` is code.** Whoever can change it can run code through the daemon, exactly as through `commands.*` (which verify runs through a shell): validation refuses the claude flags that widen permissions (`--dangerously-skip-permissions`, `--permission-mode bypassPermissions`, `--settings`, `--mcp-config`, `--add-dir`, `--agents`, a second `--plugin-dir`, a literal `--allowedTools`; docs/CONFIG.md "Daemon" has the full list), but the session still runs `commands.*` through `forge run`/`forge verify`, and `daemon.enabled: true` in committed config starts an unattended, paid session on every machine that runs `forge dash`. The config is read from the main checkout only, never from a job worktree or a PR branch, but a merged change applies everywhere. Give `daemon.command`, `daemon.allowedTools` and `daemon.enabled` code-owner review, like CI config. The session itself can't use this route (next bullet). The validator's rule that the first word is a bare `claude` or an absolute path to `claude` outside the repo catches mistakes (a migrated shell template, a relative path that would run a repo file); it is not a security boundary. Configured commands run without the `FORGE_DAEMON*` markers: the trust check guards the session's own `forge` calls, and a command's nested `forge` call against a scratch repo (a test suite) must not be judged by it. A command can run any code anyway, so that check never bound it. The git pins below still apply to commands. So the marker proves less than it seems: it keeps a session in its lane, but a process without it is not thereby a person. Branch code that a session's `forge verify` runs has no marker, which is why the human-only operations below take their go-ahead from a channel, not from the marker's absence.
- **Configured commands get an allowlisted environment and no login shell, in every mode.** The session can't change `commands.*`, but it can `Edit` a test and run `forge verify`, which executes that code before any reviewer reads it, with whatever environment Forge passes. So every spawn site of a configured command (`forge run`, verify steps, worktree setup, `forge run --background`, config-sink commands, job database builds, checkout steps, `forge integrate`'s rebuild, the eval check and `notify.command`) builds its environment with `commandEnv` and its argv with `commandShell` (`lib/engine/guard/command-env.ts`), and neither reads `FORGE_DAEMON`. `commandEnv` passes only an allowlist (fixed names such as `PATH`, `HOME`, `LANG` and the git pins; the `LC_*`, `NODE_*` but `NODE_OPTIONS`, `FORGE_*` and `GIT_CONFIG_KEY_<n>`/`VALUE_<n>` families, never a credential-like name; and what `commandEnv.inherit` names, where a glob never passes a credential-like name either), so a credential under a name nobody listed (`CORP_SESSION_BLOB`) is dropped too. It never passes the daemon markers, an outer job's `FORGE_PORT_*`/`FORGE_ENDPOINT_*`/`FORGE_BACKING_*`, `FORGE_COMMAND_PATH*` or the source variable of a declared `env` secret, whatever `inherit` says; names fold on Windows. `commandShell` runs `/bin/sh -c`, so no login profile, `.zshenv`, `BASH_ENV` or `ENV` puts back what the allowlist dropped, unless `commandEnv.loginShell: true` asks for `$SHELL -lc`. Both keys sit in `.forge/config.yml`, which is a protected path, in the deny tail and in the trust digest, and are read-only in Settings. PATH is the one `forge dash` captured from the login shell at start (`FORGE_COMMAND_PATH`, held only in the dashboard process's environment and its children's, never in a file), else Forge's own, with relative and empty entries removed so the worktree can't plant a binary on it. The job's own variables, sink env and link env are added afterwards and never filtered. A command's child sees no marker, so a nested `forge` behaves as a human's. What this does not stop: code that reads the human's files (`~/.aws/credentials`, `~/.npmrc`, `~/.config/gh/hosts.yml`, a shell profile) or starts its own login shell, and a name a human put in `inherit` exactly. `forge release run` keeps its caller's environment and `$SHELL -lc` (refused under the daemon; its publish steps need registry credentials), and Forge's own tool calls (git, gh, docker, the secret tools) keep the Forge process's.
- **The session can't change what Forge executes, what every agent reads, or anything outside its write roots.** Its cwd is the main checkout, so an agent misled by tracker or PR text could otherwise rewrite `commands.*` (which `forge run`/`forge verify` run through a shell), `daemon.*` (picked up at the next spawn or resume), the files every later agent reads with no review (`.forge/notes/`, `.forge/reviewers/`, `.forge/evals/`, `CLAUDE.md`, the instruction files), the job state the CLI trusts (`job.json`, `events.jsonl`), or files outside the repo, such as `~/.ssh/config`, whose `ProxyCommand` runs on the next push. The **protected set** is `PROTECTED` in `lib/core/config/trust.ts`: `.forge/config.yml`, `.forge/secrets-allow.txt`, `.forge/trackers/`, `.forge/verifiers/`, `.forge/notes/`, `.forge/reviewers/`, `.forge/evals/` (minus `runs/` and `recall/runs/`, which `forge` writes), `.forge/ci/`, the root's `CLAUDE.md`, `CLAUDE.local.md` and `AGENTS.md`, plus every configured `project.instructions` file. A session's **write roots** are the main checkout's `.forge/jobs/` and every worktrees root (the root's and each member repo's that is set up in `.forge/local.yml`). Five layers, each independent of the others:
  - *The CLI checks at the sink (the trust digest).* When a human starts the daemon (dashboard Start, or `forge dash` with `enabled: true`), the supervisor takes `trustDigest`: a sha256 of the checkout's realpath and every file of the protected set (an unreadable or absent one hashes as a marker; symlinks hash as links). It hands the digest to the session as `FORGE_DAEMON_TRUST`. Under `FORGE_DAEMON=1`, every `forge` command recomputes it before reading config and refuses on a mismatch, or when the variable is missing. The check catches every route, including Bash (`git mv -f`, a redirect) and a fake checkout reached through `cd`. `forge init write`, `forge migrate` and `forge config set` refuse outright, because they write config.yml through `forge` itself. config.yml is read once, and the bytes that were hashed are the bytes parsed (the instruction list too). A custom tracker module is checked again just before it is imported. Any symlink under `.forge/trackers/` is refused (its target could change without the link changing), and the walk never follows one. A `git pull` that brings in a merged retro also changes the digest and stops the daemon until a human starts it again; that cost is intended. What the digest can't see: files a tracker module imports from outside `.forge/trackers/`, so keep tracker modules self-contained.
  - *The supervisor stops the session (the poll and the post-turn check).* Every poll, and before any spawn, it compares the trust digest with the one taken at start. The same start also takes a **confine digest** (`confineDigest` in `lib/office/session/confine.ts`): `git status` over the protected set, every `CLAUDE.md` and `CLAUDE.local.md` at any depth, and an in-checkout `core.hooksPath` directory, plus the content of each file that status lists, so a nested `lib/CLAUDE.md` or a file that was already dirty and changes again still counts. After every turn ends, and before every spawn, the session recomputes it. On either change the whole pool stops with an error in the dashboard; respawns after an idle stop or a failed resume reuse the old snapshots, so a change made during a turn (or by a background agent between turns) is never blessed by a restart. A spawn hashes config.yml once and builds argv from those same bytes, so a file swapped and restored between two reads can't slip in. Only a human's Start takes new snapshots, and only when no child is running. A human editing a protected file while the daemon runs gets the same stop, which is the price of not being able to tell the two apart.
  - *Claude Code scopes the file tools.* At spawn, `buildArgv` drops every `Edit`, `Write`, `MultiEdit` and `NotebookEdit` entry of `daemon.allowedTools` (bare or scoped) and, when there was one, appends one `Edit(//<realpath>/**)` rule per write root, so a write anywhere else (`~/.ssh/config`, a shell rc file, the main checkout outside `.forge/jobs/`) becomes a dashboard prompt. One `Edit(…)` rule governs every file-writing tool. Validation refuses a `daemon.allowedTools` entry that scopes a file tool itself (`Edit(//**)`, `Write(~/**)`) or names an MCP tool (`mcp__…`). A write root equal to or containing the checkout (`worktrees.root: ..`), one inside `.forge/` or on (or around) a protected path or instruction file (`worktrees.root: .forge/runtime`, which would let the guard allow the CLI copy), or one a rule can't carry (`, ( ) * ? [ ] { }`, a newline, or a backslash off Windows), refuses the spawn with a pool fatal.
  - *Claude Code refuses the write (the deny tail).* `--disallowedTools` follows every `daemon.command`, whatever the template says: `DENY_TOOLS` in `lib/integrations/claude/argv.ts` (the protected set's `.forge/` entries, `.forge/local.yml`, `.forge/runtime/**`, `.forge/locks/**`, `.forge/archive/**`, and in job folders `job.json`, `events.jsonl`, `.lock/**` and any `CLAUDE.md` or `CLAUDE.local.md`), then `denyRules` from `lib/office/session/confine.ts`: each entry's absolute `//<realpath>/…` twin, the root's `CLAUDE.md`, `CLAUDE.local.md` and `AGENTS.md`, every configured instruction file, `**/CLAUDE.md` and `**/CLAUDE.local.md` unless a worktrees root lies inside the checkout, and a `core.hooksPath` directory inside the checkout. Root-level names appear only in absolute form, so they stay anchored at the root. Relative paths anchor at the session's cwd (the main checkout, so job worktrees, where a self-improvement job legitimately edits Forge config, are unaffected), deny beats allow in every mode, and subagents inherit the rules. `.claude/` and `.mcp.json` are already Claude Code protected paths, which are never allowed without a human: `dontAsk` refuses them, and `default` asks.
  - *The write guard refuses it.* `hooks/write-guard.ts` runs as a `PreToolUse` hook on `Edit|Write|MultiEdit|NotebookEdit`. Without `FORGE_DAEMON=1` it allows everything, so a human's own sessions are unchanged. Under it, it resolves the target's realpath and allows only paths inside a job folder (`.forge/jobs/<id>/…`) or a worktrees root, read from `FORGE_DAEMON_WRITE_ROOTS`, which the spawn sets. Inside a job folder it still refuses `job.json`, `events.jsonl`, `.lock` and anything under it, and any `CLAUDE.md` or `CLAUDE.local.md` at any depth, ignoring case. It refuses a path with a `..` segment, a path that starts with `~` (Claude Code expands it to a home directory, so it would otherwise resolve to a directory called `~` under the cwd), any `.git` segment inside a job folder or a worktree, ignoring case (so a worktree's `.git` file can't be pointed at a gitdir with a filter driver), a dangling symlink and anything it can't resolve, and fails closed on malformed input or env. It imports nothing from `lib/`, so a broken module can't change its verdict, and it doesn't depend on Claude Code's rule syntax, so it holds even if a rule form fails.

  **The CLI owns job state (#448).** `forge job new` writes a job's `job.json` and `events.jsonl` to a **CLI copy** under `.forge/runtime/job-records/<id>/` as well as the job folder, every later store write updates the copy first, and `loadJob`, `listJobs`, `readEvents` and repo spend read the copy (`stateFile` in `lib/core/paths.ts`). So a `pr.pushedSha`, a raised `budget`, a lowered `usage`, a cleared `protectedPaths` or an appended APPROVE line written into the job folder is ignored, and the next CLI write rewrites the folder's `job.json` from the copy. `.forge/runtime/` is out of reach of every file tool (the deny tail and the guard); the session's own `forge` calls write it, which is the CLI writing state. A MAC over event lines was rejected: the session runs `forge`, which must sign its own events, and it can `Read` any key the CLI can.

  The anchor is the session's environment, which it can't change: Bash allow rules don't match a command with a leading `VAR=…` assignment (except a few known-safe variables), and `env`/`export` aren't allowed. This keeps the *repo's* trusted commands in force; it does not stop those commands from running code the job wrote, which every verify does by design (that code is reviewed after verify, not before).

  **Residual risk.** Jobs created before the CLI copy have none and keep reading their job folder until they finish. Programs that write files themselves (`forge`, `git`, a configured command) can still change paths outside the digest's and the post-turn check's pathspecs. `Read`, `Glob` and `Grep` stay unscoped, so a session can read anything the user can.
- **Human-only operations.** `forge pr merge <id> --now` (skips merge.auto, the recorded approval, protected paths, the escalate floor and CI), `forge job budget <id> --set|--ack` (raises or acknowledges a job's spend limits), `forge budget ack --period P` (lifts the repo spend cap), `forge job unshelve <id>` (takes a shelved job off the shelf, so it can spend again) and `forge job set <id> --state …` on a job cancelled or set done while shelved (puts it back to work; a terminal only, no dashboard control) need a person's go-ahead from one of two channels a session's children can't reach. *A terminal*: `confirmHuman` (`lib/cli/commands/human.ts`) refuses under `FORGE_DAEMON=1`, refuses (code `human_only`) unless both stdin and stderr are TTYs, then prints what the operation skips or changes and asks the person to type the job id (the period for `budget ack`); any other answer refuses with `not confirmed; nothing changed`. A configured command's stdin is never a TTY, so a nested call or a piped answer (`echo <id> | forge …`) is refused without reading it. A TTY alone is not enough: branch code that a `forge verify` (or a `/forge` session) in the person's own terminal runs can open that terminal's `/dev/tty` and hand it to `forge`, but the prompt then appears on the person's screen and waits for the id to be typed. Sessions under `forge dash` are spawned detached, in a new session with no controlling terminal, so their children can't open `/dev/tty` at all. No flag, env var or config key skips the prompt, because branch code can set any of them. A Ctrl-D, a Ctrl-C or a stdin that closes at the prompt refuses like a wrong answer. *The dashboard*, per operation: for `pr merge --now`, Merge now posts `POST /api/jobs/:id/merge`, which takes the login, a matching Origin, JSON and the id typed back; for `budget ack`, the Acknowledge in Needs you posts `POST /api/budget/ack`, which takes the login, a matching Origin and JSON ([Dashboard security](dashboard-security.md)); for `job budget --set|--ack`, Approve & continue on the budget gate posts `POST /api/jobs/:id/budget`, which takes the login, a matching Origin and a JSON body of at most five `key=value` entries; for `job unshelve`, Un-shelve (and the Approve and Rework that un-shelve first; Close cancels the job without un-shelving it) in the Shelved list posts `POST /api/shelf`, which takes the login, a matching Origin and JSON, and pins each job to the shelving the list showed. Only a person takes a job off the shelf whatever writes: `setJob` refuses (`human_only`) any write that moves a shelved job's stage, state or `waitingOn` unless it un-shelves, finishes or cancels it, and refuses any write but `shelveJob`'s that puts a job on the shelf (`forge job shelve`, refused in every daemon session, or the gate runner's Foreman shelve under `foreman.escalations: foreman`, which needs its in-process authority). A cancel (or a done) is no way around that: the write that finishes a shelved job marks it `finishedWhileShelved` (a locked field), and `setJob` refuses (`human_only`) any write that moves a marked job out of done or cancelled without a person's grant, so a session that cancels a shelved job can't then queue it; `forge job set` asks the person at the terminal to type the job id first, logs the grant's actor on the transition and clears the mark. The engine checks the grant at runtime too (`isHumanGrant`: `mergePr`'s `now`, `budgetCmd`'s `grant`, `unshelveJob`'s `grant`, `setJob`'s `grant`), so an in-process caller can't skip the channel by accident; that is no defence against code in the same process. The events record the person's resolved actor from a terminal, `dashboard` from the dashboard. The terminal check stops agents and configured commands that call `forge` directly or pipe in an answer; any same-user process can defeat it. Residuals, which only sandboxing configured commands would close: branch code that starts its own pseudo-terminal (`script`) and types the id; branch code run from the person's own terminal (a `forge verify` there) that pushes the id into that terminal's input with `ioctl(TIOCSTI)` while the prompt waits, which macOS allows, as does Linux with `dev.tty.legacy_tiocsti` on; branch code that reads the dashboard's login file or the terminal that printed the login link and posts with a forged Origin (the login defends against browsers and other OS users, not same-user processes); branch code that runs `gh` with the person's login or rewrites state files directly. The other `FORGE_DAEMON`-keyed refusals (`job effort`, `job new --effort|--force`, `release plan --force`, `release run`, `eval --set`, `doctor --bundle`, `update`, `focus`, `dash` modes, `job interim publish|release`, `job repo add|remove`) keep a session in its lane; they are not authorization.
- **Start and stop** need the dashboard token, a matching Origin and JSON, and a pool `start` additionally needs `daemon.enabled: true` and no `daemon.*` validation problem. A scoped start only re-enables one session inside a pool a human already started, so it never takes a trust snapshot. The config migration never sets `enabled`. Concurrent start/stop POSTs never leave more than one child per session: a start while a child exists or is stopping spawns nothing new.
- **SSE is loopback-only and per session**, rejects a foreign Origin and any request whose `Sec-Fetch-Site` is not `same-origin`/`none` (the same `readGuard` the history route uses), syntax-checks `session` (400 otherwise), sends a stream only its own session's lines, sends no CORS headers, allows 8 streams at once across all sessions (`503` beyond), ends any client more than 1 MiB behind, and recycles every stream after 5 minutes (EventSource reconnects with `Last-Event-ID`). The dashboard opens only the stream of the session on screen. Another site can never read a stream. In a browser that sends neither Origin nor Fetch Metadata on a no-cors GET, a cross-site page can still occupy slots until they are recycled; that costs the live log's availability, never the daemon.
- **History reads are confined.** `GET /api/daemons/log` validates the scope before building a path, requires the daemons dir to be the real `.forge/runtime/daemons` (not a symlink to elsewhere), resolves `<scope>.log` with realpath and serves it only from inside that dir, and reads it through one descriptor opened `O_NONBLOCK` and `fstat`-checked as a regular file. Session records (`<scope>.json`) are read through one `O_NOFOLLOW|O_NONBLOCK` descriptor and must be regular files under 64 KiB, or they count as absent. Logs are opened for appending with `O_NOFOLLOW|O_NONBLOCK` and must be regular files (a session whose log can't be opened keeps running without one), and `forge daemon log` opens them the same way for reading. So a symlink or FIFO planted in the runtime dir is never followed and can't hang the server, on read (the history route, `/api/events`) or on write (session logs, reap notes, and the repo-level audit log: `.forge/runtime` must be a real directory, and a planted link or FIFO at `audit.jsonl` makes that one append fail, never redirects it or blocks the server).
- **Permission prompts are answered from the dashboard only.** Every daemon command ends with `--permission-prompt-tool stdio`, so claude sends each call it would ask a person about to the supervisor as a `control_request`. The supervisor holds it in memory (never in a file the session could edit), shows it in `/api/state`, and answers when a human posts `POST /api/daemon/permission` with the token, a matching Origin and JSON. The body names a scope, the supervisor's uuid for the prompt and a decision (`allow`, `session` or `deny`); the reply is built from claude's own request: an allow echoes its input unchanged, a deny carries fixed text, and "allow for this session" grants only the allow rules and absolute directories claude suggested, rewritten to the `session` destination, so suggestions to save rules to a settings file or change the permission mode are dropped. There is no CLI command to answer a prompt, because the session itself runs `forge`. Prompts end with their child, at most 20 wait per session, a request whose `request_id` is already waiting is ignored (a repeated id must not swap the input an allow runs), and any other control request subtype gets an error so claude never hangs. What a prompt shows (the input, the agent's description, the blocked path) is session output and renders as text. A prompt is exactly as safe as the human reading it: the tool, its full input and any blocked path are shown, and the agent's description is labelled as its own words. With `daemon.permissionTimeoutMinutes` set, a prompt nobody answers within it gets a fixed timeout deny (`TIMEOUT_DENIED`, which says no human saw the call and asks the agent to reply `NEEDS-PERMISSION` if it can't finish without it): the timer (`lib/office/session/control.ts`), read from the config when the prompt is asked, only ever denies, never allows, and only a prompt still pending from the session's current child; a human's answer, claude's cancel, the child's exit or the session's close clears it first, so a prompt is answered at most once. The session log records `permission … reason: timeout` with no actor, the denied prompt joins the session's in-memory timed-out history (the last 10, shown in the dashboard as text with no buttons), and a job session's job gets a `permission-timed-out` event carrying only the tool name, `unknown` when it fails `SAFE_TOOL`, never the input or description. When a planner, spec writer, builder or integrator replies `NEEDS-PERMISSION` with such an event inside its run, `forge job step` (NP1b) parks the job on `escalation`, a gate that stops work and grants nothing; the Foreman may decide that park like any escalation, but it never answers a prompt: no route or capability lets anything but `POST /api/daemon/permission` with the token answer one.
- **Role runs are confined as a job session's subagents are, without a person to ask.** `forge job agent run` ([Daemon runtime](daemon-runtime.md) › Role runs) starts one role as its own `claude -p --agent forge:<role>` child whose cwd is the job's worktree, not the main checkout, and which runs unattended with Bash and file tools. Its attackers are the role agent itself, steered by tracker or PR text in its inputs, a stale or foreign caller of the command, and the agent-writable `job.json` fields `worktree` and `agentId`. *Writes to the main checkout's trusted files from a worktree cwd*: the relative `DENY_TOOLS` would anchor at the worktree (denying the branch's own `.forge/notes/**` and `**/CLAUDE.md` while leaving the checkout's open), so the child's `--disallowedTools` holds only the absolute rules (`absoluteDenyRules`: every `DENY_TOOLS` entry anchored at the checkout's realpath and the path as given, the root's `CLAUDE.md`, `CLAUDE.local.md` and `AGENTS.md`, and every instruction file), and `roleArgv` throws on any rule without `//`. *The branch's own Claude Code config loaded as trusted*: a worktree is a branch's checkout of files agents write, and `claude -p` skips the workspace-trust prompt, so a child started there would load the worktree's `CLAUDE.md` and `CLAUDE.local.md` as instructions every later role reads, the hooks (shell, outside the write guard), `permissions.allow` (wider than `daemon.allowedTools`), `env` and `apiKeyHelper` of its `.claude/settings*.json`, its `.claude/skills` and `commands`, and its `.mcp.json`; `roleArgv` passes `--setting-sources user` and `--strict-mcp-config`, so only the user's own settings and the `--plugin-dir` plugin load, as for a subagent at the main checkout, and a role reads the repo's instruction files from the main checkout because its brief says to. *Agent-written text in the system prompt*: the child's `--append-system-prompt-file` is the trusted prefix (lib/engine/guard/prompt-prefix.ts), whose sources are fixed: the main checkout's `project.instructions` files for the role, `.forge/notes/learnings.md` and `.forge/notes/<role>.md`, never a brief, job file, checklist or PR text. A source that is a symlink (say `.forge/notes/learnings.md` linked to a job's `request.md`), a directory or FIFO (read with `O_NONBLOCK`, so it can't hang the runner), larger than 256 KiB, or reached through a linked parent directory is refused, as is an instruction entry under `.forge/` or under a write root (a job folder, a worktrees root nested in the checkout), and a prefix over 256 KiB. Every source is under the trust digest, so under `FORGE_DAEMON=1` the start refuses a digest that moved, and a source edited during the run fails it `untrusted`. The file lives in `.forge/runtime/prompt-prefix/`, outside every write root and under the runtime deny rule, named by the sha256 of its bytes; it is reused only when a regular file there holds exactly those bytes, and otherwise replaced atomically, so a planted file or link at the name is replaced, never followed. `roleArgv` takes only an absolute path with no NUL, CR or LF there. Any refusal starts the run as before, with no flag, the brief unchanged and `prefixRefused` in the JSON: the agent then reads the same files as data-labelled paths, which is today's baseline. Residual: a Bash route into `.forge/runtime/` outside `daemon.allowedTools`, which prompts and is denied unattended, as for every runtime file. Node has no `openat` (as `confinedDir` notes), so a source's parent directory swapped for a link between the parent check and the open, or a source changed and restored between the start digest and the prefix build, is not caught; both need write access to main-checkout paths that no role child can write. *A symlink or `../` path*: the write guard gets the same `FORGE_DAEMON=1` and `FORGE_DAEMON_WRITE_ROOTS`. *A steered root or cwd*: `FORGE_ROOT` is pinned to the main checkout, as the pool pins it for every session, and the child starts at the realpath of the worktree that was checked, not at `job.worktree` again. *A Bash or other unapproved call*: it prompts, and with no one there `runRoleChild` denies it with the fixed `UNATTENDED_DENIED` text, which tells the agent not to retry or work around the call and to record what it needed in its output file; the run log gets a `forge-permission` line. *A trusted file changed anyway*: the child's own `forge` calls refuse through `FORGE_DAEMON_TRUST`, and the runner recomputes the trust digest and the confine digest after the child exits and fails the run as `untrusted` if either moved. The confine digest is the one a session's turns are held to (`git status` and content over the protected set, every `CLAUDE.md` and `CLAUDE.local.md` at any depth, the instruction files, an in-checkout `core.hooksPath` dir), so a nested `lib/CLAUDE.md` or a `.husky/` hook changed through Bash is caught too. *Starting a role step did not choose*: the lease hold, the epoch fence and step re-run under the job lock before the start; and under `FORGE_DAEMON=1` only the job's own session may run it, since the child carries that job's own scope (`forge pr merge`, repo proposals, downstream), which no other session may mint. *Option injection through argv*: `model`, `effort` and `agent` are validated or dropped, session ids must be uuids, the prefix file must be an absolute path, and the brief goes to stdin as one JSON-escaped line, never argv. *A planted `worktree`*: `jobWorktreeProblem`, and the worktree must lie under a worktrees root. *A planted `agentId` reaching another session's transcript*: only a uuid is tried as a session file, only at the job's own worktree slug (never the root's), confined and never through a link. *Billing past the login*: `sessionEnv` drops API keys and provider switches unless `daemon.auth` is `api-key`. *A context session's fork under another agent*: a review or rework build may fork a **context session** that read the round's shared inputs first ([Daemon runtime](daemon-runtime.md) › Role runs). Its key binds the round, agent, model, effort and trusted prefix file, so a fork's `--agent`, `--model`, `--effort` and `--append-system-prompt-file` always equal the context's: a reviewer never runs on a builder's system prompt, and a builder's tool list never leaks into a reviewer. The context child and the fork take the spawn's own `roleArgv`, so both are confined exactly as a cold run (same permission mode, allowed tools, write roots, deny rules, env and cwd), and the runner recomputes the trust and confine digests right after the context child exits: a context that moved a trusted or protected file is recorded failed `untrusted`, so no lens forks it, and the launching role fails `untrusted` without starting. A context is also ready only when its main loop called no tool but `Read` no call was denied and no stdout line was dropped unread (too long, not JSON or a protocol error: one could have held a tool call the check never saw), judged from the stream's `tool-use`, `line-too-long`, `unreadable-line` and `protocol-error` events, since its turns become the prior turns of every fork. *A forged context id*: `contexts` is a locked `job.json` field (`forge job agent run` only), the CLI copy sits under `Edit(.forge/runtime/**)`, and `roleArgv` takes only a uuid for `--resume`. Residuals: the run has no `--max-budget-usd` cap and no lease heartbeat past `AGENT_LEASE_MS` (2 h), and a Bash route to a trusted file is caught after the run, not before.
- **Permission mode is a human's choice, held in memory.** `POST /api/daemon/mode` (token, matching Origin, JSON) names a scope (validated, and a job must have a `job.json`) and one of `default`, `auto` or `dontAsk` (lib/integrations/claude/argv.ts `PERMISSION_MODES`); anything else is a 400. The pool keeps the choice in memory only: session records live in `.forge/runtime/`, which the session can write, so a mode read back from disk would be one the session could choose for itself. A running child gets a `set_permission_mode` control request; a later spawn gets `--permission-mode <mode>` in place of the template's. Until claude reports its mode (at its first turn's init) the supervisor takes the one the child was launched with. A switch claude refuses or doesn't confirm fails closed: a narrowing one stops the child, so the next spawn starts in the chosen mode, and a widening one leaves the choice at what the child still reports. `auto` stays refused in `daemon.command`, so a repo's config can't put every session on every machine that runs `forge dash` into it: only a human at the dashboard can, for one session, until that `forge dash` stops. In `auto`, Claude Code's classifier approves calls outside `allowedTools` without a human, so a misled agent's call may run unread; the deny rules, the trust check and the git pins below still hold. `bypassPermissions` is never offered, and claude refuses it on a session not launched with `--dangerously-skip-permissions`, which validation forbids. The same POST with scope `_jobs` sets the default for every job session without its own choice, also in memory only; the inbox, the office and the chats never take it, and a gate run's child always runs in `dontAsk`. A chat launches in `default` even when `daemon.command` names another mode, until its owner chooses one for it. `forge dash --permission-mode` sets the run's launch mode: every job, inbox and office session of every project it loads starts in it (and the `_jobs` default starts at it) unless a human chose another for that session. It is the human's own command line, refused when `FORGE_DAEMON=1`, so a session can't start a second dashboard with it, and it is never read back from the dashboard record. The flag now reaches the inbox, which reads tracker text, and the office, which decides gates: in Auto, a call that text misleads either into runs unread, so a launch in Auto trusts that input as well as every job's. There is no CLI command to switch a running dashboard's modes, for the same reason there is none to answer a prompt. **Auto on one session reaches the whole daemon.** A same-user process can read the dashboard's login file (`forge dash url` refuses a daemon session, but the file is the owner's) and a non-browser client can send any Origin, so a session whose calls run without a human (Auto, or one a human allowed `curl` to) can read the token and post to `/api/daemon/mode` or `/api/daemon/permission`: switch other sessions to Auto, make Auto the job sessions' default (`_jobs`, which also reaches jobs created later), or answer their prompts and its own. A session that only runs what `allowedTools` lists can't: no `forge` command posts to these routes, and `forge dash --permission-mode` refuses a daemon session. Nothing on loopback tells the page apart from a session's process, so treat putting any session in Auto as trusting every session's input.
- **Effort is a human's per-job setting, read back from `job.json`.** The level reaches argv only as one word from the fixed list (`EFFORTS` in `lib/core/job/schema.ts`), and never stdin. `normalizeJob` reads anything else in `job.json` as null and `buildArgv` ignores a value outside the list, so a hand- or session-written `"--dangerously-skip-permissions"` or `"high --add-dir /"` never becomes an option. An invalid `runtime.effort` is a `daemonProblems` refusal, so no session starts. `withEffort` drops every `--effort` and `--effort=` in `daemon.command`, so a duplicate can't win over Forge's. `forge job set --field effort=…` is refused, and `forge job effort` and `forge job new --effort` refuse under `FORGE_DAEMON=1`, so a misled session can't raise its own or another job's level through the CLI. `POST /api/jobs/:id/effort` takes the token, a matching Origin and JSON, an existing job id and a value from the list or null. Residual risk: in a job that predates the CLI copy, a session can still write a valid level into its own `job.json`, as it can `budget.limits` (the deny tail and the write guard refuse the file tools; a newer job's folder copy is ignored). That costs tokens and time, bounded by `pipeline.budget` and visible in the session log's `effort` event and the card chip, and it never widens what the session may do. `complexity` is session-writable through `forge job set --field`, but only as `low`, `medium`, `high` or null, and it only selects among levels a human configured in `runtime.effortByComplexity`, which never reaches a session's argv. That is why, unlike the permission mode, effort is read back from disk: it is a human's setting that must survive a `forge dash` restart.
- **Spend caps under the daemon.** A session misled by request, tracker or PR text could try to spend more than a person allowed; four things bound it. *The backstop holds per key*: with the daemon on, `daemon.jobBudget` fills each of `tokens`, `usd` and `minutes` that config and the job's own overrides leave unset (`effectiveLimits` in `lib/engine/metrics/budget.ts`), so setting one key never drops the others; only a person's explicit per-job `null` (a confirmed terminal or the dashboard, above) lifts a key. *The budget field is locked*: `budget` is in `LOCKED_FIELDS` (`lib/core/job/fields.ts`), so `forge job set --field budget…` (any path under it, or the whole object) is refused for every caller. *A dollar cap per spawn*: every job session's child gets `--max-budget-usd`, the job's remaining dollars recomputed at each spawn (`lib/office/session/budget-cap.ts`); `buildArgv` drops any `--max-budget-usd` in `daemon.command` and validation refuses one, and a `result` with `subtype: error_max_budget_usd` stops the session at once rather than being retried as a quota limit. The figure is the job's metered spend, with the resumed conversation's baseline added back (below). *Provider switches are scrubbed*: under `daemon.auth: subscription`, `sessionEnv` drops `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `CLAUDE_CODE_USE_FOUNDRY` and `ANTHROPIC_BASE_URL` with the API keys, so a variable inherited from the process environment can't bill another account or route through a proxy; `forge doctor` and the Workers popover name any that are set. Residuals: a session with arbitrary shell could read the login file and POST the budget route itself (`daemon.allowedTools` grants no `curl`, so that is a prompt a person sees); `reconcile.json`'s resume count sits under `.forge/runtime/`, which the deny tail covers for file tools but a Bash write could reset; and variables set in claude's own settings files (the `env` block and `apiKeyHelper` in `~/.claude/settings.json` or managed settings) are not scrubbed or reported, so a `CLAUDE_CODE_USE_BEDROCK` or `ANTHROPIC_BASE_URL` set there still reaches a subscription session.
- **Metered spend.** A budget that trusts the session it bounds is not a budget, so enforcement reads what the supervisor measured, not what the session reports. claude's own `result` line feeds it (`total_cost_usd`, `modelUsage`), and only the supervisor in `forge dash` writes `.forge/runtime/meter/<scope>.jsonl`; no CLI command does ("Metered spend" in [Policies](policies.md)). Each bypass a misled session might try is closed. *Under-reporting or skipping `--import`*: a job's enforced spend is never below its meter or its reported total. *Small `--tokens`, `--tool-uses` or `--duration-ms`*: refused in a daemon session. *Ending agents without an id*: refused unless `--status lost`, or recorded `unmeasured`, and the meter still holds the cost. *Editing `events.jsonl` to claim covered runs*: the job folder's copy is a mirror Forge never reads, and covered usage in the CLI copy is clamped to the reported total, so it can't push the figure below either. *Forcing respawns or forks so the cumulative resets or repeats*: deltas are per spawn against a resumed baseline, with reset and rebase handling. *A planted symlink or FIFO at the meter path*: refused, never followed, by the writer and the reader; `Edit(.forge/runtime/**)` in `DENY_TOOLS` and the write guard already keep file tools out. *Spending outside any job*: the inbox, the office with forge dash's gate runs (one cap, the `_office` and `_gates` meters summed: at the cap no gate run starts, and each gate run's child gets `--max-budget-usd` set to what is left), and every chat of the project (`daemon.dailyUsd.chat`, every `_chat-<id>` meter in `meter/` summed) stop at `daemon.dailyUsd` per UTC day, and a start the same day is refused; raising `foreman.assistants.parallel` or opening more chats never multiplies a cap. When a meter file their cap sums can't be read, or the check after a result throws, the cap check fails closed the same way. *Lifting a cap in `daemon.dailyUsd`*: `.forge/config.yml` is trusted, so a change stops the pool. Residuals: arbitrary shell could delete or truncate a meter file or plant a link that disables the writer (`daemon.allowedTools` grants no shell beyond `forge`, `git rev-parse` and the listed `gh` reads, so that is a prompt a person sees); a deleted meter drops enforcement back to the reported figure, and a resume then rebases and loses one turn. A meter file over 64 MiB is not read: meter files are never pruned, so a long-lived one reaches that some day (years away at this repo's rate). The inbox, or the office and its gate runs, then stop, but a job's budget checks fall back to its reported figure, with a `meter: …` error in its session log. A resume that restores a different conversation than the one recorded, whose first cumulative is at or above the recorded baseline, under-counts that first delta by the baseline; a session can't force this. Cost incurred after a turn's last result and before a crash is unmetered until the next result in that conversation, which carries it. Whether `--max-budget-usd` compares claude's restored cumulative is unverified: adding the resumed baseline to the cap errs towards a generous mid-turn cap rather than a session that dies at every resume, and the per-result check still parks the job. *Under-counting through a context session's forks* ([Daemon runtime](daemon-runtime.md) › Role runs): a fork's result cumulative carries its context session's, so the runner subtracts the context's sidecar cumulative only when the fork's is at or above it on `usd` and on every token field of every model it holds (`forkBase`, lib/engine/workspace/context-session.ts), and otherwise counts the whole fork cumulative; the context's own run is recorded once, under role `context`, in `job.usage` and the ledger. Residual: a fork whose cumulative did not carry the context's but reached it on every field anyway is under-counted by at most the context's own cost, which is itself recorded.
- **Narrow permissions, still not a sandbox.** Anything `allowedTools` doesn't list is asked about (or refused under `dontAsk`), and subagents inherit the list. The default allows Bash only for `forge` and specific git/gh subcommands (rev-parse, merge/rebase `--abort`; `gh pr view|list|checks`, `gh run view`). The session's cwd is the main checkout and `cd` and `git -C` aren't allowed, so a bare `git add`/`git commit` would act on the base branch: agents stage and commit through `forge git add|commit <job>`, which runs git with the job's worktree as cwd (refusing the main checkout, a branch other than the job's, and a merge or rebase in progress for `commit`), takes only `--message`/`--message-file` (a file inside the job dir) and paths, so no `-c`, `-C`, `--git-dir`, `--amend`, `--no-verify` or `--author`, refuses paths outside the worktree or in a `.git`, checks the message for AI attribution, clears `GIT_DIR`-style variables, and under `FORGE_DAEMON=1` runs git with the session pins below (outside the daemon, a human's hooks run). Claude Code matches each part of a compound command against the rules and won't match past `git -c` or an env assignment, so `git -c core.sshCommand=…`, `git -c alias.x='!…'` and `FOO=… git …` are refused. `git diff|log|show|range-diff` are left out because `--output=<file>` writes wherever git can, and Claude Code's protected-path check covers its own file tools, not git: `git log --format=… --output=.git/config` would plant a textconv or filter driver that the next diff or add runs. Agents read history through `forge git`, which refuses `--output` (git accepts no abbreviation of it), `--ext-diff`, `--textconv` and `--open-files-in-pager`, and forces `--no-ext-diff --no-textconv`. `git rebase` is left out because `--exec` runs shell: the integrator starts merges and rebases with `forge integrate --keep-conflicts` and finishes them with `forge integrate --continue`, which refuses a rebase todo holding anything but picks. `git mv` is left out too: given a `x/../.git/config` destination it reports an invalid path, then renames the file anyway and exits 0. `gh api` and other GitHub writes are left out; Forge's own writes (push, PR, labels, comments) go through `forge`. Validation refuses `allowedTools` entries that undo this (unscoped `Bash`, bare `git`/`gh`, `git -…`, `git config|grep|submodule|bisect|…`, `git diff|log|show|range-diff|…`, `git mv`, `git rebase`, `gh api|extension|alias|auth|…`); the list catches known forms and is not exhaustive.
- **Git hooks are off in the session and in the periodic sync.** A repo can point `core.hooksPath` at a tracked directory (`.githooks/`, unlike `.git/` and `.husky/`, isn't one of Claude Code's protected paths), so a hook written there would run on the next `git commit`, on a `forge pr open` push, or on the `reference-transaction` of a fetch. An in-checkout hooks directory is in the deny tail and the confine digest, and a worktree's is reviewed with the job's diff. The daemon also spawns the session with `core.hooksPath=/dev/null` and `core.fsmonitor=false` in `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n`, which outrank every config file and are inherited by subagents, `forge` and verify commands. `forge dash`'s periodic `forge sync` child runs with `SYNC_PINS` (`lib/integrations/git/runner.ts`): the same two, plus `core.pager=cat`, `diff.external=/dev/null` and `gpg.program=gpg` (git's own default, so a user's signed merges keep working), appended after any `GIT_CONFIG_*` the caller exports; `credential.helper` is never pinned. The cost: no hooks at all in daemon mode, including Git LFS's pre-push upload. Not pinned in the session: filter, diff and merge drivers and `gpg.program`, which only `.git/config` or `~/.gitconfig` can define. The session has no allowed way to write `.git/` (Claude Code's file tools treat it as protected, so only a human's answer to a prompt could allow it, the write guard refuses any `.git` segment inside a worktree, including a worktree's `.git` file, and the git forms it may run take no output path), but anything the human or another tool puts there still applies. What remains broad is what the session writes inside its write roots: worktree files that build and test tooling executes, which verify runs and the review panel reads. Enable the daemon only on repos whose tracker input you trust (or with intake restricted, e.g. `tracker.github.comments: collaborators` and ready labels only maintainers set).
- **Keeping a slot and marking agents lost read `job.json`, which the session writes through `forge`** (and, in a job that predates the CLI copy, could write directly). A session that records agents it never ends can pin its own slot, never another job's, for at most 2 h per agent start (the `AGENT_LEASE_MS` ceiling; a `startedAt` or `endedAt` more than 60 s in the future is ignored, so a forged time can't stretch the ceiling or the idle window, and the idle timer never re-arms for longer than its window), and a human's session or pool Stop ends it sooner, the same bound as a turn that never returns a `result`. Lost-marking writes on behalf of a session that no longer exists, so it touches only agents of a job whose `lease.driver` is that session's id, never another driver's. The job id it reads is the validated scope, so no path is built from session output, and nothing new reaches the child's stdin, argv or environment. An agent role becomes a `job.json` key and part of a review path, so `forge job agent --role` and `recordAgent` take only a role name or `reviewer:<lens>` (never `__proto__` or a path), and lost-marking skips any other key.
- **`--body-file` publishes only the session job's own files.** `forge tracker comment`, `tracker create`, `job new`, `job note` and `eval new` read their text from `--body-file F`, so an agent could otherwise publish any file the user can read (`~/.ssh/id_ed25519`) through a tracker comment. Under `FORGE_DAEMON=1`, `-` (stdin) is always allowed; any other F is refused in the `_inbox` and `_office` sessions (a gate run's `_gates` scope refuses every forge command), and in a job session must resolve, after realpath, inside the realpath of that job's folder or of its computed worktree (`<worktrees root>/<id>`, never `job.json`'s session-writable `worktree`). The check compares path components, so a sibling that shares the prefix, `..` and a link pointing out are refused; the file is then read like a review (a regular file under 1 MiB, never a link or a FIFO). Tracker writes still pass the secret scan. Residual risk: a parent directory swapped between the check and the open (Node has no `openat`).
- **Chats.** A chat is the owner's conversation with the Foreman: its own pool session (scope `_chat-<id>`, the id 12 lowercase hex characters checked by `CHAT_ID` before any path is built), started only by the owner's message through `startWork`, never routed a request, never counted against a cap, and launched in `default` (it asks) unless the owner chose another mode for it. It runs under `FORGE_DAEMON=1` with the usual write roots, deny tail, trust digest and `allowedTools`. Unlike the inbox and office, it may drive a job when the owner asks, so `refuseInboxDrive` does not refuse it: `forge environment down` runs there, and a `forge job set` that moves a job to done or cancelled tears its environment down as in a job session rather than only stopping it. Its history is `.forge/runtime/chats/<id>/` (`chat.json`, `log.jsonl`), which only the dashboard server writes and the deny tail and the write guard keep every session's file tools out of; reads and appends refuse a link or FIFO in place of the dir or a file, and appends stop at 64 MiB. The threat model has five attackers, and each bypass is closed. *A cross-site page or another local process posting to the chat routes*: every POST takes the token, a matching Origin and JSON, with a 64 KiB body and an 8000-character text cap ([Dashboard security](dashboard-security.md)). *A job, inbox or office session or a gate run's assistant misled by tracker or PR text into putting text into a chat or another session's stdin*: the only free-text stdin write refuses every scope but a chat's, no `forge` command writes a chat's files or sends a message, and no request routes to a chat. *A chat session misled by what it reads (issues, PRs, job files, command output) into deciding a reserved gate, widening a mandate or merging*: in a chat scope `forge job human` refuses a gate `foreman.reserved` keeps with a person (`gate:<class>`, a reserved phrase, or a security review that didn't pass) before writing anything (`chatGateRefusal`, lib/office/chat/authority.ts), whether or not `foreman.enabled` is set, and `forge job set` of a job waiting on a gate only carries out the decision recorded at its park, as in a foreman session (`chatSetRefusal`): no `--field`, `--waiting-on` or `--reason`, only `--state running` with a stage that decision allows, and the same reservations judged with its action, or as an accept when none is recorded, so rewording the park reason, parking the job elsewhere first or moving it on after a recorded rework is refused too; `--actor foreman`, `approve-release`, repo approvals, `forge mandate` writes and `forge pr merge` (a chat scope is never the job's own) stay refused as in any daemon session; every action it records carries actor source `chat`; and `forge chat brief` fences the board's titles and park reasons and the mandates' text under a data line. *A forged scope or chat id aimed at a path*: the route pattern and `CHAT_ID` admit only 12 hex characters. *Runaway spend*: `daemon.dailyUsd.chat`, failing closed ("Metered spend" above). Residuals, unchanged from every daemon session: provenance is the unauthenticated `FORGE_DAEMON_SCOPE`, so a Bash-capable session can run `FORGE_DAEMON= forge job human …` as a person; a same-user process can read the login file and post a chat message; and owner text is the owner's instruction by design, so a chat the owner put in `auto` runs what the classifier allows unread, like any session in Auto.
- **Orphan reaping** proves each record (every `daemons/<scope>.json`) separately before signalling its pid (see ["Daemon runtime"](daemon-runtime.md)), so a stale or planted record can't make Forge kill an unrelated process.
- **The machine dashboard is a human's to start, stop and widen.** One `forge dash` serves every registered project, so registering a project (its pool would boot under that project's config), raising the machine cap and starting or stopping the server all reach every project's sessions. In a daemon session (`FORGE_DAEMON=1`), `forge dash` only reports an already-running machine dashboard for an already-registered project; anything else (an unregistered repo, `--stop`, `--background`, `--foreground`, `--dev`, or no proven dashboard) exits 1 with `forge dash starts, stops and registers the machine's dashboard, which a daemon session may not do; a human runs it in their own terminal`. `forge project settings --max-concurrent` is refused there too (`forge project settings` alone still prints), and `forge project add|remove` already are. The dashboard's Add project (`POST /api/projects`) is the human channel for registering from the browser, behind the token, a matching Origin and JSON; it never approves the project's trusted files. Each pool pins its sessions' `cwd` and `FORGE_ROOT` to its own root, and a session of one project that names another through `FORGE_ROOT` still meets that project's trust digest and the human-only operations below. The token is one per server and no longer in the page: `GET /` serves it to no one, and every `/api` route needs the login ([Dashboard security](dashboard-security.md) › Login). It stays readable by a same-user process through the 0600 login file, the browser profile or the terminal that printed the login link; `forge dash url` refuses a daemon session before reading anything, and a daemon session's `forge dash` report carries no key, but `Read(…)` deny rules for the login file are not part of the policy.
- **A project's pool boots with the machine dashboard only while a human's approval still matches its files.** A pool's start takes the digest of the files Forge trusts as approved ("The CLI checks at the sink" above), so a server that booted every registered project's pool would approve, for each, whatever bytes were on disk: after a reboot, after `forge update`'s restart, or because `forge dash` ran in another repo. So the approval is a record outside every session's write roots: `<FORGE_HOME>/trust/<rootLabel>` (`lib/engine/project/trust-approval.ts`, 0600 in a 0700 home), holding the `trustDigest` of the last human act in that project. A Start press in the dashboard (`POST /api/p/<project>/daemon`) records the snapshot its pool then runs under, which a start retakes only while no child of that pool lives, so a Start pressed mid-turn never approves what the turn wrote. `forge dash` run in the repo records the files as they are when it starts the dashboard or registers the repo, never when it only reports the running dashboard for a repo already registered (so a change a "trusted config changed" notice points at still waits for Start), never for a daemon session's report, and not with `--dev`, which boots nothing. A server boots a project's pool, at its start, when a project is registered or when one comes back from `missing`, only when `daemon.enabled` is true, `daemonProblems` is empty and the current digest equals that record. Otherwise the pool stays off and `/api/p/<project>/state` `daemons.needsApproval` is true (no `lastError`: it is no failure). The Daemon panel then shows the pill `needs approval` and says to review `.forge/config.yml` and the other files Forge trusts (notes, reviewers, CLAUDE.md, AGENTS.md), then press Start, which approves them as they are. So a change a session made to a trusted file, which stopped that daemon, survives a restart as a stopped pool until a human has looked at it. A project registered with `forge project add` or the dashboard's Add project boots after its first Start, or a `forge dash` in it that starts the dashboard. The residual: a human who presses Start while the pool is off, or starts the dashboard or registers a repo with `forge dash`, approves the files as they are at that moment, as before.
- **Every project's sessions and commands inherit the environment of the shell that started the machine dashboard.** Each pool pins `FORGE_ROOT` and nothing else per project, and `sessionEnv` strips the API and provider keys as before, so what a project's own shell exports (a direnv `.envrc`, a project `DATABASE_URL`, the key `daemon.auth: api-key` bills) reaches its sessions only if the dashboard's shell had it too. `forge dash` run in another repo while the server runs reports the running server and never contributes its shell. Configured commands still get only the `commandEnv` allowlist, and a `file` secret reads its own project's file; an `env` secret and an `inherit` name read the dashboard's environment. Start the machine dashboard from a shell that holds nothing one project would not want another's sessions to see.
- **The login service is a human's to install, and carries no credentials.** `forge service install` writes a per-user LaunchAgent or systemd user unit that runs `forge dash --service` at login (`lib/engine/project/login-service.ts`), so a session that could install one would gain a login item outliving every session, and one that could start `forge dash --service` could restart the machine dashboard under its own terms. Under `FORGE_DAEMON=1`, `forge service install|uninstall` and `forge dash --service` exit 1 (`forge service status` still prints). The unit file sits 0644 under the home directory, so its environment holds only `PATH` (sanitised), `HOME`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `LC_*`, `TZ`, `TMPDIR` and `FORGE_HOME`, each only when the command environment's `allowlisted` passes it: never a credential-like name, `NODE_OPTIONS` (it can `--require` any file), the daemon markers or `FORGE_COMMAND_PATH`; tools under the service find their credentials in their own config or keychain. Every value is escaped for its format (XML in the plist; double quotes with `\`, `"`, `%` and, in `ExecStart`, `$` escaped in the unit), and a value or path with a control character refuses, naming the variable, before anything is written, so a newline can't add a plist key or an `ExecStartPre=` line. Install renames over whatever is at the unit path and uninstall unlinks that exact path, so a planted symlink is replaced or removed, never followed. `<FORGE_HOME>/runtime/uptime.json` (0600 in a 0700 dir) is read tolerantly: names must be project names, counts bounded integers, times dates, and the helper's error one capped line, and it only ever shapes a doctor line or a cleaned notification title, never an action. Each `service-restarted` notification names only its own project, since two projects may notify different teams. The sleep helper's argv is fixed strings and the dashboard's pid.
- **The dashboard record is proven, not trusted.** The machine dashboard's record is `<FORGE_HOME>/dashboard.json` (`{pid, url, startedAt, permissionMode}`, written 0600 in a 0700 home, never holding the token, which sits apart in `<FORGE_HOME>/dashboard-login.json` (`{pid, token}`, 0600, written before the record, emptied by `--stop`, and trusted only for the proven record's pid); `permissionMode` is only reported, by `forge dash`'s mismatch refusal and `forge daemon status`, never applied, and anything but the three modes reads as null), outside every session's write roots; an older per-repo `forge dash` left `.forge/runtime/dashboard.json`, which any session that can write the runtime dir can plant, and which `forge dash --stop` and `forge daemon status` still read. Either way the proofs apply, so `provenDashboard` (`lib/engine/ops/dashboard-record.ts`) accepts it only when all of these hold: (1) it is a regular file (never a symlink or FIFO, read without blocking) of at most 4 KiB holding a JSON object; (2) `pid` is an integer > 1, not the reading process, and alive; (3) `ps` reports a start time within 30 s of `startedAt`, so a reused pid fails; (4) the process's command line has `forge` in the script position followed by `dash`: the script position is the first word (basename `forge`, or this install's `bin/forge`), or the word right after a node executable (basename `node`/`node.exe`, or Node's own path). The rule exists because start times are public, so a forged `startedAt` alone could name any process, and a `forge`…`dash` pair anywhere in the line would name an unrelated one such as `claude /forge dash`. A launch with node options before the script, or with whitespace in any other path, fails closed; Forge never launches the dashboard that way; (5) `url` is an `http:` URL on `127.0.0.1`, `localhost` or `[::1]` with an explicit port and no userinfo, path, query or hash, compared on the parsed hostname. What the proof does not bind: the url is not tied to the pid. A writer that copies the live dashboard's `pid` and `startedAt` and changes only the url to another loopback port (one it serves itself) has a proven record, so `forge dash`, `forge daemon status` and `forge update` show that url. So the worst a forged record can do is name the running `forge dash` and point at any loopback port. Binding the url to the process (an HTTP handshake) is out of scope. Anything else is stale: its pid is never signalled and its url never printed. `forge dash` (`--stop`, the running answer, the `--dev` refusal), `forge daemon status` and `forge update` read it only through this check; `forge dash --background` accepts its own child's record when the pid is that child's and the url passes rule 5; notifications use only rule 5, because they build a link and signal nothing. On native Windows no record is proven, since there is no start-time probe. Stopping the write itself is a separate layer: the daemon's deny rules over `.forge/runtime/**` (#382).
- **The logs** (`daemons/<scope>.log`) live in gitignored `.forge/runtime/`; they hold whatever the sessions printed, so treat them like transcripts. The dashboard renders every log string as text, and `forge daemon log` escapes control characters so session output can't drive the terminal.
