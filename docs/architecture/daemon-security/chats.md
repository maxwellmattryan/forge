# Daemon security › Chats

Part of [Daemon security](../daemon-security.md).

**Chats.** A chat is the owner's conversation with the Foreman: its own pool session (scope `_chat-<id>`, the id 12 lowercase hex characters checked by `CHAT_ID` before any path is built), started only by the owner's message through `startWork`, never routed a request, never counted against a cap, and launched in `default` (it asks) unless the owner chose another mode for it. It runs under `FORGE_DAEMON=1` with the usual write roots, deny tail, trust digest and `allowedTools`. Unlike the inbox and the office's runs, it may drive a job when the owner asks, so `refuseInboxDrive` does not refuse it: `forge environment down` runs there, and a `forge job set` that moves a job to done or cancelled tears its environment down as in a job session rather than only stopping it.

Its history is `.forge/runtime/chats/<id>/` (`chat.json`, `log.jsonl`), which only the dashboard server writes and the deny tail and the write guard keep every session's file tools out of; reads and appends refuse a link or FIFO in place of the dir or a file, and appends stop at 64 MiB.

The threat model has five attackers, and each bypass is closed.
- *A cross-site page or another local process posting to the chat routes*: every POST takes the token, a matching Origin and JSON, with a 64 KiB body and an 8000-character text cap ([Dashboard security](../dashboard-security.md)).
- *A job or inbox session, an office run's model child or a gate run's assistant misled by tracker or PR text into putting text into a chat or another session's stdin*: the only free-text stdin write refuses every scope but a chat's, no `forge` command writes a chat's files or sends a message, and no request routes to a chat.
- *A chat session misled by what it reads (issues, PRs, job files, command output) into deciding a reserved gate, widening a mandate or merging*: in a chat scope `forge job human` refuses a gate `foreman.reserved` keeps with a person (`gate:<class>`, a reserved phrase, or a security review that didn't pass) before writing anything (`chatGateRefusal`, lib/office/chat/authority.ts), whether or not `foreman.enabled` is set, and `forge job set` of a job waiting on a gate only carries out the decision recorded at its park, as in a foreman session (`chatSetRefusal`): no `--field`, `--waiting-on` or `--reason`, only `--state running` with a stage that decision allows, and the same reservations judged with its action, or as an accept when none is recorded, so rewording the park reason, parking the job elsewhere first or moving it on after a recorded rework is refused too.
  - `--actor foreman`, `approve-release`, repo approvals, `forge mandate` writes and `forge pr merge` (a chat scope is never the job's own) stay refused as in any daemon session; every action it records carries actor source `chat`; and `forge chat brief` fences the board's titles and park reasons and the mandates' text under a data line.
- *A forged scope or chat id aimed at a path*: the route pattern and `CHAT_ID` admit only 12 hex characters.
- *Runaway spend*: `daemon.dailyUsd.chat`, failing closed ("Metered spend" in [Spend](spend.md)).

Residuals, unchanged from every daemon session: provenance is the unauthenticated `FORGE_DAEMON_SCOPE`, so a Bash-capable session can run `FORGE_DAEMON= forge job human …` as a person; a same-user process can read the login file and post a chat message; and owner text is the owner's instruction by design, so a chat the owner put in `auto` runs what the classifier allows unread, like any session in Auto.
