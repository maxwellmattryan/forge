# Daemon security › Human-only operations

Part of [Daemon security](../daemon-security.md).

- **Human-only operations.** `forge pr merge <id> --now` (skips merge.auto, the recorded approval, protected paths, the escalate floor and CI), `forge job budget <id> --set|--ack` (raises or acknowledges a job's spend limits), `forge budget ack --period P` (lifts the repo spend cap), `forge job unshelve <id>` (takes a shelved job off the shelf, so it can spend again) and `forge job set <id> --state …` on a job cancelled or set done while shelved (puts it back to work; a terminal only, no dashboard control) need a person's go-ahead from one of two channels a session's children can't reach.
  - *A terminal*: `confirmHuman` (`lib/cli/commands/human.ts`) refuses under `FORGE_DAEMON=1`, refuses (code `human_only`) unless both stdin and stderr are TTYs, then prints what the operation skips or changes and asks the person to type the job id (the period for `budget ack`); any other answer refuses with `not confirmed; nothing changed`. A configured command's stdin is never a TTY, so a nested call or a piped answer (`echo <id> | forge …`) is refused without reading it.
  - A TTY alone is not enough: branch code that a `forge verify` (or a `/forge` session) in the person's own terminal runs can open that terminal's `/dev/tty` and hand it to `forge`, but the prompt then appears on the person's screen and waits for the id to be typed. Sessions under `forge dash` are spawned detached, in a new session with no controlling terminal, so their children can't open `/dev/tty` at all. No flag, env var or config key skips the prompt, because branch code can set any of them. A Ctrl-D, a Ctrl-C or a stdin that closes at the prompt refuses like a wrong answer.
  - *The dashboard*, per operation: for `pr merge --now`, Merge now posts `POST /api/jobs/:id/merge`, which takes the login, a matching Origin, JSON and the id typed back; for `budget ack`, the Acknowledge in Needs you posts `POST /api/budget/ack`, which takes the login, a matching Origin and JSON ([Dashboard security](../dashboard-security.md)); for `job budget --set|--ack`, Approve & continue on the budget gate posts `POST /api/jobs/:id/budget`, which takes the login, a matching Origin and a JSON body of at most five `key=value` entries; for `job unshelve`, Un-shelve (and the Approve and Rework that un-shelve first; Close cancels the job without un-shelving it) in the Shelved list posts `POST /api/shelf`, which takes the login, a matching Origin and JSON, and pins each job to the shelving the list showed.
  - Only a person takes a job off the shelf whatever writes: `setJob` refuses (`human_only`) any write that moves a shelved job's stage, state or `waitingOn` unless it un-shelves, finishes or cancels it, and refuses any write but `shelveJob`'s that puts a job on the shelf (`forge job shelve`, refused in every daemon session, or the gate runner's Foreman shelve under `foreman.escalations: foreman`, which needs its in-process authority).
  - A cancel (or a done) is no way around that: the write that finishes a shelved job marks it `finishedWhileShelved` (a locked field), and `setJob` refuses (`human_only`) any write that moves a marked job out of done or cancelled without a person's grant, so a session that cancels a shelved job can't then queue it; `forge job set` asks the person at the terminal to type the job id first, logs the grant's actor on the transition and clears the mark.
  - The engine checks the grant at runtime too (`isHumanGrant`: `mergePr`'s `now`, `budgetCmd`'s `grant`, `unshelveJob`'s `grant`, `setJob`'s `grant`), so an in-process caller can't skip the channel by accident; that is no defence against code in the same process. The events record the person's resolved actor from a terminal, `dashboard` from the dashboard. The terminal check stops agents and configured commands that call `forge` directly or pipe in an answer; any same-user process can defeat it.
  - Residuals, which only sandboxing configured commands would close: branch code that starts its own pseudo-terminal (`script`) and types the id; branch code run from the person's own terminal (a `forge verify` there) that pushes the id into that terminal's input with `ioctl(TIOCSTI)` while the prompt waits, which macOS allows, as does Linux with `dev.tty.legacy_tiocsti` on; branch code that reads the dashboard's login file or the terminal that printed the login link and posts with a forged Origin (the login defends against browsers and other OS users, not same-user processes); branch code that runs `gh` with the person's login or rewrites state files directly.
  - The other `FORGE_DAEMON`-keyed refusals (`job effort`, `job new --effort|--force`, `release plan --force`, `release run`, `eval --set`, `doctor --bundle`, `update`, `focus`, `dash` modes, `job interim publish|release`, `job repo add|remove`) keep a session in its lane; they are not authorization.
- **Start and stop** need the dashboard token, a matching Origin and JSON, and a pool `start` additionally needs `daemon.enabled: true` and no `daemon.*` validation problem. A scoped start only re-enables one session inside a pool a human already started, so it never takes a trust snapshot. The config migration never sets `enabled`. Concurrent start/stop POSTs never leave more than one child per session: a start while a child exists or is stopping spawns nothing new.
- **SSE is loopback-only and per session**, rejects a foreign Origin and any request whose `Sec-Fetch-Site` is not `same-origin`/`none` (the same `readGuard` the history route uses), syntax-checks `session` (400 otherwise), sends a stream only its own session's lines, sends no CORS headers, allows 8 streams at once across all sessions (`503` beyond), ends any client more than 1 MiB behind, and recycles every stream after 5 minutes (EventSource reconnects with `Last-Event-ID`). The dashboard opens only the stream of the session on screen. Another site can never read a stream. In a browser that sends neither Origin nor Fetch Metadata on a no-cors GET, a cross-site page can still occupy slots until they are recycled; that costs the live log's availability, never the daemon.
- **History reads are confined.** `GET /api/daemons/log` validates the scope before building a path, requires the daemons dir to be the real `.forge/runtime/daemons` (not a symlink to elsewhere), resolves `<scope>.log` with realpath and serves it only from inside that dir, and reads it through one descriptor opened `O_NONBLOCK` and `fstat`-checked as a regular file. Session records (`<scope>.json`) are read through one `O_NOFOLLOW|O_NONBLOCK` descriptor and must be regular files under 64 KiB, or they count as absent. Logs are opened for appending with `O_NOFOLLOW|O_NONBLOCK` and must be regular files (a session whose log can't be opened keeps running without one), and `forge daemon log` opens them the same way for reading. So a symlink or FIFO planted in the runtime dir is never followed and can't hang the server, on read (the history route, `/api/events`) or on write (session logs, reap notes, and the repo-level audit log: `.forge/runtime` must be a real directory, and a planted link or FIFO at `audit.jsonl` makes that one append fail, never redirects it or blocks the server).
