# Daemon security › Machine dashboard

Part of [Daemon security](../daemon-security.md).

- **Orphan reaping** proves each record (every `daemons/<scope>.json`) separately before signalling its pid (see ["Daemon runtime"](../daemon-runtime.md)), so a stale or planted record can't make Forge kill an unrelated process.
- **The machine dashboard is a human's to start, stop and widen.** One `forge dash` serves every registered project, so registering a project (its pool would boot under that project's config), raising or unsetting the machine cap and starting or stopping the server all reach every project's sessions. In a daemon session (`FORGE_DAEMON=1`), `forge dash` only reports an already-running machine dashboard for an already-registered project; anything else (an unregistered repo, `--stop`, `--background`, `--foreground`, `--dev`, or no proven dashboard) exits 1 with `forge dash starts, stops and registers the machine's dashboard, which a daemon session may not do; a human runs it in their own terminal`. `forge project settings --max-concurrent` is refused there too (`forge project settings` alone still prints), and `forge project add|remove` already are.
  - The dashboard's Add project (`POST /api/projects`) is the human channel for registering from the browser, behind the token, a matching Origin and JSON; it never approves the project's trusted files. Each pool pins its sessions' `cwd` and `FORGE_ROOT` to its own root, and a session of one project that names another through `FORGE_ROOT` still meets that project's trust digest and the [human-only operations](human-only-operations.md).
  - The token is one per server and no longer in the page: `GET /` serves it to no one, and every `/api` route needs the login ([Dashboard security › Login](../dashboard-security/login.md)). It stays readable by a same-user process through the 0600 login file, the browser profile or the terminal that printed the login link; `forge dash url` refuses a daemon session before reading anything, and a daemon session's `forge dash` report carries no key, but `Read(…)` deny rules for the login file are not part of the policy.
- **A project's pool boots with the machine dashboard only while a human's approval still matches its files.** A pool's start takes the digest of the files Forge trusts as approved ("The CLI checks at the sink" in [Write confinement](write-confinement.md)), so a server that booted every registered project's pool would approve, for each, whatever bytes were on disk: after a reboot, after `forge update`'s restart, or because `forge dash` ran in another repo. So the approval is a record outside every session's write roots: `<FORGE_HOME>/trust/<rootLabel>` (`lib/engine/project/trust-approval.ts`, 0600 in a 0700 home), holding the `trustDigest` of the last human act in that project.
  - A Start press in the dashboard (`POST /api/p/<project>/daemon`) records the snapshot its pool then runs under, which a start retakes only while no child of that pool lives, so a Start pressed mid-turn never approves what the turn wrote. `forge dash` run in the repo records the files as they are when it starts the dashboard or registers the repo, never when it only reports the running dashboard for a repo already registered (so a change a "trusted config changed" notice points at still waits for Start), never for a daemon session's report, and not with `--dev`, which boots only what is already approved.
  - A server boots a project's pool, at its start, when a project is registered or when one comes back from `missing`, only when `daemon.enabled` is true, `daemonProblems` is empty and the current digest equals that record. Otherwise the pool stays off and `/api/p/<project>/state` `daemons.needsApproval` is true (no `lastError`: it is no failure). The Daemon panel then shows the pill `needs approval` and says to review `.forge/config.yml` and the other files Forge trusts (notes, reviewers, CLAUDE.md, AGENTS.md), then press Start, which approves them as they are. So a change a session made to a trusted file, which stopped that daemon, survives a restart as a stopped pool until a human has looked at it.
  - A project registered with `forge project add` or the dashboard's Add project boots after its first Start, or a `forge dash` in it that starts the dashboard. The residual: a human who presses Start while the pool is off, or starts the dashboard or registers a repo with `forge dash`, approves the files as they are at that moment, as before.
- **Every project's sessions and commands inherit the environment of the shell that started the machine dashboard.** Each pool pins `FORGE_ROOT` and nothing else per project, and `sessionEnv` strips the API and provider keys as before, so what a project's own shell exports (a direnv `.envrc`, a project `DATABASE_URL`, the key `daemon.auth: api-key` bills) reaches its sessions only if the dashboard's shell had it too. `forge dash` run in another repo while the server runs reports the running server and never contributes its shell. Configured commands still get only the `commandEnv` allowlist, and a `file` secret reads its own project's file; an `env` secret and an `inherit` name read the dashboard's environment. Start the machine dashboard from a shell that holds nothing one project would not want another's sessions to see.
- **The login service is a human's to install, and carries no credentials.** `forge service install` writes a per-user LaunchAgent or systemd user unit that runs `forge dash --service` at login (`lib/engine/project/login-service.ts`), so a session that could install one would gain a login item outliving every session, and one that could start `forge dash --service` could restart the machine dashboard under its own terms. Under `FORGE_DAEMON=1`, `forge service install|uninstall` and `forge dash --service` exit 1 (`forge service status` still prints).
  - The unit file sits 0644 under the home directory, so its environment holds only `PATH` (sanitised), `HOME`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `LC_*`, `TZ`, `TMPDIR` and `FORGE_HOME`, each only when the command environment's `allowlisted` passes it: never a credential-like name, `NODE_OPTIONS` (it can `--require` any file), the daemon markers or `FORGE_COMMAND_PATH`; tools under the service find their credentials in their own config or keychain. Every value is escaped for its format (XML in the plist; double quotes with `\`, `"`, `%` and, in `ExecStart`, `$` escaped in the unit), and a value or path with a control character refuses, naming the variable, before anything is written, so a newline can't add a plist key or an `ExecStartPre=` line.
  - Install renames over whatever is at the unit path and uninstall unlinks that exact path, so a planted symlink is replaced or removed, never followed. `<FORGE_HOME>/runtime/uptime.json` (0600 in a 0700 dir) is read tolerantly: names must be project names, counts bounded integers, times dates, and the helper's error one capped line, and it only ever shapes a doctor line or a cleaned notification title, never an action. Each `service-restarted` notification names only its own project, since two projects may notify different teams. The sleep helper's argv is fixed strings and the dashboard's pid.
- **The dashboard record is proven, not trusted.** The machine dashboard's record is `<FORGE_HOME>/dashboard.json` (`{pid, url, startedAt, permissionMode}`, written 0600 in a 0700 home, never holding the token, which sits apart in `<FORGE_HOME>/dashboard-login.json` (`{pid, token}`, 0600, written before the record, emptied by `--stop`, and trusted only for the proven record's pid); `permissionMode` is only reported, by `forge dash`'s mismatch refusal and `forge daemon status`, never applied, and anything but the three modes reads as null), outside every session's write roots; an older per-repo `forge dash` left `.forge/runtime/dashboard.json`, which any session that can write the runtime dir can plant, and which `forge dash --stop` and `forge daemon status` still read.
  - Either way the proofs apply, so `provenDashboard` (`lib/engine/ops/dashboard-record.ts`) accepts it only when all of these hold: (1) it is a regular file (never a symlink or FIFO, read without blocking) of at most 4 KiB holding a JSON object; (2) `pid` is an integer > 1, not the reading process, and alive; (3) `ps` reports a start time within 30 s of `startedAt`, so a reused pid fails;
  - (4) the process's command line has `forge` in the script position followed by `dash`: the script position is the first word (basename `forge`, or this install's `bin/forge`), or the word right after a node executable (basename `node`/`node.exe`, or Node's own path). The rule exists because start times are public, so a forged `startedAt` alone could name any process, and a `forge`…`dash` pair anywhere in the line would name an unrelated one such as `claude /forge dash`. A launch with node options before the script, or with whitespace in any other path, fails closed; Forge never launches the dashboard that way; (5) `url` is an `http:` URL on `127.0.0.1`, `localhost` or `[::1]` with an explicit port and no userinfo, path, query or hash, compared on the parsed hostname.
  - What the proof does not bind: the url is not tied to the pid. A writer that copies the live dashboard's `pid` and `startedAt` and changes only the url to another loopback port (one it serves itself) has a proven record, so `forge dash`, `forge daemon status` and `forge update` show that url. So the worst a forged record can do is name the running `forge dash` and point at any loopback port. Binding the url to the process (an HTTP handshake) is out of scope.
  - Anything else is stale: its pid is never signalled and its url never printed. `forge dash` (`--stop`, the running answer, the `--dev` refusal), `forge daemon status` and `forge update` read it only through this check; `forge dash --background` accepts its own child's record when the pid is that child's and the url passes rule 5; notifications use only rule 5, because they build a link and signal nothing. On native Windows no record is proven, since there is no start-time probe. Stopping the write itself is a separate layer: the daemon's deny rules over `.forge/runtime/**` (#382).
- **The logs** (`daemons/<scope>.log`) live in gitignored `.forge/runtime/`; they hold whatever the sessions printed, so treat them like transcripts. The dashboard renders every log string as text, and `forge daemon log` escapes control characters so session output can't drive the terminal.
