# Daemon security › Permissions

Part of [Daemon security](../daemon-security.md).

- **Permission prompts are answered from the dashboard only.** Every daemon command ends with `--permission-prompt-tool stdio`, so claude sends each call it would ask a person about to the supervisor as a `control_request`. The supervisor holds it in memory (never in a file the session could edit), shows it in `/api/state`, and answers when a human posts `POST /api/daemon/permission` with the token, a matching Origin and JSON. The body names a scope, the supervisor's uuid for the prompt and a decision (`allow`, `session` or `deny`); the reply is built from claude's own request: an allow echoes its input unchanged, a deny carries fixed text, and "allow for this session" grants only the allow rules and absolute directories claude suggested, rewritten to the `session` destination, so suggestions to save rules to a settings file or change the permission mode are dropped.
  - There is no CLI command to answer a prompt, because the session itself runs `forge`. Prompts end with their child, at most 20 wait per session, a request whose `request_id` is already waiting is ignored (a repeated id must not swap the input an allow runs), and any other control request subtype gets an error so claude never hangs. What a prompt shows (the input, the agent's description, the blocked path) is session output and renders as text. A prompt is exactly as safe as the human reading it: the tool, its full input and any blocked path are shown, and the agent's description is labelled as its own words.
  - With `daemon.permissionTimeoutMinutes` set, a prompt nobody answers within it gets a fixed timeout deny (`TIMEOUT_DENIED`, which says no human saw the call and asks the agent to reply `NEEDS-PERMISSION` if it can't finish without it): the timer (`lib/office/session/permissions/control.ts`), read from the config when the prompt is asked, only ever denies, never allows, and only a prompt still pending from the session's current child; a human's answer, claude's cancel, the child's exit or the session's close clears it first, so a prompt is answered at most once.
  - The session log records `permission … reason: timeout` with no actor, the denied prompt joins the session's in-memory timed-out history (the last 10, shown in the dashboard as text with no buttons), and a job session's job gets a `permission-timed-out` event carrying only the tool name, `unknown` when it fails `SAFE_TOOL`, never the input or description. When a planner, spec writer, builder or integrator replies `NEEDS-PERMISSION` with such an event inside its run, `forge job step` (NP1b) parks the job on `escalation`, a gate that stops work and grants nothing; the Foreman may decide that park like any escalation, but it never answers a prompt: no route or capability lets anything but `POST /api/daemon/permission` with the token answer one.
  - Each answer sent is also appended to the prompt history (`.forge/runtime/permission-prompts.jsonl`, `lib/office/session/permissions/history.ts`), which holds only the scope, tool, the suggested rules that are printable ASCII, the decision and its reason, never the input, description, blocked path or folders; but a rule is claude's own pattern and can be most of the command, so a rule that holds a value `scopeKnownValues` names for the session (what its log redacts) is left out before it is written, and with those values unreadable no rule is kept.
  - `forge daemon prompts` re-checks every line as untrusted and only reads it, suggesting rules that were never denied (in the whole window it reads, whatever `--since` says), pass `daemon.allowedTools` validation, don't start a shell, interpreter, exec wrapper, package-runner `exec`, fetcher or file writer, and name no path outside the roots it can prove (a file rule's: the checkout and the worktrees roots; a Bash rule's: the worktrees roots), for a human to add by hand. That is a filter, not a proof: both lists are known forms, a trailing `:*` lets any later argument name any path, and a deny older than the newest 1-2 MiB, or pushed out by lines a human-allowed Bash call wrote, is forgotten. Residual, documented: the human reads every suggestion before adding it.
- **Permission mode is a human's choice, held in memory.** `POST /api/daemon/mode` (token, matching Origin, JSON) names a scope (validated, and a job must have a `job.json`) and one of `default`, `auto` or `dontAsk` (lib/integrations/claude/argv.ts `PERMISSION_MODES`); anything else is a 400. The pool keeps the choice in memory only: session records live in `.forge/runtime/`, which the session can write, so a mode read back from disk would be one the session could choose for itself. A running child gets a `set_permission_mode` control request; a later spawn gets `--permission-mode <mode>` in place of the template's.
  - Until claude reports its mode (at its first turn's init) the supervisor takes the one the child was launched with. A switch claude refuses or doesn't confirm fails closed: a narrowing one stops the child, so the next spawn starts in the chosen mode, and a widening one leaves the choice at what the child still reports. `auto` stays refused in `daemon.command`, so a repo's config can't put every session on every machine that runs `forge dash` into it: only a human at the dashboard can, for one session, until that `forge dash` stops. In `auto`, Claude Code's classifier approves calls outside `allowedTools` without a human, so a misled agent's call may run unread; the deny rules, the trust check and the git pins below still hold. `bypassPermissions` is never offered, and claude refuses it on a session not launched with `--dangerously-skip-permissions`, which validation forbids.
  - The same POST with scope `_jobs` sets the default for every job session without its own choice, also in memory only; the inbox and the chats never take it, and an office or gate run's model child always runs in `dontAsk`. A chat launches in `default` even when `daemon.command` names another mode, until its owner chooses one for it.
  - `forge dash --permission-mode` sets the run's launch mode: every job and inbox session of every project it loads starts in it (and the `_jobs` default starts at it) unless a human chose another for that session. It is the human's own command line, refused when `FORGE_DAEMON=1`, so a session can't start a second dashboard with it, and it is never read back from the dashboard record. The flag now reaches the inbox, which reads tracker text: in Auto, a call that text misleads it into runs unread, so a launch in Auto trusts that input as well as every job's. There is no CLI command to switch a running dashboard's modes, for the same reason there is none to answer a prompt.
  - **Auto on one session reaches the whole daemon.** A same-user process can read the dashboard's login file (`forge dash url` refuses a daemon session, but the file is the owner's) and a non-browser client can send any Origin, so a session whose calls run without a human (Auto, or one a human allowed `curl` to) can read the token and post to `/api/daemon/mode` or `/api/daemon/permission`: switch other sessions to Auto, make Auto the job sessions' default (`_jobs`, which also reaches jobs created later), or answer their prompts and its own. A session that only runs what `allowedTools` lists can't: no `forge` command posts to these routes, and `forge dash --permission-mode` refuses a daemon session. Nothing on loopback tells the page apart from a session's process, so treat putting any session in Auto as trusting every session's input.
- **Effort is a human's per-job setting, read back from `job.json`.** The level reaches argv only as one word from the fixed list (`EFFORTS` in `lib/core/job/schema.ts`), and never stdin. `normalizeJob` reads anything else in `job.json` as null and `buildArgv` ignores a value outside the list, so a hand- or session-written `"--dangerously-skip-permissions"` or `"high --add-dir /"` never becomes an option. An invalid `runtime.effort` is a `daemonProblems` refusal, so no session starts. `withEffort` drops every `--effort` and `--effort=` in `daemon.command`, so a duplicate can't win over Forge's.
  - `forge job set --field effort=…` is refused, and `forge job effort` and `forge job new --effort` refuse under `FORGE_DAEMON=1`, so a misled session can't raise its own or another job's level through the CLI. `POST /api/jobs/:id/effort` takes the token, a matching Origin and JSON, an existing job id and a value from the list or null.
  - Residual risk: in a job that predates the CLI copy, a session can still write a valid level into its own `job.json`, as it can `budget.limits` (the deny tail and the write guard refuse the file tools; a newer job's folder copy is ignored). That costs tokens and time, bounded by `pipeline.budget` and visible in the session log's `effort` event and the card chip, and it never widens what the session may do. `complexity` is session-writable through `forge job set --field`, but only as `low`, `medium`, `high` or null, and it only selects among levels a human configured in `runtime.effortByComplexity`, which never reaches a session's argv. That is why, unlike the permission mode, effort is read back from disk: it is a human's setting that must survive a `forge dash` restart.
- **Narrow permissions, still not a sandbox.** Anything `allowedTools` doesn't list is asked about (or refused under `dontAsk`), and subagents inherit the list. The default allows Bash only for `forge` and specific git/gh subcommands (rev-parse, merge/rebase `--abort`; `gh pr view|list|checks`, `gh run view`).
  - The session's cwd is the main checkout and `cd` and `git -C` aren't allowed, so a bare `git add`/`git commit` would act on the base branch: agents stage and commit through `forge git add|commit <job>`, which runs git with the job's worktree as cwd (refusing the main checkout, a branch other than the job's, and a merge or rebase in progress for `commit`), takes only `--message`/`--message-file` (a file inside the job dir) and paths, so no `-c`, `-C`, `--git-dir`, `--amend`, `--no-verify` or `--author`, refuses paths outside the worktree or in a `.git`, checks the message for AI attribution, clears `GIT_DIR`-style variables, and under `FORGE_DAEMON=1` runs git with the session pins below (outside the daemon, a human's hooks run). Claude Code matches each part of a compound command against the rules and won't match past `git -c` or an env assignment, so `git -c core.sshCommand=…`, `git -c alias.x='!…'` and `FOO=… git …` are refused.
  - `git diff|log|show|range-diff` are left out because `--output=<file>` writes wherever git can, and Claude Code's protected-path check covers its own file tools, not git: `git log --format=… --output=.git/config` would plant a textconv or filter driver that the next diff or add runs. Agents read history through `forge git`, which refuses `--output` (git accepts no abbreviation of it), `--ext-diff`, `--textconv` and `--open-files-in-pager`, and forces `--no-ext-diff --no-textconv`.
  - `git rebase` is left out because `--exec` runs shell: the integrator starts merges and rebases with `forge integrate --keep-conflicts` and finishes them with `forge integrate --continue`, which refuses a rebase todo holding anything but picks. `git mv` is left out too: given a `x/../.git/config` destination it reports an invalid path, then renames the file anyway and exits 0. `gh api` and other GitHub writes are left out; Forge's own writes (push, PR, labels, comments) go through `forge`. Validation refuses `allowedTools` entries that undo this (unscoped `Bash`, bare `git`/`gh`, `git -…`, `git config|grep|submodule|bisect|…`, `git diff|log|show|range-diff|…`, `git mv`, `git rebase`, `gh api|extension|alias|auth|…`); the list catches known forms and is not exhaustive.
- **Git hooks are off in the session and in the periodic sync.** A repo can point `core.hooksPath` at a tracked directory (`.githooks/`, unlike `.git/` and `.husky/`, isn't one of Claude Code's protected paths), so a hook written there would run on the next `git commit`, on a `forge pr open` push, or on the `reference-transaction` of a fetch. An in-checkout hooks directory is in the deny tail and the confine digest, and a worktree's is reviewed with the job's diff.
  - The daemon also spawns the session with `core.hooksPath=/dev/null` and `core.fsmonitor=false` in `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n`, which outrank every config file and are inherited by subagents, `forge` and verify commands. `forge dash`'s periodic `forge sync` child runs with `SYNC_PINS` (`lib/integrations/git/runner.ts`): the same two, plus `core.pager=cat`, `diff.external=/dev/null` and `gpg.program=gpg` (git's own default, so a user's signed merges keep working), appended after any `GIT_CONFIG_*` the caller exports; `credential.helper` is never pinned. The cost: no hooks at all in daemon mode, including Git LFS's pre-push upload.
  - Not pinned in the session: filter, diff and merge drivers and `gpg.program`, which only `.git/config` or `~/.gitconfig` can define. The session has no allowed way to write `.git/` (Claude Code's file tools treat it as protected, so only a human's answer to a prompt could allow it, the write guard refuses any `.git` segment inside a worktree, including a worktree's `.git` file, and the git forms it may run take no output path), but anything the human or another tool puts there still applies. What remains broad is what the session writes inside its write roots: worktree files that build and test tooling executes, which verify runs and the review panel reads. Enable the daemon only on repos whose tracker input you trust (or with intake restricted, e.g. `tracker.github.comments: collaborators` and ready labels only maintainers set).
