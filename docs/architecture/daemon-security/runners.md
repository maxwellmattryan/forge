# Daemon security › Runners

Part of [Daemon security](../daemon-security.md).

## The intake runner
**The intake runner answers inbox requests with fixed CLI calls, and its triage child writes one batch dir.** With the daemon on, no claude session reads the inbox's requests or tracker titles any more ([Daemon](../daemon.md) › Intake runner). Its attackers are: (1) tracker item text, which now reaches only the triage child; (2) a request file whose args a local process or a dashboard user wrote to inject options or paths into a `forge` argv; (3) a hostile checkout or a background agent changing trusted files mid-run; (4) the triage child, misled by `items.md`, trying to write outside its batch, run a command or load the branch's settings; (5) the fallback inbox session's exit releasing what the runner holds.

The defences, each tried by a test:
- an option-shaped value (`--now`, `--set …`, `--force`) only ever becomes one `--flag=<value>` word or follows `--`, a run's ref may not start with `-`, a retro's mandate must be a mandate id, and eval values are capped and free of control characters;
- a traversal or non-id job (`../x`) is rejected by `validJobId` before any argv or path is built, and a job id from a child's output must pass it before a later call;
- every call is its own `bin/forge` child in the `_inbox` scope with the pool's `FORGE_DAEMON_TRUST`, so `refuseInboxDrive`, `refuseDaemonMerge`, the `--set` refusal and the trust check apply, and `checkLaunch` runs before each request;
- the triage child gets `--tools Read,Write` (no Bash), `--setting-sources ''`, `--strict-mcp-config` and `--disable-slash-commands`, one `Edit(//<batch dir>/**)` allow rule under `dontAsk`, the write guard's roots set to the real `.forge/runtime/triage` (a link there that leads out of the checkout skips the spawn), and every absolute protected-path deny rule but `.forge/runtime/**` (whose rule would deny the verdicts file it must write, since deny beats allow), and after it exits the confine digest is compared with the pool's baseline: a change stops the pool and `--apply` never runs;
- the intake session id is among the inbox's ids (`inboxSessionIds`, `daemonSessionIds`) but never a session record's (`recordIds`), so the fallback session's exit lets go of nothing the runner holds;
- acks and log lines carry only job ids, counts and Forge's own error text, and the triage reply only as one `TRIAGE:` line of at most 200 characters.

Its cost is metered to `meter/_inbox.jsonl` under `daemon.dailyUsd.inbox`, checked before the spawn. Residual risk: the triage agent may Read any file, as the subagent could; what it writes is validated by `--apply`.

## Role runs
**Role runs are confined as a job session's subagents are, without a person to ask.** `forge job agent run` ([Daemon runtime](../daemon-runtime.md) › Role runs) starts one role as its own `claude -p --agent forge:<role>` child whose cwd is the job's worktree, not the main checkout, and which runs unattended with Bash and file tools. Its attackers are the role agent itself, steered by tracker or PR text in its inputs, a stale or foreign caller of the command, and the agent-writable `job.json` fields `worktree` and `agentId`.

- *Writes to the main checkout's trusted files from a worktree cwd*: the relative `DENY_TOOLS` would anchor at the worktree (denying the branch's own `.forge/notes/**` and `**/CLAUDE.md` while leaving the checkout's open), so the child's `--disallowedTools` holds only the absolute rules (`absoluteDenyRules`: every `DENY_TOOLS` entry anchored at the checkout's realpath and the path as given, the root's `CLAUDE.md`, `CLAUDE.local.md` and `AGENTS.md`, and every instruction file), and `roleArgv` throws on any rule without `//`.
- *The branch's own Claude Code config loaded as trusted*: a worktree is a branch's checkout of files agents write, and `claude -p` skips the workspace-trust prompt, so a child started there would load the worktree's `CLAUDE.md` and `CLAUDE.local.md` as instructions every later role reads, the hooks (shell, outside the write guard), `permissions.allow` (wider than `daemon.allowedTools`), `env` and `apiKeyHelper` of its `.claude/settings*.json`, its `.claude/skills` and `commands`, and its `.mcp.json`; `roleArgv` passes the literal `--setting-sources ''` (no setting source, and no input can choose another), `--strict-mcp-config` and `--disable-slash-commands`, so only the `--plugin-dir` plugin and managed settings load: neither the branch's settings nor the user's plugins, hooks and MCP servers, and a role reads the repo's instruction files from the main checkout because its brief says to.
- *More tools than the role needs*: `--tools` is the agent's own `tools:` frontmatter (`agentTools`), built-in names only: each must match `^[A-Z][A-Za-z]+$`, so no name becomes a flag, a second word or an MCP grant, and an agent without the list refuses the run before anything is written. No role gets `Agent`, `Skill`, `WebFetch`, `WebSearch` or `NotebookEdit`.

### The browser
- *The browser*: Forge's own `forge-browser` server (lib/integrations/claude/browser.ts) is passed with `--mcp-config` only to the builder, the designer and a `ui`, `ux`, `accessibility` or `design` reviewer, while the spec has a UI AC and the job has a port, and its named page tools (`BROWSER_ALLOWED`: navigate, snapshot, screenshot, click, type, fill, hover, key, select, resize, wait, console, network, tabs, dialog, close) are then allowed in `--allowedTools`, since no one can answer the child's prompt.
  - Never the server-wide `mcp__forge-browser` rule: Playwright MCP also ships `browser_run_code_unsafe`, which its README calls RCE-equivalent (arbitrary JavaScript in the server's own process, outside every write root, deny rule and hook, in the session's environment, leaving no file in the job's diff). That tool is in `--disallowedTools` (`BROWSER_DENIED`) for every session that gets the server, role child or job session, so nobody is asked about it and Auto's classifier never decides it; any other tool outside the list (`browser_evaluate`, `browser_file_upload`, `browser_install`) prompts, and with no one there is denied. The server's JSON is one argv word built from an integer port, Forge paths and the session's PATH, followed by a flag, so claude's variadic `--mcp-config` can't swallow a later word.
- *What starts the server*: `command` is an absolute `npx` found only in absolute PATH entries, and the server's own `env.PATH` is that same PATH, so a planted `./npx` on a relative or empty entry is never run and `env node` can't find one either (no such `npx` means no browser); `npx` runs with `--prefix .forge/runtime/browser`, a real empty directory outside every write root, so npm reads no project `.npmrc` (a branch-written one can set `registry`, `script-shell` and `node-options`, among others) and finds no `@playwright/mcp` in the worktree's `node_modules`; the user's own npm config still applies. It runs `--headless --isolated` (no profile or cookies) with `--allowed-origins` set to the job's two loopback origins.
  - Residuals, documented, not fixed: Playwright's origin filter is not a hard sandbox (redirects and non-HTTP schemes are the vendor's to block); the server runs with the session's environment (`sessionEnv`: API keys and provider switches dropped, the rest kept), not `commandEnv`'s allowlist; the package is fetched from npm at first use, pinned to one exact version, and kept in the user's `~/.npm/_npx` cache for later sessions;
  - `--output-dir` (the job's `screenshots` dir) covers only automatically named files, while a tool's `filename` (screenshot, snapshot, console messages, network requests) is resolved against the workspace root, the worktree for a role child and the main checkout for a job session, and written by the server, not by a file tool, so the write guard and the deny tail never see it (Playwright refuses paths outside the workspace root unless told otherwise, and Forge doesn't tell it; in a job session the call is a prompt, in Auto the classifier decides, and the confine digest after the turn covers the protected set).
  - A job session gets the same server under the same spec and port rule (`sessionBrowser`), but its browser calls stay per-call dashboard prompts; the inbox and chat sessions and the office and gate runs never get it.

### The system prompt
- *Agent-written text in the system prompt*: the child's `--append-system-prompt-file` is the trusted prefix (lib/engine/guard/prompt-prefix.ts), whose sources are fixed: the main checkout's `project.instructions` files for the role, `.forge/notes/learnings.md` and `.forge/notes/<role>.md`, never a brief, job file, checklist or PR text. A source that is a symlink (say `.forge/notes/learnings.md` linked to a job's `request.md`), a directory or FIFO (read with `O_NONBLOCK`, so it can't hang the runner), larger than 256 KiB, or reached through a linked parent directory is refused, as is an instruction entry under `.forge/` or under a write root (a job folder, a worktrees root nested in the checkout), and a prefix over 256 KiB. Every source is under the trust digest, so under `FORGE_DAEMON=1` the start refuses a digest that moved, and a source edited during the run fails it `untrusted`.
  - The file lives in `.forge/runtime/prompt-prefix/`, outside every write root and under the runtime deny rule, named by the sha256 of its bytes; it is reused only when a regular file there holds exactly those bytes, and otherwise replaced atomically, so a planted file or link at the name is replaced, never followed. `roleArgv` takes only an absolute path with no NUL, CR or LF there. Any refusal starts the run as before, with no flag, the brief unchanged and `prefixRefused` in the JSON: the agent then reads the same files as data-labelled paths, which is today's baseline.
  - Residual: a Bash route into `.forge/runtime/` outside `daemon.allowedTools`, which prompts and is denied unattended, as for every runtime file. Node has no `openat` (as `confinedDir` notes), so a source's parent directory swapped for a link between the parent check and the open, or a source changed and restored between the start digest and the prefix build, is not caught; both need write access to main-checkout paths that no role child can write.

### Paths, calls and trusted files
- *A symlink or `../` path*: the write guard gets the same `FORGE_DAEMON=1` and `FORGE_DAEMON_WRITE_ROOTS`.
- *A steered root or cwd*: `FORGE_ROOT` is pinned to the main checkout, as the pool pins it for every session, and the child starts at the realpath of the worktree that was checked, not at `job.worktree` again.
- *A Bash or other unapproved call*: it prompts, and with no one there `runRoleChild` denies it with the fixed `UNATTENDED_DENIED` text, which tells the agent not to retry or work around the call and to record what it needed in its output file; the run log gets a `forge-permission` line.
- *A trusted file changed anyway*: the child's own `forge` calls refuse through `FORGE_DAEMON_TRUST`, and the runner recomputes the trust digest and the confine digest after the child exits and fails the run as `untrusted` if either moved. The confine digest is the one a session's turns are held to (`git status` and content over the protected set, every `CLAUDE.md` and `CLAUDE.local.md` at any depth, the instruction files, an in-checkout `core.hooksPath` dir), so a nested `lib/CLAUDE.md` or a `.husky/` hook changed through Bash is caught too.
- *Starting a role step did not choose*: the lease hold, the epoch fence and step re-run under the job lock before the start; and under `FORGE_DAEMON=1` only the job's own session may run it, since the child carries that job's own scope (`forge pr merge`, repo proposals, downstream), which no other session may mint.
- *Option injection through argv*: `model`, `effort` and `agent` are validated or dropped, session ids must be uuids, the prefix file must be an absolute path, and the brief goes to stdin as one JSON-escaped line, never argv.

### Planted ids and context sessions
- *A planted `worktree`*: `jobWorktreeProblem`, and the worktree must lie under a worktrees root.
- *A planted `agentId` reaching another session's transcript*: only a uuid is tried as a session file, only at the job's own worktree slug (never the root's), confined and never through a link.
- *A planted `agentId` that makes a rework resume continue another role's conversation* (say, the security lens resuming the builder's session): a rework resume needs the runner's sidecar for that session, outside every write root, to name the same role (`role` in `<session>.json`, written by the runner after every result), so a planted id gets `no session` and runs as it would have; the uuid check comes before the sidecar path or the transcript lookup is built, and the skip reason reaches the start line only as one of step's fixed `RESUME_SKIPS`, which `forge job agent start --resume-skipped` checks again.
- *Billing past the login*: `sessionEnv` drops API keys and provider switches unless `daemon.auth` is `api-key`.
- *A context session's fork under another agent*: a review or rework build may fork a **context session** that read the round's shared inputs first ([Daemon runtime](../daemon-runtime.md) › Role runs). Its key binds the round, agent, model, effort and trusted prefix file, so a fork's `--agent`, `--model`, `--effort` and `--append-system-prompt-file` always equal the context's: a reviewer never runs on a builder's system prompt, and a builder's tool list never leaks into a reviewer.
  - The context child and the fork take the spawn's own `roleArgv`, so both are confined exactly as a cold run (same permission mode, allowed tools, write roots, deny rules, env and cwd), and the runner recomputes the trust and confine digests right after the context child exits: a context that moved a trusted or protected file is recorded failed `untrusted`, so no lens forks it, and the launching role fails `untrusted` without starting.
  - A context is also ready only when its main loop called no tool but `Read` no call was denied and no stdout line was dropped unread (too long, not JSON or a protocol error: one could have held a tool call the check never saw), judged from the stream's `tool-use`, `line-too-long`, `unreadable-line` and `protocol-error` events, since its turns become the prior turns of every fork.
- *A forged context id*: `contexts` is a locked `job.json` field (`forge job agent run` only), the CLI copy sits under `Edit(.forge/runtime/**)`, and `roleArgv` takes only a uuid for `--resume`.

Residuals: the run has no `--max-budget-usd` cap and no lease heartbeat past `AGENT_LEASE_MS` (2 h), and a Bash route to a trusted file is caught after the run, not before.

## The code driver
**The code driver adds no input a session didn't have.** Under `daemon.driver: code` ([Daemon runtime](../daemon-runtime.md) › Code driver) forge dash drives a job's resumes itself: `forge job claim`, `forge job advance`, `forge job agent run --role R --ipc`, `forge job agent end` and `forge job set` run as children with a job session's env (`sessionEnv`, the confinement env, `FORGE_DAEMON_TRUST` from the pool's snapshot, the job's own `FORGE_DAEMON_SCOPE`), argv arrays and no shell, each after the launch checks a session's spawn passes, so a moved trusted file stops the pool before the next child. Its attackers are a role agent steered by tracker or PR text (running with `Bash(forge:*)` and file tools under the job's scope env), a stale or foreign driver (a human's terminal, the fallback session), untrusted text (command output, stderr, agent summaries, tool inputs) on its way to the driver's argv or the dashboard, and a hand-edited session record. Each bypass is closed.

- *A role agent answering its own prompt*: the role child's env never holds `NODE_CHANNEL_FD` or `NODE_CHANNEL_SERIALIZATION_MODE` and it gets no IPC fd, so only the runner talks to the driver, and `--ipc` without a channel is refused before anything is read.
- *A role step did not choose*: `--role` picks only from step's current `[action, ...spawns]`, under the same epoch fence and step re-run as `--spawn-index`, and adds no mode or tool flag.
- *Option injection through a park reason or a lost summary*: built from child output only as `code driver: <what>: <detail>`, one line (control characters, line separators and backticks dropped) of at most 200 characters, passed only in the joined `--reason=`/`--summary=` form.
- *A malformed or hostile IPC message*: every field is checked by type and length (ids and tools at most 200 characters, the input at most `PROMPT_INPUT_CHARS`, rules and directories string lists) and anything else is dropped; an answer for an unknown request id matches nothing; an answer goes only to the runner that asked.
- *A prompt the dashboard can't show whole*: the session prompt policy's caps and unasked denies apply (20 waiting, an input that can't be shown whole or is too large, an unusable tool name), so it is denied, never allowed.
- *A trusted or protected file changed mid-turn*: the launch checks before every child, and a runner's `untrusted` end stops the pool.
- *A planted `driverId`*: only a uuid is read back; anything else is replaced, and a session release never passes it (`recordIds` excludes it), so only the driver's own end or a pool boot lets its lease go.
- *A stale runner writing after a takeover*: the start and end are fenced by epoch, and advance's exit 3 ends the turn and stops the live runners.
- *Orphans after a crash*: a runner whose channel disconnects interrupts its role child, a runner that dies by a signal has its reported role child's group killed by the driver, and a pool boot releases the driver's lease.

Residuals: role children run in `daemon.command`'s permission mode, not the Workers popover's; a role run has no dollar cap of its own beyond the job's budget; the IPC channel is as trusted as the runner process, which is Forge's own code.
