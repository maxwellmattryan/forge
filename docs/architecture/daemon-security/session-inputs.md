# Daemon security › Session inputs

Part of [Daemon security](../daemon-security.md).

- **One fixed stdin turn.** Every session gets only `TURN_LINE` (`/forge requests`) as a message. The only other stdin lines answer claude's own `can_use_tool` permission requests ("Permission prompts" in [Permissions](permissions.md)), carrying nothing from HTTP but the decision, or ask claude to switch permission mode ("Permission mode" in [Permissions](permissions.md)), carrying one value from a fixed list. A fourth, an error reply to a control request forge does not handle, repeats only the first 40 characters of claude's own subtype back to claude.
  - All of them are built in `lib/integrations/claude/stream.ts`, which exposes two writes that take free text. The first is a role run's or a gate run's brief (`writeBrief`, built by `briefLine`), sent once as the child's first message: by `runRoleChild` from `forge job step`'s brief (its `Instructions:` line swapped for the fixed `PREFIX_INSTRUCTIONS_LINE` when the run has a trusted prefix), or by the gate runner (lib/office/foreman/attempt.ts) from the assist brief the CLI built, and never by a pool session ("Role runs" in [Runners](runners.md)). A gate run's child may also be sent the one fixed verdict retry (`VERDICT_RETRY_LINE`).
  - The second: in a chat session (scope `_chat-<id>`), the owner's own message goes to stdin as one stream-json user line (`writeMessage`, built by `chatMessageLine` with `JSON.stringify`, so newlines and an embedded control line stay inside the one text). Only `Session.writeChat` calls it, only in a chat scope, and only from the pool's `sendChat` (lib/office/chat/send.ts), which `POST /api/p/<project>/chats/<id>/messages` reaches ([Chats](chats.md)).
  - For every other scope the supervisor can only ask for the turn, pick a decision for a request claude itself sent, or name a mode. Request text, request and job ids, config values and HTTP bodies never reach stdin; the session reads requests through `forge requests`, where the skill treats them as the human's words about one job, never as rules. Free text from the dashboard's command bar (`POST /api/jobs`) is written only to the new job's `request.md` (and, through the derived title, `job.json` and `events.jsonl`); the `resume` queued for it carries no text.
- **The scope travels in the environment only, validated.** A session learns its scope from `FORGE_DAEMON_SCOPE`, set by the supervisor from a routed request whose job id matched `^[A-Za-z0-9][A-Za-z0-9._-]*$` (at most 200 characters) and has a `job.json`; anything else routes to `_inbox`, which can't be a job id. Under `FORGE_DAEMON=1`, `forge requests list|claim|ack|scope|add` refuse a missing or invalid scope, list only that scope's requests, refuse to claim or ack a request that doesn't exist or belongs to another scope, and queue only `resume` hand-offs. These keep a session that follows the skill in its lane; they are not authentication (see ["Untrusted input"](../untrusted-input/imported-text.md)). Request ids are checked against their `<time>-<id>` format before any path is built from them. Runtime file paths are built only from validated scopes.
- **argv comes from the repo's config, with no shell.** `daemon.command` is split into words and run directly, and placeholders expand to single arguments. Nothing from HTTP or requests reaches argv. A chat session's spawn alone also gets `--append-system-prompt` with the fixed `CHAT_PROMPT` (lib/office/session/launch.ts), before the deny tail. A session id read back from a session record or a child's `system`/`init` must be a uuid before it can follow `--resume`, so a planted value can't become a flag.
- **Trust boundary: `.forge/config.yml` is code.** Whoever can change it can run code through the daemon, exactly as through `commands.*` (which verify runs through a shell): validation refuses the claude flags that widen permissions (`--dangerously-skip-permissions`, `--permission-mode bypassPermissions`, `--settings`, `--mcp-config`, `--add-dir`, `--agents`, a second `--plugin-dir`, a literal `--allowedTools`; docs/CONFIG.md "Daemon" has the full list), but the session still runs `commands.*` through `forge run`/`forge verify`, and `daemon.enabled: true` in committed config starts an unattended, paid session on every machine that runs `forge dash`.
  - The config is read from the main checkout only, never from a job worktree or a PR branch, but a merged change applies everywhere. Give `daemon.command`, `daemon.allowedTools` and `daemon.enabled` code-owner review, like CI config. The session itself can't use this route (next bullet).
  - The default `daemon.command` passes `--setting-sources project,local --strict-mcp-config`, so the user's settings, plugins, hooks, MCP servers and claude.ai connectors no longer load in default sessions: none of them is Forge's, and each would otherwise run inside a session that reads tracker and PR text (another plugin's hook on every tool call, a chat connector reachable from a misled call). The main checkout's `.claude/settings*.json`, managed settings and `--plugin-dir {pluginRoot}` still apply. `--setting-sources` may name only `user`, `project` and `local`, and `forge doctor`'s `daemon isolation` row warns while an enabled daemon's command lacks either flag or names `user`; an existing command is not migrated.
  - The validator's rule that the first word is a bare `claude` or an absolute path to `claude` outside the repo catches mistakes (a migrated shell template, a relative path that would run a repo file); it is not a security boundary.
  - Configured commands run without the `FORGE_DAEMON*` markers: the trust check guards the session's own `forge` calls, and a command's nested `forge` call against a scratch repo (a test suite) must not be judged by it. A command can run any code anyway, so that check never bound it. The git pins ("Git hooks are off" in [Permissions](permissions.md)) still apply to commands. So the marker proves less than it seems: it keeps a session in its lane, but a process without it is not thereby a person. Branch code that a session's `forge verify` runs has no marker, which is why the [human-only operations](human-only-operations.md) take their go-ahead from a channel, not from the marker's absence.
- **Configured commands get an allowlisted environment and no login shell, in every mode.** The session can't change `commands.*`, but it can `Edit` a test and run `forge verify`, which executes that code before any reviewer reads it, with whatever environment Forge passes. So every spawn site of a configured command (`forge run`, verify steps, worktree setup, `forge run --background`, config-sink commands, job database builds, checkout steps, `forge integrate`'s rebuild, the eval check and `notify.command`) builds its environment with `commandEnv` and its argv with `commandShell` (`lib/engine/guard/command-env.ts`), and neither reads `FORGE_DAEMON`.
  - `commandEnv` passes only an allowlist (fixed names such as `PATH`, `HOME`, `LANG` and the git pins; the `LC_*`, `NODE_*` but `NODE_OPTIONS`, `FORGE_*` and `GIT_CONFIG_KEY_<n>`/`VALUE_<n>` families, never a credential-like name; and what `commandEnv.inherit` names, where a glob never passes a credential-like name either), so a credential under a name nobody listed (`CORP_SESSION_BLOB`) is dropped too. It never passes the daemon markers, an outer job's `FORGE_PORT_*`/`FORGE_ENDPOINT_*`/`FORGE_BACKING_*`, `FORGE_COMMAND_PATH*` or the source variable of a declared `env` secret, whatever `inherit` says; names fold on Windows.
  - `commandShell` runs `/bin/sh -c`, so no login profile, `.zshenv`, `BASH_ENV` or `ENV` puts back what the allowlist dropped, unless `commandEnv.loginShell: true` asks for `$SHELL -lc`. Both keys sit in `.forge/config.yml`, which is a protected path, in the deny tail and in the trust digest, and are read-only in Settings. PATH is the one `forge dash` captured from the login shell at start (`FORGE_COMMAND_PATH`, held only in the dashboard process's environment and its children's, never in a file), else Forge's own, with relative and empty entries removed so the worktree can't plant a binary on it.
  - The job's own variables, sink env and link env are added afterwards and never filtered. A command's child sees no marker, so a nested `forge` behaves as a human's. What this does not stop: code that reads the human's files (`~/.aws/credentials`, `~/.npmrc`, `~/.config/gh/hosts.yml`, a shell profile) or starts its own login shell, and a name a human put in `inherit` exactly. `forge release run` keeps its caller's environment and `$SHELL -lc` (refused under the daemon; its publish steps need registry credentials), and Forge's own tool calls (git, gh, docker, the secret tools) keep the Forge process's.
