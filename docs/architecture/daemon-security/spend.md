# Daemon security › Spend

Part of [Daemon security](../daemon-security.md).

- **Spend caps under the daemon.** A session misled by request, tracker or PR text could try to spend more than a person allowed; four things bound it.
  - *The backstop holds per key*: with the daemon on, `daemon.jobBudget` fills each of `tokens`, `usd` and `minutes` that config and the job's own overrides leave unset (`effectiveLimits` in `lib/engine/metrics/budget.ts`), so setting one key never drops the others; only a person's explicit per-job `null` (a confirmed terminal or the dashboard, in [Human-only operations](human-only-operations.md)) lifts a key.
  - *The budget field is locked*: `budget` is in `LOCKED_FIELDS` (`lib/core/job/fields.ts`), so `forge job set --field budget…` (any path under it, or the whole object) is refused for every caller.
  - *A dollar cap per spawn*: every job session's child gets `--max-budget-usd`, the job's remaining dollars recomputed at each spawn (`lib/office/session/budget-cap.ts`); `buildArgv` drops any `--max-budget-usd` in `daemon.command` and validation refuses one, and a `result` with `subtype: error_max_budget_usd` stops the session at once rather than being retried as a quota limit. The figure is the job's metered spend, with the resumed conversation's baseline added back (below).
  - *Provider switches are scrubbed*: under `daemon.auth: subscription`, `sessionEnv` drops `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `CLAUDE_CODE_USE_FOUNDRY` and `ANTHROPIC_BASE_URL` with the API keys, so a variable inherited from the process environment can't bill another account or route through a proxy; `forge doctor` and the Workers popover name any that are set.
  - Residuals: a session with arbitrary shell could read the login file and POST the budget route itself (`daemon.allowedTools` grants no `curl`, so that is a prompt a person sees); `reconcile.json`'s resume count sits under `.forge/runtime/`, which the deny tail covers for file tools but a Bash write could reset; and variables set in claude's own settings files (the `env` block and `apiKeyHelper` in `~/.claude/settings.json` or managed settings) are not scrubbed or reported, so a `CLAUDE_CODE_USE_BEDROCK` or `ANTHROPIC_BASE_URL` set there still reaches a subscription session.
- **Metered spend.** A budget that trusts the session it bounds is not a budget, so enforcement reads what the supervisor measured, not what the session reports. claude's own `result` line feeds it (`total_cost_usd`, `modelUsage`), and only the supervisor in `forge dash` writes `.forge/runtime/meter/<scope>.jsonl`; no CLI command does ("Metered spend" in [Policies](../policies.md)). Each bypass a misled session might try is closed.
  - *Under-reporting or skipping `--import`*: a job's enforced spend is never below its meter or its reported total.
  - *Small `--tokens`, `--tool-uses` or `--duration-ms`*: refused in a daemon session.
  - *Ending agents without an id*: refused unless `--status lost`, or recorded `unmeasured`, and the meter still holds the cost.
  - *Editing `events.jsonl` to claim covered runs*: the job folder's copy is a mirror Forge never reads, and covered usage in the CLI copy is clamped to the reported total, so it can't push the figure below either.
  - *Forcing respawns or forks so the cumulative resets or repeats*: deltas are per spawn against a resumed baseline, with reset and rebase handling.
  - *A planted symlink or FIFO at the meter path*: refused, never followed, by the writer and the reader; `Edit(.forge/runtime/**)` in `DENY_TOOLS` and the write guard already keep file tools out.
  - *Spending outside any job*: the inbox, forge dash's office runs with its gate runs (one cap, the `_office` and `_gates` meters summed: at the cap no gate run starts, and each gate run's child gets `--max-budget-usd` set to what is left), and every chat of the project (`daemon.dailyUsd.chat`, every `_chat-<id>` meter in `meter/` summed) stop at `daemon.dailyUsd` per UTC day, and a start the same day is refused; raising `foreman.assistants.parallel` or opening more chats never multiplies a cap. When a meter file their cap sums can't be read, or the check after a result throws, the cap check fails closed the same way.
  - *Lifting a cap in `daemon.dailyUsd`*: `.forge/config.yml` is trusted, so a change stops the pool.
  - Residuals: arbitrary shell could delete or truncate a meter file or plant a link that disables the writer (`daemon.allowedTools` grants no shell beyond `forge`, `git rev-parse` and the listed `gh` reads, so that is a prompt a person sees); a deleted meter drops enforcement back to the reported figure, and a resume then rebases and loses one turn. A meter file over 64 MiB is not read: meter files are never pruned, so a long-lived one reaches that some day (years away at this repo's rate). The inbox, or the office and gate runs, then stop, but a job's budget checks fall back to its reported figure, with a `meter: …` error in its session log.
  - A resume that restores a different conversation than the one recorded, whose first cumulative is at or above the recorded baseline, under-counts that first delta by the baseline; a session can't force this. Cost incurred after a turn's last result and before a crash is unmetered until the next result in that conversation, which carries it. Whether `--max-budget-usd` compares claude's restored cumulative is unverified: adding the resumed baseline to the cap errs towards a generous mid-turn cap rather than a session that dies at every resume, and the per-result check still parks the job.
  - *Under-counting through a context session's forks* ([Daemon runtime](../daemon-runtime/role-runs.md#role-runs) › Role runs): a fork's result cumulative carries its context session's, so the runner subtracts the context's sidecar cumulative only when the fork's is at or above it on `usd` and on every token field of every model it holds (`forkBase`, lib/engine/workspace/context-session.ts), and otherwise counts the whole fork cumulative; the context's own run is recorded once, under role `context`, in `job.usage` and the ledger. Residual: a fork whose cumulative did not carry the context's but reached it on every field anyway is under-counted by at most the context's own cost, which is itself recorded.
