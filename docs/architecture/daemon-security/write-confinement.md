# Daemon security › Write confinement

Part of [Daemon security](../daemon-security.md).

- **The session can't change what Forge executes, what every agent reads, or anything outside its write roots.** Its cwd is the main checkout, so an agent misled by tracker or PR text could otherwise rewrite `commands.*` (which `forge run`/`forge verify` run through a shell), `daemon.*` (picked up at the next spawn or resume), the files every later agent reads with no review (`.forge/notes/`, `.forge/reviewers/`, `.forge/evals/`, `CLAUDE.md`, the instruction files), the job state the CLI trusts (`job.json`, `events.jsonl`), or files outside the repo, such as `~/.ssh/config`, whose `ProxyCommand` runs on the next push.

  The **protected set** is `PROTECTED` in `lib/core/config/trust.ts`: `.forge/config.yml`, `.forge/secrets-allow.txt`, `.forge/trackers/`, `.forge/verifiers/`, `.forge/notes/`, `.forge/reviewers/`, `.forge/evals/` (minus `runs/` and `recall/runs/`, which `forge` writes), `.forge/ci/`, the root's `CLAUDE.md`, `CLAUDE.local.md` and `AGENTS.md`, plus every configured `project.instructions` file. A session's **write roots** are the main checkout's `.forge/jobs/` and every worktrees root (the root's and each member repo's that is set up in `.forge/local.yml`). Five layers, each independent of the others:
  - *The CLI checks at the sink (the trust digest).* When a human starts the daemon (dashboard Start, or `forge dash` with `enabled: true`), the supervisor takes `trustDigest`: a sha256 of the checkout's realpath and every file of the protected set (an unreadable or absent one hashes as a marker; symlinks hash as links). It hands the digest to the session as `FORGE_DAEMON_TRUST`. Under `FORGE_DAEMON=1`, every `forge` command recomputes it before reading config and refuses on a mismatch, or when the variable is missing. The check catches every route, including Bash (`git mv -f`, a redirect) and a fake checkout reached through `cd`. `forge init write`, `forge migrate` and `forge config set` refuse outright, because they write config.yml through `forge` itself.
    - config.yml is read once, and the bytes that were hashed are the bytes parsed (the instruction list too). A custom tracker module is checked again just before it is imported. Any symlink under `.forge/trackers/` is refused (its target could change without the link changing), and the walk never follows one. A `git pull` that brings in a merged retro also changes the digest and stops the daemon until a human starts it again; that cost is intended. What the digest can't see: files a tracker module imports from outside `.forge/trackers/`, so keep tracker modules self-contained.
  - *The supervisor stops the session (the poll and the post-turn check).* Every poll, and before any spawn, it compares the trust digest with the one taken at start. The same start also takes a **confine digest** (`confineDigest` in `lib/office/session/confine.ts`): `git status` over the protected set, every `CLAUDE.md` and `CLAUDE.local.md` at any depth, and an in-checkout `core.hooksPath` directory, plus the content of each file that status lists, so a nested `lib/CLAUDE.md` or a file that was already dirty and changes again still counts. After every turn ends, and before every spawn, the session recomputes it.
    - On either change the whole pool stops with an error in the dashboard; respawns after an idle stop or a failed resume reuse the old snapshots, so a change made during a turn (or by a background agent between turns) is never blessed by a restart. A spawn hashes config.yml once and builds argv from those same bytes, so a file swapped and restored between two reads can't slip in. Only a human's Start takes new snapshots, and only when no child is running. A human editing a protected file while the daemon runs gets the same stop, which is the price of not being able to tell the two apart.
  - *Claude Code scopes the file tools.* At spawn, `buildArgv` drops every `Edit`, `Write`, `MultiEdit` and `NotebookEdit` entry of `daemon.allowedTools` (bare or scoped) and, when there was one, appends one `Edit(//<realpath>/**)` rule per write root, so a write anywhere else (`~/.ssh/config`, a shell rc file, the main checkout outside `.forge/jobs/`) becomes a dashboard prompt. One `Edit(…)` rule governs every file-writing tool. Validation refuses a `daemon.allowedTools` entry that scopes a file tool itself (`Edit(//**)`, `Write(~/**)`) or names an MCP tool (`mcp__…`). A write root equal to or containing the checkout (`worktrees.root: ..`), one inside `.forge/` or on (or around) a protected path or instruction file (`worktrees.root: .forge/runtime`, which would let the guard allow the CLI copy), or one a rule can't carry (`, ( ) * ? [ ] { }`, a newline, or a backslash off Windows), refuses the spawn with a pool fatal.
  - *Claude Code refuses the write (the deny tail).* `--disallowedTools` follows every `daemon.command`, whatever the template says: `DENY_TOOLS` in `lib/integrations/claude/argv.ts` (the protected set's `.forge/` entries, `.forge/local.yml`, `.forge/runtime/**`, `.forge/locks/**`, `.forge/archive/**`, and in job folders `job.json`, `events.jsonl`, `.lock/**` and any `CLAUDE.md` or `CLAUDE.local.md`), then `denyRules` from `lib/office/session/confine.ts`: each entry's absolute `//<realpath>/…` twin, the root's `CLAUDE.md`, `CLAUDE.local.md` and `AGENTS.md`, every configured instruction file, `**/CLAUDE.md` and `**/CLAUDE.local.md` unless a worktrees root lies inside the checkout, and a `core.hooksPath` directory inside the checkout.
    - Root-level names appear only in absolute form, so they stay anchored at the root. Relative paths anchor at the session's cwd (the main checkout, so job worktrees, where a self-improvement job legitimately edits Forge config, are unaffected), deny beats allow in every mode, and subagents inherit the rules. `.claude/` and `.mcp.json` are already Claude Code protected paths, which are never allowed without a human: `dontAsk` refuses them, and `default` asks.
  - *The write guard refuses it.* `hooks/write-guard.ts` runs as a `PreToolUse` hook on `Edit|Write|MultiEdit|NotebookEdit`. Without `FORGE_DAEMON=1` it allows everything, so a human's own sessions are unchanged. Under it, it resolves the target's realpath and allows only paths inside a job folder (`.forge/jobs/<id>/…`) or a worktrees root, read from `FORGE_DAEMON_WRITE_ROOTS`, which the spawn sets. Inside a job folder it still refuses `job.json`, `events.jsonl`, `.lock` and anything under it, and any `CLAUDE.md` or `CLAUDE.local.md` at any depth, ignoring case.
    - It refuses a path with a `..` segment, a path that starts with `~` (Claude Code expands it to a home directory, so it would otherwise resolve to a directory called `~` under the cwd), any `.git` segment inside a job folder or a worktree, ignoring case (so a worktree's `.git` file can't be pointed at a gitdir with a filter driver), a dangling symlink and anything it can't resolve, and fails closed on malformed input or env. It imports nothing from `lib/`, so a broken module can't change its verdict, and it doesn't depend on Claude Code's rule syntax, so it holds even if a rule form fails.

  **The CLI owns job state (#448).** `forge job new` writes a job's `job.json` and `events.jsonl` to a **CLI copy** under `.forge/runtime/job-records/<id>/` as well as the job folder, every later store write updates the copy first, and `loadJob`, `listJobs`, `readEvents` and repo spend read the copy (`stateFile` in `lib/core/paths.ts`). So a `pr.pushedSha`, a raised `budget`, a lowered `usage`, a cleared `protectedPaths` or an appended APPROVE line written into the job folder is ignored, and the next CLI write rewrites the folder's `job.json` from the copy. `.forge/runtime/` is out of reach of every file tool (the deny tail and the guard); the session's own `forge` calls write it, which is the CLI writing state. A MAC over event lines was rejected: the session runs `forge`, which must sign its own events, and it can `Read` any key the CLI can.

  The anchor is the session's environment, which it can't change: Bash allow rules don't match a command with a leading `VAR=…` assignment (except a few known-safe variables), and `env`/`export` aren't allowed. This keeps the *repo's* trusted commands in force; it does not stop those commands from running code the job wrote, which every verify does by design (that code is reviewed after verify, not before).

  **Residual risk.** Jobs created before the CLI copy have none and keep reading their job folder until they finish. Programs that write files themselves (`forge`, `git`, a configured command) can still change paths outside the digest's and the post-turn check's pathspecs. `Read`, `Glob` and `Grep` stay unscoped, so a session can read anything the user can.
- **Keeping a slot and marking agents lost read `job.json`, which the session writes through `forge`** (and, in a job that predates the CLI copy, could write directly). A session that records agents it never ends can pin its own slot, never another job's, for at most 2 h per agent start (the `AGENT_LEASE_MS` ceiling; a `startedAt` or `endedAt` more than 60 s in the future is ignored, so a forged time can't stretch the ceiling or the idle window, and the idle timer never re-arms for longer than its window), and a human's session or pool Stop ends it sooner, the same bound as a turn that never returns a `result`. Lost-marking writes on behalf of a session that no longer exists, so it touches only agents of a job whose `lease.driver` is that session's id, never another driver's. The job id it reads is the validated scope, so no path is built from session output, and nothing new reaches the child's stdin, argv or environment. An agent role becomes a `job.json` key and part of a review path, so `forge job agent --role` and `recordAgent` take only a role name or `reviewer:<lens>` (never `__proto__` or a path), and lost-marking skips any other key.
- **`--body-file` publishes only the session job's own files.** `forge tracker comment`, `tracker create`, `job new`, `job note` and `eval new` read their text from `--body-file F`, so an agent could otherwise publish any file the user can read (`~/.ssh/id_ed25519`) through a tracker comment. Under `FORGE_DAEMON=1`, `-` (stdin) is always allowed; any other F is refused in the `_inbox` and `_office` sessions (a gate run's `_gates` scope refuses every forge command), and in a job session must resolve, after realpath, inside the realpath of that job's folder or of its computed worktree (`<worktrees root>/<id>`, never `job.json`'s session-writable `worktree`). The check compares path components, so a sibling that shares the prefix, `..` and a link pointing out are refused; the file is then read like a review (a regular file under 1 MiB, never a link or a FIFO). Tracker writes still pass the secret scan. Residual risk: a parent directory swapped between the check and the open (Node has no `openat`).
