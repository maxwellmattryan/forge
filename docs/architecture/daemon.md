# Daemon

The machine dashboard (`forge dash`) supervises one **pool** per registered project ([Concurrency](concurrency.md)), each of `claude -p --input-format stream-json --output-format stream-json` children (`lib/office/pool.ts`), with the child's `cwd` and `FORGE_ROOT` pinned to that project's root whatever the server's own environment says: one inbox session for requests without a job, one **office** session (scope `_office`; nothing routes to it in this version, so it is never spawned), with `foreman.enabled` and `foreman.assistants.enabled` one **assistant foreman** session per scope `_assistant-1` … `_assistant-<n>` (n being `foreman.assistants.sessions`, 1 to 16) for `gate` requests (see [Foreman](foreman.md)), and one session per job with work, up to `daemon.maxConcurrent` (1 to 16, default 3). The inbox, the office and the assistant foremen are shared sessions: never counted against `daemon.maxConcurrent` or the machine cap, never idle-stopped for a job and never pruned. The office and the assistant foremen run in `daemon.command`'s permission mode, never the job sessions' default, unless a human chooses one for that scope. Each meters into its own `.forge/runtime/meter/<scope>.jsonl`, and `daemon.dailyUsd.office` caps the office and every assistant foreman together: the 17 meter files are summed, and when any one can't be read the cap fails closed for all of them. Each session is supervised on its own by `lib/office/session/lifecycle.ts`, with its own state, failure count, budget hold, idle stop, resume id and log, so one job's crash loop never stalls the others. The supervisor never reads claude's output: `lib/integrations/claude/child.ts` spawns the child and kills its process group, and `lib/integrations/claude/stream.ts` turns its stream-json lines into domain events (a turn started or ended, a session id, a permission prompt) that the supervisor reacts to. The supervisors never run agents or write job state: they only decide when a session gets its one turn. Every child is built the same way (`daemon.command`, `DENY_TOOLS`, git pins, the trust snapshot) and differs only in its session uuid and `FORGE_DAEMON_SCOPE=<scope>` in its environment; the scope never reaches stdin or argv.

**Periodic sync.** While the pool is wanted and `daemon.enabled` holds, it also runs `forge sync` every 2 minutes as a plain CLI child (`runSyncChild` in lib/office/sync-child.ts: no daemon scope, so it acts as the human who started `forge dash`, the same as typing it, but with git pinned by `SYNC_PINS` so no hook, fsmonitor, pager, external diff or other gpg program from the checkout's config runs on its fetches; `credential.helper` is never pinned), never in the server process, whose synchronous `gh` calls would stall every session's pipe. One runs at a time, a run over 10 minutes is killed, it is skipped while the trust snapshot is stale, and each distinct failure is logged once to the inbox log. This is what turns failing checks, PR feedback and conflicts into `gate` requests, unparks dependents and finishes merged jobs without a session having to sync first; the pool ticks as soon as each run ends.

**Reconciler** (lib/office/reconcile.ts). A job whose `state` is `running` has no gate holding it, so anything that leaves it with nothing to drive it (a crashed session, a turn that ended with nothing queued, an agent end claude never delivered) would strand it. One level-triggered pass answers "is this job driven?" from what is, not from which event happened. It runs in `forge dash` every 30 s (`RECONCILE_MS`) while the pool is wanted, for one job when its session's turn ends and when its child exits, and once per `forge sync` unless a live process holds `<locks>/daemon`, which sync reads without taking (then it reports `reconcile: "skipped (forge dash owns it)"`). Each pass first requeues orphaned requests ("Ownership" in [Job model](job-model.md)), then judges every `running` job; jobs in any other state are parked, queued, blocked, waiting on a person or finished, so it never acts on them and drops their record. A running job is **driven** when a request routed to it is pending or in progress, when (in dash) its own session is `busy` or `stopping`, or when its lease is live, except that a live lease whose driver is the job's own session does not count while that session is `off`, or has sat `idle` for 60 s (`IDLE_UNDRIVEN_MS`) with no background task in claude's latest `system`/`background_tasks_changed` (Claude Code can dequeue a finished agent's task notification into an empty result the model never sees, which left a job with an agent marked running and nothing to wake it; a claude that has not reported its tasks counts as busy with them only while `job.json` marks an agent running). An **undriven** job whose record is missing, or whose progress mark moved since its record, gets one fixed-text `resume` (`from: "reconciler"`; nothing from job.json reaches it), a record `{ mark, stage, resumedAt, request, resumes }` and a `reconcile { action: "resume" }` event; `resumes` counts the resumes at `rec.stage` and starts again at 1 when the job's stage differs from the record's. Undriven again at the same mark, with nothing routed to it, it is parked on `escalation` (`undriven at <stage>: resumed once with no progress since`), re-decided under the job lock, with a `reconcile { action: "escalate" }` event and the gate queued, so the Foreman or a person takes it. On top of that, `MAX_RESUMES_PER_STAGE` (3) is an absolute ceiling: an undriven job whose record is at its stage with 3 resumes is escalated the same way at the next undriven pass, whatever the mark says (`undriven at <stage>: resumed 3 times at this stage`), so a session that meters one agent per turn can't buy resumes for ever. A record an older Forge wrote without `resumes` reads as 1. The records live in `<runtime>/reconcile.json`, written under `<locks>/reconcile`, so a restarted dashboard keeps its count. The mark is the time of the newest progress event (`progressMark`: transitions, rounds, verify runs, integrations, integration reviews, PR opens, updates and head pulls, verdicts, and `agent-end` events that carry a `usage` object; never agent starts, human events, an `agent-end` without usage, renewals, syncs, notes or failures, which a session can log every turn without moving anything), or the job's newest meter record when that is later (`lastMeterAt` over `.forge/runtime/meter/<id>.jsonl`): a turn the supervisor metered is progress even when its agent's transcript lagged and its end was recorded `unmeasured`, and the ceiling of 3 resumes per stage still bounds a session that only spends. `forge job advance`'s repeat-failure mark below uses the same `progressMark` without the meter, so it keeps the events-only rule. Separately, `forge job advance` logs every failed command as `advance-failed {rule, command, error, mark}`; when the same rule and command fail again with the same mark, it parks the job on `escalation` with the error as the reason, queues the gate, and returns `parked: true`.

**Boot pass.** When a project's pool boots as the machine dashboard loads it (`pool.start('boot')` leaves it wanted), the server runs one reconciler pass for that project at once (`resumeProject` in lib/server/uptime.ts, with the pool's session facts), rather than waiting `RECONCILE_MS`, so a running job a crash or a reboot left undriven gets its fixed `resume` request as soon as the dashboard is back. It goes through the same memory and lock as the pool's own passes, so the boot pass followed by the 30 s timer never queues a second resume. The claimed draft requests of the office session and gate requests of the assistant foremen already return to pending at the boot's release ("Exits let go" below), and the office session or an assistant foreman spawns for them on the first tick, so a mandate's work resumes with no side channel. The open Office requests a restart notification counts are both kinds. A pool that does not boot (daemon off, trusted files awaiting approval, `--dev`) gets no boot pass. `RunningServer.booted()` resolves with the passes of the projects loaded at start, which `forge dash --service` records in `<FORGE_HOME>/runtime/uptime.json` before it sends each project with running jobs or open Office requests one `service-restarted` notification (docs/CLI.md "Login service").

**Sleep assertion.** While any served project's pool is started and has an active mandate or a `running` job at an agent stage (`plan` through `decide`), and its `daemon.keepAwake` is `auto`, the machine dashboard holds one sleep assertion for the whole machine (`startKeepAwake` in lib/server/uptime.ts): `caffeinate -i -w <pid>` on macOS, `systemd-inhibit --what=idle:sleep --mode=block tail --pid=<pid> -f /dev/null` on Linux, where `<pid>` is the dashboard's own. The check is level-triggered every 15 s rather than on events, because mandates are files `forge mandate` writes with no event and idle sleep takes at least a minute; a stopped pool holds nothing, so an idle project with an active mandate never keeps the machine up for nothing. The helper is released when no project needs it and when the dashboard closes, and exits on its own when the dashboard's pid dies, so a SIGKILL leaves nothing behind. A helper that is missing or exits early is recorded as an error and tried again at most once a minute. `FORGE_KEEP_AWAKE=never` turns it off for the machine (the test suite sets it), and a dev dashboard never holds one. Its state is `uptime.json`'s `keepAwake`, which `forge doctor` believes only while its pid is the proven machine dashboard.

**Turn timeout.** A job, inbox, office or assistant foreman session's turn still `busy` `daemon.turnTimeoutMinutes` (default 60; `null` means no limit) after it was written, or after claude woke it itself, is stopped: the supervisor logs `turn-timeout { minutes }` and kills the child (`stop`, `reason: "turn-timeout"`). The exit path then marks its agents lost, expires its lease and requeues its claims, and the session stays wanted, so the pool respawns it for the requeued work and the reconciler watches the job. The timer is a `setTimeout`, which is monotonic, so a wall-clock jump never fires it.

**Exits let go.** Whenever a session's child is gone, because it exited for any reason or a kill saw no close and gave up on it, the session runs one release (`releaseSession` in lib/office/driver.ts) over every id it has had: for every job one of those ids drives (any job, not only its own scope), it marks the running agents `lost` (re-checked per role, stopping once another driver has the job) and expires the live lease, then requeues the requests those ids claimed. The inbox, the office and the assistant foremen go through the same release. The log keeps `exit` first, then `agents-lost { job, roles }` and `lease-expired { job, session, reason }` per job, `requeued` and any `error`; then the pool reconciles the job and ticks. A pool boot runs the same release over every recorded id ("Ownership" in [Job model](job-model.md)).

**States** (per session: `/api/state.daemons.inbox|office|assistants[scope]|jobs[id].status`, `assistants` being `{}` while the foreman or its assistants are off; SSE `state` events): `off` (no child), `idle` (child alive, no turn in flight), `busy` (a turn was written and no `result` has been read), `stopping` (SIGTERM sent). Two things set `busy`: a turn write, and a `system`/`init` read while the session is `idle` after its child's first `result`. The second is a turn claude started by itself (a background agent finished and its notification woke the orchestrator): the supervisor logs `wake` once per such turn and writes the session no turn until it ends. `turns` and `lastTurnAt` count only the turns the supervisor wrote. A stdout line that parses as JSON with `type: "result"` is the only thing that sets `idle`. A fresh child is `idle`, because a stream-json `claude -p` does nothing until it reads a line. A session also reports `waiting` (it has work but no free slot), `held` (`budget` or `repo-budget`) and `kept` (`agents`: below).

**Trigger** (edge-triggered per request id). Every `pollMs` (2 s), after every `POST /api/requests` and after every `result`, the pool checks the trust digest, reads the pending requests once and routes each to its scope (`requestScope` in `lib/core/job/requests.ts`). Per session, it sets aside the budget-held requests (below) and takes the ids not yet in that session's `committed` set. If any are left and the session is not `busy`/`stopping`, it spawns a child if there is none (subject to the cap), writes the turn and records the eligible ids as in flight. A working `result` adds them to `committed`, which each tick prunes to ids still pending; a failed one (`is_error`) commits nothing and sets a retry time instead ("Failures" in [Daemon runtime](daemon-runtime.md)). So one request causes at most one turn (a request the session leaves pending can't loop), a request that arrives mid-turn causes exactly one more turn, a child that dies mid-turn drops its in-flight ids so they retrigger, a turn that failed before claiming anything is sent again, and claimed (`in-progress`) requests never count. A pool start brings the inbox up even without work; the office and job sessions spawn only on demand. `gate` requests route to the `_assistants` group, which is never a session: each assistant foreman takes every pending gate request as its own. With P the gate requests eligible after holds and B the assistant foremen `busy` or `stopping`, at most P − B fresh, idle assistants get a turn each tick, in scope order, each spawned first when it is off; the claim lock keeps two of them off one gate, so an extra turn costs one refused claim. With `foreman.enabled` or `foreman.assistants.enabled` off, no assistant runs and pending `gate` requests get no spawn and no turn: they wait for a human.

**Cap and slots.** When `maxConcurrent` job sessions are running, a job with fresh work is marked `waiting` (logged once as `waiting`). Slots go to waiting jobs in the order of their oldest pending request. When a job waits and some job session is `idle` and not kept, the pool stops the idle session with the oldest `lastResultAt` (`idle-stop`, `reason: "slot"`) and gives the slot away; that session resumes its conversation the next time it has work. A session is **kept** only while a running agent of its job keeps it; there is no grace after a result. Its agents are the `job.agents` of its job, counted only while `job.lease.driver` is one of the session's ids (current, spawn or past), so another driver's agents (a human's terminal session) never keep it. A running agent keeps it only for 2 h after its `startedAt`, the lease `agent start` gives, so a phantom can't hold a slot forever. A kept session still counts toward the cap: when every running job session is kept, the waiting job stays `waiting` and gets the next slot that frees, which the 2 s tick finds within one poll of the last agent ending. Each tick refreshes `kept` (`agents` or null) for running job sessions. After a job session's `result`, if its job is `done`, `cancelled` or `failed` (or gone) and no pending request routes to it, the pool logs `finished` and stops it (`stop`, `reason: "job-finished"`). Sessions that are off and clean, with no request routed to them, are pruned at the next tick; their files stay.

**Machine cap.** On top of each project's `daemon.maxConcurrent`, the **machine cap** bounds job sessions across every project the machine dashboard serves: the machine index's `settings.maxConcurrent` (`forge project settings --max-concurrent <1-64|auto>`), else the highest `maxConcurrent` among the loaded pools, so one project behaves as before. Inbox, office and assistant foreman sessions never count against either cap. The pools share one slot gate (`lib/office/slots.ts`): a pool spawns a waiting job only while a machine slot is free and no other project holds an older waiter (request ids start with `Date.now()`, so they compare across projects); a waiter held only by its own project's `maxConcurrent` never blocks another project. A pool still short after stopping its own idle sessions stops idle, unkept job sessions in other projects, oldest result first, less the slots already free or stopping; a job session's exit pokes every other pool, so a held waiter takes the slot. `/api/p/<project>/state` reports it as `daemons.machine: { maxConcurrent, live }`.

**Budget hold.** Limits are per job, so a hold is per session: `resume`, `rework`, `answer` and `revise-spec` requests whose job is at `waiting: budget` and still over a limit (`exceededKeys` in `lib/engine/metrics/budget.ts`) are never sent or committed, and that session reports `held: "budget"`. `approve` (the acknowledgement), `cancel` and job-less requests are never held. Once a human raises or acknowledges the budget, the next tick sends the turn. A `held` log line is written when the session's hold changes. Spend scales with the number of live sessions.

**Repo budget hold.** `budget:` caps what the whole repo spends per UTC day and month (see ["Repo budget"](policies.md#repo-budget)). While a cap is reached under `onExceeded: hold`, every job session's pending `resume`, `rework`, `answer`, `revise-spec` and `approve` waits unless its job is exempt (a retro, or one a human forced past the cap this month), and the session reports `held: "repo-budget"`, which wins over `budget` when both apply. `approve` waits too, because approving is no acknowledgement of the repo cap. `cancel`, gate requests (the assistant foremen) and job-less requests (the inbox) are never held, and a busy session finishes its turn. The pool computes the status without writing anything (`write: false`) and reuses it for up to 10 s, recomputing at once when the audit log grows (an ack) or the `budget:` block changes.
