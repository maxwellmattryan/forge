# Daemon

The machine dashboard (`forge dash`) supervises one **pool** per registered project ([Concurrency](concurrency.md)), each of `claude -p --input-format stream-json --output-format stream-json` children (`lib/office/pool.ts`), with the child's `cwd` and `FORGE_ROOT` pinned to that project's root whatever the server's own environment says: the **intake runner** (`lib/office/inbox/runner.ts`), which is no session and answers requests without a job in code with `bin/forge` children (Intake runner below), an inbox session spawned only for a request type the runner doesn't handle, and one session per job with work, up to `daemon.maxConcurrent` (1 to 16, default 3). There is no office session (it is retired): with `foreman.enabled`, the pool owns the **office runner** (`lib/office/foreman/runs/`), which is no session either: it runs `draft` and `direct` requests (scope `_office`) in code, one **office run** at a time, with CLI children and one-shot model children (the drafter, the surveyors and at most one director call). With `foreman.enabled` and `foreman.assistants.enabled`, the pool also owns the **gate runner** (`lib/office/foreman/run.ts`): it decides `gate` requests in code, up to `foreman.assistants.parallel` (1 to 16, default 2) **gate runs** at once, each with one headless one-shot `claude -p --agent forge:assistant` child (see [Foreman](foreman.md)). The inbox is a shared session: never counted against `daemon.maxConcurrent` or the machine cap, never idle-stopped for a job and never pruned; office, gate and intake runs count against neither cap either. The inbox starts in the run's launch mode (`forge dash --permission-mode`, `lib/office/modes.ts`), else in `daemon.command`'s permission mode, never the job sessions' default, unless a human chooses one for that scope; an office or gate run's model child always runs with `--permission-mode dontAsk`. Each session meters into its own `.forge/runtime/meter/<scope>.jsonl`, office runs into `meter/_office.jsonl` gate runs into `meter/_gates.jsonl`, and the intake runner's triage child into `meter/_inbox.jsonl` under `daemon.dailyUsd.inbox`; `daemon.dailyUsd.office` caps the office runs and the gate runs together: both meter files are summed, and when either can't be read the cap fails closed for both. Each session is supervised on its own by `lib/office/session/lifecycle.ts`, with its own state, failure count, budget hold, idle stop, resume id and log, so one job's crash loop never stalls the others. The supervisor never reads claude's output: `lib/integrations/claude/child.ts` spawns the child and kills its process group, and `lib/integrations/claude/stream.ts` turns its stream-json lines into domain events (a turn started or ended, a session id, a permission prompt) that the supervisor reacts to. The supervisors never run agents or write job state: they only decide when a session gets its one turn. Every child is built the same way (`daemon.command`, `DENY_TOOLS`, git pins, the trust snapshot) and differs only in its session uuid and `FORGE_DAEMON_SCOPE=<scope>` in its environment; the scope never reaches stdin or argv.

**Code driver.** Under `daemon.driver: code` (default `session`, read at each turn) a job scope's Session is the **code driver** (`createCodeDriver`, lib/office/code/job-driver.ts), which wraps the scope's ordinary session. Routing, holds, the cap and the trigger are the pool's as above. It takes every turn of the job in code, whatever its requests and the job's state: it claims the job under its own stable id, applies each request of the turn with `forge job apply` (the human-command table: a person's approve, answer, revise-spec, rework or cancel, and the dashboard's Resume on `infra`, `external`, `conflicts` or a failed job), then runs `forge job advance` and one `forge job agent run` per spawn as child processes until the job reaches a gate or `done` ([Daemon runtime](daemon-runtime.md) › Code driver). The split, an adopted PR and a retro's start are step rows now, so the driver runs them too. The one turn that goes to the wrapped session is the one holding the driver's own hand-off resume (`from: code-driver`), queued when step returns a `procedure`, which is only RC1's recall eval (given to the session at once, or logged `fallback` when the pool routes it later); the driver and that session never run at once. A code turn counts as one job session against `daemon.maxConcurrent` and the machine cap, however many role runs it has, as a session's subagents do. No `forge` command runs in the server's process: every call is a child (`startForge` in lib/office/code/children.ts) with a job session's env and scope, after the same launch checks a session's spawn passes (lib/office/session/launch.ts), and the server itself only reads and writes files through the existing helpers (requests, the lease release, the prompt history). The inbox, the office, chats and gate runs are unchanged.

**Chats.** The owner's chats with the Foreman each run in their own pool session, scope `_chat-<id>` (the id 12 lowercase hex characters), a shared session like the inbox: never counted against `daemon.maxConcurrent` or the machine cap, never leased, pruned or routed a request, and never turned by the tick. A chat's session starts only when the owner sends it a message (`POST /api/p/<project>/chats/<id>/messages`): the pool's `sendChat` (lib/office/chat/send.ts) spawns it through `startWork`, as every session is spawned, and writes the message to its stdin as one user line instead of the `/forge requests` turn; a scoped start answers 409. Its spawn appends the fixed `CHAT_PROMPT` with `--append-system-prompt`, so the session knows it is the Foreman in a chat and runs `forge chat brief` first (`skills/forge/reference/chat.md`). It launches in permission mode `default` unless the owner chose another for that chat, whatever `daemon.command` says, and never takes the job sessions' default. It idles out after `daemon.idleStopMinutes` like any session; the next message, and the first after a `forge dash` restart, resumes the same Claude session from its record. It meters into `meter/_chat-<id>.jsonl`, and `daemon.dailyUsd.chat` caps every chat of the project together: at the cap a message's spawn is refused and a running chat stops after its result, and a chat meter that can't be read fails the cap closed. Its spend shows in `forge stats` as role `chat`. A chat's files are `.forge/runtime/chats/<id>/chat.json` (`{ schemaVersion, id, title, state, createdAt, updatedAt, sessionId }`) and `log.jsonl`, one line per owner message (`owner`), per message that could not reach the session (`undelivered`), and per line the session logged (`session`, exactly as `daemons/_chat-<id>.log` has it, a line over 256 KiB cut to the `forge-truncated` marker), each with `v` and `at`. Only the dashboard server writes them (lib/office/chat/store.ts; the server's recorder appends the session's lines and follows its session id from the pool's events); `forge chat list|show|brief` reads them. Unlike the session log, the chat log never rotates, and appends stop at 64 MiB. Archiving a chat stops and drops its session.

**Periodic sync.** While the pool is wanted and `daemon.enabled` holds, it also runs `forge sync` every 2 minutes as a plain CLI child (`runSyncChild` in lib/office/inbox/children.ts: no daemon scope, so it acts as the human who started `forge dash`, the same as typing it, but with git pinned by `SYNC_PINS` so no hook, fsmonitor, pager, external diff or other gpg program from the checkout's config runs on its fetches; `credential.helper` is never pinned), never in the server process, whose synchronous `gh` calls would stall every session's pipe. One runs at a time, a run over 10 minutes is killed, it is skipped while the trust snapshot is stale, and each distinct failure is logged once to the inbox log. When the pool closes (the dashboard shutting down or a project removed), a running sync child gets SIGTERM, then SIGKILL after the grace period (`graceMs`, 5 s), and the close waits for it to exit and logs nothing for it; a `forge dash` that exits without closing still sends it SIGTERM. This is what turns failing checks, PR feedback and conflicts into `gate` requests, unparks dependents and finishes merged jobs without a session having to sync first; the pool ticks as soon as each run ends.

**Periodic Office pass.** While the pool is wanted and trusted and `foreman.enabled` holds (read each tick), it runs `forge office pass` (lib/office/mandates/pass.ts; [Foreman](foreman.md) › Director loop) as a CLI child the same way (`runPassChild` in lib/office/inbox/children.ts, through the same `runForgeChild`: no daemon scope, `SYNC_PINS`, killed after 10 minutes, and stopped the same way when the pool closes), because it may call `gh` once per mandate milestone. One runs at a time (`createPassScheduler`, lib/office/mandates/cadence.ts). A pass is due at pool start, when the names, sizes or mtimes of `.forge/runtime/mandates/*.md` change, when a job session's result leaves a job in a mandate `done`, `cancelled`, `failed` or `waiting`, and otherwise every `foreman.cadence` minutes (an integer 1 to 1440, else 10). When the child ends the pool ticks, so the `direct` request it queued becomes an office run at once; each distinct failure is logged once to the office runs' log, `_office.log` (`office pass failed: <message>`). With the foreman off, no pass runs. A direct office run's director call spawns with `--model <foreman.model>` (unless it is `inherit`; it replaces every `--model` in `daemon.command`) and `--effort <foreman.effort>`; its `office-child` log line carries both. Job sessions and the inbox keep `daemon.command`'s model; a gate run's child takes `foreman.assistants.model`, a drafter or surveyor the roster's.

**Intake runner** (lib/office/inbox/). With `daemon.enabled` and the pool wanted, each tick hands the runner the pending `_inbox` requests whose type it handles; it works on one at a time, oldest id first, and only while the inbox is wanted (a human's Stop on the inbox stops it until Start). Before each request it passes `checkLaunch`, which stops the pool when trust, config or `daemon.enabled` changed. It claims the request under the inbox's **intake session id**, a uuid kept as `intakeSessionId` in `.forge/runtime/daemons/_inbox.json` (created the first time a pool is built for the root, stable across restarts), runs the type's fixed calls, each as its own `process.execPath <plugin>/bin/forge <args>` child in the root with the session env, `FORGE_ROOT`, `FORGE_DAEMON_SCOPE=_inbox`, the pool's trusted digest and the write roots (killed after 10 minutes), and acks with a fixed one-line result. Every inbox refusal (`refuseInboxDrive`, `refuseDaemonMerge`, the `--set` refusal, the trust check) applies to each call. `sync` runs `forge sync` (`synced <n>; <n> requests queued`, `; merged <id>,…` for a merge it saw); `next` runs readiness triage once, then up to `args.n` (1 to 10, default 1) `forge next --claim --session=<id>` calls, handing each job off at once with `forge requests add resume --job=<id> --intake=next --session=<id>` (`handed off to <id>, …`, `no ready work`, `held: <reason>`); `run` runs `forge job from-ref --session=<id> -- <args.ref>` and the hand-off with `--intake=run` (exit 4 is `held: <error>`); `retro` runs `forge job new --kind=retro`, `forge retro prepare <id>` (with `--mandate`) and a hand-off with no `--intake` (a failed prepare still hands off); `eval-run` runs `forge eval start` with only `--tags`, `--tasks` and `--label` and a resume per eval job; a job request routed here is rejected (`unknown job <id>`, `malformed job`). A request value reaches argv only as one `--flag=<value>` word or after `--`, after its check (a ref of 1 to 200 characters with no control character and no leading `-`, a mandate id, eval values of at most 500 characters), and a job id from a child's output must pass `validJobId`. A non-zero exit is that command's answer; acks and log lines hold only job ids, counts and Forge's own error text. **Triage** (`triage.ts`) runs `forge tracker triage --limit=10`; with items pending and the inbox's daily cap clear, it spawns one headless `claude -p --agent forge:triage` child with the batch brief as its only message, `--tools Read,Write`, `--permission-mode dontAsk`, `--no-session-persistence` and no setting source, whose one writable path is the batch dir; its cost is metered to `meter/_inbox.jsonl`, the confine digest is compared after it exits (a change stops the pool and `--apply` never runs), then `forge tracker triage --apply=<batch>` runs. A triage failure is a `triage` log line with `error` and never blocks `next`. A stop, close or human Stop mid-run kills the child (SIGTERM, then SIGKILL after the grace period) and gives the claim back uncounted; a child that can't start, times out or dies by another signal requeues the request (counted; a second time rejects it with `its session ended twice while handling it`) and holds new runs for the backoff (`retryMinMs` doubling to `retryMaxMs`). A failed hand-off is logged and named in the ack, and the job's lease stays the runner's until it expires or the next boot releases it. The runner logs `intake-start`, `intake-call { args, code, ms }`, `intake-end { request, type, status, result, waitMs, runMs }`, `triage`, `intake-held` and `intake-fallback` to `_inbox.log`. A request routed to the inbox whose type the runner doesn't handle (a type a later Forge adds, or a hand-written file) is logged `intake-fallback` once and left to the inbox session, which spawns on demand and gets `/forge requests` as before.

**Reconciler** (lib/office/reconcile.ts). A job whose `state` is `running` has no gate holding it, so anything that leaves it with nothing to drive it (a crashed session, a turn that ended with nothing queued, an agent end claude never delivered) would strand it. One level-triggered pass answers "is this job driven?" from what is, not from which event happened. It runs in `forge dash` every 30 s (`RECONCILE_MS`) while the pool is wanted, for one job when its session's turn ends and when its child exits, and once per `forge sync` unless a live process holds `<locks>/daemon`, which sync reads without taking (then it reports `reconcile: "skipped (forge dash owns it)"`). Each pass first requeues orphaned requests ("Ownership" in [Job model](job-model.md)), then closes stale resume requests, then judges every `running` job. The stale-resume sweep (`closeStaleResumes`) looks at every `pending` `resume` with a valid job id, in order: (1) its job has no `job.json` (deleted, or archived by retention): `rejected`, `its job no longer exists`; (2) the job's events have a `claimed` event later than the request's `createdAt`, and its progress mark (events only, no meter) is later than that claim: `done`, `a session claimed the job and moved it after this request was queued`; (3) the job is `cancelled`, or `done` with no queued score run: `rejected`, `its job is <state>`. Any other resume is left: one waiting for a slot or a budget, a claim that failed before it moved anything, a `failed` job (Retry sends a resume), a done job whose score run is queued. Each close is checked again under the requests lock, so a request claimed or acked meanwhile is left alone, and a close on a job that still exists is noted on it (`request <id> (resume) closed: <result>`). `in-progress` requests stay the requeue's business. Because the sweep runs before the pass reads the open requests, a running job whose only routed request was a stale resume is judged undriven in the same pass. Only `running` jobs are judged: jobs in any other state are parked, queued, blocked, waiting on a person or finished, so it never acts on them and drops their record. A running job is **driven** when a request routed to it is pending or in progress, when (in dash) its own session is `busy` or `stopping`, or when its lease is live, except that a live lease whose driver is the job's own session does not count while that session is `off`, or has sat `idle` for 60 s (`IDLE_UNDRIVEN_MS`) with no background task in claude's latest `system`/`background_tasks_changed` (Claude Code can dequeue a finished agent's task notification into an empty result the model never sees, which left a job with an agent marked running and nothing to wake it; a claude that has not reported its tasks counts as busy with them only while `job.json` marks an agent running). An **undriven** job whose record is missing, or whose progress mark moved since its record, gets one fixed-text `resume` (`from: "reconciler"`; nothing from job.json reaches it), a record `{ mark, stage, resumedAt, request, resumes }` and a `reconcile { action: "resume" }` event; `resumes` counts the resumes at `rec.stage` and starts again at 1 when the job's stage differs from the record's. Undriven again at the same mark, with nothing routed to it, it is parked on `escalation` (`undriven at <stage>: resumed once with no progress since`), re-decided under the job lock, with a `reconcile { action: "escalate" }` event and the gate queued, so the Foreman or a person takes it. On top of that, `MAX_RESUMES_PER_STAGE` (3) is an absolute ceiling: an undriven job whose record is at its stage with 3 resumes is escalated the same way at the next undriven pass, whatever the mark says (`undriven at <stage>: resumed 3 times at this stage`), so a session that meters one agent per turn can't buy resumes for ever. A record an older Forge wrote without `resumes` reads as 1. The records live in `<runtime>/reconcile.json`, written under `<locks>/reconcile`, so a restarted dashboard keeps its count. The mark is the time of the newest progress event (`progressMark`: transitions, rounds, verify runs, integrations, integration reviews, PR opens, updates and head pulls, verdicts, and `agent-end` events that carry a `usage` object; never agent starts, human events, an `agent-end` without usage, renewals, syncs, notes or failures, which a session can log every turn without moving anything), or the job's newest meter record when that is later (`lastMeterAt` over `.forge/runtime/meter/<id>.jsonl`): a turn the supervisor metered is progress even when its agent's transcript lagged and its end was recorded `unmeasured`, and the ceiling of 3 resumes per stage still bounds a session that only spends. `forge job advance`'s repeat-failure mark below uses the same `progressMark` without the meter, so it keeps the events-only rule. Separately, `forge job advance` logs every failed command as `advance-failed {rule, command, error, mark}`; when the same rule and command fail again with the same mark, it parks the job on `escalation` with the error as the reason, queues the gate, and returns `parked: true`.

**Boot pass.** When a project's pool boots as the machine dashboard loads it (`pool.start('boot')` leaves it wanted), the server runs one reconciler pass for that project at once (`resumeProject` in lib/server/uptime.ts, with the pool's session facts), rather than waiting `RECONCILE_MS`, so a running job a crash or a reboot left undriven gets its fixed `resume` request as soon as the dashboard is back. It goes through the same memory and lock as the pool's own passes, so the boot pass followed by the 30 s timer never queues a second resume. The draft and direct requests an earlier dash's office runs left claimed (or the retired office session's, at the boot's release, "Exits let go" below) and the gate requests its gate runs left claimed are requeued (counted) when the pool starts fresh, so an office run and a gate run start for them on the first tick, and a mandate's work resumes with no side channel. The open Office requests a restart notification counts are both kinds. A pool that does not boot (daemon off, trusted files awaiting approval, `--dev`) gets no boot pass. `RunningServer.booted()` resolves with the passes of the projects loaded at start, which `forge dash --service` records in `<FORGE_HOME>/runtime/uptime.json` before it sends each project with running jobs or open Office requests one `service-restarted` notification (docs/CLI.md "Login service").

**Sleep assertion.** While any served project's pool is started and has an active mandate or a `running` job at an agent stage (`plan` through `decide`), and its `daemon.keepAwake` is `auto`, the machine dashboard holds one sleep assertion for the whole machine (`startKeepAwake` in lib/server/uptime.ts): `caffeinate -i -w <pid>` on macOS, `systemd-inhibit --what=idle:sleep --mode=block tail --pid=<pid> -f /dev/null` on Linux, where `<pid>` is the dashboard's own. The check is level-triggered every 15 s rather than on events, because mandates are files `forge mandate` writes with no event and idle sleep takes at least a minute; a stopped pool holds nothing, so an idle project with an active mandate never keeps the machine up for nothing. The helper is released when no project needs it and when the dashboard closes, and exits on its own when the dashboard's pid dies, so a SIGKILL leaves nothing behind. A helper that is missing or exits early is recorded as an error and tried again at most once a minute. `FORGE_KEEP_AWAKE=never` turns it off for the machine (the test suite sets it), and a dev dashboard never holds one. Its state is `uptime.json`'s `keepAwake`, which `forge doctor` believes only while its pid is the proven machine dashboard.

**Turn timeout.** A job or inbox session's turn still `busy` `daemon.turnTimeoutMinutes` (default 60; `null` means no limit) after it was written, or after claude woke it itself, is stopped: the supervisor logs `turn-timeout { minutes }` and kills the child (`stop`, `reason: "turn-timeout"`). The exit path then marks its agents lost, expires its lease and requeues its claims, and the session stays wanted, so the pool respawns it for the requeued work and the reconciler watches the job. The timer is a `setTimeout`, which is monotonic, so a wall-clock jump never fires it. A gate or office run's model child past the same limit is killed too, and the run fails (Trigger below). A job session whose turn's context passes `daemon.freshAfterTokens` is stopped too, at its next safe boundary, and starts its next spawn on a new conversation; the inbox starts one at every spawn ([Daemon runtime](daemon-runtime.md) › Rotation).

**Exits let go.** Whenever a session's child is gone, because it exited for any reason or a kill saw no close and gave up on it, the session runs one release (`releaseSession` in lib/office/driver.ts) over every id it has had: for every job one of those ids drives (any job, not only its own scope), it marks the running agents `lost` (re-checked per role, stopping once another driver has the job) and expires the live lease, then requeues the requests those ids claimed. The inbox goes through the same release; a gate or office run has no session, and never leaves its request claimed (Trigger below). The log keeps `exit` first, then `agents-lost { job, roles }` and `lease-expired { job, session, reason }` per job, `requeued` and any `error`; then the pool reconciles the job and ticks. A pool boot runs the same release over every recorded id ("Ownership" in [Job model](job-model.md)).

**States** (per session: `/api/state.daemons.inbox|jobs[id].status`, with the office runs in `daemons.office` and the gate runs in `daemons.gates`; SSE `state` events): `off` (no child), `idle` (child alive, no turn in flight), `busy` (a turn was written and no `result` has been read), `stopping` (SIGTERM sent). Two things set `busy`: a turn write, and a `system`/`init` read while the session is `idle` after its child's first `result`. The second is a turn claude started by itself (a background agent finished and its notification woke the orchestrator): the supervisor logs `wake` once per such turn and writes the session no turn until it ends. `turns` and `lastTurnAt` count only the turns the supervisor wrote. A stdout line that parses as JSON with `type: "result"` is the only thing that sets `idle`. A fresh child is `idle`, because a stream-json `claude -p` does nothing until it reads a line. A session also reports `waiting` (it has work but no free slot), `held` (`budget` or `repo-budget`) and `kept` (`agents`: below). `daemons.inbox` is the inbox session's state with the intake runner's facts laid over it, in the same shape: `busy` while a run is live and, with no inbox child, `idle` while the pool and the inbox are wanted; `turns` adds the runner's finished runs, `lastTurnAt` and `lastResultAt` are the later of the two, `failures` adds the runner's failure streak, and `lastError` is the runner's until a run succeeds. Each change emits a `state` event for `_inbox`.

**Trigger** (edge-triggered per request id). Every `pollMs` (2 s), after every `POST /api/requests` and after every `result`, the pool checks the trust digest, reads the pending requests once and routes each to its scope (`requestScope` in `lib/core/job/requests.ts`). Per session, it sets aside the budget-held requests (below) and takes the ids not yet in that session's `committed` set. If any are left and the session is not `busy`/`stopping`, it spawns a child if there is none (subject to the cap), writes the turn and records the eligible ids as in flight. A working `result` adds them to `committed`, which each tick prunes to ids still pending; a failed one (`is_error`) commits nothing and sets a retry time instead ("Failures" in [Daemon runtime](daemon-runtime.md)). So one request causes at most one turn (a request the session leaves pending can't loop), a request that arrives mid-turn causes exactly one more turn, a child that dies mid-turn drops its in-flight ids so they retrigger, a turn that failed before claiming anything is sent again, and claimed (`in-progress`) requests never count. A pool start spawns no session: job sessions spawn only on demand, and the inbox only for a request type the intake runner doesn't handle, since the runner takes every other inbox request (Intake runner above). `draft` and `direct` requests route to `_office`, which no session serves: each tick the office runner takes the oldest pending one when no office run is live ([Foreman](foreman.md) › Office runs). `gate` requests route to the `_gates` group, which no session serves: each tick the gate runner takes the pending gate requests oldest first and starts a gate run for each, up to `foreman.assistants.parallel` live at once. A run claims its request (session `gate-run:<uuid>`), so no two runs take one gate, and ends with the request acked; a run that fails requeues it (counted) once and then rejects it with a hand-off (`its gate run failed twice`), and a usage limit or a pool stop gives the claim back uncounted. At the `daemon.dailyUsd.office` cap no run starts. With `foreman.enabled` or `foreman.assistants.enabled` off, no gate run starts and pending `gate` requests wait, untouched, for a human.

**Cap and slots.** When `maxConcurrent` job sessions are running, a job with fresh work is marked `waiting` (logged once as `waiting`). Slots go to waiting jobs in the order of their oldest pending request. When a job waits and some job session is `idle` and not kept, the pool stops the idle session with the oldest `lastResultAt` (`idle-stop`, `reason: "slot"`) and gives the slot away; that session resumes its conversation the next time it has work, unless it rotated ([Daemon runtime](daemon-runtime.md) › Rotation). A session is **kept** only while a running agent of its job keeps it; there is no grace after a result. Its agents are the `job.agents` of its job, counted only while `job.lease.driver` is one of the session's ids (current, spawn or past), so another driver's agents (a human's terminal session) never keep it. A running agent keeps it only for 2 h after its `startedAt`, the lease `agent start` gives, so a phantom can't hold a slot forever. A kept session still counts toward the cap: when every running job session is kept, the waiting job stays `waiting` and gets the next slot that frees, which the 2 s tick finds within one poll of the last agent ending. Each tick refreshes `kept` (`agents` or null) for running job sessions. After a job session's `result`, if its job is `done`, `cancelled` or `failed` (or gone) and no pending request routes to it, the pool logs `finished` and stops it (`stop`, `reason: "job-finished"`). Sessions that are off and clean, with no request routed to them, are pruned at the next tick; their files stay.

**Machine cap.** Each project's `daemon.*` alone governs its pool: it caps, orders and evicts only its own job sessions under its own `daemon.maxConcurrent`, so with no machine setting two projects at 4 run 8 job sessions, and one project's waiter, idle session or exit never holds back, stops or pokes another's. The **machine cap** is opt-in: the machine index's `settings.maxConcurrent` (`forge project settings --max-concurrent <1-64|off>`; `null`, the default, is no machine cap). While it is set, the pools share it as one count through a slot gate (`lib/office/slots.ts`): a pool spawns a job session only while it is below its own `daemon.maxConcurrent` and fewer than the cap run across the machine. Other projects' waiters never change the order, and no pool stops another project's session; a job session's exit pokes only the other pools whose last tick held a waiter on the machine cap, and each pool still ticks every poll. Inbox and chat sessions and office and gate runs never count against either cap. Each job session reports why it waits as `waitingFor`: `project` (its own cap, also when both are full), `machine` (below its own cap, held by the machine cap) or null; the session log's `waiting` line is written when waiting starts and when that reason changes, with `cap: 'project'` and `daemon.maxConcurrent`, or `cap: 'machine'` and the machine cap. `/api/p/<project>/state` reports the cap as `daemons.machine: { maxConcurrent, live }`, null without one, and `/api/projects` as `machine.maxConcurrent` (null without one) beside `machine.live`.

**Budget hold.** Limits are per job, so a hold is per session: `resume`, `rework`, `answer` and `revise-spec` requests whose job is at `waiting: budget` and still over a limit (`exceededKeys` in `lib/engine/metrics/budget.ts`) are never sent or committed, and that session reports `held: "budget"`. `approve` (the acknowledgement), `cancel` and job-less requests are never held. Once a human raises or acknowledges the budget, the next tick sends the turn. A `held` log line is written when the session's hold changes. Spend scales with the number of live sessions.

**Repo budget hold.** `budget:` caps what the whole repo spends per UTC day and month (see ["Repo budget"](policies.md#repo-budget)). While a cap is reached under `onExceeded: hold`, every job session's pending `resume`, `rework`, `answer`, `revise-spec` and `approve` waits unless its job is exempt (a retro, or one a human forced past the cap this month), and the session reports `held: "repo-budget"`, which wins over `budget` when both apply. `approve` waits too, because approving is no acknowledgement of the repo cap. `cancel`, gate requests (the gate runner's) and job-less requests (the inbox) are never held, and a busy session finishes its turn. The pool computes the status without writing anything (`write: false`) and reuses it for up to 10 s, recomputing at once when the audit log grows (an ack) or the `budget:` block changes.
