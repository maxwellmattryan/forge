# Dashboard security › Login

Part of [Dashboard security](../dashboard-security.md).

**Login.** The page carries no token: `/` and `/index.html` serve `index.html` as built, so a local process that fetches it learns nothing. `forge dash` prints the **login link**, `http://127.0.0.1:<port>/?project=<name>#k=<token>` (without `?project=` outside a registered project), when it starts the dashboard or reports a running one, and `forge dash url` reprints it; the `--service` banner, which goes to the service's log, and a daemon session's report print the bare URL. The token, 32 random hex characters per process, rides only in the fragment, which a browser never sends to the server or in a `Referer`, and which the server never logs (the activity log records pathnames only).
- Before the app mounts, `dashboard/src/main.ts` takes a `#k=` fragment and clears it with `history.replaceState` before any request, so a failed exchange still leaves no key in the address bar or the current history entry; it then runs the `?project=` redirect and POSTs `{"k": "<key>"}` once to `POST /api/session`, mounting the app once that settles (or after 5 seconds, so a stalled server still shows the signed-out banner). A login link pasted into a page that is already open differs from it only in the fragment, so the browser fires `hashchange` and runs no boot code: `watchLoginFragment` takes the key the same way, ahead of the router, and reloads the page.
- `POST /api/session` is the one `/api` route that needs no login. It still runs dispatch's POST checks (loopback peer and Host, a matching Origin, JSON, size), takes exactly `{"k": string}` (else 400), and compares `k` with the token in constant time. A wrong key is 401 `{"error":"wrong login key"}` and sets nothing, so a forged login link (login CSRF) can't replace the cookie the owner's browser already holds. A right key is 200 `{"ok":true}` with one `Set-Cookie: forge-<port>=<token>; HttpOnly; SameSite=Strict; Path=/`: no script can read it, no other site's request carries it, and it has no `Secure` (plain loopback http), no `Domain`, and no `Max-Age` or `Expires`, so it ends with the browser session. Browsers scope cookies by host, not port, so the name carries the port.
- Every other `/api` route, machine or project, GET or POST, page fetch, event stream, screenshot `<img>` or `/raw` iframe, needs that cookie (present exactly once: a repeated name reads as none, and a cookie named for another port is ignored) or the `x-forge-token` header with one value, the CLI's and the tests' path, each compared in constant time. Without either it answers 401 `text/plain` `not signed in: open the link forge dash url prints` before any handler runs, and no route reads a `?token=` query. 401 means "not signed in"; 403 keeps its meaning, "this request's peer or origin is wrong", and the POST and read guards still run behind the login, so a request that carries the cookie from another site or another loopback port is refused by Origin or Fetch Metadata.
- The dashboard shows a 401 as a signed-out banner naming `forge dash url`: a new browser or profile, a restarted server (a new token) or a `localhost` URL (the cookie is set for `127.0.0.1`) needs the link again, while a new tab on the same origin already has the cookie. The check order, each step answering and stopping: socket peer (403 `not loopback`), Host (421), route match (404, so unknown paths stay 404), login (401), then for a POST Origin (403 `bad origin`), JSON (415) and declared size (413), the row's read guard (403 `bad origin` or `cross-site`), project resolution (404), and the handler.
- The CLI reads the token from `<FORGE_HOME>/dashboard-login.json` (`{pid, token}`, 0600 in the 0700 home), which the serving `forge dash` writes once its server listens and before its record, and which `forge dash --stop` empties; it is read without following a symlink or blocking on a FIFO, at most 4 KiB, and trusted only when its pid is the proven record's and the token is 32 lowercase hex characters. `dashboard.json` never holds the token, so nothing that reads the record (notifications, `forge daemon status`, `forge update`) touches it.
- When `forge dash` opens the browser (a person's terminal, or `--open`), the login link never enters a command line, which `ps` shows every local user and which a Linux browser keeps for as long as it runs: Forge writes `<FORGE_HOME>/runtime/dashboard-open.html` (0600 from creation, atomically, in a 0700 dir), a page whose only content is a meta refresh and a fallback link to the escaped login link, no script, `referrer` off, and passes the opener only that file's path (`lib/integrations/os-service/browser.ts`). The opener runs by absolute path without a shell: `/usr/bin/open`, `xdg-open` or `wslview` from an absolute `PATH` entry only (an empty or relative entry could be a checkout's), `<SystemRoot>\System32\rundll32.exe`, or `FORGE_BROWSER` from the human's own environment, never config. A daemon session passing `--open` or `--no-open` is refused, so text a session reads can't drive the human's browser.

**Who the login stops.** Another local OS user on a shared host or CI box gets no token from `GET /`, a 401 from every `/api` route, a 128-bit key compared in constant time at `POST /api/session`, and a 0600 login file in a 0700 home. Another website in the owner's browser gets no cookie on its requests (`SameSite=Strict`), so they are 401, and one that carried it would still fail the Origin or Fetch Metadata check; its `<img>` loads carry no cookie and meet `Cross-Origin-Resource-Policy: same-origin` anyway. A daemon session misled by tracker or PR text can't read the token from `GET /`, `forge dash url` refuses it before reading anything, and its `forge dash` report carries no key. The key never reaches a server log, a `Referer` or the `--service` log file.
- Residuals: browsers don't scope cookies by port, so if another local user runs a server on another `127.0.0.1` port and the owner opens it in the same browser, that server receives the `forge-<port>` cookie and can replay it with curl (that page's own requests to the dashboard still fail the Origin and `Sec-Fetch-Site: same-site` checks); the browser's global history may keep the visited login link, and the redirect file's `file://` path; the redirect file holds the key, like the login file, until the next open or `forge dash --stop` (a crash leaves it); and a process running as the owner can read the terminal that printed the link, the login file or the browser profile, which is out of scope like every same-user read.
