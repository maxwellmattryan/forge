# Dashboard security › Mandate routes

Part of [Dashboard security](../dashboard-security.md).

## The milestone draft
`GET /api/mandates/:id/draft` (the read guard) and `POST /api/mandates/:id/draft` (the login, Origin and JSON guard) serve a goal mandate's milestone draft and decide it (docs/architecture/foreman/mandates.md "Milestone approval and filing"). Both check the id with `isMandateId` before any path is built. The POST body is exactly `{decision: approve | revise | reject, request, digest, note?}`, with `digest` 64 lowercase hex; any other shape is a 400 with nothing read. It calls the CLI's `decideDraft` as a person (`actor.source: dashboard`), pinned to the request and digest of the GET the card rendered, so a draft that changed since is a 409 and nothing is decided unseen; every other refusal (a missing note on revise, a likely secret, a decision already running, a tracker failure) is a 409 too. Filing runs in the handler, as the tracker contract is synchronous. The card renders every draft, goal, title and error string as Svelte text; the only `{@html}` is `md()` over an issue's why, what to do and done.

## The Office page's mandate routes
The Office page's mandate routes (docs/architecture/foreman/mandates.md "Mandates").

`GET /api/mandates` (the read guard) lists every mandate with its contract, chain, progress (from the CLI's records and the spend ledger, no tracker call), a goal mandate's draft status and its live report card, an unreadable one as `{id, problem}`, plus the latest 50 directives, the classes a mandate may be given and a new mandate's defaults; it carries titles but never a mandate's guidance or goal. The report card carries no free text, so the list may serve it: only counts, finite numbers, `pending`, `null`, `byGate` keys from `WAITING_ON` (a forged `waitingOn` keys as `none`) and the `at` and `finalAt` times `buildReportCard` makes with `toISOString`, never a job title, id, reason, issue ref or actor login.

A closed mandate's row also carries its closing summary's card (`closing`), which `closingCard` rebuilds from `summary.json` (already refused by `readSummary` when it is a link, not a regular file, over 64 KiB, not JSON or newer): a fresh object with only the card's keys, every count a finite number of at least 0, every figure such a number, `pending` or `null`, `byGate` built from the `WAITING_ON` and `none` keys (any other key, `__proto__` included, refuses the card), and the times re-serialised with `toISOString`. Anything else, a card for another mandate included, makes `closing` `null`, so a tampered summary never puts text on the list and the page shows the live card.

`GET /api/mandates/:id` adds the guidance and goal as written, the owner's own words, behind the login and the read guard as `GET /api/chats/:id` is. Both replies pass through `redactDeep` with every known value. The id is checked with `isMandateId` before any path is built: `..%2F…`, `none` or an uppercase id is a 404, an unknown one a 404, and an unreadable file a 409.

`POST /api/mandates` (new) and `POST /api/mandates/:id/edit|pause|resume|close` take the login, Origin and JSON guard and its 64 KiB cap, then a shape check before anything is read: only the term keys (`title`, `milestones`, `labels`, `issues`, `until`, `maxJobs`, `order`, `decides`, `budgetUsd`, `budgetJobs`, `stallCadences`, `stallBounces`, `onUnfinishable`, `scoring`, `pauseBelow` (a number or null), `minScored`, `after`, `body`), plus `title` and an optional `id` (a mandate id; the server picks `m-` and 8 random hex digits when it is absent, as `forge mandate new` does) on new and `updatedAt` on edit; strings, lists and numbers capped (the guidance at 8000 characters, a list at 100 entries of 200); `{reason?: string | null}` for pause and close and `{}` for resume. Anything else is a 400.

The handler then calls `mandateWrite`, the one write path `forge mandate new|edit|pause|resume|close|cancel|delete` uses, under the mandates lock, as a person with `actor.source: dashboard`: every contract refusal (a `decides` class not in `foreman.decides` or reserved with `gate:<class>`, a scope entry starting with `-`, `issues` without `order: listed`, an `after` that would close a cycle, an existing id, a closed or unreadable mandate) is a 409 with the CLI's text, a missing mandate a 404, and an edit whose `updatedAt` no longer matches the stored one is a 409, so a CLI edit or an Office pass pause in between is never overwritten. A refused write writes no mandate file and no audit line.

`POST /api/mandates/:id/cancel` and `POST /api/mandates/:id/delete` take the same guard. Cancel's body is `{reason?: string | null}` (at most 1000 characters), as close's; delete's is exactly `{confirm: "<id>"}`, equal to the path's id, the "type the mandate id to confirm" step any UI must ask for, and a missing, extra or different key is a 400 `body must be {"confirm": <the mandate id>}`. Both shapes are checked before anything is read, then the id with `isMandateId` (a 404). Each calls `mandateWrite` as the CLI's `cancel` and `delete` do, with `actor.source: dashboard`: cancel's `cancel` requests carry `from: dashboard`, a person's source, and the reply adds `cancelled: [{job, request}]`; delete refuses an active or paused mandate and one an open mandate follows (409) and replies `{ok, deleted, jobs}`. An unknown mandate is a 404 and every other refusal a 409 with the CLI's text; a refused call writes no file, request or audit line.

Writes run while the pool runs: a mandate is runtime state, and a change wakes the Office pass. The page renders every mandate title, guidance, reason, capped line, problem, scope entry, directive reason and issue as Svelte text, with no `{@html}`. Residual, as for every dashboard POST: a same-user process that reads the login link or the login file can write a mandate as the owner, within `foreman.decides`.
