# Dashboard security › Support bundle and dev mode

Part of [Dashboard security](../dashboard-security.md).

`GET /api/doctor/bundle` (Settings › Diagnostics › Download support bundle) returns the redacted support bundle (docs/CLI.md "Support bundle") as a zip. It needs the login like every `/api` route, and no token is ever in its URL; an Origin, when sent, must be ours and a cross-site `Sec-Fetch-Site` is refused, so another site can neither read it nor trigger the git and gh work behind it. The optional `job` is checked with `validJobId` before any path is built, every other parameter is ignored (the endpoint never includes agent text or diffs), and the reply is `no-store`, `nosniff` and `Cross-Origin-Resource-Policy: same-origin`. Every file it reads comes from inside the job dir or the runtime dir, both checked to resolve where they should, and is opened with `O_NOFOLLOW | O_NONBLOCK` and read through that same descriptor, so a planted symlink or FIFO is skipped rather than followed or waited on.

`forge dash --dev` (what `npm run dev` runs) changes only where the page and assets come from: the fixed `node_modules/.cache/forge/dashboard-dev/` inside the plugin root, which is exactly as trusted as `dashboard/dist/` (anyone who can write either can already rewrite `lib/server/`). It takes no path, so it can't serve a job worktree's files. The loopback Host, login, Origin and JSON-POST guards and the manifest allowlist are the same in dev mode. The flag is CLI-only: no config key and no `/api` route sets it. A dev dashboard never starts the daemon by itself (only Start does), so a fresh clone of a repo that commits `daemon.enabled: true` doesn't boot a paid session; it serves every project of `FORGE_HOME` with no pool booting, and it refuses to start while a proven machine dashboard runs instead of taking it over.
