# Foreman

Unattended runs stop at every human gate. With `foreman.enabled` (off by default; docs/CONFIG.md "Foreman"), `forge dash`'s gate runner decides the gates the Foreman is allowed to, in code, with one fresh `forge:assistant` process per gate, so a human is needed only where policy says so.

**Routing.** A move (Job model › Moves) that parks a job on `spec-approval`, `split-approval`, `escalation`, `rounds-exhausted`, `conflicts` or RP1's repo proposal park (a `human` wait whose reason starts `repo proposal:` while a proposal is pending, the derived class `repo-proposal`) (a new park, or a different gate) whose class is in `foreman.decides` enqueues one `gate` request `{job, args: {gate, reserved}, from: "forge"}`, unless one for that job and gate is pending or in progress. It does so whoever writes the park: `forge job set`, `forge job advance`'s repeated-failure park, the reconciler, and the syncs in `forge pr sync`, `forge sync` and `forge pr merge`. The policy lives in `lib/engine/pipeline/moves/foreman-gates.ts`; `lib/office/foreman/` keeps the gate runner and its policy checks. `forge pr sync` (never `forge pr merge`) does the same for a job waiting on `pr-review` with changes requested or unresolved threads from someone with write access (`OWNER`, `MEMBER` or `COLLABORATOR`; a stranger's comment alone never starts an unattended rework): `args.gate: "pr-feedback"` and `args.key: <head sha>`, once per head in any status, so a push re-arms it. Failing checks on such a job skip the gate runner: sync records a foreman `rework` itself (`ciHead` on the event dedupes it per head), writes a fixed `feedback.md` with no check text in it, moves the job to `build` and queues a `resume`; a reserved match falls back to the gate. A job in a mandate gets this CI rework only when its mandate delegates `pr-feedback` (read from the CLI's record of the job); otherwise, or when the mandate can't be read, sync queues the `pr-feedback` gate instead, which assist reports reserved, so its gate run hands it off. The **CI rework cap** (`pr.maxCiReworks`, 3) bounds it: counted from the event log (foreman `rework` events with a `ciHead` since a person's latest `human` event), never from `job.json`, so a session can't reset it; at the cap a red head starts nothing, the reason names at most 5 allowlisted check names, a `ci-rework-capped` event is logged once per head, and no `pr-feedback` gate is queued, so the foreman is refused there too. A head the foreman already reworked that is still red (its round ended with no new commit) is never reworked again or sent to the gate: the **CI re-run** (`ciRerun` in `lib/engine/pr/sync.ts`) re-runs its failed GitHub Actions jobs once, only when no check is pending, only runs in the PR's own repo that `gh run view` shows on that head and completed, and at most 5, and logs `ci-rerun`; when they fail again, or nothing could be re-run, it parks the job on `pr-review` with a `CI re-run:` reason and logs `ci-rerun-failed`, once per head, a person's later action included. `reservedFor` is asked without that reason, as without the cap's, and the re-run comes before the cap and never counts toward it. Any head counts, because only someone with write access can push a same-repo branch and fork PRs are never adopted; `forge job round` pulls that head into the worktree before the builder starts. `requestScope` sends every `gate` to `_gates`, a request group no session serves (`validScope` refuses it); the dashboard (`POST /api/requests`) and `forge requests add` cannot create one. No session can list, claim or ack a gate request (claim and ack exit 1): only the pool's **gate runner** (`lib/office/foreman/run.ts`) takes them, in-process. With `daemon.enabled`, `foreman.enabled` and `foreman.assistants.enabled`, each tick hands it the pending gate requests, oldest first, and it starts a gate run (below) for each, at most `foreman.assistants.parallel` (1–16, default 2) at once. Gate runs count against neither `daemon.maxConcurrent` nor the machine cap, and the reconciler's claim-age rule counts a live run as busy. With the foreman off, `assistants.enabled: false` or the daemon stopped, gate requests stay pending for a human and the board shows each gate as a human's. A **timed-out prompt** routes the same way: when a planner, spec writer, builder or integrator replies `NEEDS-PERMISSION` after the supervisor denied one of its permission prompts at `daemon.permissionTimeoutMinutes` (a `permission-timed-out` event inside its run), step's NP1b parks the job on `escalation` with the reason `prompt timed out: <role> needed <tool>, nobody answered it in time` (an eval job fails instead, NP1), once per agent run. The reason avoids the word `permission` because the default `foreman.reserved` lists it; reserved patterns and the security-must-pass rule apply as at any escalation, and an owner who wants these parks kept for a person adds `gate:escalation` or the pattern `prompt timed out`. The assistant's brief gets one `Prompt timed out:` line built from the reason alone: no human saw the prompt, the assistant can't grant it, and the role's notes file says what it needed; it approves only when the work is complete without the call, reworks or revises with a note on going on without it, or escalates so a person can allow it. `draft` and `direct` requests route to `_office`, the office session (Intake and Director loop below), which the pool spawns only while `foreman.enabled` holds.

**Gate runs** (`lib/office/foreman/run.ts`, `attempt.ts`, `decide.ts`, `verdict.ts`). Each gate run, in the supervisor's code with no model session in between:
1. Claims the request in-process (session `gate-run:<uuid>`); a lost claim skips it. Job ids and gate classes are validated before any path or argv is built.
2. With `args.reserved` set, hands off (class `reserved`) and acks `rejected` `reserved: <pattern>`, with no child.
3. Runs assist (`gateAssist`, what `forge job assist` prints; `assistDraft` for a milestone draft), which recomputes `stale` and `reserved` and returns `{model, effort, brief}`; `stale` acks `done` `stale`, `reserved` is step 2, and a refusal acks `rejected` with it.
4. Spawns **one** headless `claude -p --agent forge:assistant` (`buildArgv` with the tools `Read, Grep, Glob, Write` and no Bash, the spawn's deny rules, `--permission-mode dontAsk`, assist's model and effort, and `--max-budget-usd` set to what is left of `daemon.dailyUsd.office` today), with `sessionEnv`, the confinement env, the trust env and `FORGE_DAEMON_SCOPE=_gates`, a scope that refuses every `forge` command. The brief is its first stdin line (`briefLine`: JSON-encoded, at most 256 KiB). This is the run's only model call.
5. Parses the last non-empty line of its result strictly: `^ASSIST: (approve|revise|rework|escalate) · (.+)$`, `·` being U+00B7. The reason is cleaned (no `"`, `` ` ``, `$`, `\` or control characters, whitespace collapsed, at most 200 characters) and must not be empty. A malformed line is asked once more on the same child with a fixed retry message; a second malformed line counts as `escalate` (`malformed verdict`). A malformed reply never becomes a decision.
6. Looks the verdict up in the **gate table** (`GATE_TABLE`): spec-approval → approve-spec / revise-spec / revise-spec; split-approval → approve-split / revise-split / revise-split; escalation and rounds-exhausted → approve / revise-spec / rework; conflicts → approve / escalate / approve; repo-proposal → approve-repos / reject-repos / reject-repos (the repos assist returned); pr-feedback → no action (ack `done` `no action: <reason>`, no resume) / rework / rework; release → approve-release / escalate / escalate; milestone-approval → draft approve / draft revise / draft revise. It records the decision through the same policy checks (`recordForemanDecision`, `decideDraft`), queues a `resume` for the job (never for `release` or a milestone draft) and acks `done` `<verdict>: <reason>`; the job's own session's next `forge job step` turns the decision into the gate's follow-up (["Job model"](job-model.md) › Answered gates).
7. On `escalate` it records a **Foreman hand-off** (class `escalated`) and acks `rejected` `escalated: <reason>`. When the policy refuses the decision, a job that no longer waits on that gate is acked `done` `stale`; otherwise the run hands off (class `refused`) and acks `rejected` with the refusal. No hand-off is recorded for `release` or a milestone draft. `forge status`, `forge job show`, `/api/state` and the dashboard's Needs you card show the hand-off (`foremanHandoff`, derived from events) until a decision answers that park or the job parks again. That is `foreman.escalations: human`, the default. Under `foreman.escalations: foreman`, a job's gate (not `release`, not a milestone draft) that escalates, or whose decision is refused while the job still waits there, goes to the **senior pass** below instead, after the title-only override.

A **title-only request** (a spec-approval gate whose `request.md` has only its title) answered `escalate` comes back as `revise-spec` with the note `title-only request: <reason>` and a fixed `feedback.md`, once per person's decision: with a foreman `revise-spec` standing since the latest person's `human` event, the escalate stands.

**Senior pass** (`lib/office/foreman/senior.ts`, `foreman.escalations: foreman`). An escalate (a malformed reply included) or a refused decision goes through these checks in order (`seniorStart`), and only the last starts a senior pass:
1. The job no longer waits on that gate: ack `done` `stale`.
2. `reservedFor` over the job and the first reason (a `foreman.reserved` pattern, the total-round ceiling, a retro spec): a hand-off of class `reserved`, ack `rejected` `reserved: <match>`. Reserved topics stay with a person in Needs you.
3. A latest security review that isn't `PASS`: the job is shelved (`security review not PASS: a person signs off. <reason>`). No senior pass ever judges it.
4. A first reason that names an injection attempt (the word `injection`, which the assistant's prompt tells it to use): shelved (`first assistant flagged an injection attempt: a person decides. <reason>`). A second model would read the same injected text, so under `human` and `foreman` alike a detected injection ends with a person.
5. A `senior-pass` event for this gate after the job's latest `transition` (one per park): shelved (`senior pass already ran at this park. <reason>`).
6. The office's daily cap reached, or a meter that can't be read: shelved (`the office's daily cap holds the senior pass`).
7. The senior's assist (`gateAssist` with `senior`): `stale` acks `stale`, `reserved` (a mandate hold) hands off as in check 2.
8. The runner logs one `senior-pass {gate, first}` event as the Foreman, then a `senior-start` gate log line, then starts one more `forge:assistant` child through `startAttempt` (the same spawn, confinement, `_gates` scope, tools and meter as step 4) on `foreman.senior.model` and `foreman.senior.effort`, which beats the job's own effort.

The senior brief is the gate's assist brief with three lines before `Untrusted:`: `Senior pass (JSON): {"first":"escalate"|"refused","reason":"<cleaned reason>"}`, `Diff: <the latest round's review dir>/diff.patch` and `Verdicts: approve | revise | rework | shelve | escalate`. Its parser takes `shelve` too (`parseVerdict(text, { senior: true })`), with the same one retry. A senior `approve`, `revise` or `rework` that the gate table maps to an action is recorded through `recordForemanDecision` with the note `senior pass: <reason>`, then one `resume`, ack `done` `<verdict>: senior pass: <reason>`; a pr-feedback `approve` records nothing (`no action`). Everything else shelves the job: `shelve` (`senior pass: <reason>`), `escalate`, malformed twice or a table `escalate` cell such as conflicts' `revise` (`senior pass escalated: <reason>`), a refused decision while the job still waits (`senior pass refused: <refusal>`; one that moved is `stale`), and no verdict, a timeout or a failed turn that isn't a limit (`senior pass failed: <message>`). A stop, a refused spawn or a usage limit gives the claim back as for the first child; the next run finds the marker and shelves (check 5). Every shelve goes through `recordForemanShelve`, which refuses without the runner's authority or when the job no longer waits on the gate the run judged (a person may have answered it while the senior ran, and the job parked at another), then calls `shelveJob` as `FOREMAN_ACTOR` (["Job model"](job-model.md) › Shelve): no hand-off, no resume, its PR left as it is, acked `done` `shelved: <reason>` with the run's outcome `shelved`. The reason is model text and stays on the job (`job.shelved`, the `shelved` event, the ack and the gate log); the note posted to the job's linked issues is fixed text naming the gate, never the reason, because a tracker comment can be public. A refused shelve on a job that moved acks `stale`; otherwise it falls back to a hand-off (class `escalated`, `shelve refused: <message>`). The run's `attempts`, `usd` and `tokens` sum both children (at most 4 attempts), and the activity list shows `shelved` as a warn chip.

**When a run fails** it never leaves a request claimed. A child that exits without a verdict, a failed turn that is not a usage limit, a turn past `daemon.turnTimeoutMinutes` (SIGTERM, then SIGKILL) or an unexpected error requeues the request through `requeueOrphanedRequests` (counted); one requeued before is rejected with `REQUEUE_REJECTED` and handed off (`its gate run failed twice`). After a failure no run starts for the retry wait, doubling from `retryMinMs` to `retryMaxMs`, reset by any run that got a verdict. A usage limit gives the claim back uncounted (`releaseClaim`) and holds every run until `resetsAt`. A pool stop or close kills live runs and gives their claims back; when `forge dash` takes the daemon lock it requeues every in-progress gate request claimed by `gate-run:…`, since no earlier dash's run can still be live. After the child exits, the confine digest is compared with the pool's baseline, as after a session's turn.

**Spend and log.** Each costed turn appends a meter record to `.forge/runtime/meter/_gates.jsonl` (ledger role `assistant`, titled `Foreman gates`; the meter files of the retired assistant sessions still read as `assistant`). `daemon.dailyUsd.office` caps the office session and the gate runs together: at the cap, or when a meter can't be read, no gate run starts. The runner writes JSON lines (`gate-start`, `gate-end`, `gate-held`, `error`, never claude's text) to `.forge/runtime/daemons/_gates.log` with `openAppend`, which `forge daemon log --gates` prints, and seeds its list of the last 50 runs from the newest valid `gate-end` records (`readLogPage`, each field validated).

**Context rule.** The gate runner never reads a job file into a model's context: the brief carries absolute paths, the gate class, config lists and mandate guidance fenced by `fenceImport`, never file content. The `forge:assistant` reads the files and writes `feedback.md` itself on `revise` or `rework`; its only other output is the verdict line.

**Authority.** Only the gate runner records a foreman decision, a foreman release approval, a foreman milestone-draft decision or a Foreman hand-off: it holds a capability object (`issueForemanAuthority()`, a frozen object registered in a module-private `WeakSet`), and no argv, environment or parsed text can produce one. `checkForemanDecision`, `checkMandateGateDecision` and `checkReleaseDecision` take it as `by` and refuse anything else first (`--actor foreman refused: only the Foreman's gate runner in forge dash records foreman decisions`); every check runs before any write, and a refusal leaves `job.json` and `events.jsonl` untouched. From the CLI, `forge job human … --actor foreman` (`approve-release` included) and `forge mandate draft approve|revise --actor foreman` therefore exit 1 in every scope, a person's terminal included. `forge job handoff` no longer exists. `forge job assist` and `forge mandate draft assist` exit 1 in every daemon session and stay read-only views for a person's own terminal. In the office session any `forge job human` exits 1 (`the office session records no gate decisions: forge dash's gate runner decides gates`), and `approve-repos`/`reject-repos` exit 1 in every daemon session. A `FORGE_DAEMON_SCOPE` of `_gates` refuses every command (`forge refuses: a gate run's assistant runs no forge commands`), and a retired assistant session's scope is an invalid scope. With the authority, a decision needs a note, takes no `--link` or `--reason`, and needs the job to be waiting on a class in `foreman.decides` (`pr-review` counts as `pr-feedback`) with an action of that class: `approve-spec`/`revise-spec`, `approve-split`/`revise-split`, `approve`/`revise-spec`/`rework` for escalation and rounds-exhausted, `approve` for conflicts, `rework` for pr-feedback, `approve-repos`/`reject-repos` for repo-proposal, naming exactly the pending set its assist judged. It is refused when a `foreman.reserved` pattern matches the reason, the note, or (for escalation and rounds-exhausted) the `## Why` and `## For the human` sections of `decision.md`, or (for repo-proposal) a pending proposal's reason; a `decision.md` that isn't a small regular file counts as a match, and a security review whose latest recorded verdict is anything but `PASS` (`CHANGES`, `MALFORMED`) refuses every action that accepts the job, at any gate, while `rework` and the revise actions stay the foreman's (`SECURITY_MITIGATIONS`): security always has to pass, so the foreman may fix it but never approve past it. Step keeps reworking such a job past `maxRounds`, up to twice it, before B2 parks it on `rounds-exhausted`. Past the **total-round ceiling** (`pipeline.maxTotalRounds`, by default twice `maxRounds`), which counts every round whoever opened it, B7 parks the job there unless a person (a `human` event whose actor isn't the foreman) reworked or revised since the previous round started, and every foreman action at that park is refused, whatever the security verdict: no gate request is queued for it. A `rework` on pr-feedback also needs a pending or in-progress `gate` request keyed by the PR's current head sha, so the foreman acts only on feedback sync armed for that push. Patterns match case-insensitively as whole phrases (no letter or digit on either side) and are escaped literals, so matching is linear; a `reserved` that isn't a list of non-empty strings makes every gate reserved. In the office session, `forge job set` only carries out a recorded foreman decision: the job must still wait, its latest `human` event must be the foreman's and newer than the park, and the change must be that action's `--state running` with its stage from the gate table, with no `--field`, `--waiting-on` or `--reason`. Of the `forge job` subcommands only `assist`, `human`, `set`, `note`, `show`, `get`, `list` and `step` run there (and `assist` and `human` then refuse). The office drives no job: `worktree create`, `job advance`, `job claim`, `job agent … start`, `pr merge` (any job, with or without `--now`) and `backing down --shared` are refused with `the office session does not drive jobs`. The assistant has no Bash at all (`disallowedTools: Bash, Edit, NotebookEdit`, and a gate run denies Bash again), so text it reads reaches the decision only through its one-line verdict, which the policy checks judge like any other note.

**The release gate class** (lib/engine/release/approval.ts). No job waits on a release, so `release` is routed from the plan, not a park: `forge release plan --job <id>` logs `release-planned {planHash}` (the full sha256, unless the job's latest one already has it) and, when the foreman decides `release`, enqueues one `gate` request `{job, args: {gate: "release", key: <planHash>, reserved}}`, unless one for that job and key exists in any status, so a gate left for a human is never re-armed for the same plan. "Decides" means `foreman.enabled`, `release` in `foreman.decides`, and no `gate:release` in `foreman.reserved`, which the defaults keep: `decides()` drops every class reserved with `gate:<class>`, so reserved wins for every gate and caller, and a `gate:` entry naming no class makes `reservedMatch` fail closed. `forge job assist <job> --gate release` is `stale` unless release.json selects the job, its latest `release-planned` is release.json's hash and that hash has no approval; its brief names release.md, config.yml (`release`, `repos[].release`) and the job's request, spec and decision paths, plus `Release plan: <path> (plan <hash12>)`. A gate run's `approve-release` (`recordForemanDecision`, through `checkReleaseDecision`) checks, before any write: the runner's authority; a note and no `--link`, `--reason` or `--repo`; the policy (each refusal names enabled, decides or `gate:release`); a readable release.json selecting this job; `freshPlan` recomputed from config and the clones matching it; the job's latest `release-planned` being that hash; a pending or in-progress `release` gate request keyed by it; no approval for it yet; and `reservedFor` over the job's reason and the note, which also refuses a latest security review that isn't PASS. It then logs one `release-approval {planHash, note, actor}` event and nothing else: no `human` event, no state change, no resume and no `SET_AFTER` entry. `forge job human <job> approve-release` is refused everywhere, with or without `--actor foreman`: a person approves at `forge release run`'s prompt. `forge release run` without a terminal passes a publish step only when the job has a foreman `release-approval` whose `planHash` is the plan it just recomputed, the foreman still decides `release`, the job's mandate (if it is in one) still delegates `release` and is neither paused nor closed (`releaseMandateRefusal`, read again at run time), and `reservedFor` over the job and the approval's note is null; the result carries `approvedBy: "foreman"`. `forge release status`'s `approval` follows the same rule: once the approval stops counting it reports `{owner: 'human', status: 'pending'}`. A terminal always asks, a manual step still needs one, and the run itself stays refused in every daemon session, so a human or CI starts it.

**Release gate threat model.** The attackers are a gate run's `forge:assistant` misled by text in release.md, the config or a tracker; a job, inbox, office or chat session posing as the foreman; and a Bash-capable agent writing `events.jsonl`, `release.json` or the request inbox directly. The authority check and the reserved note and security checks stop the first two; a forged or reused request fails the key match against the recomputed plan; an edited or stale release.json fails `freshPlan`; an approval for another plan or by another actor is ignored at run time, and so is one left over after the owner takes the class back or narrows, pauses or closes the job's mandate, because the policy and the mandate are re-read every time. Residual risk: in a repo that delegated `release`, a process that can append to the job's `events.jsonl` can stand in for the foreman's approval of the current plan. It still can't change what runs (commands come from config and the recomputed plan), and no daemon session can start the run; in a repo that did not delegate, a forged approval does nothing.

**A mandate's release** (lib/engine/release/mandate.ts). An `until: released` mandate (effective only under `foreman.ship: release`) is the one subject of the `release` class that isn't a job. When the Office pass would close it, it plans `{kind: 'since', tag, mandate, heads}` instead, `tag` being the root repo's latest tag reachable from HEAD (`git describe --tags --abbrev=0 HEAD` through the pinned git runner, then `assertSafeRef`) and `heads` each planned repo's HEAD commit by label, which the planner reads again on every recompute (`keptHeads` keeps a repo's planned head once a step that acts has run there under that plan's state.json); `planHash` covers `selection.mandate` and `heads`, so the plan is the mandate's and no plain `--since` plan's, and a commit that lands after the plan, or after its approval, makes it stale. Its records go to the repo audit log, outside every session's write roots: `mandate-release-planned {mandate, planHash, tag, actor}`, `mandate-release-approved {mandate, planHash, note, actor: foreman}` and `mandate-release-finished {mandate, planHash, actor}`, read back only when well formed (a mandate id, a 64-hex hash, a foreman actor for approvals). The pass also logs a `release` directive, notifies `gate` with reason `mandate-release` (on the first plan and on one after a release ran, not on a re-plan of a plan that never ran), and queues one job-less gate request `{job: null, args: {gate: "release", mandate, key: <planHash>, reserved: null}}` when the Foreman decides `release` and `mandateReleaseRefusal` (lib/office/foreman/policy.ts) is null, at most one per mandate and hash in any status. `mandateReleaseRefusal` is the mandate's policy, in order: the file can't be read, it is closed, it is paused, its cut `decides` leaves `release` out, its effective `until` isn't `released`, or a reserved pattern matches its title or a title of one of its live or archived jobs. Its gate run's assist (`assistMandateRelease`, what `forge mandate release assist <id> --request <rid>` shows a person, refused in every daemon session) is `stale` unless the mandate's release state is `pending` and its latest planned hash is the request's key; its brief names release.md, config.yml (`release`, `repos[].release`), `Release plan: <path> (plan <hash12>)`, the mandate's done jobs as `Mandate jobs (JSON): [{job, pr, repos}]` (no titles) and the guidance fenced. On an `approve` verdict the gate runner records the approval through `approveMandateRelease`, which checks, before its one write: the runner's ForemanAuthority; a note; the policy (enabled, `release` in `foreman.decides`, no `gate:release`); `mandateReleaseRefusal`; a readable release.json selecting this mandate; `freshPlan`; the mandate's latest planned hash being that plan's; a pending or in-progress gate request for it; no approval yet; and no reserved pattern in the note. `forge mandate release approve <id> --actor foreman` reaches the same checks and so is refused in every scope; without `--actor foreman` it is refused before anything is read. A `revise` or `rework` verdict escalates, which leaves the plan for a person at `forge release run`. `forge release run` and `forge release status` take `mandateNarrow` from the CLI and count a foreman approval of a mandate plan only through `mandateReleaseApproval`, which asks `mandateReleaseRefusal` again; without it they count none (fail closed). `forge release plan --mandate <id>` re-plans after the pass planned once, or makes the first plan while `otherReleasePlan` finds release.json holding a plan the pass won't write over (one it can't read, or another plan whose run hasn't finished), for an active mandate whose effective `until` is `released`, and is refused in every daemon session. The pass closes the mandate when its latest plan has a `mandate-release-finished` event or a finished state.json and no mandate job (live or archived, done) merged after that plan's `mandate-release-planned` event (its PRs' latest `mergedAt`, else its latest transition to `done`); a later merge makes the finished plan `stale`. Otherwise it waits with `blocked: release: <detail>` and no budget pause, cadence stall or `direct` request. It plans only an unplanned mandate or a stale plan with no run of it in progress, and `planMandateRelease` with `byPass` refuses when release.json holds a plan that isn't this mandate's and whose run hasn't started (`blocked by another plan, plan it with forge release plan --mandate <id>`), so it never overwrites another plan or a started run. A stale plan whose run has started says `…; re-plan with forge release plan --mandate <id> --force`, and `freshPlan`'s refusal of a stale mandate plan names the same re-plan rather than a plain `forge release plan`, which would replace the mandate's plan.

**Mandate release threat model.** The attackers are an agent session (a job session, or the office or a gate run's assistant misled by tracker or PR text) and a hostile checkout; they want a publish without approval, or to re-arm or reuse an approval. A planted or edited release.json fails `freshPlan`, its hash covers the mandate and the planned heads, and `readPlanFile` refuses a `selection.mandate` that isn't a mandate id or `selection.heads` that aren't commit ids; a merge after the approval changes a head, so the approval never stands for code it didn't see; only the gate runner's in-process authority records an approval, and no `forge` command can; `--mandate` is refused in every daemon session and requests are once per mandate and hash in any status, so no session re-arms a gate; the policy is asked again at approval, run and status, so narrowing, pausing, closing or lowering `ship` ends an approval; an approval is matched by mandate and hash, so it never stands for another mandate's plan or a plain `--since` plan; the pass only plans, and `refuseRun` keeps every daemon session from running; and the tag reaches git argv only after `assertSafeRef`. Residual risk: in a repo that delegated `release`, a process that can append to `.forge/runtime/audit.jsonl` can stand in for the foreman's approval of the current plan, as for a job's `events.jsonl`; it still can't change what runs, and no daemon session can start the run. The same writer can mark an acting step started in state.json so a recompute keeps that repo's planned head; it gains nothing it couldn't get by forging the approval.

**Mandates.** A mandate (docs/CONFIG.md "Mandates") is the owner's standing instruction to the Office: `.forge/runtime/mandates/<id>.md`, runtime state outside every session's write roots, written by the owner only through `mandateWrite` (`lib/office/mandates/store.ts`), under one lock with every contract check before the write: `forge mandate new|edit|pause|resume|close`, refused in every daemon session, and the dashboard's Office page (`POST /api/mandates` and `/api/mandates/:id/edit|pause|resume|close`, behind the token, Origin and JSON guard, as `actor.source: dashboard`, docs/architecture/dashboard-security.md). An edit from the page is pinned to the `updatedAt` it read, so a CLI edit or an Office pass pause in between makes it a 409 rather than being overwritten. A job joins one at creation (`forge job new --mandate`, or its split parent's) and keeps it: `mandate` is a locked field. For a job in a mandate, the classes the Foreman decides are `decides(config)` ∩ the mandate's written `decides`, whatever its status (except for `release`, below), read through `jobMandateDecides` from the CLI's record of the job (`stateFile`), never the session-writable `job.json` mirror. Four places narrow: `checkForemanDecision` refuses, after the `foreman.decides` and class-reservation checks; a gate run's `approve-release` refuses the `release` class the same way (it has no park, so it goes through `checkReleaseDecision`, which takes the job's refusal from `mandateRefusal` after its policy checks and before its plan checks); `gateOwner` shows the gate as a human's; and assist (`gateAssist`, `forge job assist`) returns `reserved: "mandate <id>: …"`, after `classReservation` and before `reservedFor`, so the gate run's reserved path hands the gate off. Engine code can't import `lib/office/`, so two engine paths take the narrowing as a function from the CLI: the CI rework in `forge pr sync` and `forge sync`, which a job in a mandate gets only when its mandate delegates `pr-feedback` (otherwise sync queues the gate, Routing above), and `forge release run` and `forge release status`, which count a foreman `release-approval` only while the job's mandate still delegates `release`. For the `release` class only, a paused or closed mandate also delegates nothing (`releaseMandateRefusal`), because publishing can't be undone: a gate run's `approve-release` is refused with `--actor foreman refused: mandate <id> is paused: release left for a human` (or `closed`), `forge job assist --gate release` reports it reserved, and an approval already recorded stops counting once the mandate narrows, pauses, closes, is deleted or can't be read. For every other class a paused mandate still delegates, so its in-flight jobs finish, and a **closed** mandate delegates nothing: `jobMandateDecides` returns `decides: []`, and `mandateRefusal` checks it first, refusing with `mandate <id> is closed: left for a human`. The **bounce hold** comes after the decides check: a job waiting on a counted gate (every wait but `pr-review` and `external`) that it has entered `stall.bounces` times since a person's latest `human` event (`bounceHold`, `lib/office/mandates/progress.ts`, over `readEvents`, the CLI copy; a reason change while already waiting there is no new entry, and a foreman decision never resets the count) is a person's: `checkForemanDecision` refuses with `--actor foreman refused: mandate <id>: back at <W> <n> times (stall.bounces <k>): left for a human`, `forge job assist` returns that text as `reserved`, and `gateOwner` returns `human`. It is checked at decision time because a gate run decides a park within seconds, long before the next Office pass. A mandate file that is missing or can't be read safely delegates nothing (fail closed). One engine path is not narrowed: `maybeEnqueueGate` (a queued request costs only the assist call that hands it off). When the gate is delegated, the assistant's brief carries a `Mandate:` line and the body fenced by `fenceImport`, and `forge mandate show` returns it fenced too, never raw.

**Mandate threat model.** The attackers: a daemon session (a job session, the inbox, the office or a chat) or a gate run's `forge:assistant`, misled by tracker, PR or mandate-body text; the builder agent; and a Bash-capable agent writing files under its write roots. Each bypass fails: detaching a job with `forge job set --field mandate=…` is refused (a locked field); editing `.forge/jobs/<id>/job.json` changes nothing Forge reads, because the narrowing reads the CLI record; widening a mandate's `decides` or creating a permissive one from a session is refused under `FORGE_DAEMON=1` before anything is read, the mandates dir is outside the session write roots (`lib/office/session/confine.ts`), and `decides` can never exceed `foreman.decides` minus reserved classes anyway; deleting, symlinking or corrupting the file makes the mandate unreadable, which delegates nothing; moving a split child to another mandate is refused; the body reaches briefs and `show` only fenced; milestones and labels, which reach `gh` as arguments through the tracker's `scope`, can't start with `-` or hold a control or hidden character (and the GitHub adapter throws on a leading `-` before gh runs); and the id grammar keeps the file inside the mandates dir. Joining a mandate with `--mandate` is allowed from a session, because it only narrows. The dashboard's Office page adds two more attackers, another site in the owner's browser and a local process holding the page token, and writes through the same `mandateWrite`: a cross-site POST that creates or widens a mandate fails the token, Origin and JSON guard; a cross-site read of the guidance fails the detail GET's token; a `decides` past `foreman.decides` or onto a `gate:<class>` reservation, a scope entry starting with `-`, or an id that climbs out of the mandates dir (`..%2F`, `none`, uppercase) is refused before anything is written (409, 400 or 404); an oversized or trickled body hits the guard's 64 KiB cap and timeout and the shape caps; an edit is pinned to the `updatedAt` it read, so a concurrent CLI edit or pass pause is never overwritten; every write logs `actor.source: dashboard`; and every mandate string renders as Svelte text. Residual, as for every dashboard POST: a same-user process that reads the page token can write a mandate as the owner. As for the Foreman as a whole, `FORGE_DAEMON= forge mandate …` from a Bash-capable session reads as a human: the line guards a misled model, not a hostile one.

**Intake** (#434, phase 1). A **goal mandate** (`forge mandate new [<id>] --title T --goal "<text>"`, or `--goal-file F` with `-` for stdin) states what to achieve instead of which issues to run: its scope stays empty, and the goal is set once, stored as the last frontmatter key on one JSON-quoted line (the YAML subset's block scalars don't round-trip every text), and shown only through `fenceImport` (`mandateGoal`). `new --goal` queues the first **draft request** `{type: "draft", job: null, args: {mandate}, from: "forge"}`, and `forge mandate draft start <id>` queues another for an active goal mandate unless one is pending or in progress; nothing else writes one (`forge requests add` and `POST /api/requests` refuse `draft`), and `requestScope` sends it to `_office`, so only the office session turns it, while `daemon.enabled` and `foreman.enabled` are on. A **drafting run** is two CLI calls with one `forge:drafter` between them, as for triage and `forge job assist`: the office claims the request, runs `forge mandate draft prepare <id> --request <rid>`, which writes the survey and returns the brief with the roster's model and effort for `drafter`, spawns the drafter with that brief, runs `forge mandate draft record <id> --request <rid> --agent-id <id>` whatever line it returned, and acks (`done` with `drafted: <n> issues in <w> waves` or `stale: <reason>`, `rejected` with a refusal). The office never reads the survey, the staging file or the draft. The files: the **survey** (`.forge/runtime/mandates/<id>/survey.md`, at most 64 KiB: a column-0 data line, the fenced goal and guidance, Forge's own stats, every tracked `AGENTS.md` with its first prose line, and the tracker's open milestones (`Tracker.milestones`, optional) and open issues, each list in one `fenced()` block with every title through `oneLineTitle`); the **staging file** the drafter writes (`<worktrees.root>/_office/drafts/<id>.json`, inside the office session's write roots, so the drafter's Write passes the write guard, and cleared by `prepare`); and the **milestone draft** `record` stores once it passes `draftProblems` (`.forge/runtime/mandates/<id>/draft.json`, a versioned shape, `lib/core/versions/draft.ts`), with a `mandate-draft` audit event. `forge mandate draft show <id>` reads it back with its status (`queued`, `drafting`, `ready`, `unreadable`, `failed` or `none`), its latest request and its spend. **Spend**: `record` first appends one `agent-end` line to `.forge/runtime/mandates/<id>/ledger.jsonl`, with the drafter's usage from its transcript when `--agent-id` finds one. `metered: true` in a daemon session says the office session's supervisor meter already holds that cost, so it counts against `daemon.dailyUsd.office` and no sum adds it twice; a person's own run is `metered: false` and is recorded only on the mandate's ledger. A ready draft waits at the `milestone-approval` gate (below); the mandate's `budget` over drafting spend comes with the director loop (#538).

**Intake threat model.** The attackers: the owner's goal or guidance and tracker titles misleading the drafter; a job or inbox session misled by tracker or PR text into starting a drafting run, or writing or replacing a draft that approval would file; the builder agent; and a Bash-capable session writing under its write roots. Each bypass fails: `prepare` and `record` exit 1 in any daemon scope but `_office` (and with a missing or invalid scope) before anything is read; draft requests are refused from `forge requests add`, `POST /api/requests`, and `forge mandate draft start` or `new --goal` in any daemon session, so no session can queue drafting spend; both calls need `--request` naming an in-progress `draft` request for that mandate, looked up in the listing before any path is built from it, so a draft can't be recorded without a claimed run or onto another mandate; the staging file is read through `readRegular` (no link, no FIFO, at most 256 KiB), a link at the drafts dir is refused, and `prepare` removes a stale one; `draftProblems` refuses unknown keys, hidden or control characters, `existing` refs `checkIssueRef` refuses (a leading `-` never reaches `gh`) and file paths that are absolute, start with `-` or climb with `..`, so filing never sends such text; tracker titles can't leave their fence, because `fenced()` picks a longer fence and `oneLineTitle` removes hidden characters and line breaks; the drafter has `tools: Read, Grep, Glob, Write` and no Bash or web tools; and `milestones` builds its `gh api` path from `repoSlug`'s checked slug only. Residual risks: a Bash-capable session can overwrite the staging file between `prepare` and `record`, but the draft stays an inert, checked file until someone decides it, and the decision pins the digest of the bytes the decider saw; `FORGE_DAEMON= forge mandate draft …` from such a session reads as a person, as for every Office check; the survey and the ledger live in the runtime dir, outside every session's write roots.

**Milestone approval and filing** (#434, phase 2). A goal mandate's ready draft waits at the `milestone-approval` gate, a gate class that belongs to the mandate, not a job: no job waits on it, so the job tables and `forge job assist` leave it alone (`assist --gate milestone-approval` is always `stale`). Its status (`draftGate`, `lib/office/mandates/gate.ts`) is `filed` once the mandate's `filedAt` is set, `filing` while `filing.json` exists unfinished, `pending` for a ready draft of a goal mandate that isn't closed, else `none`; `forge mandate draft show` and `GET /api/mandates/:id/draft` give it with the draft's **digest**, the lowercase hex SHA-256 of the exact `draft.json` bytes read (never stored in the file). Three decisions, one function (`decideDraft`) for the CLI and the dashboard: `forge mandate draft approve` files the draft; `revise --note` queues another drafting run whose brief carries the previous draft's path, its title and the note, the last two through `fenceImport` (when a `draft start` queued one first, revise exits 1 and queues and logs nothing); `reject` closes the mandate (`milestone draft rejected: <note>`), files nothing, and starts the next link of its chain. A note is 1–2000 characters of visible text on lines. `--request` and `--digest` pin the draft read (the dashboard always sends both), and every decision runs under `locks/mandate-decide-<id>` with a one-second wait, so a double click, a terminal and a gate run can't decide twice. **Who decides**: a person, in their own terminal or the dashboard; under `FORGE_DAEMON=1` a call without `--actor foreman` exits 1 in every scope before anything is read, and `--actor foreman` exits 1 everywhere (Authority above). The default `foreman.decides` leaves the class out, so a project lists it to delegate it, and a mandate's own `decides` narrows it further. When both delegate it, `forge mandate draft record` queues one job-less `gate` request (`{gate: milestone-approval, mandate, key: <draft request>, digest, reserved}`, which `enqueue` accepts only with a valid mandate id) that routes to `_gates`; its gate run takes assist from `assistDraft` (what `forge mandate draft assist <id> --request <gid>` prints: a brief of paths and fenced data, never draft text) and records `approve` or `revise` through `decideDraft` with its authority, which `checkMandateGateDecision` (`lib/office/foreman/policy.ts`) judges with the same `foremanAuthorityRefusal` and `foremanPolicyRefusal` as job gates, plus a matching in-progress gate request for the current key and digest and a cap of two foreman revisions per mandate (`FOREMAN_REVISIONS_MAX`, until the mandate's budget lands). Reject, and retrying a stopped filing, stay a person's. Every recorded draft also queues a `gate` notification (`milestone-approval`, no free text). **Filing**: the CLI, never an agent, reads the draft once (the bytes give both the digest and the body filed), runs every pre-flight check before any write (the tracker has `createMilestone`, the title is a valid scope milestone with no leading, trailing or repeated whitespace, the converted mandate passes the contract, no open milestone or item has the title, each `existing` ref is an open item of this tracker, and one secret scan over every outgoing string), then writes `filing.json` (with the digest) and the `mandate-draft-approved` event, creates the milestone, files each issue in wave order (`wave-<n>` labels, never prefixed, so triage sees them; reuse and amend move an existing item in), recording each ref as it lands, and last writes the mandate with `scope.milestones: [<title>]` and `filedAt` (`mandate-filed`). On GitHub every `@name` in an issue body, an amendment or the milestone description gets a zero-width joiner after its @ (outside a fenced code block that opens at column 0), so filing notifies no one. A tracker call that throws keeps the record with its `error` (the gate is `filing`); the refusal names where filing stopped, with the error JSON-quoted for a person and left out for the foreman (it stays in `filing.json`), since a tracker error can echo the draft's title. Approve again resumes without filing anything twice, adopting the one open item with the exact title for a key that was started but not recorded; a retry refuses once `draft.json`'s digest differs from the record's. The filed mandate is an ordinary scoped mandate whose issues go through readiness triage like any other.

**Milestone approval threat model.** The attackers: a daemon session (a job session, the inbox, the office or a chat) misled by tracker, PR, goal or draft text; the drafter, whose output reaches the tracker and the office's context; the `forge:assistant` that reads the draft; another site in the owner's browser; the builder agent; and a Bash-capable session writing under its write roots or the runtime dir. Each bypass fails. A session deciding as a person: every daemon call without `--actor foreman` is refused before anything is read. The foreman outside policy: the authority, `foreman.enabled`, `foreman.decides`, `gate:milestone-approval`, the mandate's own decides (an unreadable mandate delegates nothing), a reserved pattern anywhere in the goal, the draft or the note, reject, a stopped filing, a missing or mismatched gate request and the revision cap are each a refusal. Approving bytes nobody saw: the request and digest pins hold for the dashboard and the foreman, filing parses the digested bytes, and a retry checks the record's digest. Drafter text steering the office: `draftProblems` and filing's pre-flight name positions only (`issues[2].files[0]`, "the draft's milestone title"), a foreman's stopped filing carries no tracker error, the assistant brief holds paths and fenced data, and the revision note and previous title reach the drafter fenced. Filed text pinging people on GitHub: mentions get a zero-width joiner after the @. A credential smuggled to the tracker: one scan over every outgoing string, plus the guarded adapter's own scan of `createMilestone` and `milestoneAdd`. Option injection into `gh`: the milestone title can't start with `-`, titles go in `=` or `-f key=value` arguments, labels are fixed `wave-<n>`, refs go after `--`. A forged job-less gate request: `enqueue` takes one only for this class with a valid mandate id, `forge requests add` and `POST /api/requests` still refuse `gate`, and one that doesn't match the current key and digest decides nothing. A cross-site POST: the token, Origin and JSON guard. Double filing: the decision lock plus the record. A planted link at `draft.json` or `filing.json`: `readRegular` refuses it, and an unreadable record files nothing. Residual risks: a Bash-capable session can rewrite `draft.json` and the gate request together before anyone reads them, and the owner or assistant then judges the rewritten (still rule-checked) draft, which is exactly what files; forging `args.foreman: true` only lowers the revision cap; and `FORGE_DAEMON= forge mandate draft approve` reads as a person, as for every Office check.

**Director loop.** Enforcement is code and judgement is the model's. The **Office pass** (`forge office pass`, `lib/office/mandates/pass.ts`) is deterministic code with no model, which `forge dash` runs as a child (`runPassChild`, outside any daemon scope, with sync's env and git pins) every `foreman.cadence` minutes, at pool start, when a mandate file changes and when a job session's result leaves a mandate job `done`, `cancelled`, `failed` or `waiting` (docs/architecture/daemon.md "Periodic Office pass"). It is refused in every daemon session, the office's included, and writes nothing with `foreman.enabled` off. Under the `<locks>/office` lock it reads every mandate, skipping goal mandates whose scope is still empty and following up closed ones (the final card, below), and for each other one, in creation order: applies `onUnfinishable` to every failed job (`cancel` moves it to `cancelled`; `park` leaves it failed), logging a `mandate-unfinishable` job event that makes the job **handled**; stalls each in-flight job the bounce hold holds, once per park (`mandate-stalled` job event, `mandate-stalled` notification with the job); **closes** an active or paused mandate with no tracker error, no candidates, no in-flight and no unfinishable job, writing its closing summary (`.forge/runtime/mandates/<id>/summary.json`, versioned in `lib/core/versions/mandate-summary.ts`), which carries the mandate's report card built from the same progress at the close time (`buildReportCard`, `lib/engine/metrics/report-card.ts`, the builder `forge stats --mandate` and `GET /api/mandates` use for the live card), queuing the mandate's retro (below), and evaluating again every mandate whose `after` is the closed one, so the next link of a chain starts in the same pass (an effective `until: released` mandate first waits for its release, A mandate's release above, and is neither paused nor stalled meanwhile); pauses an active mandate at its budget (`spentUsd >= budget.usd`, or `started >= budget.jobs` with candidates left); otherwise pauses one below its **quality floor** (`qualityFloor` in `progress.ts`: `quality.pauseBelow` set, at least `quality.minScored` merged jobs scored 0-5, and their running median, `runningScore` in `report-card.ts`, strictly below the floor; reason `quality: median <m> below pauseBelow <f> over <n> scored jobs`, notification `mandate-stalled` with the reason `mandate-quality`); and otherwise pauses an active mandate with no progress for `stall.cadences × foreman.cadence` minutes (no job created or moved, no running agent). At most one pause lands per pass, in that order. A mandate the owner resumes while still below its floor stays blocked (`start` refuses it) and the next pass pauses it again. **The retro at close**: when a mandate moves to `closed`, by the pass's close or by the owner's (`mandateWrite`'s `close` that writes, from `forge mandate close` or the Foreman page), `queueMandateRetro` (`lib/engine/evals/retro.ts`) queues one `{type: "retro", job: null, args: {mandate}, from: "forge"}` over the mandate's live and archived jobs, under the `<locks>/retro-queue` lock the cadence retro takes, and the caller logs a `retro` directive (`queued request <rid> over <n> jobs`) with its own actor: the foreman for the pass, the owner for a close. It queues none with the foreman off, for a mandate with no jobs (a rejected goal draft), or when a `retro` request for that mandate exists in any status, so it is once per mandate and a scan never queues retros for mandates closed before. The inbox turns it into a retro job scoped by `forge retro prepare --mandate` (docs/IMPROVEMENT.md §3), whose spec gate stays a human's; nothing on this path writes `.forge/notes/`, `.forge/reviewers/` or `.forge/config.yml`. `enqueue` and `POST /api/requests` refuse a `retro` request whose `args.mandate` is not a mandate id, and the CLI checks it again with `mandateTarget`, since the inbox puts it on a command line. **The final card**: the closing summary carries `outcomesFinalAt`, the close time when the card at close had no open outcome, else `null`. For each closed, readable mandate whose summary reads with no problem and `outcomesFinalAt: null`, each pass builds the live card (`jobFigures` over the pass's records, `buildReportCard` at the pass time) and, once it has no open outcome, rewrites `summary.json` once through `writeSummary` (a confined dir and an atomic replace, under the office lock): the new card and `outcomesFinalAt`, every other field as written at close. The pass's result lists those mandates as `finalized`. A closed mandate with no summary, or an unreadable one (`readSummary` reads through `readRegular`, so a planted link is refused), is skipped. Each status write goes through `writeMandate` with the foreman as the audit actor, and lands only while the mandate still has the status and `updatedAt` the pass read, so an owner's edit, pause or close wins. When some active, unblocked mandate has a candidate window or a resumable job and no `direct` request is pending or in progress, the pass queues one `{type: "direct", job: null, args: {}, from: "forge"}`; `requestScope` sends it to `_office`, and nothing else writes one (`forge requests add` and `POST /api/requests` refuse it). A mandate's **jobs** are the live jobs (the CLI records) and archived jobs whose `mandate` is its id, classed against its effective `until` as reached (`merge-ready`: done, or at `pr` waiting on `pr-review` with a PR; `merged` and `released`: done), handled, unfinishable or in flight. Its spend is every ledger bucket of those jobs (never the office session's own spend, which stays under `daemon.dailyUsd.office`), and `started` counts jobs whose parent is not one of its own, so split children don't count. Its **candidates** are the scope items (`order: listed`: the written issues, with no tracker call; otherwise one `Tracker.scope` call per milestone, or one for labels alone) that are not needs-info, carried by no live job and not skipped, ordered as written, by priority then number, or by number (`graph`: the Foreman orders them by the issues' stated dependencies), and taken from the first milestone that still has open work. The **window** is the first `free` candidates under `listed` and the first `min(10, 3 × free)` otherwise, empty while the mandate is blocked (not active, at its budget, below its quality floor, the repo budget held, a tracker error, or the foreman off). On a `direct` request the office session (the skill's "For each direct request") runs `forge office survey`, which lists each active mandate's window with one-line titles, its resumable jobs, its latest 5 directives and its guidance fenced; with `foreman.surveyors.enabled` it runs `forge office board <id>` for each mandate with work in flight and hands the brief to a `forge:surveyor` (Read only, at most 5 `SURVEY:` lines over a board of one fenced line per job); then it runs `forge office start <id> <ref> --reason R` for up to `free` candidates, `forge office resume` for resumable jobs, and `forge office note` when it starts nothing deliberately. `start` re-checks everything under the office lock: the mandate is active and not blocked (a held repo budget exits 4), and the ref's stored form is in the window recomputed now (under `listed`, only the first). An issue the tracker reports closed or missing is skipped; otherwise `startFromRef` creates the job with `mandate` set and split mode never, claims the issue, and a `resume` with `args.intake: run` is queued. The office session runs on `foreman.model` and `foreman.effort` (`--model` replaces every one in `daemon.command`). Each choice and enforcement is a **directive**, a `directive` event in the repo audit log (and on the job it names) with `{mandate, action, issue, job, reason, actor}`, the action one of `start`, `resume`, `note`, `skip`, `pause`, `close`, `stall`, `park`, `cancel`, `release` (the pass planned a mandate's release) or `retro` (a mandate's close queued its retro); `forge audit`, `forge job audit` and `forge mandate show` (with `progress` and the closing `summary`) list them.

**Director threat model.** The attackers: the office session misled by tracker titles, mandate guidance or a surveyor's lines; a job, inbox or chat session or a gate run's assistant misled by tracker or PR text; the builder agent; and a Bash-capable session writing under its write roots (the job folders and worktrees, so a job folder's `job.json` and `events.jsonl` mirrors). Provenance stays the unauthenticated `FORGE_DAEMON_SCOPE`: the line guards a misled model, not a hostile local process (`FORGE_DAEMON= forge …` reads as a person). Each bypass fails. Starting an issue outside the mandate's scope or order: `start` recomputes the window from the tracker and refuses. Exceeding `maxJobs`, the mandate's budget or the repo budget, or starting under a paused, waiting or closed mandate: re-checked at `start`. Starting work from another session: `forge office survey|board|start|resume|note` are refused outside the office session and a person's terminal (`refuseOutsideOffice`). Triggering enforcement early: `forge office pass` is refused in every daemon scope. A forged `direct` request: refused from the CLI and the dashboard; a file-planted one costs at most one office turn, under `daemon.dailyUsd.office`, and every action in that turn is re-checked. Hiding spend or membership by editing a job folder's `job.json`: progress reads the CLI records and the archive. Lifting a mandate over its quality floor: a high score forged in a job folder's `job.json` is never read (the floor, too, reads the CLI records and the archive), a malformed or out-of-range value (`9`, `'1'`, `NaN`) never counts, and the floor itself sits in the mandate file, outside every session's write roots, which only `forge mandate edit` outside a daemon session changes; the score value itself is the scoring pipeline's to trust. Resetting a bounce count with a fake `human` event in the job folder's `events.jsonl`: counts read `readEvents`, the CLI copy. A gate run deciding the K-th bounce, or a closed mandate's gate: refused by `mandateRefusal`. Injection through the board or the survey: titles and reasons are one line and fenced in the board, the guidance is fenced, the surveyor has `tools: Read` only, and its lines reach only the Foreman's choice among already-checked candidates. Option injection into gh or claude argv: milestones and labels never start with `-` (the contract, and the adapter's own throw), and `foreman.model` passes `validModel` (its pattern starts alphanumeric) and is its own argv word after `--model`. Notification text: fixed reason strings; the only free text is the mandate or job title, cleaned by `cleanText`.

**Ship policy.** `foreman.ship` is ordered, `propose`, `merge`, `release`, each level including the one before (`shipAllows`, lib/core/config/load.ts, the only reader besides `effectiveContract`'s caps). `release` also lets a mandate run `until: released`; no level makes the Foreman decide a release, which stays `foreman.decides`, `foreman.reserved` and the mandate's `decides`. `foreman.ship: merge` or `release` (with the foreman on) counts as `merge.auto: true` in the approver brief's `Merge: auto` line and in step rule PR4 only. The approver still judges `merge.autoWhen` and writes `Auto-merge eligible`. PR4 requires a recorded APPROVE marked eligible for the PR head (the `decision` event `forge job decision` binds to the worktree HEAD, never decision.md), and `forge pr merge` enforces it in code with the escalate floor and CI (docs/CONFIG.md "Merge"). CI there means the rollup plus the named required checks, each bound to its source, from `merge.requiredChecks` or else the base branch's protection: a required check that has not reported from its source waits, and one that fails, is `SKIPPED` or `NEUTRAL`, or reports from two sources refuses; with neither source, the rollup alone decides and `forge doctor` warns. The foreman itself never merges, and no daemon session can pass `--now`. `propose` changes nothing.

**Audit.** Every new `human` event carries `actor: { login, source }` (["Audit trail"](audit-trail.md)); a foreman decision is `{ login: null, source: "foreman" }`, and an older event's `"foreman"` reads as that, its `"human"` or missing actor as `{ login: null, source: "unknown" }`. `isForemanActor` (lib/core/job/store.ts) is the one check protected paths, stats, retro, the title-only rule and the office's `forge job set` use, and it accepts the legacy string too. `forge stats` counts only human reworks in `humanReworks` and adds `foremanDecisions` and `foremanReworks`. The dashboard labels foreman decisions in the drawer's timeline, shows each waiting job's `gateOwner` on its card, and shows the office session and the gate runs in the status bar as the **Foreman**: an indicator always rendered first in the left cluster (active while the office is busy or any gate run is live, counting only the office's permission prompts, or dashed while `foreman.enabled` is off) whose chat-sized popover shows the identity block, the office's last error and its prompts, then the **gate activity list** from `/api/state`'s `gates` (`GateRunsState`): a header with `<live> of <parallel> running` and any pause (the daily cap's message, or until when a retry or limit holds), and one row per run, newest first (the 50 kept), with the gate, its job (which opens the drawer) or mandate, an outcome chip, the reason on one line, when it started and its tokens, the dollars only in a title. Every value renders as text. The Workers popover leads with a Foreman row that opens it and lists the office among none of its job session rows.

**Threat model.** A session's provenance is `FORGE_DAEMON_SCOPE`, unauthenticated as for the inbox, but no scope carries the Foreman's authority: the checks stop a session misled by request, PR or tracker text (a job, inbox, office or chat session passing a decision off as the foreman's, the assistant smuggling a reserved topic through its reason, a forged `gate` request with `reserved: null`, the office merging), not a hostile local process. A Bash-capable session can always run `FORGE_DAEMON= forge job human …` without `--actor foreman`, which reads as a person outside the daemon: the CLI line guards a misled model, not a hostile one.

**Gate runs.** The guard that moved into code is who may record a foreman decision or hand-off, plus the path by which brief text reaches a claude stdin. The attackers, and how each bypass fails:
1. A daemon model session (job, inbox, office, chat) misled by tracker, PR or request text into recording a foreman decision or hand-off: the CLI refuses `--actor foreman` in every scope and `forge job handoff` is gone, because the authority is an in-process object no argv or environment can produce. A Bash-capable session setting `FORGE_DAEMON_SCOPE` to a retired assistant session's scope gets an invalid scope, and `_gates` refuses every command. Residual, as before: a hostile local process can import the module itself; the line guards a misled model.
2. The `forge:assistant` misled by job text: its only outputs are the verdict line and `feedback.md`; the parser is strict and cleans the reason; the note still goes through `reservedFor`; it has no Bash and its `_gates` scope refuses every `forge` call; and `dontAsk` means no prompt ever reaches a person to approve.
3. Verdict-line games: several `ASSIST:` lines (the last counts), text after the line, a lookalike dot or a typo are malformed, and a malformed reply never becomes approve.
4. A forged gate request file (from a Bash-capable session) with `reserved: null` or a wrong key: assist recomputes reserved, the policy recomputes everything, and pr-feedback needs the request keyed by the current head. Job ids and gate classes are validated before any path or argv is built.
5. Brief text on stdin: the brief is the CLI-built text (paths, the gate class, config lists, mandate guidance fenced by `fenceImport`), JSON-encoded into one user line by `briefLine`, so it can't become a control line, and refused over 256 KiB.
6. Spend and concurrency amplification: `foreman.assistants.parallel` is 1–16 and locked; the office cap covers `_gates` and fails closed on an unreadable meter; each child is capped at the remainder; failures back off; a request is requeued once, then rejected.
7. A planted `_gates.log` (a link, a FIFO or a forged `gate-end`): it is written with `openAppend` and read with `readLogPage` (no-follow), each seeded record is validated, and the dashboard renders text only.
8. Loops: one retry per run, one counted requeue per request, and one title-only revise per person's decision.
9. The senior pass (`foreman.escalations: foreman`). The guard is still who may record a foreman decision, now plus who may shelve as the Foreman, and how the first assistant's text reaches the senior:
   - The first assistant, steered by job text, smuggling instructions to the senior through its reason: the reason is cleaned (no quotes, backticks, `$`, `\`, control or line separators, at most 200 characters) and JSON-encoded on one line labelled data, and the whole brief still goes through `briefLine`.
   - The first assistant, steered by job text, naming an injection attempt and so sending the same text to a second model: a first reason that names `injection` is shelved for a person before any senior pass (check 4), as a detected injection always reached a person under `human`.
   - A model-written reason reaching a public tracker comment (the assistant has unscoped `Read`, so a steered one could put a file's text in its reason): the Foreman's shelve posts fixed text and the gate's name, and the full reason stays on the job, its events and the gate log, which are local.
   - The senior, steered by job text or the diff, approving past a floor: its decision goes through `recordForemanDecision` (the authority, the gate's actions, `reservedFor` on its note, the security floor, mandate holds, the pr-feedback head key), and security and reserved are screened before it starts, so a security hold is shelved for a person and never judged.
   - A model session shelving or forging a senior decision through the CLI: only the in-process authority shelves as the Foreman (`recordForemanShelve`), and `forge job shelve` stays refused in every daemon session.
   - Loops and spend: one marker per park, written before the spawn, survives a restart; each child is capped at the office remainder, and the cap is checked again before the senior.
   - A forged or deleted marker in the appendable `events.jsonl`: a forged one only shelves sooner, toward a person; a deleted one allows at most one more senior pass per run, still under every check above. Residual, as for every events-derived guard: the line guards a misled model, not a hostile local process.

A release approval that outlives its mandate stops counting at run and status time, and tampering with the mandate file only makes it unreadable, which revokes it. A CI rework on a job whose mandate keeps `pr-feedback` with a human becomes the gate instead, with the mandate read from the CLI's record of the job, never `job.json`.
