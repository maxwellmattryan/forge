# Foreman

Unattended runs stop at every human gate. With `foreman.enabled` (off by default; docs/CONFIG.md "Foreman"), the Foreman's assistant foremen decide the gates it is allowed to, through `forge:assistant` sub-agents, so a human is needed only where policy says so.

**Routing.** A move (Job model › Moves) that parks a job on `spec-approval`, `split-approval`, `escalation`, `rounds-exhausted`, `conflicts` or RP1's repo proposal park (a `human` wait whose reason starts `repo proposal:` while a proposal is pending, the derived class `repo-proposal`) (a new park, or a different gate) whose class is in `foreman.decides` enqueues one `gate` request `{job, args: {gate, reserved}, from: "forge"}`, unless one for that job and gate is pending or in progress. It does so whoever writes the park: `forge job set`, `forge job advance`'s repeated-failure park, the reconciler, and the syncs in `forge pr sync`, `forge sync` and `forge pr merge`. The policy lives in `lib/engine/pipeline/moves/foreman-gates.ts`; `lib/office/foreman.ts` keeps the session side. `forge pr sync` (never `forge pr merge`) does the same for a job waiting on `pr-review` with changes requested or unresolved threads from someone with write access (`OWNER`, `MEMBER` or `COLLABORATOR`; a stranger's comment alone never starts an unattended rework): `args.gate: "pr-feedback"` and `args.key: <head sha>`, once per head in any status, so a push re-arms it. Failing checks on such a job skip the assistant foremen: sync records a foreman `rework` itself (`ciHead` on the event dedupes it per head), writes a fixed `feedback.md` with no check text in it, moves the job to `build` and queues a `resume`; a reserved match falls back to the gate. A job in a mandate gets this CI rework only when its mandate delegates `pr-feedback` (read from the CLI's record of the job); otherwise, or when the mandate can't be read, sync queues the `pr-feedback` gate instead, which `forge job assist` reports reserved, so the assistant foreman hands it off. The **CI rework cap** (`pr.maxCiReworks`, 3) bounds it: counted from the event log (foreman `rework` events with a `ciHead` since a person's latest `human` event), never from `job.json`, so a session can't reset it; at the cap a red head starts nothing, the reason names at most 5 allowlisted check names, a `ci-rework-capped` event is logged once per head, and no `pr-feedback` gate is queued, so the foreman is refused there too. Any head counts, because only someone with write access can push a same-repo branch and fork PRs are never adopted; `forge job round` pulls that head into the worktree before the builder starts. `requestScope` sends every `gate` to `_assistants`, a request group and never a session scope; the dashboard (`POST /api/requests`) and `forge requests add` cannot create one. In an assistant foreman scope (`_assistant-1` … `_assistant-<n>`, n being `foreman.assistants.sessions`, 1–16) `forge requests` lists every pending gate request and `claim` and `ack` accept them; the first claim wins, and a second assistant's claim exits 3, so it skips the request. Job, inbox and office sessions can't see, claim or ack a gate request, and an assistant foreman can't see, claim or ack anything else (exit 1). With `foreman.enabled` and `foreman.assistants.enabled`, the pool keeps one session per assistant scope. Each tick, with P the pending gate requests eligible after holds and B the assistant foremen busy or stopping, at most P − B fresh, idle assistants get the fixed `/forge requests` turn, in scope order, each spawned first when it is off. The pool treats them like the inbox for trust, `DENY_TOOLS`, budget holds and failures, never counting them against the cap. With the foreman off or `assistants.enabled: false`, no assistant runs, gate requests stay pending for a human and the board shows each gate as a human's. `draft` and `direct` requests route to `_office`, the office session (Intake and Director loop below), which the pool spawns only while `foreman.enabled` holds.

**The turn** (`skills/forge/reference/foreman.md`). Claim, then `forge job assist <job> --gate <gate>`, which returns `{gate, stale, reserved, model, effort, subagent: "forge:assistant", brief}` and writes nothing. The assistant foreman spawns one `forge:assistant` with that brief, reads its single line `ASSIST: approve|revise|rework|escalate · <reason>` (anything else is `escalate`), records the verdict with `forge job human <job> <action> --actor foreman --note "<reason>"`, queues a `resume` for the job's own session, and acks; that session's next `forge job step` turns the decision into the gate's follow-up (["Job model"](job-model.md) › Answered gates). On `escalate`, a reserved gate, or a decision the CLI refuses (not a stale one), it records a **Foreman hand-off** with `forge job handoff <job> --class escalated|reserved|refused --reason "<reason>"` (a command only an assistant foreman scope may run, whose gate is read from the job) and acks `rejected`, and the job keeps waiting for a human. `forge status`, `forge job show`, `/api/state` and the dashboard's Needs you card show the hand-off (`foremanHandoff`, derived from events) until a decision answers that park or the job parks again.

**Context rule.** An assistant foreman never reads a job file: the brief `forge job assist` returns carries absolute paths, the gate class and the reserved list, never file content, and the procedure names only `forge` calls. The `forge:assistant` reads the files and writes `feedback.md` itself on `revise` or `rework`, so the assistant foreman's log holds CLI JSON and one-line verdicts.

**Authority, enforced by the CLI.** `forge job human … --actor foreman` runs every check before any write, and a refusal (exit 1) leaves `job.json` and `events.jsonl` untouched. It is refused outside an assistant foreman scope, the office's included (`--actor foreman refused: only an assistant foreman session records foreman decisions`); inside one, `job human` without `--actor foreman` is refused too. `forge job handoff`, `forge job assist` in a daemon session, and `approve-repos`/`reject-repos` from a daemon session need an assistant foreman scope as well. It needs a `--note`, takes no `--link` or `--reason`, and needs the job to be waiting on a class in `foreman.decides` (`pr-review` counts as `pr-feedback`) with an action of that class: `approve-spec`/`revise-spec`, `approve-split`/`revise-split`, `approve`/`revise-spec`/`rework` for escalation and rounds-exhausted, `approve` for conflicts, `rework` for pr-feedback, `approve-repos`/`reject-repos` for repo-proposal, with `--repo` naming the whole pending set (then `--state running` with no stage). It is refused when a `foreman.reserved` pattern matches the reason, the note, or (for escalation and rounds-exhausted) the `## Why` and `## For the human` sections of `decision.md`, or (for repo-proposal) a pending proposal's reason; a `decision.md` that isn't a small regular file counts as a match, and a security review whose latest recorded verdict is anything but `PASS` (`CHANGES`, `MALFORMED`) refuses every action that accepts the job, at any gate, while `rework` and the revise actions stay the foreman's (`SECURITY_MITIGATIONS`): security always has to pass, so the foreman may fix it but never approve past it. Step keeps reworking such a job past `maxRounds`, up to twice it, before B2 parks it on `rounds-exhausted`. Past the **total-round ceiling** (`pipeline.maxTotalRounds`, by default twice `maxRounds`), which counts every round whoever opened it, B7 parks the job there unless a person (a `human` event whose actor isn't the foreman) reworked or revised since the previous round started, and every foreman action at that park is refused, whatever the security verdict: no gate request is queued for it. A `rework` on pr-feedback also needs a pending or in-progress `gate` request keyed by the PR's current head sha, so the foreman acts only on feedback sync armed for that push. Patterns match case-insensitively as whole phrases (no letter or digit on either side) and are escaped literals, so matching is linear; a `reserved` that isn't a list of non-empty strings makes every gate reserved. In an assistant foreman scope (and the office), `forge job set` only carries out a recorded foreman decision: the job must still wait, its latest `human` event must be the foreman's and newer than the park, and the change must be that action's `--state running` with its stage from the gate table, with no `--field`, `--waiting-on` or `--reason`. Of the `forge job` subcommands only `assist`, `human`, `set`, `note`, `handoff`, `show`, `get`, `list` and `step` run there. An assistant foreman drives no job: `worktree create`, `job advance`, `job claim`, `job agent … start`, `pr merge` (any job, with or without `--now`) and `backing down --shared` are refused with `an assistant foreman session decides gates and does not drive jobs`, and in the office with `the office session does not drive jobs`. The assistant has no Bash at all (`disallowedTools: Bash, Edit, NotebookEdit`), so text it reads reaches the CLI only through its one-line verdict.

**The release gate class** (lib/engine/release/approval.ts). No job waits on a release, so `release` is routed from the plan, not a park: `forge release plan --job <id>` logs `release-planned {planHash}` (the full sha256, unless the job's latest one already has it) and, when the foreman decides `release`, enqueues one `gate` request `{job, args: {gate: "release", key: <planHash>, reserved}}`, unless one for that job and key exists in any status, so a gate left for a human is never re-armed for the same plan. "Decides" means `foreman.enabled`, `release` in `foreman.decides`, and no `gate:release` in `foreman.reserved`, which the defaults keep: `decides()` drops every class reserved with `gate:<class>`, so reserved wins for every gate and caller, and a `gate:` entry naming no class makes `reservedMatch` fail closed. `forge job assist <job> --gate release` is `stale` unless release.json selects the job, its latest `release-planned` is release.json's hash and that hash has no approval; its brief names release.md, config.yml (`release`, `repos[].release`) and the job's request, spec and decision paths, plus `Release plan: <path> (plan <hash12>)`. `forge job human <job> approve-release --actor foreman --note "<reason>"` checks, before any write: an assistant foreman scope; a note and no `--link`, `--reason` or `--repo`; the policy (each refusal names enabled, decides or `gate:release`); a readable release.json selecting this job; `freshPlan` recomputed from config and the clones matching it; the job's latest `release-planned` being that hash; a pending or in-progress `release` gate request keyed by it; no approval for it yet; and `reservedFor` over the job's reason and the note, which also refuses a latest security review that isn't PASS. It then logs one `release-approval {planHash, note, actor}` event and nothing else: no `human` event, no state change, and no `SET_AFTER` entry, so the assistant foreman's `forge job set` stays refused. Without `--actor foreman` it is refused everywhere: a person approves at `forge release run`'s prompt. `forge release run` without a terminal passes a publish step only when the job has a foreman `release-approval` whose `planHash` is the plan it just recomputed, the foreman still decides `release`, the job's mandate (if it is in one) still delegates `release` and is neither paused nor closed (`releaseMandateRefusal`, read again at run time), and `reservedFor` over the job and the approval's note is null; the result carries `approvedBy: "foreman"`. `forge release status`'s `approval` follows the same rule: once the approval stops counting it reports `{owner: 'human', status: 'pending'}`. A terminal always asks, a manual step still needs one, and the run itself stays refused in every daemon session, so a human or CI starts it.

**Release gate threat model.** The attackers are an assistant foreman or its `forge:assistant` misled by text in release.md, the config or a tracker; a job, inbox or office session posing as the foreman; and a Bash-capable agent writing `events.jsonl`, `release.json` or the request inbox directly. The scope check and the reserved note and security checks stop the first two; a forged or reused request fails the key match against the recomputed plan; an edited or stale release.json fails `freshPlan`; an approval for another plan or by another actor is ignored at run time, and so is one left over after the owner takes the class back or narrows, pauses or closes the job's mandate, because the policy and the mandate are re-read every time. Residual risk: in a repo that delegated `release`, a process that can append to the job's `events.jsonl` can stand in for the foreman's approval of the current plan. It still can't change what runs (commands come from config and the recomputed plan), and no daemon session can start the run; in a repo that did not delegate, a forged approval does nothing.

**Mandates.** A mandate (docs/CONFIG.md "Mandates") is the owner's standing instruction to the Office: `.forge/runtime/mandates/<id>.md`, runtime state outside every session's write roots, written by the owner only through `mandateWrite` (`lib/office/mandates/store.ts`), under one lock with every contract check before the write: `forge mandate new|edit|pause|resume|close`, refused in every daemon session, and the dashboard's Foreman page (`POST /api/mandates` and `/api/mandates/:id/edit|pause|resume|close`, behind the token, Origin and JSON guard, as `actor.source: dashboard`, docs/architecture/dashboard-security.md). An edit from the page is pinned to the `updatedAt` it read, so a CLI edit or an Office pass pause in between makes it a 409 rather than being overwritten. A job joins one at creation (`forge job new --mandate`, or its split parent's) and keeps it: `mandate` is a locked field. For a job in a mandate, the classes the Foreman decides are `decides(config)` ∩ the mandate's written `decides`, whatever its status (except for `release`, below), read through `jobMandateDecides` from the CLI's record of the job (`stateFile`), never the session-writable `job.json` mirror. Four places narrow: `checkForemanDecision` refuses, after the `foreman.decides` and class-reservation checks; `forge job human <job> approve-release --actor foreman` refuses the `release` class the same way (it has no park, so it goes through `checkReleaseDecision`, which takes the job's refusal from `mandateRefusal` after its policy checks and before its plan checks); `gateOwner` shows the gate as a human's; and `forge job assist` returns `reserved: "mandate <id>: …"`, after `classReservation` and before `reservedFor`, so the assistant foreman's reserved path hands the gate off. Engine code can't import `lib/office/`, so two engine paths take the narrowing as a function from the CLI: the CI rework in `forge pr sync` and `forge sync`, which a job in a mandate gets only when its mandate delegates `pr-feedback` (otherwise sync queues the gate, Routing above), and `forge release run` and `forge release status`, which count a foreman `release-approval` only while the job's mandate still delegates `release`. For the `release` class only, a paused or closed mandate also delegates nothing (`releaseMandateRefusal`), because publishing can't be undone: `approve-release --actor foreman` is refused with `--actor foreman refused: mandate <id> is paused: release left for a human` (or `closed`), `forge job assist --gate release` reports it reserved, and an approval already recorded stops counting once the mandate narrows, pauses, closes, is deleted or can't be read. For every other class a paused mandate still delegates, so its in-flight jobs finish, and a **closed** mandate delegates nothing: `jobMandateDecides` returns `decides: []`, and `mandateRefusal` checks it first, refusing with `mandate <id> is closed: left for a human`. The **bounce hold** comes after the decides check: a job waiting on a counted gate (every wait but `pr-review` and `external`) that it has entered `stall.bounces` times since a person's latest `human` event (`bounceHold`, `lib/office/mandates/progress.ts`, over `readEvents`, the CLI copy; a reason change while already waiting there is no new entry, and a foreman decision never resets the count) is a person's: `checkForemanDecision` refuses with `--actor foreman refused: mandate <id>: back at <W> <n> times (stall.bounces <k>): left for a human`, `forge job assist` returns that text as `reserved`, and `gateOwner` returns `human`. It is checked at decision time because an assistant foreman decides a park within seconds, long before the next Office pass. A mandate file that is missing or can't be read safely delegates nothing (fail closed). One engine path is not narrowed: `maybeEnqueueGate` (a queued request costs only the assist call that hands it off). When the gate is delegated, the assistant's brief carries a `Mandate:` line and the body fenced by `fenceImport`, and `forge mandate show` returns it fenced too, never raw.

**Mandate threat model.** The attackers: a daemon session (a job session, the inbox, the office, or an assistant foreman and its `forge:assistant`) misled by tracker, PR or mandate-body text; the builder agent; and a Bash-capable agent writing files under its write roots. Each bypass fails: detaching a job with `forge job set --field mandate=…` is refused (a locked field); editing `.forge/jobs/<id>/job.json` changes nothing Forge reads, because the narrowing reads the CLI record; widening a mandate's `decides` or creating a permissive one from a session is refused under `FORGE_DAEMON=1` before anything is read, the mandates dir is outside the session write roots (`lib/office/session/confine.ts`), and `decides` can never exceed `foreman.decides` minus reserved classes anyway; deleting, symlinking or corrupting the file makes the mandate unreadable, which delegates nothing; moving a split child to another mandate is refused; the body reaches briefs and `show` only fenced; milestones and labels, which reach `gh` as arguments through the tracker's `scope`, can't start with `-` or hold a control or hidden character (and the GitHub adapter throws on a leading `-` before gh runs); and the id grammar keeps the file inside the mandates dir. Joining a mandate with `--mandate` is allowed from a session, because it only narrows. The dashboard's Foreman page adds two more attackers, another site in the owner's browser and a local process holding the page token, and writes through the same `mandateWrite`: a cross-site POST that creates or widens a mandate fails the token, Origin and JSON guard; a cross-site read of the guidance fails the detail GET's token; a `decides` past `foreman.decides` or onto a `gate:<class>` reservation, a scope entry starting with `-`, or an id that climbs out of the mandates dir (`..%2F`, `none`, uppercase) is refused before anything is written (409, 400 or 404); an oversized or trickled body hits the guard's 64 KiB cap and timeout and the shape caps; an edit is pinned to the `updatedAt` it read, so a concurrent CLI edit or pass pause is never overwritten; every write logs `actor.source: dashboard`; and every mandate string renders as Svelte text. Residual, as for every dashboard POST: a same-user process that reads the page token can write a mandate as the owner. As for the Foreman as a whole, `FORGE_DAEMON= forge mandate …` from a Bash-capable session reads as a human: the line guards a misled model, not a hostile one.

**Intake** (#434, phase 1). A **goal mandate** (`forge mandate new <id> --title T --goal "<text>"`, or `--goal-file F` with `-` for stdin) states what to achieve instead of which issues to run: its scope stays empty, and the goal is set once, stored as the last frontmatter key on one JSON-quoted line (the YAML subset's block scalars don't round-trip every text), and shown only through `fenceImport` (`mandateGoal`). `new --goal` queues the first **draft request** `{type: "draft", job: null, args: {mandate}, from: "forge"}`, and `forge mandate draft start <id>` queues another for an active goal mandate unless one is pending or in progress; nothing else writes one (`forge requests add` and `POST /api/requests` refuse `draft`), and `requestScope` sends it to `_office`, so only the office session turns it, while `daemon.enabled` and `foreman.enabled` are on. A **drafting run** is two CLI calls with one `forge:drafter` between them, as for triage and `forge job assist`: the office claims the request, runs `forge mandate draft prepare <id> --request <rid>`, which writes the survey and returns the brief with the roster's model and effort for `drafter`, spawns the drafter with that brief, runs `forge mandate draft record <id> --request <rid> --agent-id <id>` whatever line it returned, and acks (`done` with `drafted: <n> issues in <w> waves` or `stale: <reason>`, `rejected` with a refusal). The office never reads the survey, the staging file or the draft. The files: the **survey** (`.forge/runtime/mandates/<id>/survey.md`, at most 64 KiB: a column-0 data line, the fenced goal and guidance, Forge's own stats, every tracked `AGENTS.md` with its first prose line, and the tracker's open milestones (`Tracker.milestones`, optional) and open issues, each list in one `fenced()` block with every title through `oneLineTitle`); the **staging file** the drafter writes (`<worktrees.root>/_office/drafts/<id>.json`, inside the office session's write roots, so the drafter's Write passes the write guard, and cleared by `prepare`); and the **milestone draft** `record` stores once it passes `draftProblems` (`.forge/runtime/mandates/<id>/draft.json`, a versioned shape, `lib/core/versions/draft.ts`), with a `mandate-draft` audit event. `forge mandate draft show <id>` reads it back with its status (`queued`, `drafting`, `ready`, `unreadable`, `failed` or `none`), its latest request and its spend. **Spend**: `record` first appends one `agent-end` line to `.forge/runtime/mandates/<id>/ledger.jsonl`, with the drafter's usage from its transcript when `--agent-id` finds one. `metered: true` in a daemon session says the office session's supervisor meter already holds that cost, so it counts against `daemon.dailyUsd.office` and no sum adds it twice; a person's own run is `metered: false` and is recorded only on the mandate's ledger. A ready draft waits at the `milestone-approval` gate (below); the mandate's `budget` over drafting spend comes with the director loop (#538).

**Intake threat model.** The attackers: the owner's goal or guidance and tracker titles misleading the drafter; a job or inbox session misled by tracker or PR text into starting a drafting run, or writing or replacing a draft that approval would file; the builder agent; and a Bash-capable session writing under its write roots. Each bypass fails: `prepare` and `record` exit 1 in any daemon scope but `_office` (and with a missing or invalid scope) before anything is read; draft requests are refused from `forge requests add`, `POST /api/requests`, and `forge mandate draft start` or `new --goal` in any daemon session, so no session can queue drafting spend; both calls need `--request` naming an in-progress `draft` request for that mandate, looked up in the listing before any path is built from it, so a draft can't be recorded without a claimed run or onto another mandate; the staging file is read through `readRegular` (no link, no FIFO, at most 256 KiB), a link at the drafts dir is refused, and `prepare` removes a stale one; `draftProblems` refuses unknown keys, hidden or control characters, `existing` refs `checkIssueRef` refuses (a leading `-` never reaches `gh`) and file paths that are absolute, start with `-` or climb with `..`, so filing never sends such text; tracker titles can't leave their fence, because `fenced()` picks a longer fence and `oneLineTitle` removes hidden characters and line breaks; the drafter has `tools: Read, Grep, Glob, Write` and no Bash or web tools; and `milestones` builds its `gh api` path from `repoSlug`'s checked slug only. Residual risks: a Bash-capable session can overwrite the staging file between `prepare` and `record`, but the draft stays an inert, checked file until someone decides it, and the decision pins the digest of the bytes the decider saw; `FORGE_DAEMON= forge mandate draft …` from such a session reads as a person, as for every Office check; the survey and the ledger live in the runtime dir, outside every session's write roots.

**Milestone approval and filing** (#434, phase 2). A goal mandate's ready draft waits at the `milestone-approval` gate, a gate class that belongs to the mandate, not a job: no job waits on it, so the job tables and `forge job assist` leave it alone (`assist --gate milestone-approval` is always `stale`). Its status (`draftGate`, `lib/office/mandates/gate.ts`) is `filed` once the mandate's `filedAt` is set, `filing` while `filing.json` exists unfinished, `pending` for a ready draft of a goal mandate that isn't closed, else `none`; `forge mandate draft show` and `GET /api/mandates/:id/draft` give it with the draft's **digest**, the lowercase hex SHA-256 of the exact `draft.json` bytes read (never stored in the file). Three decisions, one function (`decideDraft`) for the CLI and the dashboard: `forge mandate draft approve` files the draft; `revise --note` queues another drafting run whose brief carries the previous draft's path, its title and the note, the last two through `fenceImport` (when a `draft start` queued one first, revise exits 1 and queues and logs nothing); `reject` closes the mandate (`milestone draft rejected: <note>`), files nothing, and starts the next link of its chain. A note is 1–2000 characters of visible text on lines. `--request` and `--digest` pin the draft read (the dashboard always sends both), and every decision runs under `locks/mandate-decide-<id>` with a one-second wait, so a double click, a terminal and an assistant foreman can't decide twice. **Who decides**: a person, in their own terminal or the dashboard; under `FORGE_DAEMON=1` a call without `--actor foreman` exits 1 in every scope before anything is read. The default `foreman.decides` leaves the class out, so a project lists it to delegate it, and a mandate's own `decides` narrows it further. When both delegate it, `forge mandate draft record` queues one job-less `gate` request (`{gate: milestone-approval, mandate, key: <draft request>, digest, reserved}`, which `enqueue` accepts only with a valid mandate id) that routes to `_assistants`; an assistant foreman runs `forge mandate draft assist <id> --request <gid>` (read-only: a brief of paths and fenced data, never draft text) and records `approve` or `revise` with `--actor foreman`, which `checkMandateGateDecision` (`lib/office/foreman.ts`) judges with the same `foremanScopeRefusal` and `foremanPolicyRefusal` as job gates, plus a matching in-progress gate request for the current key and digest and a cap of two foreman revisions per mandate (`FOREMAN_REVISIONS_MAX`, until the mandate's budget lands). Reject, and retrying a stopped filing, stay a person's. Every recorded draft also queues a `gate` notification (`milestone-approval`, no free text). **Filing**: the CLI, never an agent, reads the draft once (the bytes give both the digest and the body filed), runs every pre-flight check before any write (the tracker has `createMilestone`, the title is a valid scope milestone with no leading, trailing or repeated whitespace, the converted mandate passes the contract, no open milestone or item has the title, each `existing` ref is an open item of this tracker, and one secret scan over every outgoing string), then writes `filing.json` (with the digest) and the `mandate-draft-approved` event, creates the milestone, files each issue in wave order (`wave-<n>` labels, never prefixed, so triage sees them; reuse and amend move an existing item in), recording each ref as it lands, and last writes the mandate with `scope.milestones: [<title>]` and `filedAt` (`mandate-filed`). On GitHub every `@name` in an issue body, an amendment or the milestone description gets a zero-width joiner after its @ (outside a fenced code block that opens at column 0), so filing notifies no one. A tracker call that throws keeps the record with its `error` (the gate is `filing`); the refusal names where filing stopped, with the error JSON-quoted for a person and left out for the foreman (it stays in `filing.json`), since a tracker error can echo the draft's title. Approve again resumes without filing anything twice, adopting the one open item with the exact title for a key that was started but not recorded; a retry refuses once `draft.json`'s digest differs from the record's. The filed mandate is an ordinary scoped mandate whose issues go through readiness triage like any other.

**Milestone approval threat model.** The attackers: a daemon session (a job session, the inbox, the office or an assistant foreman) misled by tracker, PR, goal or draft text; the drafter, whose output reaches the tracker and the office's context; the `forge:assistant` that reads the draft; another site in the owner's browser; the builder agent; and a Bash-capable session writing under its write roots or the runtime dir. Each bypass fails. A session deciding as a person: every daemon call without `--actor foreman` is refused before anything is read. The foreman outside policy: the scope, `foreman.enabled`, `foreman.decides`, `gate:milestone-approval`, the mandate's own decides (an unreadable mandate delegates nothing), a reserved pattern anywhere in the goal, the draft or the note, reject, a stopped filing, a missing or mismatched gate request and the revision cap are each a refusal. Approving bytes nobody saw: the request and digest pins hold for the dashboard and the foreman, filing parses the digested bytes, and a retry checks the record's digest. Drafter text steering the office: `draftProblems` and filing's pre-flight name positions only (`issues[2].files[0]`, "the draft's milestone title"), a foreman's stopped filing carries no tracker error, the assistant brief holds paths and fenced data, and the revision note and previous title reach the drafter fenced. Filed text pinging people on GitHub: mentions get a zero-width joiner after the @. A credential smuggled to the tracker: one scan over every outgoing string, plus the guarded adapter's own scan of `createMilestone` and `milestoneAdd`. Option injection into `gh`: the milestone title can't start with `-`, titles go in `=` or `-f key=value` arguments, labels are fixed `wave-<n>`, refs go after `--`. A forged job-less gate request: `enqueue` takes one only for this class with a valid mandate id, `forge requests add` and `POST /api/requests` still refuse `gate`, and one that doesn't match the current key and digest decides nothing. A cross-site POST: the token, Origin and JSON guard. Double filing: the decision lock plus the record. A planted link at `draft.json` or `filing.json`: `readRegular` refuses it, and an unreadable record files nothing. Residual risks: a Bash-capable session can rewrite `draft.json` and the gate request together before anyone reads them, and the owner or assistant then judges the rewritten (still rule-checked) draft, which is exactly what files; forging `args.foreman: true` only lowers the revision cap; and `FORGE_DAEMON= forge mandate draft approve` reads as a person, as for every Office check.

**Director loop.** Enforcement is code and judgement is the model's. The **Office pass** (`forge office pass`, `lib/office/mandates/pass.ts`) is deterministic code with no model, which `forge dash` runs as a child (`runPassChild`, outside any daemon scope, with sync's env and git pins) every `foreman.cadence` minutes, at pool start, when a mandate file changes and when a job session's result leaves a mandate job `done`, `cancelled`, `failed` or `waiting` (docs/architecture/daemon.md "Periodic Office pass"). It is refused in every daemon session, the office's included, and writes nothing with `foreman.enabled` off. Under the `<locks>/office` lock it reads every mandate, skipping closed ones and goal mandates whose scope is still empty, and for each, in creation order: applies `onUnfinishable` to every failed job (`cancel` moves it to `cancelled`; `park` leaves it failed), logging a `mandate-unfinishable` job event that makes the job **handled**; stalls each in-flight job the bounce hold holds, once per park (`mandate-stalled` job event, `mandate-stalled` notification with the job); **closes** an active or paused mandate with no tracker error, no candidates, no in-flight and no unfinishable job, writing its closing summary (`.forge/runtime/mandates/<id>/summary.json`, versioned in `lib/core/versions/mandate-summary.ts`) and evaluating again every mandate whose `after` is the closed one, so the next link of a chain starts in the same pass; pauses an active mandate at its budget (`spentUsd >= budget.usd`, or `started >= budget.jobs` with candidates left); and pauses an active mandate with no progress for `stall.cadences × foreman.cadence` minutes (no job created or moved, no running agent). Each status write goes through `writeMandate` with the foreman as the audit actor, and lands only while the mandate still has the status and `updatedAt` the pass read, so an owner's edit, pause or close wins. When some active, unblocked mandate has a candidate window or a resumable job and no `direct` request is pending or in progress, the pass queues one `{type: "direct", job: null, args: {}, from: "forge"}`; `requestScope` sends it to `_office`, and nothing else writes one (`forge requests add` and `POST /api/requests` refuse it). A mandate's **jobs** are the live jobs (the CLI records) and archived jobs whose `mandate` is its id, classed against its effective `until` as reached (`merge-ready`: done, or at `pr` waiting on `pr-review` with a PR; `merged`: done), handled, unfinishable or in flight. Its spend is every ledger bucket of those jobs (never the office session's own spend, which stays under `daemon.dailyUsd.office`), and `started` counts jobs whose parent is not one of its own, so split children don't count. Its **candidates** are the scope items (`order: listed`: the written issues, with no tracker call; otherwise one `Tracker.scope` call per milestone, or one for labels alone) that are not needs-info, carried by no live job and not skipped, ordered as written, by priority then number, or by number (`graph`: the Foreman orders them by the issues' stated dependencies), and taken from the first milestone that still has open work. The **window** is the first `free` candidates under `listed` and the first `min(10, 3 × free)` otherwise, empty while the mandate is blocked (not active, at its budget, the repo budget held, a tracker error, or the foreman off). On a `direct` request the office session (the skill's "For each direct request") runs `forge office survey`, which lists each active mandate's window with one-line titles, its resumable jobs, its latest 5 directives and its guidance fenced; with `foreman.surveyors.enabled` it runs `forge office board <id>` for each mandate with work in flight and hands the brief to a `forge:surveyor` (Read only, at most 5 `SURVEY:` lines over a board of one fenced line per job); then it runs `forge office start <id> <ref> --reason R` for up to `free` candidates, `forge office resume` for resumable jobs, and `forge office note` when it starts nothing deliberately. `start` re-checks everything under the office lock: the mandate is active and not blocked (a held repo budget exits 4), and the ref's stored form is in the window recomputed now (under `listed`, only the first). An issue the tracker reports closed or missing is skipped; otherwise `startFromRef` creates the job with `mandate` set and split mode never, claims the issue, and a `resume` with `args.intake: run` is queued. The office session runs on `foreman.model` and `foreman.effort` (`--model` replaces every one in `daemon.command`). Each choice and enforcement is a **directive**, a `directive` event in the repo audit log (and on the job it names) with `{mandate, action, issue, job, reason, actor}`, the action one of `start`, `resume`, `note`, `skip`, `pause`, `close`, `stall`, `park` or `cancel`; `forge audit`, `forge job audit` and `forge mandate show` (with `progress` and the closing `summary`) list them.

**Director threat model.** The attackers: the office session misled by tracker titles, mandate guidance or a surveyor's lines; a job, inbox or assistant foreman session misled by tracker or PR text; the builder agent; and a Bash-capable session writing under its write roots (the job folders and worktrees, so a job folder's `job.json` and `events.jsonl` mirrors). Provenance stays the unauthenticated `FORGE_DAEMON_SCOPE`: the line guards a misled model, not a hostile local process (`FORGE_DAEMON= forge …` reads as a person). Each bypass fails. Starting an issue outside the mandate's scope or order: `start` recomputes the window from the tracker and refuses. Exceeding `maxJobs`, the mandate's budget or the repo budget, or starting under a paused, waiting or closed mandate: re-checked at `start`. Starting work from another session: `forge office survey|board|start|resume|note` are refused outside the office session and a person's terminal (`refuseOutsideOffice`). Triggering enforcement early: `forge office pass` is refused in every daemon scope. A forged `direct` request: refused from the CLI and the dashboard; a file-planted one costs at most one office turn, under `daemon.dailyUsd.office`, and every action in that turn is re-checked. Hiding spend or membership by editing a job folder's `job.json`: progress reads the CLI records and the archive. Resetting a bounce count with a fake `human` event in the job folder's `events.jsonl`: counts read `readEvents`, the CLI copy. An assistant foreman deciding the K-th bounce, or a closed mandate's gate: refused by `mandateRefusal`. Injection through the board or the survey: titles and reasons are one line and fenced in the board, the guidance is fenced, the surveyor has `tools: Read` only, and its lines reach only the Foreman's choice among already-checked candidates. Option injection into gh or claude argv: milestones and labels never start with `-` (the contract, and the adapter's own throw), and `foreman.model` passes `validModel` (its pattern starts alphanumeric) and is its own argv word after `--model`. Notification text: fixed reason strings; the only free text is the mandate or job title, cleaned by `cleanText`.

**Ship policy.** `foreman.ship: merge` (with the foreman on) counts as `merge.auto: true` in the approver brief's `Merge: auto` line and in step rule PR4 only. The approver still judges `merge.autoWhen` and writes `Auto-merge eligible`. PR4 requires a recorded APPROVE marked eligible for the PR head (the `decision` event `forge job decision` binds to the worktree HEAD, never decision.md), and `forge pr merge` enforces it in code with the escalate floor and CI (docs/CONFIG.md "Merge"). CI there means the rollup plus the named required checks, each bound to its source, from `merge.requiredChecks` or else the base branch's protection: a required check that has not reported from its source waits, and one that fails, is `SKIPPED` or `NEUTRAL`, or reports from two sources refuses; with neither source, the rollup alone decides and `forge doctor` warns. The foreman itself never merges, and no daemon session can pass `--now`. `propose` changes nothing.

**Audit.** Every new `human` event carries `actor: { login, source }` (["Audit trail"](audit-trail.md)); a foreman decision is `{ login: null, source: "foreman" }`, and an older event's `"foreman"` reads as that, its `"human"` or missing actor as `{ login: null, source: "unknown" }`. `isForemanActor` (lib/core/job/store.ts) is the one check protected paths, stats, retro and an assistant foreman's `forge job set` use, and it accepts the legacy string too. `forge stats` counts only human reworks in `humanReworks` and adds `foremanDecisions` and `foremanReworks`. The dashboard labels foreman decisions in the drawer's timeline, shows each waiting job's `gateOwner` on its card, and shows the office and the assistant foremen in the status bar as the **Foreman**: an indicator always rendered first in the left cluster (active while the office or any assistant foreman is busy, counting all their permission prompts, or dashed while `foreman.enabled` is off) whose chat-sized popover stacks those prompts per scope and holds a session log, with Start/Stop, the permission mode and read-only model and effort facts. When assistant foremen exist, a Select above the log chooses `Foreman` (the office) or `Assistant foreman <n>`, defaulting to assistant 1. The Needs you count includes the assistant foremen's prompts. The Workers popover leads with a Foreman row that opens it and lists neither the office nor an assistant foreman among its job session rows.

**Threat model.** Provenance is `FORGE_DAEMON_SCOPE`, unauthenticated as for the inbox: the checks stop a session misled by request, PR or tracker text (a job session passing a decision off as the foreman's, the assistant smuggling a reserved topic through its reason, a forged `gate` request with `reserved: null`, an assistant foreman or the office merging), not a hostile local process. A Bash-capable session can always run `FORGE_DAEMON= forge job human …`, which reads as a human outside the daemon and skips every foreman check: the CLI line guards a misled model, not a hostile one.

**Assistant foremen.** Up to 16 pool sessions in scopes `_assistant-1` … `_assistant-16` hold the Foreman's authority over gates, so their threat model is the Foreman's with more sessions. The attackers: a daemon session misled by tracker, PR or mandate text (a job session, the inbox, the office, or an assistant foreman and its `forge:assistant`); the builder agent; and a Bash-capable session setting `FORGE_DAEMON_SCOPE`. Provenance stays that unauthenticated scope variable: the CLI line guards a misled model, not a hostile local process. Each bypass has a guard. A forged scope string (`_assistant-0`, `_assistant-17`, `_assistant-01`, `_assistants`, or any suffix) is rejected, and the session fails closed as a broken scope; no path or meter file is built from one. The office or a job session recording a foreman decision or a Foreman hand-off is refused. An assistant foreman driving, claiming or merging a job is refused. An assistant claiming a non-gate request, or a job or office session claiming a gate, is refused by the scope check. Two assistants on one gate: the second claim exits 3. Spend amplification: the office and every assistant share one `daemon.dailyUsd.office` cap, summed over all 17 meter files, and any one that can't be read stops them all. Concurrency amplification: at most `foreman.assistants.sessions` (1–16) run, and only while `foreman.enabled`, a locked key a session can't set. The requeue path never reads a lease for `_assistants`, since no session leases the group. A release approval that outlives its mandate stops counting at run and status time, and tampering with the mandate file only makes it unreadable, which revokes it. A CI rework on a job whose mandate keeps `pr-feedback` with a human becomes the gate instead, with the mandate read from the CLI's record of the job, never `job.json`.
