# Foreman: gate runs

Part of [Foreman](../foreman.md).

## Routing

A move (Job model › Moves) that parks a job on `spec-approval`, `split-approval`, `escalation`, `rounds-exhausted`, `conflicts` or RP1's repo proposal park (a `human` wait whose reason starts `repo proposal:` while a proposal is pending, the derived class `repo-proposal`) (a new park, or a different gate) whose class is in `foreman.decides` enqueues one `gate` request `{job, args: {gate, reserved}, from: "forge"}`, unless one for that job and gate is pending or in progress. It does so whoever writes the park: `forge job set`, `forge job advance`'s repeated-failure park, the reconciler, and the syncs in `forge pr sync`, `forge sync` and `forge pr merge`. The policy lives in `lib/engine/pipeline/moves/foreman-gates.ts`; `lib/office/foreman/` keeps the gate runner and its policy checks.

`forge pr sync` (never `forge pr merge`) does the same for a job waiting on `pr-review` with changes requested or unresolved threads from someone with write access (`OWNER`, `MEMBER` or `COLLABORATOR`; a stranger's comment alone never starts an unattended rework): `args.gate: "pr-feedback"` and `args.key: <head sha>`, once per head in any status, so a push re-arms it.

Failing checks on such a job skip the gate runner: sync records a foreman `rework` itself (`ciHead` on the event dedupes it per head), writes a fixed `feedback.md` with no check text in it, moves the job to `build` and queues a `resume`; a reserved match falls back to the gate. A job in a mandate gets this CI rework only when its mandate delegates `pr-feedback` (read from the CLI's record of the job); otherwise, or when the mandate can't be read, sync queues the `pr-feedback` gate instead, which assist reports reserved, so its gate run hands it off.

The **CI rework cap** (`pr.maxCiReworks`, 3) bounds it: counted from the event log (foreman `rework` events with a `ciHead` since a person's latest `human` event), never from `job.json`, so a session can't reset it; at the cap a red head starts nothing, the reason names at most 5 allowlisted check names, a `ci-rework-capped` event is logged once per head, and no `pr-feedback` gate is queued, so the foreman is refused there too.

A head the foreman already reworked that is still red (its round ended with no new commit) is never reworked again or sent to the gate: the **CI re-run** (`ciRerun` in `lib/engine/pr/sync.ts`) re-runs its failed GitHub Actions jobs once, only when no check is pending, only runs in the PR's own repo that `gh run view` shows on that head and completed, and at most 5, and logs `ci-rerun`; when they fail again, or nothing could be re-run, it parks the job on `pr-review` with a `CI re-run:` reason and logs `ci-rerun-failed`, once per head, a person's later action included. `reservedFor` is asked without that reason, as without the cap's, and the re-run comes before the cap and never counts toward it. Any head counts, because only someone with write access can push a same-repo branch and fork PRs are never adopted; `forge job round` pulls that head into the worktree before the builder starts.

`requestScope` sends every `gate` to `_gates`, a request group no session serves (`validScope` refuses it); the dashboard (`POST /api/requests`) and `forge requests add` cannot create one. No session can list, claim or ack a gate request (claim and ack exit 1): only the pool's **gate runner** (`lib/office/foreman/run.ts`) takes them, in-process. With `daemon.enabled`, `foreman.enabled` and `foreman.assistants.enabled`, each tick hands it the pending gate requests, oldest first, and it starts a gate run (below) for each, at most `foreman.assistants.parallel` (1–16, default 2) at once. Gate runs count against neither `daemon.maxConcurrent` nor the machine cap, and the reconciler's claim-age rule counts a live run as busy. With the foreman off, `assistants.enabled: false` or the daemon stopped, gate requests stay pending for a human and the board shows each gate as a human's.

A **timed-out prompt** routes the same way: when a planner, spec writer, builder or integrator replies `NEEDS-PERMISSION` after the supervisor denied one of its permission prompts at `daemon.permissionTimeoutMinutes` (a `permission-timed-out` event inside its run), step's NP1b parks the job on `escalation` with the reason `prompt timed out: <role> needed <tool>, nobody answered it in time` (an eval job fails instead, NP1), once per agent run. The reason avoids the word `permission` because the default `foreman.reserved` lists it; reserved patterns and the security-must-pass rule apply as at any escalation, and an owner who wants these parks kept for a person adds `gate:escalation` or the pattern `prompt timed out`.

The assistant's brief gets one `Prompt timed out:` line built from the reason alone: no human saw the prompt, the assistant can't grant it, and the role's notes file says what it needed; it approves only when the work is complete without the call, reworks or revises with a note on going on without it, or escalates so a person can allow it.

`draft` and `direct` requests route to `_office`, a request group no session serves (the office session is retired): the pool's **office runner** runs each one as an **office run**, in code, while `foreman.enabled` holds ([Office runs](office.md#office-runs)).

## Gate runs

Code: `lib/office/foreman/run.ts`, `attempt.ts`, `decide.ts`, `verdict.ts`.

Each gate run, in the supervisor's code with no model session in between:
1. Claims the request in-process (session `gate-run:<uuid>`); a lost claim skips it. Job ids and gate classes are validated before any path or argv is built.
2. With `args.reserved` set, hands off (class `reserved`) and acks `rejected` `reserved: <pattern>`, with no child.
3. Runs assist (`gateAssist`, what `forge job assist` prints; `assistDraft` for a milestone draft), which recomputes `stale` and `reserved` and returns `{model, effort, brief}`; `stale` acks `done` `stale`, `reserved` is step 2, and a refusal acks `rejected` with it.
4. Spawns **one** headless `claude -p --agent forge:assistant` (`buildArgv` with the tools `Read, Grep, Glob, Write` and no Bash, the spawn's deny rules, `--permission-mode dontAsk`, assist's model and effort, and `--max-budget-usd` set to what is left of `daemon.dailyUsd.office` today), with `sessionEnv`, the confinement env, the trust env and `FORGE_DAEMON_SCOPE=_gates`, a scope that refuses every `forge` command. The brief is its first stdin line (`briefLine`: JSON-encoded, at most 256 KiB). This is the run's only model call.
5. Parses the last non-empty line of its result strictly: `^ASSIST: (approve|revise|rework|escalate) · (.+)$`, `·` being U+00B7. The reason is cleaned (no `"`, `` ` ``, `$`, `\` or control characters, whitespace collapsed, at most 200 characters) and must not be empty. A malformed line is asked once more on the same child with a fixed retry message; a second malformed line counts as `escalate` (`malformed verdict`). A malformed reply never becomes a decision.
6. Looks the verdict up in the **gate table** (`GATE_TABLE`): spec-approval → approve-spec / revise-spec / revise-spec; split-approval → approve-split / revise-split / revise-split; escalation and rounds-exhausted → approve / revise-spec / rework; conflicts → approve / escalate / approve; repo-proposal → approve-repos / reject-repos / reject-repos (the repos assist returned); pr-feedback → no action (ack `done` `no action: <reason>`, no resume) / rework / rework; release → approve-release / escalate / escalate; milestone-approval → draft approve / draft revise / draft revise. It records the decision through the same policy checks (`recordForemanDecision`, `decideDraft`), queues a `resume` for the job (never for `release` or a milestone draft) and acks `done` `<verdict>: <reason>`; the job's own session's next `forge job step` turns the decision into the gate's follow-up (["Job model"](../job-model.md) › Answered gates).
7. On `escalate` it records a **Foreman hand-off** (class `escalated`) and acks `rejected` `escalated: <reason>`. When the policy refuses the decision, a job that no longer waits on that gate is acked `done` `stale`; otherwise the run hands off (class `refused`) and acks `rejected` with the refusal. No hand-off is recorded for `release` or a milestone draft. `forge status`, `forge job show`, `/api/state` and the dashboard's Needs you card show the hand-off (`foremanHandoff`, derived from events) until a decision answers that park or the job parks again. That is `foreman.escalations: human`, the default. Under `foreman.escalations: foreman`, a job's gate (not `release`, not a milestone draft) that escalates, or whose decision is refused while the job still waits there, goes to the **senior pass** below instead, after the title-only override.

A **title-only request** (a spec-approval gate whose `request.md` has only its title) answered `escalate` comes back as `revise-spec` with the note `title-only request: <reason>` and a fixed `feedback.md`, once per person's decision: with a foreman `revise-spec` standing since the latest person's `human` event, the escalate stands.

## Senior pass

Code: `lib/office/foreman/senior.ts`, under `foreman.escalations: foreman`.

An escalate (a malformed reply included) or a refused decision goes through these checks in order (`seniorStart`), and only the last starts a senior pass:
1. The job no longer waits on that gate: ack `done` `stale`.
2. `reservedFor` over the job and the first reason (a `foreman.reserved` pattern, the total-round ceiling, a retro spec, or a human-only rule on an escalation park): a hand-off of class `reserved`, ack `rejected` `reserved: <match>`. Reserved topics stay with a person in Needs you.
3. A latest security review that isn't `PASS`: the job is shelved (`security review not PASS: a person signs off. <reason>`). No senior pass ever judges it.
4. A first reason that names an injection attempt (the word `injection`, which the assistant's prompt tells it to use): shelved (`first assistant flagged an injection attempt: a person decides. <reason>`). A second model would read the same injected text, so under `human` and `foreman` alike a detected injection ends with a person.
5. A `senior-pass` event for this gate after the job's latest `transition` (one per park): shelved (`senior pass already ran at this park. <reason>`).
6. The office's daily cap reached, or a meter that can't be read: shelved (`the office's daily cap holds the senior pass`).
7. The senior's assist (`gateAssist` with `senior`): `stale` acks `stale`, `reserved` (a mandate hold) hands off as in check 2.
8. The runner logs one `senior-pass {gate, first}` event as the Foreman, then a `senior-start` gate log line, then starts one more `forge:assistant` child through `startAttempt` (the same spawn, confinement, `_gates` scope, tools and meter as step 4) on `foreman.senior.model` and `foreman.senior.effort`, which beats the job's own effort.

The senior brief is the gate's assist brief with three lines before `Untrusted:`: `Senior pass (JSON): {"first":"escalate"|"refused","reason":"<cleaned reason>"}`, `Diff: <the latest round's review dir>/diff.patch` and `Verdicts: approve | revise | rework | shelve | escalate`. Its parser takes `shelve` too (`parseVerdict(text, { senior: true })`), with the same one retry.

A senior `approve`, `revise` or `rework` that the gate table maps to an action is recorded through `recordForemanDecision` with the note `senior pass: <reason>`, then one `resume`, ack `done` `<verdict>: senior pass: <reason>`; a pr-feedback `approve` records nothing (`no action`). Everything else shelves the job: `shelve` (`senior pass: <reason>`), `escalate`, malformed twice or a table `escalate` cell such as conflicts' `revise` (`senior pass escalated: <reason>`), a refused decision while the job still waits (`senior pass refused: <refusal>`; one that moved is `stale`), and no verdict, a timeout or a failed turn that isn't a limit (`senior pass failed: <message>`).

A stop, a refused spawn or a usage limit gives the claim back as for the first child; the next run finds the marker and shelves (check 5). Every shelve goes through `recordForemanShelve`, which refuses without the runner's authority or when the job no longer waits on the gate the run judged (a person may have answered it while the senior ran, and the job parked at another), then calls `shelveJob` as `FOREMAN_ACTOR` (["Job model"](../job-model.md) › Shelve): no hand-off, no resume, its PR left as it is, acked `done` `shelved: <reason>` with the run's outcome `shelved`.

The reason is model text and stays on the job (`job.shelved`, the `shelved` event, the ack and the gate log); the note posted to the job's linked issues is fixed text naming the gate, never the reason, because a tracker comment can be public. A refused shelve on a job that moved acks `stale`; otherwise it falls back to a hand-off (class `escalated`, `shelve refused: <message>`). The run's `attempts`, `usd` and `tokens` sum both children (at most 4 attempts), and the activity list shows `shelved` as a warn chip.

## When a run fails

When a run fails it never leaves a request claimed. A child that exits without a verdict, a failed turn that is not a usage limit, a turn past `daemon.turnTimeoutMinutes` (SIGTERM, then SIGKILL) or an unexpected error requeues the request through `requeueOrphanedRequests` (counted); one requeued before is rejected with `REQUEUE_REJECTED` and handed off (`its gate run failed twice`). After a failure no run starts for the retry wait, doubling from `retryMinMs` to `retryMaxMs`, reset by any run that got a verdict.

A usage limit gives the claim back uncounted (`releaseClaim`) and holds every run until `resetsAt`. A pool stop or close kills live runs and gives their claims back; when `forge dash` takes the daemon lock it requeues every in-progress gate request claimed by `gate-run:…`, since no earlier dash's run can still be live. After the child exits, the confine digest is compared with the pool's baseline, as after a session's turn.

## Spend and log

Each costed turn appends a meter record to `.forge/runtime/meter/_gates.jsonl` (ledger role `assistant`, titled `Foreman gates`; the meter files of the retired assistant sessions still read as `assistant`). `daemon.dailyUsd.office` caps the office runs and the gate runs together: at the cap, or when a meter can't be read, no gate or office run starts. The runner writes JSON lines (`gate-start`, `gate-end`, `gate-held`, `error`, never claude's text) to `.forge/runtime/daemons/_gates.log` with `openAppend`, which `forge daemon log --gates` prints, and seeds its list of the last 50 runs from the newest valid `gate-end` records (`readLogPage`, each field validated).

## Context rule

The gate runner never reads a job file into a model's context: the brief carries absolute paths, the gate class, config lists and mandate guidance fenced by `fenceImport`, never file content. The `forge:assistant` reads the files and writes `feedback.md` itself on `revise` or `rework`; its only other output is the verdict line. An office run keeps the same rule: it reads only the CLI children's JSON (never a survey, board, staging file or draft), the drafter's reply is never read, a surveyor's reply only as cleaned `SURVEY:` lines, and the director's only through `parseDirect`.
