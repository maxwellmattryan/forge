# Job model

`stage` is where the job is in the pipeline:
`backlog → plan → spec → design → build → verify → review → integrate → decide → pr → done`

Under `pipeline.plan: auto` intake goes to `spec`, and the planner runs only for a split: on a long request the spec-writer's **split check** answers one job or a split first, and a `Split: yes` spec moves the job to `plan` (SP8); a planner `SINGLE` sends it back to `spec`, where the spec-writer writes the full spec (SP2). `plan: always` still plans first.

Integrate runs before decide, so the approver judges the branch as it will merge, and an approved job opens its PR at once. With `approver.skipWhenClean` on and auto-merge off, a **clean pass** skips the approver: every lens of the full panel passed, the gate check since the review found no escalation reason, and no protected path, runbook, unproven acceptance criterion, instruction change, recall eval, wait or decision since the review stands in the way. DC13 then runs `forge job decision --clean`, which checks the same again, renders `decision.md` and `pr.md`, and records Forge's own `APPROVE` (`clean: true`, never auto-merge eligible), bound to the last review: the job goes on as for the approver's `APPROVE`, and a later review checks again (docs/CONFIG.md "Clean pass"). An escalated one opens its PR too: an `ESCALATE`, the **gate reasons** `forge job gate` records before the approver (DC12: unapproved protected paths, a review Summary that says ESCALATE, a runbook, unmapped or failing ACs, a changed version or dependency table) and a missing recall eval are **merge gates**, which hold the merge, not the push. The PR opens, `forge pr gate` says on it why it waits and labels it, and the job parks in `pr` once, on one escalation park listing every open rule (PR15, `escalation: <rules>`; then PR17 for the recall eval), until a person decides on the open PR; one person's approve there clears every rule it lists, and the Foreman never clears `protected-paths`, `lens-escalate` or `runbook`. A push that is itself the risk (CI config, a security review that isn't `PASS`, secrets the scan only reported) is a **held push**: `forge pr open` refuses it and the job parks before anything leaves the machine (PR13; docs/CONFIG.md "The held push"). After any gate wait (an escalation, an infra runbook, a budget stop), step runs `forge integrate` again before the PR, and does more work (verify, the integrator, the integration review) only when it reports `behind > 0`. Older jobs found in `decide` with no integration since their review integrate before `pr`. Eval jobs never integrate: review sends them straight to `decide`.

`state` is what is happening there:
`queued | running | waiting | blocked | failed | cancelled | done`

`waitingOn` says why a job is waiting:
`spec-approval | split-approval | issue-link | input | escalation | infra | conflicts | rounds-exhausted | pr-review | external | budget | human | shelved | overlap` (`human`: a CLI check, such as the secret scan, stopped the job; approve means "I cleared it, check again", never "ship it anyway"; `shelved`: a person, or the Foreman's senior pass, set the job aside, see **Shelve**; `overlap`: step PR20 holds a mandate PR's merge while a ready PR ranked ahead of it in its merge queue lands, and `forge sync` releases it, so nobody is asked to decide, see ["Foreman"](foreman.md) › Ship policy)

Trackers see a coarser view: `queued`, `in-progress`, `review`, `blocked`, `done`, `cancelled`. Adapters map those to labels, GitHub Project options, or anything else.

**Moves** (`lib/engine/pipeline/moves/`). A change to a job's stage, state or `waitingOn` that needs follow-up goes through `moveJob`: one locked `setJob` write, then three effects in this order, each once, against the job as the write's lock read it and the job after it. The **environment** effect tears down a job's environment when an active job finishes; the **gate** effect queues the Foreman's `gate` request on a new park on a class it decides (Foreman › Routing); the **mirror** effect mirrors the job to its tracker, logging a failure as `tracker-error` and never throwing. An effect with nothing to do is a no-op, and the call resolves once the mirror has finished. Three named inputs change it, and nothing disables the gate: `environment: 'stop'` only stops the environment (the inbox session and the office's `_office` scope, chosen from the process's own daemon scope, never from job data), `mirror: false` skips the mirror (a cancel after a failed tracker claim, where Forge doesn't hold the issue), and `afterWrite` runs between the write and the effects (`forge job set`'s dependency refresh). `forge job set`, `forge job advance`'s repeated-failure park, the reconciler's escalation, the syncs in `forge pr sync`, `forge sync` and `forge pr merge`, the tracker claim-failure cancels and `forge sync`'s umbrella done all move through it. `mirrorJob` runs the mirror alone, for `forge sync`'s dependency release and `forge job delete`. Notifications follow every transition from every writer instead, through `setJob`'s transition hook list (`lib/core/job/transitions.ts`), on which `main()` in `lib/cli/main.ts` registers notify at start; importing `lib/office/notify.ts` registers nothing.

**Answered gates** (`lib/engine/pipeline/step/answered.ts`, rules GA1–GA11). A decision recorded with `forge job human` (a person's or the foreman's) moves the job at its next `forge job step`, which returns the gate's follow-up `forge job set` as a `run` action ahead of the park's wait (G4/G4b) and the PR claim release (G3), so `forge job human` plus `forge requests add resume --job <id>` is the whole recipe from any session. A decision answers the park only when it is a `human` event logged after the job's last `transition`, that transition entered exactly the job's current stage, `waiting` state and `waitingOn`, and the latest such event's action is one the gate takes; positions in the log, not timestamps, decide. So an approve at an earlier park, or at a `budget` park, never moves a later escalation, and `note`, `budget-ack`, `release-approval` and `foreman-handoff` events never answer. The follow-ups: `approve-spec` → `--state running`; `approve` at `escalation` or `rounds-exhausted` → `integrate` (`decide` from `integrate`), at `infra` → `integrate`, at `issue-link` or a `human` check → `--state running`; `approve` or `rework` at `conflicts` → `integrate`; `rework` at `escalation`, `rounds-exhausted`, `infra`, `pr-review` or `human` → `build`; `revise-spec` → `spec`; `approve-split`/`revise-split` → `plan`; `approve-repos`/`reject-repos` at a repo proposal park → `--state running` (RP1 parks again while proposals remain); `answer` at `input` → `--state running`. A `budget` park is answered by an approve only while nothing is still over its limit after acks (`budgetExceeded`, which `loadStepInput` computes only at a budget park), and never when it is the repo cap (`repo budget:`). An `approve` or `rework` at an escalation before build (`backlog`, `plan`, `spec`, `design`) is not answered: revise instead. Anything unanswered waits as before. A job whose log holds no matching transition (hand-written or very old) waits too. Once the follow-up has run the job is no longer waiting, so no GA rule fires twice.

**Shelve** (`lib/engine/pipeline/moves/shelve.ts`). `forge job shelve <id> --reason "…"` sets a waiting, queued, failed or blocked job aside, with no agent running, from a person's own terminal (every daemon session is refused): in one locked write it waits on `shelved` at its stage, with reason `shelved: <reason>`, records `job.shelved` (`{ at, reason, actor, from: { state, waitingOn, reason } }`, job schema step `shelved`) and releases its lease. Then it logs `shelved`, stops its environment (the worktree stays) and posts one note to its issues (docs/TRACKERS.md); its PR is never touched. Under `foreman.escalations: foreman`, `forge dash`'s gate runner shelves too, as the Foreman: a gate its senior pass could not settle, or one held by a security review that isn't `PASS`, goes through `recordForemanShelve` (lib/office/foreman/senior.ts), which needs the runner's in-process authority and a job still waiting on the gate the run judged, then the same `shelveJob` with actor `{ login: null, source: "foreman" }` and a fixed note for the issues that names the gate and never the model-written reason (["Foreman"](foreman.md) › Senior pass). Every automatic mover keys on specific `waitingOn` values, so none moves a shelved job: no answered gate (a `human` approve logged while shelved answers nothing, and step waits at G4b), no Foreman gate request, no notification, no dependency unpark, no reconciler resume. `forge sync` and `forge pr sync` still finish it when a person merged its PR (`done`) or closed it (`cancelled`), and otherwise leave it: no route to `integrate`, no re-park on `pr-review` or `conflicts`, no reopen. Only a person takes it off the shelf, and `setJob` holds that for every writer (`checkShelfMove` in lib/core/job/fields.ts): a write that moves a shelved job's stage, state or `waitingOn` is refused (`human_only`) unless it un-shelves it or moves it to `done` or `cancelled`; only `shelveJob` (`forge job shelve`, or the gate runner's Foreman shelve) puts a job on `shelved`; a job off the shelf keeps no record; and `--field shelved` is locked. Finishing a shelved job (a cancel, Close in the Shelved list, a merge or close on GitHub) sets `job.finishedWhileShelved`, kept while it stays `done` or `cancelled` and locked too, and a write that moves such a job back to an active state is refused (`human_only`) without a person's grant (`isHumanGrant`): `forge job set <id> --state …` asks the person at the terminal to type the job id, and the transition then carries their actor and clears the mark. Un-shelving is a human-only operation (`forge job unshelve`, or the dashboard's Shelved list through `POST /api/shelf`): one `setJob` restores `from` (or `waiting` on `human` when the record is missing or unreadable), logs `unshelved` with the grant's actor and channel, and mirrors the job. It queues no Foreman gate request, since the person is already acting, so the job comes back to their Needs you. A shelved job is not counted as waiting: `forge status` lists it last as `shelved`, `forge stats` counts it in `counts.shelved`, and the dashboard leaves it out of Needs you, the Waiting filter and the Overview's count.

**Ownership**: one fenced **lease** per job (`job.lease`: `{ driver, epoch, since, renewedAt, expiresAt }`, lib/core/job/store.ts) says which session drives it. The lease is `live` while it has a driver and `expiresAt` is ahead, `expired` once that time has passed, and `none` without a driver.
- **Claim** (`forge job claim`, `forge job new|from-ref --session`, `forge next --claim`, dependency claims) takes a lease that is none, expired or already the caller's; another driver's live lease refuses with exit 3 (`owned`) unless `--force`. Every change of driver (null to a session included) increments `epoch` and sets `since`; a re-claim by the same driver keeps both. Every claim sets `renewedAt` and extends `expiresAt` to at least 30 minutes ahead (`LEASE_MS`). The `claimed` event records the epoch, and a takeover logs a `note`: `took over from session <old> (lease expired|forced)`. The claim's output returns `lease` and `epoch`.
- **Renewal** comes only from the driver's own activity: `forge job step|advance <id> --session S` (only while S is the driver, even past expiry, provided nobody took over), the worktree commands its agents run (`forge run`, `forge verify` and the others in `lib/engine/workspace/` and `lib/engine/verify/`) and `forge job agent start|end`. `agent start` extends the lease to two hours (`AGENT_LEASE_MS`), so a long builder with no CLI writes keeps its driver; that is the ceiling, so a crashed session can't hold a job forever. A renewal without a session (the worktree and agent commands) renews only a live lease, so an orphaned agent can't revive a dead driver's. Nothing else renews: sync, dependency parking, other sessions, the dashboard and the reconciler never do.
- **Expiry by the supervisor**: when a `forge dash` session's child exits for any reason, the supervisor expires the lease of every job whose driver is any of that session's ids (current, spawn or past: `recordIds` in lib/office/driver.ts), not only its own scope's, each in one locked write: `expiresAt` becomes now, driver and epoch are kept, and a `lease-expired { session, reason }` event is logged. So an inbox that dies holding a job it claimed for intake frees it at once. At pool start, holding the daemon lock and after reaping orphans, the pool runs the same release for every id in every session record (`daemonSessionIds`, reason `dash-start`), since no earlier dash's child can still run, and marks those jobs' running agents lost too. A lease held by an interactive session (in no record) runs out only by time, and its agents and claims are left alone.
- **Release** (`forge job release`, parking on dependencies) drops the driver and `expiresAt` and keeps the epoch, so it only ever grows. Idle jobs give their lease up: parking a job on dependencies releases it in the same locked write (a `released` event), split children start with no driver (`forge job new --parent` never claims, even with `--session`), and `forge job split` releases the parked umbrella.
- **Fencing**: `forge job step|advance|set|claim` and `forge job agent start|end` accept `--epoch N`, the epoch the caller's claim returned. With it, the command is refused before any write, inside the job lock and in the same write it guards, when `lease.epoch` is not N, or (with `--session S`) the driver is not S: exit 3, code `stale_epoch`, `job <id> was taken over (lease epoch <cur>, you hold <N>); stop driving it`. `advance` checks at entry and before every command it runs. Without `--epoch`, `advance` keeps the driver check (it refuses a job its session does not drive). Writes not made on a driver's behalf (sync, the dashboard, humans, the reconciler) are never fenced. The orchestrator skill passes `--epoch` on every step and advance, so a session that slept or was suspended through a takeover can't write after it.
- **Requests follow the lease** (`requeueOrphans` in lib/core/job/requests.ts): an `in-progress` request goes back to `pending` when (a) it routes to a job whose lease its session holds and that lease has expired, (b) its session is one the caller saw exit (the supervisor on a child's exit, the pool at boot), or (c) neither lease rule covers it and its claim is older than 30 minutes (inbox, office, gate and job-less requests; no lease is ever read for the `_gates` group). Rule (c) never requeues a claim of a `forge dash` session that is `busy` or `stopping`, or of a live gate run (claim session `gate-run:<uuid>`), since a turn may run up to `daemon.turnTimeoutMinutes`, and only callers that can see those sessions apply it: the dash's reconciler, `forge sync` and `forge requests` (list) when no dash runs, and the pool at boot. A supervisor seeing its own child exit applies only (a) and (b). Requeueing clears its session, increments `requeues` and notes it on the job; a request orphaned a second time is `rejected` with `its session ended twice while handling it`, so one that kills its session can't loop. A gate run requeues its own request the same way when it fails, and the second failure rejects it with a Foreman hand-off (`its gate run failed twice`); a usage limit or a pool stop gives the claim back without counting. A `resume` is closed by Forge, not the model: when a job session's written turn ends with a working result, each `resume` for that job the turn was written for, still `pending` or `in-progress` under one of the session's own ids, becomes `done` (`its job session's turn took it up`, logged as `requests-closed`); a failed turn, a woken turn and the inbox, office and chat sessions close nothing, and an ack already made wins. A resume that arrives mid-turn gets its own next turn. Every reconciler pass then sweeps the `pending` resumes no session will act on ([Daemon](daemon.md) › Reconciler).

`forge next --claim --session S` first resumes a queued job nobody drives (not eval, not an umbrella, dependencies done, no `resume` request pending or in progress, no live lease), oldest first, and returns it with `resumed: true`; only then does it start a new tracker item. `forge sync` moves a PR job to `integrate` only when its lease is not live, judged inside the job lock, and never claims the job itself. The dashboard drawer's **Resume** (and the command bar's `continue`) queues a `resume` for a queued, failed or expired job; the server refuses one with 409 while another driver's lease is live, but not when the driver is any id the job's own pool session has had (current, spawn or past, so a `session-changed` doesn't make it a stranger) and that session's child runs (`idle`, `busy` or `stopping`), since it takes the resume itself (see ["Dashboard security"](dashboard-security.md)). The server asks only the pool session whose scope is that job (`whoDrives` in lib/office/driver.ts, never `ps`), so the same id driving another job is a stranger there. `/api/state` and the job detail report each job's `ownerStatus` from the lease; only the detail sets `jobSession`, from the same answer. Jobs record each session that drove them in `runs[]`.

**Evidence**: every `forge verify` run records the worktree HEAD it checked, its attempt number within the round, and its result; earlier attempts are archived, never overwritten, so "verify first-pass" means the first attempt. `forge pr open` refuses to push a HEAD that this round's last verify run did not pass on (and every member HEAD with it). `forge job scope` records the commit the reviewers are given (the round's `scope` event, logged before any reviewer starts), and `forge job verdicts` the HEAD when the verdicts are recorded, after the panel ended. When the integrator resolves conflicts after the panel passed, a one-lens `code` review of the resolution (`review/integration/code.md`, `forge job verdicts --round integration`) must pass before the PR opens (under `pr.integrationReview: code-only`, the default, a resolution whose conflicts and changed files were all docs or generated files skips it with a note); it is logged as an `integration-review` event, not in `job.verdicts`, so stats keep counting numbered rounds only. `forge pr open` records the sha it pushed (`pr.pushedSha`), and the first `forge pr sync` that sees the PR merged measures the human delta, the commits, lines and files humans added after that push (`pr.humanDelta`). After the merge, `forge sync` keeps measuring the job's outcome (`job.outcome`: a revert, follow-up bug issues and churn inside `outcomes.windowDays`) until the window closes, and `lib/engine/evals/autonomy.ts` judges a job with a final outcome for the autonomy rate. Each verify also writes a test-integrity report (deleted or renamed tests, added skip/focus markers, the test-count delta, test and CI config edits since the merge-base), which reviewers and the approver read and `verifyIntegrity: block` turns into a failure. Evidence for an older commit is not evidence.

**Reviewed head**: in `decide` and `pr`, `forge job step` checks that HEAD is still the head the round's review was given (`reviewCurrent` in `lib/engine/pr/eligible.ts`). The reviewed head is the `head` on the round's own `scope` event, the one step logs after verify and before any reviewer starts (RV2): the round's first `scope` event after its last verify run, both before the panel's first reviewer start (the first `reviewer:` `agent-start` since the round's `round` event, so leaving review and coming back within the round keeps that bound), and only when it names the head that run passed on. A `forge job scope` run earlier in the round, while building, is not that event and anchors nothing. A commit, a `forge verify` or a `scope` event after a reviewer started (RV2 logs a fresh one after any verify) doesn't move the anchor either: the reviewers read the head they were started on, so a later head goes back to review. Member repos use that event's `heads`. The `verdicts` sha is not the anchor, because a reviewer's commit made during the panel would already be inside it. HEAD may carry clean merges of the base on top (the same `headFollows` rule the merge gate uses). Anything else (a plain commit, a merge that carries extra changes, a merge of a branch that is not the base, rewritten history, a missing or malformed record, a reviewed member with no trusted worktree, a git failure) sends the job back: DC11 (first in decide) and PR12 (first in pr) run `forge job set <id> --stage review`, RV11 hands the recorded round to `build`, B1 opens the next round, B8 sends it to `verify` with no builder, and the new head then gets a full round: verify, the panel (or `review.onPrFeedback`'s lenses on an open PR), integrate and the approver again. A round with no `verdicts` event binds nothing (a skipped review, an eval job, a rounds-exhausted round a human approved). An integrate conflict episode is exempt when it started on a reviewed head, left `integrate` for `decide` or `pr`, and its last verify passed: the head that verify checked becomes the reviewed head, so a commit after it still goes back to review. A conflict-free `pr.updateStrategy: rebase`, each interim release bump commit and a generated-only integration (see **Generated files**) cost one review round each, since none of them is a clean base merge. Every return opens a new round that either records verdicts on its own scope head or has none, so one commit can't send a job back twice, and repeated late commits stop at `maxRounds`, `maxTotalRounds` and the round budget, where the job parks on `rounds-exhausted` for a human.

**Generated files**: committed paths a command regenerates (`worktrees.generated`, e.g. `dashboard/dist/**`) are never hand-merged. When `forge integrate` stops on conflicts, Forge splits them: a path counts as generated only when it matches a glob and passes the same checks as `forge git add` (no leading `-`, nothing absolute, no `..`, no `.git` segment, no symlinked parent leading out of the worktree, and the name must resolve to itself); everything else is a real conflict. When generated paths are all a stop has, Forge takes the base side of each (`--theirs` in a merge, `--ours` in a rebase; a path the base deleted is deleted), runs `worktrees.generatedBy` through the same logging as `forge run` (`logs/integrate-regenerate-*.log`), stages every glob-matching path the build wrote, added or deleted, and commits the merge or continues the rebase, repeating for each later pick that stops the same way. Names reach git only as literal pathspecs, over stdin. The build runs only in the job's own worktree on the job's branch (never the main checkout, a subdirectory or another branch; mid-rebase the branch is read from `rebase-merge/head-name`), and every `rebase --continue` Forge runs first checks that the todo holds only picks. A mixed stop goes to the integrator with the real conflicts only: the generated paths are listed as `regenerated` and, under `--keep-conflicts`, staged from the base side but not built, since the sources may still hold conflict markers; `forge integrate --continue` rebuilds them once nothing is unmerged. When Forge can't rebuild (no `generatedBy` command, an invalid glob, the worktree guard, or a failing build), it falls back to the old behaviour: every unmerged path is listed, `regenerateError` says why (with the build's last 20 lines), and an aborted merge leaves the worktree clean. A generated-only integration logs `integrated` with `regenerated`, so step re-verifies it and moves to `pr`: no integrator runs and no integration review is needed. Its merge commit is not git's own merge, so the reviewed-head rule (see **Reviewed head**) sends the job back to review once before the PR opens. Results and events carry `regenerated` and `regenerateError` only when they are non-empty.

**Budgets**: `pipeline.budget` limits tokens, estimated cost, agent minutes (summed agent run time), committed changed lines vs the base, and failed verify runs per round. Limits are read from config at every check, and a job's own `budget.limits` override them. Three checkpoints enforce them: `forge job agent end`, `forge job round` (before incrementing) and `forge verify`. An exceeded key parks the job at `waiting` on `budget` with its stage kept, logs a `budget` event, and adds a `budget` block to the command's JSON. `forge job budget <id> --set k=v` raises a limit; `--ack` grants one more full budget past the current use (a `verifyRetries` ack lasts only for its round). Both are human-only operations: without a person confirming at a terminal they refuse with `human_only`, and the dashboard's Approve & continue on the budget gate does the same through `POST /api/jobs/:id/budget` ([Daemon security](daemon-security.md) › Human-only operations). Neither changes state; the orchestrator resumes the job. Every checkpoint writes `budget.lastCheck` with what was used, so the dashboard can show it without running git. The dashboard derives effective limits and use client-side from `config.pipeline.budget`, the job's usage and `lastCheck`, and offers approve (ack, or raise via the note) on `waiting:budget`.

**Dependencies**: `dependsOn` lists job ids, set with `forge job set <id> --field 'dependsOn=[…]'`, which rejects unknown ids, the job itself and cycles. A dependency counts only when its job is `done`; `cancelled` or missing ones block until a human removes them. A queued job with unmet dependencies is parked at `waiting` on `external` with a `dependencies not done: …` reason (other waits are never overwritten), `forge next` skips it, and `forge job claim` refuses it with exit code 4 unless `--force`. Parking releases the job's lease, since nobody drives a parked job; rewriting the reason of a parked job or unparking it keeps the driver, so a `--force` claim on a parked job survives sync. `forge sync` unparks a job to `queued` once its dependencies are done, and `forge next --claim` then resumes it. A new branch for a job with exactly one unmerged dependency starts from that dependency's branch, and `job.base` becomes that branch, so the PR, `forge integrate` and reviewers' diffs are against it (a `stacked` event). Once the dependency merges, `forge sync` moves the base back to the dependency's own base (retargeting an open PR with `gh pr edit --base`) and logs `retargeted`. More than one unmerged dependency is refused.

**Inbox**: dashboard requests are claimed by a session before they are handled, under a lock, so two orchestrators draining the same inbox cannot both act on one request. A claim with no ack for 30 minutes can be taken over. The drainer is either your own session (`/forge requests`) or, with `daemon.enabled`, the headless sessions `forge dash` supervises (see ["Daemon"](daemon.md)); both go through the same claims, so they can run side by side. Each request has a **scope**: a job request (`approve`, `revise-spec`, `rework`, `answer`, `cancel`, `resume`) whose job exists belongs to that job, and everything else, including a job request whose job is malformed or unknown, belongs to the inbox (`_inbox`). A daemon session sees and may claim or ack only the requests of its own scope; a human's session sees them all. With `daemon.enabled`, `forge dash`'s **intake runner** answers the inbox's requests in code, with no claude session (["Daemon"](daemon.md) › Intake runner): it claims each under the inbox's intake session id (`intakeSessionId` in `_inbox.json`), runs its fixed `forge` calls as CLI children in the `_inbox` scope, and acks it; only a request type it doesn't handle reaches the inbox session. Either way the inbox does intake only: for `run`/`next` it creates or claims the job and hands it off with `forge requests add resume --job <id> --intake run|next --session <its session>`, which releases the claim when that session (or any inbox session id, the intake session id included) holds it, so every pipeline runs in its job's own session. A boot releases the intake session id's leases and claims like any recorded session's; the inbox session's own exit never does. Under the inbox scope, `forge worktree create` and `forge job agent … start` refuse, so the inbox never drives a pipeline. A job created from the dashboard (`POST /api/jobs`) skips the inbox: the server creates it and queues its `resume` (`args.intake: new`) straight to the job's own session.
