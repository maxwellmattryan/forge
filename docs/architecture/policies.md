# Policies

## Authorship policy

`lib/engine/guard/attribution.ts` defines what counts as AI attribution: signature lines and trailers, not mentions. It is shared by the Bash `PreToolUse` hook (`hooks/no-ai-attribution.ts`, which blocks before anything is written), by `forge pr open` (which rewrites the messages of the commits it checked from their raw objects, keeping every tree, author and committer, moves the branch only if it still points at the checked commit, then pushes that exact commit with `--force-with-lease` if anything changed), and by the GitHub tracker (which strips issue and comment bodies). On Node older than 22.18 the hook cannot load and exits 1, which Claude Code does not treat as a block, so the policy is not enforced there. The policy is on by default (`aiAttribution: forbid`).

The hook (`commandAttribution`) checks every Bash command that mentions `git`, `gh` or `glab`, so global options before the subcommand (`git -c k=v commit`, `git -C dir commit`, `gh -R o/r pr create`) and a path to the binary hide nothing. It scans the command text and every message file the command names: `--file`, `--body-file`, `--notes-file` (`gh release create|edit`, `glab release`), `--input` (`gh api`, `glab api`) and `--template` with `=` or a space, plus git's unambiguous abbreviations `--fi`, `--fil` and `--te` through `--templat` (only when `=` or a space follows the name, so `--filter=`, `--fixup=` and `--text` never count); `-F` or `-t` attached, spaced or ending a short-option cluster (`-aF msg`); and a field that reads a file, `key=@path` after `-F`, `-f`, `--field` or `--raw-field` (attached, spaced, with `=`, or quoted as a whole), of which only `path` is read. A relative file is tried against the command's cwd and against each of the first 8 `-C <dir>`, each resolved against the one before; only the first 32 distinct message files, in command order, are read, and at most 8 MiB is read in total across them: a file whose size would pass what is left is skipped unread, and a later one that fits is still read. Those caps keep the hook fast on any command, which matters because Claude Code lets a timed-out hook through. The command and each file's text are scanned as they are and once more split on quotes and literal `\n`, so a JSON body for `gh api --input` reports its trailer line. Only an existing regular file under 1 MiB is read, opened non-blocking, so a FIFO, device or directory is skipped and never stalls the hook; `-` and `@-` (stdin) are skipped. A command that names no attribution exits 0 without starting a git child. Only then does it read the opt-out (`repoAllowsAttribution`): `aiAttribution: allow` counts only in the `.forge/config.yml` of the main checkout of `CLAUDE_PROJECT_DIR` (found through `git rev-parse --git-common-dir`), never a worktree's own `.forge/`, the command's cwd or `FORGE_ROOT`, all of which an agent can choose or write; any failure there means no opt-out.

Accepted residuals, which the hook does not catch:
- a message built at run time, from command substitution or a variable (`-m "$(cat msg)"`, `-F "$F"`);
- a relative file after `cd dir &&`, or a `~` path;
- a commit made by another program (`node -e`, an editor);
- a worktree whose `.git` file was rewritten to point at another repository;
- an agent that writes the main checkout's own `.forge/config.yml` (the same trust as every other main-checkout key);
- past the first 8 `-C` directories or the first 32 message files, nothing more is read;
- a message file that would take the bytes read past 8 MiB is skipped unread (an agent that can write that much can already use `$(cat msg)`);
- a `-C` in an earlier command on the same line shifts later bases: `git -C a …; git -C b commit -F m` tries `a/b/m`, not `b/m`;
- a path with spaces after `=@` that isn't quoted as a whole (`-F body=@"a b.md"`; `-F 'body=@a b.md'` is read);
- a JSON body escaped beyond `\n` (`\u003c` for `<`, say);
- an unquoted `--trailer=` value with no space (`--trailer=Co-Authored-By:Claude`).

The hook runs outside the Bash sandbox, as the user. It stats and reads (regular files under 1 MiB only, 8 MiB in total per command) every path a command names, and echoes back only attribution-shaped lines. So a sandboxed session can learn whether a file outside its sandbox holds such a line, and that line's text, but nothing else.

The backstop for all of them is `forge pr open`, which rewrites offending commit messages before it pushes and strips PR bodies, plus the GitHub tracker's body stripping.

## Review policy

Reviewers tag findings `[blocker] [major] [minor] [nit]`. The CLI decides the verdict from the tags and the repo's `review.blockOn`, not from the reviewer's own first line. This keeps the threshold consistent across lenses and models: "CHANGES over a nit" or "PASS over a blocker" can't slip through. A review without a verdict line is `CHANGES` when its tags already force a round, otherwise `MALFORMED` and re-run once; a second malformed review is counted as `CHANGES` (`--malformed changes`) so a reviewer that cannot follow the format cannot stall the job. A lens with no file is `PENDING` while its reviewer (`reviewer:<lens>` in `job.agents`) has not ended for that review, and `MISSING`, with the expected path, once it has: an agent can claim a review it never wrote, so the orchestrator re-spawns it rather than waiting. `forge job round` and `forge job paths` create the review directory before any reviewer is briefed.

**Model diversity.** A gate that runs on the same model as the builder tends to share its blind spots: it finds the code plausible for the same reasons the builder wrote it. `forge roster` therefore always reports which gatekeepers (the approver, then each panel lens) share the builder's model family. The family is `opus`, `sonnet`, `haiku` or `fable` when the model string names one, else the whole string, with `inherit` resolved through the orchestrator's model. With `runtime.diversity: true`, `forge roster` and `forge init write` turn each overlap into a warning. It never blocks a job: picking models is the human's call. The Balanced init preset already puts the approver on a different family.

## Repo budget

Per-job budgets stop one job; `budget:` (docs/CONFIG.md "Repo budget") caps the repo's spend per UTC day and month. `lib/engine/metrics/spend.ts` is one ledger from two sources, bucketed by UTC day, role and model: every `agent-end` usage across live jobs and `.forge/archive/` records, re-priced with today's table (`buckets`, source `reported`), and every daemon session's meter (`metered`, source `supervisor`, below), which claude priced and which is never re-priced. A job's meter feeds role `job-session`, `_inbox` role `inbox`, `_office` role `office`, `_gates` role `assistant` (titled `Foreman gates`: every gate run's `forge:assistant` turns; a retired assistant session's meter from before gate runs still reads as role `assistant`, titled with its number), and each `_chat-<id>` role `chat` (titled `Chat <id>`). Each metered cell, per day and model, is the remainder `max(0, metered − covered)`, where covered is the usage of the job's `metered: true` agent ends, priced and keyed as the reported buckets are; so the `job-session` row is what the session spent beyond the agents it reported (any agent spend it never reported included), and nothing counts twice. A third source, `session-usage`, carries the sessions' own per-turn usage (**Session usage** below) as role `orchestrator`: from each job's `session-usage` events and the inbox's and office's session-usage files, priced as the reported buckets are. The meter already counts those calls, so its rows overlap the `supervisor` ones and no total adds them: `periodTotals`, the repo budget, `jobSpend`, `spentFrom` and `mandateSpend` read only `reported` and `supervisor`. The inbox, the office, the gate runs, each chat, and the meter of a deleted job are entries of their own (`source: 'session'`), the inbox and office also with a session-usage file and no meter yet; meter files are never deleted. `.forge/runtime/spend.json` caches each entry's buckets keyed by its events file's size and mtime (an archive record's by `lstat`), its meter file's and (inbox and office) its session-usage file's, plus the cache version (3) and a hash of the price table. It is read through one `O_NOFOLLOW | O_NONBLOCK` descriptor and rebuilt on any mismatch, so a planted symlink or a stale or understated cache is never trusted; `/api/state` and the daemon pool compute the status with `write: false`, so neither writes it. `lib/engine/metrics/repo-budget.ts` turns the ledger into `RepoBudgetStatus` and enforces it in the CLI only, at every place a job starts: `forge job new` (parks the new job), `forge job claim` (parks it and exits 4, unless an agent is running, another live session owns it, or it already waits), `forge next` (starts nothing) and `forge job from-ref` (exits 4). Repo holds reuse `waiting: budget` with a `repo budget:` reason, so the budget notifications fire unchanged. Release (back to `queued`, plus a `resume` when the daemon is on) re-checks the job's own per-job budget, so a session that rewrites its per-job stop's reason to `repo budget:` stays held. A human acknowledges a period with `forge budget ack` or `POST /api/budget/ack`; the ack is a `repo-budget-ack` line in `.forge/runtime/audit.jsonl`, and the effective cap is `cap × (1 + acks)`. `forge budget ack` is a human-only operation (see [Daemon security](daemon-security.md) › Human-only operations), `forge job new --force` refuses under `FORGE_DAEMON=1`, and `DENY_TOOLS` covers the cache and the audit log.

Residual risk: a session with shell write access could still append a fake `repo-budget-ack` line or forge a fingerprint-matching cache, the same trust level as rewriting `job.json`'s `budget.ack` by hand ("Request provenance is not authenticated" in [Untrusted input](untrusted-input.md)). `forge budget ack` and `forge job budget --set|--ack` themselves are human-only operations: a person confirms them at a terminal, or acknowledges in the dashboard ([Daemon security](daemon-security.md) › Human-only operations). A job claimed before the cap trips runs until its next claim, bounded by its per-job budget.

## Usage accounting

The orchestrator records every agent start and end. With Claude Code, `--import` reads the subagent transcript (`<session>/subagents/agent-<id>.jsonl` under `$CLAUDE_CONFIG_DIR/projects`, else `~/.claude/projects`). It looks first under the job's own sessions (the owner's, then the last five in `runs[]`) in this repo's project dirs, and falls back to scanning every project dir for an agent whose parent session isn't recorded. The orchestrator records a background agent's id as soon as it is spawned (`forge job agent <id> attach`), so the dashboard can follow that transcript while the agent runs. Input and cache tokens come out exact, along with tool calls (by unique block id) and duration. Output tokens are estimated from the logged content, because transcripts store the stream's opening usage snapshot. A resumed agent (SendMessage, as the builder is for rework) appends to the same transcript, so each agent record keeps `importedThrough`, the last transcript timestamp imported per agent id, and the next import of that agent counts and times only the lines after it. Without a transcript, the runtime-reported total is used with a blend assumption, and the dashboard shows coverage (how many agent runs reported usage, and how many exactly). Prices live in `lib/integrations/claude/pricing.json` (dated, overridable via `usage.pricing`). For subscription plans they're API-equivalent figures, not a bill.

**Agent runs.** `forge job agent <id> end` also records each ended run on the role's agent record, as one `runHistory` entry (`recordRun` in `lib/core/job/schema.ts`, the newest 50 per role): its round, start and end, status, model, the billing split it added to `usage` (input, output, cache read, cache write and the total, which for a `--tokens` run is the total alone), and, when the end imported a transcript (`--import`, or always in a daemon session), its context composition. A further end with usage on an ended agent adds to the last run; a lost end of a running agent records a run with no usage. `usage.byRole`, `usage.byModel` and the `agent-end` event are unchanged: the composition is never in an event. The composition (`composeContext` in `lib/engine/metrics/composition.ts`) is an estimate of the last request's context in the imported span. The first request's whole input in the transcript is the start prefix: its Forge share is the role prompt's body (`rolePromptChars` in `lib/engine/evals/provenance.ts`; learnings and addenda arrive through tool reads) plus the brief, at 3.5 characters per token and capped at the prefix, and the rest is the harness (Claude Code's system prompt, tools, MCP and skills, which transcripts don't show). What the last request's exact input adds beyond the prefix is shared out by largest remainder over the transcript's message text between them, in proportion to its characters: tool results by tool name (an image block counts as 5,000 characters; `mcp__<server>__*` tools as one `mcp:<server>` entry; a name outside `[A-Za-z0-9_.-]{1,64}`, or an unknown tool, as `other`; at most 12 named entries, the rest as `other`), assistant output and user turns, and every message before the span as `carried` (earlier runs of a resumed agent). So the parts are integers that sum to the request's exact input; a last request smaller than the prefix (a compacted context) is all prefix. Only the checked tool and server names are stored, never transcript text. A job from before job schema v19 keeps, per agent, `legacyRuns`, how many of its runs had already ended; the job detail rebuilds those from `agent-start`/`agent-end` events (`agentRuns` in `lib/engine/metrics/runs.ts`; billing only, no round, no composition) before the recorded ones, so no run counts twice. `roundAgents` in `lib/server/routes/transcripts.ts` serves every run as the job detail's `agents[].runs`, and a row's `tokens` is their sum; `/api/state` and the detail's `job` leave `runHistory` and `legacyRuns` out.

**Metered spend.** What sessions report about themselves can't bound them, so the supervisor in `forge dash` also measures every daemon session from claude's own cost report. Each `result` line carries `total_cost_usd` and `modelUsage` (per model: tokens and `costUSD`), cumulative per conversation, carried over a `--resume`, and including background subagents; `usage` on the same line is the last turn's main-loop calls only, so the meter doesn't use it and the session-usage record (below) does. At each `turn-ended` the supervisor appends one record to `.forge/runtime/meter/<scope>.jsonl` (`lib/engine/metrics/meter.ts`, through `lib/office/session/meter.ts`): this turn's delta against a baseline held per spawn (zero for a fresh session, the last recorded cumulative of the session id for a resume, a 0-delta rebase when the meter has no record of it, the whole cumulative when it fell below the baseline) and claude's raw cumulative. It is written through one `O_NOFOLLOW | O_NONBLOCK` descriptor, refused when the runtime or meter directory is not a real directory, and read tolerantly, dropping a line that breaks the record rules; a record that can't be written logs `meter: …` in the session log and never stops a job's session. A file over 64 MiB, a link, or a runtime or meter directory that is not a real one reads as no records with a named problem (`readMeterChecked`): a job's budget checks then fall back to its reported figure, and its session log says so once with a `meter: …` error; the inbox, the office with its gate runs, and the chats, whose daily cap can't then be checked, stop and refuse to start. No CLI command writes it. A job's enforced spend (`jobSpend` and `spentFrom` in `lib/engine/metrics/spend.ts`, read by `measureJob` in `lib/engine/metrics/budget.ts`) is the reported total without meter records, else `max(reported, metered + max(0, reported − covered))`, with covered clamped to reported: an under-report, a skipped `--import` or a forged covered run in `events.jsonl` can't take it below the meter or below the report. Every budget check reads it: `enforceBudget`, `forge job budget`, the budget hold, the repo budget's release check, the step's budget gate, the score sampler and the per-spawn dollar cap. In a daemon session, `forge job agent <id> end` refuses `--tokens`, `--tool-uses` and `--duration-ms`, needs an agent id (`--agent-id` or the recorded one) unless `--status lost`, always imports the transcript, records `unmeasured: true` and no usage when the transcript isn't found, and marks an end inside the job's own session `metered: true` (docs/CLI.md). `daemon.dailyUsd` caps the inbox, the office with forge dash's gate runs summed (each gate run's child gets `--max-budget-usd` set to what is left), and every chat of the project summed (`daemon.dailyUsd.chat`), per UTC day on the same meter; a chat meter that can't be read fails the chats' cap closed.

**Session usage.** The meter can't say what a session spent on its own calls, apart from the agents it ran: its figures add up over the whole session process and include every subagent. So at every `result` line the claude stream also reports the turn's own `usage` (`resultUsage` in `lib/integrations/claude/stream.ts`): its four token counts, from the session's main-loop calls only, with `num_turns`, `duration_ms` and the model of the latest `system`/`init` (a trailing context tag such as `[1m]` dropped). That holds for failed turns too. `modelUsage` and `total_cost_usd` are never used for this figure: summed per turn, they would count agent spend twice. A count that is not finite and ≥ 0 reads 0, an unusable `num_turns`, `duration_ms` or model reads null, and a result with no `usage` object records nothing. The supervisor (`recordTurnUsage` in `lib/office/session/meter.ts`) writes it under the session's own project root, so each project of a machine `forge dash` keeps its own: a job session's as a `session-usage` job event (`{session, turn, model, usage, numTurns, durationMs, ok}`, event v20; it survives archiving), and the inbox's and office's as one line in `.forge/runtime/session-usage/_inbox.jsonl` or `_office.jsonl` (the same fields plus `v`, `ts` and `scope`). Chats and gate runs record none. The file is written and read with the meter's safety (one `O_NOFOLLOW | O_NONBLOCK` descriptor, real directories only, a 64 MiB cap, bad lines dropped), and no path is built from any other scope. A write that fails logs `usage: …` in the session log and never stops the session. No CLI command writes either store, and readers take the CLI copy of events. `forge stats` prices each record with today's table as `cost.orchestrator`, by lane (`job` over the stats population, `inbox` and `office` since `--since`), with `coverage` (the population, the jobs with session usage, and those jobs' agent spend), and the spend ledger carries it as role `orchestrator` (**Repo budget** above). No budget, cap or gate ever reads it: a forged figure can only skew a stats row. `/api/state`'s `lastEvent`, the job detail's events and the stall figure leave `session-usage` events out, since they are accounting, not activity.
