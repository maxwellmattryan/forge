# Release security

`.github/workflows/release.yml` holds the only write token Forge's automation uses: it moves the `stable` branch, which every plugin install follows, tags the stable commit and publishes the Release. [RELEASES.md](../RELEASES.md#releasing) describes the flow. `test/invariants/release-workflow.test.ts` pins the file with allowlists that fail closed on any trigger, job, permission, action or expression it does not list, and runs the write job's steps against a stub `gh` with hostile inputs, so weakening it means editing that test in the same reviewed diff.

- **Who it defends against.** Each attacker, with the check that stops it:
  - a PR author, a fork included, who wants the token or the Release through the PR's title, body, branch name or commit messages: only a push to `develop` runs the workflow;
  - whoever can push a branch, a Forge agent with the maintainer's credentials included, who pushes a version bump to `develop` or a fork's `release/v<version>`: the PR lookup needs this repo's merged `release/v<version>` PR into `develop`, whose merge commit is the pushed sha (but not one who pushes a workflow of their own that moves `stable` through the ruleset's bypass: see Residual risk);
  - repo text (the `package.json` version, the tree sha, dist file names) that would reach a shell, argv or `GITHUB_OUTPUT`: every value is checked by pattern before use, nothing reaches `run` through `${{ }}`, no step reads `github.event`, jq builds every request body, and no value can start with `-`;
  - another job in the run, such as a compromised dependency in `verify`, that swaps the `stable-dist` artifact after `build` uploaded it: the write job's tree must equal the one `build` checked;
  - a race or a replayed run that would move `stable` backwards or sideways: the write job re-reads `stable` before it moves it, moves it with `force: false`, stops when the tag exists, and never force-pushes;
  - a symlink or odd file in the artifact: refused before any blob is made;
  - a retagged or compromised action: every action is pinned to a full SHA;
  - a later edit, by a person or an agent, that quietly weakens the workflow: the invariant tests pin triggers, jobs, permissions, the write job's contents and where the token reaches, each with hostile mutation rows.
- **A release is a reviewed PR.** `npm run release` never pushes `develop` or `stable`: it opens the release PR from `release/v<version>` into `develop`, an ordinary PR with its own CI that a human merges. A ruleset on `stable` keeps people off it, with GitHub Actions on its bypass list so the workflow's `GITHUB_TOKEN` can move it ([RELEASES.md](../RELEASES.md#releasing) › Repository settings); that bypass covers every workflow run, not only `release.yml` (see Residual risk). Nothing ever merges `stable` into `develop`.
- **Never on PR events.** It runs on pushes to `develop` only: no `pull_request`, `pull_request_target`, `workflow_run` or `workflow_dispatch`, and no other branch, `main` and `stable` included.
- **Write scope in one job, after verify and build.** The workflow's token is `contents: read`. Only the `release` job asks for more, exactly `contents: write` and `actions: read` (to download its own run's artifacts), and it needs `detect`, `verify` (all of `ci.yml`, called with no inputs, no secrets and the read-only token) and `build`.
- **Nothing but gh beside the write token.** The `release` job has no checkout, no `uses:` and runs no repo code: its steps call only the runner's `gh`, `jq`, `base64`, `find` and shell builtins, never `node`, `npm`, `npx` or `git`, with `github.token` as `GH_TOKEN` in each step's env and nowhere else in the workflow. Steps hand values to later steps only through files in `$RUNNER_TEMP/release/`, and each step checks every value it reads by pattern again (`X.Y.Z` for the version, 40 hex for each sha). The read-only `build` job runs checkout, setup-node, `npm ci`, the dashboard build, `scripts/stable-tree.ts` and `scripts/release-plan.ts notes`, and builds the archive; checkouts keep no credentials.
- **Only this run's files.** The `release` job downloads `release-files` and `stable-dist` with `gh run download "$GITHUB_RUN_ID" --repo "$GITHUB_REPOSITORY"`, so an artifact another run uploaded never reaches it. `release-files` must hold only the notes and the archive; `stable-dist` only plain files and directories (`find ! -type f ! -type d` prints nothing) whose names are `index.html`, `manifest.json`, `build-stamp.json` or `assets/<name>.js|css|woff2`, checked before any blob is created.
- **Only the merge of this repo's release PR.** Before anything is written, it looks up the pushed commit's PRs and needs exactly one merged PR into `develop` from `release/v<version>` in this repository whose merge commit is the pushed sha. The jq filter reads only `env.VERSION`, `env.GITHUB_SHA` and `env.GITHUB_REPOSITORY` inside a single-quoted program, and the number it yields must be digits before it is used. That PR must also hold exactly one commit (`gh api pulls/<number>` gives `commits`, compared as the string `1`): the release commit `npm run release` made, which is what makes the first-parent comparison in "Only the bump" hold for every merge method. A fork's PR with the same branch name fails the head repository check, and a bumped push to `develop` with no release PR publishes nothing.
- **Only the bump.** The PR lookup checks the head branch's name, not what it carries, so the read-only `build` job refuses the push first, before `npm ci` installs from a lockfile it may have edited. Against the pushed commit's first parent (a merge commit's base side, or the commit a squash or a rebase of one commit sits on), only `package.json`, `package-lock.json`, `.claude-plugin/plugin.json` and CHANGELOG.md may differ; the version files only in the lines that name the old or the new version (so another `resolved` URL, a dependency's version, a hook in `plugin.json` or a script refuses); CHANGELOG.md only by lines added. A file name is printed shell-quoted, so a name cannot add a workflow command. The check is plain `git`, `jq`, `sed` and `cmp` in the workflow file, not a repo script, and it runs before setup-node reads `.nvmrc`, so neither a script nor a Node version edited in the same push can switch it off; editing the workflow file can, which is a protected-path change that a person reviews. It is weaker than the check `npm run release` makes before it adopts a branch (`rewriteVersion` replayed byte for byte). It also depends on the PR holding one commit. A rebase merge of several commits leaves the pushed commit's first parent at another commit of the PR, so the commits before the last would skip the comparison (an earlier one adds the change and sets the version back, the last bumps it again, and `detect` sees a bump). The `release` job's PR lookup therefore refuses any release PR that does not hold exactly one commit, and with that the comparison is against `develop`'s previous head for a merge commit, a squash and a rebase alike.
- **The tree cross-check.** `build` writes the stable tree with git plumbing in a temporary index (the pushed commit's tree, minus `.github/workflows/`, plus each dist file hashed with `--no-filters` at 100644), runs the release check (`--dist present`) on a checkout of it, and outputs its sha. The write job rebuilds the same tree through the GitHub git-data API, the pushed commit's tree as `base_tree` with a blob per dist file and a deletion per workflow file, and refuses before it commits unless the API returns that exact sha.
- **`stable` only moves forward.** The write job reads the `stable` tip first, commits with parents `[that tip, pushed sha]`, reads `stable` again and refuses if it moved, then moves it with `PATCH … force: false`, which GitHub accepts only as a fast-forward. It refuses when `v<version>` already exists, so a replayed run never retags. A re-run after a failed tag step reuses a `stable` tip whose second parent is the pushed sha and whose tree is the build's, and tags it.
- **`stable` holds no workflows.** `GITHUB_TOKEN` can't get the `workflows` permission, and GitHub refuses a ref update by it whose change touches a workflow file. The stable tree drops `.github/workflows/` and the first `stable` commit was made without it, so no `stable` update ever touches one. Nothing that reads `stable` needs them, and a push by `GITHUB_TOKEN` starts no workflow run anyway.
- **Repo and PR text are validated or passed as a file.** `scripts/release-plan.ts detect` exits before writing anything unless the version is `X.Y.Z`, so a version with a newline can't add outputs, and `scripts/stable-tree.ts` prints exactly `tree=<40 hex>` or nothing. The notes are the CHANGELOG section of the merged commit, frozen in the release commit and reviewed in the PR diff; the PR body is a copy for reviewers that no workflow reads. They reach `gh` only as `--notes-file`. The commit message, tag message and Release title are fixed text around the checked version.
- **Pinned actions.** Only `actions/checkout`, `actions/setup-node` and `actions/upload-artifact`, each pinned to the same full SHA as `ci.yml`, and none in the `release` job.
- **A pushed release branch is not trusted.** `npm run release` runs with the maintainer's credentials, so it adopts a `release/v<version>` branch only when its tip is a release commit: one parent, a commit on `origin/develop`'s first-parent chain (not one from a branch merged into it), changing only the version files and CHANGELOG.md, each the parent's bytes with exactly the bump (`rewriteVersion`, the function that makes it, replayed; one `## <version>` section inserted into CHANGELOG.md). A file list alone would let a changed `resolved` URL in `package-lock.json` (`npm ci` in `build` would build with it, and the build stamp hashes only names and versions), a hook added to `plugin.json` or an edit to `marketplace.json` ride in with the bump. The release PR is reviewed and CI-checked like any PR into `develop`, and `release.yml` publishes exactly the commit the merge pushed, so there is no head to re-derive after the merge; instead `build` checks the push is only the bump (above), a weaker form of the same rule. `--phase wait-tag` accepts a tag only when it peels to a commit on `origin/stable` whose second parent is the PR's merge commit.
- **`forge release run` drives the same script.** Once Forge's `.forge/config.yml` declares its release as `mechanism: script` (a maintainer's edit), `forge release plan|run` runs `scripts/release.ts`'s phases (`--phase start|wait-tag`, `--check merged`) as release steps, and every adoption and tag check above stays in the script, reached through the same functions `npm run release` calls. The engine only spawns `node scripts/release.ts …`: it runs no git or gh against release branches, PRs or tags, and its `start` step has no skip-check, so a resume always re-checks the branch tip before the merge. Phase mode answers only the push question, which the engine already asked at its publish step. The version comes back from `release.json` but must be `X.Y.Z`, sits in every step's argv (so in the plan hash that `state.json` and a Foreman approval bind to, and in every publish prompt), and `start` refuses one that is not the patch, minor or major release after develop's. The notes path is always Forge's own, never the file's, and the draft runs under the command environment, so the script never sees credentials while planning.
- **Residual risk: the `stable` ruleset trusts GitHub Actions, not `release.yml`.** The only actor on its bypass list is the `github-actions` app, which is every workflow run in the repository on every ref. Anyone who can push a branch with a workflow file, or open a same-repo PR (a `pull_request` run uses the PR's own workflow files), can ask for `contents: write` in a job of their own, and that job can move `stable`, with `force: true` and deletions too, since a bypass actor skips the rule that blocks them. That reaches every install on its next `forge update`, and skips the PR lookup, the tree cross-check, `force: false` and review, because those are steps inside `release.yml`. The default "Read repository contents" only sets a default that a workflow's `permissions:` key can raise. A Forge agent with the maintainer's credentials, over SSH or with a `workflow`-scoped token, is such an attacker. The previous flow had a similar hole (tags were unprotected, so a branch workflow could retag), but installs pinned a tag named in `develop`'s reviewed marketplace.json, not a moving branch the bypass list grants. So `stable` is only as protected as write access to the repository, and the claims "only `release.yml` moves it" and "every commit after the first is a release's stable commit" describe what the workflow does, not what the ruleset enforces. **Follow-up** (outside this flow, a human decision): make a GitHub App token, or a deploy key, held as a secret of a `release` environment that only `develop` may deploy to, the ruleset's only bypass actor and the credential of the `release` job's writes; then drop GitHub Actions from the bypass list. A `develop` ruleset (PRs and CI required) narrows who can land a workflow change but does not close this.
- **Residual risk: a compromised `build` controls both the dist and the tree.** A compromised pinned action or dependency inside `build` (`npm ci`, the Vite build) can upload any `stable-dist` and print the matching tree sha, and the write job would commit it onto `stable`: the cross-check catches another job swapping the artifact, not `build` lying about both. That is the same exposure the dashboard build of the previous release flow had. `build` holds only the read-only token and cannot lift the write token, which only the `release` job's steps ever see, and the archive is still `git archive` of the pushed commit, so it can be checked against `v<version>^2`. A second, independent build to compare against would close it; a GitHub App token for the write job (one that may touch workflow files) is the follow-up if GitHub refuses `GITHUB_TOKEN`'s `stable` updates after all.
- **The archive proves its commit.** The build refuses an archive whose stamped `COMMIT` is not the pushed sha. There is no `.sha256` asset: published by the same job in the same Release, it proved nothing HTTPS doesn't. `forge version --json` is self-reported; the annotated tag, and comparing the archive with `git archive` of `v<version>^2`, are the audit anchors.

`forge doctor`'s release row (`latestReleaseCheck` in `lib/engine/ops/version.ts`) runs `gh release view` with a repo taken from `known_marketplaces.json` or the install's `plugin.json`, both writable by anything that can write `~/.claude` or the checkout. The repo must match `^[A-Za-z0-9][A-Za-z0-9-]*/[A-Za-z0-9._][A-Za-z0-9._-]*$` (no leading `-`) before it becomes argv, with no shell. The call has a 5 s timeout, the returned tag must be `v?X.Y.Z` before it is shown, and any failure leaves the row out.
