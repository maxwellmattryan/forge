# Release security

`.github/workflows/release.yml` holds the only write token Forge's automation uses: it tags commits and publishes Releases. [RELEASES.md](../RELEASES.md#releasing) describes the flow. `test/invariants/release-workflow.test.ts` pins the file with allowlists that fail closed on any trigger, key, permission, action or expression it does not list, so weakening it means editing that test in the same reviewed diff.

- **Who it defends against.** A PR author (a fork included) who wants the token or the Release, a retagged or compromised action, repo text (the `package.json` version, CHANGELOG) that would reach a shell, `GITHUB_OUTPUT` or argv, and a later edit, by a person or an agent, that quietly weakens the workflow.
- **Never on PR events.** It runs on pushes to `main` only: no `pull_request`, `pull_request_target`, `workflow_run` or `workflow_dispatch`.
- **Write scope in one job, after verify.** The workflow's token is `contents: read`. Only the `release` job asks for `contents: write`, and it needs `detect` and `verify` (all of `ci.yml`, called with no inputs, no secrets and the read-only token).
- **The token reaches two steps.** `github.token` appears only as `GH_TOKEN` on the tag and publish steps, which call `gh`. Checkout keeps no credentials, so the scripts and `git archive` never hold a token.
- **Repo text is validated or passed as a file.** `scripts/release-plan.ts detect` exits before writing anything unless the version is `X.Y.Z`, so a version with a newline can't add outputs. The version reaches `run` only through `env`, never `${{ }}`. The CHANGELOG section reaches `gh` only as `--notes-file`. The tag message and Release title are fixed text.
- **Pinned actions.** Only `actions/checkout` and `actions/setup-node`, each pinned to the same full SHA as `ci.yml`.
- **Residual risk: code runs beside the write token.** The `release` job still runs `actions/setup-node` and `node scripts/release-plan.ts notes` while it holds `contents: write`. On a hosted runner, any step can read the runner's memory and lift the job token (the 2025 tj-actions compromise did this). Both are pinned or come from merged `main`, so this is accepted rather than closed: a change to `scripts/release-plan.ts` or the pinned actions is a change to what runs with the token, and gets reviewed as one.
- **The archive proves its commit.** The release job refuses an archive whose stamped `COMMIT` is not the pushed sha, and publishes its `.sha256` beside it. `forge version --json` is self-reported; the annotated tag and the checksum are the audit anchors.

`forge doctor`'s release row (`latestReleaseCheck` in `lib/engine/ops/version.ts`) runs `gh release view` with a repo taken from `known_marketplaces.json` or the install's `plugin.json`, both writable by anything that can write `~/.claude` or the checkout. The repo must match `^[A-Za-z0-9][A-Za-z0-9-]*/[A-Za-z0-9._][A-Za-z0-9._-]*$` (no leading `-`) before it becomes argv, with no shell. The call has a 5 s timeout, the returned tag must be `v?X.Y.Z` before it is shown, and any failure leaves the row out.
