# Release security

`.github/workflows/release.yml` holds the only write token Forge's automation uses: it tags commits and publishes Releases. `.github/workflows/main-update.yml` builds the dashboard for the main update with a read-only token and writes nothing. [RELEASES.md](../RELEASES.md#releasing) describes the flow. `test/invariants/release-workflow.test.ts` pins the file with allowlists that fail closed on any trigger, job, permission, action or expression it does not list, so weakening it means editing that test in the same reviewed diff.

- **Who it defends against.** A PR author (a fork included) who wants the token or the Release, through the PR's title, body, branch name or commit messages; whoever can push a branch, a Forge agent with the maintainer's credentials included; a retagged or compromised action; repo text (the `package.json` version, CHANGELOG) that would reach a shell, `GITHUB_OUTPUT` or argv; and a later edit, by a person or an agent, that quietly weakens the workflow.
- **A release is a reviewed PR.** `npm run release` never pushes `main`: it opens the release PR from `release/v<version>`, and a human merges it with a merge commit. A ruleset on `main` that requires a PR keeps everyone else from pushing it (a repository setting, [RELEASES.md](../RELEASES.md#releasing)).
- **Never on PR events.** It runs on pushes to `main` only: no `pull_request`, `pull_request_target`, `workflow_run` or `workflow_dispatch`.
- **Write scope in one job, after verify and build.** The workflow's token is `contents: read`. Only the `release` job asks for more, exactly `contents: write` and `actions: read` (to download its own run's artifact), and it needs `detect`, `verify` (all of `ci.yml`, called with no inputs, no secrets and the read-only token) and `build`.
- **Nothing but gh beside the write token.** The `release` job has no checkout, no `uses:` and no node, npm or npx: each step is a `run:` step that calls the runner's `gh`, with `github.token` as `GH_TOKEN` in that step's env and nowhere else in the workflow. The read-only `build` job runs checkout, setup-node and `scripts/release-plan.ts notes` and builds the archive; checkouts keep no credentials.
- **Only this run's files.** The `release` job downloads `release-files` with `gh run download "$GITHUB_RUN_ID" --repo "$GITHUB_REPOSITORY"`, so an artifact another run uploaded (a pushed `release/v*` branch's, say) never reaches it.
- **Only the merge of this repo's release PR.** Before anything is published, it looks up the pushed commit's PRs and needs exactly one merged PR into `main` from `release/v<version>` in this repository whose merge commit is the pushed sha. The jq filter reads only `env.VERSION`, `env.GITHUB_SHA` and `env.GITHUB_REPOSITORY` inside a single-quoted program, and the number it yields must be digits before it is used. A fork's PR with the same branch name fails the head repository check, and a bumped push to `main` with no release PR (a ruleset bypass, say) publishes nothing.
- **Repo and PR text are validated or passed as a file.** `scripts/release-plan.ts detect` exits before writing anything unless the version is `X.Y.Z`, so a version with a newline can't add outputs and no option reaches `gh` through it. The version reaches `run` only through `env`, never `${{ }}`, and no step reads `github.event` at all. The notes are the CHANGELOG section of the merged commit, frozen in the release commit and reviewed in the PR diff; the PR body is a copy for reviewers that no workflow reads. They reach `gh` only as `--notes-file`. The tag message and Release title are fixed text.
- **Pinned actions.** Only `actions/checkout`, `actions/setup-node` and `actions/upload-artifact`, each pinned to the same full SHA as `ci.yml` or `main-update.yml`, and none in the `release` job.
- **A pushed release branch is not trusted.** `npm run release` runs with the maintainer's credentials, so it adopts a `release/v<version>` branch only when it can re-derive it. The release commit must have one parent, a commit on `origin/develop`'s first-parent chain (not one from a branch merged into it), and change only the version files, marketplace.json and CHANGELOG.md, and each of them must be the parent's bytes with exactly the bump: the version lines and marketplace's ref rewritten (`rewriteVersion`, the function that makes the bump), one `## <version>` section inserted into CHANGELOG.md. An exact bump of an older `develop` commit passes, so before it pushes anything or shows the PR, `npm run release` prints how many commits `origin/develop` has that the release lacks and asks: such a release would quietly leave them out, a security fix among them. A file list alone would let a changed `resolved` URL in `package-lock.json` (`npm ci` in `main-update.yml` would build with it, and the build stamp hashes only names and versions) or a hook added to `plugin.json` ride in with the bump. A main update on top of it must have exactly the tree that `scripts/main-update.ts` builds from that commit and the `dashboard-dist` artifact of `main-update.yml`'s own push run on it, checked on every resume, before the PR is opened or shown. A commit someone else pushed to the branch, shaped like the main update but carrying other `dashboard/dist/` bytes or files, is refused rather than opened as the release PR. The human who merges the PR still reads its diff, but `dashboard/dist/` is minified build output nobody can review by eye, so this check is what ties it to the sources. The check is repeated before anything lands on `develop`: a push to the branch after the last resume is merged and published, and `release.yml` reads no tree, so `npm run release` derives the merged head again (and requires the merge commit to have its tree) before it moves `develop`'s marketplace.json, which every install reads, to the tag. A head it cannot derive lands nothing and says to delete the Release and tag; installs keep following the previous tag. `npm run release` prints the head it checked and the PR body names it, so the human merges only that sha. The optional `release/v*` ruleset ([RELEASES.md](../RELEASES.md#releasing) › Repository settings), which lets only maintainers create, update or force-push those branches, closes that window before the merge instead of after it.
- **Residual risk: the write job publishes what the run's read jobs built.** A compromised pinned action or dependency in `detect`, `verify` (all of `ci.yml`: `npm ci`, the Claude Code CLI install, the full test suite) or `build` could swap the `release-files` artifact before `release` downloads it, because any job in a run can upload or replace that run's artifacts. Those jobs hold only the read-only token and cannot lift the write token, which only the `release` job's `gh` steps ever see. The annotated tag is made by the API on the merge commit, not from the artifact, so `git archive` of the tag is the check: an archive that differs from it was swapped.
- **The archive proves its commit.** The build refuses an archive whose stamped `COMMIT` is not the pushed sha. There is no `.sha256` asset: published by the same job in the same Release, it proved nothing HTTPS doesn't. `forge version --json` is self-reported; the annotated tag, and comparing the archive with `git archive` of the tag, are the audit anchors.

`forge doctor`'s release row (`latestReleaseCheck` in `lib/engine/ops/version.ts`) runs `gh release view` with a repo taken from `known_marketplaces.json` or the install's `plugin.json`, both writable by anything that can write `~/.claude` or the checkout. The repo must match `^[A-Za-z0-9][A-Za-z0-9-]*/[A-Za-z0-9._][A-Za-z0-9._-]*$` (no leading `-`) before it becomes argv, with no shell. The call has a 5 s timeout, the returned tag must be `v?X.Y.Z` before it is shown, and any failure leaves the row out.
