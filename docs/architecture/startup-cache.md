# Start-up cache

Agents and the orchestrator call `forge` hundreds of times a job, so start-up time is paid on every call. Before it imports `lib/cli/main.ts`, `bin/forge` turns on two caches in one directory:

- **V8's code cache** (`module.enableCompileCache`), on every Node. From Node 24 it covers type-stripped modules too.
- **Stripped modules**, on Node 22 and 23 only. Their code cache skips type-stripped modules, so every start loads the stripper and strips all of `lib/` again. A `module.registerHooks` load hook keeps each stripped `.ts` file of the plugin as `strip/<node version>/<sha256 of the source>.js`. Content keys mean an edited file or an updated plugin is never served stale, and identical files of different installs share an entry. A miss strips with `module.stripTypeScriptTypes` and silences its one-time ExperimentalWarning, which agents would read as a fault. The entry is written aside and renamed, so concurrent starts never read half a module. A file the stripper rejects goes to Node's own loader, which reports the error as usual. Beside it, a resolve hook resolves each layer alias (`#core/…`) a `lib/` file imports once per process, because Node 22 walks up to `package.json` on every one.

`forge job list`, median of 30 warm starts on an M-series Mac:

| Node | Before | After |
|---|---|---|
| 22.18 | 144 ms | 37 ms |
| 22.23 | 98 ms | 39 ms |
| 26.3 | 148 ms | 70 ms |

A miss costs about 15 ms over an uncached start, once per changed file. On Node 22 the modules `forge job list` loads take about 1.3 MB of cache (0.9 MB stripped, 0.4 MB V8), per Node version.

The cache holds code the CLI runs, so it must be no easier to write than the code it caches. It is `.cache/` in the plugin root (or `$FORGE_CACHE_DIR`), so whoever can write it could already rewrite `lib/`. It is not in a temp or other shared dir, because Claude Code's sandbox lets Bash write the temp dir: a sandboxed agent could plant a module there that a later unsandboxed `forge` would run. `bin/forge` creates the dir as `0700` with a `.gitignore` of `*`, so a checkout's `git status` never shows it. It uses the dir only when it is a real directory (not a symlink), owned by the current user, not group- or world-writable, in a parent owned by that user or root that is either not group- or world-writable or sticky. Otherwise, and whenever a read or write fails, the CLI runs uncached and prints nothing. A read-only install, or a sandbox that can't write the plugin, still reads entries an earlier unsandboxed start wrote and skips writing misses. Each plugin version starts with an empty cache and is removed along with it. `NODE_DISABLE_COMPILE_CACHE=1` turns both caches off. A `NODE_COMPILE_CACHE` already set wins for the V8 cache. Deleting the directory is always safe.

## Worktree seeds

The same directory holds [worktree seeds](../CONFIG.md#worktree-seed) under `seeds/<repoId>/` (`lib/engine/workspace/seed.ts`). A seed is a copy of a fresh worktree's `node_modules` (or whatever `worktrees.seed.paths` names), which every later job worktree clones, and it holds code later runs execute: a module planted in `node_modules/.cache/forge/strip-cache/` under a real file's content key would run in another job's tests or in an unsandboxed `forge`. The attacker here is a job's agents, possibly steered by tracker or PR text. They can write their own worktree, any worktree under `worktrees.root`, the job dir, the temp dir and, through a sandboxed Bash, the main checkout's working tree. The design closes each way in. The seed sits outside all of those, beside the plugin's code, and Forge uses it only after `bin/forge`'s ownership checks, applied again to `seeds/` and `seeds/<repoId>/` (real directories, yours, not group- or world-writable, created `0700`). It is written only by `forge worktree create`, from a worktree that call just created as a new branch at the tip of `git.base` from the main checkout's config (never the job's own `base`), after the remote-tracking refs are fetched, and only when none of the seed paths was already there before setup and, after setup and warm, the worktree's HEAD is still that commit with no tracked file changed. So its content is the merged base branch plus what the main checkout's configured setup and warm commands produce, the same trust setup has today. A job's own branch, a stacked or `--from` branch, a worktree whose paths came from `worktrees.copy`, and an eval clone never refresh it. Clones are copy-on-write or plain copies, never hardlinks or symlinks, so a write in a worktree never reaches the seed. A staged symlink that is absolute, resolves outside the staging dir, or has a `..` after another segment refuses the refresh, so no seed shares a writable path with a worktree. The last rule is what makes the second one sound: the kernel follows a link before the `..` after it, so `x -> y/../../outside` beside `y -> ..` looks like a path inside the staging dir and physically leaves it, while a target whose `..` all lead climbs only the real directories the walk has seen. The key covers the key files, the setup commands, the seed paths, the platform, the arch and the Node ABI. A seed becomes visible only by renaming a staging dir whose `seed.json` was written last, and `seed.setup` runs before a clone is trusted: a failing check deletes that seed. Seed paths are validated as relative paths with no leading `-`, and `cp` gets absolute paths after `--` as argv, with no shell. Anyone who can rewrite the main checkout's `.git/config` or refs could already plant hooks git runs.

Three risks remain. An agent of another live job can write any worktree, so it could write into the fresh worktree during that one create's setup and warm, and the seed would carry that write to later jobs until the key changes. The HEAD and tracked-file checks narrow that to writes in ignored paths, such as `node_modules/.cache`. `FORGE_CACHE_DIR` in `forge`'s environment redirects the seed, but whoever sets that environment already controls `NODE_OPTIONS`. A sandboxed `forge` that can't write the plugin dir still reads seeds and skips refreshes (`failed` or `cache-unusable`).
