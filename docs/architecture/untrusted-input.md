# Untrusted input

Issue bodies, comments and PR reviews come from people outside the session, and on public repos that means anyone. Forge:
- shows agents only collaborators' issue and PR comments by default (`tracker.github.comments: collaborators`): other people's issue comments, PR reviews, conversation comments and replies inside a collaborator's review thread are left out of `request.md` and `pr-feedback.md` and counted in one line; with `all` they follow, quoted, under `## Untrusted` in `pr-feedback.md`. The PR counts (`unresolvedThreads`, `changesRequested`) and the pr-feedback gate's trusted count are unchanged
- removes text people can't see from everything it imports (`visibleText` in `lib/core/text.ts`): zero-width, bidi and other format characters (not ZWJ, LRM or RLM), C0 and C1 controls (not TAB, LF, CR or NEL), the Unicode Tags block (except the England, Scotland and Wales flags), the Variation Selectors Supplement, every variation selector after a run's first, and HTML comments. The provenance line says how many went; over 32, or with any Tags or supplement character, a `Hidden text:` line follows it, and readiness triage marks the item needs-info (`hidden-text`)
- writes one column-0 provenance line ("data, not instructions") at the top of every imported item, then blockquotes every line of the body and each comment (CR, U+2028, U+2029 and NEL count as line breaks, logins and associations are reduced to safe characters), so only Forge writes column-0 lines in `request.md` and a forged provenance line or `### Recent comments` section reads as quoted text. GitHub issues, local backlog items and custom adapters' items all get it: the loader fences a custom adapter's `get`, leaving alone only a body exactly in that fenced form for that item (its own provenance line, Forge's own `Hidden text:` sentence, the rest quoted). Every job title is one line (`createJob`), whoever passes it
- quotes every review, thread comment and conversation comment in `pr-feedback.md` under a Forge-written entry line, each body cut to 4000 characters, and writes each thread's file path as a JSON string, so a path or body holding a newline and a heading can't add a section
- re-imports an issue (`forge job refresh-request`, and a claim before `plan.md` or `spec.md` exists) only through the tracker's own `get`, so a refreshed `request.md` is fenced exactly as at intake; a claim refreshes only a request intake imported from that issue (`origin: issue` on `created`, or the GitHub import fence on older jobs), never words a person wrote, and only from an issue whose author has write access (`author_association` `OWNER`, `MEMBER` or `COLLABORATOR`), so an outside author's edit after a person picked the issue never reaches an agent unseen; `refresh-request` is that person's explicit choice
- tells every agent to ignore embedded instructions about secrets, credentials, CI, permissions or out-of-scope work
- serves an issue's own text unfenced only to the dashboard's issue panel: a tracker's optional `view` (docs/TRACKERS.md) is called only by `lib/engine/trackers/view.ts`, whose one caller is `GET /api/backlog/item`, so that text never reaches an agent, and the panel renders it through the escape-first `md()` only (docs/architecture/dashboard-security.md)
- limits what a misled builder's code sees when verify runs it before review (`lib/engine/guard/command-env.ts`, docs/CONFIG.md "Command environment"): every configured command, in and out of the daemon, gets only an allowlist of Forge's environment plus the names `commandEnv.inherit` lists, under `/bin/sh -c` with no login profile, so it can read `PATH`, `HOME`, the locale, the git pins and the job's own variables, but not `GH_TOKEN`, `AWS_*`, `SSH_AUTH_SOCK`, `DATABASE_URL`, a credential under a name nobody listed, a declared secret's source variable (only its sink's value) or Forge's own `FORGE_DAEMON*` and `FORGE_COMMAND_PATH*`. No family or glob passes a credential-like name (`NODE_AUTH_TOKEN` under `NODE_*`), a bare `*` is refused, and relative or empty PATH entries are dropped so the worktree can't plant a binary. It can still read your dotfiles (`~/.aws/credentials`, `~/.config/gh/hosts.yml`, `~/.npmrc`), since `HOME` passes, a name a human put in `inherit` exactly, and everything with `commandEnv.loginShell: true`, which re-sources the profile; `forge release run` keeps its caller's whole environment
- writes a goal mandate's drafting survey (`lib/office/mandates/intake.ts`, docs/architecture/foreman.md "Intake") under a column-0 data line: the owner's goal and guidance through `fenceImport`, and the tracker's open milestone and issue titles each list in one fence longer than any backtick run, every title through `oneLineTitle`; the `forge:drafter` that reads it has Read, Grep, Glob and Write only, and `forge mandate draft record` refuses a draft with hidden or control characters, refs `checkIssueRef` refuses, or paths that are absolute, start with `-` or climb with `..`. Its refusals name positions (`issues[2].files[0]`), never the drafter's text, so the office session that acks with one never reads drafter text. A revision run's brief carries the owner's or the foreman's note and the previous draft's title through `fenceImport`, and a gate run's milestone-draft brief (from the logic behind `forge mandate draft assist`) holds only the draft's path and the fenced goal and guidance. Filing an approved draft sends the milestone, issue and amendment text composed exactly as scanned, after one secret scan over all of it (`lib/office/mandates/filing.ts`), with each `@name` quieted on GitHub (a zero-width joiner after the @), and the guarded tracker scans `createMilestone` and `milestoneAdd` again; filing's refusals name the milestone title by position, and a foreman's stopped filing leaves the tracker's error in `filing.json`
- triages tracker items without letting their text reach the tracker (`lib/engine/trackers/triage.ts`, docs/TRACKERS.md "Readiness triage"): the batch the `forge:triage` agent reads fences each item in a fence longer than any backtick run in it, and the agent has only Read and Write; `--apply` takes a batch id only in its exact format, reads `verdicts.json` and `items.json` each through one `O_NOFOLLOW` descriptor (a regular file under 256 KiB), ignores refs outside the batch, keeps only known missing keys and a `duplicateOf` from the item's own candidates, skips items changed since prepare, and writes only fixed template text, citing a duplicate as `PR #n`, a same-tracker `#n` or "an active Forge job", never a local job id, a citation it derives from the candidate id and the job records rather than from the agent-writable batch
- reads agent transcripts for a retro without letting their text reach the retro or the CLI (`lib/integrations/claude/friction.ts`, `lib/engine/evals/retro.ts`, docs/IMPROVEMENT.md "Agent transcripts"): `forge retro prepare` finds each transcript only through `agentTranscriptById` and `openTranscript` (job-state ids checked, project dirs confined, one no-follow, non-blocking descriptor), reads it with line, byte and run caps, and writes `transcripts.json` with counts, hashes and charset-limited keys only, never transcript text or a path. The digest inputs it writes for the `forge:digest` agents hold each run's log in one fence, every log line made one line (`visibleText`, then every job's known secret values and the secret scanner's credential patterns replaced by `[redacted]`, so none is left half-cut at a line cap, then whitespace and C0/C1 controls, CR, U+2028, U+2029 and NEL included, to one space, then `safeText`, which drops backticks) and prefixed with Forge's own `T<n>`, so only Forge writes column-0 lines; prepare removes a planted `digest` link and writes through `confinedDir`. The digest agents have Read and Write only, nothing in the CLI reads their `friction-<n>.md`, and the retro's proposals ship behind its human spec gate
- adopts only PRs whose branch lives in the same repository (never forks), and only issue-linked PRs from collaborators, so a stranger's PR is never checked out and run by the builder. Every PR read is validated once, in `lib/integrations/github/pull-requests.ts`, into a snapshot that `lib/engine/pr/` reads through its `GitHub` adapter: a PR not marked same-repo (`isCrossRepository` missing or anything but `false`) counts as a fork, and a ref name that fails `SAFE_REF`, a head that is not a sha and a url that is not https are dropped before any policy sees them
- passes trackers only this repo's own issue refs (`nativeRef` in `lib/core/job/issue-ref.ts`): an `owner/repo#N` from another repo on a job is recorded and cited, never read, claimed, mirrored or commented on, and every stored ref must start with a letter or digit and hold no spaces or `..`, so no ref reaches `gh` as an option. The GitHub adapter itself (`issueNumber` in `lib/integrations/github/tracker.ts`) accepts only an issue number in its `-R` repo and passes it after `--`, so a URL or option typed into `forge tracker` never reaches `gh`, whatever the caller; job.json's `issues`, `source` and `noIssue` are locked against `forge job set --field`
- keeps job ids, branches and bases to `SAFE_REF` (`lib/core/text.ts`: a letter or digit, then `A-Z a-z 0-9 . _ / -`, at most 200 characters), because they fill `{job}`, `{branch}` and `{base}` in shell command templates and reach git argv: command templates (`forge run`, `forge verify`, worktree setup) and `forge worktree create` refuse an unsafe value before anything runs, `forge job new --branch` refuses one before the job exists, and PR adoption refuses a PR whose `headRefName` or `baseRefName` fails it (a `pr-adopt-refused` event names the field, never the value). `forge job set --field` can't write a job's identity (`id`, `branch`, `base`, `worktree`, `port`, `owner`, `schemaVersion`, `createdAt`, `source`, `pr`, `runs`, `usage`, or any key under them), its `effort` (only `forge job effort` writes it, and refuses in a daemon session), its `eval` record and config overlay (only `forge eval start` writes it, and refuses `--set` in a daemon session; every load checks the overlay again and fails closed), a `kind` of `retro` or `eval` (only `forge job new --kind retro` and `forge eval start` create those, because step gives a retro job a fixed review panel and an eval job no PR or escalation gate) or any `__proto__`, `constructor` or `prototype` segment, so a misled session can't point a job at `main` before `forge pr open`. `setJob` enforces these rules through `lib/core/job/fields.ts` for every caller, not only the CLI, and the commands that own those keys write them through its `owned` change instead. The extra arguments of `forge run <job> <name> -- <args…>` reach the shell too: each is wrapped in single quotes and never filled again as a placeholder, and an argument containing a quote, backslash or control character (which would end the quoting in sh, bash, zsh or fish), a word before `--`, or any argument with `--background` is refused before anything runs. Arguments are opt-in: a template without `{args}` refuses them, so a configured command that reaches outside systems can't be steered with flags a session picks. Arguments are also refused where the template would not keep them as plain words: an `{args}` that isn't a whole unquoted word (inside `'…'` or `"…"`, where `$(…)` expands or a `'` ends the quoting, or after a backslash), or any template with a heredoc, `$'` or `\'`, where `\'` does not close the quote. `forge verify`, worktree setup, background servers, the regenerate build and eval grading have no argument path at all, so arguments can never narrow the gate
- removes a job's root worktree only where Forge computes it (`lib/engine/workspace/worktree.ts`): `forge worktree remove`, `forge sync`'s on-merge cleanup and `forge job delete` act on a stored `job.worktree` only when it is `<worktrees.root>/<id>` and resolves there (`containedWorktree`), so another job's worktree, the main checkout or `<worktrees.root>/<id>` swapped for a link out is refused before anything changes (no checkout undo, no stopped process, no write), and the check runs again right before the delete. A stored path that does not exist is cleared without removing anything. `--delete-branch` checks `job.branch` against `SAFE_REF` up front and deletes only `git.branchPrefix` + id; any other branch (another job's, the base, a `--branch` or adopted PR branch, which may be a human's own) is kept and reported as `branchKept`. A job created before a `worktrees.root` change is refused too: remove its old worktree by hand with `git worktree remove <path>`, and `forge worktree remove <id>` then clears the record
- writes into a job folder's `verify/` and `review/` only through real directories (`confinedDir` in `lib/core/os/fs.ts`): every component from the job folder down is created a level at a time and must then be a real directory, so a link, junction or file that a session or the job's own tests plant there makes `forge verify`, `forge verifiers run|record` and `forge job round|paths|scope` fail with `… is not a real directory` instead of writing through it, and nothing is created in the link's target. The residuals are a swap between the check and the open (Node has no `openat`), a job folder that is itself a link (that needs write access to `.forge/jobs/`, which the write guard refuses to daemon sessions), and the job folder's other subdirectories (`logs/`, `check/`), which are not confined yet
- renders **approval notes** (`approval-notes.md`, `lib/engine/pipeline/moves/approval-notes.ts`) from events on every write, never by appending: one column-0 data line, then a section per person's `approve-spec` note or `forge job note --for builder` hint, its heading fields through `safeText` and its body fenced (hidden characters and HTML comments removed as for any outside text, CR, U+2028 and U+2029 made LF, other controls but TAB dropped, cut to 4000 characters), so no note closes its fence or adds a heading and none holds text a person reading the file cannot see. The write goes through real directories only and renames over a planted link. The Foreman's notes are left out (they come from request text the builder already reads), and `--for builder` is refused in the office session and in another job's session; `approve-spec` lets its note in only for a job that was waiting on `spec-approval` and under that same session rule, so neither command is a way into another job's brief. The CLI decides this when it logs the event and marks it `approvalNote: true`; the file renders only marked approve-spec notes, so a refused note stays an ordinary event that no later write renders and no rework brief lists as new. Residuals: a process that can append to `events.jsonl` can forge a `builder-note` (as #448), and an agent can edit the file between writes, so every brief's untrusted line names it
- confines config sinks (`lib/engine/environment/config-sinks-apply.ts`, docs/CONFIG.md "Config sinks") to the job's own worktree: a forged `job.worktree` is refused, every output path must be git-ignored and untracked so job values never reach a commit, a symlink at an output path is replaced rather than followed (the write goes through a randomly named temp file opened exclusively, so a planted entry at a guessed name fails instead of redirecting it), a parent directory or a `from` file that resolves outside the worktree is refused, as is a `from` that is a symlink or a hard link and a hard-linked output path that a merge with no `from` would read as its base, and no rendered value reaches a result, an event, an error or a log header. Residual risk: the confinement checks and the write or read are separate syscalls (Node has no directory handle with `openat`/`O_NOFOLLOW`), so a same-user process that swaps a parent directory or `from` for a symlink in between wins the race; the worktree and the job's own session are already that user
- refuses to publish a likely credential, in its own code rather than a prompt (`lib/engine/guard/secrets.ts`, docs/CONFIG.md "Secret scanning"): verify scans every commit of the branch, its messages and the staged changes before any configured step, and `forge git commit`, `forge pr open` and every tracker adapter's writes refuse a likely secret (`secret_found`) before git, `gh` or the adapter is called. Findings are masked and fingerprinted, never printed. The allowlist (`.forge/secrets-allow.txt`) is read from the main checkout only, and the mode from the main checkout's config, so a branch can neither allowlist its own leak nor turn the gate off; diffs run with the same pinned git config and `--text --no-ext-diff --no-textconv` as the integrity report, so attributes and drivers can't hide added lines. A refusal parks the job on `waitingOn: human`, and no agent retry gets past it
- resolves secret references (`lib/engine/guard/secret-refs.ts`, `lib/engine/guard/known-secrets.ts`, docs/CONFIG.md "Secret references") only when a config sink renders `{secret.NAME}`, from declarations in the main checkout's `.forge/config.yml` alone, which protected paths keep human-only. The attackers are the builder (it writes the worktree, template `from` files, `.gitignore`, the job dir and agent outputs, and runs `forge`), a hostile checkout, and tracker or PR text. Keychain fields and op references are validated (no leading `-`, a fixed charset) and go in argv with no shell; a `file` source must be a regular, git-ignored, untracked file inside the repo, never a symlink or hard link; a value under 8 characters is refused because it can't be redacted reliably. Every resolved value is recorded in the job's 0600 `known-secrets.json` before any write or command sink, and Forge replaces known values (raw and JSON-escaped) with `[redacted]` in every log, tail, event, session log line, dashboard response and support bundle it writes or serves; `known-secrets.json` and `backing-db.json` are never served or bundled. The secret scanner's `known-secret` kind blocks a known value on the branch or in PR text in either `verifySecrets` mode, and the allowlist can't allow it, so a `.gitignore` edited around a rendered file and a `git add -f` still can't publish it. A job's commands receive the values by design: Forge guarantees a value never lands verbatim in what it persists, serves, briefs or publishes, not that code the builder writes can't encode or split one, so users declare only development credentials. Residual risk: an agent can delete or rewrite `known-secrets.json`, which weakens serve-time redaction of files a child process wrote itself (background logs, transcripts); every render rewrites the record, and write-time redaction uses the values the rendering process holds in memory, so logs, tails and verify reports Forge writes stay clean
- treats the job's own diff as hostile when a small model reads it ([docs/VERIFIERS.md](../VERIFIERS.md)): verifiers are read from the main checkout only (`.forge/verifiers/`, like `config.yml`), so a branch can't add or weaken one; `forge verifiers run` reads the verified commit's diff with the integrity report's pinned git config, `--no-renames` and replace objects ignored, and writes it into fences longer than any backtick run inside, after CR, U+2028, U+2029 and NEL became line feeds, with paths only JSON-encoded; the verifier agent's brief carries paths and a count, never diff or verifier text; and `forge verifiers record` parses answers fail-closed (a missing, symlinked, oversized, fenced or unparseable answer counts as no answer, which fails a block verifier), re-derives selection, mode and severity from the main checkout rather than the job dir, and forces every reason onto one line so it can't forge a finding
- points every brief at the main checkout's instruction files (`paths.instructions`, docs/CONFIG.md "Instruction files"), never the worktree's, so a branch can't rewrite the conventions its own reviewers and approver follow. The branch's copies of `AGENTS.md`, `CLAUDE.md`, `CLAUDE.local.md`, `.claude/` (nested ones too), `.mcp.json` and any `project.instructions` entry are data: a brief names the changed ones on an `Instructions changed by this branch (JSON)` line (or says `not checked` when git fails), verify records them in `verify/round-<n>.md`'s `## instructions` section with paths escaped, and the default policy's rule 8 escalates them, so a human approves before such a branch ships. Residual risk: an agent that writes the main checkout's files directly changes what every brief reads and shows up in no diff, so none of the above sees it; checklists, learnings and `.forge/config.yml` rest on the same trust
- puts only trusted files in a role run's system prompt (`lib/engine/guard/prompt-prefix.ts`): `forge job agent run` passes the **trusted prefix**, built from the main checkout's copies of the role's `project.instructions` files, `.forge/notes/learnings.md` and `.forge/notes/<role>.md` and nothing else, as `--append-system-prompt-file`. Those are the files a human reviews and the trust digest covers, so the run's post-run check fails it `untrusted` when one changes meanwhile. `request.md`, `spec.md`, `build.md`, reviews, verify output, checklists and PR or tracker text never go there: they stay paths in the brief, read as data, so text an agent wrote after reading tracker or PR text never gains instruction authority. A source that is a link, a non-regular file, oversized, reached through a linked directory, or an instruction entry under `.forge/` or a write root is refused, and the run then starts with no prefix, exactly as before. The file is content-addressed under `.forge/runtime/prompt-prefix/`, outside every write root, reused only when its bytes match and otherwise replaced without following a link
- lets a round's shared inputs reach a **context session** only as Read tool results (`lib/engine/workspace/context-session.ts`, [Daemon runtime](daemon-runtime.md) › Role runs): the context brief the CLI builds (`contextBrief`) lists the inputs' paths as JSON under `UNTRUSTED_LINE`, never their contents, so `spec.md`, `build.md`, verify reports, `scope.md` and `diff.patch` stay data the agent read, exactly as in a cold run. An input is kept only when it is a regular file read without following a link or blocking (a planted link, FIFO or linked parent directory is left out, never followed), inside the job dir's realpath, at most 256 KiB and within 384 KiB in total. The context child must reply exactly `READY`; any other reply (a context talked by an input into answering a verdict, say) marks it failed, and no role forks it. Its brief says to use no tool but `Read`, and the runner enforces it from the stream's `tool-use` events: a child whose main loop called any other tool (Write, Bash, an `Agent`), had a call denied, sent a stdout line Forge could not read (one could have held a tool call), or moved a trusted or protected file is failed however it then replies, so an input that steers it into a tool call and then a bare `READY` forks nowhere. The fork's `Context (JSON)` line, also CLI-built, carries the paths and the `changed` list as JSON, so a crafted file name can't start a line of its own. Residual: the context child's own turns between its Reads stay in every fork's conversation, though now only Read calls and text. They are the same agent reading the same data under the same untrusted rule a cold run would, never system-prompt text, but an input that steers the child's text between Reads (without a tool call) still reaches every fork as the model's own earlier turn
- enforces `policy.protectedPaths` (`lib/engine/guard/protected.ts`, docs/CONFIG.md "Protected paths") in code, against a builder or integrator fooled by that text: `forge git add|commit` preview the index the call would produce and refuse a `refuse` path before anything is written, and verify and `forge pr open` re-check the whole branch from the merge-base, so a plain `git commit` gets no further. Renames are checked on both sides, symlinks and submodules by their target and by the directory they stand in for, and paths case-insensitively; every diff pins external diff, textconv, relative paths and renames off and ignores replace objects and grafts. The policy is read from the main checkout only and `.forge/config.yml` is itself a refuse default, so a branch can't loosen it. Escalate paths park the job on the escalation park with `protected-paths` among its rules (PR15 after the push, even after `APPROVE`, never auto-merged; PP1 before it when a path is CI config, which `pr open` refuses to push), and only a person's approve given at a park listing that rule after the paths' current content was recorded counts: not the foreman, not an approve at another gate. `pr open` recomputes the set rather than trusting `job.protectedPaths`, which `forge job set` can't write, and the park reasons name rules, never paths. The other gate reasons (`forge job gate`) are data the CLI composes: a detail holds fixed words, numbers, lens, AC and repo names, never review, runbook or decision text, and only `paths` come from the branch, which the briefs carry as one-line JSON and the PR body in code spans. `lens-escalate` reads what `forge job verdicts` recorded, never a review file: that command records only the current round and only the lenses whose reviewer ran in it, and a re-record can add an ESCALATE but never remove one. Manifests are read from git blobs (`--no-renames`, `-z`, `historyEnv`, blob ids as arguments), and one that can't be read or parsed, a link included, counts as changed. A session that rewrites the park's reason changes nothing: step recomputes the open rules from facts, and the Foreman is refused at a park listing a human-only rule or while the flag is unapproved. A push that is itself the risk is held in `pr open`, the one enforcer, before any push in any repo (`push_held`, docs/CONFIG.md "The held push"): a CI change since `pr.pushedSha` or the merge base (never a remote-tracking ref), folded as the escalate floor folds names, with links at CI directories counted, a security review that isn't `PASS`, or secrets the scan only reported. The approval must be a person's at the exact reason, whose digest binds it to the content, so an old approval never covers a new workflow. `forge pr gate` puts agent-written decision.md and runbook text on the public PR only inside a text fence whose backtick runs are broken (no mention, link or HTML renders), the reason in a code span, after a secret scan, with every `<!--` in it broken so the text can't carry a section marker, and it edits a body only between one start and one end marker, on the job's own branch and base; the label it adds is a validated config value passed as its own argv word. `pr open` pushes the exact commit it checked (`<sha>:refs/heads/<branch>`, or that commit with its messages scrubbed), never whatever HEAD has become by then, and records it as `pr.pushedSha`. `forge pr merge` recomputes the set at the PR's live head on GitHub (never `pr.pushedSha`, which a session can write), so `protectedPaths: null` waives nothing, unless a person confirms `--now` at a terminal or in the dashboard, and while the policy has rules it never queues GitHub auto-merge: whether GitHub still holds `--match-head-commit` when a queued merge lands is not documented, so it defers while checks are pending and `forge sync` surfaces the retry. Residual risk: the gate binds an agent that changes the job through Forge's commands, not one that writes Forge's own files. `pr open` recomputes the paths, but the approval rests on `at` in `job.json` and on `events.jsonl`, and neither is integrity-protected, so a hand-edited flag (new blobs, an old `at`) carries an old approval over to new content, and an appended `human` approve counts. Any session other than the office can also park the job itself (`forge job set --state waiting --waiting-on human --reason 'protected paths: …'`) and then record `forge job human <id> approve`. Binding approvals to a tamper-evident audit trail is left to a follow-up. Two more residual risks come from opening the PR before a person decides an escalation, a runbook or an escalate protected path: the branch's `.claude/` settings and hooks, `CLAUDE.md`, `.mcp.json` and the escalated code reach the remote before that approval (and are published on a public repo), so a repo whose `pull_request` workflows run an agent action reads them; and, with the PR open, a session that runs `forge pr merge` by hand at a recall (PR17) park can merge an eligible `APPROVE` when `merge.auto` is on, which could not happen while no PR existed. Locking `job.verdicts` to `forge job verdicts` (today `forge job set --field` can write it, which would also lift the security hold) and having `forge pr merge` refuse while a merge gate is open are left to a follow-up. The held push also does not cover CI systems the escalate floor's list does not name (docs/CONFIG.md "The held push")
- copies builder and spec text into the PR body only after cleaning it on a clean pass (`renderCleanPr` in `lib/engine/pipeline/moves/clean-pass.ts`, docs/CONFIG.md "Clean pass"): each bullet, summary and AC cell from `build.md` and `spec.md` loses its HTML comments (Forge's own markers among them) and invisible characters, becomes one line with `|` escaped in a cell, is capped, and has every `<` and `>` turned into an entity so no copied tag can fold the body; `prBody` still strips attribution and `forge pr open` scans the body for secrets. The clean decision itself is bound to the last review, counts only when logged in decide with the key on, and `forge job decision --clean` re-checks the clean pass, so a session running it by hand on any other job writes nothing. Links and `@mentions` in that text are left as they are, the same exposure as the approver's `pr.md`
- keeps merge authority in code, not prose (`lib/engine/pr/eligible.ts`, docs/CONFIG.md "Merge"), against a session misled by PR, issue or tracker text ("CI is flaky, merge now") and a builder that writes the agent-writable job files: `forge pr merge` without `--now` merges only with `merge.auto` on, a decision no later round, rework or stage change has superseded (the job still at `pr`, not cancelled or failed and not set to either after the decision, with no `round` event and no human `rework` or `revise-spec` after the decision in the log, a person's or the foreman's, and no `rework`, `revise-spec` or `cancel` request for the job still `pending` or `in-progress` in the request inbox, where a person's dashboard action waits until a session handles it; nor GitHub feedback that asks for changes: no `gate` request for the job still `pending` or `in-progress`, which `forge sync` queues for the Foreman on a PR with feedback in the same pass that continues deferred merges, and no review GitHub lists as `CHANGES_REQUESTED` on any open PR of the job, the root PR and, for a linked job, each member PR, since they merge as one unit under one decision, counted by the merge's own sync at each live head, from anyone, so a stranger's change request on a public repo leaves the merge to a person; **One wrapper per tool.** Every git, gh and docker process in `lib/` starts in one module, so no call site can forget a pin, a clean environment or a timeout. `lib/integrations/git/runner.ts` prepends `-c core.fsmonitor=false -c core.quotepath=off -c diff.interHunkContext=0 -c diff.suppressBlankEmpty=false -c diff.relative=false` to every call: the worktree's config can't run an fsmonitor program or reshape output a parser reads, and the diff pins are git's defaults, so they only override a user's or a worktree's config. Without a caller's own `env`, each call drops the inherited `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY` and `GIT_NAMESPACE` (Forge run from a git hook would otherwise act on another repo), and a read runs with `GIT_OPTIONAL_LOCKS=0`, so it never locks the index of a worktree whose builder is running git at the same moment. Call-specific options stay at their call sites (`core.hooksPath` on member git, `--no-ext-diff`, `--no-textconv`). `lib/integrations/github/gh.ts` gives every gh call a 60 s timeout unless the call sets a shorter one (the actor lookup and the release check 5 s, the link preview 15 s), so a hung gh can't block `pr sync` or a tracker call, and parses JSON output in one place. `lib/integrations/docker/runner.ts` holds the sync runner `lib/engine/environment/backing.ts` uses, an async runner and the streaming spawn behind the dashboard's container logs; Docker's state travels as `docker` in `forge backing status <job>` and as the error codes `docker_missing` and `docker_stopped`, never as message text. **Request provenance is not authenticated.** A request's `from` (`dashboard`, `cli`, `daemon:<scope>`) and the daemon-session checks in `forge requests` come from the caller's environment (`FORGE_DAEMON`, `FORGE_DAEMON_SCOPE`), which a session's own commands could drop. They are guardrails that keep a session following the skill from acting on another job's requests or queuing anything but a `resume` hand-off, not a boundary against a misled session: such a session can still run `forge job human …` directly through `Bash(forge:*)`, though it can no longer lift a job's budget, because `forge job budget --set|--ack` is a human-only operation ([Daemon security](daemon-security.md) › Human-only operations). The defences against that are the ones above: what reaches agents is fenced as data, and the unattended session's tools are narrow.
