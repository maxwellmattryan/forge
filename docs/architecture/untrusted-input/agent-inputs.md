# Untrusted input › Agent inputs

Part of [Untrusted input](../untrusted-input.md).

Forge:
- renders **approval notes** (`approval-notes.md`, `lib/engine/pipeline/moves/approval-notes.ts`) from events on every write, never by appending: one column-0 data line, then a section per person's `approve-spec` note or `forge job note --for builder` hint, its heading fields through `safeText` and its body fenced (hidden characters and HTML comments removed as for any outside text, CR, U+2028 and U+2029 made LF, other controls but TAB dropped, cut to 4000 characters), so no note closes its fence or adds a heading and none holds text a person reading the file cannot see. The write goes through real directories only and renames over a planted link
  - The Foreman's notes are left out (they come from request text the builder already reads), and `--for builder` is refused in the office (scope `_office`) and in another job's session; `approve-spec` lets its note in only for a job that was waiting on `spec-approval` and under that same session rule, so neither command is a way into another job's brief. The CLI decides this when it logs the event and marks it `approvalNote: true`; the file renders only marked approve-spec notes, so a refused note stays an ordinary event that no later write renders and no rework brief lists as new. Residuals: a process that can append to `events.jsonl` can forge a `builder-note` (as #448), and an agent can edit the file between writes, so every brief's untrusted line names it
- applies a job request (`forge job apply`, `lib/engine/pipeline/moves/request-table.ts`) only by the human-command table and in-process: a decision request is recorded only when its `from` is `dashboard` or `cli` (a person), so one queued from a daemon scope or by Forge itself is acked `rejected`, and a `resume` records the dashboard's buttons (Steps done, Unblocked, Leave for later, Retry) only from a person too, since a resume from Forge, `sync` or a session would otherwise pass the infra gate, defer the conflicts the Foreman approved a fix for, or retry a failed job
  - a request for another job, from another job's scope, the inbox, the office or a chat, or with an id outside the request grammar is refused before anything is written; its text never reaches argv, and reaches `feedback.md` or the `questions.md` answer only fenced (`fenceImport`: Forge's provenance line, then every line quoted, after `visibleText` and a split on every CommonMark line break), written through real directories with a rename over a planted link; an `args.link` goes through `forge job human`'s `checkIssueRef`. The code driver passes `forge job apply` only the job id and the request id
- turns plan.md's `## Jobs` into child jobs (`forge job split`, `lib/engine/pipeline/moves/split.ts`) as planner-written data: each title becomes one line (`oneLineTitle`, at most 200 characters), each scope is fenced in the child's `request.md` under Forge's own line naming the parent by its repo-relative paths (the body becomes the child's tracker issue, so it carries no machine path), a split is refused while the planner runs and from a daemon session of any other job, and the `## External` items reach the parent's `runbook.md` only quoted, and tracker titles and bodies go to the adapter as values. plan.md is read without following a link
- treats the job's own diff as hostile when a small model reads it ([docs/VERIFIERS.md](../../VERIFIERS.md)): verifiers are read from the main checkout only (`.forge/verifiers/`, like `config.yml`), so a branch can't add or weaken one; `forge verifiers run` reads the verified commit's diff with the integrity report's pinned git config, `--no-renames` and replace objects ignored, and writes it into fences longer than any backtick run inside, after CR, U+2028, U+2029 and NEL became line feeds, with paths only JSON-encoded; the verifier agent's brief carries paths and a count, never diff or verifier text
  - `forge verifiers record` parses answers fail-closed (a missing, symlinked, oversized, fenced or unparseable answer counts as no answer, which fails a block verifier), re-derives selection, mode and severity from the main checkout rather than the job dir, and forces every reason onto one line so it can't forge a finding
- points every brief at the main checkout's instruction files (`paths.instructions`, docs/CONFIG.md "Instruction files"), never the worktree's, so a branch can't rewrite the conventions its own reviewers and approver follow. The branch's copies of `AGENTS.md`, `CLAUDE.md`, `CLAUDE.local.md`, `.claude/` (nested ones too), `.mcp.json` and any `project.instructions` entry are data: a brief names the changed ones on an `Instructions changed by this branch (JSON)` line (or says `not checked` when git fails), verify records them in `verify/round-<n>.md`'s `## instructions` section with paths escaped, and the default policy's rule 8 escalates them, so a human approves before such a branch ships
  - Residual risk: an agent that writes the main checkout's files directly changes what every brief reads and shows up in no diff, so none of the above sees it; checklists, learnings and `.forge/config.yml` rest on the same trust
- puts only trusted files in a role run's system prompt (`lib/engine/guard/prompt-prefix.ts`): `forge job agent run` passes the **trusted prefix**, built from the main checkout's copies of the role's `project.instructions` files, `.forge/notes/learnings.md` and `.forge/notes/<role>.md` and nothing else, as `--append-system-prompt-file`. Those are the files a human reviews and the trust digest covers, so the run's post-run check fails it `untrusted` when one changes meanwhile
  - `request.md`, `spec.md`, `build.md`, reviews, verify output, checklists and PR or tracker text never go there: they stay paths in the brief, read as data, so text an agent wrote after reading tracker or PR text never gains instruction authority. A source that is a link, a non-regular file, oversized, reached through a linked directory, or an instruction entry under `.forge/` or a write root is refused, and the run then starts with no prefix, exactly as before. The file is content-addressed under `.forge/runtime/prompt-prefix/`, outside every write root, reused only when its bytes match and otherwise replaced without following a link
- lets a round's shared inputs reach a **context session** only as Read tool results (`lib/engine/workspace/context-session.ts`, [Daemon runtime](../daemon-runtime/role-runs.md#role-runs) › Role runs): the context brief the CLI builds (`contextBrief`) lists the inputs' paths as JSON under `UNTRUSTED_LINE`, never their contents, so `spec.md`, `build.md`, verify reports, `scope.md` and `diff.patch` stay data the agent read, exactly as in a cold run. An input is kept only when it is a regular file read without following a link or blocking (a planted link, FIFO or linked parent directory is left out, never followed), inside the job dir's realpath, at most 256 KiB and within 384 KiB in total
  - The context child must reply exactly `READY`; any other reply (a context talked by an input into answering a verdict, say) marks it failed, and no role forks it. Its brief says to use no tool but `Read`, and the runner enforces it from the stream's `tool-use` events: a child whose main loop called any other tool (Write, Bash, an `Agent`), had a call denied, sent a stdout line Forge could not read (one could have held a tool call), or moved a trusted or protected file is failed however it then replies, so an input that steers it into a tool call and then a bare `READY` forks nowhere. The fork's `Context (JSON)` line, also CLI-built, carries the paths and the `changed` list as JSON, so a crafted file name can't start a line of its own
  - Residual: the context child's own turns between its Reads stay in every fork's conversation, though now only Read calls and text. They are the same agent reading the same data under the same untrusted rule a cold run would, never system-prompt text, but an input that steers the child's text between Reads (without a tool call) still reaches every fork as the model's own earlier turn
- copies builder and spec text into the PR body only after cleaning it on a clean pass (`renderCleanPr` in `lib/engine/pipeline/moves/clean-pass.ts`, docs/CONFIG.md "Clean pass"): each bullet, summary and AC cell from `build.md` and `spec.md` loses its HTML comments (Forge's own markers among them) and invisible characters, becomes one line with `|` escaped in a cell, is capped, and has every `<` and `>` turned into an entity so no copied tag can fold the body; `prBody` still strips attribution and `forge pr open` scans the body for secrets. The clean decision itself is bound to the last review, counts only when logged in decide with the key on, and `forge job decision --clean` re-checks the clean pass, so a session running it by hand on any other job writes nothing. Links and `@mentions` in that text are left as they are, the same exposure as the approver's `pr.md`
