# Untrusted input › Merge authority

Part of [Untrusted input](../untrusted-input.md).

Forge:
- enforces `policy.protectedPaths` (`lib/engine/guard/protected.ts`, docs/CONFIG.md "Protected paths") in code, against a builder or integrator fooled by that text: `forge git add|commit` preview the index the call would produce and refuse a `refuse` path before anything is written, and verify and `forge pr open` re-check the whole branch from the merge-base, so a plain `git commit` gets no further
  - Renames are checked on both sides, symlinks and submodules by their target and by the directory they stand in for, and paths case-insensitively; every diff pins external diff, textconv, relative paths and renames off and ignores replace objects and grafts. The policy is read from the main checkout only and `.forge/config.yml` is itself a refuse default, so a branch can't loosen it
  - Escalate paths park the job on the escalation park with `protected-paths` among its rules (PR15 after the push, even after `APPROVE`, never auto-merged; PP1 before it when a path is CI config, which `pr open` refuses to push), and only a person's approve given at a park listing that rule after the paths' current content was recorded counts: not the foreman, not an approve at another gate. `pr open` recomputes the set rather than trusting `job.protectedPaths`, which `forge job set` can't write, and the park reasons name rules, never paths
  - The other gate reasons (`forge job gate`) are data the CLI composes: a detail holds fixed words, numbers, lens, AC and repo names, never review, runbook or decision text, and only `paths` come from the branch, which the briefs carry as one-line JSON and the PR body in code spans. `lens-escalate` reads what `forge job verdicts` recorded, never a review file: that command records only the current round and only the lenses whose reviewer ran in it, and a re-record can add an ESCALATE but never remove one
  - Manifests are read from git blobs (`--no-renames`, `-z`, `historyEnv`, blob ids as arguments), and one that can't be read or parsed, a link included, counts as changed. A session that rewrites the park's reason changes nothing: step recomputes the open rules from facts, and the Foreman is refused at a park listing a human-only rule or while the flag is unapproved
  - A push that is itself the risk is held in `pr open`, the one enforcer, before any push in any repo (`push_held`, docs/CONFIG.md "The held push"): a CI change since `pr.pushedSha` or the merge base (never a remote-tracking ref), folded as the escalate floor folds names, with links at CI directories counted, a security review that isn't `PASS`, or secrets the scan only reported. The approval must be a person's at the exact reason, whose digest binds it to the content, so an old approval never covers a new workflow
  - `forge pr gate` puts agent-written decision.md and runbook text on the public PR only inside a text fence whose backtick runs are broken (no mention, link or HTML renders), the reason in a code span, after a secret scan, with every `<!--` in it broken so the text can't carry a section marker, and it edits a body only between one start and one end marker, on the job's own branch and base; the label it adds is a validated config value passed as its own argv word
  - `pr open` pushes the exact commit it checked (`<sha>:refs/heads/<branch>`, or that commit with its messages scrubbed), never whatever HEAD has become by then, and records it as `pr.pushedSha`. `forge pr merge` recomputes the set at the PR's live head on GitHub (never `pr.pushedSha`, which a session can write), so `protectedPaths: null` waives nothing, unless a person confirms `--now` at a terminal or in the dashboard, and while the policy has rules it never queues GitHub auto-merge: whether GitHub still holds `--match-head-commit` when a queued merge lands is not documented, so it defers while checks are pending and `forge sync` surfaces the retry
  - Residual risk: the gate binds an agent that changes the job through Forge's commands, not one that writes Forge's own files. `pr open` recomputes the paths, but the approval rests on `at` in `job.json` and on `events.jsonl`, and neither is integrity-protected, so a hand-edited flag (new blobs, an old `at`) carries an old approval over to new content, and an appended `human` approve counts. Any session other than the office can also park the job itself (`forge job set --state waiting --waiting-on human --reason 'protected paths: …'`) and then record `forge job human <id> approve`. Binding approvals to a tamper-evident audit trail is left to a follow-up
  - Two more residual risks come from opening the PR before a person decides an escalation, a runbook or an escalate protected path: the branch's `.claude/` settings and hooks, `CLAUDE.md`, `.mcp.json` and the escalated code reach the remote before that approval (and are published on a public repo), so a repo whose `pull_request` workflows run an agent action reads them; and, with the PR open, a session that runs `forge pr merge` by hand at a recall (PR17) park can merge an eligible `APPROVE` when `merge.auto` is on, which could not happen while no PR existed
  - Locking `job.verdicts` to `forge job verdicts` (today `forge job set --field` can write it, which would also lift the security hold) and having `forge pr merge` refuse while a merge gate is open are left to a follow-up. The held push also does not cover CI systems the escalate floor's list does not name (docs/CONFIG.md "The held push")
- keeps merge authority in code, not prose (`lib/engine/pr/eligible.ts`, docs/CONFIG.md "Merge"), against a session misled by PR, issue or tracker text ("CI is flaky, merge now") and a builder that writes the agent-writable job files: `forge pr merge` without `--now` merges only with
  - `merge.auto` on
  - a decision no later round, rework or stage change has superseded:
    - the job still at `pr`, not cancelled or failed and not set to either after the decision, with no `round` event and no human `rework` or `revise-spec` after the decision in the log, a person's or the foreman's, and no `rework`, `revise-spec` or `cancel` request for the job still `pending` or `in-progress` in the request inbox, where a person's dashboard action waits until a session handles it;
    - nor GitHub feedback that asks for changes: no `gate` request for the job still `pending` or `in-progress`, which `forge sync` queues for the Foreman on a PR with feedback in the same pass that continues deferred merges, and no review GitHub lists as `CHANGES_REQUESTED` on any open PR of the job, the root PR and, for a linked job, each member PR, since they merge as one unit under one decision, counted by the merge's own sync at each live head, from anyone, so a stranger's change request on a public repo leaves the merge to a person; a PR GitHub reports merged or closed counts none, because a person merged or closed it past that review; a forged request or a stranger's review can only block a merge
  - the last recorded `decision` event an auto-merge eligible `APPROVE` bound to the PR's live head (or that head plus clean merges of the base: no rework, rebase, human push or merge carrying extra changes) on a PR that still targets the job's base on GitHub
  - protected paths recomputed at that head and approved
  - and nothing on the escalate floor (`.forge/`, Claude Code's own control files such as `.claude/` and `CLAUDE.md`, instruction files, test, build and CI config, each name folded the way macOS and Windows open it, so `agentſ.md` and `Jest.config.js` count).
  - Every check against the base uses the base branch fetched from the push remote at merge time into a private ref, never `<remote>/<base>` in the clone, which a worktree can move, and a base that can't be fetched refuses. `forge job decision` records once per approver run (an agent's end time moves only when a running agent ends, and `forge job set` can't write `agents`), so a `decision.md` edited afterwards changes nothing, and step's PR4 never reads it
  - Under `FORGE_DAEMON=1`, `forge pr merge` refuses `--now` in every scope, another job's id, the inbox, the office and a broken scope, before any `gh` call, and `forge sync` continues deferred merges itself through the same checks, only a deferral logged after the decision on a job whose decision still stands, so a rework a person asked for is not merged around once Forge has it, in the log or in the inbox, and neither is PR feedback the Foreman has yet to decide or a change request on GitHub. Every `pr-merged` records `actor`, and `scope` in a daemon session, so a merge one session ran for another job can be traced. A direct merge waits until the head has settled for 5 minutes, so a rollup read before every check registered can't pass
  - The CI decision also needs the PR's required checks (`lib/engine/pr/required.ts`), each bound to its source: `merge.requiredChecks` for the root PR, else the base branch's protection, read through `gh api` with the base checked against `SAFE_REF` (no `..`) and URL-encoded and the slug against `SLUG_RE` before any call, and never stored. A required check that has not reported is pending however green the rollup is; a commit status, which anyone with push access can post under any name, never satisfies a name without a `creator` binding and never matches a check-run binding; a same-name check from another source (a workflow the PR adds with the same job name) is `foreign` when the requirement is bound and `ambiguous` (refused) when it is not; a failing or pending duplicate from any source blocks; and `SKIPPED` or `NEUTRAL` refuses
  - `merge.requiredChecks` is locked in the settings, so neither `forge config set` nor `/api/config` can empty it, and a support bundle counts its entries without printing them (a creator login can be a person's). A list that fails validation is never partly read: the root PR's merge refuses (`required.state: failing`, the note naming the first problem), as an invalid `policy.protectedPaths` does, so a typo cannot loosen the gate
  - Residual risks of the binding:
    - a `workflow` binding trusts the PR's own copy of that file, and only the default `.github/workflows/**` escalate rule in `policy.protectedPaths` (and the escalate floor's CI config) keeps a PR from rewriting it unreviewed;
    - protection bound only by an app id can't tell two workflows of that app apart beyond the `ambiguous` rule;
    - an unbound or `app`-bound requirement is also met by a check run that any Actions workflow creates through the Checks API on the PR's head (a `workflow_dispatch` workflow on another branch with `checks: write`, say), which is outside the PR's diff, so the escalate floor does not see it, and which works only while the real check never registers (a `paths` filter, a disabled workflow), since a failing, unfinished or second-source duplicate blocks, so `merge.requiredChecks` should bind `workflow` (docs/CONFIG.md "Merge");
    - a session that makes the protection read fail gets the rollup-only decision of before (`required.source: unavailable`), no worse than before, and with `merge.requiredChecks` set no protection read happens.
  - Residual risks:
    - a merge already queued with GitHub `--auto` (`pr-auto-merge`, which `forge pr merge` queues only when `policy.protectedPaths` has no rules, the required checks do not come from `merge.requiredChecks` (GitHub's protection does not know them, so those merges defer) and GitHub reports `BLOCKED` or `BEHIND` while checks are pending) is never disabled by a later rework or cancel, and whether GitHub still holds `--match-head-commit` when it lands is not documented, so a person who reworks or cancels a job with a queued auto-merge disables it on GitHub (`gh pr merge --disable-auto`);
    - review threads and comments with no change request hold a merge only through their `pr-feedback` gate request, so only on the root PR (a member PR's threads and comments reach neither `pr-feedback.md` nor that gate), only where the Foreman decides `pr-feedback`, and only until it acks that request;
    - a member PR whose sync fails in a pass keeps the change-request count its last sync recorded, and while that member waits unread the walk can still merge the PRs that do not depend on it;
    - a process that can append to `events.jsonl`, or that fabricates an approver run (`forge job agent start` and `end` with an edited `decision.md` in between), can forge an eligible decision (#448), a commit made between the approver's end and `forge job decision` is bound as approved (the record carries the worktree's `HEAD` at that moment), and branch code `forge verify` runs without `FORGE_DAEMON` can't pass `--now`, which is a human-only operation confirmed at a terminal or from the dashboard ([Daemon security › Human-only operations](../daemon-security/human-only-operations.md), with its residuals);
    - branch protection's required reviews and status checks stay the backstop no session can change
- re-runs failed checks only on the PR's own head (`rerunRuns` in `lib/engine/pr/ci.ts`, which sync's `ciRerun` and a person's `forge pr rerun` or **Re-run failed checks** share; docs/CONFIG.md "Open PRs"), against whoever controls that head's checks: the PR's workflows, or any Checks API writer in the repo, choose each check's name and `detailsUrl`
  - A rollup entry counts only when it is failing and its `detailsUrl` is exactly `https://github.com/<owner>/<repo>/actions/runs/<id>/job/<id>` (`failingRunsOf` in `lib/integrations/github/pull-requests.ts`: anchored, no query, fragment or trailing segment, a commit status's `targetUrl` never), with both ids digits and no leading zero (`RUN_ID`, checked again in the gh adapter before they reach argv, which never goes through a shell), and in the PR's own repo; at most 20 are read and 5 runs re-run. Every call passes `-R` with the PR's repo, and `gh run view` must show the run on the PR's head and completed, so a crafted URL can't re-run another repo's runs or an unrelated failed run in the same repo, such as a deploy
  - Check names reach the park reason, the event and step's tell only through the `CHECK_NAME` allowlist, and the tell echoes the reason only when it matches `CI_RERUN_REASON`. It runs once per head, with no gate, rework or `resume`, so a check that keeps failing can't make Forge loop
  - A person's re-run (`rerunFailedChecks`) and Fix CI (`fixFailingChecks`, a person's rework) act only on a job parked on `pr-review` at the head the dashboard row showed (`POST /api/jobs/:id/ci` pins it; a re-run also compares the live head), behind the dashboard's default POST guards. Fix CI builds its note and `feedback.md` from the stored `job.pr.failingChecks` names, each checked against `CHECK_NAME` again (job.json is session-writable) and set in backticks, which `CHECK_NAME` excludes, under a data label; no check name travels as request text to a session. Residual risk: a process that can append to `events.jsonl` can forge a `ci-rerun` or `ci-rerun-failed` line, which only suppresses the re-run or a CI rework and leaves the job with a person, as in #448
