# Untrusted input › Secrets and verify

Part of [Untrusted input](../untrusted-input.md).

Forge:
- limits what a misled builder's code sees when verify runs it before review (`lib/engine/guard/command-env.ts`, docs/CONFIG.md "Command environment"): every configured command, in and out of the daemon, gets only an allowlist of Forge's environment plus the names `commandEnv.inherit` lists, under `/bin/sh -c` with no login profile, so it can read `PATH`, `HOME`, the locale, the git pins and the job's own variables, but not `GH_TOKEN`, `AWS_*`, `SSH_AUTH_SOCK`, `DATABASE_URL`, a credential under a name nobody listed, a declared secret's source variable (only its sink's value) or Forge's own `FORGE_DAEMON*` and `FORGE_COMMAND_PATH*`
  - No family or glob passes a credential-like name (`NODE_AUTH_TOKEN` under `NODE_*`), a bare `*` is refused, and relative or empty PATH entries are dropped so the worktree can't plant a binary. It can still read your dotfiles (`~/.aws/credentials`, `~/.config/gh/hosts.yml`, `~/.npmrc`), since `HOME` passes, a name a human put in `inherit` exactly, and everything with `commandEnv.loginShell: true`, which re-sources the profile; `forge release run` keeps its caller's whole environment
- refuses to publish a likely credential, in its own code rather than a prompt (`lib/engine/guard/secrets.ts`, docs/CONFIG.md "Secret scanning"): verify scans every commit of the branch, its messages and the staged changes before any configured step, and `forge git commit`, `forge pr open` and every tracker adapter's writes refuse a likely secret (`secret_found`) before git, `gh` or the adapter is called. Findings are masked and fingerprinted, never printed. The allowlist (`.forge/secrets-allow.txt`) is read from the main checkout only, and the mode from the main checkout's config, so a branch can neither allowlist its own leak nor turn the gate off; diffs run with the same pinned git config and `--text --no-ext-diff --no-textconv` as the integrity report, so attributes and drivers can't hide added lines. A refusal parks the job on `waitingOn: human`, and no agent retry gets past it
- resolves secret references (`lib/engine/guard/secret-refs.ts`, `lib/engine/guard/known-secrets.ts`, docs/CONFIG.md "Secret references") only when a config sink renders `{secret.NAME}`, from declarations in the main checkout's `.forge/config.yml` alone, which protected paths keep human-only. The attackers are the builder (it writes the worktree, template `from` files, `.gitignore`, the job dir and agent outputs, and runs `forge`), a hostile checkout, and tracker or PR text
  - Keychain fields and op references are validated (no leading `-`, a fixed charset) and go in argv with no shell; a `file` source must be a regular, git-ignored, untracked file inside the repo, never a symlink or hard link; a value under 8 characters is refused because it can't be redacted reliably
  - Every resolved value is recorded in the job's 0600 `known-secrets.json` before any write or command sink, and Forge replaces known values (raw and JSON-escaped) with `[redacted]` in every log, tail, event, session log line, dashboard response and support bundle it writes or serves; `known-secrets.json` and `backing-db.json` are never served or bundled. The secret scanner's `known-secret` kind blocks a known value on the branch or in PR text in either `verifySecrets` mode, and the allowlist can't allow it, so a `.gitignore` edited around a rendered file and a `git add -f` still can't publish it
  - A job's commands receive the values by design: Forge guarantees a value never lands verbatim in what it persists, serves, briefs or publishes, not that code the builder writes can't encode or split one, so users declare only development credentials. Residual risk: an agent can delete or rewrite `known-secrets.json`, which weakens serve-time redaction of files a child process wrote itself (background logs, transcripts); every render rewrites the record, and write-time redaction uses the values the rendering process holds in memory, so logs, tails and verify reports Forge writes stay clean
- sends notifications without that text (`lib/office/notify.ts`, docs/CONFIG.md "Notifications"): the webhook and command set is trusted config (`.forge/config.yml`, read-only in Settings and `forge config set`, a protected path, and in the daemon's trust digest), and the payload has a fixed key set whose `reason` is a fixed English string chosen by code. The only free text is the job title, control-stripped and capped at 200 characters; in Slack it sits only in `plain_text` (no mentions or links) and is escaped in the fallback, and the command receives every value through `FORGE_NOTIFY_*` environment variables its `{placeholders}` reference, never interpolated into the shell source. Webhooks refuse redirects, and only a webhook's host is recorded, shown in doctor or sent to the dashboard (`/api/config` masks the path). An agent that runs `forge notify send` or `forge notify test` itself reaches only the targets a human configured, with the same fixed payload
