# Untrusted input › Sessions and services

Part of [Untrusted input](../untrusted-input.md).

Forge:
- limits what an agent fooled by that text can do when nobody is watching: the daemon's default `allowedTools` names only the git/gh subcommands the agents use (no `git -c`, `git rebase --exec`, `git config`, `git log --output` or `gh api`), validation refuses blanket git/gh entries and permission-widening `daemon.command` flags, and the session runs git with hooks and fsmonitor pinned off ([Daemon security › Permissions](../daemon-security/permissions.md))
- keeps the user's own Claude Code setup out of the agents that read that text (["Daemon security"](../daemon-security.md)): default daemon sessions pass `--setting-sources project,local --strict-mcp-config` and role runs `--setting-sources ''`, so neither reaches the user's claude.ai connectors, MCP servers or other plugins' hooks; each role has an explicit tool list, and the one browser Forge passes, to UI roles of a spec with a UI AC only, is limited to the job's loopback dev-server origins
- runs backing services without letting a session steer Docker (`lib/engine/environment/backing.ts`, docs/CONFIG.md "Backing services"): config is read from the main checkout only, and validation keeps every image, name and volume path to a fixed charset with no leading `-`, so nothing reaches `docker` as an option; every call is argv only; env values go through a 0600 `--env-file` in a fresh temp directory that is removed afterwards, and errors carry only the subcommand and a stderr tail, so a value never reaches argv, `ps`, events or results; ports bind to `127.0.0.1` only
  - teardown derives container and volume names from the job id and config, never from the agent-writable `backing.json`, and removes only what is labelled with this checkout's root hash and job, so a forged record or a same-named container of another checkout is never touched. A forged record can at most reserve ports in range (wasting them) or name ports that are ignored and allocated again
- gives each job its own database on a shared Postgres without letting a session reach another job's data (`lib/engine/environment/backing-db.ts`, docs/CONFIG.md "Job databases"): every database and role name is derived from the job id or the template hash, checked against `^[a-z_][a-z0-9_]{0,62}$` and double-quoted, and every SQL statement goes to `psql` on stdin, never in argv; Postgres receives only a SCRAM-SHA-256 verifier, so a password never reaches argv, `ps`, the server log or `pg_authid`
  - the job's password lives only in the 0600 `backing-db.json` and the env of the job's configured commands, and the setup and template-build tails Forge stores are redacted; that record is agent-writable, so it is read without following a symlink, a field that fails its regex is ignored, and teardown drops only the names derived from the job id: the record only picks which configured shared entries teardown visits (each with `database`, plus each it names), and one it names that is not a configured shared entry is skipped
  - each job role has its own login, `CONNECT` on its database is revoked from everyone else, no job role is a member of the `forge_tpl` role that owns a template while it builds (a clone's objects are reassigned to the job's role instead), `CONNECT` on a template is revoked from everyone else from its creation, and a built template belongs to the superuser and takes no connections, and each build ends every `forge_tpl` session on the server before it grants the role its login and again after it takes the login away (a connection migrate or seed left open could otherwise alter a later build's template), so a job cannot reach another job's database or alter the template, mid-build or after; and template build commands run only in the worktree path Forge computes for the job, never `job.worktree`
  - The residual risks: migrate and seed run code from the building job's worktree, and a file they read outside `inputs` can shape a template later jobs with the same hash reuse; and a record that names a configured shared entry that is not Postgres (`redis`, say) makes teardown's psql call there fail, so that job's own teardown reports `ok: false` and keeps the record until the name is removed
