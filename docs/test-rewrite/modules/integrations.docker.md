The runner is reached from lib/engine/environment/backing.ts (`dockerRun`, `dockerStateOf`, `DOCKER_TIMEOUT_MS`), lib/engine/environment/status.ts (`dockerRunAsync` for `docker stats`) and lib/server/start.ts (`dockerSpawn` for `docker logs --follow`). The unit tests of those modules inject an in-memory `DockerRunner`, so the real runner ran only in the integration tests, with `test/fixtures/docker-bin` first on PATH.

## Behaviours
- B1. `dockerRun(args, opts)` runs `docker <args>` with argv only (no shell), always allow-fail, with `timeoutMs` defaulting to `DOCKER_TIMEOUT_MS` (30 000) and `input` on stdin, and returns `run()`'s `{ok, stdout, stderr, status, …}` plus `missing`. A zero exit → `ok: true, status: 0, missing: false`. Old: integration/cli/backing.test.ts › "forge backing up|status|down" (owned by engine/environment)
- B2. A non-zero exit (the daemon down: fake docker answers `Cannot connect to the Docker daemon at unix:///var/run/docker.sock. Is the docker daemon running?`, exit 1) → `ok: false`, `status: 1`, `missing: false`, so `dockerStateOf` → `'stopped'`; through the CLI, `forge backing up|status|stop|down` then exit 5 and say `docker is installed but its daemon is not reachable…`. Old: integration/cli/backing.test.ts › "forge backing up|status|down" (its stopped-daemon part); backing.test.ts › "doctor docker check: missing, stopped, healthy"
- B3. `dockerStateOf(r)`: `r.missing` → `'missing'`; else `r.ok` → `'ok'`; else `'stopped'`. State comes from the result's fields, never from the error text. Old: backing.test.ts › "status finds orphans and shows env names only", "doctor docker check: missing, stopped, healthy" (with an injected runner returning `{ok:false, stderr:'spawnSync docker ENOENT', status:null, missing:true}` → `docker: 'missing'`, error code `docker_missing`, message `^docker not found on PATH`)
- B4. `dockerRunAsync(args, {timeoutMs, maxBuffer})` runs `docker` with `execFile` (argv only, utf8, `maxBuffer` default 2 MiB) without blocking, resolving `{ok, stdout, stderr, status, missing}`: success → `status: 0`; a numeric error code → that `status`; a spawn `ENOENT` → `missing: true`, `status: null`. The environment status reads `docker stats --no-stream --format {{json .}} -- <containers…>` through it, once per poll for every running container. Old: integration/server/environment.test.ts › "project-wide environments" (one `docker stats` call naming the job's and the shared container)
- B5. `dockerSpawn(args)` starts a long-running `docker` child with `stdio: ['ignore','pipe','pipe']`: the server's backing log stream runs `logs --follow --tail 200 -- <container>`, forwards stdout and stderr lines, ends with an `end` frame when docker exits (the container stopped), and kills the child when the client leaves. Old: integration/server/environment.test.ts › "log streams"

## Edge and corner cases
- E1. `docker` not on PATH (a spawn error with no exit status whose stderr says `ENOENT`, not a timeout) → `dockerRun` returns `missing: true`; a timeout (`timedOut`) is never read as missing. Setup: in-process, `process.env.PATH` (or a child's PATH) set to an empty temp dir; `dockerRun(['version'])` → `{ok:false, status:null, missing:true}`; `dockerRunAsync(['version'], {timeoutMs: 5000})` → `missing: true`. A timeout case: the shim with `versionDelayMs` in the state above `timeoutMs` → `missing: false`. Old: none direct (from source; backing.test.ts injects the missing result)
- E2. A failure's error message never carries the argv: `dockerRun` never takes `run()`'s throwing path (always `allowFail`), so passwords in `docker exec -i … psql` input or env-file paths can't reach an error. Setup: the PATH shim with `{"daemon":"down"}`; `dockerRun(['exec','-i','c','psql'], {input:'SECRET'})` returns a result (no throw) whose `stderr` doesn't contain the argv or input. Old: none direct (from source)
- E3. `dockerRunAsync` output past `maxBuffer` → the error result (`ok: false`), never a partial success. Setup: the PATH shim and a container whose `logs` exceed `maxBuffer: 10` with `dockerRunAsync(['logs','c'], {timeoutMs:5000, maxBuffer:10})` → `ok: false`. Old: none (from source)

## Regressions worth keeping
- R1. Docker's state was read from its message text, which differs across versions and locales → `missing` from ENOENT with no status, `stopped` from any other failure. Setup: the in-memory runner from Setup recipes (`missing: true` result, then `state.daemon = 'down'`) through `backingStatus`/`dockerCheck`, or `dockerStateOf` with literals `{missing:true}`, `{ok:true}`, `{ok:false, stderr:'anything'}`. Old: backing.test.ts › "doctor docker check: missing, stopped, healthy"

## Cheapest layer
- `dockerStateOf` is pure: test it in-process with literal results.
- `dockerRun`, `dockerRunAsync`, `dockerSpawn` start a real process: put `test/fixtures/docker-bin` first on PATH (it runs `fake-docker.mjs`'s `main`) with `FAKE_DOCKER_STATE` and `FAKE_DOCKER_LOG` set, in-process (no `bin/forge` needed); for the missing case set PATH to a directory with no `docker` (spawn ENOENT). Mutating `process.env.PATH` means no `describe(…, {concurrency})`; prefer passing a PATH through a child where possible.
- Everything that interprets docker's answers (backing, environment status, the log route) belongs to engine/environment and server and is tested there with an injected runner or the PATH shim.

## Setup recipes
- In-memory fake for callers: `import { emptyState, handle } from 'test/fixtures/fake-docker.mjs'`; a runner `(args, opts) => { const r = handle(state, args, opts?.input); return { ok: r.status === 0, ...r }; }`; `state.daemon = 'down'` makes every call fail with the daemon message; a missing binary is `{ok:false, stdout:'', stderr:'spawnSync docker ENOENT', status:null, missing:true}`.
- PATH shim for the real runner: `PATH = <repo>/test/fixtures/docker-bin + path.delimiter + PATH`, `FAKE_DOCKER_STATE = <tmp>/state.json` (created on first call; `{daemon:'up', version:'27.1.1', containers:{}, volumes:{}, …}` from `emptyState()`), `FAKE_DOCKER_LOG = <tmp>/argv.log` (one JSON argv per line), `FAKE_DOCKER_PIDS = <tmp>/pids` (a `logs --follow` child writes its pid). `docker version` → `27.1.1\n`, exit 0; with `{"daemon":"down"}` in the state file → exit 1. `logs --follow <name>` keeps running until the container's `running` is false or it is removed. A container for logs/stats: write `containers: {<name>: {running:true, labels:{}, logs:['line'], errLogs:['warn']}}` into the state file.

## Dropped on purpose
- The backing, environment and server tests that use the fake docker belong to the engine/environment and server inventories; only their runner-level facts (B1–B5) are kept here.
